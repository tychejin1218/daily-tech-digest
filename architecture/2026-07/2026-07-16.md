### Semantic Cache — "같은 질문을 두 번 계산하지 않는다"는 원칙이 벡터 유사도와 만나면 벌어지는 일

전통 캐시는 키가 **정확히 일치**해야 히트한다. `GET /user/42`와 `GET /user/42`는 같은 키지만, `"오늘 서울 날씨 어때?"`와 `"서울 오늘 날씨 알려줘"`는 문자열로는 완전히 다른 두 키다. LLM 시대의 캐시는 이 두 요청을 "같은 의도"로 인식하고 하나의 응답을 재사용해야 한다. Semantic Cache는 요청 텍스트를 임베딩(embedding)으로 변환한 뒤 벡터 유사도가 임계값 이상이면 캐시 히트로 판정하는 캐시 계층이다. LLM 호출 비용($0.01~$0.10/req)과 지연(500ms~5s)이 크기 때문에, 히트율 20~40%만 확보해도 인프라 비용의 절반이 사라진다.

#### 동작 구조

```
   ┌────────────────────────────────────────────────────────┐
   │  Client Request: "How do I reset my password?"         │
   └───────────────────────┬────────────────────────────────┘
                           │
                           ▼
             ┌──────────────────────────┐
             │  Embedding Model         │  (text-embedding-3-small)
             │  → vector[1536]          │
             └───────────┬──────────────┘
                         │
              ┌──────────▼──────────┐
              │  Vector DB (ANN)    │
              │  cosine_sim >= 0.92 │──── HIT ────┐
              └──────────┬──────────┘             │
                         │ MISS                   │
                         ▼                        │
               ┌──────────────────┐               │
               │  LLM Provider    │               │
               │  (OpenAI/Claude) │               │
               └──────────┬───────┘               │
                          │                       │
                          ▼                       │
                ┌──────────────────┐              │
                │  Store (q_vec,   │              │
                │   response, ttl) │              │
                └──────────┬───────┘              │
                           │                      │
                           ▼                      ▼
                     ┌──────────────────────────────┐
                     │  Response to Client          │
                     └──────────────────────────────┘
```

핵심은 세 단계: **(1) 임베딩화**, **(2) ANN 검색(cosine similarity)**, **(3) 임계값 판정**. 임계값 τ가 캐시의 성격을 결정한다. τ=0.95면 거의 동일 문장만 히트하는 보수적 캐시, τ=0.85면 "비슷한 의도"까지 히트하는 공격적 캐시가 된다.

#### 진짜 문제 1: 유사하다는 것이 같다는 뜻이 아니다

`"파이썬으로 파일 읽는 법"`과 `"파이썬으로 파일 쓰는 법"`은 임베딩 공간에서 cosine 0.94 이상 나온다. 문장 구조가 거의 동일하기 때문이다. τ=0.92로 잡으면 **읽기 질문에 쓰기 답변이 돌아간다**. 이 문제는 도메인이 좁을수록 심해진다. 금융 챗봇에서 `"내 계좌 잔액 조회"`와 `"내 계좌 이체 실행"`이 유사도 0.93으로 잡히면 그 캐시는 그날로 폐기해야 한다.

해결책은 세 가지 층에서 온다.
- **임계값을 도메인별로 다르게**: 정보성 질문은 τ=0.88, 트랜잭션성 질문은 캐시 자체를 비활성.
- **Reranker로 2차 검증**: ANN 상위 K개를 뽑고 cross-encoder(예: `bge-reranker`)로 재점수화해 최종 판정.
- **Negative filter**: 동사(read/write, get/set, buy/sell) 어휘를 추출해 다르면 캐시 무효화.

#### 진짜 문제 2: 컨텍스트가 캐시 키가 아니다

LLM 요청은 프롬프트 + 시스템 메시지 + **사용자 컨텍스트**(로그인 사용자, 세션 대화 이력, RAG로 검색된 문서)로 구성된다. `"내 최근 주문 알려줘"`라는 질문은 사용자 A와 B에게 완전히 다른 답이 나가야 한다. 질문 텍스트만 임베딩해 캐시하면 **크로스 유저 데이터 유출**이 즉시 발생한다.

실무적 해결은 캐시 파티션을 명시적으로 분리하는 것이다: `namespace = tenant_id + user_id + rag_doc_hash`. 파티션 안에서만 유사도 검색을 돌린다. 대신 히트율은 급락한다. B2B SaaS는 tenant 단위 파티션(사용자 간 공유 가능한 FAQ성 질문), B2C는 익명 질문만 전역 파티션에 두는 하이브리드 전략이 정답에 가깝다.

#### 진짜 문제 3: 임베딩 모델을 바꾸면 캐시가 통째로 무효화된다

`text-embedding-ada-002`로 저장한 벡터와 `text-embedding-3-small`로 새로 뽑은 벡터는 **차원 수도 다르고 좌표계도 다르다**. 모델 업그레이드는 캐시 전체 재구축을 의미한다. 프로덕션 환경에서 이걸 무중단으로 하려면 두 벌의 벡터를 병렬 저장하고, 새 모델의 히트율이 안정화될 때까지 dual-write하는 마이그레이션이 필요하다.

여기에 더해 임베딩 API 비용도 무시할 수 없다. LLM 호출을 아끼려고 도입한 캐시가 임베딩 요청 비용으로 원가를 잠식하면 배보다 배꼽이다. **로컬 임베딩 모델(`bge-small`, `all-MiniLM`)**을 CPU/GPU에 상주시켜 임베딩 단계를 무료화하는 것이 실무의 정답이다.

#### 트레이드오프

| 관점 | 정확한 캐시 (τ↑) | 공격적 캐시 (τ↓) |
|---|---|---|
| 히트율 | 5~15% | 30~50% |
| 오답 위험 | 낮음 | 높음 (특히 부정문/반의어) |
| 비용 절감 | 제한적 | 크지만 신뢰도 하락 |
| 적합 도메인 | 트랜잭션, 금융, 의료 | FAQ, 문서 검색, 코드 스니펫 |

Semantic Cache는 **"틀린 답이 나오면 얼마나 아픈가"**로 τ가 결정된다. FAQ 챗봇은 30% 히트율에 3% 오답이 감내 가능하지만, 은행 챗봇은 히트율 5%라도 오답 0%를 요구한다.

#### 실제 사례

- **GPTCache (Zilliz)**: 2023년 오픈소스로 공개. Milvus 위에서 semantic cache를 구현한 초기 구현체. LangChain 통합으로 대중화됨. 임계값·임베딩 모델·스토어를 플러그인화한 것이 표준적 설계로 자리잡음.
- **Anthropic Prompt Caching**: 정확 문자열 매칭 기반(entity-level cache)이라 semantic cache와는 다르지만, 시스템 프롬프트·툴 정의같이 반복되는 큰 컨텍스트를 90%까지 할인해준다. Semantic cache와 **레이어를 나누어** 병용하는 것이 최근 패턴 — 프롬프트 프리픽스는 provider cache, 사용자 질문 단은 semantic cache.
- **Perplexity**: 검색 성격의 반복 질의(예: `"who is the CEO of X"`)에 semantic cache를 활용해 응답 지연을 서브초로 유지. 답변이 시간에 민감한 질문(주가, 뉴스)은 TTL을 초 단위로 짧게 잡아 stale 방지.
- **Discord Clyde(deprecated)**: 게임/커뮤니티 특성상 유사 질문 반복이 극심해 semantic cache 히트율 40%대를 기록했으나, 사용자별 페르소나 컨텍스트 유출 문제로 파티션 재설계를 거침.

#### 시니어의 관점: 언제 쓰고, 언제 쓰면 안 되는가

**쓸 것**:
- FAQ, 문서 QA, 코드 도우미처럼 **정답이 상대적으로 안정적**이고 사용자 간 공유 가능한 도메인
- LLM 호출당 원가가 지연·비용 모두에서 병목인 경우(월 $10K 이상 LLM 비용)
- RAG의 검색 단계 결과까지 캐시해 임베딩·retrieval·generation 세 단을 함께 절감할 수 있는 경우

**쓰지 말 것**:
- 트랜잭션·계정 조작이 포함된 요청(잘못된 히트가 실제 손해로 이어짐)
- 시간에 민감한 정보(주가, 재고, 예약 가능 여부) — TTL을 아무리 짧게 잡아도 stale 위험
- 사용자별 컨텍스트가 응답의 대부분을 결정하는 경우(파티션이 사용자 수만큼 쪼개져 히트율 0에 수렴)
- **관측 없이 도입하면 절대 안 됨** — 히트율, false-hit rate, 사용자 재질문율(캐시로 잘못된 답을 받아 다시 물어보는 비율)을 반드시 계측해야 한다. false-hit rate가 히트율의 5%를 넘으면 τ를 즉시 올려라.

Semantic Cache는 "빠르고 싸다"는 매력 뒤에 **"조용히 틀린 답을 준다"**는 위험을 숨긴다. 지연·비용 문제를 풀지만, 정확성 문제를 새로 만든다. 도입 여부보다 **오답 허용 예산(error budget)**을 먼저 정의하는 것이 순서다.

> 💡 **왜 중요한가**: Semantic Cache는 LLM 비용의 30~50%를 절감할 수 있지만, "유사 ≠ 동일"이라는 벡터 공간의 함정을 이해하지 못하면 조용히 틀린 답을 대량 생산하는 기계가 된다.
