### 1. PostgreSQL CTE의 `MATERIALIZED` / `NOT MATERIALIZED` — 12 버전에서 바뀐 인라인 최적화 제어하기

PostgreSQL 12 이전에는 `WITH` CTE가 항상 별도로 실행되는 "옵티마이저 펜스(optimizer fence)"였지만, 12부터는 단일 참조 CTE를 기본적으로 인라인 처리한다. 옵티마이저가 잘못된 판단을 내려 CTE를 외부 쿼리로 밀어 넣어 필터 순서가 뒤바뀔 때는 `WITH cte AS MATERIALIZED (...)`로 강제 실체화하고, 반대로 오래된 코드가 펜스를 노렸다면 `NOT MATERIALIZED`로 인라인화해 조인 재정렬을 유도할 수 있다.

```sql
-- 무거운 집계 CTE를 한 번만 계산하도록 강제
WITH heavy_stats AS MATERIALIZED (
  SELECT user_id, COUNT(*) AS cnt
  FROM events
  WHERE created_at >= NOW() - INTERVAL '7 days'
  GROUP BY user_id
)
SELECT u.*, h.cnt
FROM users u
JOIN heavy_stats h ON h.user_id = u.id
WHERE u.status = 'active';
```

> 💡 **왜 중요한가**: 같은 SQL이 PG 11과 12+에서 실행 계획이 완전히 달라질 수 있어, 마이그레이션 후 성능 회귀의 숨은 원인이 되곤 한다.

### 2. MongoDB 복합 인덱스의 ESR 규칙 — Equality, Sort, Range 순서로 컬럼을 배치하기

MongoDB 복합 인덱스는 컬럼 순서에 따라 성능이 극단적으로 갈리는데, 공식 권장 순서는 **Equality(등호 조건) → Sort(정렬 키) → Range(범위 조건)** 이다. 이 순서를 지키면 인덱스만으로 정렬을 처리(`IXSCAN`)하고 `SORT` 단계와 인메모리 정렬 32MB 제한을 피할 수 있으며, 범위 조건을 마지막에 두어야 정렬 키가 이미 정렬된 상태로 스캔된다.

```javascript
// 쿼리: status = 'active' AND createdAt >= X, ORDER BY priority DESC
// ❌ Range를 Sort 앞에 두면 인메모리 정렬 발생
db.tasks.createIndex({ status: 1, createdAt: 1, priority: -1 })

// ✅ ESR: Equality → Sort → Range
db.tasks.createIndex({ status: 1, priority: -1, createdAt: 1 })

// explain()에서 winningPlan에 SORT 단계가 사라졌는지 확인
db.tasks.find({ status: 'active', createdAt: { $gte: iso } })
  .sort({ priority: -1 }).explain('executionStats')
```

> 💡 **왜 중요한가**: 같은 컬럼 집합의 인덱스라도 순서가 잘못되면 정렬 단계가 메모리에서 재실행되어 `OperationFailed: Sort exceeded memory limit` 에러로 프로덕션 쿼리가 통째로 죽는다.
