### 1. `Collectors.filtering(predicate, downstream)` (Java 9 정식)로 `stream().filter(...).collect(groupingBy(...))` 때 그룹별 빈 버킷 사라지는 관성 벗어나기

`groupingBy` 전에 `filter`를 걸면 조건을 만족하는 요소가 하나도 없는 그룹은 결과 맵에서 아예 사라져버린다. `Collectors.filtering(predicate, Collectors.toList())`를 다운스트림으로 넣으면 그룹 키는 보존하면서 필터링된 리스트(빈 리스트 포함)를 유지할 수 있다. "성인 사용자 그룹별 집계인데 미성년자만 있는 부서가 통째로 누락"되는 사일런트 버그를 막는 핵심 패턴.

```java
// ❌ 관성: 필터 → 그룹핑. 조건 미달 그룹은 맵에서 증발
Map<Dept, List<User>> byDept = users.stream()
    .filter(u -> u.age() >= 18)
    .collect(groupingBy(User::dept));

// ✅ 그룹핑 → 필터. 모든 부서 키 보존, 값은 필터된 리스트
Map<Dept, List<User>> byDept = users.stream()
    .collect(groupingBy(User::dept,
        filtering(u -> u.age() >= 18, toList())));
```

> 💡 **왜 중요한가**: "그룹별 집계에서 빈 그룹이 사라졌다"는 리포트/대시보드 사일런트 버그의 90%가 이 순서 뒤바뀜에서 온다.

### 2. `CompletableFuture.orTimeout(duration, unit)` (Java 9 정식)로 `CompletableFuture.anyOf(future, delayedTimeout)` 수동 조립 관성 벗어나기

비동기 작업에 타임아웃을 걸 때 과거엔 `CompletableFuture.anyOf()`로 지연된 예외 Future와 레이스시키거나 별도 스케줄러로 `completeExceptionally()`를 호출하는 보일러플레이트가 필요했다. `orTimeout(5, SECONDS)`는 내부적으로 `ScheduledThreadPoolExecutor`를 재사용해 Future 체인에 바로 `TimeoutException`을 전파하고, `completeOnTimeout(fallback, 5, SECONDS)`은 예외 대신 기본값으로 완료시킨다. 외부 API 호출·DB 조회 체인에서 "응답이 영원히 안 오면 스레드가 매달려 있는" 관성을 한 줄로 끊어낸다.

```java
// ❌ 관성: anyOf + 수동 타임아웃 Future 조립
CompletableFuture<String> timeout = new CompletableFuture<>();
scheduler.schedule(() -> timeout.completeExceptionally(new TimeoutException()),
    5, TimeUnit.SECONDS);
CompletableFuture.anyOf(callApi(), timeout).thenAccept(...);

// ✅ 체인에 바로 타임아웃 선언
callApi()
    .orTimeout(5, TimeUnit.SECONDS)                    // 초과 시 TimeoutException
    .exceptionally(ex -> "default")
    .thenAccept(this::handle);

// ✅ 또는 예외 대신 폴백 값으로 즉시 완료
callApi()
    .completeOnTimeout("fallback", 5, TimeUnit.SECONDS)
    .thenAccept(this::handle);
```

> 💡 **왜 중요한가**: 비동기 체인의 타임아웃 누락은 "느린 외부 의존성 하나가 전체 스레드풀을 고갈시키는" 장애의 단골 원인인데, `orTimeout` 한 줄로 방어선이 생긴다.
