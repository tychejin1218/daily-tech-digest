### LLM Gateway 패턴 — "우리 회사 백엔드가 OpenAI에 직접 붙어있다"는 문장이 CTO를 밤에 못 자게 하는 이유

---

당신의 회사에 어제 이런 일이 일어났다고 상상해보자.

- **오전 9시**: OpenAI API가 us-east-1에서 30분 다운. 챗봇, 요약 API, 내부 CS 도구, 코드 리뷰 봇이 동시에 죽었다.
- **오전 10시**: 복구 후 슬랙에 한 마디. "우리 GPT-4 호출하는 서비스가 몇 개죠?" 아무도 정확히 모른다.
- **오후 2시**: 재무팀이 지난달 청구서를 들고 온다. 4만 달러. "어느 팀이 이만큼 쓴 거예요?" 로그가 각 서비스에 흩어져 있어 취합 불가.
- **오후 4시**: 보안팀 미팅. "사내 문서를 OpenAI에 보내면 안 되는 거 아시죠?" 실제로 어떤 서비스가 무엇을 보냈는지 감사(audit) 불가능.
- **오후 6시**: 모델 담당자가 말한다. "우리 이제 Claude Opus로 절반, GPT-4o로 절반 나눠서 A/B 테스트하려고요." 서비스 12개 코드를 다 뜯어야 한다.

이 다섯 가지는 서로 다른 문제처럼 보이지만, **모두 하나의 아키텍처 결정에서 파생된다**: LLM Provider SDK를 애플리케이션 코드가 직접 import했다는 것.

LLM Gateway는 이 결정을 되돌리는 인프라 레이어다. 마이크로서비스에서 API Gateway가 하는 일 — 라우팅, 인증, 레이트 리밋, 관찰성 — 을 LLM 호출에 대해 하는 것이다. 하지만 "그냥 API Gateway 하나 두면 되잖아?"라고 생각하는 순간, 왜 대부분의 회사가 이걸 자체 구축했다가 후회하는지 알게 된다.

---

#### 1. 없을 때 vs 있을 때 — 아키텍처의 진짜 차이

**Anti-pattern: SDK 직결 (대부분의 스타트업이 시작하는 방식)**

```
┌─────────────────┐         ┌─────────────────┐
│  Chatbot API    │────────▶│                 │
├─────────────────┤         │                 │
│  Summarizer     │────────▶│    OpenAI API   │
├─────────────────┤         │                 │
│  Code Review    │────────▶│                 │
├─────────────────┤         │                 │
│  CS Tool        │────────▶│                 │
├─────────────────┤         └─────────────────┘
│  Analytics      │────────▶ Anthropic
├─────────────────┤────────▶ Google Gemini
│  Search API     │        (각 서비스가 각자 SDK, 각자 API 키, 각자 재시도 로직)
└─────────────────┘
```

각 서비스가 자기 API 키를 관리하고, 자기 재시도 로직을 짜고, 자기 로그를 찍는다. 6개 서비스 = 6번의 중복. 그리고 **6개의 코드베이스에서 동시에 발생하는 6개의 버그**.

**With Gateway**

```
┌─────────────────┐
│  Chatbot API    │─┐
├─────────────────┤ │
│  Summarizer     │─┤    ┌──────────────────────────┐
├─────────────────┤ │    │      LLM Gateway         │
│  Code Review    │─┼───▶│  ─────────────────────   │
├─────────────────┤ │    │  • Auth / API Key Vault  │      ┌──────────┐
│  CS Tool        │─┤    │  • Rate Limit / Quota    │─────▶│ OpenAI   │
├─────────────────┤ │    │  • Routing (model/tier)  │      ├──────────┤
│  Analytics      │─┤    │  • Retry / Fallback      │─────▶│ Anthropic│
├─────────────────┤ │    │  • Semantic Cache        │      ├──────────┤
│  Search API     │─┘    │  • Cost Tracking (tag)   │─────▶│ Gemini   │
└─────────────────┘      │  • PII Scrubbing         │      ├──────────┤
                         │  • Audit Log             │─────▶│ Self-host│
      OpenAI-compatible  │  • Prompt Guard          │      └──────────┘
      단일 endpoint       └──────────────────────────┘
```

핵심은 **애플리케이션은 여전히 `openai.chat.completions.create(...)`처럼 쓴다**는 것이다. Gateway는 OpenAI-compatible endpoint를 제공하고, base_url만 바꾸면 된다. 애플리케이션 코드 변경 zero. 이게 왜 중요한지는 뒤에서 다시 다룬다.

#### 2. Gateway가 실제로 하는 일 — 7가지 책임

시니어 개발자에게 익숙한 API Gateway의 책임과 비교하면 이해가 빠르다.

| 책임 | 일반 API Gateway | LLM Gateway (다른 점) |
|---|---|---|
| **인증** | JWT/OAuth | + Provider API Key **금고**(각 팀이 키 몰라도 됨) |
| **레이트 리밋** | req/sec | + **TPM (tokens/min)** — OpenAI는 요청 수가 아니라 토큰 수로 제한 |
| **라우팅** | path 기반 | **모델/태스크/비용/지연** 기반 (같은 요청도 상황따라 다른 곳으로) |
| **재시도** | 5xx 재시도 | + **모델 fallback** (GPT-4 죽으면 Claude로) |
| **캐싱** | HTTP cache | **Semantic Cache** (문자열 다르지만 의미 같으면 hit) |
| **로깅** | 요청/응답 | + **토큰 사용량**, **비용**, **latency by model**, **prompt/completion 페어** |
| **보안** | WAF | **PII 스크러빙**, **프롬프트 인젝션 탐지**, **egress DLP** |

특히 세 가지가 일반 API Gateway와 결정적으로 다르다.

**첫째, 응답 스트리밍.** LLM은 SSE(Server-Sent Events)로 토큰을 흘려보낸다. Kong이나 nginx는 이걸 처리할 순 있지만, **스트리밍 중에 토큰 카운트하고 비용 계산하고 로그 남기는 것**은 별도 로직이다. 대부분의 일반 Gateway는 이 지점에서 무너진다.

**둘째, 요청/응답 크기 비대칭.** REST API는 요청 100KB, 응답 100KB가 흔하다. LLM은 요청 100KB(system prompt + context), 응답 4KB인 경우가 많다. 반대로 RAG는 요청 500KB(retrieved docs), 응답 2KB. 캐싱 전략과 payload 처리 로직이 다르다.

**셋째, 실패의 정의가 다르다.** 200 OK로 온 응답이 프롬프트 인젝션에 당해서 시스템 프롬프트를 유출했을 수도 있다. HTTP 상태 코드로는 못 잡는다. Gateway가 **응답 내용을 검사**해야 한다.

#### 3. "그럼 Kong에 플러그인 얹으면 되지 않나?" — 자체 구축 vs 전용 솔루션

이게 시니어 개발자들이 실제로 가장 많이 하는 질문이다. 답은 "된다. 그런데 6개월 뒤에 후회한다."

**자체 구축 경로 (예: Kong + custom Lua 플러그인)**

```
장점: 기존 인프라 재사용, 러닝 커브 낮음, 완전한 통제
단점:
  - Semantic Cache는 별도 벡터 DB 필요 (Redis만으로 안 됨)
  - 토큰 카운팅을 각 모델의 tokenizer로 구현해야 함 (tiktoken, Claude tokenizer, ...)
  - 새 모델 추가할 때마다 SDK 스펙 매핑 코드 작성
  - 스트리밍 응답 중 토큰 로깅은 논트리비얼
  - 프롬프트 인젝션 탐지 룰은 계속 업데이트되어야 함
```

**전용 솔루션 (LiteLLM, Portkey, Kong AI Gateway, Cloudflare AI Gateway, LangChain LangServe)**

- **LiteLLM**: 오픈소스, 100+ 모델의 OpenAI-compatible proxy. Netflix, Rocket Money가 프로덕션에서 사용. Python 기반이라 커스터마이즈 쉬움.
- **Portkey**: SaaS + self-hosted. 관찰성 대시보드 강력. Postman이 초기부터 사용.
- **Cloudflare AI Gateway**: 엣지에서 캐싱/로깅. 이미 Cloudflare 쓰는 조직엔 zero-config.
- **Kong AI Gateway**: 이미 Kong 쓰는 조직의 자연스러운 선택.

실제 결정 프레임:

```
                    [LLM 호출 서비스 수]
                            │
        ┌───────────────────┼───────────────────┐
        │ 1~2개              │ 3~10개            │ 10개 이상
        │                   │                   │
     그냥 SDK              LiteLLM proxy       전용 인프라팀 소유
     직접 써라              (self-hosted)       + Portkey/Kong
        │                   │                   │
   (Gateway는            (하루 만에 구축,      (온콜 로테이션,
   과잉 엔지니어링)       비용 대비 효과 최대)   SLA, dedicated cluster)
```

#### 4. 실제 사례 — 왜 이 회사들은 이걸 만들었나

**Netflix Metaflow LLM Gateway (2024)**
- 문제: 데이터 사이언티스트가 노트북에서 LLM 호출. 어느 프로젝트가 얼마 썼는지 추적 불가.
- 해결: 사내 Gateway가 `X-Metaflow-Flow` 헤더로 프로젝트 태깅. 매달 자동 청구서 발행.
- 교훈: **비용 귀속(cost attribution)이 Gateway의 킬러 기능이다.** 관찰성보다도 CFO가 먼저 원한다.

**Uber Michelangelo + Genie (2024)**
- 문제: 여러 팀이 다른 모델(자체 파인튜닝 + OpenAI + Anthropic)을 각자 방식으로 호출.
- 해결: 통합 Gateway가 라우팅. `task=summarization`이면 저비용 모델, `task=code`면 GPT-4o.
- 교훈: **태스크 기반 라우팅이 모델 선택 결정을 코드에서 config로 옮긴다.** 배포 없이 A/B 테스트 가능.

**Duolingo (2023~)**
- 문제: 학습 콘텐츠 생성이 폭증하면서 GPT-4 비용이 감당 불가.
- 해결: Gateway 레벨 semantic cache + 문제 유형별 모델 라우팅. 비용 60% 절감.
- 교훈: **캐싱은 애플리케이션이 아니라 Gateway에서 해야 여러 서비스가 공유한다.**

**Notion AI**
- 문제: 사용자 문서를 LLM에 보낼 때 PII/기밀정보 유출 우려.
- 해결: Gateway가 egress 시점에 PII 스크러빙 + 감사 로그.
- 교훈: **컴플라이언스는 애플리케이션에 맡기면 반드시 새는 곳이 생긴다. Gateway가 유일한 egress 포인트여야 한다.**

#### 5. 트레이드오프 — 시니어가 진짜 걱정해야 할 것들

**❌ 지연(Latency) 오버헤드**
- Gateway 홉이 20~50ms 추가된다. 대부분의 LLM 호출(1~10초)에선 무시할 수 있지만, 스트리밍 첫 토큰 시간(TTFT)에 민감한 UX면 문제.
- **완화**: Gateway를 LLM Provider와 같은 리전에 배치. 애플리케이션 → Gateway는 keep-alive.

**❌ 단일 장애점(SPOF)**
- Gateway가 죽으면 모든 LLM 기능이 죽는다. "OpenAI 대신 우리 Gateway가 죽는다"는 시나리오.
- **완화**: 다중 리전, 헬스체크 기반 클라이언트 사이드 fallback. 최악의 경우 SDK 직결로 폴백하는 escape hatch 코드 유지.

**❌ 기능 요청 병목**
- "우리 팀은 새 Anthropic 기능(예: extended thinking) 쓰고 싶은데 Gateway가 지원 안 함."
- **완화**: passthrough 모드 제공. Gateway를 통하되 요청/응답을 그대로 전달. 관찰성만 챙기고 기능 매핑은 우회.

**❌ 조기 도입의 함정**
- 서비스 1개짜리 스타트업이 Gateway부터 만들면, 6개월 동안 Gateway 유지보수만 한다.
- **원칙**: **3번째 LLM 호출 서비스가 생길 때 도입한다.** 그 전엔 오버엔지니어링.

**❌ Provider 종속성의 아이러니**
- Gateway 도입 이유 중 하나가 "provider lock-in 방지"인데, 정작 Gateway 자체(예: Portkey SaaS)에 lock-in되는 경우.
- **완화**: OpenAI-compatible endpoint 표준을 지키는 솔루션 선택. 마이그레이션 비용 낮게 유지.

#### 6. 언제 쓰고 언제 쓰면 안 되는가

**✅ 도입해야 할 때**
- LLM 호출 서비스가 3개 이상.
- 여러 provider를 실제로(가정이 아니라) 병행 사용 중이거나 6개월 내 계획 있음.
- 비용 귀속을 팀/프로젝트 단위로 정확히 요구받음.
- 규제 산업(금융/의료/공공)이라 감사 로그 필수.
- A/B 테스트로 모델을 자주 스위칭해야 함.
- Semantic Cache로 비용 절감 여지가 큰 워크로드(반복 질의 많은 챗봇, CS 봇).

**❌ 도입하면 안 될 때**
- 서비스가 1~2개고, 향후 6개월 내 확장 계획 없음.
- LLM 호출이 하루 몇 백 건 수준(관찰성 오버킬).
- 팀에 인프라 담당자 없음. Gateway는 인프라 컴포넌트고, 온콜 대상이다.
- 지연 예산이 극도로 타이트한 실시간 UX(예: 음성 대화 어시스턴트). 이 경우 SDK 직결 + 클라이언트 사이드 로깅이 낫다.
- **Semantic Cache가 유일한 도입 이유**라면 Gateway 필요 없다. Redis + 벡터 라이브러리로 애플리케이션 레벨 캐시 만들면 된다.

#### 7. 최소 실전 구현 — LiteLLM으로 하루 안에

시니어에게 감을 잡히게 하는 최소 예시:

```yaml
# litellm_config.yaml
model_list:
  - model_name: fast-summarize      # 애플리케이션이 부르는 이름
    litellm_params:
      model: gpt-4o-mini
      api_key: os.environ/OPENAI_KEY

  - model_name: fast-summarize      # 같은 이름에 fallback 등록
    litellm_params:
      model: claude-haiku-4-5
      api_key: os.environ/ANTHROPIC_KEY

  - model_name: heavy-reasoning
    litellm_params:
      model: claude-opus-4-7

router_settings:
  routing_strategy: latency-based-routing
  fallbacks:
    - fast-summarize: [heavy-reasoning]

general_settings:
  master_key: sk-gateway-master
  database_url: postgres://...      # 감사 로그 저장
  redis_url: redis://...            # semantic cache
```

애플리케이션 코드는 이것만 바뀐다:

```python
# Before
client = OpenAI(api_key="sk-...")
client.chat.completions.create(model="gpt-4o-mini", ...)

# After
client = OpenAI(
    api_key="sk-team-chatbot-abc",   # 팀별 키, Gateway가 발급
    base_url="https://llm-gw.internal.corp/v1"
)
client.chat.completions.create(model="fast-summarize", ...)
```

이제 팀별 비용이 자동 집계되고, GPT-4o-mini가 죽으면 Claude Haiku로 fallback되고, 같은 질문은 캐시되고, 감사 로그가 쌓인다. **애플리케이션 코드 3줄 변경으로.**

---

> 💡 **왜 중요한가**: LLM Gateway가 없으면 "OpenAI에 얼마 썼는가", "누가 무엇을 보냈는가", "provider를 바꿀 수 있는가"라는 세 가지 질문에 답할 수 없고, 이 세 질문에 답할 수 없는 조직은 결국 LLM 인프라를 다시 만들게 된다.
