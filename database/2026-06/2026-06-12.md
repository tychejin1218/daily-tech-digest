### 1. PostgreSQL `fillfactor`와 HOT(Heap-Only Tuple) Update — 인덱스 갱신 없이 UPDATE 비용 줄이기
PostgreSQL의 UPDATE는 사실 "기존 튜플을 죽이고 새 튜플을 만드는" MVCC 동작이라, 같은 페이지 내에 빈 공간이 있고 인덱스 컬럼이 바뀌지 않으면 HOT 체인으로 묶여 인덱스를 갱신하지 않는다. 그런데 기본 `fillfactor=100`이면 페이지가 꽉 차서 새 버전이 다른 페이지로 밀려나 HOT이 깨지므로, UPDATE가 잦은 테이블은 `ALTER TABLE t SET (fillfactor=80)`처럼 의도적으로 페이지 여유 공간을 남겨둬야 효과가 산다. `pg_stat_user_tables`의 `n_tup_hot_upd` / `n_tup_upd` 비율로 HOT이 실제로 일어나고 있는지 검증할 수 있다.

> 💡 **왜 중요한가**: 같은 행을 자주 업데이트하는 카운터·상태 컬럼에서 HOT이 동작하면 인덱스 쓰기 I/O와 WAL 양이 크게 줄고, autovacuum이 인덱스 정리 없이 페이지 내부에서 죽은 튜플을 회수해 테이블 팽창을 막을 수 있다.

### 2. Spring Data JPA `Persistable` 인터페이스 — `save()`가 INSERT 직전에 날리는 숨은 SELECT 막기
`JpaRepository.save()`는 엔티티가 "새 것"인지 판단하려고 ID가 null이 아니면 `EntityManager.find()`로 존재 여부를 먼저 조회한 뒤 없으면 INSERT, 있으면 merge한다. 그래서 UUID나 자연키처럼 애플리케이션이 ID를 직접 채워서 넣는 엔티티는 INSERT 한 번에 항상 SELECT가 한 번씩 따라붙는다. 엔티티에 `Persistable<ID>`를 구현해 `isNew()`가 신규 여부를 직접 알려주게 하면(보통 `@Transient` 플래그 + `@PrePersist`로 false 전환), Spring Data가 SELECT를 건너뛰고 곧장 INSERT를 발행한다.

> 💡 **왜 중요한가**: 대량 적재나 외부 ID를 받아 저장하는 API에서 매 건마다 발생하던 EXISTS-체크용 SELECT가 사라져 쿼리 수가 절반, 트랜잭션 시간과 DB 라운드트립이 그만큼 줄어든다.
