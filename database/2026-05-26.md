### PostgreSQL `CREATE INDEX CONCURRENTLY` — 운영 중 테이블 락 없이 인덱스 만들기
일반 `CREATE INDEX`는 `SHARE` 락을 걸어 인덱스 생성 동안 쓰기를 막지만, `CONCURRENTLY` 옵션을 쓰면 두 번에 걸쳐 테이블을 스캔하면서 쓰기를 허용한다. 단점은 시간이 더 오래 걸리고 트랜잭션 안에서 못 쓰며, 실패 시 `INVALID` 상태의 인덱스가 남으므로 `pg_index.indisvalid`를 확인해 `DROP INDEX CONCURRENTLY`로 정리해야 한다.

> 💡 **왜 중요한가**: 운영 DB에서 인덱스 추가만으로 수십 분간 서비스가 멈추는 사고를 막을 수 있다.

### MySQL `EXPLAIN ANALYZE`와 `FORMAT=TREE` — 실제 실행 시간으로 조인 순서 디버깅하기
MySQL 8.0.18+의 `EXPLAIN ANALYZE`는 PostgreSQL과 마찬가지로 쿼리를 실제 실행한 뒤 각 단계의 누적 시간·반복 횟수·실측 행 수를 보여준다. `FORMAT=TREE`로 출력하면 중첩 루프 조인의 안쪽/바깥쪽이 어떻게 평가되는지 직관적으로 보이고, 예상 행 수(`rows=`)와 실제 행 수(`actual rows=`)의 괴리로 통계 부정확 여부를 판별할 수 있다.

> 💡 **왜 중요한가**: 옵티마이저가 "왜 이 순서로 조인했는가"를 추정이 아닌 측정값으로 설명해주므로, 인덱스 추가/`STRAIGHT_JOIN` 힌트 판단의 근거가 명확해진다.
