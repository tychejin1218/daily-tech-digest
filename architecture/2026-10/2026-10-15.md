### Hybrid Search (BM25 + Vector) — "임베딩이 의미를 다 잡는다"는 순진함, 그리고 "주문번호 ORD-20260314-7812 어떻게 됐나요"라는 CS 질의에 '유사한 주문 10건'만 뜬 채 상담사가 Oracle SQL*Plus 창을 다시 열어 사내 챗봇 프로젝트가 "그래서 ES 왜 끈 거야?"로 포스트모템에 올라간 금요일 저녁

---

#### 1. 사건 재구성 — 2026년 3월, 국내 N 커머스 CS 챗봇

- **스택**: OpenAI `text-embedding-3-large`(3,072차원) + Pinecone(serverless) + GPT-4o
- **이전**: Elasticsearch 7.x BM25로 돌아가던 CS 지식베이스 + 주문/상담 로그 검색
- **마이그레이션**: "요즘은 Vector DB가 표준이지. ES는 레거시다." → ES 인덱스 종료, Pinecone 단일 리트리버로 전환
- **런칭 후 48시간**: 체류시간·만족도 지표 양호
- **4일차 금요일 저녁 19:40**: CS팀장이 Slack에 투척 — "ORD-20260314-7812 조회 안 돼요. 비슷한 주문 10건만 뜨고 정작 그 주문은 리스트에 없음"
- **원인**: `text-embedding-3-large`가 `ORD-20260314-7812`를 "20260314라는 숫자 토큰 + 7812"로 **의미적으로 가장 비슷한 다른 주문번호들**과 묶었다. 코사인 유사도 0.91~0.93으로 유사 주문들이 top-10을 차지, 정작 **정확히 일치하는 주문은 top-23**에 있었다
- **후폭풍**: CS 상담사들이 "그냥 Oracle 돌릴게요"로 복귀, 챗봇 DAU 72% → 11%. 월요일 회고에 PM이 적어넣은 한 줄 — *"ES를 왜 끈 거야? 아무도 명확히 대답 못 함"*

이 사건의 핵심은 "Vector DB가 느려서"도 "Pinecone이 비싸서"도 아니다. **Dense Vector는 'exact token match'를 포기한 자료구조**라는, 설계 당시 아무도 명시적으로 테이블에 올리지 않은 사실 때문이다.

---

#### 2. 왜 Vector 혼자서는 안 되는가 — Dense의 원죄

Dense Embedding은 토큰을 연속 공간에 사영(projection)한다. 사영의 본질은 **압축**이고, 압축의 본질은 **구별 가능하던 두 신호를 "비슷한 것"으로 뭉개는 것**이다. 그래서 다음은 Dense가 구조적으로 못 하거나 매우 못 한다:

| 질의 유형 | Dense Vector | 실제 필요한 결과 |
|---|---|---|
| `ORD-20260314-7812` (주문번호) | 유사 번호들을 top-k에 묶음 | 정확히 그 ID 하나 |
| `error code E-4091` | E-40xx 계열 혼재 | E-4091 로그 |
| 희귀 고유명사 ("재이형제과") | top-50에도 안 뜸 | 가장 먼저 떠야 함 |
| `iPhone 15 Pro Max 256GB 티타늄 블루` | 색상 무시, 용량 섞임 | 정확 매칭 1건 |
| 신조어 ("K-패스 환급") | 임베딩 학습 데이터에 없음 → 0.3대 유사도 | top-1 |

반대로 BM25(또는 그 변형: BM25F, LM-Dirichlet)는 **toknize 후 inverted index로 완전 일치**를 세기 때문에 위 질의들에는 거의 완벽하다. 하지만 BM25는 반대로:

- "환불이 늦어요" ↔ "리펀드 처리 지연 문의" — **동의어/의역**을 모른다
- "결제가 안 돼요" ↔ "카드 승인 실패" — **의미 유사성**을 못 잡는다
- 다국어 혼용 — 토큰 매칭이 깨진다

**즉, Dense는 "의미는 알지만 글자를 못 세고", Sparse(BM25)는 "글자는 세지만 의미를 모른다"**. 둘은 서로의 결함을 메우는 **상보적 자료구조**다. 이걸 한쪽만 쓰는 순간, 다른 쪽이 커버하던 질의 분포가 통째로 리콜 0으로 떨어진다. N 커머스 사례는 그 "다른 쪽 분포"가 CS 질의의 34%였다는 걸 뒤늦게 발견했을 뿐이다.

#### 3. Hybrid Search의 뼈대 — 두 리트리버를 어떻게 합치나

```
┌─────────────────────────────────────────────────────────────────┐
│                       사용자 질의 Query                           │
└───────────────────────────┬─────────────────────────────────────┘
                            │
            ┌───────────────┴────────────────┐
            │                                │
            ▼                                ▼
   ┌─────────────────┐              ┌─────────────────┐
   │  Sparse (BM25)  │              │  Dense (Vector) │
   │  Elasticsearch  │              │   Pinecone /    │
   │   / OpenSearch  │              │   pgvector /    │
   │   / Vespa       │              │   Weaviate      │
   └────────┬────────┘              └────────┬────────┘
            │                                │
    top-50 ranked list              top-50 ranked list
    [doc3, doc7, doc1, ...]        [doc1, doc9, doc5, ...]
            │                                │
            └────────────┬───────────────────┘
                         ▼
            ┌────────────────────────────┐
            │   Fusion Layer             │
            │   - RRF (Reciprocal Rank)  │  ← 가장 흔한 선택
            │   - Weighted Score (α)     │
            │   - Learned Fusion         │
            └────────────┬───────────────┘
                         ▼
                 Fused top-50
                         │
                         ▼
            ┌────────────────────────────┐
            │   Reranker                 │  ← 선택: Cross-Encoder
            │   (Cohere Rerank 3,        │     (별도 세션에서 다룸)
            │    bge-reranker-v2-m3)     │
            └────────────┬───────────────┘
                         ▼
                 Final top-k (5~10)
                         │
                         ▼
                    LLM Context
```

융합 방식은 크게 세 갈래다.

**(1) RRF — Reciprocal Rank Fusion (Cormack et al., 2009)**

```
score(d) = Σ   1 / (k + rank_i(d))        (일반적으로 k=60)
         i∈리트리버
```

- **점수가 아니라 '순위'만 쓴다**. BM25 점수(0~수십)와 코사인 유사도(0~1)의 **스케일을 맞출 필요가 없다**. 이게 결정적 장점이다.
- 튜닝할 하이퍼파라미터가 사실상 `k` 하나. 운영에서 안 깨진다.
- Elasticsearch 8.9+ (`rrf` retriever), OpenSearch 2.12+, Weaviate `hybrid` 쿼리, Vespa `global-phase`가 전부 RRF를 **기본값**으로 깐 이유다.

**(2) Weighted Score Fusion — `α * dense + (1-α) * sparse`**

- 점수 정규화 필요(min-max 또는 z-score). 정규화를 매 쿼리마다 리셋해야 하는지, 코퍼스 전체 통계로 할지 선택지가 갈린다.
- α를 질의 유형별로 바꾸는 조건부 가중치가 가능 → 세밀한 튜닝의 여지는 더 크지만, **깨지기 쉽다**. 코퍼스가 바뀌면 α도 바꿔야 한다.
- Weaviate가 `alpha=0.5`를 노출하는 이유.

**(3) Learned Fusion (ColBERT, SPLADE, Hybrid-Attn)**

- 융합 자체를 학습 모델에 맡김. SPLADE는 "sparse 벡터를 학습"하는 접근으로, BM25의 정확성과 Dense의 일반화를 한 모델이 다 하려 함.
- 이론적 상한은 가장 높지만 **학습 파이프라인·버전관리·추론 레이턴시**가 커진다. 조직이 ML 인프라를 이미 갖고 있지 않다면 보통 과하다.

**현장 디폴트는 "RRF + 선택적 Reranker"**다. 복잡성 대비 리콜 상승이 가장 안정적이다.

#### 4. 트레이드오프 매트릭스

| 축 | Sparse Only (BM25) | Dense Only (Vector) | Hybrid (RRF) | Hybrid + Rerank |
|---|---|---|---|---|
| ID/고유명사 리콜 | ★★★★★ | ★ | ★★★★★ | ★★★★★ |
| 의미/의역 리콜 | ★ | ★★★★ | ★★★★ | ★★★★★ |
| 다국어 혼용 | ★★ | ★★★★ | ★★★★ | ★★★★★ |
| 질의 레이턴시 | 20~50ms | 30~80ms | 80~150ms (병렬) | 200~400ms |
| 인프라 비용 | 저 (ES/OS 1클러스터) | 중~고 (Vector DB) | 고 (둘 다) | 고 + Rerank API |
| 운영 복잡도 | 낮음 | 낮음 | **중** (두 인덱스 동기화) | 높음 |
| 콜드 스타트 | 바로 좋음 | 임베딩 품질 의존 | 바로 좋음 | 바로 좋음 |
| 코퍼스 변경 적응 | 즉시 | 재임베딩 필요 | 부분적으로 즉시 | 부분적으로 즉시 |
| 튜닝 가능성 | BM25 파라미터 | 임베딩 모델 교체 | **α, k 둘 다** | +rerank 모델 |

**핵심 숨은 비용**: 두 인덱스(Sparse·Dense)를 **동기화**해야 한다. 문서 하나 삭제됐을 때 양쪽에서 함께 사라지지 않으면, 한쪽에만 유령 문서가 남아 top-k에 섞이고, 사용자는 "지워졌다던 그 FAQ가 왜 아직 뜨냐"는 민원을 넣는다. 이걸 Outbox + CDC로 처리할지, 양쪽에 tx-like 쓰기로 처리할지가 Hybrid 도입 시 가장 과소평가되는 운영 부담이다.

#### 5. 실제 사례 — 왜 다 돌아왔나

**(1) Elastic (2024) — ELSER + Dense 하이브리드 디폴트화**
- 2024년 Elasticsearch 8.14에서 `retrievers`·`rrf` API가 GA. "Vector는 BM25의 대체가 아니라 보완"이라는 걸 벤더가 공식 블로그에 못 박았다.
- ELSER(Elastic Learned Sparse EncodeR) 자체도 sparse+dense의 중간 지점을 노린 학습된 sparse 모델.

**(2) Weaviate `hybrid` 쿼리 (2023 Q4→2024)**
- `alpha=0.5`가 디폴트. 2023년 초만 해도 "Vector 전용"을 밀던 Weaviate가 1년 만에 하이브리드를 전면에 세운 방향 전환.

**(3) Pinecone Sparse-Dense Vectors (2023 Q3 → 2024 serverless 통합)**
- 2023년에 "하이브리드는 다른 DB의 영역"이라던 Pinecone이, 2024년 serverless에서 sparse index 공식 지원. 시장의 신호가 명확했다는 뜻.

**(4) Vespa (Yahoo) — 처음부터 하이브리드**
- Yahoo 검색의 10년 넘은 분산 검색엔진. BM25·ANN·신경망 랭킹을 한 쿼리 플랜에 섞는 설계가 **원래부터** 전제. "Vector DB 열풍 전부터 하이브리드가 정답이었다"는 가장 오래된 증거.

**(5) Perplexity (2024)**
- 공식 블로그·엔지니어링 Q&A에서 수차례 밝힘: 웹 검색은 **BM25(또는 유사한 sparse) + Dense + Rerank** 파이프라인. "Vector only가 되는 순간 Wikipedia의 긴 고유명사·버전 번호·인명이 다 샌다"가 반복 등장하는 설명.

**(6) OpenAI Assistants / GPTs File Search (2024)**
- 벡터만 쓰던 Retrieval을 2024년 중반 **하이브리드**(auto-chunking + keyword + semantic)로 교체. 자체 벤치마크에서 리콜 상승 명시.

**(7) 국내 N 커머스 (앞서 사건) — 2026-03-21 복구**
- Pinecone을 끄지 않고, Elasticsearch 재가동 후 `rrf` retriever로 묶었다. 전환 비용은 재인덱싱 36시간 + 양측 동기화를 위한 Debezium 기반 Outbox 파이프라인 2주. 복구 후 CS 챗봇 DAU 11% → 68%, 리콜(top-10 포함률) 61% → 94%.
- 포스트모템 결론 한 줄: *"BM25는 레거시가 아니라 상보적 자료구조였다."*

**(8) 실패 사례 — 국내 B 보험 (2025)**
- Hybrid를 도입했으나 **α=0.5 가중치 융합**만 쓰고 점수 정규화를 생략. BM25가 코퍼스 변경(약관 개정)으로 IDF가 요동치는 날, Dense 쪽 점수를 완전히 압도해 사실상 BM25 단독 결과만 나왔다. 사용자는 "오늘따라 챗봇이 왜 문자 그대로만 찾냐"고 민원. **RRF로 바꾸는 하루짜리 PR로 종결.** 교훈: 점수 융합을 쓸 거면 정규화·모니터링을 안 할 거면 그냥 RRF.

#### 6. 자주 밟는 함정

1. **"Reranker가 뒤에 있으니까 융합은 대충 해도 된다"** — Reranker는 보통 top-50~100만 본다. 융합 단계에서 **정답이 top-100 밖으로 밀리면** 아무리 좋은 Cross-Encoder도 복구 불가. 융합은 리콜의 1차 방어선이다.
2. **BM25 쪽 분석기(analyzer) 설정을 안 건드린다** — 한국어는 Nori/은전한닢 선택, 복합명사 분해 레벨, 사용자 사전이 리콜을 지배한다. Dense만 튜닝하고 BM25는 디폴트로 둔 하이브리드는 BM25 쪽이 거의 랜덤이 된다.
3. **두 인덱스의 문서 ID를 다르게 쓴다** — 융합할 때 같은 문서인지 매칭 못 하면 RRF가 깨진다. **ID 정책을 쓰기 전에 합의**해야 한다.
4. **쿼리마다 ANN 재인덱스 튜닝을 반복한다** — HNSW `ef_search`를 올리면 Dense는 좋아지지만 레이턴시가 두 배. 하이브리드는 Sparse가 커버해주는 분포가 있으므로 **ef_search를 오히려 낮추고** Sparse에 책임을 넘겨 TPS를 벌 수 있다. 이걸 하지 않고 Dense 쪽만 올리면 비용만 두 배.
5. **A/B 테스트를 Hybrid vs Dense로만 돌린다** — 반드시 **Sparse-only, Dense-only, Hybrid 셋**을 함께 돌려야 어떤 질의 분포가 어느 쪽 덕분인지 분해 가능. 둘만 돌리면 "Hybrid가 조금 좋다"로 끝나고 왜인지 모른다.
6. **Fusion을 리트리버 쪽에 내장 vs 애플리케이션 쪽에 둠을 안 정한다** — Elasticsearch `rrf` 안으로 밀어 넣으면 운영은 편하지만, 여러 다른 소스(ES + Pinecone + 사내 KB API)를 합치려면 결국 애플리케이션 쪽 Fusion이 필요. **처음부터 애플리케이션 쪽에 Fusion 레이어를 두는 게 장기적으로 유연**하다.

#### 7. 언제 쓰고, 언제 쓰면 안 되는가 — 시니어 체크리스트

**✅ 반드시 Hybrid로 가야 하는 경우**
- 검색 대상에 **ID·코드·버전번호·고유명사**가 섞여 있음 (주문/상품/티켓/오류코드/법령조항/약관번호)
- 코퍼스가 **자주 바뀐다** (뉴스, 공지, CS 지식베이스) — Dense 재임베딩은 느리고 비싸다
- 질의 분포가 **긴 꼬리** — 소수의 희귀 질의가 전체 만족도의 20~40%를 좌우
- 다국어·전문용어·신조어가 섞임
- **감사/추적 요구** — "왜 이 문서가 top-k였나" 설명이 BM25 쪽에서 나오는 게 Dense 임베딩 기하학보다 쉽다

**⚠️ 신중해야 하는 경우**
- 코퍼스가 작고(<10만 문서) 균일한 자연어로만 쓰여 있음 → Dense 혼자서도 충분
- 운영 인력이 ES/OS 운영 경험이 없다 → Hybrid 복잡도가 조직 역량 초과
- 질의 분포가 **거의 전부 '의미 기반 자유서술'** (예: "비슷한 분위기 책 추천해줘") → Sparse가 거의 기여 못함, Dense + Rerank가 효율적

**❌ 쓰면 안 되는 경우**
- 사용자가 **구조화된 쿼리**(필터·범위·정렬)만 날리는 어드민 검색 — SQL 또는 관계형 인덱스가 답
- 지식베이스가 사실상 **FAQ 50건** 수준 — 그냥 LLM에 다 컨텍스트로 넣어라 (하이브리드는 과잉 설계)
- 두 인덱스 동기화 파이프라인(CDC/Outbox)을 만들 **엔지니어링 여유가 없고** 데이터가 자주 바뀜 → 유령 문서로 민원이 터진다. 차라리 BM25 단일로 가라
