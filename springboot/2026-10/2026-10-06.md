### `@ConfigurationProperties`는 생성자 바인딩을 쓰지 않으면 **불변 객체가 될 수 없다** — Setter가 강제된다

`@ConfigurationProperties`를 필드에 바인딩하려면 Setter가 반드시 있어야 한다. `final` 필드로 불변 설정을 만들고 싶다면 `@ConstructorBinding`을 명시적으로 붙이거나 Spring Boot 3.x부터는 생성자가 하나뿐일 때 자동으로 생성자 바인딩이 동작한다는 점을 활용해야 한다. Setter를 열어두면 런타임에 누군가 설정값을 바꿀 수 있는 보안 리스크가 생긴다.

```java
// ❌ Setter 강제 — 가변 객체
@ConfigurationProperties(prefix = "app")
public class AppProperties {
    private String name;
    public void setName(String name) { this.name = name; }
}

// ✅ 생성자 바인딩 — 불변
@ConfigurationProperties(prefix = "app")
public class AppProperties {
    private final String name;
    public AppProperties(String name) { this.name = name; }
}
```

> 💡 **왜 중요한가**: 설정은 애플리케이션 시작 시점에 확정되어야 하는 **불변값**이다 — 런타임에 바뀔 수 있다는 가능성 자체가 디버깅 지옥을 만든다.

---

### `JpaRepository.save()`는 **엔티티가 영속 상태면 아무 일도 하지 않는다** — 호출 자체가 불필요하다

`save()`는 내부적으로 `persist()`나 `merge()`를 호출하는데, 이미 영속 상태(managed)인 엔티티라면 둘 다 호출되지 않는다. 더티 체킹이 트랜잭션 커밋 시점에 자동으로 UPDATE를 날리기 때문이다. 그런데 많은 개발자가 "안전하게" `save()`를 반복 호출하다가 `@Version` 기반 낙관적 락이 걸린 엔티티에서 **버전이 꼬이는 버그**를 만든다.

```java
@Transactional
public void updateUser(Long id, String name) {
    User user = userRepository.findById(id).orElseThrow();
    user.changeName(name);
    userRepository.save(user); // ❌ 불필요 — 더티 체킹으로 이미 UPDATE됨
}
```

> 💡 **왜 중요한가**: JPA는 **상태 기반**이지 **명령 기반**이 아니다 — `save()`를 "저장 버튼"처럼 쓰는 순간 JPA의 설계 철학과 충돌한다.
