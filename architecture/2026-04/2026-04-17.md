### Bounded Context — "같은 단어, 다른 의미"를 인정하는 순간 도메인 모델이 살아난다

DDD를 처음 접한 팀이 가장 흔히 저지르는 실수는 **"우리 회사의 User는 하나여야 한다"**는 강박이다. 회원가입, 주문, 배송, 정산, CS 상담까지 모두 같은 `User` 엔티티를 공유하려 든다. 그 결과 `User` 클래스는 30개 필드짜리 괴물이 되고, 마케팅팀이 "생일 필드 하나 추가하자"고 하면 결제 시스템의 배포까지 흔들린다. **Bounded Context(경계 컨텍스트)는 이 문제의 근본 원인이 "모델의 크기"가 아니라 "언어의 경계 부재"라고 말한다.**

Bounded Context란 **하나의 유비쿼터스 언어(Ubiquitous Language)가 일관되게 통용되는 명시적 경계**다. 같은 "상품"이라도 **주문 컨텍스트의 상품**(가격·재고·옵션)과 **카탈로그 컨텍스트의 상품**(설명·이미지·SEO 메타)과 **정산 컨텍스트의 상품**(공급가·수수료율·세율)은 서로 다른 모델이어야 한다. 이들을 억지로 하나로 통합하면, 각 컨텍스트의 요구사항 변화가 다른 컨텍스트를 오염시킨다.

```
┌─────────────────────────────────────────────────────────────┐
│                     E-commerce Platform                     │
│                                                             │
│  ┌──────────────────┐         ┌──────────────────┐          │
│  │  Catalog Context │         │  Order Context   │          │
│  │                  │         │                  │          │
│  │  Product         │◄────────│  Product         │          │
│  │  - name          │  ACL    │  - productId     │          │
│  │  - description   │ (번역)  │  - unitPrice     │          │
│  │  - images[]      │         │  - quantity      │          │
│  │  - seoTags       │         │  - snapshotName  │          │
│  │                  │         │                  │          │
│  │  Language:       │         │  Language:       │          │
│  │  "노출", "진열"  │         │  "주문", "결제"  │          │
│  └──────────────────┘         └──────────────────┘          │
│           ▲                            │                    │
│           │ Published Language          │ Domain Event      │
│           │ (REST API)                  │ (OrderPlaced)     │
│           │                             ▼                   │
│  ┌──────────────────┐         ┌──────────────────┐          │
│  │  Search Context  │         │Settlement Context│          │
│  │                  │         │                  │          │
│  │  Product         │         │  Product         │          │
│  │  - indexedName   │         │  - supplyPrice   │          │
│  │  - facets[]      │         │  - feeRate       │          │
│  │  - popularity    │         │  - taxCategory   │          │
│  └──────────────────┘         └──────────────────┘          │
└─────────────────────────────────────────────────────────────┘

           Context Map: 컨텍스트 간 관계를 명시적으로 표현
```

**컨텍스트 간 관계(Context Map)의 7가지 패턴** 중 실무에서 자주 마주치는 것은 4가지다.

| 패턴 | 관계 | 언제 쓰나 |
|------|------|-----------|
| **Shared Kernel** | 두 컨텍스트가 일부 모델을 공유 | 팀이 매우 밀접, 변경 조율 가능할 때만 (위험) |
| **Customer/Supplier** | 상류(공급)-하류(소비) 관계, 하류의 요구가 상류에 반영됨 | 사내 팀 간 협업 가능할 때 |
| **Conformist** | 하류가 상류 모델을 그대로 수용 | 외부 API(PG사, 배송사) 등 통제 불가할 때 |
| **Anti-Corruption Layer (ACL)** | 하류가 번역 계층을 두어 상류 모델의 오염을 차단 | 레거시 통합, 외부 시스템 연동 시 필수 |

**트레이드오프**: Bounded Context는 공짜가 아니다. 같은 "고객"에 대한 데이터가 여러 컨텍스트에 **의도적으로 중복 저장**된다. 주문 컨텍스트는 주문 시점의 배송지 스냅샷을 갖고, 회원 컨텍스트는 현재 배송지를 갖는다. 이는 데이터베이스 관점에서는 "정규화 위반"이지만, 도메인 관점에서는 **"주문의 배송지"와 "회원의 현재 배송지"가 애초에 다른 개념**이라는 사실을 반영한 것이다. 데이터 일관성은 도메인 이벤트로 최종 일관성(Eventual Consistency)을 통해 맞춘다.

또 하나의 함정: **Bounded Context = 마이크로서비스가 아니다.** Bounded Context는 **논리적 경계**이고, 배포 단위는 **물리적 결정**이다. Amazon도 초기에는 하나의 모노리스 안에서 여러 Bounded Context를 모듈로 분리해 운영했고, 필요에 따라 점진적으로 서비스로 분리했다. 시니어 관점의 원칙은 명확하다: **먼저 Bounded Context로 논리적 경계를 그어라. 서비스 분리는 조직·확장성·배포 주기가 요구할 때 하라.**

**실제 사례**:
- **쿠팡**은 "상품"이 카탈로그·판매·물류·정산에서 완전히 다른 모델로 운영된다. 판매자가 등록하는 "상품"과 물류센터가 관리하는 "SKU"의 관계는 ACL을 통해 매핑되며, 이 덕분에 판매자 정책 변경이 물류 시스템을 흔들지 않는다.
- **Netflix**는 "Title(작품)"이라는 개념을 스튜디오 계약 컨텍스트, 스트리밍 재생 컨텍스트, 추천 컨텍스트에서 각각 다른 모델로 관리한다. 재생 컨텍스트의 Title은 재생 가능한 인코딩 매니페스트를 의미하지만, 계약 컨텍스트의 Title은 지역별 라이선스 만료일을 의미한다.
- **우아한형제들(배민)**은 초기 모노리스에서 주문·결제·배달·정산을 하나의 `Order` 테이블로 관리하다가 정산팀과 배달팀의 배포 주기가 서로를 방해하는 지경에 이르자 Bounded Context 단위로 재설계했다. 지금은 각 컨텍스트가 독립된 데이터베이스와 도메인 모델을 갖는다.

**언제 쓰지 말아야 하나**: 도메인 자체가 단순하거나(예: 사내 admin 툴), 팀이 5명 이하의 단일 팀이라면 Bounded Context를 억지로 나누는 것이 오히려 오버엔지니어링이다. 이 경우엔 하나의 컨텍스트 안에서 애그리거트 경계만 명확히 잡는 것으로 충분하다. Bounded Context는 **"서로 다른 언어를 쓰는 팀이 존재할 때"** 비로소 그 값어치를 한다.

> 💡 **왜 중요한가**: 애그리거트가 "일관성의 경계"라면, Bounded Context는 **"의미의 경계"**다 — 같은 단어가 다른 뜻이 되는 지점을 인정하지 않으면 어떤 아키텍처 패턴도 대형 도메인을 구원하지 못한다.
