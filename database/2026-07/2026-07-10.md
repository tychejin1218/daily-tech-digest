### PostgreSQL `REINDEX CONCURRENTLY` — 서비스 중단 없이 부풀어 오른 인덱스 되살리기

잦은 `UPDATE`·`DELETE`로 인덱스가 팽창(bloat)하면 스캔 속도가 느려지고 디스크도 낭비된다. `REINDEX INDEX CONCURRENTLY idx_name`은 새 인덱스를 백그라운드에서 만든 뒤 원자적으로 교체하므로, 읽기·쓰기를 막지 않고도 인덱스를 재구축할 수 있다.

```sql
-- 팽창도 확인 (pgstattuple 확장 필요)
SELECT schemaname, indexname, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes
WHERE indexrelname = 'orders_status_idx';

-- 서비스 중단 없이 재구축
REINDEX INDEX CONCURRENTLY orders_status_idx;
```

> 💡 **왜 중요한가**: `REINDEX` 기본 옵션은 테이블에 배타 락을 걸어 트래픽을 마비시키지만, `CONCURRENTLY`는 운영 중에도 안전하게 인덱스 건강을 회복시킨다.

### MySQL `Gap Lock`과 `REPEATABLE READ`의 팬텀 락 함정 — 존재하지 않는 행까지 잠기는 이유

InnoDB의 기본 격리 수준인 `REPEATABLE READ`에서는 인덱스 범위 조회 시 존재하지 않는 "간격(gap)"까지 잠근다. `WHERE id BETWEEN 10 AND 20 FOR UPDATE`는 실제로 없는 `id=15`에도 락을 걸어, 다른 트랜잭션의 `INSERT id=15`를 대기시키거나 데드락을 유발한다.

```sql
-- 트랜잭션 A: id 10~20 범위 조회
BEGIN;
SELECT * FROM orders WHERE id BETWEEN 10 AND 20 FOR UPDATE;
-- 이 순간 (5, 25) 사이 전체 gap이 잠김

-- 트랜잭션 B: 대기 발생
INSERT INTO orders (id, ...) VALUES (15, ...);  -- 블록!

-- 회피: READ COMMITTED로 낮추거나, PK 단건 조회로 좁히기
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

> 💡 **왜 중요한가**: 범위 잠금과 삽입 충돌의 원인을 모르면 "왜 쓰지도 않은 행에서 데드락이 나지?" 라는 미궁의 장애를 반복하게 된다.
