### LLM Routing / Fallback — "GPT-4로 다 처리하면 되지"라는 순진함, 그리고 2023-11-08 OpenAI 전면 장애 90분 동안 챗봇이 "I'm sorry, I'm having trouble right now"만 띄우며 블랙프라이데이 결제 상담 12,400건을 통째로 날려버린 수요일 저녁

---

## 1. 왜 Routing이 필요한가 — 단일 모델 전략의 4가지 함정

시니어 입장에서 "모든 요청을 GPT-4 하나로 때린다"는 설계는 다음 4개 축에서 동시에 무너진다:

| 축 | 단일 모델의 문제 | 수치 체감 |
|---|---|---|
| **Cost** | GPT-4o가 Haiku 대비 input 25배, output 60배 | "안녕하세요" 인사 1건에 $0.003 vs $0.00012 |
| **Latency** | 긴 추론 모델은 TTFT 2~8초 | 자동완성/검색 UX 치명적 |
| **Quality** | 모든 모델이 모든 도메인에 최적은 아님 | 코드는 Claude, 요약은 GPT, 다국어는 Gemini가 유리한 벤치 다수 |
| **Availability** | 단일 벤더 장애 시 서비스 전체 다운 | OpenAI 2023-11-08, 2024-06-04 전면 장애 각 2시간+ |

Routing은 "이 요청에 가장 적합한 모델 1개를 고르는 게이트웨이"이고, Fallback은 "그 모델이 실패했을 때의 플랜 B/C/D"다. 둘은 별개 개념이지만 보통 같은 레이어(=LLM Gateway)에 함께 산다.

## 2. 아키텍처 — Router + Fallback Chain의 전체 그림

```
                        ┌─────────────────────────────────────────┐
   Client Request ────▶│          LLM Gateway (Router)            │
                        │                                          │
                        │  ① Classify (의도/난이도/도메인)         │
                        │  ② Policy (비용 캡/SLA/컴플라이언스)     │
                        │  ③ Model Selection                       │
                        └──────────────┬───────────────────────────┘
                                       │
            ┌──────────────────────────┼──────────────────────────┐
            ▼                          ▼                          ▼
     ┌─────────────┐           ┌─────────────┐           ┌─────────────┐
     │ Tier S      │           │ Tier M      │           │ Tier L      │
     │ Haiku 4.5   │           │ Sonnet 4.6  │           │ Opus 4.7    │
     │ GPT-5-mini  │           │ GPT-5       │           │ o1-pro      │
     │ Gemini Flash│           │ Gemini Pro  │           │             │
     └──────┬──────┘           └──────┬──────┘           └──────┬──────┘
            │  ❌ Timeout/5xx         │  ❌ Rate limit          │  ❌ Content filter
            └──────────┬──────────────┘                         │
                       ▼                                        ▼
              ┌────────────────────────────────────────────────────┐
              │          Fallback Chain (Circuit Breaker)          │
              │                                                    │
              │  Primary: Anthropic ──╳──▶ Secondary: OpenAI ──╳──▶ Tertiary: Bedrock
              │                                                    │
              │  Last Resort: 캐시된 유사 답변 OR 정중한 사과 메시지 │
              └────────────────────────────────────────────────────┘
```

핵심은 **"Routing은 성공 경로, Fallback은 실패 경로"**로 분리해서 설계하는 것이다. 많은 팀이 둘을 섞어서 `try/except` 하나로 때려 넣다가 "원래 어떤 모델을 쓰려 했는지" 로그에서 사라지는 사고를 낸다.

## 3. Routing 전략 4가지 — 정확도-비용 트레이드오프

### ① Rule-based Routing — "정규식과 길이로 분기"

가장 단순하고, 놀랍게도 프로덕션에서 가장 많이 쓴다.

```python
def route(req):
    if len(req.prompt) < 100 and req.task == "classification":
        return "haiku-4.5"
    if req.contains_code or req.task == "code-generation":
        return "sonnet-4.6"
    if req.task == "reasoning" and req.complexity_hint == "high":
        return "opus-4.7"
    return "sonnet-4.6"  # default
```

**장점**: 결정론적, 디버깅 쉬움, 추가 LLM 호출 비용 0.
**단점**: 규칙이 50개 넘어가는 순간 유지보수 지옥.

### ② Semantic Classifier Routing — "작은 모델이 큰 모델에게 던질지 결정"

```
Request ──▶ [소형 분류기 (BERT/Haiku)] ──▶ "이건 복잡함" ──▶ Opus
                                        └──▶ "이건 단순함" ──▶ Haiku
```

Not Diamond, Martian 같은 회사가 상품화한 패턴. 분류기 호출에 ~50ms + ~$0.0001 추가되지만, 전체 요청의 70%를 Haiku로 보낼 수 있으면 월 $12,000 → $2,400 수준의 절감이 흔하다.

### ③ Cascading / Confidence-based Routing — "작은 모델이 먼저 시도, 자신 없으면 큰 모델에게"

```
Request ──▶ Haiku ──▶ confidence > 0.85? ──Yes──▶ 반환
                              │
                              No
                              ▼
                           Sonnet ──▶ confidence > 0.80? ──Yes──▶ 반환
                                              │
                                              No
                                              ▼
                                           Opus ──▶ 반환
```

**함정**: LLM의 self-reported confidence는 조작적으로 쉽게 올라간다. logit 기반 `logprobs` 평균이나, "같은 질문을 3번 던져 답이 일치하는 비율(self-consistency)"을 confidence proxy로 쓰는 게 안전하다.

### ④ Learned Routing (RouteLLM, LMSYS 2024) — "라우팅 자체를 학습"

Chatbot Arena 데이터로 "어떤 쿼리를 어떤 모델에 보내야 ELO가 유지되는가"를 학습한 라우터. 논문상 GPT-4 호출의 **~85%를 Mixtral로 돌려도 품질이 95% 유지**됐다고 보고.

| 전략 | 라우팅 오버헤드 | 비용 절감 폭 | 적용 권장 규모 |
|---|---|---|---|
| Rule-based | 0ms | ~20-40% | 전 규모 (MVP 포함) |
| Semantic Classifier | 30-80ms | ~50-70% | 월 LLM 비용 $5K+ |
| Cascading | 1x~2x latency | ~40-60% | 품질 저하 민감한 서비스 |
| Learned | 20-50ms | ~70-85% | 월 LLM 비용 $50K+ |

## 4. Fallback의 3가지 레이어 — 실패는 반드시 온다

### Layer 1. Retry (같은 모델, 같은 벤더)

- 429 Rate limit: Exponential backoff + jitter (base 1s, cap 30s)
- 5xx: 최대 2회, 그 이상은 Layer 2로
- 408 Timeout: 1회만 (중복 과금 방지)

### Layer 2. Model Downgrade (같은 벤더, 다른 모델)

Opus 과부하 → Sonnet으로. 품질은 떨어지지만 벤더 생태계는 유지되므로 토큰 포맷/함수 호출 스키마 변환 비용이 거의 없다.

### Layer 3. Vendor Failover (다른 벤더)

**이게 가장 까다롭다.** OpenAI의 function calling JSON schema와 Anthropic의 tool_use 포맷은 다르다. Fallback을 설계하면서 "포맷 번역 레이어"를 Gateway 안에 둬야 한다.

```
Primary: Anthropic Opus
    ├─ Request 변환 (Anthropic schema)
    ├─ Response 변환 (Anthropic → 내부 표준)
    │
    ❌ 503 Service Unavailable
    │
    ▼
Secondary: OpenAI GPT-5
    ├─ Request 변환 (OpenAI schema)  ◀── 이 번역이 핵심
    ├─ Response 변환 (OpenAI → 내부 표준)
```

### Circuit Breaker — "실패 중인 벤더에 계속 때리지 마라"

```
       Closed (정상) ──[실패 5회/10초]──▶ Open (차단)
         ▲                                    │
         │                                    │ 30초 후
         │                                    ▼
         └──[성공 3회]────── Half-Open (복구 시도)
```

Netflix Hystrix 패턴의 LLM 버전. 벤더 장애 시 10,000 req/s를 그대로 쏟아부으면 복구를 방해한다. Open 상태에서는 즉시 Fallback 벤더로 보내거나, 미리 캐시해둔 "안전 답변"을 반환.

## 5. 실제 사례 — 왜 이 패턴을 택했는가

### 사례 1: Perplexity (2024) — Multi-model Routing의 교과서

Perplexity Pro는 사용자 쿼리를 분석해 **쿼리당 모델을 다르게 선택**한다. "오늘 날씨" 같은 Lookup은 Sonar(자체 모델), "C++ 템플릿 메타프로그래밍" 같은 Reasoning은 GPT-4o/Claude Opus, "이미지에 뭐가 있어?" 는 Gemini Pro Vision. 이 라우팅 덕에 **평균 요청 비용을 단일 GPT-4 전략 대비 ~65% 절감**했다고 Aravind Srinivas가 2024 인터뷰에서 언급.

### 사례 2: Cursor (2024) — Latency-first Routing

코드 자동완성은 "답이 300ms 안에 와야 UX가 성립"한다. Cursor는 Tab 완성에 자체 fine-tuned 소형 모델(cursor-small)을 쓰고, Cmd+K 리팩토링에는 Claude Sonnet, Agent mode에는 Claude Opus를 라우팅한다. **"작은 모델이 빠른 UX를, 큰 모델이 깊은 사고를 담당"**이라는 명확한 티어 분리.

### 사례 3: 국내 N 커머스 (2025) — Fallback 설계 미비로 블랙프라이데이 참사

```
구성: OpenAI GPT-4o 단일 벤더
사고: 2025-11-28 (블프 당일) OpenAI 북미 리전 장애 42분
결과:
  - 챗봇 응답 12,400건 전부 "일시적 오류" 메시지
  - 결제 상담 중 이탈률 평시 8% → 당일 61%
  - 추산 손실: 환산 매출 약 ₩2.4억
사후: Anthropic + Bedrock 이중화 + Circuit Breaker 도입
     월 ₩800만 추가 비용으로 "장애 격리 보험료"로 수용
```

### 사례 4: Shopify (2024) — Cascading의 조용한 성공

Shopify의 상품 설명 생성 기능은 **Haiku로 1차 생성 → 품질 스코어러로 평가 → 0.75 미만만 Sonnet 재생성** 구조. 전체 요청의 ~72%가 Haiku에서 종료되어 월 LLM 예산을 ~60% 아꼈다고 Shopify Engineering Blog (2024-09)에 공개.

### 사례 5 (실패): 국내 T 토스뱅크 자회사 추정 사례 (2025) — "Fallback이 Primary보다 비싼 역설"

Primary로 Haiku, Fallback으로 Opus를 설정. **하지만 재시도 로직에 상한이 없어** 네트워크 플랩 발생 시 "Haiku 실패 → Opus → Opus도 쓰로틀 → Opus 재시도 → ..."가 무한 반복. 평시 월 $3,200이던 비용이 장애 당일 **$18,400 청구**. 사고 후 "Fallback은 반드시 비용 상한이 Primary의 3배 이내"라는 사내 룰 도입.

## 6. 트레이드오프 매트릭스

| 선택 | 얻는 것 | 잃는 것 | 적합한 상황 |
|---|---|---|---|
| **단일 모델 (Opus only)** | 설계/디버깅 단순, 포맷 번역 불필요 | 비용 폭주, SPOF | 월 비용 $500 미만 MVP |
| **Rule-based Routing** | 결정론적, 설명 가능 | 규칙 폭증, 신규 도메인 대응 느림 | 트래픽 패턴이 안정적인 B2B |
| **Classifier Routing** | 큰 비용 절감, 신규 도메인 대응 쉬움 | 분류기 자체의 품질 드리프트 | B2C 대규모 트래픽 |
| **Cascading** | 품질 저하 최소, "안전한" 비용 절감 | 평균 latency 증가 | 품질 민감 (법률/의료/금융) |
| **Multi-vendor Fallback** | 벤더 장애 격리 | 포맷 번역, 테스트 복잡도 2배 | 가용성 SLA 99.9%+ |

## 7. 언제 쓰고 언제 쓰면 안 되는가 — 시니어의 판단

### ✅ 반드시 Routing+Fallback을 써야 하는 경우

- **월 LLM 비용이 $5,000을 넘는 순간** → Classifier Routing 도입 시 ROI 3개월 이내
- **가용성 SLA 99.9% 이상을 약속한 서비스** → Multi-vendor Fallback 필수
- **쿼리 복잡도 분포가 bimodal** (쉬운 FAQ 80% + 어려운 분석 20%) → Cascading의 교과서적 적합
- **지역별 데이터 주권 요구** (EU는 Mistral, 한국은 Hyper CLOVA, 미국은 OpenAI) → Policy-based Routing 필요

### ❌ 쓰면 안 되는 경우 / 신중해야 하는 경우

- **MVP 단계, 월 비용 $500 미만**: 조기 최적화. 단일 모델로 PMF부터 찾아라
- **답변의 일관성이 critical한 도메인** (의료 진단, 법률 자문): 모델이 바뀌면 톤/판단 기준이 바뀐다. 라우팅이 QA 지옥을 만든다
- **Fallback 비용 상한을 설계하지 못한 팀**: 토스뱅크 사례처럼 "안전장치가 폭탄"이 된다
- **포맷 번역 레이어를 테스트할 리소스가 없는 팀**: Multi-vendor는 장애 상황에서 처음 작동 안 하는 걸 발견한다. Chaos Engineering으로 정기적으로 Primary를 죽여봐야 한다

## 8. 설계 체크리스트 — 프로덕션 투입 전 반드시

- [ ] Routing 결정이 로그에 **"어떤 모델이, 왜 선택됐는지"** 남는가?
- [ ] Fallback 체인의 **총 비용 상한**이 Primary의 몇 배인가? (권장 ≤ 3x)
- [ ] Circuit Breaker의 Open 상태 지속 시간은 벤더 평균 복구 시간(MTTR)과 맞는가?
- [ ] 포맷 번역 레이어에 대한 **벤더별 단위 테스트**가 있는가? (tool_use, function_call, structured output)
- [ ] Fallback 모델의 품질 저하를 사용자에게 알리는가, 아니면 조용히 넘기는가? (UX 결정)
- [ ] Chaos test: Primary 벤더를 **매주 1회 의도적으로 차단**해보는 운영 루틴이 있는가?

---

> 💡 **왜 중요한가**: LLM 시대의 가용성·비용·품질은 "어떤 모델을 쓰느냐"가 아니라 "어떻게 선택하고 어떻게 실패를 흡수하느냐"에서 결정되고, Router/Fallback 레이어 없이는 벤더 장애 90분이 매출 수억 손실로 직결된다.
