### Database Tip 1: PostgreSQL `TOAST`(The Oversized-Attribute Storage Technique) — 8KB 페이지에 들어가지 않는 거대한 값을 "몰래 쪼개서" 별도 테이블에 숨기는 투명한 압축 창고

PostgreSQL의 기본 페이지 크기는 8KB인데, `TEXT`/`JSONB`/`BYTEA`에 수 MB짜리 값이 들어오면 한 행이 페이지를 넘어버린다. TOAST는 이런 거대 컬럼을 자동으로 압축하고, 그래도 크면 `pg_toast_<oid>` 라는 비밀 테이블에 2KB 청크로 쪼개 저장한 뒤 원본 자리엔 포인터만 남긴다. 애플리케이션은 `SELECT *`만 해도 투명하게 복원되지만, 대신 `SELECT huge_json_col`을 하는 순간 수십 번의 랜덤 I/O가 터지는 숨은 비용이 발생한다.

```
[일반 테이블 users]           [비밀 테이블 pg_toast_12345]
+----+--------+----------+     +--------+---------+-------+
| id | name   | bio_ptr  |---->| chunk_ | chunk_  | data  |
+----+--------+----------+     | id     | seq     |       |
                               +--------+---------+-------+
                               | 101    | 0       | "안녕..."|
                               | 101    | 1       | "하세..."|
```

실무 트레이드오프: `JSONB` 컬럼 하나에 큰 로그를 쌓는 순간 `SELECT id, created_at FROM logs`는 빠르지만 `SELECT * FROM logs`는 수십 배 느려진다. 해결책은 (1) 핫 컬럼과 콜드 컬럼을 테이블 분리, (2) `ALTER TABLE ... SET STORAGE EXTERNAL`로 압축 끄고 조회 속도 우선, (3) `ALTER TABLE ... SET STORAGE MAIN`으로 TOAST를 피해 인라인 저장 등이 있다. Netflix는 `JSONB`에 재생 메타데이터를 통째로 저장하다 TOAST 폭발로 리포팅 쿼리가 분 단위로 느려지자 핫/콜드 컬럼 분리로 전환했다.

> 💡 **왜 중요한가**: `SELECT *`가 공짜라는 착각은 TOAST가 쪼개둔 수십 개 청크를 매번 조립하는 숨은 랜덤 I/O 때문에 깨진다.

### Database Tip 2: JPA `@Version`과 Optimistic Locking — "마지막에 쓴 사람이 이기는" Last-Write-Wins 참사를 버전 번호 하나로 막는 낙관적 동시성 제어

두 사용자가 같은 주문을 동시에 수정하면 트랜잭션은 각자 커밋되지만 나중에 쓴 쪽이 조용히 이전 변경을 덮어버린다 — 이것이 `Lost Update` 문제다. `@Version` 필드를 붙이면 Hibernate가 `UPDATE ... SET ..., version = version + 1 WHERE id = ? AND version = ?`로 쿼리를 바꾸고, 영향 받은 행이 0이면 `OptimisticLockException`을 던져 커밋을 거부한다. DB 락 없이 "충돌이 날 때만" 실패시키는 접근이라, 읽기가 많고 쓰기 충돌이 드문 워크로드에 이상적이다.

```java
@Entity
public class Order {
    @Id private Long id;
    private int quantity;

    @Version
    private Long version;  // Hibernate가 자동 관리
}

// 트랜잭션 A, B가 동시에 version=5인 주문을 읽음
// A가 먼저 커밋: UPDATE orders SET quantity=10, version=6 WHERE id=1 AND version=5  → 성공
// B가 커밋 시도: UPDATE orders SET quantity=20, version=6 WHERE id=1 AND version=5  → 0 rows → 예외!
```

비관적 락(`SELECT ... FOR UPDATE`)과의 트레이드오프: 비관적 락은 충돌을 "원천 봉쇄"하지만 모든 트랜잭션이 대기하며 데드락과 커넥션 풀 고갈을 부른다. 낙관적 락은 동시성은 높지만 충돌 시 재시도 로직(Spring Retry, `@Retryable`)이 필수다. Shopify는 재고 차감에 처음엔 비관적 락을 썼지만 블랙 프라이데이에 락 경합으로 API가 마비되자, 낙관적 락 + 지수 백오프 재시도로 전환해 TPS를 8배 끌어올렸다. 반대로 잔액 이체처럼 재시도가 비즈니스적으로 애매한 경우엔 여전히 비관적 락이 안전하다.

> 💡 **왜 중요한가**: 동시성 제어를 "모든 쓰기를 직렬화"가 아니라 "충돌이 났을 때만 실패"로 바꾸면 처리량과 정합성을 동시에 잡을 수 있다.
