### 1. PostgreSQL `pg_locks` + `pg_blocking_pids()`로 락 대기 그래프 추적하기
"왜 갑자기 응답이 멈췄지?"의 원인이 락 대기일 때, `pg_stat_activity`만 보면 누가 누구를 막고 있는지가 모호하다. 9.6+의 `pg_blocking_pids(pid)`는 각 세션을 막고 있는 PID 배열을 반환해, 한 쿼리로 "대기 → 차단자" 화살표 그래프를 만들 수 있다. 운영 장애에서 가장 먼저 돌려야 할 진단 쿼리 중 하나다.

```sql
SELECT a.pid,
       a.state,
       now() - a.xact_start  AS xact_age,
       pg_blocking_pids(a.pid) AS blocked_by,
       left(a.query, 80)     AS query
FROM pg_stat_activity a
WHERE a.state <> 'idle'
ORDER BY xact_age DESC NULLS LAST;
```

> 💡 **왜 중요한가**: "느린 쿼리"가 아니라 "락 대기 사슬"이 원인인 장애는 일반 APM으로는 잘 안 잡히는데, 이 쿼리 한 번이면 누구의 긴 트랜잭션이 전체를 막고 있는지 즉시 보인다.

### 2. JPA `@DynamicInsert`로 NULL 컬럼을 INSERT 문에서 빼고 DB 기본값 살리기
JPA 기본 동작은 모든 컬럼을 포함한 단일 INSERT를 캐시해 재사용하기 때문에, 엔티티 필드가 null이면 `INSERT ... VALUES (..., NULL, ...)`로 들어가 DB의 `DEFAULT` 값과 트리거 보정이 모두 무력화된다. `@DynamicInsert`를 붙이면 값이 있는 컬럼만 INSERT에 포함되어 DB 측 기본값이 살아난다. 단 INSERT마다 SQL 생성 비용이 들고 Statement Cache 효과가 줄어드는 트레이드오프가 있어, 기본값이 정말 살아 있어야 하는 테이블에만 선택적으로 적용한다.

```java
@Entity
@DynamicInsert
public class Audit {
    @Id @GeneratedValue Long id;
    String actor;
    @Column(insertable = true, updatable = false)
    Instant createdAt;     // DB default: now()
    String status;         // DB default: 'PENDING'
}
```

> 💡 **왜 중요한가**: 감사·이력 테이블처럼 "DB가 시간·기본 상태를 결정해야 하는" 케이스에서 코드가 명시적으로 null을 박아 DB 기본값을 깨뜨리는 흔한 함정을 피할 수 있다.
