### MySQL `Index Condition Pushdown (ICP)` — 인덱스가 "일단 다 가져와서 서버에서 걸러라" 대신 스토리지 엔진에서 미리 거르게 만드는 최적화

`WHERE age > 30 AND name LIKE '%김%'` 같은 쿼리에서 인덱스가 `(age, name)`이라도, `LIKE '%김%'`은 인덱스로 못 쓴다. ICP 없이는 MySQL 서버 레이어가 스토리지 엔진에게 "age > 30인 행을 다 달라"고 요청받아 테이블을 읽은 뒤 서버에서 `name` 조건을 검사하지만, ICP가 켜지면 인덱스 엔트리에 있는 `name` 값을 스토리지 엔진 레이어에서 먼저 검사해 조건에 안 맞는 행은 테이블 접근(random I/O) 자체를 건너뛴다. `EXPLAIN` 결과의 `Extra` 컬럼에 `Using index condition`이 뜨면 ICP가 적용된 것이고, 안 뜨면 인덱스 구성을 재검토할 신호다.

> 💡 **왜 중요한가**: 같은 인덱스, 같은 쿼리인데 MySQL 5.6 이후로 조용히 10~100배 빨라진 이유가 여기에 있고, 인덱스 컬럼 순서를 잘못 잡으면 이 최적화를 통째로 놓친다.

### PostgreSQL `CLUSTER` vs `pg_repack` — 테이블을 인덱스 순서로 물리 정렬하되, 락 없이 하고 싶다면

PostgreSQL은 MySQL InnoDB와 달리 클러스터드 인덱스가 없어서, 오래된 테이블은 물리적 순서와 인덱스 순서가 완전히 어긋나 범위 스캔(`WHERE created_at BETWEEN ...`)이 랜덤 I/O 폭탄이 된다. `CLUSTER` 명령이 테이블을 특정 인덱스 순서로 물리 재배치해 이 문제를 해결하지만, 실행 중 테이블 전체에 `ACCESS EXCLUSIVE LOCK`을 걸어 프로덕션에서는 사실상 못 쓴다. `pg_repack` 확장은 트리거로 변경분을 새 테이블에 실시간 반영하면서 백그라운드로 복사한 뒤 짧은 락으로 스왑하는 방식이라, 서비스 중단 없이 같은 효과를 낸다.

> 💡 **왜 중요한가**: "인덱스는 있는데 왜 이렇게 느리지?"의 답이 인덱스가 아니라 힙의 물리 배치인 경우가 많고, 이걸 해결하는 도구 선택이 다운타임을 결정한다.
