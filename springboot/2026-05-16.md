### 1. `ProblemDetail`과 `@RestControllerAdvice`로 RFC 7807 표준 에러 응답 일원화하기

Spring Framework 6부터 도입된 `ProblemDetail` 클래스를 사용하면 RFC 7807 표준을 따르는 일관된 에러 응답 포맷을 손쉽게 만들 수 있습니다. `@RestControllerAdvice`에서 `ResponseEntityExceptionHandler`를 상속하거나 직접 `ProblemDetail.forStatusAndDetail()`을 반환하면, `type`, `title`, `status`, `detail`, `instance` 필드를 표준화된 JSON으로 클라이언트에 전달할 수 있습니다. `setProperty()`로 커스텀 필드(traceId, errorCode 등)도 추가 가능합니다.

> 💡 **왜 중요한가**: 마이크로서비스 간 통신이나 외부 API 노출 시 표준화된 에러 포맷은 클라이언트 측 에러 처리 로직을 단순화하고 디버깅 시간을 크게 줄여줍니다.

### 2. `@Async`와 `AsyncTaskExecutor` 분리로 가상 스레드 환경에서도 컨텍스트 전파 안전하게 처리하기

Spring Boot 3.2+에서 가상 스레드와 `@Async`를 함께 쓸 때는 `SimpleAsyncTaskExecutor`에 `setVirtualThreads(true)`를 지정한 별도 빈을 등록하고, `@Async("커스텀빈이름")`으로 명시하는 것이 안전합니다. 기본 `applicationTaskExecutor`만 의존하면 SecurityContext나 MDC가 누락되기 쉬우므로, `DelegatingSecurityContextAsyncTaskExecutor`로 감싸거나 `TaskDecorator`를 등록해 ThreadLocal 기반 컨텍스트를 명시적으로 전파해야 합니다.

> 💡 **왜 중요한가**: 비동기 메서드에서 인증 정보나 로그 추적 ID가 사라지면 권한 오류와 로그 추적 불가 문제가 동시에 발생하므로, 초기 설계 단계에서 명확히 분리해두면 운영 단계의 디버깅 비용을 막을 수 있습니다.
