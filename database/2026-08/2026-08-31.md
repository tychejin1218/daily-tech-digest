### MySQL `EXPLAIN ANALYZE` — 예상 실행 계획이 아닌, 실제로 흘러간 시간을 초 단위로 되감기

`EXPLAIN`은 옵티마이저가 "이렇게 할 예정"이라고 답하는 청사진이고, `EXPLAIN ANALYZE`는 쿼리를 실제로 실행한 뒤 각 노드에서 몇 초, 몇 행이 흘렀는지 되감아주는 재생 버튼이다. 예상 rows가 10인데 실제 rows가 1,200만이라면 통계가 썩었거나 조인 순서가 잘못됐다는 뜻인데, 전통적인 `EXPLAIN`은 이 괴리를 절대 보여주지 못한다. MySQL 8.0.18부터 도입되었고, "왜 인덱스를 안 타냐"가 아니라 "인덱스는 탔는데 왜 여전히 느리냐"의 답을 준다.

```sql
EXPLAIN ANALYZE
SELECT o.id, u.name FROM orders o JOIN users u ON o.user_id = u.id
WHERE o.created_at > '2026-08-01';

-- -> Nested loop inner join  (cost=8.4e+6 rows=8.3e+6)
--    (actual time=0.089..47234.5 rows=12,341,022 loops=1)
--     -> Index range scan on o using idx_created_at
--        (actual time=0.041..8123.2 rows=12,341,022 loops=1)
--     -> Single-row index lookup on u using PRIMARY
--        (actual time=0.003..0.003 rows=1 loops=12,341,022)
```

위 예시에서 `loops=12,341,022`가 진범이다. `users` 조회를 1,200만 번 반복하고 있다는 뜻이고, 인덱스는 탔지만 조인 카디널리티 자체가 잘못 예측됐다. `EXPLAIN`만 봤다면 "PRIMARY 잘 타네"로 끝났을 것을, `ANALYZE`는 47초의 진짜 원인을 지목한다.

> 💡 **왜 중요한가**: 프로덕션에서 "인덱스 다 걸려있는데 왜 느리죠?"라는 질문의 90%는 예상 통계와 실제 실행의 괴리에서 나오고, 그 괴리는 `EXPLAIN ANALYZE` 없이는 눈에 보이지 않는다.

### JPA `@Transactional(readOnly = true)` — 단순 최적화 힌트가 아니라, 스냅샷을 통째로 스킵하는 스위치

많은 개발자가 `readOnly = true`를 "읽기 전용임을 문서화하는 어노테이션" 정도로 생각하지만, Hibernate 내부에서는 완전히 다른 실행 경로를 탄다. `FlushMode`가 `MANUAL`로 바뀌어 트랜잭션 종료 시 flush를 건너뛰고, 무엇보다 엔티티의 **스냅샷(초기 상태 복사본)을 아예 만들지 않는다**. 스냅샷이 없으면 dirty checking 대상에서 제외되므로, 조회한 엔티티가 1만 개면 1만 개분의 스냅샷 메모리와 커밋 시점의 변경 감지 순회가 통째로 사라진다.

```java
// 이 두 메서드는 SQL은 같지만, JVM에서 하는 일이 완전히 다르다
@Transactional
public List<Order> findAll() {          // 스냅샷 1만 개 생성 + 커밋 시 전수 비교
    return orderRepository.findAll();
}

@Transactional(readOnly = true)
public List<Order> findAllReadOnly() {  // 스냅샷 0개, dirty checking 0회
    return orderRepository.findAll();
}
```

추가로 스프링 5.1+에서는 `readOnly = true`가 JDBC Connection에 `setReadOnly(true)`를 호출하고, 이는 MySQL 커넥터 기준으로 replica routing 힌트로 작동한다. 즉 이 한 줄이 "메모리 절약 + dirty checking 스킵 + 리드 레플리카 라우팅"이라는 세 가지를 동시에 활성화한다.

> 💡 **왜 중요한가**: 조회 API에 `readOnly = true`를 안 붙이면 SQL은 똑같이 나가지만 JVM은 조회한 모든 엔티티의 복사본을 들고 있다가 커밋 시점에 전부 순회하는데, 이건 트래픽이 늘어야 비로소 드러나는 종류의 낭비다.
