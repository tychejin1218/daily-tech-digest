### MySQL `Deadlock`과 인덱스 순서 — 데드락은 동시성 문제가 아니라, "락 획득 순서"의 문제다

두 트랜잭션이 서로 다른 순서로 락을 잡으면 데드락이 난다. 그런데 개발자가 SQL에서 명시적으로 락 순서를 정한 적이 없다면? 그건 옵티마이저가 인덱스를 어떤 순서로 스캔했느냐에 따라 결정된다. 같은 `UPDATE users SET balance = ... WHERE id IN (1, 2, 3)` 쿼리라도, 세컨더리 인덱스 스캔 순서가 달라지면 락을 잡는 행의 순서가 뒤바뀌고, 다른 트랜잭션과 교차하는 순간 데드락이 터진다.

```
Tx1: UPDATE ... WHERE user_id IN (100, 200)  → PK 오름차순으로 잠금 → row 100 → row 200
Tx2: UPDATE ... WHERE email IN ('b@x', 'a@x') → 인덱스 순서로 잠금  → row 200 → row 100
                                                                       ↑ 데드락 발생 지점
```

해결책은 두 가지다. (1) 애플리케이션에서 `ORDER BY id`로 락 획득 순서를 강제하거나, (2) 데드락을 정상 상황으로 받아들이고 재시도 로직을 둔다. InnoDB는 데드락을 감지하면 한쪽을 자동 롤백하므로, 재시도만 잘 걸어두면 실제 장애로 이어지지 않는다. `SHOW ENGINE INNODB STATUS`의 `LATEST DETECTED DEADLOCK` 섹션에서 실제 락 순서를 되짚어볼 수 있다.

**트레이드오프**: `ORDER BY id`로 순서를 강제하면 데드락은 줄지만, 옵티마이저가 선택할 수 있는 인덱스가 제한되어 쿼리 자체가 느려질 수 있다. 트래픽이 낮으면 재시도가 낫고, 트래픽이 폭발적이면 순서 강제가 낫다.

> 💡 **왜 중요한가**: 데드락 로그를 보고 "동시 요청이 몰려서 그렇다"고 결론 내리면 영원히 못 고친다. 진짜 원인은 락을 잡는 "순서"고, 그 순서는 SQL이 아니라 실행 계획이 결정한다.

### JPA `flush()` 타이밍과 쓰기 지연 — INSERT/UPDATE는 `commit()` 때가 아니라, "예상하지 못한 순간"에 실행된다

Hibernate는 영속성 컨텍스트에 변경을 쌓아뒀다가 트랜잭션 커밋 직전에 flush한다고 알려져 있다. 하지만 실제로는 세 가지 경우에 조기 flush가 강제로 일어난다. (1) JPQL이나 네이티브 쿼리를 실행하기 전(변경 사항이 반영되지 않은 결과를 막기 위해), (2) `IDENTITY` 전략으로 PK를 생성하는 엔티티를 `persist()` 하는 순간(DB가 PK를 발급해야 영속 상태가 되므로), (3) 명시적 `entityManager.flush()` 호출 시.

```
[개발자 예상]
save() → save() → save() → commit → INSERT ×3

[실제 IDENTITY 전략]
save() → INSERT → save() → INSERT → save() → INSERT → commit
         ↑ PK 받으려고 즉시 flush. 배치 INSERT 최적화 무력화

[JPQL 섞였을 때]
save() → save() → em.createQuery("SELECT ...") → flush() 강제 → SELECT
                                                  ↑ 개발자가 예상 못한 지점
```

이 특성은 두 가지 실무 함정을 만든다. (1) **배치 INSERT 최적화가 무력화된다**. `hibernate.jdbc.batch_size=100`을 걸어도 IDENTITY 전략이면 매 `save()` 마다 flush되어 배치가 안 묶인다. 대량 삽입이 필요하면 `SEQUENCE` 전략으로 바꾸거나 JDBC를 직접 써야 한다. (2) **트랜잭션 로직에 JPQL을 섞으면 예상 못 한 시점에 UPDATE가 나간다**. 아직 검증 로직이 안 끝났는데 dirty checking 결과가 DB로 먼저 나가버릴 수 있다.

**해결책**: 조기 flush를 막고 싶다면 `FlushModeType.COMMIT`으로 바꾼다. 단, 이 경우 같은 트랜잭션 안에서 변경 후 JPQL로 조회하면 옛 데이터가 나올 수 있으니, 조회는 반드시 영속성 컨텍스트를 우선 확인하도록 코드를 짜야 한다.

> 💡 **왜 중요한가**: "커밋할 때 flush된다"는 어림짐작으로 코드를 짜면, 성능(배치 무력화)과 정합성(예상 못한 UPDATE) 양쪽에서 조용히 손해를 본다. flush 타이밍은 Hibernate의 3대 블랙박스 중 하나다.
