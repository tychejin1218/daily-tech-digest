### Database Tip 1: PostgreSQL `JIT Compilation` — 복잡한 OLAP 쿼리를 "실행 시점에 네이티브 코드로 컴파일"해 CPU 사이클을 갈아 넣는 LLVM 가속기

PostgreSQL 11부터 도입된 JIT은 `WHERE`, `aggregation`, `tuple deforming` 같은 핫패스를 LLVM IR로 변환한 뒤 머신 코드로 컴파일해 인터프리터 오버헤드를 제거한다. `jit_above_cost=100000` 임계값을 넘는 쿼리에만 자동 활성화되며, 수억 행을 스캔하는 분석 쿼리에서 20~40% CPU 감소를 뽑아낸다. 그러나 OLTP 짧은 쿼리에서는 **컴파일 비용이 실행 비용을 역전**해 오히려 느려지는 함정이 있어, 트랜잭션 워크로드에선 `jit=off`가 정답인 경우가 많다.

```
[OLAP 쿼리]           [JIT ON]              [JIT OFF]
SELECT SUM(amount)    LLVM IR 생성 (50ms)   인터프리터 Loop
FROM orders           → 네이티브 코드         → 매 row마다 함수 호출
WHERE date > ...      → 실행 (800ms)          → 실행 (1,400ms)
(1억 row)             합계: 850ms            합계: 1,400ms  ✗
                              ↑
                      컴파일 비용 < 실행 이득

[OLTP 쿼리]           [JIT ON]              [JIT OFF]
SELECT * FROM users   LLVM 컴파일 (30ms)     인터프리터 실행
WHERE id = 42         → 실행 (0.1ms)         → 실행 (0.2ms)
(1 row)               합계: 30.1ms  ✗        합계: 0.2ms
                              ↑
                      컴파일 비용이 압도적 손해
```

> 💡 **왜 중요한가**: JIT은 "항상 켜면 빠르다"가 아니라 **쿼리 cost가 임계값을 넘어야만 ROI가 발생하는 투자**다 — 단순 쿼리가 많은 서비스에서 디폴트 켜짐을 그대로 두면 p99 레이턴시가 조용히 악화된다.

### Database Tip 2: JPA `OSIV`(Open Session In View) — 트랜잭션이 끝나도 영속성 컨텍스트를 "뷰 렌더링까지" 질질 끌고 가는 Spring Boot의 숨은 디폴트

Spring Boot는 `spring.jpa.open-in-view=true`가 기본값이라, `@Transactional`이 끝난 뒤에도 Controller/View 레이어에서 지연 로딩(Lazy Loading)이 "그냥 동작"하는 편의를 제공한다. 문제는 **DB 커넥션이 HTTP 응답이 완전히 나갈 때까지 반환되지 않는다**는 점 — 느린 View 렌더링이나 외부 API 호출이 Controller에 끼어들면 커넥션 풀이 순식간에 고갈된다. 트래픽이 몰리는 서비스일수록 `open-in-view=false`로 끄고, Service 레이어에서 필요한 데이터를 전부 `fetch join`으로 초기화하는 것이 정석이다.

```
[OSIV ON - 디폴트]
Request → Filter → Controller → Service → Repository
                      ↑           ↓           ↓
                      └─ 영속성 컨텍스트 열림 (커넥션 점유 시작)
                      ↓
                   View 렌더링 (Lazy Loading OK, 하지만 커넥션 계속 점유)
                      ↓
                   외부 API 호출 (3초) ← 💀 커넥션 3초 동안 묶임
                      ↓
                   Response 전송 → 커넥션 반환

[OSIV OFF]
Request → Controller → Service (트랜잭션 시작) → Repository
                         ↓
                      fetch join으로 필요한 데이터 다 가져옴
                         ↓
                      트랜잭션 종료 → 커넥션 즉시 반환 ✓
                         ↓
                   Controller → View (LazyInitializationException 위험)
                         ↓
                      외부 API 호출 (3초) ← 커넥션 이미 반환됨, 안전
```

> 💡 **왜 중요한가**: OSIV는 "편하지만 **커넥션 풀을 인질로 잡는 디폴트**"다 — 서비스가 커지면 반드시 꺼야 하는데, 끄는 순간 숨어 있던 `LazyInitializationException`이 쏟아져 나와 "지금껏 Service 레이어가 책임을 떠넘기고 있었다"는 사실이 폭로된다.
