#### 1. 사건: "임베딩이 짱이에요"라고 외친 신입 ML 엔지니어, 3개월 뒤 조용히 자리를 비우다

패턴이 보이는가? **고유명사, 에러코드, API 파라미터 — 즉 "정확한 토큰 매칭이 필요한 쿼리"가 전부 뭉개졌다.** 임베딩은 이들을 "결제 관련 어떤 것", "스케줄러 관련 어떤 것"으로 추상화해버렸고, 그 추상화된 벡터 공간에서는 PGM-2047과 PGM-3012의 거리가 0.03밖에 안 된다.

#### 2. 왜 Vector Search 단독으로는 안 되는가 — 임베딩의 "의미 추상화"는 양날의 검

임베딩 모델은 **의미적으로 비슷한 것을 가깝게** 만들도록 학습됐다. 이게 축복이자 저주다.

```
쿼리: "PGM-2047 에러"

임베딩 공간에서의 Top-5 유사도:
  1. "결제 모듈 일반 에러 처리"       cosine: 0.87
  2. "PG사 연동 트러블슈팅"           cosine: 0.85
  3. "결제 실패 시 재시도 전략"        cosine: 0.84
  4. "PGM-2047 발생 원인과 해결"      cosine: 0.82  ← 정답, 하지만 4위
  5. "주문 결제 플로우 다이어그램"     cosine: 0.81
```

**정답 문서가 4위**다. Top-3만 LLM context로 넘기면 영원히 안 보인다. 왜?

- `PGM-2047`은 토크나이저가 `PGM`, `-`, `20`, `47`로 쪼개고, 임베딩은 이 토큰들의 가중평균을 "결제 관련 식별자" 정도로 흐릿하게 표현한다.
- 반면 "결제 모듈 일반 에러"는 **의미 자체가 쿼리와 정면으로 겹친다**. 벡터가 더 가까운 건 당연하다.

이게 바로 **Lexical Gap**(어휘적 격차)이다. 사용자는 "정확한 단어"를 찾는데, 임베딩은 "비슷한 의미"를 돌려준다. 인간은 Ctrl+F로 1초면 찾을 걸, 수억 원짜리 LLM 파이프라인이 실패한다.

반대로 **Keyword Search(BM25)** 는 정확히 반대의 문제를 가진다:

```
쿼리: "주문이 왜 이렇게 늦게 처리되나요"

BM25 Top-3:
  1. "주문 처리 FAQ"                  score: 12.3
  2. "주문 상세 조회 API"             score: 8.7
  3. "주문 취소 가이드"                score: 7.2

→ 정답인 "결제 지연 시 재처리 큐 설계" 문서는 '주문'이라는 단어가 안 들어가 있어서 0점
```

BM25는 **동의어/의미 확장에 완전히 눈이 먼다**. "주문 지연"과 "결제 지연"이 사실상 같은 문제인 걸 모른다.

**결론: 둘 중 하나만 쓰면 반대편의 블라인드 스팟에 당한다.** 둘을 합쳐야 한다. 이게 Hybrid Search다.

#### 3. Hybrid Search 아키텍처 — 두 검색을 "어떻게" 합칠 것인가

```
                    ┌──────────────────────────┐
                    │     User Query           │
                    │ "PGM-2047 해결법"         │
                    └────────────┬─────────────┘
                                 │
                ┌────────────────┼────────────────┐
                │                                 │
                ▼                                 ▼
    ┌───────────────────────┐       ┌───────────────────────┐
    │  Keyword Search       │       │  Vector Search        │
    │  (BM25 / Elastic)     │       │  (pgvector / Pinecone)│
    │                       │       │                       │
    │  정확한 토큰 매칭       │       │  의미적 유사도          │
    │  에러코드, API명, SKU   │       │  동의어, 의도 파악        │
    │                       │       │                       │

                │                         │

                │   LLM Context 주입       │
                └─────────────────────────┘
```

##### 3.1 핵심은 "Score Fusion"을 어떻게 할 것인가

**방법 A. Weighted Sum (초보 함정)**

```python
final_score = 0.7 * vector_score + 0.3 * bm25_score
```

문제: vector_score는 0~1 범위, bm25_score는 0~∞ (로그 기반, 문서마다 다름). **단위가 다른 두 값을 그냥 더하면 BM25가 압도하거나 묻힌다.** 쿼리마다 분포가 달라서 α를 튜닝해도 다른 쿼리에서 깨진다.

**방법 B. Reciprocal Rank Fusion (RRF) — 사실상 표준**

```python
def rrf(vector_ranks: dict, bm25_ranks: dict, k: int = 60) -> dict:
    scores = defaultdict(float)
    for doc_id, rank in vector_ranks.items():
        scores[doc_id] += 1.0 / (k + rank)
    for doc_id, rank in bm25_ranks.items():
        scores[doc_id] += 1.0 / (k + rank)
    return dict(sorted(scores.items(), key=lambda x: -x[1]))
```

왜 RRF가 기가 막힌가:
- **점수가 아니라 "순위"만 사용** → 단위 차이 문제 소멸
- `k=60`은 Elastic/Vespa에서 경험적으로 검증된 값 (상위권은 변별, 하위권은 부드럽게 감쇠)
- 두 검색 모두 Top-1인 문서가 압도적 1위가 되고, 한쪽만 Top-1인 문서는 2위권으로 밀린다

```
예시 (PGM-2047 쿼리):
 문서                              Vector Rank  BM25 Rank  RRF Score
 ─────────────────────────────────────────────────────────────────
 "PGM-2047 발생 원인과 해결"           4           1        0.0319
 "결제 모듈 일반 에러 처리"             1           23       0.0284
 "PG사 연동 트러블슈팅"                2           ∞        0.0161
 ─────────────────────────────────────────────────────────────────
→ 정답 문서가 1위로 올라옴. BM25의 "정확한 매칭 보너스"가 벡터의 "의미 유사도"를 보완
```

**방법 C. Learned Ranker (대규모 시스템)**

Netflix, Pinterest, Amazon이 쓰는 방식. 쿼리-문서 쌍의 피처(BM25 점수, 코사인 유사도, 쿼리 길이, 문서 신선도, 사용자 과거 클릭 등)를 XGBoost나 LightGBM에 넣어 **학습된 순위**를 만든다. 클릭 로그가 충분히 쌓인 뒤의 고도화 단계. 처음부터 할 필요 없다.

#### 4. 실제 사례 — 왜 이름 있는 회사들은 모두 Hybrid로 돌아왔는가

##### 4.1 Notion AI (2023년 말 전환)

Notion은 초기에 순수 벡터 검색으로 "Ask AI" 기능을 런칭했다. 3개월 후 사용자 피드백 1순위: *"내가 쓴 메모에서 'OKR'을 검색했는데 OKR이라는 단어 없는 문서가 1등으로 나온다."* 2024년 초 Hybrid(BM25 + Embedding + RRF)로 전환. 내부 발표에서 **Recall@5가 71% → 88%로 상승**했다고 밝혔다.

##### 4.2 Elastic이 2023년 `elasticsearch`에 RRF를 아예 네이티브 기능으로 넣은 이유

Elastic의 공식 블로그 표현: *"We observed that in nearly every customer deployment, dense retrieval alone underperformed hybrid by 15-30% in NDCG@10."* 그들이 Vector DB 시장에 뒤늦게 뛰어들며 가장 세게 민 메시지가 "**순수 벡터 DB는 당신의 production 품질을 보장하지 않는다**"였다.

##### 4.3 Perplexity의 검색 스택

공개된 아키텍처 인터뷰에서 CTO Denis Yarats는 "우리는 처음부터 BM25와 벡터를 함께 썼다. LLM의 환각을 줄이는 가장 저렴한 방법은 **더 정확한 retrieval**이지 더 큰 모델이 아니다"라고 명시했다.

##### 4.4 Shopify Merchant Assistant

상품 검색을 벡터 only로 했다가 "SKU AX-7701" 같은 쿼리를 완전히 놓쳐 CS 티켓이 폭증. BM25를 복원하고 RRF로 합친 뒤 "정확 매칭 쿼리"의 Top-1 정확도가 **34% → 91%**로 뛰었다 (2024 Shopify Engineering 블로그).

#### 5. 구현 레시피 — pgvector + PostgreSQL FTS로 추가 인프라 없이 시작하기

Elastic이나 Vespa를 새로 들일 필요 없다. 이미 pgvector를 쓰고 있다면 Postgres의 `tsvector`로 BM25 유사 기능을 공짜로 얻는다.

```sql
-- 테이블 설계
CREATE TABLE documents (
    id          BIGSERIAL PRIMARY KEY,
    content     TEXT NOT NULL,
    embedding   VECTOR(1536),
    ts          TSVECTOR GENERATED ALWAYS AS (
                    to_tsvector('simple', content)
                ) STORED
);

CREATE INDEX idx_embedding ON documents 
    USING hnsw (embedding vector_cosine_ops);
CREATE INDEX idx_ts ON documents USING GIN(ts);
```

```sql
-- Hybrid Query with RRF (k=60)
WITH vector_search AS (
    SELECT id, 
           ROW_NUMBER() OVER (ORDER BY embedding <=> $1) AS rank
    FROM documents
    ORDER BY embedding <=> $1
    LIMIT 50
),
keyword_search AS (
    SELECT id,
           ROW_NUMBER() OVER (
             ORDER BY ts_rank_cd(ts, plainto_tsquery('simple', $2)) DESC
           ) AS rank
    FROM documents
    WHERE ts @@ plainto_tsquery('simple', $2)
    LIMIT 50
)
SELECT d.id, d.content,
       COALESCE(1.0 / (60 + v.rank), 0) + 
       COALESCE(1.0 / (60 + k.rank), 0) AS rrf_score
FROM documents d
LEFT JOIN vector_search v ON v.id = d.id
LEFT JOIN keyword_search k ON k.id = d.id
WHERE v.id IS NOT NULL OR k.id IS NOT NULL
ORDER BY rrf_score DESC
LIMIT 10;
```

한국어 처리가 핵심이면 `simple` 대신 **Mecab-ko 기반 tsvector 커스텀 설정**이 필요하다. 영어는 PG 기본 설정으로도 꽤 동작한다.

#### 6. 트레이드오프 — Hybrid는 공짜가 아니다

| 항목 | 순수 Vector | Hybrid (BM25+Vec+RRF) | Hybrid + Reranker |
|------|------------|----------------------|-------------------|
| **품질 (NDCG@10)** | 0.68 | 0.82 (+21%) | 0.89 (+31%) |
| **Latency p95** | 45ms | 90ms (+2x) | 280ms (+6x) |
| **인프라 비용** | Vector DB 1종 | Vector DB + BM25 엔진 (또는 PG 확장) | + Reranker API/GPU |
| **운영 복잡도** | 낮음 | 중간 (두 인덱스 동기화) | 높음 (모델 서빙) |
| **디버깅 난이도** | "왜 이게 나왔지?" 1개 소스 | 2개 소스 + Fusion 로직 | 3단 블랙박스 |
| **콜드 스타트** | 바로 가능 | 바로 가능 | Reranker 선정/튜닝 필요 |

##### 숨겨진 비용 1: 인덱스 동기화

문서가 업데이트되면 **두 인덱스를 원자적으로** 갱신해야 한다. 벡터는 업데이트됐는데 BM25가 안 됐다면? 쿼리에 따라 랜덤하게 다른 결과가 나오는 유령 버그가 생긴다. pgvector처럼 **같은 트랜잭션에서 두 컬럼을 동시에 갱신**할 수 있는 스택이 운영상 훨씬 편하다.

##### 숨겨진 비용 2: 토크나이저 지옥

BM25는 토크나이저에 생사가 달렸다. 한국어라면 Mecab, Nori, Kkma 중 선택이 결과를 뒤집는다. 코드 검색이라면 `camelCase`, `snake_case` 분리 규칙 또한 핵심이다. **벡터 검색은 토크나이저가 뭐든 Embedding 모델이 알아서 처리하지만, BM25는 토크나이저 선택이 품질의 40%를 좌우한다.**

##### 숨겨진 비용 3: 두 배의 평가 비용

품질 평가 세트를 만들 때, 벡터 only 시절에는 "정답 문서 1개"만 라벨링하면 됐다. Hybrid가 되면 "BM25로는 찾았는데 벡터로는 못 찾은 케이스", "그 반대 케이스", "둘 다 못 찾는 케이스"를 모두 별도로 트래킹해야 한다. **평가 대시보드를 두 배로 설계해야 한다.** [[llm-evaluation-automation]]

#### 7. 시니어 판단 — "언제 쓰고 언제 쓰면 안 되는가"

##### ✅ 반드시 Hybrid를 써야 하는 경우

1. **고유명사·식별자가 쿼리에 자주 등장** — 에러코드, API명, SKU, 버전 번호, 사명, 인명
2. **기술 문서 / 코드 검색** — 함수명, 클래스명, 설정 키가 정확히 매칭돼야 함
3. **이커머스 상품 검색** — 브랜드명, 모델명 정확 매칭 + 의미적 "비슷한 상품" 둘 다 필요
4. **법률/의료/금융 도메인** — 특정 법령 조항 번호, 질병 코드(ICD-10), 상품 코드가 정확히 매칭돼야 함
5. **RAG 검색 결과를 LLM이 소비** — 벡터가 놓친 문서 하나 때문에 환각이 발생하면 하류 비용이 모든 걸 압도한다

##### ❌ Hybrid가 과한 경우

1. **대화형 chit-chat 검색** — "오늘 기분 좋은 책 추천" 같은 완전 의미 기반 쿼리만 들어옴
2. **이미지/오디오 유사도 검색** — 애초에 keyword 개념이 없음
3. **쿼리량이 극히 적고 레이턴시 예산이 극도로 타이트한 경우** — 광고 노출 like 10ms 이내 응답
4. **아직 BM25 토크나이저조차 세팅할 리소스가 없는 PoC 단계** — 먼저 벡터로 가치 증명 후 품질 이슈 생기면 그때 추가

##### 🤔 중급 함정

- **"Reranker 쓰면 다 해결됨"** — 아니다. Reranker는 **입력된 Top-50이 좋을 때** 빛난다. 벡터 only로 Top-50에 정답이 없으면 Reranker가 신이어도 못 찾는다. **Retrieval(BM25+Vec) → Reranker** 순서를 지켜라.
- **"α 가중치만 잘 튜닝하면 됨"** — 쿼리 종류마다 최적 α가 다르다. "SKU 쿼리는 BM25 비중↑, 자연어 질문은 Vec 비중↑"이 이상적이지만, 그걸 판별하는 router가 또 다른 복잡도다. **RRF는 이걸 거의 공짜로 해결한다** — 그래서 사실상 표준이 됐다.
- **"벡터 모델을 더 큰 걸로 바꾸면 BM25 필요 없음"** — `text-embedding-3-large`도 PGM-2047을 PGM-3012와 구별 못 한다. **모델 크기로 해결될 문제가 아니라, retrieval 패러다임 자체의 한계다.**

#### 8. 다음 단계로의 연결

Hybrid Search는 RAG 품질의 **1단 로켓**이다. 이게 안 되면 그 위에 뭘 올려도 환각이 뚫고 나온다. 2단은 **Reranker**(Cross-Encoder로 Top-50 → Top-10 정밀 재정렬), 3단은 **Query Rewriting**(LLM이 사용자 쿼리를 BM25/벡터 각각에 최적화된 형태로 재작성), 4단은 **HyDE**(Hypothetical Document Embeddings — LLM이 "이 질문의 답이 될 가상의 문서"를 먼저 생성해서 그걸로 검색).

하지만 2~4단은 1단이 튼튼한 뒤의 이야기다. **Hybrid 없이 Reranker부터 고민하는 팀은 절반이 6개월 뒤 "retrieval을 처음부터 다시 설계합시다"라는 회의를 연다.**

---

> 💡 **왜 중요한가**: 임베딩은 "의미"는 알지만 "단어"는 모른다 — 사용자가 PGM-2047을 입력했는데 "결제 트러블슈팅 일반"을 돌려주는 RAG는 수억 원짜리 Ctrl+F 열화판이고, Hybrid Search는 그 간극을 메우는 사실상 유일한 저비용 해법이다.
