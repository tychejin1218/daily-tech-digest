### 1. `Optional.or(() -> Optional.of(fallback))` (Java 9 정식)로 Optional 체인 폴백하기 — `optional.orElseGet(() -> getFallback())`이 값을 벗겨내 버리는 관성 벗어나기

```java
// 관성: orElseGet은 T를 반환해서 Optional 체인이 끊긴다
User user = findInCache(id)
    .orElseGet(() -> findInDb(id)
        .orElseGet(() -> findInLegacy(id)
            .orElse(null)));  // null 폭탄
if (user == null) throw new UserNotFoundException(id);

// 벗어나기: or()은 Optional<T>를 반환해 체인을 유지한다
User user = findInCache(id)
    .or(() -> findInDb(id))
    .or(() -> findInLegacy(id))
    .orElseThrow(() -> new UserNotFoundException(id));
```

`orElseGet`은 `T`를 반환해서 호출하는 순간 Optional 모나드에서 빠져나와 null 체크·NPE·중첩 삼항이 돌아온다. `or(Supplier<Optional<T>>)`는 끝까지 `Optional<T>`를 유지하므로 "여러 데이터 소스를 순차 탐색 후 마지막에 예외" 패턴이 한 줄로 평평해진다. `findInDb`가 비쌀 때 첫 조건에서 값이 있으면 `Supplier`가 지연 평가 덕에 아예 호출되지 않는다는 점도 `orElse(findInDb(...))` 대비 명확한 이득이다.

> 💡 **왜 중요한가**: 폴백 체인은 리포지토리 계층에서 매일 나오는 패턴인데, `orElseGet`으로 섞어 쓰는 순간 Optional의 "값 부재를 타입으로 표현한다"는 장점이 조기 소실된다.

### 2. `Collectors.toUnmodifiableMap(keyMapper, valueMapper, mergeFunction)` (Java 10 정식)로 중복 키까지 안전하게 처리하기 — `Collectors.toMap(...)`으로 수집 후 `Collections.unmodifiableMap()`으로 감싸고 `IllegalStateException`에 놀라던 관성 벗어나기

```java
// 관성: toMap은 중복 키에서 IllegalStateException을 던지고, 불변은 별도 래핑
Map<String, Order> mutable = orders.stream()
    .collect(Collectors.toMap(
        Order::customerId,
        Function.identity()));  // 같은 customerId 두 건이면 런타임 폭발
Map<String, Order> immutable = Collections.unmodifiableMap(mutable);

// 벗어나기: 병합 함수 + 처음부터 불변
Map<String, Order> latestByCustomer = orders.stream()
    .collect(Collectors.toUnmodifiableMap(
        Order::customerId,
        Function.identity(),
        (existing, incoming) ->
            incoming.createdAt().isAfter(existing.createdAt()) ? incoming : existing));
```

Java 10에 추가된 `toUnmodifiableMap`은 내부적으로 `Map.copyOf` 수준의 진짜 불변 맵을 돌려주기 때문에 `Collections.unmodifiableMap`처럼 "뷰(view)" 특성으로 원본이 바뀌면 같이 흔들리는 함정이 없다. 특히 3-인자 버전은 중복 키를 "최신 레코드가 이김", "합산", "먼저 들어온 것 우선" 등 비즈니스 규칙으로 깔끔하게 선언할 수 있어, 테스트에서 같은 키가 두 번 들어오면 터지는 `toMap` 폭탄을 피한다. 반환 맵에 `null` 키·값이 금지되는 점만 기억하면, DTO 매핑에서 "불변 + 중복 허용" 두 축을 한 수집기로 끝낼 수 있다.

> 💡 **왜 중요한가**: 실무 리포지토리 조회 결과는 거의 항상 "ID로 맵핑"으로 끝나는데, 중복 키와 불변성을 각자 다른 레이어에서 땜질하면 `toMap` → 폭발 → 몽키패치의 반복에 갇힌다.
