### `@Cacheable`의 `sync = true`는 캐시 스탬피드(cache stampede)를 막는 유일한 옵션이다

`@Cacheable`은 기본적으로 캐시 미스가 동시에 발생하면 여러 스레드가 원본 메서드를 중복 실행한다. `sync = true`를 주면 동일 키에 대해 락을 걸어 하나의 스레드만 원본을 호출하고 나머지는 결과를 기다린다. 단, `unless`, `condition`, 여러 캐시(`cacheNames = {"a", "b"}`)와는 함께 쓸 수 없다는 제약이 있다.

```java
@Cacheable(cacheNames = "products", key = "#id", sync = true)
public Product findById(Long id) {
    return repository.findById(id).orElseThrow();
}
```

> 💡 **왜 중요한가**: 인기 캐시가 만료되는 순간 트래픽이 DB로 몰리는 캐시 스탬피드는 실서비스에서 흔한 장애 원인인데, 한 줄 옵션으로 방어할 수 있다.

### `ApplicationEventPublisher`로 발행한 이벤트는 기본이 동기이고 발행 트랜잭션에 묶인다

`applicationEventPublisher.publishEvent(...)`로 발행한 이벤트는 별도 설정 없이는 리스너가 발행자의 같은 스레드·같은 트랜잭션에서 실행된다. 리스너에서 예외가 나면 발행 쪽 트랜잭션까지 롤백되고, "커밋된 뒤에만" 후속 처리를 하고 싶다면 `@TransactionalEventListener(phase = AFTER_COMMIT)`를, 비동기로 돌리려면 리스너에 `@Async`를 추가로 붙여야 한다.

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Async
public void handle(OrderCreatedEvent event) {
    mailService.send(event.orderId());
}
```

> 💡 **왜 중요한가**: "이벤트로 뺐으니 결합이 풀렸다"고 착각하기 쉽지만, 기본 동작은 여전히 동기·같은 트랜잭션이므로 메일 전송 실패로 주문이 롤백되는 사고가 일어난다.
