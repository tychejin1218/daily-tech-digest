### 1. `sealed class` vs `enum class`: "닫힌 집합"을 표현하는 두 가지 방법, 그리고 상태를 담을 수 있느냐의 차이

`enum`은 "값의 유한한 집합"이지만 각 상수가 **동일한 형태**를 가져야 하고 **인스턴스별 다른 데이터**를 담기 어렵습니다. 반면 `sealed class`는 "타입의 유한한 집합"이라, 각 하위 타입이 **서로 다른 프로퍼티와 생성자**를 가질 수 있고 `when`에서 **스마트 캐스트**가 작동합니다.

```kotlin
// enum: 모든 상수가 같은 모양
enum class OrderStatus { PENDING, PAID, SHIPPED, FAILED }

// sealed class: 각 상태가 다른 데이터를 가짐
sealed class OrderState {
    object Pending : OrderState()
    data class Paid(val paidAt: Instant, val amount: Long) : OrderState()
    data class Shipped(val trackingNo: String) : OrderState()
    data class Failed(val reason: String, val retryable: Boolean) : OrderState()
}

fun handle(state: OrderState) = when (state) {  // else 불필요
    is OrderState.Pending -> notify("대기 중")
    is OrderState.Paid    -> ledger.record(state.amount)   // 스마트 캐스트
    is OrderState.Shipped -> tracker.update(state.trackingNo)
    is OrderState.Failed  -> if (state.retryable) retry() else alert(state.reason)
}
```

**트레이드오프**:
- `enum`: 직렬화 쉬움(이름 하나), DB 저장 간단, 메모리 효율적. **대신** 상태별 데이터 불가.
- `sealed`: 상태 + 데이터를 함께 표현, `when`의 **완전성 검사**로 새 상태 추가 시 컴파일 에러로 누락 방지. **대신** 직렬화 설정이 필요(`@JsonTypeInfo` 등).

실무 기준: "상태의 종류만 구분"하면 `enum`, "상태마다 담을 데이터가 다르면" `sealed class`. 특히 **도메인 이벤트/결과 타입/UI State**는 `sealed`가 정답입니다.

> 💡 **왜 중요한가**: `if-else` 사다리와 `instanceof` 체크로 분기하던 Java 코드가, `sealed + when`으로 **컴파일러가 누락을 잡아주는 대수적 데이터 타입(ADT)**이 됩니다.

### 2. `data class`의 `copy()`와 구조 분해: "불변 객체 수정"의 비용을 0으로 만드는 패턴, 그러나 함정이 있다

`data class`는 `equals/hashCode/toString/copy/componentN`을 자동 생성합니다. 그중 `copy()`는 **불변성을 유지하면서 일부 필드만 바꾼 새 인스턴스**를 만드는 핵심 도구인데, 여기서 많은 사람이 놓치는 **얕은 복사(shallow copy)** 함정이 있습니다.

```kotlin
data class User(val id: Long, val name: String, val roles: MutableList<String>)

val u1 = User(1, "Park", mutableListOf("USER"))
val u2 = u1.copy(name = "Kim")

u2.roles.add("ADMIN")
println(u1.roles)  // [USER, ADMIN] ← u1까지 오염됐다!
```

`copy()`는 **참조만 복사**하므로, 내부에 가변 컬렉션이 있으면 원본과 사본이 **같은 리스트를 공유**합니다. 해결책:

```kotlin
// 1) 아예 불변 컬렉션으로 선언
data class User(val id: Long, val name: String, val roles: List<String>)

// 2) 구조 분해로 가독성 ↑
val (id, name, roles) = user
log.info("user=$id, name=$name")

// 3) Map 반복에서 자동 구조 분해
for ((key, value) in headers) { ... }
```

**주의 사항**:
- `componentN()`은 **선언 순서**에 묶입니다. 필드 순서를 바꾸면 기존 구조 분해 코드가 **조용히 깨집니다**(타입이 같으면 컴파일 에러도 안 남). 그래서 공개 API의 `data class`는 필드 순서 변경이 **breaking change**입니다.
- `equals`는 **주 생성자의 프로퍼티만** 비교합니다. `class body`에 선언한 `val`은 동등성 비교에서 **무시**되므로, "왜 같은데 다르게 나오지?"의 원인이 됩니다.

> 💡 **왜 중요한가**: `copy()`는 함수형 스타일의 핵심이지만 "복사했으니 안전하다"는 환상을 심어줍니다. **불변 객체는 내부까지 불변**일 때만 진짜 불변입니다.
