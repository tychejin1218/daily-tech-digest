### 1. `Files.mismatch(path1, path2)` (Java 12 정식, JEP 305 계열)로 두 파일이 같은지 비교 — `Files.readAllBytes()` 두 번 읽어서 `Arrays.equals()`로 비교하거나 바이트 스트림을 직접 루프 도는 관성 벗어나기

```java
// Before: 전체 파일을 메모리에 로드해서 비교 (큰 파일은 OOM 위험)
byte[] a = Files.readAllBytes(path1);
byte[] b = Files.readAllBytes(path2);
boolean same = Arrays.equals(a, b);

// Before 2: InputStream으로 바이트 단위 비교 (장황한 보일러플레이트)
try (InputStream in1 = Files.newInputStream(path1);
     InputStream in2 = Files.newInputStream(path2)) {
    int b1, b2;
    while ((b1 = in1.read()) != -1) {
        b2 = in2.read();
        if (b1 != b2) return false;
    }
    return in2.read() == -1;
}

// After: Files.mismatch — 첫 불일치 바이트 위치를 반환, 같으면 -1L
long pos = Files.mismatch(path1, path2);
boolean same = (pos == -1L);
// 덤: pos 값으로 "어디서부터 다른가"까지 알 수 있음
```

내부적으로 버퍼 단위로 비교하기 때문에 수 GB 파일도 힙을 거의 안 쓰고 처리된다. 특히 빌드 산출물 캐시 비교, 테스트에서 "생성된 파일이 골든 파일과 같은가" 검증, 백업 무결성 체크에 `readAllBytes()` 관성이 가장 많이 남아있다.

> 💡 **왜 중요한가**: 파일 비교는 "메모리에 통째로 올려서 `Arrays.equals`"가 관성인데, 이 한 줄은 OOM 위험 없이 불일치 지점 오프셋까지 돌려주는 유일한 표준 API다.

### 2. `Thread.ofVirtual().name("worker-", 0).factory()` (Java 21 정식, JEP 444)로 이름 붙은 가상 스레드 팩토리 만들기 — `Executors.defaultThreadFactory()` 익명 스레드로 스레드 덤프에서 뭐가 뭔지 못 알아보는 관성 벗어나기

```java
// Before: 가상 스레드는 기본적으로 이름이 없음 → 스레드 덤프/로그에서 식별 불가
ExecutorService exec = Executors.newVirtualThreadPerTaskExecutor();
exec.submit(() -> handleRequest());
// 스레드 덤프: "VirtualThread[#42]/runnable@ForkJoinPool-1-worker-3"  ← 뭐 하는 녀석?

// Before 2: 수동으로 Thread.currentThread().setName() — 매 작업마다 try/finally 필요
exec.submit(() -> {
    String original = Thread.currentThread().getName();
    Thread.currentThread().setName("order-processor-" + orderId);
    try { handleOrder(orderId); }
    finally { Thread.currentThread().setName(original); }
});

// After: ThreadFactory로 이름 패턴 + 카운터를 한 번에
ThreadFactory factory = Thread.ofVirtual()
    .name("order-worker-", 0)   // "order-worker-0", "order-worker-1", ...
    .factory();

try (var exec = Executors.newThreadPerTaskExecutor(factory)) {
    orders.forEach(o -> exec.submit(() -> handleOrder(o)));
}
// 스레드 덤프: "VirtualThread[#128,order-worker-42]/runnable"  ← 바로 식별
```

이름을 분리해두면 `jcmd <pid> Thread.dump_to_file -format=json`으로 덤프를 뜰 때나 JFR 이벤트에서 "어떤 종류의 작업이 몇 개 떠 있나"를 한눈에 볼 수 있다. 플랫폼 스레드와 달리 가상 스레드는 수만 개가 떠있을 수 있어서 이름 규칙이 없으면 디버깅이 사실상 불가능해진다.

> 💡 **왜 중요한가**: 가상 스레드 시대에는 "익명으로 수만 개 뜨는 스레드"가 흔해져서, 이름 패턴을 가진 팩토리가 관측가능성의 최소 단위가 된다.
