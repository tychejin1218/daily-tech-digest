### 1. `inline`은 알았으니, 이제 `crossinline`과 `noinline`: "람다에도 권한이 있다"

`inline` 함수는 람다를 호출부에 통째로 복사해서 성능을 챙기지만, 그 부작용으로 람다 안에서 `return`을 쓰면 **바깥 함수까지 탈출(non-local return)** 해버린다. 이걸 막고 싶을 때 쓰는 게 `crossinline`(비지역 return 금지, 인라인은 유지), 아예 다른 함수에 람다를 넘겨야 해서 인라인 자체가 불가능할 때 쓰는 게 `noinline`(해당 람다만 인라인 제외)이다. 즉 `inline`은 "전부 복사", `crossinline`은 "복사하되 탈출 금지", `noinline`은 "얘만 그냥 객체로 넘김"이다.

```kotlin
inline fun runTask(
    crossinline onSuccess: () -> Unit,   // 다른 스레드/람다 안에서 호출 → 비지역 return 차단
    noinline onError: (Throwable) -> Unit // 다른 함수로 넘겨야 함 → 인라인 제외
) {
    executor.submit {
        try {
            doWork()
            onSuccess()              // return 하면 runTask 탈출? → crossinline이 막음
        } catch (e: Throwable) {
            registerHandler(onError) // 함수 참조로 넘김 → noinline 필수
        }
    }
}
```

| 키워드 | 인라인 되나? | 비지역 return 허용? | 언제 쓰나 |
|---|---|---|---|
| `inline` | ✅ | ✅ | 기본 인라인 람다 |
| `crossinline` | ✅ | ❌ | 람다를 다른 context(스레드, 콜백) 안에서 호출할 때 |
| `noinline` | ❌ | ❌ | 람다를 함수 참조로 다른 함수에 전달할 때 |

**실무 사례**: 스프링 `@Transactional` 대체용 커스텀 `transactional { ... }` 함수를 만들 때, 람다 안에서 `return`으로 바깥 서비스 메서드를 통째로 탈출시키면 트랜잭션이 커밋 전에 끊긴다. 이럴 때 `crossinline`으로 막아 **"람다 끝 = 트랜잭션 종료"** 의 의미를 명확하게 만든다.

> 💡 **왜 중요한가**: `inline`만 알고 `crossinline`/`noinline`을 모르면, 람다 안의 `return` 하나로 트랜잭션·락·리소스 해제가 전부 꼬이는 버그를 만든다.

### 2. `value class`(인라인 클래스): "원시 타입인데 타입 안전성까지" 공짜로 얻기

`UserId`, `OrderId`, `Email` 같은 식별자를 `Long`/`String`으로 그냥 쓰면 **`userRepository.findBy(orderId)` 같은 치명적 혼용**이 컴파일을 통과한다. 그렇다고 `data class UserId(val value: Long)`로 감싸면 객체 할당 비용이 생긴다. `@JvmInline value class`는 런타임에는 그냥 `Long`으로 취급되고(박싱 X), 컴파일 타임에는 완전히 다른 타입으로 구분되는 "제로 코스트 래퍼"다.

```kotlin
@JvmInline
value class UserId(val value: Long)

@JvmInline
value class OrderId(val value: Long)

fun findUser(id: UserId): User = ...

val userId = UserId(1L)
val orderId = OrderId(1L)

findUser(userId)   // ✅
findUser(orderId)  // ❌ 컴파일 에러 — 런타임엔 둘 다 Long인데도!
findUser(1L)       // ❌ 컴파일 에러
```

**바이트코드 수준에서 어떻게 동작하나**:

```
소스:       fun findUser(id: UserId)
바이트코드: fun findUser(id: long)   ← 그냥 Long이 됨, 객체 할당 0
```

**주의할 함정 3가지**:
1. **nullable이면 박싱됨**: `UserId?`는 null 표현이 필요해서 실제 객체로 박싱된다. 성능이 중요한 경로면 피하자.
2. **JPA 엔티티 ID로 쓸 때**: Hibernate가 바로 인식 못 하므로 `AttributeConverter`를 등록해야 한다.
3. **인터페이스 구현 시**: 해당 메서드 호출 때는 박싱이 일어난다(다형성 때문).

**Spring Boot 실무 예시**:
```kotlin
@RestController
class UserController(private val service: UserService) {
    @GetMapping("/users/{id}")
    fun get(@PathVariable id: Long): UserDto =
        service.find(UserId(id))   // 경계에서만 감싸고, 내부는 UserId로만 유통
}
```

> 💡 **왜 중요한가**: `Long` 두 개를 바꿔 넘긴 버그는 **프로덕션에서만 재현되고 스택트레이스에도 안 남는다**. `value class`는 그 버그 클래스를 통째로 컴파일 타임에 제거하면서, 성능은 원시 타입과 동일하다.
