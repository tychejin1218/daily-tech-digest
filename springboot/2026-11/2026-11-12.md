### 1. Spring Boot의 `@Valid`는 **중첩 객체의 필드까지 검증하지 않는다** — 그래서 DTO 안의 또 다른 DTO는 `@Valid`를 "두 번" 붙여야 비로소 검증된다

`@PostMapping`의 파라미터에 `@Valid @RequestBody UserRequest request`를 붙여도, `UserRequest` 내부의 `Address address` 필드는 자동으로 검증되지 않는다. 중첩 객체를 검증하려면 **필드 선언 지점에도 `@Valid`를 명시적으로 붙여야** 한다 (`@Valid private Address address;`). 이게 없으면 `@NotBlank`, `@Email` 같은 제약이 조용히 무시되고, 유효성 검증을 "통과한 척" 서비스 레이어로 흘러간다.

```java
public class UserRequest {
    @NotBlank
    private String name;
    
    @Valid  // ← 이거 없으면 Address 내부 필드 검증 안 됨
    @NotNull
    private Address address;
}

public class Address {
    @NotBlank  // ← @Valid 없으면 이 제약이 무시된다
    private String city;
    
    @Pattern(regexp = "\\d{5}")
    private String zipCode;
}
```

컬렉션(`List<Address>`)의 경우에도 동일하게 `@Valid private List<@Valid Address> addresses;` 처럼 **타입 파라미터 위치에 `@Valid`를 붙여야** 각 원소까지 검증이 재귀적으로 내려간다. 이걸 놓치면 "왜 검증 어노테이션을 다 붙였는데 null이 넘어오지?"라는 디버깅 지옥이 열린다.

> 💡 **왜 중요한가**: `@Valid`는 "진입점에서 한 번"이 아니라 "검증 그래프의 각 노드마다" 명시해야 작동하며, 이 재귀 전파의 암묵적 종료 지점이 가장 자주 발생하는 검증 누락 지점이다.

### 2. Spring Security의 `SecurityContextHolder`는 **기본적으로 `ThreadLocal`에 저장되어, `@Async`나 새 스레드로 넘어가는 순간 인증 정보가 사라진다**

`SecurityContextHolder.getContext().getAuthentication()`은 현재 요청 스레드에서만 유효하다. `@Async` 메서드, `CompletableFuture.supplyAsync()`, 또는 `ExecutorService`로 넘긴 작업에서는 **인증 정보가 `null`로 조회되거나, 최악의 경우 이전 요청의 인증 정보가 재사용된다** (스레드 풀이 재사용되므로). 이걸 해결하려면 `SecurityContextHolder.setStrategyName(MODE_INHERITABLETHREADLOCAL)`로 전략을 바꾸거나, `DelegatingSecurityContextExecutor`로 Executor를 감싸야 한다.

```java
@Service
public class OrderService {
    
    @Async
    public void processOrder(Long orderId) {
        // ❌ 여기서 authentication == null
        // 또는 더 위험하게, 이전 요청의 사용자로 조회됨
        Authentication auth = SecurityContextHolder.getContext()
            .getAuthentication();
        
        auditLog.record(orderId, auth.getName()); // NPE or 보안사고
    }
}

// ✅ 해결: Executor를 감싸기
@Bean
public Executor taskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.initialize();
    return new DelegatingSecurityContextExecutor(executor);
}
```

더 큰 함정은 **스레드 풀 재사용 때문에 "null"이 아니라 "다른 사용자의 Context"가 남아 있을 수 있다는 것**이다. `SecurityContextHolder`는 요청 끝에 `clearContext()`가 호출되지만, 비동기 스레드로 넘긴 작업이 끝나기 전에 메인 요청이 종료되면 그 비동기 스레드의 ThreadLocal은 **다음 요청에서 재사용될 때까지 이전 사용자의 인증 정보를 품고 있다**. Audit 로그에 "A가 주문했다"고 찍혔는데 실제로는 B가 주문한 사건이 여기서 나온다.

> 💡 **왜 중요한가**: ThreadLocal 기반 보안 컨텍스트는 "스레드 경계를 넘지 않는다"는 전제에 의존하며, 이 전제가 깨지는 순간 null보다 더 위험한 **다른 사용자로 오인되는 조용한 권한 혼선**이 발생한다.
