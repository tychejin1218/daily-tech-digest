### 1. `Collectors.collectingAndThen(downstream, finisher)`로 수집 후 후처리를 한 파이프라인에 봉인하기 (Java 8 정식)

`stream().collect(toList())` 뒤에 다시 변수를 받아 `Collections.unmodifiableList()`나 `List.copyOf()`를 씌우는 2단 호출 대신, `collectingAndThen`으로 수집기 자체에 마무리 함수를 합성하면 중간 변수 없이 결과가 이미 최종 형태로 나온다. 특히 `groupingBy`의 downstream 자리에 넣으면 각 그룹마다 후처리(예: `List → 불변 List`, `List → 요약 통계 객체`)를 반복하는 지옥에서 벗어난다.

```java
// Before: 그룹별로 불변화하려면 2단계 필요, downstream 자리에 못 씀
Map<Dept, List<Emp>> raw = emps.stream().collect(groupingBy(Emp::dept));
Map<Dept, List<Emp>> frozen = raw.entrySet().stream()
    .collect(toMap(Entry::getKey, e -> List.copyOf(e.getValue())));

// After: downstream 자리에서 그룹마다 finisher가 적용됨
Map<Dept, List<Emp>> frozen = emps.stream().collect(
    groupingBy(Emp::dept,
        collectingAndThen(toList(), List::copyOf)));
```

> 💡 **왜 중요한가**: `collectingAndThen`은 "수집 결과를 다른 컬렉터의 입력으로 쓸 수 있게" 만드는 어댑터라, 중첩 컬렉터의 조립 자유도를 결정하는 접착제다 — 이걸 모르면 `groupingBy` 안에서 후처리를 못 하고 매번 밖으로 빼서 재수집하게 된다.

### 2. `CompletableFuture.completeOnTimeout(value, timeout, unit)`로 타임아웃 실패를 예외 대신 기본값으로 처리하기 (Java 9 정식)

`orTimeout()`은 시간 초과 시 `TimeoutException`을 던져 downstream에서 `exceptionally`로 다시 잡아야 하지만, `completeOnTimeout`은 지정한 폴백 값으로 정상 완료시켜버린다. "실패해도 기본값으로 진행되는" UX (추천 목록 없으면 빈 리스트, 광고 못 받으면 스킵) 에 예외 처리 사다리 없이 딱 맞는다.

```java
// Before: 타임아웃을 예외로 잡아서 다시 기본값으로 복구
CompletableFuture.supplyAsync(this::fetchAds)
    .orTimeout(200, MILLISECONDS)
    .exceptionally(ex -> List.of())          // TimeoutException 포함 모든 예외를 잡아버림
    .thenAccept(this::render);

// After: 타임아웃은 기본값으로 조용히 완료, 진짜 에러만 exceptionally로
CompletableFuture.supplyAsync(this::fetchAds)
    .completeOnTimeout(List.of(), 200, MILLISECONDS)
    .exceptionally(ex -> { log.warn("ad fetch failed", ex); return List.of(); })
    .thenAccept(this::render);
```

> 💡 **왜 중요한가**: `exceptionally`로 모든 예외를 뭉뚱그려 잡으면 "타임아웃"과 "진짜 장애"가 같은 코드 경로를 타서 원인 계측이 불가능해진다 — `completeOnTimeout`은 두 실패 유형을 문법 레벨에서 분리해준다.
