### 1. `@Retryable`과 `@Recover`로 일시적 장애에 대한 선언적 재시도 처리하기

Spring Retry의 `@Retryable` 어노테이션을 사용하면 메서드 호출이 특정 예외로 실패했을 때 자동으로 재시도하도록 선언적으로 정의할 수 있습니다. `maxAttempts`로 재시도 횟수를, `backoff`로 지수 백오프 간격을 설정하고, 모든 재시도가 실패하면 `@Recover` 메서드가 폴백 로직을 수행합니다. 외부 API 호출이나 일시적인 네트워크 오류처럼 재시도로 복구 가능한 상황에서 try-catch 루프 없이 깔끔하게 구현할 수 있습니다.

```java
@Retryable(
    retryFor = { RestClientException.class },
    maxAttempts = 3,
    backoff = @Backoff(delay = 1000, multiplier = 2)
)
public PaymentResult callPaymentGateway(Order order) {
    return restClient.post().uri("/pay").body(order).retrieve().body(PaymentResult.class);
}

@Recover
public PaymentResult recover(RestClientException e, Order order) {
    log.error("결제 게이트웨이 호출 최종 실패: orderId={}", order.getId(), e);
    return PaymentResult.failed("PAYMENT_GATEWAY_UNAVAILABLE");
}
```

> 💡 **왜 중요한가**: 분산 시스템에서 흔한 일시적 장애(transient failure)를 비즈니스 로직과 분리해 처리함으로써 코드 가독성과 시스템 복원력(resilience)을 동시에 확보할 수 있습니다.

### 2. `@DynamicUpdate`로 JPA 엔티티의 변경된 컬럼만 UPDATE하기

기본적으로 Hibernate는 엔티티의 모든 컬럼을 포함한 UPDATE 쿼리를 생성하지만, 엔티티 클래스에 `@DynamicUpdate`를 붙이면 실제로 변경된(dirty) 컬럼만 SET 절에 포함되는 쿼리가 동적으로 만들어집니다. 컬럼이 매우 많거나 일부 컬럼만 자주 갱신되는 엔티티(예: 사용자 프로필, 주문 상태)에서 불필요한 컬럼 갱신을 줄이고, 컬럼별 인덱스 재계산이나 트리거 부하를 낮출 수 있습니다. 단, 매번 쿼리를 새로 생성하므로 PreparedStatement 캐싱 이점이 줄어들 수 있어 변경 빈도가 낮은 엔티티에는 적용하지 않는 것이 좋습니다.

```java
@Entity
@DynamicUpdate
public class Member {
    @Id @GeneratedValue
    private Long id;
    private String email;
    private String nickname;
    private String profileImage;
    @Column(columnDefinition = "TEXT")
    private String bio;
    // nickname만 변경하면 UPDATE member SET nickname=? WHERE id=? 만 실행
}
```

> 💡 **왜 중요한가**: 와이드 테이블에서 부분 업데이트가 빈번할 때 네트워크 트래픽과 DB I/O를 줄여 쓰기 성능을 개선할 수 있습니다.
