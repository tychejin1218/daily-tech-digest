### 1. `inline class` (`value class`): "타입 안전성"은 얻고 "객체 할당 비용"은 0으로 만드는 Kotlin의 제로-코스트 추상화

`UserId`, `Email`, `Money` 같은 도메인 값을 `String`이나 `Long`으로 그대로 쓰면 `fun transfer(from: String, to: String, amount: Long)` 같은 함수에서 인자 순서를 바꿔도 컴파일러가 못 잡는다. 그렇다고 래퍼 클래스를 만들면 매번 힙 할당이 발생해 핫패스에서 GC 압력이 생기는데, `@JvmInline value class UserId(val value: Long)`은 바이트코드 레벨에서 원시 `Long`으로 언박싱되어 "타입은 다르지만 런타임 오버헤드는 없는" 구조를 만든다. 다만 컬렉션에 담기거나 제네릭 타입 파라미터로 쓰이는 순간 박싱이 발생해 이점이 사라지므로, 어디서 언박싱이 유지되는지 디컴파일해 확인하는 습관이 필요하다.

> 💡 **왜 중요한가**: 도메인 주도 설계(DDD)의 "원시 타입 집착(Primitive Obsession)" 안티패턴을 성능 손실 없이 깨는 거의 유일한 Kotlin 도구이기 때문이다.

### 2. `Nothing` 타입: "값이 없다"가 아니라 "절대 반환되지 않는다"는 컴파일러와의 계약

Kotlin의 `Nothing`은 `Unit`(값 없음)과 완전히 다르다. `Nothing`은 "이 함수는 정상 종료되지 않는다(예외를 던지거나 무한 루프)"는 뜻으로, `fun fail(msg: String): Nothing = throw IllegalStateException(msg)`처럼 선언하면 컴파일러는 이후 코드를 도달 불가능으로 간주해 스마트 캐스트와 타입 추론을 더 공격적으로 수행한다. 예를 들어 `val name = user.name ?: fail("name required")` 같은 코드에서 `name`이 non-null로 추론되는 이유가 바로 `fail`의 반환 타입이 `Nothing`이기 때문이며, `emptyList<Nothing>()`처럼 "모든 타입의 하위 타입"이라는 성질은 제네릭 공변성 처리에도 쓰인다.

> 💡 **왜 중요한가**: `throw`를 함수로 추출하거나 Elvis 연산자와 조합할 때 컴파일러의 흐름 분석을 깨지 않고 유지시키는 것이 `Nothing`이며, 이를 모르면 "분명 체크했는데 왜 스마트 캐스트가 안 되지?"라는 함정에 빠진다.
