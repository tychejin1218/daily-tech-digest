### PostgreSQL `CLUSTER` 명령 — 물리적 행 순서를 인덱스와 정렬해 범위 스캔 I/O를 뭉텅이로 줄이기

B-Tree 인덱스가 논리적으로 정렬되어 있어도, 힙(heap) 위의 실제 행들은 삽입 순서대로 흩어져 있어 범위 스캔 시 랜덤 I/O가 발생합니다. `CLUSTER table USING index_name`은 지정한 인덱스 순서에 맞춰 힙을 물리적으로 재배치하여, `created_at BETWEEN ...` 같은 범위 쿼리에서 연속된 페이지만 읽도록 만듭니다. 단, 재클러스터링 중 `ACCESS EXCLUSIVE` 락이 걸리고 이후 새로 들어온 행에는 다시 적용되지 않기 때문에, `pg_repack` 확장이나 파티셔닝과 병행하는 것이 실무 표준입니다.

```sql
-- 시계열 로그 테이블에 대해 최근 조회가 압도적일 때
CREATE INDEX idx_logs_created_at ON logs (created_at);
CLUSTER logs USING idx_logs_created_at;

-- 실행 계획에서 Heap Fetches가 급감, Buffers: shared read 값이 1/10로 떨어짐
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM logs WHERE created_at BETWEEN '2026-08-01' AND '2026-08-05';
```

**트레이드오프 다이어그램**:
```
[클러스터링 전]                    [클러스터링 후]
Heap Page 1: [3][17][8]            Heap Page 1: [1][2][3]
Heap Page 2: [1][9][22]     →      Heap Page 2: [4][5][6]
Heap Page 3: [2][15][6]            Heap Page 3: [7][8][9]
범위 스캔 = 랜덤 3페이지            범위 스캔 = 연속 1페이지
```

> 💡 **왜 중요한가**: 인덱스는 "어디를 읽을지"를 알려주지만, 물리적 정렬이 없으면 결국 디스크 헤드는 흩어진 페이지를 랜덤하게 왕복해야 한다.

### MySQL `innodb_flush_log_at_trx_commit` — 커밋 지속성(D)을 3단계로 조정해 처리량과 데이터 손실 위험을 저울질하기

InnoDB는 매 커밋마다 redo log를 디스크에 fsync하는 것이 기본값(`=1`, 완전한 ACID)이지만, 이 fsync 하나가 초당 트랜잭션을 수천 → 수만으로 늘릴 수도 있는 병목입니다. `=2`로 두면 OS 버퍼까지만 쓰고 fsync는 1초에 한 번, `=0`이면 아예 백그라운드에 위임해 최대 1초치 트랜잭션이 크래시 시 소실될 수 있습니다. 배치 ETL, 세션 저장소, 캐시 워밍 같이 "재실행 가능한" 워크로드에서는 `=2`가 안전한 절충점이며, 결제·주문 같은 트랜잭션에는 `=1`을 유지하되 별도 인스턴스로 분리하는 것이 정석입니다.

```ini
# my.cnf — 성능 튜닝 시 가장 먼저 검토되는 설정
[mysqld]
innodb_flush_log_at_trx_commit = 2   # OS 버퍼까지만, fsync는 1초 간격
sync_binlog = 1000                    # 바이너리 로그도 함께 완화 (복제 지연 트레이드오프)
```

**세 값의 실제 동작 비교**:
```
값  | 커밋 시 동작                      | 크래시 시 손실       | TPS (예시)
----+----------------------------------+---------------------+----------
 1  | 로그 버퍼 → 파일 → fsync         | 0건 (완전 지속성)   | 2,000
 2  | 로그 버퍼 → OS 파일 캐시         | OS 크래시 시 ~1초치 | 12,000
 0  | 백그라운드 스레드가 1초마다 처리 | MySQL 크래시 시 ~1초치 | 18,000
```

실무 함정은 `innodb_flush_log_at_trx_commit=2`로 성능은 잡았지만 `sync_binlog=1`을 그대로 두어 결국 binlog fsync에서 다시 병목이 걸리는 경우. 두 설정은 반드시 함께 검토해야 하며, 복제 토폴로지가 있다면 `sync_binlog`를 낮추는 것은 슬레이브 정합성과 직결됩니다.

> 💡 **왜 중요한가**: ACID의 D(Durability)는 이분법이 아니라 스펙트럼이며, "얼마나 잃어도 되는가"를 명시적으로 선택하는 것이 곧 아키텍처 결정이다.
