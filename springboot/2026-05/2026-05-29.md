### `@Transactional`의 `readOnly = true`가 단순한 힌트가 아닌 이유 — Hibernate FlushMode를 MANUAL로 바꿔 dirty checking 자체를 건너뛴다

조회 전용 서비스 메서드에 `@Transactional(readOnly = true)`을 붙이면 JPA는 영속성 컨텍스트의 FlushMode를 `MANUAL`로 전환하고 스냅샷 비교(dirty checking)를 생략한다. 대량 조회 시 엔티티 개수만큼 발생하던 스냅샷 복제 비용이 사라지고, 실수로 setter가 호출되어도 UPDATE 쿼리가 나가지 않아 안전하다.

```java
@Transactional(readOnly = true)
public List<OrderDto> findRecentOrders(Long userId) {
    return orderRepository.findByUserId(userId).stream()
        .map(OrderDto::from)
        .toList();
}
```

> 💡 **왜 중요한가**: 쓰기 전용 트랜잭션과 명확히 분리해 성능·안전성을 동시에 챙기는 무료 최적화다.

### `@ModelAttribute` 바인딩 실패 시 `BindingResult`를 바로 다음 파라미터에 두지 않으면 400이 아니라 예외가 터진다

`@ModelAttribute`나 `@Valid`가 붙은 파라미터의 바인딩·검증 오류를 컨트롤러에서 직접 처리하려면 반드시 **해당 파라미터 바로 뒤**에 `BindingResult`를 선언해야 한다. 순서가 어긋나면 Spring은 오류를 잡을 대상이 없다고 판단해 `MethodArgumentNotValidException`을 던지고, 커스텀 응답 대신 기본 400 응답이 나가버린다.

```java
@PostMapping("/users")
public ResponseEntity<?> create(@Valid @ModelAttribute UserForm form,
                                BindingResult bindingResult) {
    if (bindingResult.hasErrors()) {
        return ResponseEntity.badRequest().body(toErrorMap(bindingResult));
    }
    return ResponseEntity.ok(userService.create(form));
}
```

> 💡 **왜 중요한가**: 파라미터 순서 한 칸이 전역 예외 핸들러 경로와 컨트롤러 내부 처리 경로를 가른다.
