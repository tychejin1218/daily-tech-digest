### MySQL `Skip Scan Index` — 복합 인덱스의 "첫 컬럼"을 WHERE에서 빼먹어도 인덱스를 타는 8.0의 마법

복합 인덱스 `(a, b)`가 있을 때 `WHERE b = 10`은 인덱스를 못 탄다는 게 상식이었다. MySQL 8.0.13부터 도입된 Skip Scan은 `a` 컬럼의 distinct 값이 적을 때(성별, 상태 코드 등) 각 값을 순회하며 `b` 조건을 병렬적으로 스캔해서, 첫 컬럼을 명시하지 않아도 인덱스를 활용한다. 다만 `a`의 카디널리티가 높으면 오히려 풀 스캔보다 느려지므로 옵티마이저가 `skip_scan=off`로 꺼버린다.

```sql
CREATE INDEX idx_status_created ON orders(status, created_at);
-- status는 3개 값(PENDING, PAID, CANCELLED)만 존재
EXPLAIN SELECT * FROM orders WHERE created_at > '2026-09-01';
-- Extra: "Using index for skip scan" ← 첫 컬럼 없어도 인덱스 사용!
```

```
[전통적 방식]                    [Skip Scan]
WHERE b = 10 → Full Scan     WHERE b = 10
                              → a=PENDING 구간에서 b=10 탐색
                              → a=PAID 구간에서 b=10 탐색
                              → a=CANCELLED 구간에서 b=10 탐색
                              (a의 distinct 값만큼 "점프")
```

**언제 유리한가**: `a`의 distinct 값이 10개 미만 && 전체 행이 매우 많을 때. `a`가 유저 ID처럼 카디널리티가 폭발하면 skip scan은 손해다.

**함정**: `EXPLAIN`에서 `type=range`, `Extra=Using index for skip scan`이 떠야 실제로 동작 중. 없으면 여전히 풀 스캔이다. 그리고 이 최적화를 믿고 인덱스 순서를 대충 짜는 건 위험 — 5.7 이하 버전, MariaDB에서는 안 먹힌다.

> 💡 **왜 중요한가**: "복합 인덱스는 반드시 앞 컬럼부터 순서대로 써야 한다"는 10년 묵은 룰이 특정 조건에서 깨졌다는 걸 모르면, 불필요한 중복 인덱스를 계속 만들게 된다.

### PostgreSQL `BRIN (Block Range Index)` — 10억 행에 인덱스를 만들어도 B-Tree의 1/1000 크기인 "느슨한 인덱스"

B-Tree는 모든 행을 트리에 매핑하지만, BRIN은 "블록 범위별로 min/max만 저장"하는 초경량 인덱스다. 예를 들어 128개 블록마다 `created_at`의 최솟값과 최댓값 하나씩만 기록해서, `WHERE created_at BETWEEN ...` 쿼리 시 범위 밖 블록은 통째로 건너뛴다. 시계열/로그 테이블처럼 **물리적 저장 순서와 컬럼 값이 상관관계가 높을 때** 마법을 부린다.

```sql
-- 10억 행 로그 테이블 (created_at 순서로 INSERT됨)
CREATE INDEX idx_logs_brin ON logs USING BRIN(created_at) WITH (pages_per_range = 128);

-- B-Tree: 인덱스 크기 ~30GB
-- BRIN:   인덱스 크기 ~30MB  (1/1000!)

SELECT * FROM logs WHERE created_at BETWEEN '2026-09-01' AND '2026-09-02';
-- BRIN이 "이 날짜 범위를 포함하는 블록만" 리턴 → 그 블록만 스캔
```

```
[B-Tree]                          [BRIN]
행 하나하나 → 리프 노드           블록 범위 → min/max 요약
     │                                 │
   정확한 위치                    "이 범위 어딘가에 있다"
   O(log n)                       느슨한 필터링
   크기 크지만 빠름                크기 작지만 재스캔 필요
```

**BRIN이 죽는 순간**: `UPDATE`나 `DELETE`로 물리적 순서가 흐트러지면 min/max 범위가 넓어져서 "쓸모없는 인덱스"가 된다. 그래서 `pg_repack`이나 `CLUSTER`로 주기적으로 물리 정렬을 맞춰줘야 한다.

**함정**: 카디널리티가 낮거나 값이 무작위로 흩어진 컬럼(UUID, 랜덤 해시)에 BRIN을 걸면 모든 블록의 min/max가 겹쳐서 전체 스캔이 된다. "값이 저장 순서와 함께 증가하는가?"가 유일한 판단 기준.

> 💡 **왜 중요한가**: 시계열/로그 테이블에서 B-Tree 인덱스가 테이블 크기의 30%를 차지하는 낭비를 1000배 압축할 수 있는데, 대부분의 개발자는 BRIN의 존재조차 모른다.
