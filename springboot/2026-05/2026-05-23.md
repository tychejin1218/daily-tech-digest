### `@TransactionalEventListener`로 트랜잭션 커밋 이후에만 이벤트 처리하기

`@EventListener`는 이벤트 발행 즉시 실행되어 트랜잭션이 롤백되어도 후속 작업(메일 발송·외부 API 호출)이 나가버린다. `@TransactionalEventListener(phase = AFTER_COMMIT)`을 사용하면 커밋이 확정된 뒤에만 리스너가 동작해 "결제는 롤백됐는데 알림톡만 나갔다" 같은 사고를 원천 차단할 수 있다.

```java
@Component
public class OrderNotificationListener {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void handle(OrderCreatedEvent event) {
        notificationClient.send(event.orderId());
    }
}

@Service
@RequiredArgsConstructor
public class OrderService {
    private final ApplicationEventPublisher publisher;

    @Transactional
    public void createOrder(OrderRequest req) {
        Order saved = orderRepository.save(req.toEntity());
        publisher.publishEvent(new OrderCreatedEvent(saved.getId()));
    }
}
```

> 💡 **왜 중요한가**: DB 상태와 외부 부수효과의 일관성은 트랜잭션 경계와 이벤트 발행 시점을 정렬해야만 지켜진다.

### `RestClient`로 `RestTemplate`을 대체하고 fluent API로 HTTP 호출 단순화하기 (Spring 6.1+)

`RestTemplate`은 유지보수 모드고 `WebClient`는 리액티브 스택 의존성을 끌고 온다. Spring 6.1의 `RestClient`는 동기 방식 그대로 `WebClient`스러운 fluent API를 제공해서 블로킹 환경에서도 가독성 좋게 HTTP 호출을 작성할 수 있다.

```java
@Bean
RestClient restClient(RestClient.Builder builder) {
    return builder
        .baseUrl("https://api.example.com")
        .defaultHeader("X-Api-Key", apiKey)
        .build();
}

public User fetchUser(Long id) {
    return restClient.get()
        .uri("/users/{id}", id)
        .retrieve()
        .onStatus(HttpStatusCode::is4xxClientError,
            (req, res) -> { throw new UserNotFoundException(id); })
        .body(User.class);
}
```

> 💡 **왜 중요한가**: 리액티브 의존성 없이도 최신 fluent API의 이점을 얻을 수 있어 신규 코드에서 `RestTemplate`을 고를 이유가 사라졌다.
