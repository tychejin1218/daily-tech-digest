### 1. `@Async`와 `TaskDecorator`로 비동기 작업에 MDC/SecurityContext 전파하기

`@Async`로 메서드를 비동기 실행하면 새로운 스레드에서 동작하기 때문에 `ThreadLocal` 기반의 MDC 로그 컨텍스트와 `SecurityContextHolder`가 유실됩니다. `TaskDecorator`를 구현하여 `ThreadPoolTaskExecutor`에 등록하면, 호출 시점의 컨텍스트를 캡처해 작업 스레드에 복사하고 실행 후 정리하는 로직을 일관되게 적용할 수 있습니다.

```java
public class ContextPropagatingTaskDecorator implements TaskDecorator {
    @Override
    public Runnable decorate(Runnable runnable) {
        Map<String, String> mdc = MDC.getCopyOfContextMap();
        SecurityContext securityContext = SecurityContextHolder.getContext();
        return () -> {
            try {
                if (mdc != null) MDC.setContextMap(mdc);
                SecurityContextHolder.setContext(securityContext);
                runnable.run();
            } finally {
                MDC.clear();
                SecurityContextHolder.clearContext();
            }
        };
    }
}

@Bean
public Executor taskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setTaskDecorator(new ContextPropagatingTaskDecorator());
    executor.initialize();
    return executor;
}
```

> 💡 **왜 중요한가**: 비동기 처리 시 traceId가 끊기거나 인증 정보가 사라지면 분산 추적·인가 검증이 깨져 운영 환경에서 디버깅이 사실상 불가능해집니다.

### 2. `@EntityGraph`로 JPA N+1 문제를 선언적으로 해결하기

JPA 연관관계 조회 시 발생하는 N+1 문제는 `JOIN FETCH`로 해결할 수 있지만 매번 JPQL을 작성해야 하고 페이징과 함께 쓰면 `MultipleBagFetchException`이나 메모리 페이징 경고가 발생합니다. `@EntityGraph(attributePaths = {...})`를 Repository 메서드에 선언하면 기존 메서드 시그니처를 유지한 채로 특정 호출 경로에서만 연관 엔티티를 함께 로딩하도록 명시할 수 있어, 동일한 엔티티에 대해 조회 시나리오별 페치 전략을 분리할 수 있습니다.

```java
public interface OrderRepository extends JpaRepository<Order, Long> {

    @EntityGraph(attributePaths = {"customer", "items"})
    Optional<Order> findWithDetailsById(Long id);

    @EntityGraph(attributePaths = {"customer"})
    Page<Order> findAllByStatus(OrderStatus status, Pageable pageable);
}
```

> 💡 **왜 중요한가**: N+1은 트래픽이 늘어날 때 가장 먼저 DB를 무너뜨리는 성능 이슈이며, `@EntityGraph`는 엔티티의 기본 페치 전략을 `LAZY`로 유지하면서도 호출 지점별 최적화를 깔끔하게 분리할 수 있는 표준 도구입니다.
