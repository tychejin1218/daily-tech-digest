### Database Tip 1: PostgreSQL `Write-Ahead Log`의 `Full Page Writes`와 체크포인트 직후의 "쓰기 폭발" — 8KB 페이지가 처음 더럽혀지는 순간 WAL에 "페이지 통째로" 박히는 숨은 I/O 증폭기

PostgreSQL은 체크포인트 직후 어떤 페이지가 처음 수정될 때, 4바이트짜리 UPDATE 하나를 기록하는 게 아니라 **그 페이지 전체(8KB)를 WAL에 통째로 복사**해 넣습니다. 이는 운영체제가 4KB 단위로 쓰기 때문에 fsync 도중 크래시가 나면 "반쪽 페이지(torn page)"가 남을 수 있고, 복구 시 WAL의 변경 로그를 "온전한 페이지"에 적용할 수 없기 때문입니다. 그 결과 `checkpoint_timeout`을 짧게 잡으면 매번 체크포인트 직후 수 분간 WAL 생성량이 평소의 10~50배로 튀어 올라 복제 지연, 디스크 IOPS 포화, Aurora의 스토리지 과금 폭증을 유발합니다. `full_page_writes=off`는 ZFS/Btrfs처럼 원자적 페이지 쓰기를 보장하는 파일시스템이거나 CoW 스냅샷 기반 복구가 있을 때만 끌 수 있고, 일반 ext4/XFS에서는 데이터 파손 각오 없이는 절대 끄면 안 됩니다. 실무 완화책은 `checkpoint_timeout`을 15~30분으로 길게 잡고 `max_wal_size`를 넉넉히 줘서 체크포인트 빈도 자체를 낮추는 것 — 체크포인트가 드물수록 "첫 수정"도 드물어져 전체 페이지 쓰기 비율이 극적으로 떨어집니다.

> 💡 **왜 중요한가**: WAL 생성량이 평소의 수십 배로 튀는 "쓰기 폭발"의 범인이 쿼리가 아니라 체크포인트 주기라는 걸 모르면, 디스크를 늘려도 복제 지연이 계속 반복된다.

### Database Tip 2: MySQL `Query Cache` 제거와 `Prepared Statement Cache`의 세대교체 — 8.0에서 조용히 사라진 "결과 캐시"와 그 자리를 메운 "실행 계획 캐시"의 숨은 이동

MySQL 5.7까지 존재했던 `query_cache`(쿼리 문자열 → 결과 집합을 통째로 캐시)는 **8.0에서 완전히 제거**됐습니다. 이유는 멀티코어 환경에서 캐시 무효화 락(단일 `qcache mutex`)이 CPU 코어 수가 늘수록 선형적으로 느려져, 쓰기가 조금만 섞여도 캐시 켠 쪽이 꺼둔 쪽보다 TPS가 2~3배 떨어지는 역설이 벌어졌기 때문입니다. 대신 8.0은 `Prepared Statement`의 실행 계획을 세션/글로벌 단위로 재사용하는 방향으로 선회했고, `max_prepared_stmt_count`(기본 16,382)와 커넥션 풀의 `cachePrepStmts=true&useServerPrepStmts=true` 조합이 새로운 성능 지렛대가 됐습니다. HikariCP + MySQL 8에서 `useServerPrepStmts=false`로 두면 매 쿼리마다 파싱/최적화를 다시 하면서 CPU 20~30%를 그냥 태우고, 반대로 `true`인데 `max_prepared_stmt_count`를 안 늘리면 "Can't create more than max_prepared_stmt_count statements" 에러로 서비스가 통째로 멈춥니다. 결과적으로 MySQL 5.7에서 8.0으로 올리면서 "쿼리 캐시가 사라졌으니 Redis를 앞단에 두자"가 아니라, **애플리케이션 레벨의 PreparedStatement 재사용이 사실상 강제**됐다는 아키텍처 전환을 이해해야 합니다.

> 💡 **왜 중요한가**: MySQL 8.0 업그레이드 후 CPU가 치솟는 서비스의 상당수는 "query_cache가 사라진 자리"를 PreparedStatement 캐시로 못 메운 것 — 결과를 캐시하던 시대에서 실행 계획을 캐시하는 시대로 넘어왔다.
