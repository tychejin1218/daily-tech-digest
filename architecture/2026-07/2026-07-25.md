### LLM Eval — "테스트가 통과하면 배포한다"는 원칙이 확률적 출력 앞에서 무너지는 순간

시니어 백엔드에서 배포 파이프라인의 기본 전제는 이렇다. "커밋 → CI가 unit/integration 테스트 실행 → 통과하면 배포." 이 전제는 **함수의 출력이 결정론적(deterministic)** 이라는 사실 위에 서 있다. `assertEquals("hello", greet("world"))` 는 오늘도 내일도 같은 결과를 낸다.

LLM은 이 전제를 무너뜨린다. 같은 프롬프트, 같은 모델, `temperature=0`으로 고정해도 provider의 내부 스케줄링/양자화 변화 때문에 결과가 미묘하게 달라진다. 프롬프트를 한 줄 고쳤을 때 "1000개 요청 중 몇 개가 좋아졌고 몇 개가 나빠졌는가"를 판단해야 한다. 이 판단을 자동화하는 시스템이 **LLM Eval**이다.

#### 왜 unit test로는 안 되는가

전통적 테스트는 "출력 == 기대값"을 검사한다. LLM 응답을 이 방식으로 검증하면 실패한다.

```python
# 이 테스트는 "맞는 답"에도 실패한다
def test_summary():
    result = llm.summarize("긴 텍스트...")
    assert result == "3문장으로 요약된 결과"  # 문자열이 매번 다름
```

그렇다고 `assert len(result) < 500` 같은 껍데기 검증만 하면, **의미가 완전히 틀린 답**도 통과한다. Eval의 본질은 **정답 문자열**이 아니라 **품질 차원(dimension)** 을 측정하는 것이다.

#### Eval 시스템 구조

```
┌─────────────────────────────────────────────────────────────┐
│                    LLM Eval Pipeline                        │
└─────────────────────────────────────────────────────────────┘

  [Prompt v2]  ──┐
                 │
  [Model gpt-x]──┼──▶ ┌────────────────────┐
                 │    │  Test Dataset      │  ← Golden set
  [RAG index] ───┘    │  (500~5000 cases)  │    (도메인 전문가 검수)
                      └────────┬───────────┘
                               │
                               ▼
                      ┌────────────────────┐
                      │  Run all cases     │  ← 병렬 호출, 캐싱
                      └────────┬───────────┘
                               │
                    ┌──────────┼──────────┐
                    ▼          ▼          ▼
             [Rule-based] [LLM-as-judge] [Human review]
              exact/regex    GPT-4o가       (샘플만)
              length/format  1~5점 채점
                    │          │          │
                    └──────────┼──────────┘
                               ▼
                      ┌────────────────────┐
                      │  Aggregate scores  │
                      │  vs. baseline      │
                      └────────┬───────────┘
                               │
                    Regression? ──── Yes ──▶ Block deploy
                               │
                               No
                               ▼
                         Promote to prod
```

핵심은 세 층의 채점기를 조합한다는 점이다.

1. **Rule-based**: JSON 스키마 valid 여부, 금지어 포함 여부, 길이 제약. 빠르고 확정적.
2. **LLM-as-judge**: "이 답변이 관련성 있는가?"를 GPT-4o에게 1~5점으로 물어봄. 사람 판단을 근사하지만 편향(길이 편향, 자기 모델 선호)이 있다.
3. **Human review**: 채점기가 못 잡는 미묘한 실패를 잡음. 전체를 못하니 샘플링.

#### Versioning — 무엇을 버전 관리하는가

전통적 배포는 코드 버전만 관리한다. LLM 시스템은 **네 개의 축**을 동시에 관리해야 한다.

| 축 | 변경 시 영향 | 예시 |
|---|---|---|
| Prompt template | 톤/포맷/추론 방식 | "step by step" 추가 |
| Model version | 지능/속도/비용/거절율 | `gpt-4o-2024-11-20` → `2025-02-15` |
| RAG index | 검색 품질/최신성 | 임베딩 모델 교체, chunk size 변경 |
| Tool schema | Agent 동작 경로 | tool 파라미터 rename |

넷 중 하나만 바뀌어도 출력 분포가 달라진다. 어떤 축을 바꿔서 성능이 올라갔는지/떨어졌는지 추적하려면 **Prompt/Model/Index/Tool을 별도 아티팩트로 버전 태깅**하고, 매 Eval run에 이 4-tuple을 기록해야 한다.

#### 트레이드오프

- **Golden dataset 크기 vs 비용**: 5000 케이스에 GPT-4o judge를 붙이면 1 run에 $50~$200. PR마다 돌리면 예산이 터진다. 실무에선 "PR용 200케이스 smoke set + 릴리스용 5000케이스 full set"으로 계층화한다.
- **LLM-as-judge 신뢰도 vs 속도**: judge 모델이 target 모델보다 강해야 신뢰할 수 있다. `gpt-4o-mini`로 `gpt-4o`를 채점하면 위쪽을 못 본다.
- **재현성 vs 현실성**: `temperature=0`으로 고정하면 재현성은 좋아지지만 실제 서비스는 `temperature=0.7`로 운영한다. eval과 프로덕션의 분포가 어긋난다. 해결책은 `n=5`로 여러 번 sampling해서 분산까지 리포트하는 것.
- **정답 없는 태스크**: 요약, 창작, 조언 같은 open-ended 태스크는 "정답"이 없다. Pairwise comparison(A vs B 어느 쪽이 낫나?) 방식으로 전환해야 한다.

#### 실제 사례

- **Anthropic**: 모델 릴리스마다 수백 개의 자동화된 eval + Red Team 결과를 model card에 공개한다. "Claude 3 Opus는 MMLU에서 86.8%" 같은 수치는 eval pipeline의 산출물.
- **Notion AI**: 초기에는 배포마다 사내 dogfooding으로 품질을 판단했으나, 요약/번역/이어쓰기 각 태스크에 별도 golden set을 구축하고 Braintrust 같은 eval 플랫폼으로 회귀 감지를 자동화. 프롬프트를 고칠 때마다 "요약 품질 -3%, 번역 품질 +1%" 같은 리포트가 나온다.
- **Shopify Sidekick**: LangSmith에서 프로덕션 트래픽을 샘플링해 계속 새 케이스를 golden set에 추가하는 loop를 돌린다. "실제 사용자가 던진 어려운 질문"이 시간이 지나면서 eval의 난이도를 자동으로 끌어올린다.
- **GitHub Copilot**: 코드 완성은 "정답"이 명확해서(테스트 통과 여부) rule-based eval이 강력하게 작동한다. 이 덕분에 다른 LLM 제품보다 훨씬 빠르게 반복이 가능했다.

#### 시니어 관점: 언제 쓰고, 언제 쓰면 안 되는가

**써야 하는 경우**
- 프롬프트/모델/인덱스를 **주 1회 이상** 만지는 팀. 회귀를 사람 눈으로 잡을 수 없는 임계를 이미 넘었다.
- 응답 품질이 매출/신뢰와 직결되는 도메인(금융 상담, 의료 요약, 법률 초안). 은근한 품질 저하가 사업 위험이다.
- Multi-tenant SaaS에서 프롬프트가 고객별로 갈라지는 경우. 튜닝 하나가 다른 고객을 부순다.

**쓰면 안 되는(과할) 경우**
- PoC 단계, 사용자 10명 미만. Eval 파이프라인 구축 비용이 제품 만드는 비용을 넘는다. 이때는 **로그 + 사람이 직접 200개 훑기**가 더 빠르다.
- Golden set을 만들 도메인 전문가가 없는 상황. 부실한 golden set에 대고 채점하면 **잘못된 방향으로 자신 있게** 최적화된다. 이건 eval이 없는 것보다 위험하다.
- 답이 완전히 open-ended이고 회사가 아직 "좋은 답"의 정의도 못 내린 초기 단계. Eval을 짜기 전에 rubric부터 사람이 합의해야 한다.

배포 파이프라인의 gate가 "green tick"에서 **"regression 없음 + 품질 지표 유지"** 로 바뀌는 것이 LLM 시대 백엔드의 조용한 패러다임 전환이다. CI에 red/green 대신 dashboard가 붙기 시작하면, 팀은 이미 반쯤 이 세계에 들어와 있다.

> 💡 **왜 중요한가**: LLM 시스템에서 "테스트 통과 → 배포"라는 결정론적 CI 모델은 무너지므로, 확률적 출력의 회귀를 정량적으로 감지하는 Eval 파이프라인이 배포 게이트의 새로운 표준이 된다.
