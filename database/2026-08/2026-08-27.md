### MySQL `Adaptive Hash Index` — InnoDB가 자주 쓰이는 인덱스를 몰래 해시로 바꿔주는 자동 캐시

InnoDB는 B-Tree 인덱스에서 반복적으로 조회되는 키를 감지하면, 메모리 안에 자동으로 해시 인덱스를 만들어 O(log N) 탐색을 O(1)로 줄인다. 문제는 이 기능이 항상 이득이 아니라는 점 — 동시성 높은 워크로드에서는 AHI 내부의 `btr_search_latch` 경합이 오히려 병목이 되어, DBA들이 `innodb_adaptive_hash_index=OFF`로 끄는 사례가 늘고 있다.

```
[일반 조회]                    [AHI 활성화 후]
B-Tree Root                    Hash Table
    ↓ (3~4 hop)                    ↓ (1 hop)
Internal Node                  Leaf Page 직행
    ↓
Leaf Page                      ⚡ latch 경합 위험
```

실무 판단 기준:
- **켜라**: 읽기 위주, 특정 키 반복 조회, 단일 스레드/저동시성
- **꺼라**: OLTP 고동시성, `SHOW ENGINE INNODB STATUS`에서 `hash searches/s`보다 `non-hash searches/s`가 훨씬 크거나, `RW-latch` 대기가 상위에 보일 때

> 💡 **왜 중요한가**: "자동으로 알아서 최적화해준다"는 기능일수록, 그것이 병목이 되는 순간을 알아보지 못하면 원인 불명의 CPU 급등을 며칠씩 쫓게 된다.

### JPA `@BatchSize` — N+1을 완전히 없애는 대신 "N/K+1"로 절충하는 현실적인 카드

`@BatchSize(size=100)`를 걸면, Lazy 로딩되는 연관 엔티티를 100개씩 묶어 `WHERE id IN (?, ?, ...)` 한 번으로 가져온다. `JOIN FETCH`처럼 카티션 곱 폭발이나 페이징 불가 문제를 만들지 않으면서, 순수 Lazy의 N+1도 피하는 중간 지대다.

```java
@Entity
public class Order {
    @OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
    @BatchSize(size = 100)   // ← 100개 Order마다 IN 절 하나
    private List<OrderItem> items;
}

// 결과: Order 1000건 조회 시
// JOIN FETCH → 1 쿼리 (단, 페이징 시 메모리 페이징으로 폭발)
// 순수 Lazy  → 1001 쿼리 (N+1)
// @BatchSize → 11 쿼리 (1 + 1000/100)
```

트레이드오프:
- **JOIN FETCH**: 컬렉션 여러 개는 `MultipleBagFetchException`, 페이징하면 Hibernate가 전체를 메모리로 올림
- **@BatchSize**: IN 절 크기가 커지면 옵티마이저가 인덱스 대신 풀스캔을 고르는 경계값(대개 200~500) 주의
- **전역 설정**: `spring.jpa.properties.hibernate.default_batch_fetch_size=100`으로 프로젝트 전체 기본값을 잡는 게 실무 정석

> 💡 **왜 중요한가**: "N+1 해결 = JOIN FETCH"라는 반사가 페이징을 만나는 순간 무너진다. `@BatchSize`는 그 상황에서 유일하게 살아남는 도구다.
