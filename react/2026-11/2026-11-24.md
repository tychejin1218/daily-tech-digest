### 1. `useSyncExternalStore`: 외부 스토어(Zustand, Redux)가 "tearing" 없이 React 18 Concurrent와 공존하는 비결 — 라이브러리 저자만의 Hook이 아니다

React 18의 Concurrent Rendering은 렌더링 도중에 state 읽기를 "중단-재개"할 수 있어서, 외부 스토어(window 이벤트, 브라우저 API, Redux store)의 값을 `useState` + `useEffect`로 구독하면 같은 렌더 트리 안에서 서로 다른 값이 보이는 **tearing(찢어짐)** 현상이 발생한다. `useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot)`는 "스냅샷"을 동기적으로 읽어 이 문제를 원천 차단하도록 설계된 전용 Hook이며, `window.matchMedia`, `navigator.onLine`, `localStorage` 같은 **브라우저 API를 React state처럼 다룰 때**가 가장 흔한 실전 용례다. 세 번째 인자(`getServerSnapshot`)를 빼먹으면 SSR에서 hydration mismatch가 터지므로, 브라우저 전용 값은 서버 스냅샷으로 "기본값"을 꼭 반환해야 한다.

```jsx
// ❌ 흔한 실수: useState + useEffect로 online 상태 구독
function useOnlineStatus_wrong() {
  const [isOnline, setIsOnline] = useState(true);
  useEffect(() => {
    const on = () => setIsOnline(true);
    const off = () => setIsOnline(false);
    window.addEventListener('online', on);
    window.addEventListener('offline', off);
    return () => { /* ... */ };
  }, []);
  return isOnline; // Concurrent 렌더 중 "찢어질" 수 있음
}

// ✅ useSyncExternalStore — tearing 불가능
function useOnlineStatus() {
  return useSyncExternalStore(
    (callback) => {
      window.addEventListener('online', callback);
      window.addEventListener('offline', callback);
      return () => {
        window.removeEventListener('online', callback);
        window.removeEventListener('offline', callback);
      };
    },
    () => navigator.onLine,     // 클라이언트 스냅샷
    () => true                  // 서버 스냅샷 (hydration 안전)
  );
}
```

> 💡 **왜 중요한가**: Zustand·Jotai·Redux가 React 18에서 안전하게 동작하는 이유가 바로 이 Hook이며, 직접 외부 상태를 구독할 때 `useEffect` 대신 이 Hook을 써야 Concurrent 기능(Suspense, Transition)과 충돌 없이 공존할 수 있다.

### 2. "상태 끌어올리기(Lifting State Up)"는 만능이 아니다 — 두 형제 컴포넌트를 동기화하려다 앱 전체가 리렌더링되는 함정과 "Composition"이라는 탈출구

React 공식 문서가 가르치는 "상태 끌어올리기"는 두 컴포넌트가 같은 state를 공유해야 할 때 가장 가까운 공통 부모로 state를 올리는 패턴이다. 하지만 그 부모가 앱 루트에 가까울수록 **state가 바뀔 때마다 그 아래의 모든 컴포넌트가 리렌더링**되어, 결국 "Context 지옥"이나 "Redux 남용"으로 도망치게 된다. 해결책은 state를 더 올리는 게 아니라 **컴포넌트를 `children` prop으로 받아 "구멍"을 뚫는 Composition 패턴**이다 — state가 바뀌는 부모는 유지하되, 리렌더가 필요 없는 부분은 "밖에서 주입"해서 참조를 그대로 유지시킨다.

```jsx
// ❌ state가 바뀔 때마다 <ExpensiveTree>까지 리렌더링됨
function Parent() {
  const [color, setColor] = useState('red');
  return (
    <div style={{ color }}>
      <input value={color} onChange={(e) => setColor(e.target.value)} />
      <ExpensiveTree /> {/* color와 무관하지만 매번 리렌더 */}
    </div>
  );
}

// ✅ Composition — state가 바뀌는 범위를 "격리"
function ColorPicker({ children }) {
  const [color, setColor] = useState('red');
  return (
    <div style={{ color }}>
      <input value={color} onChange={(e) => setColor(e.target.value)} />
      {children} {/* 밖에서 주입된 children은 리렌더 안 됨 */}
    </div>
  );
}

function App() {
  return (
    <ColorPicker>
      <ExpensiveTree /> {/* App의 자식이므로 color 변경과 무관 */}
    </ColorPicker>
  );
}
```

> 💡 **왜 중요한가**: `React.memo`나 `useMemo`를 남발하기 전에, "state의 위치"와 "컴포넌트의 소유 관계"를 먼저 설계하는 것이 React의 리렌더 성능을 공짜로 얻는 가장 선언적인 방법이다.
