### 1. `Sequence` vs `List`: "체이닝 한 줄"이 N번의 중간 리스트를 만드는 순간, 그리고 지연 평가가 뒤집는 게임

`list.filter { ... }.map { ... }.first()` 는 **깔끔하지만**, filter 결과용 리스트 하나, map 결과용 리스트 하나를 통째로 만든 뒤 first()를 호출한다. `asSequence()`를 붙이는 순간 각 원소가 파이프라인을 **세로로** 통과하며, first()가 걸리면 뒤의 원소는 아예 계산하지 않는다.

```kotlin
// List: 가로 계산 (연산마다 중간 컬렉션 생성)
list.filter { heavy(it) }.map { transform(it) }.first()
// → filter 전체 실행 → 중간 List → map 전체 실행 → 중간 List → first()

// Sequence: 세로 계산 (원소 하나씩 끝까지)
list.asSequence().filter { heavy(it) }.map { transform(it) }.first()
// → 원소1: filter→map→first() ✓ 종료. 나머지는 계산조차 안 함.
```

**실무 함정**: 원소가 적거나(수십 개) 연산이 가볍거나, 터미널 연산이 `toList()`/`sum()`처럼 **전체를 소모**하는 경우엔 Sequence가 오히려 느리다. Sequence는 람다 호출마다 `Iterator` 상태를 들고 다니므로 오버헤드가 있다. **대용량 + 짧은 종료(find/first/take) + 긴 체이닝**일 때만 실질적 이득이 있다.

> 💡 **왜 중요한가**: "스트림 체이닝은 항상 좋다"는 착각을 깨고, **언제 지연 평가가 득이고 언제 독인지**를 구분하는 눈이 Kotlin 컬렉션 설계의 핵심이다.

### 2. `by` 위임 (Delegation): "상속하지 말고 위임하라"를 언어 문법으로 승격시킨 Kotlin의 선택

Java에서 "구현 재사용"을 하려면 상속하거나, 필드로 보유한 뒤 모든 메서드를 손으로 포워딩해야 했다. Kotlin의 `class MyList(list: List<Int>) : List<Int> by list` 한 줄은 **List의 모든 메서드를 자동으로 `list.xxx()`로 위임**한다 — 상속 없이 "is-a" 를 흉내낸다.

```kotlin
interface Repository { fun save(user: User) }

class LoggingRepo(private val delegate: Repository) : Repository by delegate {
    override fun save(user: User) {         // 선택적으로 "덮어쓰기"
        log.info("saving $user")
        delegate.save(user)
    }
}
// save() 외의 모든 Repository 메서드는 delegate로 자동 포워딩
```

**프로퍼티 위임도 같은 철학**: `by lazy`, `by Delegates.observable`, `by map` 등이 모두 `getValue`/`setValue` 연산자 함수 하나로 동작한다. Spring에선 `by lazy`로 "순환 참조 회피"나 "비싼 초기화 지연"에 자주 쓴다.

**숨은 함정**: 위임은 **생성자 시점에 캡처**된다. `class A(b: B) : I by b` 는 생성자 파라미터 `b` 를 그 순간 복사해 저장하므로, 이후 `b`의 상태가 바뀌어도 반영되지 않을 수 있다. 또 위임 대상의 메서드끼리의 호출은 **this가 아닌 delegate**를 통해 일어나므로, 오버라이드한 메서드가 **위임 체인 내부에서 호출되면 무시**된다.

> 💡 **왜 중요한가**: GoF의 "Composition over Inheritance" 원칙이 Kotlin에선 **언어 문법**이다. 디자인 패턴을 외우는 시대에서, 언어가 패턴을 흡수한 시대로 넘어왔다는 증거.
