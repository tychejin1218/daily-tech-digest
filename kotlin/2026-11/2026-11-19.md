### 1. `inline` 함수: "함수 호출의 비용"을 0으로 만드는 대신, 당신의 바이트코드를 뚱뚱하게 하는 거래

Kotlin의 고차 함수는 람다를 `Function` 객체로 래핑해 힙에 할당하는데, `inline` 키워드를 붙이면 컴파일러가 함수 본문과 람다를 **호출 지점에 그대로 복사**한다. 덕분에 객체 할당과 가상 호출이 사라지고, 람다 안에서 `return`으로 바깥 함수까지 탈출하는 **non-local return**이 가능해진다. 하지만 함수가 크거나 호출이 많으면 바이트코드가 폭발적으로 커지므로, 람다를 받는 작은 유틸리티 함수에만 선별적으로 써야 한다.

```
일반 고차 함수:                      inline 함수:
┌─────────────┐                      ┌─────────────┐
│ caller()    │                      │ caller()    │
│  ↓ 호출     │                      │  [본문 복사] │
│ runBlock{}  │  ← Function 객체     │  [람다 복사] │
│  ↓ invoke() │     힙 할당          │  ← 호출 없음│
│ 람다 실행   │                      └─────────────┘
└─────────────┘
```

> 💡 **왜 중요한가**: `stdlib`의 `let`, `run`, `apply`, `forEach`가 모두 `inline`이라 "스코프 함수를 남발해도 성능 손해가 없다"는 Kotlin의 핵심 약속이 바로 이 키워드에서 나온다.

---

### 2. `crossinline` vs `noinline`: inline이 깨지는 두 가지 경계선과 그 이유

`inline` 함수에 전달된 람다는 기본적으로 **호출 지점에 복사**되지만, 람다를 다른 스레드로 넘기거나 변수에 저장하면 "복사"가 불가능해진다. 이때 `noinline`을 붙이면 **그 람다만** 일반 `Function` 객체로 남겨두고 나머지는 인라인되고, `crossinline`을 붙이면 인라인은 유지하되 람다 안에서 **바깥 함수로 탈출하는 non-local return을 금지**한다. 즉, `crossinline`은 "다른 실행 컨텍스트(예: `Runnable`, 콜백)로 넘길 때, return이 엉뚱한 곳으로 튀는 것을 막는 안전장치"다.

```
inline fun run(block: () -> Unit)
   └── block 안에서 return → 바깥 함수까지 탈출 OK

inline fun runLater(crossinline block: () -> Unit) {
   Thread { block() }.start()  ← 다른 컨텍스트
   └── block 안에서 return → 컴파일 에러 (탈출 불가)
}

inline fun saveAndRun(noinline block: () -> Unit) {
   callbacks.add(block)  ← 저장 필요
   └── block만 일반 Function 객체로 유지
}
```

| 키워드 | 인라인 되나? | non-local return | 주 용도 |
|---|---|---|---|
| (기본) | O | O | 일반 스코프 함수 |
| `crossinline` | O | X | 콜백/스레드로 전달 |
| `noinline` | X | X | 람다를 변수에 저장 |

> 💡 **왜 중요한가**: `inline`을 쓰다 보면 반드시 "이 람다 저장하거나 다른 스레드로 못 넘기는데요?" 컴파일 에러를 만나는데, 이 두 키워드의 차이를 모르면 무작정 `noinline`을 붙여 인라인의 성능 이득을 스스로 지워버리게 된다.
