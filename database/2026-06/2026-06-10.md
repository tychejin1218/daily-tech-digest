### 1. PostgreSQL `SELECT ... FOR UPDATE SKIP LOCKED` — DB만으로 동시성 안전한 작업 큐 만들기

여러 워커가 같은 작업 테이블을 폴링할 때 일반 `FOR UPDATE`는 다른 워커가 잡은 행에서 블로킹된다. `SKIP LOCKED`를 붙이면 이미 잠긴 행은 건너뛰고 잠금 가능한 다음 행만 가져오기 때문에, Kafka/Redis Streams 같은 별도 큐 인프라 없이도 안전하게 작업을 분배할 수 있다. `UPDATE jobs SET status='RUNNING' WHERE id = (SELECT id FROM jobs WHERE status='READY' ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING *` 패턴이 정석이다.

> 💡 **왜 중요한가**: "분산 큐 도입 전에 DB로 먼저 해결되는 케이스"가 의외로 많은데, `SKIP LOCKED`를 모르면 워커 늘릴수록 락 대기로 처리량이 도리어 줄어드는 함정에 빠진다.

### 2. Hibernate `hibernate.jdbc.batch_size` + `order_inserts` / `order_updates` — `saveAll()`이 한 건씩 INSERT 날아가는 함정

`saveAll(10_000건)` 호출이 batch INSERT로 묶일 거라 기대하지만, 기본 설정만으로는 그냥 INSERT 10,000번이 따로 날아간다. `hibernate.jdbc.batch_size=50` 외에 `hibernate.order_inserts=true`, `hibernate.order_updates=true`를 같이 켜야 같은 테이블끼리 정렬되어 실제로 JDBC `addBatch()`로 묶이고, 부모-자식이 섞인 경우에도 batch가 깨지지 않는다. PostgreSQL JDBC라면 추가로 URL에 `reWriteBatchedInserts=true`를 붙여야 N개 INSERT가 진짜 한 문장으로 합쳐진다.

> 💡 **왜 중요한가**: 세 설정 중 하나만 빠져도 batch가 조용히 깨져 "왜 똑같은 코드인데 운영만 느리지?" 상황이 만들어진다 — 로그에 에러도 안 남고 EXPLAIN으로도 안 잡힌다.
