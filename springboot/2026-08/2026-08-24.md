### `@Transactional`의 `Propagation.REQUIRES_NEW`는 별도 트랜잭션이 아니라 **별도 커넥션**을 잡는다 — 커넥션 풀 고갈의 조용한 원인

`REQUIRES_NEW`는 기존 트랜잭션을 일시 정지(suspend)하고 새 트랜잭션을 시작하는데, 이때 기존 커넥션을 반환하지 않고 **홀드한 채로** 풀에서 새 커넥션을 하나 더 꺼낸다. 즉 하나의 요청이 최소 2개의 커넥션을 동시에 점유하며, 중첩 호출이 깊어질수록 기하급수적으로 풀이 마르고, HikariCP의 `connectionTimeout`이 터지기 전까지 겉으로는 "느린 API"로만 보인다.

```
[Outer TX]───────── Conn#1 (suspended, 반환 X) ──────────┐
     │                                                    │
     └─▶ [REQUIRES_NEW]─── Conn#2 (active) ──── commit ──┘
                                                          │
     ◀── resume ── Conn#1 재개 ── commit ─────────────────┘
```

실제 사례로 감사 로그(audit log)를 `REQUIRES_NEW`로 남기는 서비스가 트래픽 급증 시 커넥션 풀 20개가 순식간에 소진되어 전체 API가 멈춘 케이스가 흔하다. 트레이드오프: 롤백 격리가 꼭 필요하지 않다면 `@TransactionalEventListener(phase = AFTER_COMMIT)` + `@Async`로 분리하는 편이 커넥션 사용량과 응답 시간 모두 유리하다.

> 💡 **왜 중요한가**: "TX 하나 더 여는 것"으로 착각하기 쉽지만 실제로는 **커넥션 하나 더 잡는 것**이며, 풀 사이즈 계산에서 이 배수를 빠뜨리면 프로덕션에서만 재현되는 지옥의 타임아웃이 열린다.

### Spring Security의 `SecurityContextHolder`는 기본이 `ThreadLocal` — `@Async`/`CompletableFuture`/리액티브로 넘어가는 순간 인증 정보가 **증발**한다

`SecurityContextHolder.getContext().getAuthentication()`은 요청 스레드에 묶여 있어서, `@Async`로 새 스레드에 작업을 던지거나 `parallelStream()`으로 워커 스레드에 넘기는 순간 **`null`이 반환되어 익명 사용자로 처리**된다. 더 무서운 건 예외가 아니라 **조용한 권한 상실**로 나타나기 때문에, 개발 환경에서는 로그인 상태로 잘 돌아가다가 특정 코드 경로에서만 `AccessDeniedException` 혹은 "본인 데이터가 아닌 데이터"가 조회되는 형태로 드러난다.

```
Request Thread                   @Async Worker Thread
─────────────                    ────────────────────
SecurityContext = user123    ✗   SecurityContext = null
    │                            (ThreadLocal이 복사 안 됨)
    └─▶ asyncService.run() ─────▶ getAuthentication() → null
```

해결책은 3가지 계층이다: (1) `SecurityContextHolder.setStrategyName(MODE_INHERITABLETHREADLOCAL)` — 자식 스레드에 상속되지만 스레드 풀에서 재사용되는 스레드에는 이전 사용자의 컨텍스트가 남는 **더 위험한 버그**를 만든다. (2) `DelegatingSecurityContextAsyncTaskExecutor`로 `Executor`를 감싸기 — 권장. (3) 리액티브라면 `ReactiveSecurityContextHolder` + `Context` 전파 사용. 트레이드오프: 옵션 1은 편해 보이지만 스레드 풀 환경에서는 절대 쓰면 안 된다.

> 💡 **왜 중요한가**: 인증 실패가 예외가 아니라 "다른 사용자로 보이는" 형태로 나오기 때문에 프로덕션 데이터 유출 사고 원인 1순위이며, 스레드 풀을 감싸지 않으면 언젠가 반드시 터진다.
