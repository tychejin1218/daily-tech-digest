### `@RequestScope` 빈을 싱글톤에 주입할 때는 `proxyMode = TARGET_CLASS`로 스코프 프록시 켜기
싱글톤 빈은 컨테이너 부팅 시 한 번만 생성되므로, 그 안에 `@RequestScope` 빈을 그냥 주입하면 부팅 시점의 빈 인스턴스가 영구적으로 박혀버려 매 요청마다 새로운 값을 가져오지 못합니다. `@RequestScope(proxyMode = ScopedProxyMode.TARGET_CLASS)`로 등록하면 Spring이 CGLib 프록시를 삽입해 호출 시점마다 현재 요청의 빈으로 위임합니다.

```java
@Component
@RequestScope(proxyMode = ScopedProxyMode.TARGET_CLASS)
public class RequestContext {
    private final String traceId = UUID.randomUUID().toString();
    public String getTraceId() { return traceId; }
}

@Service
@RequiredArgsConstructor
public class AuditService {                      // 싱글톤
    private final RequestContext ctx;            // 프록시가 주입됨
    public void log(String msg) {
        log.info("[{}] {}", ctx.getTraceId(), msg);  // 요청마다 다른 traceId
    }
}
```

> 💡 **왜 중요한가**: traceId·로그인 사용자·테넌트 ID 같은 "요청별 컨텍스트"를 깊은 서비스 레이어까지 파라미터로 끌고 다닐 필요 없이 안전하게 전달할 수 있습니다.

### `ApplicationStartup` API로 부팅 단계 트레이싱하기 (Spring Boot 2.4+)
"애플리케이션이 왜 30초나 걸려서 뜨지?"의 원인을 추측 대신 데이터로 잡으려면 `ApplicationStartup`을 켭니다. `BufferingApplicationStartup`을 등록하면 빈 생성·자동 설정·`@PostConstruct` 같은 각 단계가 타임라인 이벤트로 기록되고, JFR·Actuator(`/actuator/startup`)로 시각화해 가장 오래 걸린 단계를 콕 집어낼 수 있습니다.

```java
@SpringBootApplication
public class App {
    public static void main(String[] args) {
        SpringApplication app = new SpringApplication(App.class);
        app.setApplicationStartup(new BufferingApplicationStartup(2048));
        app.run(args);
    }
}
// application.yml
// management.endpoints.web.exposure.include: startup
// → GET /actuator/startup 호출 후 JSON을 Chrome trace로 임포트
```

> 💡 **왜 중요한가**: 부팅 지연은 보통 "느린 Flyway 마이그레이션", "JPA 메타데이터 스캔", "잘못된 Eureka 클라이언트" 같은 단일 원인이 대부분이며, 이 API로 5분 만에 진범을 식별할 수 있습니다.
