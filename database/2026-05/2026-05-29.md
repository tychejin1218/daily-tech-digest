### PostgreSQL `pg_stat_user_indexes.idx_scan = 0` — 실제로 안 쓰이는 인덱스를 찾아 저장·쓰기 비용 되찾기

인덱스는 `SELECT`를 빠르게 하지만 `INSERT/UPDATE/DELETE`마다 갱신되고 디스크·WAL을 소모한다. `pg_stat_user_indexes`의 `idx_scan`을 확인하면 프로덕션에서 한 번도 사용되지 않은 인덱스를 정확히 식별할 수 있다.

```sql
SELECT schemaname, relname AS table, indexrelname AS index,
       idx_scan, pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
  AND indexrelname NOT LIKE '%_pkey'
ORDER BY pg_relation_size(indexrelid) DESC;
```

통계 리셋 이후 충분한 기간(최소 1~2주, 월말 배치가 있다면 한 달) 관찰한 뒤 제거해야 안전하다. `pg_stat_reset()` 시점을 `pg_stat_database.stats_reset`으로 확인할 것.

> 💡 **왜 중요한가**: 안 쓰이는 인덱스 하나를 지우는 것만으로 write 성능이 눈에 띄게 올라가고, VACUUM·백업 시간도 함께 줄어든다.

### MySQL `innodb_flush_log_at_trx_commit` — 내구성과 처리량 사이에서 의식적으로 트레이드오프하기

InnoDB는 커밋할 때마다 redo log를 디스크에 `fsync`하는데(`=1`, 기본값), 대량 배치·로그성 테이블에서는 이 fsync가 병목이 된다. `=2`로 바꾸면 OS 캐시까지만 쓰고 1초마다 fsync하므로 처리량이 몇 배로 뛰지만, OS 크래시 시 최대 1초 데이터 손실이 발생한다.

```sql
-- 배치 세션에서만 잠깐 완화
SET GLOBAL innodb_flush_log_at_trx_commit = 2;
-- 배치 완료 후 반드시 원복
SET GLOBAL innodb_flush_log_at_trx_commit = 1;
```

결제·주문 등 절대 손실 불가 데이터는 `=1`을 유지하고, 로그·통계·복구 가능한 데이터가 있는 인스턴스만 `=2`를 검토한다. `sync_binlog=1`과 세트로 관리해야 복제 안전성까지 함께 챙길 수 있다.

> 💡 **왜 중요한가**: "왜 커밋이 느리지?"의 답이 이 파라미터 하나에 있는 경우가 많고, 데이터 특성별로 다르게 설정할 수 있음을 아는 것 자체가 튜닝의 시작이다.
