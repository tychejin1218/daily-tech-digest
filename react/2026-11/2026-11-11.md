### 1. useSyncExternalStore: Zustand/Redux가 React 18에서 왜 조용히 갈아탔나 — "tearing" 문제의 정체

React 18의 Concurrent Rendering은 하나의 렌더를 여러 조각으로 나눠서 처리하는데, 그 중간에 외부 스토어(Redux, Zustand 등)의 값이 바뀌면 같은 렌더 트리 안에서 어떤 컴포넌트는 옛 값, 어떤 컴포넌트는 새 값을 쓰는 "tearing(찢어짐)" 현상이 발생한다. `useSyncExternalStore(subscribe, getSnapshot)`은 스냅샷을 동기적으로 읽어서 하나의 렌더 안에서는 반드시 같은 값만 보이도록 강제하는 전용 Hook이고, Zustand v4·Redux Toolkit v8이 내부 구현을 이 Hook으로 전면 교체한 이유가 이것이다. 직접 `useState + useEffect`로 외부 구독을 구현하면 React 17까지는 멀쩡히 돌아가지만 18부터는 `useTransition`·`Suspense`와 섞이는 순간 데이터가 뒤섞여 보이는 버그가 조용히 생긴다.

> 💡 **왜 중요한가**: "외부 상태를 React에 끌어오는 모든 통로"는 이제 React가 지정한 한 개의 공식 Hook만 안전하며, 그 외 방식은 Concurrent 기능과 함께 쓰는 순간 데이터 일관성이 깨진다.

### 2. flushSync: Automatic Batching을 "강제로 깨는" 유일한 탈출구 — DOM 측정과 스크롤 점프의 함정

React 18의 Automatic Batching은 이벤트 핸들러 바깥(Promise, setTimeout)에서도 `setState`들을 하나의 렌더로 묶어버리는데, 이게 축복이자 재앙이다. 예를 들어 "새 메시지를 추가하고 즉시 스크롤을 맨 아래로 내리는" 코드에서 `setMessages(...)` 다음 줄에 `scrollRef.current.scrollTop = scrollRef.current.scrollHeight`를 적으면, 아직 DOM이 업데이트되지 않아 "한 단계 전 높이"로 스크롤되어 마지막 메시지가 가려지는 고전적 버그가 생긴다. `react-dom`의 `flushSync(() => setMessages(...))`로 감싸면 그 상태 업데이트만 동기적으로 DOM에 반영된 뒤 다음 줄이 실행되어 정확한 높이로 스크롤된다. 단, flushSync는 모든 Concurrent 최적화를 포기하는 "비상 탈출구"라서 리스트 가상화·애니메이션 블록과 섞이면 프레임 드롭을 유발하므로, 반드시 "렌더 직후 DOM을 측정해야 하는 그 한 줄"에만 좁게 써야 한다.

> 💡 **왜 중요한가**: `useLayoutEffect`로도 못 푸는 "같은 핸들러 안에서 상태 변경 → 즉시 DOM 측정" 시나리오는 flushSync뿐이며, 이 도구의 존재를 모르면 `setTimeout(() => scroll(), 0)` 같은 레이스 컨디션 폭탄 코드를 양산하게 된다.
