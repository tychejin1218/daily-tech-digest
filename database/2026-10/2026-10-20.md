### Database Tip 1: MySQL `MRR`(Multi-Range Read) — 보조 인덱스 범위 조회의 "랜덤 I/O 지옥"을 순차 I/O로 뒤집는 옵티마이저의 숨은 재정렬

보조 인덱스로 범위 스캔 후 PK로 테이블(클러스터드 인덱스)을 참조할 때, 인덱스가 돌려주는 PK 순서는 테이블의 물리적 PK 순서와 완전히 다르다. MRR은 인덱스에서 뽑은 PK들을 `read_rnd_buffer`에 모아 PK 오름차순으로 재정렬한 뒤 테이블을 읽어, 디스크 헤드가 "앞뒤로 날뛰던" 랜덤 I/O를 순차 접근에 가깝게 바꾼다. HDD는 물론 SSD에서도 버퍼 풀 적중률과 OS 페이지 캐시의 선반입(readahead) 효율을 끌어올려 수 배의 처리량을 만든다.

> 💡 **왜 중요한가**: `WHERE indexed_col BETWEEN ... AND ...` 같은 범위 쿼리에서 "인덱스는 분명히 탔는데 왜 느리지?"의 상당수는 PK 랜덤 접근 비용이며, MRR 활성화 여부(`optimizer_switch='mrr=on,mrr_cost_based=off'`)만으로 실행 계획 설명 없이 성능이 수 배 바뀐다.

### Database Tip 2: PostgreSQL `TOAST`(The Oversized-Attribute Storage Technique) — 2KB 넘는 컬럼이 "조용히 옆방으로 이사"가는 투명한 뒤편의 창고

PostgreSQL의 한 행(튜플)은 반드시 8KB 페이지 하나에 들어가야 하므로, 큰 `TEXT`/`JSONB`/`BYTEA` 값은 자동으로 압축되고 TOAST 전용 테이블로 분리되어 포인터만 본 테이블에 남는다. 겉보기엔 하나의 컬럼이지만 실제로는 별도 테이블에 흩어져 있어, "작은 메타 컬럼만 SELECT"하면 TOAST는 건드리지 않아 수십 배 빠르고, 반대로 `SELECT *`로 거대 JSONB를 매번 끌어오면 보이지 않는 조인 비용과 압축 해제 CPU가 누적된다. `ALTER TABLE ... SET STORAGE (PLAIN/EXTENDED/EXTERNAL/MAIN)`으로 컬럼별 전략을 바꿀 수 있다.

> 💡 **왜 중요한가**: `jsonb`나 긴 `text`를 담는 테이블의 체감 성능은 "행 수"가 아니라 "TOAST 접근 패턴"에 지배되며, 필요한 키만 뽑는 쿼리 설계와 `STORAGE` 튜닝이 인덱스 추가보다 더 큰 효과를 낼 때가 많다.
