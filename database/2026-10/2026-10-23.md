### Database Tip 1: MySQL `Index Condition Pushdown`(ICP) — 스토리지 엔진까지 WHERE 조건을 "밀어 내려서" 불필요한 테이블 접근을 걷어내는 숨은 필터

전통적으로 MySQL은 인덱스에서 찾은 레코드를 **먼저 테이블에서 전부 읽어온 뒤** 서버 계층에서 WHERE 조건을 적용했다. ICP는 인덱스에 이미 포함된 컬럼의 조건을 **스토리지 엔진(InnoDB) 레벨에서 미리 평가**해서, 조건에 맞지 않는 행은 아예 테이블 페이지를 읽지 않고 버린다. 다중 컬럼 인덱스의 선두 컬럼만 범위로 쓰고 뒤 컬럼은 "그냥 걸려 있던" 경우에 특히 효과적이다.

```sql
-- INDEX(last_name, first_name) 가 있을 때
SELECT * FROM people
 WHERE last_name LIKE '김%'   -- 범위 조건
   AND first_name LIKE '%수';  -- 비선두 컬럼 조건

-- ICP OFF: last_name='김%'로 인덱스 스캔 → 모든 매칭 행을 테이블에서 읽음 → 서버가 first_name 필터
-- ICP ON : last_name='김%'로 인덱스 스캔 → 인덱스 안의 first_name을 먼저 평가 → 통과한 것만 테이블 읽기
--          EXPLAIN의 Extra에 "Using index condition" 표시
```

ICP는 선두 컬럼이 **범위(range)**이고 뒤 컬럼이 조건절에 있지만 커버링 인덱스는 아닐 때 극적으로 체감된다 — 랜덤 I/O를 수백 배 줄이는 사례가 흔하다. 반대로 조건이 함수로 감싸져 있거나(`WHERE UPPER(first_name) = ...`) 트리거/가상 컬럼 등으로 평가가 복잡하면 옵티마이저가 ICP를 포기한다.

> 💡 **왜 중요한가**: "인덱스는 탔는데 왜 이렇게 느리지?"의 상당수는 테이블로 돌아간 뒤 버려지는 행 때문이며, ICP는 이 왕복 자체를 없애는 가장 저렴한 최적화다.

### Database Tip 2: JPA `clearAutomatically`와 `flushAutomatically` — 벌크 업데이트 이후 영속성 컨텍스트에 남은 "유령 엔티티"가 조용히 데이터를 덮어쓰는 함정

`@Modifying`이 붙은 JPQL/네이티브 벌크 쿼리는 영속성 컨텍스트를 **우회**해서 DB에 바로 쏜다. 문제는 같은 트랜잭션 안에 이미 로드된 엔티티가 있으면, 1차 캐시의 값은 **옛날 값 그대로** 남고, 트랜잭션 종료 시점의 Dirty Checking이 그 옛날 값으로 다시 UPDATE를 날려 "방금 벌크로 바꾼 결과"를 되돌려 버린다는 점이다.

```java
// 위험한 패턴
Member m = memberRepository.findById(1L).orElseThrow(); // 1차 캐시에 로드
m.getPoint();                                            // 100 (옛날 값)

memberRepository.bulkAddPoint(1L, 500);                  // DB는 이제 600
// 하지만 1차 캐시의 m.point는 여전히 100
// → 커밋 시점에 Dirty Checking이 UPDATE member SET point=100 ... 을 날릴 수 있음

@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("UPDATE Member m SET m.point = m.point + :p WHERE m.id = :id")
int bulkAddPoint(@Param("id") Long id, @Param("p") int p);
```

`flushAutomatically = true`는 **쿼리 실행 전** 영속성 컨텍스트의 변경을 먼저 DB에 flush해서 "이미 수정 중이던 엔티티"가 벌크 쿼리에 반영되게 한다. `clearAutomatically = true`는 **쿼리 실행 후** 1차 캐시를 비워, 뒤이은 조회가 반드시 DB에서 다시 읽도록 강제한다. 둘을 같이 켜지 않으면 벌크 연산 전후의 엔티티 조회 결과가 예측 불가능해진다.

> 💡 **왜 중요한가**: 벌크 UPDATE가 "로그에는 분명 나갔는데 결과가 원복되는" 유령 버그의 범인은 거의 100% 1차 캐시이며, 이 두 플래그는 그 유령을 끄는 유일한 선언적 스위치다.
