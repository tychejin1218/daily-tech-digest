### Database Tip 1: MySQL `Index Merge` — 하나의 테이블에 여러 인덱스를 "동시에" 쓰는 옵티마이저의 숨은 수

보통 MySQL은 테이블 하나당 인덱스 하나만 사용한다고 알려져 있지만, 사실 옵티마이저는 `WHERE a = 1 OR b = 2` 같은 조건에서 두 개의 단일 컬럼 인덱스를 각각 스캔해 결과를 `UNION`/`INTERSECT`/`SORT_UNION`으로 합치는 **Index Merge** 전략을 꺼낸다. `EXPLAIN`에서 `type: index_merge`와 `Extra: Using union(idx_a, idx_b)`를 발견했다면 복합 인덱스를 만들기 전에 한 번 더 고민해야 하는 신호다 — 반대로 Index Merge가 자꾸 선택된다면 그건 "진짜 필요한 복합 인덱스가 빠져 있다"는 옵티마이저의 간접적인 비명이기도 하다.

```sql
-- 두 개의 단일 인덱스가 각각 존재할 때
EXPLAIN SELECT * FROM orders
WHERE user_id = 100 OR status = 'PENDING';
-- type: index_merge
-- key: idx_user_id, idx_status
-- Extra: Using union(idx_user_id,idx_status); Using where
```

> 💡 **왜 중요한가**: Index Merge는 "구원"이자 "경고"다. OR 조건이 느릴 때 Full Scan을 피해주는 마지막 보루이면서, 동시에 `(user_id, status)` 같은 복합 인덱스로 더 빨라질 수 있다는 힌트를 준다. `index_merge`를 보면 "다행이다"가 아니라 "왜 하나로 못 풀고 있지?"를 먼저 물어야 한다.

### Database Tip 2: PostgreSQL `FILLFACTOR` — 테이블/인덱스의 "빈 공간"을 미리 남겨 HOT Update와 페이지 분할을 조율하는 설정

`FILLFACTOR`는 테이블이나 인덱스 페이지를 처음 채울 때 얼마나 꽉 채울지(기본 테이블 100%, B-tree 인덱스 90%)를 결정하는 저장 파라미터다. 일부러 70~80%로 낮춰두면 같은 페이지 안에 UPDATE된 새 튜플이 들어갈 자리가 생기므로 **HOT Update**가 활성화되어 인덱스 갱신을 건너뛸 수 있고, 인덱스 쪽에서는 **페이지 분할(page split)** 빈도가 줄어 쓰기 지연과 단편화가 완화된다. 공짜 점심은 없어서 디스크 사용량과 Full Scan 비용은 늘어나므로, UPDATE가 잦은 "핫 테이블"에만 선택적으로 적용하는 것이 정석이다.

```sql
-- UPDATE가 빈번한 테이블: 20% 여유 공간 확보
CREATE TABLE user_sessions (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL,
    last_seen_at TIMESTAMPTZ NOT NULL,
    payload JSONB
) WITH (fillfactor = 80);

-- 기존 테이블 조정 후 재구성
ALTER TABLE user_sessions SET (fillfactor = 80);
VACUUM FULL user_sessions;  -- 또는 pg_repack

-- 인덱스 FILLFACTOR (B-tree 기본 90)
CREATE INDEX idx_sessions_user ON user_sessions(user_id) WITH (fillfactor = 80);
```

> 💡 **왜 중요한가**: PostgreSQL의 MVCC는 UPDATE를 "새 튜플 INSERT + 기존 튜플 dead"로 처리하기 때문에, 같은 페이지 안에 새 튜플이 못 들어가는 순간 인덱스 전체가 갱신되고 테이블은 부풀어 오른다. FILLFACTOR 80은 "HOT Update가 숨 쉴 수 있는 20%의 공기"를 미리 남겨두는, 쓰기 성능을 위한 가장 저렴한 투자다.
