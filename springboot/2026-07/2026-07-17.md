### `hibernate.query.in_clause_parameter_padding=true`로 IN 절 쿼리 플랜 캐시 히트율 극대화하기

Hibernate가 `IN (?, ?, ?)` 절의 파라미터 개수를 2의 거듭제곱(1, 2, 4, 8, 16, 32…)으로 자동 패딩해 SQL 문자열의 형태를 몇 가지로 수렴시킵니다. 결과적으로 PreparedStatement 캐시와 Oracle/PostgreSQL의 쿼리 플랜 캐시 히트율이 크게 올라 파싱·플래닝 비용이 줄어듭니다.

```yaml
spring:
  jpa:
    properties:
      hibernate:
        query:
          in_clause_parameter_padding: true
```

예를 들어 `findAllById(List.of(1, 2, 3))`는 `IN (?, ?, ?, ?)`로 마지막 파라미터가 3으로 중복 패딩되어, 5개 조회(`IN (?, ?, ?, ?, ?, ?, ?, ?)` → 8개 슬롯)와 함께 캐시 엔트리가 무한히 늘어나지 않습니다.

> 💡 **왜 중요한가**: 서로 다른 크기의 IN 절이 매번 새로운 SQL로 취급되어 DB의 shared pool을 잠식하고 hard parse가 반복되는 문제를, 설정 한 줄로 근본 차단할 수 있습니다.

### `@AuthenticationPrincipal`로 `SecurityContextHolder` 직접 호출 없이 인증 사용자 주입받기

컨트롤러 파라미터에 `@AuthenticationPrincipal`을 붙이면 Spring Security가 현재 인증된 `Principal` 객체를 자동으로 바인딩해 줍니다. `SecurityContextHolder.getContext().getAuthentication().getPrincipal()` 같은 정적 호출이 사라져 테스트 용이성과 가독성이 함께 좋아집니다.

```java
@GetMapping("/me")
public UserResponse me(@AuthenticationPrincipal CustomUserDetails user) {
    return UserResponse.of(user.getId(), user.getEmail());
}

// SpEL로 필드까지 직접 뽑을 수도 있습니다
@GetMapping("/orders")
public List<Order> myOrders(@AuthenticationPrincipal(expression = "id") Long userId) {
    return orderService.findByUserId(userId);
}
```

테스트에서는 `@WithMockUser` 대신 `@WithUserDetails` 또는 커스텀 `SecurityMockMvcRequestPostProcessors.user(...)`로 자연스럽게 대체됩니다.

> 💡 **왜 중요한가**: 정적 컨텍스트 조회를 컨트롤러 시그니처의 명시적 파라미터로 바꾸면 의존성이 드러나고, Mock 주입만으로 단위 테스트가 가능해져 시큐리티 결합도가 크게 낮아집니다.
