### `@Cacheable`은 같은 클래스 내부 호출 시 캐시가 동작하지 않는다

Spring의 캐시 추상화(`@Cacheable`, `@CachePut`, `@CacheEvict`)는 AOP 프록시 기반으로 동작하기 때문에, 같은 빈 내부에서 `this.method()`로 자기 자신을 호출하면 프록시를 우회해 캐시 로직이 전혀 실행되지 않는다. `@Transactional`과 정확히 동일한 self-invocation 함정이며, 캐시 히트율이 0%인데 원인을 못 찾겠다면 대부분 이 문제다. 해결책은 캐시 대상 메서드를 별도 빈으로 분리하거나, `AopContext.currentProxy()` 또는 자기 자신을 `@Lazy`로 주입받아 프록시를 통해 호출하는 것이다.

```java
@Service
public class ProductService {
    // ❌ 캐시 안 걸림 - 내부 호출은 프록시 우회
    public List<Product> getProductsByCategory(String category) {
        return findProduct(category); // this.findProduct() 와 동일
    }

    @Cacheable("products")
    public List<Product> findProduct(String category) {
        return productRepository.findByCategory(category);
    }
}
```

> 💡 **왜 중요한가**: 캐시가 안 걸리는 것을 모르고 운영에 배포하면 DB에 그대로 부하가 전달되어 성능 개선 효과가 0이 된다.

### `@MockBean`은 각 테스트마다 `ApplicationContext`를 새로 만들어 테스트를 느리게 한다

`@MockBean`과 `@SpyBean`은 Spring이 관리하는 빈을 목으로 교체하는데, 이 과정에서 컨텍스트 캐시 키가 달라져 테스트 클래스마다 새로운 `ApplicationContext`가 생성된다. 100개 테스트 클래스가 각기 다른 `@MockBean` 조합을 쓰면 100개의 컨텍스트가 뜨고, 통합 테스트 시간이 수 배로 늘어난다. 순수 단위 테스트에서는 `@ExtendWith(MockitoExtension.class)`와 `@Mock`을 쓰고, 통합 테스트에서는 `@MockBean` 조합을 최대한 통일해서 컨텍스트 재사용률을 높여야 한다.

```java
// ❌ 매 테스트 클래스마다 컨텍스트 재생성
@SpringBootTest
class OrderServiceTest {
    @MockBean private PaymentClient paymentClient;
    @MockBean private InventoryClient inventoryClient;
}

// ✅ 컨텍스트 없이 순수 Mockito
@ExtendWith(MockitoExtension.class)
class OrderServiceTest {
    @Mock private PaymentClient paymentClient;
    @Mock private InventoryClient inventoryClient;
    @InjectMocks private OrderService orderService;
}
```

> 💡 **왜 중요한가**: CI 시간을 결정짓는 가장 큰 요인 중 하나가 Spring 컨텍스트 생성 횟수이며, `@MockBean` 남용은 빌드 시간을 조용히 몇 배로 늘린다.
