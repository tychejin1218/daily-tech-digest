### Database Tip 1: MySQL `Covering Index` — 테이블 접근을 "0회"로 만드는 인덱스 설계의 극한

보조 인덱스는 보통 "인덱스 → PK → 테이블 데이터" 순으로 2단계 조회를 거치지만, SELECT·WHERE·ORDER BY에 등장하는 모든 컬럼이 인덱스에 포함되어 있다면 옵티마이저는 테이블 접근(Random I/O)을 통째로 건너뛴다. 이것이 `Covering Index`이고, `EXPLAIN`의 `Extra` 컬럼에 `Using index`로 찍히면 성공한 것이다. MySQL 8.0부터는 인덱스 끝에 비검색 컬럼을 매달아 커버링 전용으로 만드는 패턴이 흔하게 쓰인다.

> 💡 **왜 중요한가**: 수백만 행 테이블에서 응답 시간이 100ms → 2ms로 떨어지는 가장 극적인 최적화가 "SELECT 컬럼 하나를 인덱스 끝에 추가"하는 것뿐일 때가 많기 때문이다.

```
-- Before: PK로 테이블 뒤짐 (Random I/O N번)
CREATE INDEX idx_user_status ON orders(user_id, status);
SELECT user_id, status, amount FROM orders WHERE user_id = 42;
-- Extra: NULL (테이블 접근 발생)

-- After: 인덱스만으로 쿼리 완결
CREATE INDEX idx_user_status_cover ON orders(user_id, status, amount);
SELECT user_id, status, amount FROM orders WHERE user_id = 42;
-- Extra: Using index  ← 테이블 접근 0회
```

**트레이드오프**: 인덱스 크기가 커져 쓰기 비용과 메모리 사용량이 늘어난다. 모든 쿼리를 커버링으로 만들면 안 되고, "읽기 빈도 × 응답시간 민감도"가 높은 핵심 쿼리에만 선별 적용해야 한다.

### Database Tip 2: JPA `@EntityGraph` — Fetch Join의 "쿼리 따로 선언 따로" 문제를 메서드 단위로 해결하는 선언적 그래프

`@EntityGraph`는 "이 조회에서는 이 연관을 EAGER로 당겨와라"를 **쿼리와 분리해서** 선언하는 방식이다. 기존 Fetch Join은 JPQL에 `JOIN FETCH`를 박아야 해서 같은 엔티티를 다른 로딩 전략으로 조회하려면 쿼리를 N개 복제해야 했지만, `@EntityGraph`는 **동일한 쿼리 메서드에 어노테이션만 바꿔** 로딩 전략을 재구성할 수 있다. Spring Data JPA의 Repository 메서드 위에 바로 붙일 수 있어 특히 강력하다.

> 💡 **왜 중요한가**: "리스트 조회에서는 User만, 상세 조회에서는 User+Orders+Items까지" 같은 화면별 로딩 전략 분기를 쿼리 중복 없이 선언적으로 처리할 수 있어, N+1 해결과 코드 가독성을 동시에 잡을 수 있기 때문이다.

```java
public interface OrderRepository extends JpaRepository<Order, Long> {

    // 리스트: Order만 (Lazy 유지)
    List<Order> findByUserId(Long userId);

    // 상세: Order + User + Items 한방 조회
    @EntityGraph(attributePaths = {"user", "items"})
    Optional<Order> findWithDetailsById(Long id);

    // 같은 JPQL을 다른 그래프로 재사용
    @EntityGraph(attributePaths = {"items"})
    @Query("SELECT o FROM Order o WHERE o.status = :status")
    List<Order> findByStatusWithItems(@Param("status") OrderStatus status);
}
```

**함정**: `@EntityGraph`는 내부적으로 `LEFT OUTER JOIN`을 생성하므로 **ToMany 연관을 두 개 이상 포함하면 MultipleBagFetchException** 또는 카티션 곱 폭발이 발생한다. 이 경우 하나는 `@BatchSize`로 분리해야 한다. 또한 페이징(`Pageable`)과 함께 쓰면 Hibernate가 "메모리에서 페이징"하는 경고(`HHH000104`)를 띄우니 반드시 확인해야 한다.
