### LLM Gateway 패턴 — "여러 모델을 하나의 엔드포인트로" 뒤에 숨은 진짜 문제들

LLM Gateway는 표면적으로는 "OpenAI, Anthropic, Bedrock, 자체 호스팅 모델을 하나의 API로 감싼다"는 프록시로 보인다. 하지만 시니어 관점에서 LLM Gateway가 실제로 푸는 문제는 **프록시**가 아니라 **거버넌스**다. 애플리케이션 코드에서 `openai.chat.completions.create()`를 직접 호출하는 순간, 조직은 다음 다섯 가지를 잃는다: 비용 가시성, 키 로테이션 능력, 모델 A/B 실험 능력, 레이트 리밋 통제, PII 필터링 지점. LLM Gateway는 이 다섯 가지를 되찾기 위한 "네트워크 밖의 컨트롤 플레인"이다. Kong, LiteLLM, Portkey, AWS Bedrock Gateway, Cloudflare AI Gateway가 모두 이 층을 서로 다른 방식으로 구현하고 있다.

#### 왜 애플리케이션에서 직접 부르면 안 되는가

한 팀이 GPT-4o로 파일럿을 만들고, 다른 팀은 Claude Sonnet으로 시작하고, 또 다른 팀은 자체 Llama 파인튜닝을 붙인다. 6개월 뒤 CFO가 "지난달 LLM 비용이 왜 4배 늘었지?"라고 물으면, 각 서비스가 각자의 SDK로 각자의 API 키를 쓰고 있어 **어느 팀의 어느 프롬프트가 얼마를 태웠는지 아무도 대답 못 한다**. 이것이 LLM Gateway 없이 시작한 조직이 6개월 안에 반드시 마주치는 벽이다.

더 심각한 건 **모델 벤더 락인**이다. OpenAI에 장애가 나면 서비스가 죽는데, 코드베이스 곳곳에 `openai.ChatCompletion`이 박혀 있어서 Anthropic으로 즉시 페일오버할 수가 없다. 이 두 문제 — 비용 가시성과 벤더 독립성 — 가 LLM Gateway의 존재 이유다.

#### 아키텍처

```
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│  App A      │  │  App B      │  │  Batch Job  │
│ (Chatbot)   │  │ (Summarize) │  │  (Nightly)  │
└──────┬──────┘  └──────┬──────┘  └──────┬──────┘
       │                │                │
       │  OpenAI-compat REST (동일 스펙)  │
       ▼                ▼                ▼
┌──────────────────────────────────────────────┐
│              LLM Gateway                      │
│  ┌────────────────────────────────────────┐   │
│  │  1. AuthN/AuthZ (팀별 가상 API 키)      │   │
│  │  2. Rate Limit (팀·모델별 쿼터)         │   │
│  │  3. PII Redactor (요청 전 마스킹)        │   │
│  │  4. Router (모델 선택 규칙)             │   │
│  │  5. Semantic Cache (동일 질의 재사용)    │   │
│  │  6. Retry / Fallback (벤더 장애 시)     │   │
│  │  7. Logger (프롬프트·응답·토큰·비용)     │   │
│  │  8. Guardrail (응답 필터·JSON 강제)     │   │
│  └────────────────────────────────────────┘   │
└────┬───────────┬───────────┬──────────────┬───┘
     │           │           │              │
     ▼           ▼           ▼              ▼
  OpenAI     Anthropic    Bedrock       Self-hosted
  (GPT-4o)  (Claude 4.6)  (Llama 3.1)   (vLLM)
```

핵심은 **애플리케이션이 벤더 SDK가 아니라 Gateway의 통일된 스펙(대개 OpenAI 호환)에만 의존한다**는 것이다. 모델을 바꾸는 결정은 Gateway 설정 파일에서 이루어진다.

#### 라우팅 규칙의 실제 예시

```yaml
routes:
  - name: chatbot-cheap
    conditions:
      team: customer-support
      task: classification
    primary: bedrock/llama-3.1-70b     # 저비용
    fallback:
      - anthropic/claude-haiku-4.5     # 벤더 장애 시
    rate_limit: 100 rpm, $500/day

  - name: reasoning-premium
    conditions:
      team: research
      task: complex-reasoning
    primary: anthropic/claude-opus-4.7
    fallback:
      - openai/gpt-4o
    semantic_cache:
      similarity_threshold: 0.95
      ttl: 24h
```

`task: classification`처럼 **단순 작업엔 저렴한 모델을**, 복잡한 추론엔 프리미엄 모델을 라우팅하는 결정이 **애플리케이션 배포 없이 YAML 수정만으로** 이루어진다. 이것이 LLM Gateway가 "프록시가 아니라 컨트롤 플레인"인 이유다.

#### 트레이드오프

| 항목 | 얻는 것 | 잃는 것 |
|------|---------|---------|
| **레이턴시** | 캐시 히트 시 수 ms | 캐시 미스 시 30~100ms 오버헤드 |
| **비용 가시성** | 팀·프롬프트별 정산 | Gateway 자체 운영비 |
| **모델 자유도** | 벤더 교체가 설정 변경 | 벤더별 고유 기능(예: OpenAI Assistants API, Anthropic Files API)은 최소 공통분모로 수렴 |
| **가용성** | 페일오버로 SLA 상승 | Gateway 자체가 SPOF — HA 구성 필수 |
| **거버넌스** | PII·감사 로그 단일 지점 | 규정상 로그 보존 의무가 새로 생김 |

**"최소 공통분모 문제"** 가 가장 자주 간과된다. OpenAI의 structured output, Anthropic의 tool_use, Gemini의 grounding — 각 벤더의 강점 기능은 Gateway의 통합 스펙에 담기 어렵다. Gateway를 도입하면 "가장 낮은 공통 수준의 API"만 쓰게 되어, 특정 벤더의 첨단 기능을 포기하는 대가를 치른다.

#### 실제 사례

- **Uber**: `Michelangelo`에 LLM Gateway 계층을 붙여 사내 수백 개 서비스가 OpenAI/Bedrock/자체 모델을 동일 스펙으로 호출한다. 이유는 "각 팀이 자기 마음대로 벤더와 계약하면 조달·법무·보안 리뷰가 팀 수만큼 반복된다"였다.
- **Doordash**: 초기엔 OpenAI 직접 호출로 시작했다가, GPT-4 outage 시 주문 지원 챗봇이 다운되는 사고 후 LiteLLM 기반 Gateway를 도입, Claude/Bedrock 페일오버를 붙였다.
- **Cloudflare AI Gateway**: SaaS 형태의 Gateway로, 캐싱만으로 30~70% 비용 절감을 마케팅한다. 소규모 팀이 자체 Gateway를 만들 여력이 없을 때 채택된다.
- **Portkey / LiteLLM Proxy**: 오픈소스 진영의 표준. LiteLLM은 100+ 벤더를 OpenAI 스펙으로 어댑팅하는 데 특화되어 있고, Portkey는 관측성·거버넌스 UI가 강점이다.

#### 언제 쓰고, 언제 쓰지 말아야 하는가

**써야 할 때**
- **팀이 3개 이상**이고 각 팀이 LLM을 독립적으로 쓸 때. 비용 정산과 감사 요구가 반드시 온다.
- **PII·기밀 데이터가 프롬프트에 실릴 위험**이 있을 때. 마스킹을 애플리케이션마다 반복 구현하면 반드시 누락된다.
- **벤더 SLA를 신뢰 못 할 때**. LLM API의 실질 가용성은 전통적 SaaS보다 낮다. 페일오버가 사업 요구사항이면 Gateway가 사실상 유일한 답이다.
- **비용 최적화가 목표일 때**. Semantic Cache와 모델 라우팅은 Gateway 없이 구현하면 애플리케이션마다 재발명된다.

**쓰지 말아야 할 때**
- **파일럿·PoC 단계**. 아직 어떤 모델·어떤 프롬프트가 맞는지 모를 때 Gateway부터 세우면 조기 추상화의 함정에 빠진다. 벤더 SDK를 직접 부르며 시행착오를 겪는 편이 낫다.
- **단일 벤더 고급 기능이 핵심일 때**. Anthropic의 Extended Thinking, OpenAI의 Realtime API처럼 벤더 고유 기능에 사업 가치가 걸려 있으면 Gateway의 최소 공통분모 스펙이 걸림돌이 된다. 이때는 벤더별 얇은 클라이언트를 유지하는 편이 낫다.
- **초저지연 요구**. 음성 대화처럼 100ms 예산이 빠듯할 때 Gateway 오버헤드는 부담이다. 이 경우 라우팅·캐싱을 애플리케이션 안으로 인라이닝하는 것도 정당한 선택이다.
- **팀이 1개, 모델도 1개**. Gateway는 "여러 소비자와 여러 공급자"를 전제로 한 패턴이다. 소비자·공급자가 각각 하나면 SDK 직접 호출이 정답이다.

#### 시니어의 판단 기준

LLM Gateway는 **"모델 API를 인프라 계층으로 강등시키는 결정"** 이다. 강등이 이르면 조기 추상화, 늦으면 거버넌스 부재로 인한 비용·규정 사고가 온다. 기준은 단순하다 — **"CFO나 CISO가 LLM 사용 현황을 물었을 때 30분 안에 답할 수 있는가?"** 없으면 Gateway가 필요한 시점이 이미 지난 것이다.

> 💡 **왜 중요한가**: LLM Gateway는 API 프록시가 아니라 "여러 팀·여러 모델을 감당 가능한 조직 자산으로 만드는 컨트롤 플레인"이며, 도입 시점을 놓치면 비용 가시성·벤더 독립성·규정 준수를 동시에 잃는다.
