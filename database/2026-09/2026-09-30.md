### MySQL `EXPLAIN`의 `Extra` 컬럼 완전 정복 — `Using filesort`와 `Using temporary`가 진짜 무서운 이유

`EXPLAIN`을 볼 때 대부분 `type`(ref, range, ALL)과 `rows`만 본다. 하지만 진짜 성능 지옥은 `Extra` 컬럼에 숨어 있다. `Using index`(커버링 인덱스, 최고의 신호)와 `Using where`(WHERE 필터링, 정상)는 괜찮지만, `Using filesort`(ORDER BY용 별도 정렬)와 `Using temporary`(GROUP BY/DISTINCT용 임시 테이블)가 함께 뜨면 MySQL은 결과를 메모리(`tmp_table_size` 초과 시 디스크)에 복사한 뒤 정렬한다. 특히 `Using temporary; Using filesort`가 동시에 뜬 GROUP BY는 대용량에서 그대로 서버를 눕힌다.

```sql
-- ❌ Extra: Using where; Using temporary; Using filesort
SELECT user_id, COUNT(*) FROM orders 
WHERE created_at > '2026-01-01' 
GROUP BY user_id ORDER BY COUNT(*) DESC;

-- ✅ (user_id, created_at) 복합 인덱스 + 정렬 컬럼 재설계
-- Extra: Using index
```

해결책은 세 가지다. (1) ORDER BY 컬럼을 인덱스 순서에 맞추거나, (2) GROUP BY 컬럼을 인덱스 선두에 두거나, (3) 애초에 집계 결과를 별도 테이블로 미리 만들어두는 것(materialized view 패턴). `filesort`를 봤다면 반드시 `Using filesort` 옆에 `Using index`가 함께 뜨는 인덱스 정렬(index sort)로 바꿔야 한다.

> 💡 **왜 중요한가**: `type=ref`로 인덱스 잘 탄다고 안심하는 순간, `Extra`의 `filesort`가 정렬을 위해 100만 행을 디스크에 복사하고 있을 수 있다.

### PostgreSQL `SKIP LOCKED` — 여러 워커가 같은 큐 테이블을 "겹치지 않게" 나눠 먹는 우아한 방법

DB 테이블을 잡 큐로 쓰는 순간 모두가 부딪히는 문제: 워커 10개가 동시에 `SELECT ... FOR UPDATE LIMIT 1`을 날리면 9개는 락 대기로 멈춰버린다. Redis, Kafka 없이 그냥 PostgreSQL만으로 이걸 해결하는 마법의 두 단어가 `FOR UPDATE SKIP LOCKED`(PG 9.5+, MySQL 8.0+)다. 이미 다른 트랜잭션이 락을 잡은 행은 **기다리지 않고 그냥 건너뛴다**.

```sql
-- 워커 N개가 동시에 실행해도 서로 다른 행을 잡는다
BEGIN;
SELECT id, payload FROM job_queue 
WHERE status = 'pending' 
ORDER BY created_at 
LIMIT 10 
FOR UPDATE SKIP LOCKED;  -- 🔑 잠긴 행은 스킵

-- 처리 후...
UPDATE job_queue SET status = 'done' WHERE id IN (...);
COMMIT;
```

트레이드오프: (1) 처리 순서가 엄격히 보장되지 않는다 — 5번 행이 잠겨 있으면 6번을 먼저 잡는다. FIFO가 필수라면 부적합. (2) `status='pending'` 조건에 부분 인덱스(`WHERE status='pending'`)를 걸어야 큐가 커져도 성능이 유지된다. (3) 진짜 대규모(초당 수만 건)라면 결국 Kafka로 가야 하지만, 초당 수백~수천 건까지는 이 한 줄로 충분하다. Sidekiq, RQ 같은 큐 라이브러리들이 왜 최근 PostgreSQL 백엔드를 밀고 있는지 이유가 여기 있다.

> 💡 **왜 중요한가**: 별도 큐 시스템 없이 DB만으로 병렬 워커를 굴리는 가장 깔끔한 방법 — Redis 추가 인프라 없이 트랜잭션 안전성까지 공짜로 얻는다.
