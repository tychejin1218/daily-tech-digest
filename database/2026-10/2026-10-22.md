### Database Tip 1: MySQL `innodb_buffer_pool_instances` — 단일 Mutex 경합을 "여러 개의 작은 풀"로 쪼개 멀티코어 CPU를 질식시키지 않는 숨은 분할 통치

InnoDB의 Buffer Pool은 전역 Mutex로 보호되는데, 수십 개 코어가 동시에 페이지를 요청하면 이 Mutex가 병목이 되어 CPU가 놀면서도 TPS가 멈춰 선다. `innodb_buffer_pool_instances`를 N으로 설정하면 Buffer Pool이 N개의 독립된 풀로 쪼개지고 각 풀이 자신만의 LRU/Flush/Free 리스트와 Mutex를 가져, 페이지 해시의 모듈로 연산으로 분산되어 경합이 1/N로 줄어든다. Buffer Pool이 1GB 이상이고 코어가 많다면 보통 `물리 코어 수`나 `buffer_pool_size / 1GB` 중 작은 값으로 맞추는 것이 공식처럼 쓰이지만, 반대로 작은 Buffer Pool(1GB 미만)에서는 인스턴스를 쪼개면 각 풀이 너무 작아져 Hit Ratio가 떨어진다.

```
┌─────────────────────────────────────────────────────────┐
│  instances = 1 (단일 풀)                                │
│  ┌─────────────────────────────────────────────────┐    │
│  │     Buffer Pool 128GB                           │    │
│  │     [LRU][Flush][Free]  ← 하나의 Mutex          │    │
│  └─────────────────────────────────────────────────┘    │
│  Thread1 ─┐                                             │
│  Thread2 ─┼─→ 🔒 Mutex 대기열 (경합 폭발)                │
│  Thread3 ─┘                                             │
└─────────────────────────────────────────────────────────┘
                        ↓ 분할
┌─────────────────────────────────────────────────────────┐
│  instances = 8                                          │
│  ┌─────┐┌─────┐┌─────┐┌─────┐┌─────┐┌─────┐┌─────┐┌───┐ │
│  │16GB ││16GB ││16GB ││16GB ││16GB ││16GB ││16GB ││..│  │
│  │🔒L  ││🔒L  ││🔒L  ││🔒L  ││🔒L  ││🔒L  ││🔒L  ││🔒L│  │
│  └─────┘└─────┘└─────┘└─────┘└─────┘└─────┘└─────┘└───┘ │
│  Thread1 ─→ hash(page) % 8 → Pool 3 (경합 1/8로 분산)    │
└─────────────────────────────────────────────────────────┘
```

> 💡 **왜 중요한가**: Buffer Pool을 키우기만 했는데 TPS가 안 오르는 "메모리는 쌓였는데 속도는 그대로" 현상의 범인은 거의 전역 Mutex 경합이며, `innodb_buffer_pool_instances`는 코드 한 줄 안 고치고 멀티코어의 숨겨진 처리량을 뽑아내는 가장 저렴한 손잡이다.

### Database Tip 2: JPA `Persistence Context`의 1차 캐시 — "같은 트랜잭션 안의 동일 ID 조회"는 SELECT를 날리지 않는 영속성 컨텍스트의 숨은 메모화

JPA에서 `em.find(Member.class, 1L)`을 같은 트랜잭션 안에서 두 번 호출하면 두 번째 호출은 SQL이 나가지 않는데, 이는 영속성 컨텍스트가 `@Id`를 키로 하는 Map 형태의 1차 캐시에 엔티티를 담아두고 재사용하기 때문이다. 또한 이 메커니즘은 "동일성(==) 보장"까지 제공해 같은 트랜잭션에서 조회한 엔티티는 `==` 비교가 참이 되는데, 이는 Repository 레이어에서 조회한 엔티티와 Service 레이어에서 다시 조회한 엔티티를 안심하고 참조 비교할 수 있다는 뜻이다. 다만 1차 캐시는 트랜잭션 범위이므로 트랜잭션이 끝나면 함께 사라지며, JPQL이나 `findAll()`은 1차 캐시를 "먼저 조회"하지 않고 항상 DB로 쿼리를 날린 뒤 결과를 1차 캐시와 동기화하는 식으로 동작하기에 "find는 캐시 히트, JPQL은 캐시 미스"라는 비대칭이 생긴다.

```
┌─────────────────── Transaction ───────────────────┐
│                                                   │
│  em.find(Member, 1L) ──→ 1차 캐시 조회            │
│                            │                      │
│                      ┌─────▼─────┐                │
│                      │  (empty)  │                │
│                      └─────┬─────┘                │
│                            ↓ miss                 │
│                     🗄️ DB SELECT                  │
│                            │                      │
│                      ┌─────▼─────────────┐        │
│                      │ {1L: Member@a1}   │ ← 저장  │
│                      └─────┬─────────────┘        │
│                                                   │
│  em.find(Member, 1L) ──→ 1차 캐시 조회            │
│                            │                      │
│                      ┌─────▼─────────────┐        │
│                      │ {1L: Member@a1}✓  │ hit!   │
│                      └─────┬─────────────┘        │
│                            ↓                      │
│                     🚫 SELECT 생략                │
│                     return Member@a1              │
│                                                   │
│  m1 == m2  →  true (동일성 보장)                  │
└───────────────────────────────────────────────────┘
```

> 💡 **왜 중요한가**: 1차 캐시의 작동 방식을 모르면 "왜 같은 메서드를 두 번 호출해도 쿼리가 한 번만 나가지?"라거나 반대로 "JPQL은 왜 캐시를 안 쓰지?" 같은 혼란이 반복되며, 이 비대칭을 알면 "조회가 많은 메서드는 `findById`로 통일" 같은 성능 최적화와 "엔티티 동일성 비교 가능 범위"를 설계 단계에서 명확히 그릴 수 있다.
