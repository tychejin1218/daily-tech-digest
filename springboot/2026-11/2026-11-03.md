### 1. Spring의 `@Scope("prototype")` 빈을 싱글톤 빈에 주입하면, **프로토타입이 아니게 된다** — 그래서 "매번 새로 생성"이라는 약속은 조용히 깨진다

`@Scope("prototype")`은 "요청할 때마다 새 인스턴스"를 보장하지만, 이건 **컨테이너에게 요청할 때** 이야기다. 싱글톤 빈이 생성자에서 프로토타입 빈을 주입받으면 그 참조는 싱글톤의 생애 동안 **딱 한 번만** 세팅되고, 그 뒤로는 영원히 같은 인스턴스를 공유한다. 매번 새 인스턴스가 필요하다면 `ObjectProvider<T>`, `Provider<T>`, 또는 `@Lookup` 메서드로 **컨테이너에 다시 물어보는 통로**를 열어야 한다.

```
[잘못된 패턴]                        [올바른 패턴]
@Service(싱글톤) ──주입──> Prototype   @Service(싱글톤) ──주입──> ObjectProvider<Prototype>
   ↓ 참조 고정 (1회)                     ↓ getObject() 호출 시마다
   항상 같은 인스턴스                     컨테이너가 새로 생성
```

> 💡 **왜 중요한가**: `UUID` 생성기, 요청별 상태 객체, 세션 토큰 빌더 같은 걸 프로토타입으로 선언해 놓고 "왜 값이 안 바뀌지?"로 몇 시간을 날리는 전형적인 함정이다 — 스코프는 **주입 시점이 아니라 조회 시점**에 결정된다는 걸 모르면 영원히 재현된다.

### 2. Spring의 `@Transactional`은 **기본적으로 Checked Exception에서 롤백하지 않는다** — 그래서 `IOException`을 던져도 커밋이 조용히 성공한다

Spring의 트랜잭션 롤백 기본 규칙은 EJB에서 물려받은 유산이다: `RuntimeException`과 `Error`만 롤백하고, `Exception`을 상속한 **Checked Exception은 그대로 커밋한다.** 즉 `throws IOException`을 던지는 메서드에서 외부 API 호출이 실패해도, 그 전에 저장한 주문 데이터는 멀쩡히 DB에 남는다. 명시적으로 `@Transactional(rollbackFor = Exception.class)`을 걸거나, 아예 Unchecked로 래핑하지 않으면 아무도 이 사실을 눈치채지 못한 채 데이터 정합성이 썩어간다.

```
메서드가 던지는 예외          기본 @Transactional 동작
├─ RuntimeException     →   롤백 ✅
├─ Error                →   롤백 ✅
├─ IOException          →   커밋 ❌ (조용히 성공)
├─ SQLException         →   커밋 ❌ (조용히 성공)
└─ 커스텀 BusinessException(extends Exception)  →   커밋 ❌
```

실제 사례: 주문 저장 → 결제 Gateway 호출(`throws PaymentException extends Exception`) → 결제사가 timeout. 로그에는 "결제 실패"가 찍히는데 **주문은 DB에 PAID로 남아있다.** CS에서 "결제 안 됐는데 주문됐어요"가 쏟아져야 비로소 발견된다.

> 💡 **왜 중요한가**: 팀 컨벤션으로 **"모든 `@Transactional`에 `rollbackFor = Exception.class`를 명시한다"** 또는 **"비즈니스 예외는 Unchecked로만 설계한다"** 중 하나를 반드시 정해야 한다 — 기본값에 맡기면 Checked/Unchecked 설계 결정이 **트랜잭션 경계와 뒤섞여** 유지보수 중에 반드시 사고가 난다.
