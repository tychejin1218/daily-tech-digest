### Database Tip 1: MySQL `Buffer Pool`의 `Midpoint Insertion Strategy` — 거대한 풀스캔 한 번이 "핫 데이터 전체"를 쓸어버리지 않도록 LRU를 반으로 가르는 숨은 방어막

InnoDB는 Buffer Pool의 LRU 리스트를 단순 LRU가 아니라 `young` 영역(5/8)과 `old` 영역(3/8)으로 분할하고, 새로 읽어온 페이지를 맨 앞이 아닌 "중간 지점(old의 머리)"에 삽입합니다. 이 페이지가 `innodb_old_blocks_time`(기본 1000ms) 이후에 다시 접근돼야만 비로소 young 영역으로 승격되기 때문에, 한 번의 거대한 `SELECT *` 풀스캔이 수억 개의 페이지를 읽어도 자주 쓰이는 핫 페이지들은 young 영역에서 보호받습니다.

```
[young 5/8 ← 핫 페이지] [old 3/8 ← 풀스캔 페이지]
         ↑ midpoint
    새 페이지는 여기로 삽입 → 1초 내 재접근 없으면 그대로 evict
```

실제로 야간 배치나 리포팅 쿼리가 돌 때 서비스 응답이 급격히 느려진다면 `innodb_old_blocks_pct`(기본 37)와 `innodb_old_blocks_time`을 조정하는 것이 첫 번째 처방입니다. 트레이드오프는 `old_blocks_time`을 너무 크게 잡으면 정상적인 OLTP 쿼리가 young으로 승격되지 못해 반복 I/O가 늘어난다는 점입니다.

> 💡 **왜 중요한가**: Buffer Pool Hit Ratio가 99%에서 70%로 떨어지며 "왜 갑자기 DB가 느려졌지?"라는 질문이 나오는 순간, 범인은 거의 항상 풀스캔이고 해법은 쿼리 튜닝 이전에 LRU의 분할 구조를 이해하는 것이다.

### Database Tip 2: JPA `Persistence Context`의 `flush()` 타이밍과 `FlushModeType.COMMIT` — 영속성 컨텍스트가 "DB에 쿼리를 날리는 시점"을 조작하는 숨은 스위치

JPA의 `flush()`는 쓰기 지연 SQL 저장소에 쌓인 INSERT/UPDATE/DELETE를 실제 DB로 내보내는 동작이며, 기본 모드 `FlushModeType.AUTO`는 커밋 직전은 물론이고 **JPQL 쿼리 실행 직전에도 자동으로 flush**가 일어납니다. 이 때문에 "엔티티를 저장한 뒤 JPQL로 조회했더니 이미 쿼리가 나가 있었다"는 현상이 발생하고, 대량 저장 로직에서 중간에 `Repository.findBy...()`가 섞이면 의도치 않게 플러시가 반복되며 성능이 급락합니다.

```java
// 배치 처리: flush를 커밋 시점에만 몰아서 수행
em.setFlushMode(FlushModeType.COMMIT);
for (int i = 0; i < 10_000; i++) {
    em.persist(new Order(...));
    if (i % 1000 == 0) {
        em.flush();   // 수동 flush
        em.clear();   // 1차 캐시 비우기 → OOM 방지
    }
}
```

`FlushModeType.COMMIT`으로 바꾸면 JPQL 실행 중에도 flush가 일어나지 않지만, 대신 "같은 트랜잭션 내에서 저장한 엔티티가 JPQL 결과에 보이지 않는" 일관성 문제가 생길 수 있습니다. 트레이드오프는 명확합니다 — 성능을 얻는 대신 "읽기-쓰기 순서"를 개발자가 직접 책임져야 한다는 것입니다.

> 💡 **왜 중요한가**: 배치 로직에서 "분명히 `saveAll`만 호출했는데 쿼리가 1만 번 나갔다"는 현상의 90%는 중간에 끼어든 JPQL 조회가 AUTO flush를 트리거한 것이고, 이걸 모르면 `@Transactional` 안에서 벌어지는 성능 저하를 영원히 재현 못 한다.
