### 1. `@Modifying(clearAutomatically = true, flushAutomatically = true)`로 JPA 벌크 연산 후 영속성 컨텍스트 동기화하기

Spring Data JPA에서 `@Modifying`이 붙은 벌크 UPDATE/DELETE 쿼리는 DB에는 직접 반영되지만 1차 캐시(영속성 컨텍스트)에는 반영되지 않아, 같은 트랜잭션 내에서 후속 조회 시 변경 이전의 stale 엔티티가 반환될 수 있습니다. `flushAutomatically = true`로 쿼리 실행 전 pending 변경을 DB에 먼저 반영하고, `clearAutomatically = true`로 실행 후 영속성 컨텍스트를 비워 이후 조회가 DB에서 fresh하게 다시 로드되도록 강제할 수 있습니다.

```java
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("update Member m set m.status = 'DORMANT' where m.lastLoginAt < :cutoff")
int markDormant(@Param("cutoff") LocalDateTime cutoff);
```

> 💡 **왜 중요한가**: 두 옵션을 빠뜨리면 "DB는 갱신됐는데 조회 결과는 옛 값"이라는 재현 어려운 데이터 불일치 버그가 트랜잭션 경계 안에서 발생합니다.

### 2. ShedLock으로 클러스터 환경에서 `@Scheduled` 중복 실행 방지하기

`@Scheduled` 메서드는 인스턴스마다 독립적으로 트리거되므로, 동일 애플리케이션을 여러 노드로 띄우면 동일 시각에 모든 노드가 작업을 동시에 실행해 중복 처리·자원 경합이 발생합니다. ShedLock은 DB(JDBC/Redis/MongoDB 등)를 공유 락 저장소로 사용해 한 시점에 단 한 노드만 작업을 수행하도록 보장하며, `@SchedulerLock`을 추가하기만 하면 됩니다.

```java
@Scheduled(cron = "0 0 3 * * *")
@SchedulerLock(name = "settlementJob", lockAtMostFor = "10m", lockAtLeastFor = "1m")
public void runSettlement() {
    // 야간 정산 배치 — 클러스터 내 한 노드만 실행됨
}
```

> 💡 **왜 중요한가**: 별도의 배치 전용 서버나 리더 선출 인프라 없이도, 무상태(stateless)로 수평 확장된 Spring Boot 인스턴스에서 스케줄 작업의 단일 실행 보장을 가장 가볍게 얻을 수 있습니다.
