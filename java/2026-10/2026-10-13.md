### 1. `Objects.checkIndex(index, length)` (Java 9 정식)로 `if (i < 0 || i >= size) throw new IndexOutOfBoundsException(...)` 수동 검사 관성 벗어나기

배열이나 리스트에 접근하기 전에 범위 체크를 손으로 쓰다 보면, 조건식을 거꾸로 쓰거나 메시지 포맷을 매번 다르게 만드는 실수가 생긴다. `Objects.checkIndex(i, size)`는 유효하면 `i`를 그대로 반환하고, 아니면 JDK가 규격화한 `IndexOutOfBoundsException`을 던져서 `arr[Objects.checkIndex(i, arr.length)]` 처럼 한 줄로 "검증 + 사용"을 묶을 수 있다. 범위 전체를 검사하는 `checkFromToIndex(from, to, size)`, `checkFromIndexSize(from, size, length)`도 세트로 있으니, 서브리스트/슬라이스 로직에서 off-by-one 걱정을 JDK에 위임하자.

```java
// Before: 조건 뒤집기 쉽고, 메시지도 매번 다름
public E get(int i) {
    if (i < 0 || i >= size) {
        throw new IndexOutOfBoundsException("index: " + i + ", size: " + size);
    }
    return data[i];
}

// After: 검증과 사용이 한 줄, 메시지 포맷은 JDK가 책임
public E get(int i) {
    return data[Objects.checkIndex(i, size)];
}

// 범위 검사도 세트로
public List<E> subList(int from, int to) {
    Objects.checkFromToIndex(from, to, size);
    return new SubList<>(this, from, to);
}
```

> 💡 **왜 중요한가**: 범위 검사 코드는 "뻔해서" 리뷰에서 그냥 넘어가는데, 그 뻔한 곳에서 off-by-one과 음수 인덱스 처리 누락이 가장 많이 터진다 — JDK 표준 검사로 넘기면 조건과 예외 메시지가 모든 호출부에서 동일해진다.

### 2. `HashMap.newHashMap(expectedSize)` (Java 19 정식)로 `new HashMap<>(expectedSize)` 쓰고 리사이즈 터지는 관성 벗어나기

`new HashMap<>(1000)`을 보고 "1000개까지 리사이즈 없이 들어가겠지"라고 생각하면 틀렸다. HashMap의 생성자 인자는 **초기 용량(capacity)**이지 **기대 엔트리 수**가 아니고, 기본 load factor 0.75를 넘어가면 리사이즈가 발생한다 — 즉 1000개 넣으려면 실제로는 capacity가 ~1334 이상이어야 한다. `HashMap.newHashMap(1000)`은 "1000개를 넣어도 리사이즈 안 터지는 맵"을 돌려주는 팩토리라서 이 산수를 JDK가 알아서 해 준다. `LinkedHashMap.newLinkedHashMap(n)`, `HashSet.newHashSet(n)`, `LinkedHashSet.newLinkedHashSet(n)`도 쌍으로 제공된다.

```java
// Before: 1000개 넣으면 중간에 리사이즈 발생 (0.75 * 1000 = 750에서 리사이즈)
Map<String, User> cache = new HashMap<>(1000);
users.forEach(u -> cache.put(u.id(), u));

// After: 1000개까지 리사이즈 보장 없음
Map<String, User> cache = HashMap.newHashMap(1000);
users.forEach(u -> cache.put(u.id(), u));

// 과거의 수동 계산 — 이제 할 필요 없음
Map<String, User> old = new HashMap<>((int) (1000 / 0.75f) + 1);
```

> 💡 **왜 중요한가**: "용량 미리 지정해서 성능 챙겼다"는 코드가 실제로는 load factor 때문에 리사이즈를 그대로 겪고 있는 경우가 많다 — 벌크 적재(캐시 워밍, 배치 조회 결과 수집) 경로에서 이 한 줄 교체만으로 리해시 비용과 임시 배열 할당이 사라진다.
