### 1. StrictMode가 useEffect를 "두 번" 실행하는 이유 — 버그가 아니라 "cleanup 누락"을 폭로하는 검사기다

개발 환경에서 `useEffect`가 마운트 시 두 번 실행되는 걸 보고 "StrictMode를 꺼야 하나" 고민한 적이 있다면, 그건 React의 의도된 동작이다. React 18의 StrictMode는 모든 effect를 `마운트 → 언마운트 → 재마운트` 순서로 강제 실행해서, cleanup 함수가 없거나 잘못된 effect(중복 구독, 타이머 누수, API 중복 호출)를 즉시 터지게 만든다. 예를 들어 `useEffect(() => { socket.connect() }, [])`처럼 cleanup 없이 작성하면 StrictMode에서 소켓이 두 개 연결된 채 남아 당장 문제가 드러나지만, cleanup을 `return () => socket.disconnect()`로 추가하면 두 번 실행돼도 정상적으로 동작한다. 운영 환경(production)에서는 한 번만 실행되므로 성능 걱정은 불필요하고, 오히려 Future Compatible하게 짜려면 StrictMode의 이중 실행을 "통과시키는" 코드를 쓰는 게 React Fiber의 재사용 가능한 상태(React Forget, offscreen rendering) 시대의 생존 조건이다.

> 💡 **왜 중요한가**: StrictMode를 끄는 건 "경고등을 테이프로 가리는 것"과 같다 — 진짜 문제는 cleanup 누락이지 두 번 실행이 아니다.

### 2. useDeferredValue: "같은 값을 두 번 렌더링하는데 더 빨라 보이는" 역설 — useTransition과의 결정적 차이

`useDeferredValue(value)`는 입력받은 값의 "지연된 복사본"을 돌려주는 훅으로, 비싼 리스트 필터링에서 사용자 입력창의 반응성을 지키는 데 쓰인다. `useTransition`이 "내가 일으킨 업데이트를 저우선순위로 만들겠다"는 선언적 API라면, `useDeferredValue`는 "남이 준 값(예: props로 받은 검색어)을 저우선순위로 다루겠다"는 수동적 API다 — 라이브러리 컴포넌트에서 setState를 감쌀 수 없을 때 유일한 탈출구다. 핵심 트릭은 React가 컴포넌트를 **두 번** 렌더링한다는 것: 먼저 이전 값으로 즉시 렌더링해서 입력창 반응성을 지키고, 그다음 백그라운드에서 새 값으로 렌더링을 시도하다가 중간에 더 긴급한 업데이트(새 타자 입력)가 들어오면 그걸 버리고 다시 시작한다. 그래서 `<SlowList query={deferredQuery} />`에 `React.memo`를 반드시 붙여야 효과가 있다 — 안 그러면 두 번 다 비싼 렌더링을 해서 오히려 느려진다.

> 💡 **왜 중요한가**: `useTransition`은 "내 setState를 미룰 때", `useDeferredValue`는 "남의 값을 미룰 때" — 역할을 혼동하면 최적화가 아니라 리렌더 2배로 끝난다.
