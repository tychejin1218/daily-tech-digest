### 1. Spring Boot의 `@PathVariable`과 `@RequestParam`은 **URL 디코딩 시점이 달라서 `+` 문자를 다르게 해석한다** — `@RequestParam`은 `application/x-www-form-urlencoded` 규칙을 따라 `+`를 공백으로 바꾸지만, `@PathVariable`은 RFC 3986을 따라 `+`를 그대로 문자 `+`로 둔다

같은 요청 `/search/a+b?q=a+b`를 처리할 때 `@PathVariable String path`에는 `"a+b"`가 들어오지만 `@RequestParam String q`에는 `"a b"`가 들어온다. 그래서 "경로로 받든 쿼리로 받든 똑같겠지"라고 믿고 짠 검색 키 로직이, 사용자가 특수문자를 포함한 순간 경로/쿼리 따라 다른 결과를 돌려주는 유령 버그를 만든다.

```
요청: GET /search/hello+world?q=hello+world

┌─────────────────────────────────────┐
│  @PathVariable String path          │
│  → "hello+world"  (+ 그대로)         │
├─────────────────────────────────────┤
│  @RequestParam String q             │
│  → "hello world"  (+ → 공백)         │
└─────────────────────────────────────┘
      ↓ 같은 값으로 DB 조회하면 miss
```

| 구분 | `+` 처리 | 표준 근거 |
|------|---------|----------|
| `@PathVariable` | 문자 `+` 유지 | RFC 3986 (URI) |
| `@RequestParam` | 공백으로 치환 | HTML form 규칙 |

> 💡 **왜 중요한가**: 사용자 입력을 URL 어느 위치로 받느냐에 따라 Spring이 "조용히" 다른 디코딩 규칙을 적용하므로, 공백/특수문자가 섞인 검색·태그·이메일 ID에서 재현 불가 버그를 만든다.

### 2. Spring Boot의 `WebClient`는 **응답 Body를 끝까지 소비(consume)하지 않으면 커넥션이 풀로 반환되지 않는다** — `bodyToMono()` 없이 `exchangeToMono()`에서 상태 코드만 보고 끝내면, 커넥션이 half-open 상태로 묶여 있다가 결국 "PoolAcquireTimeoutException"으로 서비스가 멈춘다

`WebClient`의 기반인 Reactor Netty는 HTTP keep-alive 커넥션 풀을 쓰는데, 응답 바디를 drain(소비)해야만 해당 커넥션이 "다음 요청에 재사용 가능" 상태로 돌아간다. 그래서 상태코드만 확인하고 바디를 버리는 코드는, 부하 테스트에서는 괜찮다가 운영에서 몇 시간 뒤 풀이 고갈되는 전형적인 "서서히 죽는" 장애를 만든다.

```java
// ❌ 커넥션 누수 — 바디를 소비하지 않음
webClient.get().uri("/ping")
    .exchangeToMono(res -> Mono.just(res.statusCode()));

// ✅ 바디를 비워서라도 소비
webClient.get().uri("/ping")
    .exchangeToMono(res -> res.releaseBody()
        .thenReturn(res.statusCode()));

// ✅ 혹은 bodyToMono로 자연스럽게 소비
webClient.get().uri("/ping")
    .retrieve()
    .toBodilessEntity()
    .map(ResponseEntity::getStatusCode);
```

```
[요청 1] ──► 커넥션 A 획득 ──► 200 받음 ──► 바디 미소비
                                            │
                                            ▼
                               커넥션 A: "사용 중" 상태 유지
[요청 2~N] ──► 풀에서 새 커넥션 계속 꺼냄 ──► 풀 고갈
                                            │
                                            ▼
                     PoolAcquireTimeoutException (기본 45초 후)
```

> 💡 **왜 중요한가**: "성공 여부만 알면 되니까 바디는 안 읽어도 되겠지"라는 상식이 Reactor Netty에서는 커넥션 누수로 직결되며, 운영 몇 시간 뒤 알 수 없는 타임아웃으로 터져 원인 추적이 매우 어렵다.
