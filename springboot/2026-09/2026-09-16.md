### `@Value`로 주입한 필드는 **생성자에서 사용할 수 없다** — 필드 주입 시점이 생성자 실행 이후이기 때문

`@Value("${my.config}")`를 필드에 붙이고 생성자에서 그 값을 참조하면 `null`이 나온다. Spring은 객체를 먼저 `new`로 생성한 뒤 리플렉션으로 필드에 값을 주입하기 때문에, 생성자 실행 시점에는 아직 값이 세팅되지 않은 상태다. 초기화 로직에서 설정값이 필요하다면 **생성자 파라미터로 `@Value`를 받거나** `@PostConstruct`에서 처리해야 한다.

```java
// ❌ 동작 안 함 — 생성자에서 apiUrl은 null
@Component
public class ApiClient {
    @Value("${api.url}")
    private String apiUrl;

    public ApiClient() {
        this.client = WebClient.create(apiUrl); // NPE!
    }
}

// ✅ 생성자 주입 — 값이 보장된다
@Component
public class ApiClient {
    private final WebClient client;

    public ApiClient(@Value("${api.url}") String apiUrl) {
        this.client = WebClient.create(apiUrl);
    }
}
```

> 💡 **왜 중요한가**: "설정값을 못 읽는다"는 버그의 90%는 이 시점 문제다 — 필드 주입은 편해 보이지만 초기화 순서를 숨긴다.

### `Jackson`은 기본적으로 **`getter`를 기준으로 직렬화**한다 — 필드가 아니라 메서드가 JSON 키를 결정한다

`private String userName;` 필드가 있고 `getUserName()` getter가 있으면 JSON 키는 `userName`이 된다. 하지만 getter 이름을 `getUsername()`으로 바꾸면 필드는 그대로여도 JSON 키는 `username`으로 변한다. 필드명을 리팩터링해도 getter를 안 건드리면 API 응답이 그대로지만, 반대로 getter만 실수로 바꾸면 **필드는 그대로인데 API 스펙이 조용히 깨진다**.

```java
public class User {
    private String userName;  // 필드명

    // getter가 JSON 키를 결정
    public String getUserName() { return userName; }
    // → {"userName": "..."}

    public String getUsername() { return userName; } // 오타!
    // → {"username": "..."} — API 스펙 깨짐
}

// 명시적으로 잠그려면
@JsonProperty("userName")
public String getUserName() { return userName; }
```

> 💡 **왜 중요한가**: IDE의 "getter 자동 생성"이 만드는 이름과 프론트가 기대하는 키가 다르면 리팩터링 한 방에 프로덕션이 터진다 — `@JsonProperty`로 계약을 명시하라.
