### MySQL `Window Function` + `ROW_NUMBER()` — GROUP BY로는 못 푸는 "그룹별 N번째 행"을 서브쿼리 없이 한 방에

MySQL 8.0부터 지원되는 윈도우 함수는 집계 함수와 달리 "행을 뭉개지 않고" 그룹별 순위/누적/이동평균을 계산한다. 특히 `ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC)` 패턴은 "각 사용자의 최신 주문 3건" 같은 Top-N per Group 문제를 상관 서브쿼리나 자기조인 없이 단일 쿼리로 해결하는 정석이다. `PARTITION BY` 컬럼에 인덱스가 있으면 정렬 비용도 거의 공짜가 된다.

```sql
-- 각 유저의 최신 주문 3건만 뽑기
SELECT * FROM (
  SELECT o.*,
         ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn
  FROM orders o
) t WHERE rn <= 3;
```

> 💡 **왜 중요한가**: "그룹별 최신 N건" 요구사항을 상관 서브쿼리로 풀면 N+1에 가까운 지옥을 만나지만, 윈도우 함수는 테이블을 한 번만 훑고 끝낸다. 레거시 코드에서 자기조인·서브쿼리 중첩을 발견하면 90%는 윈도우 함수로 리팩토링 가능하다.

### JPA `OSIV`(Open Session In View) — 트랜잭션 밖에서 Lazy 로딩이 "되는 것처럼 보이는" 거대한 함정

Spring Boot는 기본적으로 `spring.jpa.open-in-view=true`로 설정되어, HTTP 요청이 끝날 때까지 영속성 컨텍스트와 DB 커넥션을 열어둔다. 덕분에 Controller/View에서 Lazy 로딩이 "그냥 되지만", 대신 **커넥션이 요청 전체 시간 동안 점유**되어 트래픽이 몰리면 커넥션 풀이 즉시 고갈된다. 외부 API 호출이 섞인 요청이라면 더 치명적이다.

```yaml
# application.yml
spring:
  jpa:
    open-in-view: false  # 명시적으로 끄고, 서비스 레이어에서 필요한 데이터를 모두 조회
```

> 💡 **왜 중요한가**: 로컬에선 멀쩡하다가 운영에서 `HikariPool-1 - Connection is not available` 에러로 터지는 전형적 원인. OSIV를 끄는 순간 "LazyInitializationException 지뢰밭"이 드러나지만, 그게 바로 설계가 커넥션을 어디서 낭비하고 있었는지 보여주는 진짜 설계도다.
