### PostgreSQL `pg_stat_statements` — 쿼리별 실행 통계를 정규화해 진짜 병목 찾기

`pg_stat_statements` 익스텐션은 실행된 SQL을 파라미터가 제거된 정규화 형태로 그룹핑해서, 각 쿼리 유형별로 총 호출 횟수, 누적 실행 시간, 평균 실행 시간, 읽은 블록 수, I/O 시간까지 누적 집계해줍니다. `slow query log`가 "느린 한 방"을 잡는다면 이 뷰는 "느리지 않지만 하루 100만 번 호출되어 CPU를 갉아먹는" 쿼리를 드러냅니다.

```sql
-- postgresql.conf: shared_preload_libraries = 'pg_stat_statements'
CREATE EXTENSION pg_stat_statements;

-- 총 실행 시간 상위 10개 쿼리 (진짜 시스템 부하 주범)
SELECT
    substring(query, 1, 80) AS query,
    calls,
    round(total_exec_time::numeric, 2) AS total_ms,
    round(mean_exec_time::numeric, 2) AS mean_ms,
    round((100 * total_exec_time / sum(total_exec_time) OVER ())::numeric, 2) AS pct
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

**어떻게 쓰나 — 실무 감각**
- **평균이 아닌 총합을 봐라**: `mean_exec_time` 상위만 보면 실수한다. 10ms짜리 쿼리가 초당 1000번 호출되면 1ms짜리 쿼리 100번보다 100배 더 심각한 부하다. `total_exec_time` 기준 정렬이 실제 CPU 점유를 반영한다.
- **`shared_blks_hit` vs `shared_blks_read` 비율**: `read`가 높으면 캐시 미스가 잦다는 뜻 — 인덱스가 없거나, 워킹셋이 `shared_buffers`를 벗어났다는 신호.
- **주기적 `pg_stat_statements_reset()`**: 누적 통계라 배포 후·부하 테스트 전에 리셋해야 "직전 시점 이후"의 스냅샷을 볼 수 있다.
- **N+1 발견기**: 같은 정규화 쿼리의 `calls`가 비정상적으로 높으면 애플리케이션에서 반복 호출되고 있다는 뜻. APM 없이도 N+1을 잡을 수 있다.

**⚠️ 주의**: 오버헤드는 보통 1~3% 정도지만, `track = all`로 함수 내부 쿼리까지 추적하면 더 커진다. 프로덕션에서는 `track = top` 권장.

> 💡 **왜 중요한가**: "가장 느린 쿼리"가 아니라 "시스템에 가장 큰 짐이 되는 쿼리"를 정량적으로 지목해주는, DBA의 첫 번째 진단 도구다.

### JPA `@Version` 낙관적 락 — 동시 수정 충돌을 `SELECT FOR UPDATE` 없이 감지하기

`@Version` 필드를 붙이면 Hibernate가 UPDATE 시 `WHERE id = ? AND version = ?` 조건을 자동으로 붙이고, 성공하면 version을 +1 합니다. 다른 트랜잭션이 먼저 커밋했다면 영향받은 행이 0개가 되고 `OptimisticLockException`이 던져집니다 — 락 없이 "먼저 쓴 사람이 이긴다"를 구현하는 방식입니다.

```java
@Entity
public class Order {
    @Id private Long id;
    private OrderStatus status;
    private BigDecimal amount;

    @Version
    private Long version;  // Long, Integer, Timestamp 모두 가능
}

// 동시에 두 트랜잭션이 같은 order를 읽어 수정하려 하면:
// TX1: UPDATE orders SET status=?, version=2 WHERE id=1 AND version=1  → 성공 (1 row)
// TX2: UPDATE orders SET status=?, version=2 WHERE id=1 AND version=1  → 실패 (0 rows)
//      → Hibernate가 OptimisticLockException 발생
```

**비관적 락(`SELECT ... FOR UPDATE`)과의 결정적 차이**
| | 낙관적 락 (`@Version`) | 비관적 락 (`FOR UPDATE`) |
|---|---|---|
| 락 획득 시점 | 없음 (UPDATE 시점에 체크) | SELECT 시점부터 |
| 충돌이 드문 경우 | ✅ 최고 성능 | 락 오버헤드 낭비 |
| 충돌이 잦은 경우 | 재시도 폭주 → 라이브락 위험 | ✅ 직렬화로 안정 |
| 읽기-생각-쓰기 간격 | ✅ 트랜잭션 짧게 유지 | 사용자 입력 대기 중에도 락 유지 → 위험 |
| DB 커넥션 점유 | 짧음 | 김 |

**실무 함정**
- **재시도 전략 필수**: `OptimisticLockException` 발생 시 그냥 500을 던지면 UX가 망가진다. Spring Retry의 `@Retryable(OptimisticLockException.class, maxAttempts = 3)` + `@Backoff`로 지수 백오프를 걸어야 한다.
- **`@DynamicUpdate`와 궁합**: 변경 컬럼만 UPDATE해도 `WHERE version = ?`은 항상 포함된다 — 두 최적화가 서로를 방해하지 않는다.
- **재고 차감 같은 카운터형 로직에는 부적합**: 충돌률이 높아 재시도가 폭발한다. 이 경우엔 `UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty >= 1` 같은 조건부 UPDATE + 영향받은 행 수 체크가 낫다.
- **Detached 엔티티의 함정**: 세션 밖에서 오래 들고 있던 엔티티를 merge하면 version이 오래된 값이라 항상 충돌한다 — 화면 편집 후 저장 UX엔 특히 조심.

> 💡 **왜 중요한가**: 충돌이 드문 대부분의 CRUD에서 락 오버헤드 없이 데이터 정합성을 지키는 표준 패턴이며, 언제 낙관/비관을 골라야 하는지 판단하는 능력이 시니어의 갈림길이다.
