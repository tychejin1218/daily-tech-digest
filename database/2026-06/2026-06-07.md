### PostgreSQL `BRIN` 인덱스 — 시계열·로그 테이블에서 B-tree의 1/1000 크기로 범위 스캔하기

`BRIN`(Block Range Index)은 페이지 범위마다 최솟값·최댓값만 저장하는 인덱스로, 삽입 순서가 값 순서와 일치하는 시계열/로그 데이터에서 B-tree 대비 인덱스 크기가 수백~수천 배 작다. `created_at` 같은 컬럼에 `CREATE INDEX ON logs USING BRIN (created_at) WITH (pages_per_range = 128)`로 만들면 범위 조회 시 관련 없는 블록을 통째로 건너뛰어 I/O가 극적으로 줄지만, 데이터가 물리적으로 정렬돼 있어야 효과가 나온다.

```sql
CREATE INDEX idx_logs_created_at_brin ON logs
  USING BRIN (created_at) WITH (pages_per_range = 128);

-- 정렬이 흐트러졌을 때 요약 갱신
SELECT brin_summarize_new_values('idx_logs_created_at_brin'::regclass);
```

> 💡 **왜 중요한가**: 수십억 행 로그 테이블에서 인덱스가 차지하던 수백 GB를 수백 MB로 줄이면서도 시간 범위 쿼리 성능은 거의 그대로 유지된다.

### MySQL `ORDER BY ... LIMIT`의 `filesort` 함정 — 인덱스 컬럼 순서와 정렬 방향까지 맞추기

`WHERE status = 'ACTIVE' ORDER BY created_at DESC LIMIT 20` 같은 쿼리는 `(status, created_at)` 인덱스가 있어도 정렬 방향이 어긋나면 `Using filesort`가 붙어 결과 전부를 읽어 정렬한다. MySQL 8.0부터 지원하는 내림차순 인덱스(`INDEX idx (status ASC, created_at DESC)`)나 조건 컬럼 → 정렬 컬럼 순서 정렬 규칙을 지켜야 인덱스만으로 상위 N개를 뽑아낼 수 있다.

```sql
-- Bad: filesort 발생
CREATE INDEX idx_bad ON posts (created_at, status);

-- Good: WHERE 컬럼 먼저, ORDER BY 컬럼 방향까지 일치
CREATE INDEX idx_good ON posts (status, created_at DESC);

EXPLAIN SELECT id FROM posts
 WHERE status = 'ACTIVE' ORDER BY created_at DESC LIMIT 20;
-- Extra: Using index (filesort 없음)
```

> 💡 **왜 중요한가**: `LIMIT 20`처럼 보이는 쿼리가 실제로는 수백만 행을 정렬하고 있을 수 있어, 정렬 방향까지 맞춘 인덱스 하나로 응답 시간이 초 단위에서 밀리초로 떨어진다.
