### 1. `@Async`와 `AsyncTaskExecutor` 분리로 작업 종류별 스레드 풀 격리하기

Spring Boot의 `@Async`는 기본적으로 단일 `TaskExecutor`를 공유하기 때문에, 무거운 작업과 가벼운 알림이 같은 풀에서 경쟁하면 한쪽이 풀을 점유해 전체가 정체될 수 있습니다. `@Async("mailExecutor")`처럼 빈 이름을 명시하고 `ThreadPoolTaskExecutor`를 용도별(메일, 외부 API 호출, 배치 등)로 별도 등록하면 풀별 큐 크기·코어 스레드 수·거부 정책을 독립적으로 튜닝할 수 있습니다. Spring Boot 3.2+의 가상 스레드(`spring.threads.virtual.enabled=true`)와 조합하면 I/O 바운드 풀은 가상 스레드로, CPU 바운드 풀은 플랫폼 스레드로 나누는 패턴이 깔끔합니다.

> 💡 **왜 중요한가**: 단일 풀 공유는 한 작업의 지연이 무관한 다른 작업까지 마비시키는 "스레드 풀 오염"의 가장 흔한 원인입니다.

### 2. `HandlerMethodArgumentResolver`로 인증 컨텍스트를 컨트롤러 파라미터로 직접 주입하기

`SecurityContextHolder.getContext().getAuthentication()`을 매 컨트롤러마다 호출하는 대신, `@CurrentUser` 같은 커스텀 어노테이션과 `HandlerMethodArgumentResolver`를 구현하면 `public ResponseEntity<...> get(@CurrentUser Member me)`처럼 메서드 시그니처에 인증 정보를 직접 표현할 수 있습니다. 이렇게 하면 컨트롤러 코드에서 정적 호출이 사라져 단위 테스트 시 mock 주입이 쉬워지고, 인증 객체 → 도메인 객체(예: `Member`) 변환 로직도 리졸버 한 곳에 모입니다. `WebMvcConfigurer.addArgumentResolvers()`에 등록만 하면 즉시 동작합니다.

> 💡 **왜 중요한가**: 인증 추출 로직을 컨트롤러에서 추방하면 시그니처가 의도를 그대로 드러내고, 보안 관련 변경의 영향 범위를 한 클래스로 좁힐 수 있습니다.
