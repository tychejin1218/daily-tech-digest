### Bulkhead 패턴 — "한 배의 침몰이 함대 전체를 삼키지 않도록" 자원을 격벽으로 나누기

Bulkhead(격벽)는 원래 배 내부를 여러 개의 수밀 구획으로 나눠 한 구획이 침수돼도 배 전체가 가라앉지 않도록 하는 조선 공학 용어다. Michael Nygard가 『Release It!』에서 이 은유를 소프트웨어로 가져오면서 널리 알려졌다. 핵심 명제는 단순하다: **"공유된 자원 풀은 반드시 전염된다."** 하나의 느린 다운스트림 호출이 스레드 풀·커넥션 풀·메모리를 다 잡아먹으면, 그와 무관한 다른 기능들까지 함께 죽는다. Circuit Breaker가 "실패한 것을 부르지 않는" 시간적 격리라면, Bulkhead는 **"실패해도 다른 것에 옮기지 않는" 공간적(자원) 격리**다.

---

#### 왜 필요한가: 톰캣 스레드 풀 200개의 비극

전형적인 시나리오를 보자. 하나의 API 게이트웨이 서비스가 세 개의 다운스트림(주문, 결제, 추천)을 호출한다. 톰캣 워커 스레드는 200개, 모두 공유한다.

```
[상황] 추천 서비스가 느려짐 (평소 50ms → 30초)

시각 T=0s:  추천 호출 10개 동시 발생 → 스레드 10개 점유 (대기)
시각 T=5s:  추천 호출 계속 유입 → 스레드 100개 점유
시각 T=10s: 스레드 200개 전부 추천 대기로 점유됨
시각 T=11s: 주문/결제 요청 들어옴 → "스레드 없음" → 전체 서비스 다운

           ┌─────────────────────────────────┐
           │   Shared Thread Pool (200)      │
           │  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ (추천)  │  ← 다 잠식됨
           │  ░ ░ ░ ░ (주문/결제 못 들어옴)   │
           └─────────────────────────────────┘
```

**추천 서비스는 부가 기능이었지만, 결과는 전사 장애다.** 이것이 "Cascading Failure"이고, Bulkhead는 이 전염 경로를 물리적으로 끊는다.

#### 두 가지 구현 방식: Semaphore vs Thread Pool

Resilience4j 기준으로 Bulkhead는 두 종류다.

```
┌─────────────────────────────────────────────────────────────┐
│ 1) SemaphoreBulkhead (경량, 동기 호출)                       │
│                                                              │
│   [Caller Thread] ──permit acquire──> [Downstream]          │
│                    max=25                                    │
│   → 호출자 스레드에서 실행. 카운터로만 격리.                 │
│   → 오버헤드 낮음. WebFlux/Coroutine과 궁합 좋음.            │
│                                                              │
├─────────────────────────────────────────────────────────────┤
│ 2) ThreadPoolBulkhead (강한 격리, 비동기)                    │
│                                                              │
│   [Caller Thread] ──submit──> [Dedicated Pool: 10 threads]  │
│                                        │                     │
│                                        └──> [Downstream]     │
│   → 별도 스레드 풀로 실행 컨텍스트 자체를 분리.              │
│   → Caller 스레드는 즉시 해방됨. 진정한 격리.                │
│   → 대신 스레드 컨텍스트 스위칭 + 스레드 컨텍스트 손실 이슈. │
└─────────────────────────────────────────────────────────────┘
```

Resilience4j 설정 예시:

```yaml
resilience4j.bulkhead:
  instances:
    recommendationService:
      maxConcurrentCalls: 25       # 동시 25개까지만
      maxWaitDuration: 100ms       # 자리 없으면 100ms만 대기 후 fail-fast

resilience4j.thread-pool-bulkhead:
  instances:
    paymentService:
      maxThreadPoolSize: 10
      coreThreadPoolSize: 5
      queueCapacity: 20            # 넘치면 BulkheadFullException
      keepAliveDuration: 20ms
```

```java
@Bulkhead(name = "recommendationService", type = Bulkhead.Type.SEMAPHORE,
          fallbackMethod = "recommendFallback")
public List<Item> recommend(Long userId) { ... }

public List<Item> recommendFallback(Long userId, BulkheadFullException e) {
    return Collections.emptyList();  // 격벽 초과 → 빈 결과. 전체는 계속 동작.
}
```

#### Circuit Breaker와의 결정적 차이

둘 다 방어 패턴이라 자주 혼동되지만 작동 층위가 다르다.

| 관점 | Circuit Breaker | Bulkhead |
|---|---|---|
| 격리 대상 | **시간** (실패율/느림 감지 후 차단) | **자원** (스레드/커넥션 풀 분리) |
| 트리거 | 에러율·응답시간 초과 | 동시 호출 수 초과 |
| 실패 시나리오 | "이 서비스가 죽었다" | "이 서비스가 자원을 다 먹고 있다" |
| 실무 결합 | **거의 항상 함께 씀** — Bulkhead로 격리하고, 그 안에서 CB로 시간 차단 |

즉 Bulkhead가 없으면 CB가 열리기 전(감지 지연 몇 초) 사이에 스레드가 이미 다 잠식된다. **Bulkhead는 CB보다 먼저 방어선을 친다.**

#### 트레이드오프

**얻는 것**
- 장애 전염 차단. 부가 기능 하나가 코어를 죽이지 않음.
- 예측 가능한 자원 사용량. "결제는 최대 스레드 10개"라는 SLO 계산이 가능해짐.
- Fail-fast. 100ms 대기 후 바로 실패 → 사용자는 30초 기다리지 않음.

**잃는 것**
- **처리량 제한**: 격벽 크기가 곧 상한선. 트래픽 스파이크에 유연하지 못함.
- **튜닝 지옥**: 다운스트림별로 적정 격벽 크기를 알아내야 함. Little's Law(`N = λ × W`)로 계산하지만, 실측 없이는 어렵다.
- **ThreadPoolBulkhead의 컨텍스트 손실**: `ThreadLocal`(SecurityContext, MDC, Sleuth의 Trace ID)이 넘어가지 않아 별도 전파 설정 필요.
- 자원 낭비 우려: 서비스 100개 있으면 격벽 100개, 유휴 스레드가 늘어남.

#### 실제 사례

**Netflix Hystrix (원조)** — 2011년 Netflix가 AWS 장애 이후 전면 도입한 게 Hystrix고, 그 핵심이 바로 커맨드별 격리된 스레드 풀이었다. 각 다운스트림 호출을 자체 스레드 풀로 감싸서 "추천 서비스 장애가 상품 상세 페이지를 죽이지 않도록" 만들었다. Hystrix는 지금은 maintenance mode고, 사실상 후계자가 Resilience4j다.

**AWS Lambda의 Reserved Concurrency** — 함수별로 동시 실행 개수 상한을 걸 수 있는 기능이 바로 Bulkhead의 관리형 구현체다. 한 함수가 계정 전체 동시성(기본 1000)을 다 먹지 않도록 격리한다.

**Kubernetes의 ResourceQuota / LimitRange** — 네임스페이스 단위로 CPU·메모리 상한을 걸어 한 팀의 서비스가 클러스터를 잠식하지 못하게 하는 것도 개념적으로 동일하다. **격벽은 스레드 층에서 끝나지 않고, 프로세스·컨테이너·네트워크 층 어디에서든 반복되는 원리**다.

**카카오 2022 장애 사후 분석** — 데이터센터 단일 장애가 전체로 번진 근본 원인 중 하나로 "서비스 간 자원 격리 부족"이 지적됐다. 물리 격벽(멀티 DC)도 결국 같은 원리다.

#### 시니어 관점: 언제 쓰고 언제 쓰면 안 되는가

**써야 하는 경우**
- 다운스트림이 3개 이상이고, 그중 하나라도 **SLA가 다르거나 신뢰도가 다른** 서비스가 섞여 있을 때. 특히 "코어 기능 + 부가 기능"이 한 프로세스에 공존할 때는 필수.
- 외부 API(결제 PG, SMS, 광고 네트워크)를 호출할 때. 외부는 통제 불가하므로 격벽으로 담을 방어벽을 쳐야 한다.
- 배치 작업과 실시간 API가 같은 커넥션 풀을 쓰는 경우 — 배치용/API용 DataSource를 물리적으로 분리하는 것도 Bulkhead다.

**쓰면 안 되는 경우 (혹은 과설계)**
- 다운스트림이 1~2개뿐인 작은 서비스. 오버헤드가 이득을 초과한다.
- **동기 서블릿 스택에서 ThreadPoolBulkhead를 무분별하게** — ThreadLocal 전파, 스레드 폭발, 튜닝 비용이 너무 크다. 이 경우 SemaphoreBulkhead로 충분한 경우가 대부분.
- 이미 **비동기/논블로킹(WebFlux, Coroutine)** 스택인데 ThreadPoolBulkhead를 얹는 것 — 논블로킹의 장점(적은 스레드로 많은 요청)을 스스로 무력화한다. 이 경우엔 SemaphoreBulkhead + Reactor의 `flatMap(concurrency=N)`이 자연스럽다.
- 격벽 크기를 **감(感)으로 설정**하고 방치하는 것. 관찰 없이 넣은 격벽은 "장애 시 fallback만 뜨는" 새로운 병목이 된다. Bulkhead 도입은 반드시 **P99 응답시간·동시 호출 수 메트릭 계측**과 세트로 가야 한다.

가장 흔한 실수는 "Bulkhead 넣었으니 안전하다"고 착각하는 것이다. Bulkhead는 **전염을 막을 뿐, 근본 원인을 고치지 않는다.** 격벽 초과 알람이 뜨면 그건 "다운스트림에 무슨 일이 벌어지고 있다"는 신호이지, "격벽 크기를 늘리자"는 신호가 아니다.

> 💡 **왜 중요한가**: MSA에서 장애는 반드시 발생하며, 그 장애를 "느린 하나의 서비스"에서 끝낼지 "전사 다운"으로 키울지는 자원 격리를 설계했느냐가 결정한다.
