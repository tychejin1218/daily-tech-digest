### MySQL `InnoDB Buffer Pool`과 `innodb_buffer_pool_size` — 디스크 IO를 "증발"시키는 메모리 캐시의 본체

InnoDB는 테이블/인덱스 데이터를 디스크에서 바로 읽는 게 아니라, 먼저 메모리 영역인 `Buffer Pool`에 페이지 단위(기본 16KB)로 올려두고 거기서 읽는다. `innodb_buffer_pool_size`를 서버 메모리의 **50~75%**로 설정하면 핫 데이터가 전부 메모리에 상주해 디스크 IO가 사실상 사라지고, 반대로 1~2GB로 방치하면 스캔할 때마다 디스크를 때려 쿼리가 10배 느려진다. 작동 중인 서버에서는 `SHOW ENGINE INNODB STATUS`의 `Buffer pool hit rate`가 **1000/1000**에 가까워야 정상이다.

> 💡 **왜 중요한가**: 인덱스를 아무리 잘 걸어도 Buffer Pool이 작으면 "메모리에서 찾기" 대신 "디스크에서 찾기"가 되어 모든 최적화가 무력화된다.

### JPA `@DynamicUpdate` — 변경된 컬럼만 UPDATE 쿼리에 포함시키는 "선택적 업데이트"

JPA/Hibernate는 기본적으로 엔티티의 **모든 컬럼**을 UPDATE 문에 포함시킨다 (`UPDATE user SET name=?, email=?, age=?, ... WHERE id=?`). 컬럼이 50개인 테이블이라면 1개만 바꿔도 50개가 전송되고, 더 치명적인 건 **변경되지 않은 컬럼까지 인덱스 갱신 대상**이 되어 불필요한 락 경합과 이진로그(binlog) 비대화를 일으킨다. `@DynamicUpdate`를 붙이면 Hibernate가 변경된 필드만 추려 `UPDATE user SET name=? WHERE id=?`로 보내지만, 매 UPDATE마다 SQL을 동적으로 생성하므로 **PreparedStatement 캐시 효율이 떨어진다** — 그래서 "넓은 테이블 + 부분 수정"이 잦은 엔티티에만 선별 적용하는 게 정석이다.

> 💡 **왜 중요한가**: 컬럼 수가 많은 레거시 테이블에서 `@DynamicUpdate` 하나만 붙여도 binlog 크기와 복제 지연이 극적으로 줄고, 멀티 컬럼 인덱스의 불필요한 재구성을 막을 수 있다.
