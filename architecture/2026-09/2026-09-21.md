### Query Understanding & Rewriting — "사용자가 물어본 그대로 검색하면 되지"라는 순진함, 그리고 챗봇이 3개월간 재현율 42%에 머물러 CS팀이 "이거 그냥 검색이 안 되는 거 아니냐"며 프로젝트 킬 회의를 소집한 새벽

---

#### 사건 재구성

2026년 3월, 국내 대형 이커머스 A사의 CS 챗봇.

- 3개월 전 오픈, RAG 파이프라인은 "정석대로" 구축: OpenAI `text-embedding-3-large` + pgvector + Hybrid Search(RRF) + Cohere Reranker.
- 문서 45,000건 (약관/FAQ/상품 정책/배송 규정).
- 초기 벤치마크(오프라인 골든셋 200개) 재현율 84%. 팀장은 "이 정도면 프로덕션 감"이라며 배포 승인.
- 3개월 뒤 실제 로그 기반 재현율 **42%**. CSAT 2.1/5.0. CS 인바운드 감소 목표 30%였는데 실제 감소 6%.

원인 분석 3주 끝에 나온 결론:
> "임베딩·인덱스·리랭커는 다 잘 동작한다. **사용자가 던지는 문장이 검색용이 아니다.**"

로그 샘플:
```
사용자: "저번에 산 그거 반품하고 싶은데 어떻게 함?"
사용자: "이거 왜 안 와요 ㅠㅠ"
사용자: "카드 바꿨는데"
사용자: "배송비 왜케 비싼거임"
```

이걸 그대로 벡터화해서 던지면 top-k에 **"반품 정책 v3.2"** 문서가 안 뽑힌다. 왜? 문서에는 `"본 반품 정책은 구매 후 7일 이내..."`라고 적혀 있고, 임베딩 공간에서 `"그거 반품하고 싶은데"`와 `"본 반품 정책은..."`의 코사인 유사도가 0.31에 불과했다.

**RAG의 재현율은 인덱스·리랭커가 아니라 쿼리에서 결정된다.** 이 사실을 3개월 뒤에 알았다.

---

#### 문제의 본질: 두 종류의 언어 불일치

RAG 시스템은 근본적으로 **두 개의 서로 다른 언어 분포**를 연결해야 한다:

| | 사용자 쿼리 | 문서(코퍼스) |
|---|---|---|
| 길이 | 5~15 토큰 | 200~2000 토큰 |
| 어조 | 구어체·축약·오탈자 | 문어체·정제된 서술 |
| 표현 | "그거", "어떻게 함?" | "해당 사항", "다음과 같은 절차로" |
| 맥락 | 대화 히스토리 의존 | 자기완결적 |
| 의도 | 암묵적 | 명시적 |

임베딩 모델이 아무리 좋아도 이 gap을 완전히 메우진 못한다. 특히:
- **한국어**는 조사·어미 변형 때문에 gap이 더 크다.
- **도메인 전문 문서**(법률·의료·금융)는 코퍼스가 극단적으로 formal해서 gap이 벌어진다.
- **멀티턴 대화**에서 "그거", "저번 거"처럼 대명사가 나오면 임베딩은 완전히 길을 잃는다.

Query Understanding & Rewriting은 이 gap을 **LLM으로 사전에 메우는 상류 처리**다. Reranker가 하류에서 정밀도(precision)를 올리는 계층이라면, Query Rewriting은 상류에서 **재현율(recall)을 올리는 계층**이다.

#### 파이프라인에서의 위치

```mermaid
flowchart LR
    U[사용자 쿼리<br/>"그거 반품 어떻게 함?"] --> QU[Query Understanding Layer]

    subgraph QU[Query Understanding Layer]
        direction TB
        CTX[대화 히스토리<br/>Coreference 해소] --> INT[Intent 분류]
        INT --> RW{Rewriting 전략}
        RW -->|단순| EXP[Query Expansion]
        RW -->|추상| SB[Step-back]
        RW -->|복합| DEC[Decomposition]
        RW -->|gap 큼| HYDE[HyDE]
        RW -->|재현율| MQ[Multi-Query]
    end

    QU --> Q1[쿼리 1]
    QU --> Q2[쿼리 2]
    QU --> Q3[쿼리 N]

    Q1 & Q2 & Q3 --> HS[Hybrid Search<br/>Vector + BM25]
    HS --> RRF[RRF Fusion]
    RRF --> RR[Reranker]
    RR --> LLM[Answer LLM]
```

핵심은 **"검색 전에 LLM 한 번 더 태운다"**. 이 추가 지연·비용을 어떻게 정당화할 것인가가 시니어의 판단 지점이다.

#### 5가지 대표 기법 (시니어가 반드시 구분해야 할 것)

##### 1. Query Expansion — 동의어·용어 확장

가장 원시적이지만 가장 확실하다. 도메인 사전 + LLM으로 사용자 어휘를 코퍼스 어휘로 매핑.

```
입력: "카드 바꿨는데"
확장: ["카드 바꿨는데", "결제수단 변경", "정기결제 카드 교체", "빌링 카드 업데이트"]
```

- **적용처**: 도메인 용어가 강한 시스템(금융·의료·B2B SaaS)
- **비용**: LLM 호출 1회 + 인덱스 검색 N배
- **함정**: 확장 어휘가 너무 많으면 오히려 노이즈 유입. **top 3~5개 확장이 최적점.**

##### 2. HyDE — Hypothetical Document Embeddings (2022, Gao et al.)

> "질문을 임베딩하지 말고, **가상의 정답 문서를 LLM으로 생성한 뒤 그걸 임베딩해라.**"

```
입력: "반품 어떻게 함?"
     ↓ LLM: "이 질문에 답하는 문서를 한 문단으로 써봐라"
가상 문서: "본 스토어의 반품 정책은 다음과 같습니다.
          구매 후 7일 이내에 마이페이지에서 반품 신청이 가능하며,
          단순 변심의 경우 배송비는 고객 부담입니다..."
     ↓ 이걸 임베딩
검색: 실제 "반품 정책 v3.2" 문서와 코사인 유사도 0.87 ✓
```

- **핵심**: 쿼리-문서 gap을 **문서-문서 유사도로 변환**. 임베딩 공간에서 훨씬 잘 동작.
- **적용처**: 코퍼스가 매우 formal한 도메인(법률·연구논문·기술 표준)
- **주의**: LLM이 hallucinate한 가상 문서가 **실제로 존재하지 않는 개념**을 만들면 엉뚱한 문서를 뽑는다. **temperature 0.0 + system prompt로 "실제 존재할 법한 사실 위주로"** 강제 필요.

##### 3. Multi-Query — 여러 각도로 재구성 (LangChain MultiQueryRetriever)

```
입력: "배송 왜 늦어?"
     ↓ LLM: "이 질문을 3가지 다른 관점으로 재구성해라"
Q1: "배송 지연의 일반적 원인은 무엇인가?"
Q2: "배송 조회 방법과 지연 시 대응 절차"
Q3: "택배사별 평균 배송 소요일과 지연 보상 정책"
     ↓ 각각 검색 → RRF fusion
```

- **적용처**: 재현율이 정밀도보다 훨씬 중요할 때 (탐색적 검색·리서치)
- **비용**: LLM 1회 + 검색 N배 + fusion 로직
- **함정**: N을 3 이상으로 늘려도 재현율은 로그 스케일로 증가. **N=3이 실무 sweet spot.**

##### 4. Step-back Prompting — 추상화 후퇴 (Google DeepMind, 2023)

> "구체 질문을 먼저 상위 개념으로 후퇴시킨 뒤, 상위 문서를 먼저 찾아라."

```
입력: "iPhone 15 Pro Max 512GB 티타늄 블랙 반품하려면?"
     ↓ Step-back
상위 질문: "이 스토어의 반품 정책 일반 원칙은?"
     ↓ 검색
컨텍스트: [반품 정책 v3.2 전문] + [원래 구체 질문]
     ↓ LLM 답변
```

- **핵심**: 구체 쿼리는 **너무 좁아서** 정책 문서를 못 뽑는다. 한 단계 후퇴시켜야 정책 문서가 잡힌다.
- **적용처**: 도메인이 "일반 원칙 + 구체 케이스" 구조인 곳(법률·규정·정책)
- **주의**: step-back을 너무 세게 하면 답이 지나치게 일반적으로 나옴.

##### 5. Query Decomposition — 복합 질문 분해

```
입력: "이번 달에 A상품 3개 반품하면 배송비 얼마고 언제 환불됨?"
     ↓ LLM 분해
Q1: "A상품 반품 시 배송비 정책"
Q2: "반품 배송비 계산 방식 (수량별)"
Q3: "환불 소요일 및 처리 절차"
     ↓ 각각 검색·답변 → 조합
```

- **적용처**: Agent 시스템·복잡한 tool 조합 필요한 도메인
- **함정**: 분해된 sub-query 간 **의존성**이 있으면 순차 실행 필요 → latency 3배.

#### 트레이드오프 — 얻는 것 vs 잃는 것

| 항목 | Query Rewriting 도입 전 | 도입 후 |
|---|---|---|
| 재현율 | 42% | 78% (실측, A사 사례) |
| P99 latency | 800ms | 1,800~2,400ms |
| 검색당 비용 | $0.0002 | $0.0015~0.003 |
| 코드 복잡도 | 파이프라인 3단계 | 5~7단계 |
| 디버깅 난이도 | "왜 이 문서가 안 나오지" | "왜 이렇게 rewrite됐지 → 왜 이 문서가 안 나오지" (계층 하나 늘어남) |
| Fallback 필요성 | 낮음 | **높음** (LLM 실패 시 원 쿼리로) |

**핵심 트레이드오프**: latency 2~3배, 비용 5~10배, 복잡도 증가를 **재현율 +30~40%p로 정당화할 수 있는가.**

시니어가 반드시 물어야 할 질문:
1. **오프라인 골든셋이 아니라 실제 프로덕션 로그로 재현율을 측정했는가?** (A사가 3개월 태운 원인)
2. Semantic Cache로 rewrite 결과를 캐싱할 수 있는가? (같은 질문 패턴은 매우 반복적)
3. 사용자 쿼리 분포를 봤을 때, **rewrite가 필요한 쿼리가 몇 %인가**? (30% 미만이면 selective rewriting)

#### 실제 사례

##### 사례 1: Perplexity (2024) — Multi-step Query Rewriting

Perplexity는 검색 서비스라 재현율이 곧 상품성이다. 공개된 아키텍처 조각:
- 1단계: 대화 히스토리로 coreference 해소 ("이건 어떻게 생각해?" → "GPT-5의 추론 능력은 어떻게 생각해?")
- 2단계: intent 분류 (factual / opinion / how-to / navigational)
- 3단계: intent별 **다른 rewriting 전략** 적용
- 4단계: Multi-query fan-out (검색 소스별 다른 쿼리)

핵심 인사이트: **모든 쿼리에 같은 rewriting을 적용하지 않는다.** Intent 분류로 selective하게.

##### 사례 2: Notion Q&A (2024) — HyDE 실전 적용

Notion의 workspace 검색은 사용자 문서 스타일이 극단적으로 다양하다(회의록·기술문서·이메일 사본·투두). Notion 엔지니어링 블로그(2024):
> "임베딩만으로는 사용자 자연어 쿼리와 문서 gap을 못 좁혔다. HyDE로 가상 문서 생성 후 검색하니 재현율이 유의미하게 개선."

주의점: HyDE 생성용 LLM은 **저가 모델**(Haiku·GPT-4o-mini) 사용. 이 단계에서 Opus 쓰면 비용이 폭발.

##### 사례 3: 국내 B 은행 콜센터 도우미 (2025)

상담원이 규정을 검색하는 내부 도구. 상담원 쿼리는 극단적으로 축약형("담보대출 중도상환 수수료 면제 조건 65세 이상 확인"). 규정 문서는 극단적으로 formal("본 조항은 다음 각 호에 해당하는 경우...").

적용한 조합:
- **Step-back**: "담보대출 중도상환 수수료 정책 개요" → 대분류 문서 확보
- **Query Expansion**: 은행 용어 사전 기반 확장 ("면제" → "감면·유예·전액공제")
- **Original query**: 원 쿼리도 함께 검색
- **RRF fusion**: 3개 결과 융합

결과: 상담원 평균 응답 시간 6분 → 2분 30초. **HyDE는 안 씀** — 규정 도메인은 gap이 크지 않고, hallucination 리스크가 컴플라이언스 문제로 직결되어 도입 부결.

##### 사례 4: Anthropic Contextual Retrieval (2024) — 상류 vs 하류

주의: Contextual Retrieval은 **문서 색인 시점에 컨텍스트를 붙이는 것**(하류 처리 개선)이고, Query Rewriting은 **쿼리 시점에 처리하는 것**(상류 처리)이다. **두 기법은 상호 배타가 아니라 곱셈 효과.** Anthropic 벤치마크에서 두 개를 조합했을 때 재현율이 각각 단독 적용보다 유의미하게 더 올랐다.

#### 언제 쓰고 언제 쓰면 안 되는가

##### 반드시 써야 하는 경우
- **B2C 자연어 챗봇** (사용자 쿼리 어조와 코퍼스 어조 gap이 큼)
- **멀티턴 대화** ("그거", "저번 거" 같은 대명사 다수)
- **도메인 전문 코퍼스** (법률·의료·금융 등 formal 문서)
- **재현율이 상품성의 핵심**인 서비스 (검색·리서치·헬프데스크)
- 실측 재현율이 **70% 미만**으로 정체된 RAG 시스템

##### 신중해야 하는 경우
- **latency SLA가 500ms 이하**인 실시간 서비스 (rewriting LLM 호출로 예산 초과)
- **도메인이 좁고 쿼리 패턴이 반복적**인 경우 → Semantic Cache가 더 나은 투자
- **사용자가 이미 정형화된 쿼리를 던지는 B2B 툴** (개발자 대상 API 검색 등)

##### 쓰면 안 되는 경우
- **컴플라이언스가 극단적으로 엄격한 도메인** — HyDE의 가상 문서가 감사 트레일에 남으면 "이 시스템이 가짜 문서를 만들었다"는 오독 소지. 이 경우 Expansion·Step-back까지만.
- **로그·모니터링·감사가 아직 안 붙은 상태** — rewriting은 디버깅 난이도를 한 단계 올린다. 관측이 없으면 사고 원인 추적 불가.
- **Intent가 다양하지 않은 단일 목적 시스템** (예: 상품 검색만) — Query Understanding의 ROI가 낮음. 임베딩 fine-tuning이 더 나은 투자.

#### 함정 (시니어가 반드시 경계할 것)

##### 함정 1. "LangChain MultiQueryRetriever 붙였으니 끝"
LangChain 기본 prompt는 영어 기반이라 한국어 쿼리에 대해 rewriting 품질이 낮다. **도메인·언어별 prompt 튜닝은 필수 작업이지 옵션이 아니다.**

##### 함정 2. Rewriting LLM에 Opus·GPT-4 쓰기
Rewriting은 **저가·저지연 모델**로 충분하다. Haiku·GPT-4o-mini·Gemini Flash. Opus 쓰면 latency 800ms + 비용 10배. Rewriting을 정확도 문제로 착각해서 상위 모델 붙이는 팀이 많다.

##### 함정 3. Rewriting 결과를 로그로 안 남김
"챗봇이 왜 저 답을 했지?" → answer LLM 추적만 하고 rewriting 단계는 로깅 누락 → 사고 원인 파악 3일 소요. **모든 rewriting 결과는 trace_id와 함께 필수 로깅.** LangSmith/LangFuse가 여기서 진가 발휘.

##### 함정 4. Cache 없이 매번 rewriting
"저번에 산 거 반품 어떻게 함?" 같은 쿼리는 하루 수천 건. Semantic Cache로 rewriting 결과 캐싱 안 하면 **비용의 60%가 rewriting에 들어간다.** Rewriting 캐시는 원 쿼리 임베딩 기준 similarity threshold 0.95 이상으로 세팅.

##### 함정 5. Fallback 없이 rewriting을 강제
Rewriting LLM이 실패(timeout·rate limit·garbage output)했을 때 파이프라인 전체가 멈추면 안 된다. **반드시 "원 쿼리로 fallback" 로직 필수.** 재현율은 낮아지겠지만 시스템은 살아있어야 한다.

##### 함정 6. Rewriting 후 원 쿼리를 버림
Rewriting된 쿼리만으로 검색하면 **원 쿼리에만 있던 고유 표현**(제품명·에러코드·고유명사)을 놓친다. 반드시 **원 쿼리 + rewriting 쿼리를 함께** 검색하고 RRF fusion.

##### 함정 7. Intent 분류 없이 모든 쿼리에 동일 rewriting
"안녕하세요" 같은 인사말에도 HyDE 돌리면 latency·비용만 낭비. **Intent 분류(또는 규칙 기반 filter)로 rewriting이 필요한 쿼리만 선별.** 실무에서 rewriting 필요 쿼리는 전체의 40~60% 수준.

---

#### 조합의 시너지 (그리고 위험)

| 조합 | 시너지 | 위험 |
|---|---|---|
| Query Rewriting + Hybrid Search | 재현율 크게 상승 (한국어 BM25가 놓친 걸 vector가 잡음) | 검색 fan-out 6~9배 |
| Query Rewriting + Reranker | rewriting으로 후보 확장 → reranker로 정밀도 회복 | latency 2~3배 |
| Query Rewriting + Contextual Retrieval | 상류·하류 모두 gap 해결 → 재현율 최대치 | 색인 비용 + 쿼리 비용 이중 부담 |
| Query Rewriting + Semantic Cache | 반복 쿼리 rewriting 스킵 → 비용 절감 | cache hit 시 stale rewriting 리스크 |

**시니어의 판단**: 이 조합을 한 번에 다 붙이는 게 아니라 **단계적으로 도입**하고 각 단계에서 재현율·latency·비용을 측정. "이론상 좋다"가 아니라 "우리 코퍼스·쿼리 분포에서 좋다"를 실측으로 증명.

---

> 💡 **왜 중요한가**: RAG의 재현율은 임베딩 모델 스펙이 아니라 **쿼리와 문서 사이의 언어 gap을 얼마나 좁혔는가**로 결정된다. 리랭커·인덱스 튜닝에 3개월을 태우기 전에, LLM 한 번 더 태워서 쿼리를 다시 쓰는 게 대개 더 빠르고 확실한 승부수다.
