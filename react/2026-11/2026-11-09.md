### 1. useReducer vs useState: 상태 전이가 "여러 개 얽혀 있을 때" 갈아타는 신호

`useState`를 쓰다 보면 `setLoading(true); setError(null); setData(res)`처럼 **한 사건에 여러 setState가 묶여서 호출되는 순간**이 온다. 이건 상태가 개별 변수가 아니라 "하나의 상태 기계(state machine)"로 다뤄져야 한다는 신호이고, 이때 `useReducer`로 전환하면 `dispatch({type: 'FETCH_SUCCESS', payload})` 한 번으로 전이가 원자적으로 끝난다. 특히 테스트하기 좋은 이유는 reducer가 순수 함수라 **컴포넌트 없이 입력(state, action) → 출력(state)** 만 단위테스트로 검증할 수 있다는 점이다.

```jsx
// useState: 상태 전이가 분산됨 → 중간 상태 버그 발생 가능
const [loading, setLoading] = useState(false);
const [error, setError] = useState(null);
const [data, setData] = useState(null);

const fetchData = async () => {
  setLoading(true);
  setError(null); // 혹시 빼먹으면? → 이전 에러가 남아있음
  try {
    const res = await api.get('/users');
    setData(res); // loading은 누가 false로? → 또 빼먹을 수 있음
  } catch (e) {
    setError(e);
  } finally {
    setLoading(false);
  }
};

// useReducer: 전이가 명시적 → 불가능한 상태 조합을 차단
const initialState = { status: 'idle', data: null, error: null };

function reducer(state, action) {
  switch (action.type) {
    case 'FETCH_START':   return { status: 'loading', data: null, error: null };
    case 'FETCH_SUCCESS': return { status: 'success', data: action.payload, error: null };
    case 'FETCH_ERROR':   return { status: 'error', data: null, error: action.error };
    default: throw new Error(`Unknown action: ${action.type}`);
  }
}

const [state, dispatch] = useReducer(reducer, initialState);
// "loading이면서 error도 있는" 불가능한 조합 자체를 만들 수 없음
```

**전환 기준 체크리스트**:
- 한 이벤트 핸들러에서 setState가 3개 이상 연달아 호출되는가?
- `loading && error` 같은 **논리적으로 불가능한 상태 조합**이 발생할 여지가 있는가?
- 다음 상태가 이전 상태에 의존하는 분기가 2개 이상인가?

하나라도 YES면 useReducer로 갈아탈 타이밍이다.

> 💡 **왜 중요한가**: `useState`를 여러 번 호출하는 코드는 "상태 전이의 원자성"을 잃고, 중간 단계(`loading=true`인데 `data`도 남아있는) 때문에 UI가 깜빡이거나 잘못 렌더링되는 버그의 온상이 된다.

### 2. React 18 Suspense + use(): "로딩 상태를 if 문으로 분기하는" 시대의 끝

전통적인 React에서는 `if (loading) return <Spinner/>; if (error) return <Error/>;` 같은 **삼단 분기**가 모든 데이터 컴포넌트에 반복됐다. React 18의 `<Suspense>`와 19에 정식화된 `use()` 훅은 이 패턴을 뒤집어서, **컴포넌트는 "데이터가 있다"는 전제로만 작성**하고 로딩 UI는 상위 `<Suspense fallback>`이, 에러는 `<ErrorBoundary>`가 가로채도록 책임을 분리한다. 핵심은 Promise를 그대로 던지면 React가 가장 가까운 Suspense 경계에서 잡아서 fallback을 보여준다는 것이다.

```jsx
// Before: 모든 컴포넌트가 로딩/에러 분기를 직접 처리
function UserProfile({ userId }) {
  const [user, setUser] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    fetchUser(userId)
      .then(setUser)
      .catch(setError)
      .finally(() => setLoading(false));
  }, [userId]);

  if (loading) return <Spinner />;
  if (error) return <Error error={error} />;
  return <div>{user.name}</div>; // 진짜 하고 싶은 일은 이 한 줄
}

// After: 데이터는 "있는 것"으로 간주, 분기는 경계로 위임
function UserProfile({ userId }) {
  const user = use(fetchUser(userId)); // Promise가 resolve될 때까지 "일시정지"
  return <div>{user.name}</div>;
}

function Page() {
  return (
    <ErrorBoundary fallback={<Error />}>
      <Suspense fallback={<Spinner />}>
        <UserProfile userId={1} />
      </Suspense>
    </ErrorBoundary>
  );
}
```

**주의할 트레이드오프**:
- `use()`에 넘기는 Promise는 **컴포넌트 외부에서 캐시**되어야 한다 (매 렌더마다 새 Promise를 만들면 무한 로딩). React Query, SWR, Next.js의 캐시 레이어와 함께 쓰는 게 일반적이다.
- 폭포수(waterfall) 문제: Suspense 경계를 잘못 배치하면 자식이 하나씩 순차 로딩되어 **병렬 fetch의 이점이 사라진다**. 부모에서 `Promise.all`로 미리 시작하거나 Next.js의 parallel routes로 해결한다.
- 서버 컴포넌트와 짝을 이룰 때 진가가 나온다. 클라이언트에서만 쓰면 기존 React Query보다 투박할 수 있다.

> 💡 **왜 중요한가**: 로딩/에러 분기가 비즈니스 로직 컴포넌트 안에 뒤섞이면 **"진짜 하고 싶은 일"의 가독성이 무너진다**. Suspense는 관심사 분리를 컴파일 타임이 아닌 **렌더 트리의 경계**로 끌어올려, 데이터 컴포넌트를 "성공 케이스만 서술하는" 선언적 코드로 되돌린다.
