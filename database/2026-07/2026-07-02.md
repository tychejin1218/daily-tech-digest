### 1. PostgreSQL `SELECT ... FOR UPDATE SKIP LOCKED` — 별도 큐 시스템 없이 안전한 작업 큐 만들기

여러 워커가 같은 테이블에서 작업을 꺼낼 때 `FOR UPDATE`만 쓰면 워커들이 서로의 락을 기다리며 직렬화된다. `SKIP LOCKED`를 붙이면 이미 잠긴 행은 건너뛰고 사용 가능한 다음 행만 즉시 잠그기 때문에, Redis나 RabbitMQ 없이도 PostgreSQL 한 대로 병렬 소비가 가능한 작업 큐를 만들 수 있다.

```sql
SELECT id, payload
FROM jobs
WHERE status = 'pending'
ORDER BY created_at
LIMIT 10
FOR UPDATE SKIP LOCKED;
```

> 💡 **왜 중요한가**: 트래픽이 작거나 중간인 서비스에서 "큐 인프라 도입" 대신 기존 DB로 충분한 처리량을 뽑아낼 수 있어 운영 복잡도가 크게 줄어든다.

### 2. JPA `hibernate.query.in_clause_parameter_padding` — 동적 `IN` 절이 유발하는 쿼리 플랜 캐시 오염 막기

`WHERE id IN (?, ?, ?)`는 파라미터 개수가 바뀔 때마다 새로운 SQL 문자열로 취급되어 JDBC 드라이버·DB의 prepared statement 캐시를 매번 갈아엎는다. `hibernate.query.in_clause_parameter_padding=true`를 켜면 파라미터 개수를 2의 거듭제곱(2, 4, 8, 16, …)으로 반올림해 채워, 동일한 SQL 형태를 재사용하도록 만든다.

```properties
spring.jpa.properties.hibernate.query.in_clause_parameter_padding=true
```

> 💡 **왜 중요한가**: 캐시가 지속적으로 히트하기 시작하면서 Oracle의 hard parse나 PostgreSQL의 plan 재작성 오버헤드가 사라져, IN 절이 많은 조회 API의 P99 지연이 눈에 띄게 줄어든다.
