### 1. Spring Boot의 `@Transactional`은 **`private` 메서드에 붙이면 아무 일도 일어나지 않는다** — 컴파일 에러도 없고, 경고도 없이 조용히 무시된다

Spring AOP는 프록시 기반이라 `public` 메서드만 가로챌 수 있다. `private`, `protected`(기본), `package-private` 메서드에 `@Transactional`을 붙이면 프록시가 개입하지 못하고, 트랜잭션 없이 그대로 실행된다. 더 치명적인 건 같은 클래스 내부에서 `public` 메서드가 다른 `public` 메서드를 `this.`로 호출하는 경우도 프록시를 우회하므로 트랜잭션이 걸리지 않는다는 점이다.

```java
@Service
public class OrderService {
    @Transactional
    public void placeOrder(Order order) {
        save(order);           // ❌ 프록시 우회 → 트랜잭션 없음
        this.updateStock();    // ❌ 동일 - self-invocation
    }

    @Transactional
    private void save(Order order) { ... }  // ❌ private → AOP 불가
}
```

> 💡 **왜 중요한가**: "`@Transactional`을 붙였으니 안전하다"는 가정이 운영에서 데이터 정합성 사고로 이어진다. AspectJ 로드타임 위빙을 쓰지 않는 한, 프록시 경계(= 외부에서 `public` 호출)를 반드시 지켜야 한다.

### 2. Spring Boot의 `@RestController`에서 `ResponseEntity<Void>` 대신 `void`를 반환하면 **200 OK가 나간다, 심지어 `@ResponseStatus`를 안 붙여도** — 그리고 이게 REST 설계를 조용히 망친다

컨트롤러 메서드가 `void`를 반환하면 Spring MVC는 기본적으로 **200 OK + 빈 본문**을 응답한다. DELETE든 POST든 PUT이든 상관없다. REST 관례상 DELETE는 `204 No Content`, 생성은 `201 Created` + `Location` 헤더가 맞지만, `void`로 두는 순간 이 모든 의미가 사라진다. 더 미묘한 건, `ResponseEntity<Void>`를 반환하면 상태 코드를 명시적으로 제어할 수 있지만 `void`는 `@ResponseStatus`로만 바꿀 수 있다는 점이다.

```java
@DeleteMapping("/orders/{id}")
public void delete(@PathVariable Long id) {  // ❌ 200 OK 나감
    orderService.delete(id);
}

@DeleteMapping("/orders/{id}")
@ResponseStatus(HttpStatus.NO_CONTENT)       // ✅ 204
public void delete(@PathVariable Long id) { ... }

@PostMapping("/orders")                       // ✅ 가장 명시적
public ResponseEntity<Void> create(@RequestBody OrderRequest req) {
    Long id = orderService.create(req);
    return ResponseEntity.created(URI.create("/orders/" + id)).build();
}
```

> 💡 **왜 중요한가**: HTTP 상태 코드는 클라이언트(브라우저 캐시, CDN, API Gateway, 재시도 로직)가 의존하는 계약이다. `204`를 기대한 클라이언트가 `200 OK + 빈 본문`을 받으면 JSON 파싱 에러로 터지거나, 캐시 전략이 어긋난다.
