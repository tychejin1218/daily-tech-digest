### PostgreSQL `pg_hint_plan` — 옵티마이저가 잘못 고른 실행 계획을 힌트로 강제하기

통계가 튀거나 파라미터 스니핑으로 옵티마이저가 엉뚱한 조인 순서·인덱스를 고를 때, `pg_hint_plan` 확장을 쓰면 SQL 주석 형태로 실행 계획을 명시적으로 강제할 수 있다. Oracle의 `/*+ ... */` 힌트와 동일한 문법이라 특정 쿼리만 핀포인트로 교정하고 나머지는 옵티마이저에 맡길 수 있다.

```sql
CREATE EXTENSION pg_hint_plan;

/*+ IndexScan(orders orders_customer_created_idx)
    Leading((orders customers))
    HashJoin(orders customers) */
SELECT o.*, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.created_at >= now() - interval '1 day';

-- hint_plan.hints 테이블에 등록하면 애플리케이션 코드 수정 없이도 힌트 적용 가능
INSERT INTO hint_plan.hints (norm_query_string, application_name, hints)
VALUES ('SELECT o.* FROM orders o WHERE o.status = ?', '', 'IndexScan(o orders_status_idx)');
```

> 💡 **왜 중요한가**: 통계 재수집·인덱스 재설계 없이 문제 쿼리 한 개만 즉시 교정할 수 있어, 새벽에 옵티마이저가 계획을 뒤집었을 때의 소방수 역할을 한다.

### JPA `Persistable` 인터페이스 — `@Id`를 직접 할당한 엔티티가 `save()`에서 불필요한 `SELECT`를 하지 않게 하기

Spring Data JPA의 `save()`는 새 엔티티인지 판별하기 위해 기본적으로 `@Id`가 null인지 확인하는데, UUID·자연키처럼 애플리케이션이 ID를 직접 할당하는 경우 항상 "이미 존재하는 엔티티"로 오판해 매번 `SELECT` 후 `INSERT`를 실행한다. `Persistable<ID>`를 구현해 `isNew()`를 명시하면 이 판정 로직을 우리가 통제할 수 있어 불필요한 왕복 조회를 없앨 수 있다.

```java
@Entity
public class Event implements Persistable<UUID> {
    @Id
    private UUID id;

    @CreatedDate
    private Instant createdAt;

    @Override
    public UUID getId() { return id; }

    @Override
    public boolean isNew() {
        return createdAt == null; // 아직 영속화 전이면 새 엔티티
    }
}
```

> 💡 **왜 중요한가**: 자연키·UUID 기반 도메인에서 `saveAll()` 벌크 시 발생하던 N번의 `SELECT`를 통째로 제거해 대량 적재 성능을 수 배로 끌어올린다.
