### RAG의 Chunking 전략 — "그냥 1000자로 자르면 되지"라는 순진함, 그리고 계약서 챗봇이 "위약금은 계약금의 10%입니다"의 뒤 문장 "단, 고의·중과실 시 300%"를 잘라먹어 30억 소송의 피고 답변서로 인용된 새벽

---

시니어가 3년차에 처음 RAG를 만들면 대개 이 코드를 짠다.

```python
def chunk(text: str, size: int = 1000, overlap: int = 200) -> list[str]:
    chunks = []
    for i in range(0, len(text), size - overlap):
        chunks.append(text[i:i + size])
    return chunks
```

LangChain 튜토리얼에도 이렇게 나온다. `RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)`. 이걸 프로덕션에 그대로 밀어넣고, 3개월 뒤에 회사가 소송을 당한다.

이 글은 **"청크를 어떻게 자를 것인가"**라는, 언뜻 사소해 보이는 문제가 실제로는 RAG 시스템의 정확도·비용·법적 리스크를 모두 결정하는 이유를 다룬다. Vector DB 선택([[vector-db-architecture]])이나 임베딩 모델 마이그레이션([[embedding-migration]])이 화려한 주제라면, 청킹은 지루하지만 실패했을 때 가장 빨리 회사를 무너뜨리는 주제다.

## 1. 왜 "1000자 고정"이 지옥으로 가는 특급열차인가

### 1.1 의미 단위(Semantic Unit)가 문자 수와 무관하다

법률 문서, 의료 기록, 재무 공시, 기술 매뉴얼 — 시니어가 실제로 다루는 도메인 문서는 **한 문장이 한 문단보다 길고, 한 조항이 한 페이지에 걸친다**. 그런데 문자 수로 자르면 이런 일이 벌어진다.

```
원문 (계약서 제12조):
"甲은 乙에게 위약금으로 계약금의 10%를 지급한다.  ← 999자 지점에서 끊김
 단, 甲의 고의 또는 중과실로 인한 경우 위약금은 계약금의 300%로 한다."
                                                 ↑ 다음 청크로 분리됨
```

**챗봇에 "위약금이 얼마인가요?"라고 물으면**:
- Chunk 1이 top-1으로 리턴 → "10%입니다"
- Chunk 2(예외조항)는 유사도 밀려서 top-5 밖으로 → 컨텍스트에 안 들어감
- LLM은 "위약금은 계약금의 10%입니다"라고 확신에 차서 답변

이게 진짜 문제인 이유: **틀린 답이 아니라, 반쪽짜리 답**이다. 완전히 틀리면 사용자가 의심하고 재확인한다. 하지만 "10%"는 팩트로 존재하기 때문에, 사용자는 이걸 근거로 계약서에 사인하고, 3개월 뒤 상대방이 "고의·중과실입니다"를 주장하며 30억을 청구한다.

### 1.2 Overlap 200자가 "안전장치"라는 착각

`chunk_overlap=200`으로 겹치게 자르면 안전하다고 배운다. 하지만 위 예시에서 "단, 甲의 고의 또는 중과실..." 문장이 잘리는 지점이 overlap 구간 밖이라면 무의미하다. **Overlap은 문자 단위의 우연에 의존하는 안전장치**다. 우연을 프로덕션 아키텍처에 넣지 마라.

### 1.3 한국어 문서의 이중 지옥

영어 튜토리얼의 청킹 파라미터를 한국어에 그대로 적용하면 상황이 더 나쁘다.

| 항목 | 영어 | 한국어 |
|---|---|---|
| 1 token ≈ | 4 chars | 1.5~2 chars |
| 1000자 청크 | ~250 tokens | ~600 tokens |
| tiktoken/CLIP 계열 임베딩 최대 | 8191 tokens | 8191 tokens |
| **동일한 임베딩 quality가 나오는 자연 청크 크기** | 500–800 tokens | **200–350 tokens** |

즉, 영어에서 검증된 `chunk_size=1000`은 한국어에서는 **너무 큰** 청크가 되어 임베딩이 "여러 주제가 뒤섞인 벡터"를 만든다. 결과: 유사도 검색이 중구난방으로 튄다.

## 2. 청킹 전략 4계층 — 시니어의 결정 트리

```
                    ┌──────────────────────────┐
                    │  청크 전략 선택 (도메인) │
                    └────────────┬─────────────┘
                                 │
        ┌────────────────────────┼─────────────────────────┐
        │                        │                          │
        ▼                        ▼                          ▼
  구조 있는 문서            반정형 문서              자유 서술 문서
  (계약서, 매뉴얼)         (블로그, 위키)            (콜센터 녹취)
        │                        │                          │
        ▼                        ▼                          ▼
  ① Structural            ② Semantic                ③ Sliding Window
     Chunking                Chunking                  + Sentence-BERT
     (조항 단위)             (문단+임베딩 유사도)      (문장 경계 필수)
        │                        │                          │
        └────────────────────────┼─────────────────────────┘
                                 ▼
                    ④ Parent-Child 계층화
                    (검색용 small chunk +
                     컨텍스트용 large parent)
```

### ① Structural Chunking — "문서의 뼈대를 따라 잘라라"

법률·재무·의료 문서는 **이미 인간이 의미 단위로 설계한 구조**를 가진다. 제O조, 별표, 각주, 목차. 이걸 무시하고 문자로 자르는 건 건축가가 이미 그려둔 방 구조를 무시하고 "벽지를 균등하게" 잘라 붙이는 짓이다.

```python
# 예: 계약서 청킹
def structural_chunk_contract(doc: str) -> list[Chunk]:
    articles = re.split(r'제\s*(\d+)\s*조', doc)  # 조항 단위로 분리
    chunks = []
    for article_num, article_body in pairs(articles):
        # 조항 하나가 너무 길면 → "단서 조항" 단위로 재분리
        if len(article_body) > 2000:
            sub_chunks = re.split(r'(?<=[.。])\s*(?=단,|다만,|그러나)', article_body)
            for sub in sub_chunks:
                chunks.append(Chunk(
                    text=sub,
                    metadata={"article": article_num, "type": "clause"}
                ))
        else:
            chunks.append(Chunk(text=article_body, metadata={"article": article_num}))
    return chunks
```

**핵심**: 위 코드의 `단,`, `다만,`, `그러나`는 한국 법률 문서에서 **예외 조항을 시작하는 접속사**다. 이걸 청크 경계로 삼으면 "10% / 단 300%" 파편화 문제가 원천 차단된다.

### ② Semantic Chunking — "임베딩 유사도가 급락하는 지점을 경계로"

블로그·위키처럼 구조는 없지만 주제가 바뀌는 지점이 있는 문서에 쓴다.

```
문단 1 → embed → v1
문단 2 → embed → v2   cosine(v1,v2) = 0.87  (같은 주제, 계속)
문단 3 → embed → v3   cosine(v2,v3) = 0.83  (같은 주제)
문단 4 → embed → v4   cosine(v3,v4) = 0.41  ← 급락, 여기가 청크 경계
문단 5 → embed → v5   cosine(v4,v5) = 0.79
```

Percentile threshold(예: 하위 5%)로 경계를 자동 감지한다. LlamaIndex의 `SemanticSplitterNodeParser`가 이 방식이다.

**함정**: 임베딩 API 비용이 청킹 단계에서 이미 발생한다. 100만 문서 × 평균 20문단 = 2000만 API 호출. `text-embedding-3-small` 기준 $2000. 청킹만으로 $2000 쓴다는 걸 CFO에게 설명하려면 근거가 필요하다.

### ③ Sliding Window with Sentence Boundary — "문장은 절대 안 자른다"

콜센터 녹취, 이메일 대화 같은 자유 서술 텍스트에 쓴다. **문자로 자르되, 문장 경계에서 스냅**한다.

```python
def sliding_window_sentence_aware(text: str, target_size: int = 500) -> list[str]:
    sentences = kss.split_sentences(text)  # 한국어 문장 분리기
    chunks, current, current_size = [], [], 0
    for sent in sentences:
        if current_size + len(sent) > target_size and current:
            chunks.append(" ".join(current))
            current = current[-2:]  # 마지막 2문장을 다음 청크에 이월(overlap)
            current_size = sum(len(s) for s in current)
        current.append(sent)
        current_size += len(sent)
    if current:
        chunks.append(" ".join(current))
    return chunks
```

핵심은 `kss.split_sentences` 같은 **한국어 문장 분리기**를 반드시 쓰는 것. `.` 하나로 자르면 "3.5%", "1.4.2절" 같은 경우에서 다 깨진다.

### ④ Parent-Child Chunking — "검색은 작게, 답변은 크게"

이게 시니어의 진짜 답이다. **검색용 청크(small)와 LLM에 넣는 컨텍스트(large)를 분리**한다.

```
┌─────────────────────────────────────────────────────────┐
│  Parent Chunk (2000 tokens, 조항 전체)                  │
│  ┌────────────┬────────────┬────────────┬───────────┐  │
│  │ Child 1    │ Child 2    │ Child 3    │ Child 4   │  │
│  │ (300 tok)  │ (300 tok)  │ (300 tok)  │ (300 tok) │  │
│  │ embedded   │ embedded   │ embedded   │ embedded  │  │
│  └────────────┴────────────┴────────────┴───────────┘  │
│  parent_id: contract_v3_article_12                      │
└─────────────────────────────────────────────────────────┘

Retrieval flow:
  Query → embed → top-k Child chunks 검색
       → 각 Child의 parent_id로 Parent 청크를 fetch
       → Parent를 LLM 컨텍스트로 주입
```

**왜 이게 답인가**:
- 검색 정확도(recall)는 **작은 청크**일수록 높다 (임베딩이 하나의 주제만 담기 때문)
- LLM 답변 품질은 **큰 컨텍스트**일수록 높다 (예외 조항, 배경, 정의가 함께 들어감)
- 두 요구가 상충하는데, Parent-Child는 이걸 분리해서 둘 다 얻는다

앞의 계약서 예시로 돌아가면: "위약금이 얼마?" 쿼리가 "10%" Child chunk에 매칭되어도, Parent chunk를 통째로 LLM에 주면 "단, 300%" 조항이 함께 들어간다. **파편화가 원천적으로 불가능**해진다.

## 3. 트레이드오프 매트릭스

| 전략 | 구현 난이도 | 임베딩 비용 | Recall | 컨텍스트 품질 | 유지보수 |
|---|---|---|---|---|---|
| Fixed-size (1000자) | ★ | 저 | 중 | **저 (파편화)** | 저 |
| Structural | ★★★ (도메인별 파서) | 저 | 고 | 고 | 중 (문서 포맷 바뀌면 파서 수정) |
| Semantic | ★★ | **고 (2배)** | 중~고 | 중 | 저 |
| Sliding+Sentence | ★★ | 저 | 중 | 중 | 저 |
| **Parent-Child** | ★★★★ | 중 (child만 embed) | **고** | **고** | 중 |

**시니어의 선택**: 프로덕션 RAG는 대개 **Structural(가능한 경우) + Parent-Child(항상)** 조합으로 수렴한다.

## 4. 실제 사례

### 사례 1: Anthropic Contextual Retrieval (2024)

Anthropic이 2024년 9월 공개한 [Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)이 사실상 청킹 문제의 다른 해법이다. 각 청크를 embed하기 전에 **"이 청크가 전체 문서에서 어떤 맥락에 있는지"를 LLM이 한 줄로 요약해서 붙인 다음** embed한다.

```
원본 청크: "위약금은 계약금의 10%로 한다."
                    ↓ Claude가 앞부분 문서를 보고 컨텍스트 생성
Contextualized: "이 조항은 [삼성전자-LG전자 부품 공급 계약서] 제12조의
                 일반 위약금 규정이며, 뒤에 이어지는 단서 조항(고의·중과실 시 300%)와
                 함께 해석되어야 한다. 위약금은 계약금의 10%로 한다."
```

Anthropic이 발표한 벤치마크: **retrieval failure rate 49% 감소**. 이 수치가 의미하는 바는 명확하다 — "청크를 어떻게 자를 것인가"가 아니라 **"청크에 얼마나 많은 맥락을 심을 것인가"**가 진짜 문제였다는 것.

비용: 100만 청크 × 컨텍스트 생성(Claude Haiku, prompt caching 적용) ≈ $15. 이게 감당 가능한 이유가 바로 **Prompt Caching**([[llm-gateway-pattern]] 참고)이다. 문서 본문은 캐시되고, 청크만 변수로 들어간다.

### 사례 2: Notion AI (2024) — 청크 크기와 임베딩 모델 동시 교체의 재앙

Notion이 2024년 초 `ada-002 → 3-large`로 임베딩 교체하면서 **동시에 청크 크기도 512 → 1024 tokens로 바꿨다**. "어차피 재색인하는 김에". 결과: 수 주간 검색 품질이 왔다갔다 하다가 롤백. 원인은 나중에야 밝혀졌는데, `3-large`가 긴 컨텍스트에서 성능이 좋아진 게 아니라 **오히려 512 tokens 근처에서 최적**이었다는 것. 청크만 키우면서 임베딩 성능을 낭비했다.

**교훈**: 청크 크기·임베딩 모델·prompt 형식은 **한 번에 하나씩만 바꾼다**. A/B가 안 되면 아무것도 배우지 못한다.

### 사례 3: 국내 H 로펌 (2025) — 판례 챗봇의 조항 파편화 참사

국내 대형 로펌이 자체 판례 검색 챗봇을 만들었다. LangChain 기본값 `chunk_size=1000, overlap=200`. 3개월 시범 운영 중, 파트너 변호사가 챗봇 답변을 근거로 서면을 작성해 법원에 제출했는데 **뒤늦게 상대측 변호사가 "해당 판결의 반대 취지 판시가 뒷문단에 있다"고 지적**. 서면 정정 + 기일 연기 + 내부 감사. 로펌은 이후 판례 청킹을 "판시사항 / 판결요지 / 이유 각 항목" 단위의 Structural + Parent-Child로 재설계했고, 청크 개수는 4.7배 증가, 임베딩 재색인 비용 약 $1,200이 들었다. 파트너급 시니어 시간의 시급을 생각하면 **이 $1,200은 감사 대응 1시간보다 싸다**.

### 사례 4: Perplexity — 웹 스케일에서의 다른 답

Perplexity는 웹 전체를 크롤링하기 때문에 문서 구조가 통제 불가능하다. 이들이 택한 방향은 **"청킹을 아예 얕게 하고, Reranker에 다 맡긴다"**. 청크는 작게(200 tokens 근처), 후보를 100개 이상 뽑은 뒤 강력한 reranker로 재정렬. Structural chunking을 웹 스케일에서 하는 건 불가능하다는 판단.

**교훈**: 청킹 전략은 **문서의 통제 가능성**에 따라 다르다. 내부 문서(통제 가능) → Structural. 웹 크롤링(통제 불가) → Small chunk + Reranker.

## 5. 흔한 함정

### 함정 1. Markdown/HTML 태그를 그대로 embed에 포함

```
"### 위약금 조항\n\n<table><tr><td>10%</td></tr></table>"
```

이런 청크를 embed하면 **"### / \<table\> / \<tr\>" 같은 마크업 토큰이 유사도 계산을 오염**시킨다. 구조 정보는 metadata로 빼고, 임베딩 대상 텍스트에서는 제거한다.

### 함정 2. 표(Table)를 Row 단위로 자름

재무제표에서 "매출액 / 영업이익 / 당기순이익"이 한 행씩 잘리면 "당기순이익이 얼마?" 쿼리가 header(어느 회사, 어느 연도)를 잃는다. **표는 반드시 header + row를 한 청크에 유지**한다. `pandas.to_markdown()`으로 통째로 넣거나, row별로 자를 때 header를 prepend한다.

### 함정 3. 코드 블록을 함수 중간에서 자름

기술 문서 청킹 시, ```` ``` ```` 안쪽에서 청크 경계를 만들면 함수 시그니처와 body가 분리된다. **코드 블록은 unbreakable region으로 처리**한다. `chunk_size`를 초과해도 코드 블록은 통째로 유지.

### 함정 4. 청크 metadata 없이 저장

청크 하나에는 최소 이만큼의 metadata가 필요하다.

```python
Chunk(
    text=...,
    metadata={
        "doc_id": "contract_2026_v3.pdf",
        "doc_version": "v3",
        "chunk_index": 47,
        "parent_chunk_id": "article_12",
        "section": "제12조 위약금",
        "created_at": "2026-09-15",
        "chunk_strategy": "structural_v2",  # ← 이거 진짜 중요
        "embedding_model": "text-embedding-3-large",
    }
)
```

`chunk_strategy`와 `embedding_model`이 저장되어야 나중에 [[embedding-migration]] 할 때 어느 청크가 어느 전략으로 만들어졌는지 추적 가능하다. 없으면 재색인 지옥.

### 함정 5. 청크 크기를 프롬프트 컨텍스트 한계로 결정

"우리 Claude 3.5 Sonnet 쓰니까 200k 컨텍스트 있잖아, 청크 크게 잡자"는 논리가 제일 위험하다. 컨텍스트가 크다고 LLM이 그 안의 모든 정보를 균등하게 활용하는 게 아니다. **"Lost in the Middle" 현상**은 여전히 2026년에도 유효하다. 청크 크기는 **임베딩 모델의 sweet spot(200~500 tokens)**으로 정하고, LLM 컨텍스트는 Parent-Child로 채운다.

### 함정 6. 청킹 로직을 애플리케이션 코드에 하드코딩

```python
# 이런 코드가 3년 뒤 기술부채가 된다
chunks = text.split("\n\n")
```

청킹은 **Pipeline의 first-class citizen**으로 다뤄야 한다. 별도 모듈, 버전 관리, 테스트 케이스(특히 엣지 케이스: 표, 코드, 각주, 목차). 청킹 로직 변경 = 임베딩 재계산 = 비용 = 다운타임 리스크. 이걸 함부로 바꿀 수 없게 만들어야 한다.

## 6. 언제 쓰고 언제 쓰면 안 되는가

### 반드시 Structural + Parent-Child를 써야 하는 경우
- 법률/의료/재무 문서 (파편화가 곧 법적 리스크)
- 기술 매뉴얼, API 문서 (함수와 예제가 분리되면 무용지물)
- 사내 정책 문서 (예외조항이 본조항보다 중요)

### Semantic Chunking이 정당한 경우
- 블로그, 위키, 기술 아티클 (문서 구조가 없지만 주제 변화가 뚜렷)
- 청킹 API 비용이 감당 가능한 규모 (수십만 문서 이하)

### Fixed-size + Overlap으로 충분한 경우
- **거의 없다**. 굳이 꼽자면: 완전히 균질한 텍스트(예: 트윗 모음, 상품 리뷰). 이런 경우도 문장 경계 스냅은 반드시 넣어야 한다.

### 청킹 자체를 하지 말아야 하는 경우
- 문서 자체가 짧다 (1-2 페이지, 512 tokens 이하) → 통째로 embed
- 문서 간 독립성이 강하고 개수가 적다 (수백 개) → Full-doc embedding + BM25 hybrid
- Q&A pairs가 이미 있다 → 질문을 embed key로, 답변을 payload로. 청킹 필요 없음

### 하이브리드가 답인 경우
Contextual Retrieval + Parent-Child. Anthropic이 발표한 방식과 검색-답변 분리를 결합. 2026년 프로덕션 RAG의 사실상 표준.

---

> 💡 **왜 중요한가**: RAG 시스템의 정확도 문제는 십중팔구 임베딩 모델이 아니라 청킹에서 온다 — 그리고 청킹 실패는 소송이 걸리기 전까지 아무도 눈치채지 못한다.
