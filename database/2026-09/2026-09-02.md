### MySQL `Redo Log`와 `Undo Log` — 커밋 순간 데이터파일에 안 써도 살아남는 이유, 그리고 롤백이 가능한 이유

InnoDB는 커밋 시점에 실제 데이터 페이지를 디스크에 쓰지 않는다. 대신 **Redo Log**(변경 후 상태)를 순차적으로 기록해 크래시 복구를 보장하고, **Undo Log**(변경 전 상태)를 별도로 남겨 롤백과 MVCC 스냅샷 읽기를 지원한다. 즉 커밋된 데이터가 데이터파일에 반영되지 않은 상태로 서버가 죽어도 Redo Log를 재생(replay)해 복구하며, 반대로 아직 커밋되지 않은 변경은 Undo Log를 통해 되돌린다.

```
트랜잭션 시작
  ├─ UPDATE user SET name='B' WHERE id=1  (원래 'A')
  │    ├─ Undo Log: "id=1 → 'A'로 되돌려라"   (롤백/MVCC용)
  │    └─ Redo Log: "id=1 → 'B'로 바꿔라"     (재실행/복구용)
  │
  ├─ COMMIT
  │    └─ Redo Log 만 fsync → 디스크 확정 (WAL: Write-Ahead Logging)
  │       ※ 실제 데이터 페이지는 아직 메모리(Buffer Pool)에만 있음
  │
  └─ [크래시 발생]
       └─ 재기동 시 Redo Log 재생 → 데이터 페이지 복구
```

WAL(Write-Ahead Logging) 원칙 덕분에 "커밋된 변경은 Redo Log에만 반영되면 안전"하다. 실제 데이터 페이지(더 무거운 랜덤 I/O)는 이후 백그라운드 스레드가 여유롭게 flush 한다. 이 구조 때문에 `innodb_flush_log_at_trx_commit=1`이 곧 "커밋당 fsync 1번"을 의미하는 것이고, 대량 트랜잭션에서 Undo Log가 계속 커지면 **long-running transaction**이 다른 세션의 MVCC 스냅샷을 붙잡아 두어 undo 영역이 폭증하는 문제(history list length 증가)가 발생한다.

> 💡 **왜 중요한가**: DB가 "빠른데도 안전한" 이유의 대부분은 이 두 로그가 역할을 나눠 갖기 때문이며, 장애 복구·성능 튜닝·롱 트랜잭션 문제 진단의 출발점이 전부 여기다.

### PostgreSQL `VACUUM`과 `autovacuum` — DELETE 해도 디스크는 줄지 않는다, 죽은 튜플이 쌓이는 MVCC의 청구서

PostgreSQL은 UPDATE/DELETE 시 기존 행을 즉시 지우지 않는다. MVCC 구현상 **새 버전을 추가**하고 옛 버전은 "dead tuple"로 남겨둔 뒤, `VACUUM`이 나중에 회수한다. 이 때문에 `DELETE FROM t`를 실행해도 테이블 파일 크기는 그대로이고, 오히려 dead tuple이 쌓여 인덱스 스캔·시퀀셜 스캔 모두 느려진다.

```
UPDATE user SET name='B' WHERE id=1
   ├─ (old) id=1, name='A', xmin=100, xmax=200   ← dead tuple (아직 남아있음)
   └─ (new) id=1, name='B', xmin=200, xmax=NULL  ← live tuple

  ※ MVCC: 각 트랜잭션은 xmin/xmax로 자기 스냅샷에서 보이는 버전만 읽음
     → 아직 진행 중인 오래된 트랜잭션이 있으면 옛 버전을 지울 수 없음

autovacuum이 하는 일:
  1) dead tuple 회수 → 재사용 가능한 공간으로 표시 (파일 크기는 그대로)
  2) visibility map 갱신 → Index-Only Scan 가능하게
  3) ANALYZE → 통계 갱신 → 옵티마이저 정확도↑
  4) XID wraparound 방지 (32bit XID 소진 시 DB 정지)
```

문제는 **autovacuum이 트리거되는 임계치**가 기본값(`autovacuum_vacuum_scale_factor=0.2`, 20%)이라 대형 테이블에서는 dead tuple이 수천만 건 쌓여야 겨우 돈다는 것. 이때는 `ALTER TABLE ... SET (autovacuum_vacuum_scale_factor = 0.05)`처럼 테이블별 조정이 필수다. 또한 **long-running transaction이 하나라도 있으면** VACUUM이 dead tuple을 회수하지 못한다(그 트랜잭션의 스냅샷에서 여전히 보일 수 있으므로) — 배치 잡·리포팅 세션이 밤새 열려 있으면 낮 동안 만들어진 모든 dead tuple이 회수 불가 상태로 쌓인다. 심각해지면 **XID wraparound**를 막기 위해 강제 anti-wraparound VACUUM이 돌며, 이때는 취소도 안 되고 서비스가 사실상 멈춘다.

> 💡 **왜 중요한가**: PostgreSQL의 성능 문제 절반은 "왜 VACUUM이 안 돌았는가"이고, 나머지 절반은 "왜 VACUUM이 회수를 못 했는가"다 — MySQL InnoDB의 undo 관리와 정확히 대칭되는 구조적 비용이다.
