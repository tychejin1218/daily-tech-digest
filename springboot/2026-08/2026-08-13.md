### `@Valid`와 `@Validated`는 이름만 비슷할 뿐 동작 범위가 완전히 다르다

`@Valid`는 JSR-303 표준 애노테이션으로 컨트롤러의 `@RequestBody` 파라미터 검증이나 중첩 객체 필드에 붙여 하위 객체까지 재귀적으로 검증할 때 쓴다. 반면 `@Validated`는 Spring 전용 애노테이션으로 그룹(groups) 검증과 `@Service` 계층의 메서드 파라미터 검증(AOP 프록시 기반)을 지원하지만, 필드에 붙여도 중첩 검증은 트리거되지 않는다. 실무에서 `@RestController`에 `@Validated`를 클래스 레벨로 붙이고 `@PathVariable`, `@RequestParam`에 `@Min`, `@NotBlank`를 걸어야 검증이 동작하는데, 이 조합을 모르면 파라미터 검증이 조용히 무시되는 걸 못 알아챈다.

```java
@RestController
@Validated  // @PathVariable, @RequestParam 검증에 필수
public class UserController {
    @GetMapping("/users/{id}")
    public User get(@PathVariable @Min(1) Long id) { ... }

    @PostMapping("/users")
    public User create(@RequestBody @Valid UserDto dto) { ... }
    // UserDto 내부의 @Valid Address address; 필드는 @Valid로만 재귀 검증됨
}
```

또한 `@Validated`가 던지는 예외는 `ConstraintViolationException`이고, `@Valid`가 던지는 예외는 `MethodArgumentNotValidException`이라 `@ControllerAdvice`에서 각각 별도로 처리해야 한다. 이걸 하나로 뭉뚱그리면 500 에러가 그대로 클라이언트에 노출된다.

> 💡 **왜 중요한가**: 두 애노테이션의 차이를 모르면 검증 로직이 절반만 동작하는 상태로 프로덕션에 배포되고, 예외 타입이 달라 글로벌 예외 핸들러가 절반의 케이스만 잡는다.

### `RestTemplate`의 `HttpClient` 커넥션 풀은 기본값이 없어 매 요청마다 TCP 핸드셰이크가 일어난다

`new RestTemplate()`을 그대로 쓰면 내부적으로 `SimpleClientHttpRequestFactory`를 사용하는데, 이건 JDK의 `HttpURLConnection` 기반이라 커넥션 풀이 없다. 매 요청마다 3-way handshake와 TLS handshake가 반복되어 외부 API 호출이 많은 서비스에서 P99 레이턴시가 수백 ms씩 튀는 원인이 된다. `Apache HttpClient`나 `OkHttp` 기반의 `HttpComponentsClientHttpRequestFactory`로 교체하고 커넥션 풀 크기, keep-alive, timeout을 명시적으로 설정해야 한다.

```java
@Bean
public RestTemplate restTemplate() {
    PoolingHttpClientConnectionManager cm = new PoolingHttpClientConnectionManager();
    cm.setMaxTotal(200);                // 전체 최대 커넥션
    cm.setDefaultMaxPerRoute(50);       // 라우트(호스트)당 최대 커넥션

    CloseableHttpClient httpClient = HttpClients.custom()
        .setConnectionManager(cm)
        .evictIdleConnections(30, TimeUnit.SECONDS)  // idle 커넥션 정리
        .build();

    HttpComponentsClientHttpRequestFactory factory = new HttpComponentsClientHttpRequestFactory(httpClient);
    factory.setConnectTimeout(2000);    // 연결 타임아웃
    factory.setReadTimeout(5000);       // 읽기 타임아웃 — 미설정 시 무한 대기

    return new RestTemplate(factory);
}
```

특히 `readTimeout`이 미설정이면 상대 서버가 응답을 안 줄 때 스레드가 무한 블로킹되어 톰캣 워커 풀이 순식간에 고갈된다. 장애 전파의 대표적인 경로이며, Hystrix나 Resilience4j 같은 서킷 브레이커를 붙이기 전에 반드시 잡아야 하는 기본기다.

> 💡 **왜 중요한가**: 커넥션 풀 없는 `RestTemplate`은 트래픽이 늘수록 지수적으로 느려지고, 타임아웃 미설정은 하나의 느린 외부 API가 전체 서비스를 마비시키는 장애의 씨앗이 된다.
