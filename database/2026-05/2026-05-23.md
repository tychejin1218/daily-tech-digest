### PostgreSQL `MATERIALIZED VIEW` + `REFRESH CONCURRENTLY` — 무거운 집계 쿼리를 스냅샷으로 미리 계산해두기

대시보드용 다중 조인·집계 쿼리를 매 요청마다 실행하는 대신, `MATERIALIZED VIEW`로 결과를 물리 테이블처럼 저장해두고 `REFRESH MATERIALIZED VIEW CONCURRENTLY`로 락 없이 갱신할 수 있다. `CONCURRENTLY`는 유니크 인덱스가 필수이며, 갱신 중에도 기존 뷰에 대한 `SELECT`를 차단하지 않아 무중단 리프레시가 가능하다.

```sql
CREATE MATERIALIZED VIEW daily_sales_summary AS
SELECT date_trunc('day', created_at) AS day,
       product_id,
       SUM(amount) AS total,
       COUNT(*) AS orders
FROM orders
GROUP BY 1, 2;

CREATE UNIQUE INDEX ON daily_sales_summary (day, product_id);

-- 락 없이 갱신 (cron이나 pg_cron으로 주기 실행)
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_sales_summary;
```

> 💡 **왜 중요한가**: 실시간성이 크게 중요하지 않은 집계는 뷰 스냅샷으로 밀어두면 응답 시간이 초 단위에서 밀리초 단위로 떨어진다.

### JPA `Hibernate.initialize()` vs `@BatchSize` — N+1을 상황별로 골라 잡기

`FetchType.LAZY` 연관에서 N+1이 발생할 때, 특정 지점에서 컬렉션을 즉시 초기화하고 싶다면 `Hibernate.initialize(entity.getItems())`로 명시적으로 로드하고, 여러 부모 엔티티의 자식을 한 번에 묶어 가져오고 싶다면 `@BatchSize(size = N)`으로 `IN (?, ?, ...)` 쿼리로 그룹핑한다. `fetch join`은 페이징이 깨지고 카티션 곱이 발생하므로, 페이징 있는 리스트 조회에는 `@BatchSize`가 더 안전하다.

```java
@Entity
public class Order {
    @OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
    @BatchSize(size = 100)  // 100개 부모마다 IN 쿼리 1번으로 자식 로드
    private List<OrderItem> items;
}

// 특정 지점에서만 강제 초기화
Order order = orderRepository.findById(id).orElseThrow();
Hibernate.initialize(order.getItems());
```

> 💡 **왜 중요한가**: fetch join은 페이징·중복 문제로 만능이 아니므로, `@BatchSize`와 `initialize()`를 상황에 맞게 조합해야 진짜 N+1이 사라진다.
