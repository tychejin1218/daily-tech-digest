### LLM Gateway 패턴 — "OpenAI SDK를 각 서비스에서 직접 호출한다"는 순진함, 그리고 API 키 하나 로테이션에 6개 서비스가 동시에 죽는 방식

#### 시나리오: 2026년 3월, 어느 이커머스 회사의 새벽 4시 17분

인프라 팀 리더의 폰이 울린다. `openai-key-rotation-emergency` 채널에 30분 전 알림이 떴다. 결제 팀이 어제 저녁 GitHub에 실수로 `.env`를 커밋했고, OpenAI가 자동으로 그 키를 revoke했다.

문제는 이 키를 쓰는 서비스가 결제 팀만이 아니라는 것이다.

- 상품 설명 자동생성 (마케팅 팀)
- CS 티켓 자동 분류 (CX 팀)
- 리뷰 요약 (검색 팀)
- 이상거래 탐지 보조 프롬프트 (리스크 팀)
- 챗봇 (그로스 팀)
- 결제 실패 원인 요약 (결제 팀)

각 팀은 `pip install openai` 하고 자기 서비스의 환경변수에 키를 박아넣었다. 심지어 두 개 팀은 하드코딩했다. 이걸 다 찾아서 로테이션하는 데 4시간이 걸렸고, 그 4시간 동안 상품 설명 API가 500을 뱉으면서 신규 등록 상품이 검색에 안 걸렸다.

리더는 그날 아침 회고 미팅에서 이렇게 말한다.

> "우리는 API Gateway 없이 결제 API 뚫어놓지 않죠. 근데 왜 LLM은 각 서비스가 직접 뚫고 있죠?"

이 질문이 LLM Gateway 패턴의 시작이다.

#### API Gateway는 이미 아는 이야기, 그런데 왜 하나 더 필요한가

시니어 백엔드라면 API Gateway는 손등 보듯 안다. Kong, Envoy, AWS API Gateway. 인증, 레이트 리미트, 라우팅, 로깅. 왜 LLM에는 별도 게이트웨이가 필요한가? 그냥 기존 API Gateway로 프록시하면 안 되나?

안 된다. 이유는 세 가지다.

1. **LLM API는 "인증하고 넘기면 끝"이 아니다.** OpenAI 응답 하나에 프롬프트 토큰 3200개, 완성 토큰 850개, 캐시 히트 1900개, 총 비용 $0.0142가 붙어있다. 이걸 팀별로 attribution하지 않으면 월말에 "누가 이만큼 태웠는지" 아무도 모른다. Envoy는 이걸 안다? 모른다. 만들어 넣어야 한다.

2. **LLM API는 실패 방식이 이상하다.** 429가 아니라 200에 `{"error": "rate limit"}`이 오기도 하고, 스트리밍 중 SSE 프레임이 잘리기도 하고, JSON mode인데 JSON이 아닌 게 오기도 한다. 이런 실패는 L7 로드밸런서의 헬스체크가 잡을 수 없다.

3. **모델은 계속 바뀐다.** `gpt-4o` → `gpt-4o-2024-11` → `gpt-5-nano` → `claude-sonnet-4-6`. 각 서비스가 SDK를 직접 쓰면 이 변경이 6개 PR로 쪼개진다. 게이트웨이가 있으면 1개 설정 변경이다.

즉, **LLM Gateway는 "API Gateway + FinOps 미터 + 모델 추상화 레이어"의 조합**이다.

#### 다이어그램: Before / After

```
[Before — 각 서비스가 직접 LLM API 호출]

  ┌────────────┐         ┌──────────────┐
  │ Search Svc │────┐    │              │
  ├────────────┤    │    │              │
  │  Chatbot   │────┤    │              │
  ├────────────┤    ├───▶│  OpenAI      │
  │  Payment   │────┤    │  Anthropic   │
  ├────────────┤    │    │  Bedrock     │
  │  CX Ticket │────┤    │              │
  ├────────────┤    │    └──────────────┘
  │  Reviews   │────┘
  └────────────┘
   ↑ 각자 SDK, 각자 키, 각자 재시도, 각자 로깅
   ↑ 비용 attribution 불가
   ↑ 모델 교체 = 6개 PR
   ↑ 키 유출 = 6곳 로테이션


[After — LLM Gateway 도입]

  ┌────────────┐
  │ Search Svc │──┐
  ├────────────┤  │   ┌─────────────────────────┐
  │  Chatbot   │──┤   │      LLM Gateway         │      ┌──────────┐
  ├────────────┤  │   │                          │      │ OpenAI   │
  │  Payment   │──┼──▶│ • Auth / Key vault       │─────▶├──────────┤
  ├────────────┤  │   │ • Rate limit (per team)  │      │ Anthropic│
  │  CX Ticket │──┤   │ • Cost attribution       │      ├──────────┤
  ├────────────┤  │   │ • Model routing          │      │ Bedrock  │
  │  Reviews   │──┘   │ • Semantic cache         │      ├──────────┤
  └────────────┘      │ • Retry / Fallback       │      │ Self-host│
                      │ • PII redaction          │      │  vLLM    │
                      │ • Observability trace    │      └──────────┘
                      └─────────────────────────┘
```

핵심은 **각 서비스가 OpenAI를 모른다는 것**이다. 그들이 아는 것은 사내 엔드포인트 `POST /v1/chat/completions` 뿐이다. 헤더에 `X-Team-Id: risk`, `X-Use-Case: fraud-summary`만 붙이면 된다.

#### LLM Gateway가 담당하는 7가지 책임

시니어 관점에서 게이트웨이의 책임을 뜯어보면 이렇다. 아래 7가지 중 4개 이상이 필요해지는 순간이 도입 시점이다.

**1. Key Management & Rotation**

각 서비스가 아니라 게이트웨이만 실제 프로바이더 키를 안다. 서비스는 사내 발급 토큰만 갖는다. 유출되면 게이트웨이에서 revoke, 프로바이더 키는 무사하다. Vault/KMS 연동이 여기에 붙는다.

**2. Per-Team / Per-Use-Case Rate Limit**

OpenAI Tier 5 계정 하나에 6개 팀이 붙어있으면, 챗봇이 트래픽 스파이크로 TPM 다 태우는 순간 결제 실패 요약도 죽는다. 게이트웨이는 팀별/유스케이스별 quota를 별도로 관리한다.

```
챗봇: 500 RPM, 60k TPM
결제: 50 RPM, 10k TPM  (얘는 무슨 일이 있어도 살아있어야 함)
마케팅: burst 200 RPM, sustained 50 RPM
```

**3. Cost Attribution & Budget Kill**

각 요청을 `team_id + use_case + trace_id`로 태깅하고 응답의 `usage` 필드를 파싱해서 비용을 기록한다. 팀별 월 예산을 넘으면 **자동 차단**하거나 저렴한 모델로 강등한다.

이걸 SDK 직접 호출로 하려면? 각 팀이 미들웨어를 짜야 한다. 6팀이면 6번. 그리고 3팀은 안 짠다.

**4. Model Routing & Fallback**

같은 `/chat/completions` 엔드포인트라도, `use_case=simple-classification`이면 Haiku로, `use_case=complex-reasoning`이면 Opus로 라우팅. Anthropic 다운되면 OpenAI로 fallback. 이 로직은 이미 [LLM Routing/Fallback](../lv5/llm-routing.md) 학습에서 다뤘다. 게이트웨이는 그걸 **호스팅하는 자리**다.

**5. Semantic Cache**

이미 다룬 주제. 게이트웨이는 캐시가 붙는 자연스러운 자리다. 서비스마다 각자 캐시 붙이면 히트율이 파편화되고, 캐시 오염도 팀별로 따로 겪는다.

**6. PII Redaction & Guardrails**

요청에 주민번호/카드번호가 들어가면? 응답에 회사 내부 정보가 유출되면? 게이트웨이가 정규식/모델 기반으로 마스킹하거나 차단한다. 컴플라이언스는 6개 서비스 대신 게이트웨이 한 곳만 감사받으면 된다.

**7. Unified Observability**

모든 LLM 트래픽이 한 곳을 지나므로 `trace_id → prompt → response → tokens → cost → latency` 데이터가 통일된 스키마로 쌓인다. LangFuse/LangSmith 연동도 여기 한 번만 하면 된다.

#### 실제 사례: 누가 왜 이 패턴을 택했나

**Portkey (오픈소스 + SaaS)**

전형적인 LLM Gateway 제품. 250+ 모델을 하나의 OpenAI-compatible API로 노출한다. "너네 코드에서 `base_url`만 우리 걸로 바꿔라"가 세일즈 라인이다. Portkey가 잘 노리는 시장은 **"이미 OpenAI SDK로 프로덕션 뿌려놓은 회사"**. 코드 안 바꾸고 게이트웨이만 앞에 붙이는 것이 그들의 셀링포인트다.

**LiteLLM (BerriAI)**

Portkey의 오픈소스 진영 라이벌. Python proxy로 시작해서 지금은 100M+ 요청/월 처리하는 회사들이 자기네 게이트웨이로 쓴다. Netflix, Rocket Money가 공개적으로 사용을 언급했다. 강점은 **provider abstraction**과 **spend tracking**. 약점은 Python이라 latency 오버헤드가 붙는다는 것 (평균 20-40ms).

**Cloudflare AI Gateway**

**정치적으로 흥미로운 케이스**. Cloudflare는 이미 워크로드가 자기네 엣지를 지난다. 거기서 그냥 LLM 요청도 인터셉트해서 캐시/분석/레이트리미트 붙여준다. 별도 인프라 없이 "이미 있는 프록시"에 기능을 얹었다. 대신 자체 모델 라우팅 로직은 아직 제한적이다.

**Uber의 내부 GenAI Gateway**

Uber는 2024년 기술 블로그에 자체 게이트웨이 아키텍처를 공개했다. 이유는 위의 7가지 그대로였다 — 팀별 비용 attribution, 사내 온프렘 vLLM과 외부 OpenAI를 하나의 인터페이스로. 여기서 배울 점은 **"OpenAI만 쓴다면 안 만들었을 것"** 이라는 뉘앙스다. 온프렘 모델과 외부 API를 섞는 순간 게이트웨이가 필수가 된다.

**Doordash, Airbnb, Discord 등**

내부 자료를 종합하면 500명 이상 엔지니어링 조직에서 LLM을 프로덕션에 여러 곳에서 쓰기 시작하면 **거의 예외 없이** 사내 게이트웨이를 만든다. 규모가 커지면 사도 아니고 만든다. 왜냐면 위의 7가지 책임이 그 규모에서는 협상 대상이 아니기 때문이다.

#### 트레이드오프: 공짜가 아니다

**1. Latency 오버헤드**

게이트웨이 한 홉이 추가된다. 잘 짠 Go/Rust 게이트웨이는 5-10ms, LiteLLM 같은 Python은 20-40ms. LLM 응답 자체가 초 단위인 걸 감안하면 무시할 수 있지만, **스트리밍 first-token latency**에는 예민한 유스케이스가 있다 (실시간 챗봇 등). 이 경우 게이트웨이가 SSE proxy를 얼마나 잘 하는지가 중요하다.

**2. SPOF (Single Point of Failure)**

모든 LLM 트래픽이 한 곳을 지난다는 것은 **한 곳이 죽으면 다 죽는다**는 뜻이다. HA 구성, 회로차단기, "게이트웨이 자체가 죽으면 direct-call로 우회하는 escape hatch"까지 설계해야 한다. 이걸 안 하면 API Gateway를 새로 만들면서 옛날에 배운 교훈을 다시 배우게 된다.

**3. 팀 자율성 vs 중앙 통제**

게이트웨이는 본질적으로 **중앙 통제 도구**다. "마케팅 팀이 새 모델 실험하고 싶다"고 하면 게이트웨이 팀이 승인해야 한다. 이게 처음엔 좋은 거버넌스지만, 조직이 크면 병목이 된다. 그래서 성숙한 조직은 게이트웨이를 **셀프서비스 플랫폼**으로 만든다 — 팀이 UI에서 자기 use_case를 등록하고 모델을 고르는 방식.

**4. Provider Feature Lag**

OpenAI가 어제 새 파라미터를 추가했다. 게이트웨이가 아직 지원 안 한다면? 서비스 팀은 기다려야 한다. 이를 완화하려면 **passthrough 모드** (모르는 파라미터는 그대로 프로바이더에 넘김) 를 지원해야 한다.

#### 언제 쓰고, 언제 쓰지 말아야 하는가

**써야 하는 경우**

- **LLM을 쓰는 서비스가 3개 이상**이고 앞으로 늘어날 계획이다.
- **월 LLM 비용이 $10k 넘어가는데** 팀별 attribution이 안 된다.
- **모델 프로바이더가 2개 이상**이거나 자체 vLLM 온프렘을 섞어 쓴다.
- **컴플라이언스 요구**가 있다 (PII 마스킹, 감사 로그 통합).
- 프롬프트/모델을 **PR 없이 바꾸고 싶다** (설정 기반 라우팅).

**쓰지 말아야 하는 경우**

- **서비스가 1-2개**고 앞으로도 그럴 것이다. 게이트웨이는 오버엔지니어링이다. 잘 짠 사내 SDK 하나로 충분하다.
- **초저지연이 미션 크리티컬**이고 (게임, 트레이딩) 게이트웨이 한 홉의 5-10ms도 허용 안 된다.
- **팀이 5명 이하**다. 이 규모에서는 게이트웨이 운영 비용이 얻는 이득을 넘어선다. 그냥 shared library로 재시도/로깅 표준화하는 편이 낫다.
- **하나의 프로바이더에 완전 lock-in되어 있고** 앞으로도 그럴 계획이다. 이 경우 프로바이더 SDK를 잘 쓰는 게 오히려 낫다.

시니어의 감각으로 말하면 이렇다. **"우리 팀 지금 3개 서비스에서 LLM 쓰고, 다음 분기에 5개로 늘어난다"**는 시점이 게이트웨이 도입의 스윗스팟이다. 그 전엔 이르고, 그 후엔 늦다. 늦어지면 나중에 "각 팀 SDK 코드 다 걷어내기"가 마이그레이션 지옥이 된다 — 실제로 위의 새벽 4시 시나리오가 그 지옥의 예고편이다.

> 💡 **왜 중요한가**: LLM Gateway는 새로운 개념이 아니라 API Gateway의 교훈이 LLM 세계에서 반복되는 것이며, 조직이 LLM을 "실험"에서 "프로덕션"으로 옮기는 순간 반드시 마주치는 아키텍처 결정이다.
