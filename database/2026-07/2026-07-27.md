### PostgreSQL `pg_hint_plan` — 옵티마이저를 우회하지 않고 힌트로 실행 계획 유도하기

PostgreSQL은 기본적으로 옵티마이저 힌트를 지원하지 않지만, `pg_hint_plan` 확장을 설치하면 주석 형태로 조인 순서·인덱스·스캔 방식을 강제할 수 있다. 통계가 왜곡됐거나 특정 파라미터 조합에서만 계획이 무너질 때 애플리케이션 쿼리를 수정하지 않고 `hint_plan.hints` 테이블에 규칙을 등록해 대응한다.

```sql
/*+ IndexScan(orders idx_orders_customer_created) NestLoop(orders customers) */
SELECT o.id, c.name
FROM orders o JOIN customers c ON c.id = o.customer_id
WHERE o.created_at >= now() - interval '1 day';
```

> 💡 **왜 중요한가**: 응급 상황에서 옵티마이저 판단을 덮어쓰면서도, 통계 개선 후 힌트만 제거해 원복할 수 있는 안전한 우회로가 된다.

### MySQL `Generated Column` + 함수 인덱스 — `WHERE LOWER(email) = ?` 같은 함수 조건을 인덱스로 태우기

`WHERE LOWER(email) = ?`, `WHERE JSON_EXTRACT(data, '$.status') = ?`처럼 컬럼에 함수를 씌우면 일반 인덱스는 무력화된다. MySQL 5.7+의 `STORED`/`VIRTUAL` 생성 컬럼에 인덱스를 걸거나, 8.0.13+의 함수 인덱스(`CREATE INDEX ... ON t ((LOWER(email)))`)로 표현식 자체를 인덱싱해 원본 쿼리를 그대로 두고 풀 스캔을 막을 수 있다.

```sql
ALTER TABLE users
  ADD COLUMN email_lower VARCHAR(255) GENERATED ALWAYS AS (LOWER(email)) VIRTUAL,
  ADD INDEX idx_users_email_lower (email_lower);

-- 또는 함수 인덱스 (MySQL 8.0.13+)
CREATE INDEX idx_users_email_lower ON users ((LOWER(email)));
```

> 💡 **왜 중요한가**: 애플리케이션이 대소문자·JSON 경로·정규화된 값으로 자주 조회할 때, 쿼리를 바꾸지 않고 인덱스만 얹어 O(log n) 탐색으로 되돌릴 수 있다.
