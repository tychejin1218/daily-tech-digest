### Vector DB 통합의 삼국지 — Pinecone, Weaviate, pgvector 중 무엇을 골라야 하는가, 그리고 왜 대부분의 팀이 잘못 고르는가

#### 도발: "일단 Pinecone 쓰죠"라는 결정이 6개월 뒤 청구서를 찢게 만드는 이유

RAG 프로젝트의 첫 스프린트에서 가장 흔한 대화는 이렇다.

> "임베딩 저장하려면 벡터 DB 필요하죠?"
> "그럼 Pinecone 쓰죠. 튜토리얼도 많고."
> "OK."

이 30초짜리 결정이 다음 세 가지 중 하나로 귀결된다.
1. **비용 폭발**: 10만 벡터 넣었더니 월 $70, 1000만 벡터로 늘렸더니 월 $2400. 그런데 실제 QPS는 초당 3개.
2. **락인(Lock-in) 후회**: 메타데이터 필터링이 SQL만큼 강력하지 않다는 걸 6개월 뒤에 깨닫고, 원본 DB와 Pinecone을 이중으로 관리 중.
3. **일관성 지옥**: Postgres의 유저 데이터와 Pinecone의 임베딩이 동기화가 어긋나서 "삭제된 문서인데 검색에 계속 뜨는" 버그를 3주째 추적 중.

시니어 관점에서 벡터 DB는 "AI 스택의 새 컴포넌트"가 아니라 **"기존 데이터 아키텍처에 억지로 끼워넣는 이질적 저장소"**다. 이걸 이해하지 않으면 선택 자체가 무의미하다.

---

#### 세 가지 접근의 근본적 차이

```
┌─────────────────────────────────────────────────────────────────────┐
│                     "벡터 검색"을 어디에 둘 것인가                  │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  [A] 전용 SaaS: Pinecone                                            │
│  ┌────────────────┐     ┌──────────────┐                            │
│  │  App Server    │────▶│  Pinecone    │  ← Managed, HTTP API       │
│  └────────────────┘     │  (Serverless)│                            │
│         │               └──────────────┘                            │
│         │               ┌──────────────┐                            │
│         └──────────────▶│  Postgres    │  ← 원본 데이터             │
│                         └──────────────┘                            │
│  → 두 개의 저장소, 두 개의 트랜잭션 경계                            │

│         │               └──────────────────┘                        │

│                         └──────────────┘                            │
│  → 여전히 이중 저장, 대신 검색 기능이 풍부                          │
│                                                                     │
│  [C] RDBMS 확장: pgvector                                           │
│  ┌────────────────┐                                                 │
│  │  App Server    │─────────┐                                       │
│  └────────────────┘         │                                       │
│                             ▼                                       │
│                    ┌──────────────────────┐                         │
│                    │  Postgres            │                         │
│                    │  + pgvector          │  ← 한 트랜잭션 안에      │
```

세 옵션의 진짜 차이는 "성능"이 아니라 **"데이터 경계선을 어디에 그을 것인가"**다.

#### 트레이드오프: 시니어가 봐야 할 5개 축

| 축 | Pinecone (SaaS) | Weaviate/Qdrant (자체 호스팅 특화 DB) | pgvector (RDBMS 확장) |
|---|---|---|---|
| **초기 도입 속도** | 즉시 (API 키만 있으면 OK) | 중간 (Helm/도커 배포) | 즉시 (`CREATE EXTENSION`) |
| **운영 부담** | 없음 (완전 관리형) | 높음 (샤딩, 복제 직접 관리) | 낮음 (기존 Postgres 인프라 재활용) |
| **1000만 벡터 이상** | 성능 최상, 비용 최악 | 튜닝 시 최상, 튜닝 실패 시 최악 | HNSW 기준 100만~500만이 안전지대 |
| **트랜잭션 일관성** | 없음 (외부 DB와 eventual) | 없음 (외부 DB와 eventual) | ACID (`INSERT INTO docs ... RETURNING embedding` 가능) |
| **하이브리드 검색** | 최근 지원, 미성숙 | 강함 (BM25 내장) | Postgres tsvector와 조합 (수동) |
| **필터링 표현력** | 제한적 (equality, IN 정도) | JSON path 필터 | 임의 SQL (JOIN 포함) |
| **월 비용 (1M 벡터, 1536-dim)** | ~$70~$100 (Serverless) | ~$50 (EC2 m5.large 기준) | ~$25 (기존 Postgres에 얹기) |

핵심 통찰:
- **Pinecone의 진짜 강점은 "성능"이 아니라 "운영 부담 zero"다.** 팀에 인프라 엔지니어가 없다면 이 값어치는 크다.
- **pgvector의 진짜 강점은 "속도"가 아니라 "트랜잭션 경계"다.** `documents` 테이블을 삭제하면 그 문서의 임베딩도 같은 트랜잭션에서 사라진다. Pinecone에서는 이걸 애플리케이션 코드로 보장해야 하고, 100% 성공은 불가능하다.
- **Weaviate/Qdrant는 애매한 위치에 있다.** 완전 관리형도 아니고, 기존 DB 통합도 안 되고. 다만 벡터 검색이 "제품의 핵심 기능"이고 규모가 크면 이 카테고리가 최적이다.

#### 실제 사례: 어떤 회사가 왜 그걸 골랐는가

**Notion (pgvector 채택)**
Notion AI는 초기에 Pinecone을 검토했지만 pgvector로 갔다고 알려져 있다. 이유는 두 가지.
1. 이미 Postgres 인프라가 대규모로 있고, DBA 팀이 튜닝 노하우를 축적한 상태.
2. Notion 문서의 **권한 체크**가 복잡한 SQL 조인 필요 (workspace_members, page_permissions 등). 벡터 검색 결과에 권한 필터를 걸어야 하는데, Pinecone에서는 이걸 다시 Postgres에 물어야 함 → RTT 두 번.

pgvector면 이렇게 끝난다:
```sql
SELECT p.id, p.title
FROM pages p
JOIN page_permissions pp ON pp.page_id = p.id
WHERE pp.user_id = $1
ORDER BY p.embedding <=> $2  -- 벡터 거리
LIMIT 10;
```

한 쿼리로 권한 + 벡터 검색이 끝난다. Pinecone으로는 절대 못 한다.

**Perplexity (자체 벡터 인프라 + 특화 DB 혼합)**
Perplexity는 검색이 "제품의 전부"이고, 규모가 매우 크다 (수십억 벡터). SaaS 비용은 파산 수준이고, pgvector는 성능이 부족하다. 그래서 자체 벡터 검색 엔진을 부분적으로 만들고 Qdrant/Vespa 같은 특화 스택을 조합한다.

**초기 스타트업 (Pinecone이 정답인 케이스)**
- 팀 5명, 백엔드 2명.
- 아직 벡터 데이터가 10만 개 이하.
- 벡터 검색이 제품의 중심이 아니라 "AI 챗 기능 하나" 추가.
- → **Pinecone 서버리스로 시작하고 나중에 옮기는 게 옳다.** pgvector 마이그레이션은 진짜 나중 문제고, 지금 시간을 인프라에 쓰는 건 낭비.

#### 시니어의 판단 기준: 언제 쓰고 언제 쓰면 안 되는가

**pgvector를 골라야 하는 경우** ✅
- 이미 Postgres를 쓰고 있고, DBA/DevOps 역량이 있다.
- 벡터 수 100만~500만 이하 (HNSW 인덱스 기준).
- 검색 결과에 복잡한 권한/메타데이터 필터가 필요 (특히 JOIN).
- 트랜잭션 일관성이 중요 (문서 삭제 시 임베딩도 원자적으로 삭제).
- 예산 제약이 크다.

**pgvector를 피해야 하는 경우** ❌
- 벡터 수 1000만 이상 + p99 < 50ms 요구.
- Postgres가 이미 CPU/IO 병목이다 (벡터 인덱스 빌드는 무겁다).
- 임베딩 차원이 1536보다 크거나 (예: text-embedding-3-large의 3072-dim), 여러 임베딩 모델을 동시에 실험한다.

**Pinecone(SaaS)를 골라야 하는 경우** ✅
- 팀이 작고 인프라 관리 여력이 없다.
- 벡터 검색이 제품의 "핵심"이 아니라 "부가 기능"이다.
- 규모가 예측 가능하고 서버리스 요금제 안에 들어온다.
- Multi-region 서비스라 지역별 벡터 저장이 필요하다.

**Pinecone을 피해야 하는 경우** ❌
- 규모가 1000만 벡터를 넘어가는 게 확실 (비용 폭발).
- 검색 결과에 복잡한 SQL-스러운 필터/조인이 필요.
- 데이터 주권/컴플라이언스 제약이 있다 (금융/의료).
- **트랜잭션 일관성이 조금이라도 중요하다.**

**Weaviate/Qdrant를 골라야 하는 경우** ✅
- 벡터 검색이 제품의 핵심이고, 규모가 크다.
- 하이브리드 검색을 특화 DB의 내장 기능으로 쓰고 싶다.
- 자체 호스팅을 감당할 수 있는 인프라 팀이 있다.

#### 함정 3개 — 어느 옵션을 골라도 만나게 되는 문제

**함정 1: 이중 저장의 일관성 부채**
Pinecone이든 Weaviate든 원본 데이터는 결국 다른 DB에 있다. `DELETE FROM documents WHERE id = 42` 후에 Pinecone에서 `id=42` 벡터를 지우는 코드가 실패하면? → 좀비 벡터가 검색에 뜬다. 이 문제를 해결하려면 outbox 패턴, CDC(Change Data Capture), 배치 재동기화 중 하나를 반드시 도입해야 한다. **이 비용은 아무도 초기 견적에 안 넣는다.**

**함정 2: 인덱스 재빌드 비용**
임베딩 모델을 바꾸면 (예: `ada-002` → `text-embedding-3-small`) 모든 벡터를 다시 계산해야 한다. 1000만 벡터라면 OpenAI 임베딩 API 호출료만 수천 달러, 시간은 며칠. Pinecone은 인덱스를 두 개 두고 A/B로 전환하는 게 표준. pgvector는 새 컬럼 만들고 `UPDATE` 배치. 어느 쪽이든 **다운타임 없는 전환 전략을 미리 설계**하지 않으면 프로덕션 배포일에 지옥을 본다.

**함정 3: "성능 벤치마크"의 무의미함**
Pinecone은 초당 수천 QPS를 광고하고, pgvector도 튜닝하면 1000 QPS는 나온다. 하지만 대부분의 RAG 시스템의 실제 QPS는 **초당 1~10개**다. LLM 호출이 병목이지 벡터 검색이 병목이 아니다. 벤치마크 숫자로 선택하지 말고, **팀의 운영 역량과 데이터 경계 요구사항**으로 선택하라.

---

> 💡 **왜 중요한가**: 벡터 DB 선택은 "성능 비교표"의 문제가 아니라 "당신의 트랜잭션 경계선을 어디에 그을 것인가"라는 아키텍처 결정이다. 이걸 6개월 뒤에 깨달으면 마이그레이션 비용이 초기 절약분의 10배다.
