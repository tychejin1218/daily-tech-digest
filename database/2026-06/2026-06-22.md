### 1. PostgreSQL `array_agg(... ORDER BY ...)`로 정렬된 집계 결과 한 줄에 만들기
"고객별 최근 주문 5건의 ID 배열" 같은 결과를 만들 때 서브쿼리·`STRING_AGG`+`SPLIT_PART` 같은 우회를 쓰기 쉽지만, PostgreSQL은 집계 함수 인자에 `ORDER BY`를 직접 받을 수 있어 한 줄로 끝난다. `array_agg(col ORDER BY ... DESC) FILTER (WHERE ...)`처럼 `FILTER`와 조합하면 "조건부 + 정렬된" 집계도 한 패스로 떨어진다.

```sql
SELECT
  customer_id,
  array_agg(id ORDER BY created_at DESC) FILTER (WHERE status = 'PAID')
    AS recent_paid_ids
FROM orders
GROUP BY customer_id;
```

> 💡 **왜 중요한가**: 애플리케이션 단에서 N+1로 모았다가 정렬하던 코드를 단 한 번의 쿼리로 대체해, 네트워크 왕복과 메모리 사용량을 동시에 줄인다.

### 2. MySQL `EXPLAIN ANALYZE`(8.0.18+)와 iterator 트리로 진짜 실행 시간 측정하기
전통적인 `EXPLAIN`은 옵티마이저의 "계획"만 보여주지만, MySQL 8.0.18부터의 `EXPLAIN ANALYZE`는 실제 실행 시간·반복 횟수·반환 행 수를 트리 형태로 출력한다. `actual time`과 `rows`만 비교해도 어느 노드에서 추정이 빗나갔는지(통계 갱신 필요), 어디서 행 수가 폭증하는지(잘못된 조인 순서)를 즉시 알 수 있다.

```sql
EXPLAIN ANALYZE
SELECT o.id, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'PAID' AND o.created_at >= NOW() - INTERVAL 7 DAY;

-- 출력 일부:
-- -> Nested loop inner join  (cost=... rows=120)
--     -> Index range scan on o using idx_status_created  (actual time=0.04..3.2 rows=8500)
--     -> Single-row index lookup on c using PRIMARY      (actual time=0.001 rows=1)
```

> 💡 **왜 중요한가**: "옵티마이저는 빠르다고 했는데 실제로는 느린" 케이스의 진단 단서를 별도 도구 없이 즉시 얻을 수 있어, PostgreSQL의 `EXPLAIN (ANALYZE, BUFFERS)`에 해당하는 자리를 차지한다.
