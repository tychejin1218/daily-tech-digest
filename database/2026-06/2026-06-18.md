### 1. PostgreSQL `pg_advisory_lock` — 테이블 락 없이 애플리케이션 레벨 분산 락 구현하기
배치 잡, 스케줄러 중복 실행, 외부 API 호출 직렬화 같은 "프로세스 간 상호 배제" 문제는 Redis나 ZooKeeper 없이도 `pg_advisory_lock(key)` / `pg_try_advisory_lock(key)`로 해결할 수 있다. 행이나 테이블을 잠그는 게 아니라 임의의 `bigint` 키 공간에 락을 걸기 때문에 실제 데이터에는 영향이 없고, 세션이 끊기면 자동 해제되어 죽은 락이 남지 않는다. 단, `pg_advisory_lock`은 명시적으로 unlock 하지 않으면 세션 종료까지 유지되므로, 트랜잭션 종료와 함께 풀리길 원한다면 반드시 `pg_advisory_xact_lock` 변형을 써야 한다.

> 💡 **왜 중요한가**: 별도 락 인프라를 도입하기 전에 이미 들고 있는 DB만으로 충분히 견고한 분산 락을 만들 수 있고, "세션 종료 시 자동 해제" 덕분에 좀비 락 운영 부담이 사라진다.

### 2. Spring `@Transactional` Self-Invocation — 같은 클래스 내부 호출에는 트랜잭션이 안 걸린다
`@Transactional`은 Spring AOP 프록시가 메서드를 가로채서 동작하는데, 같은 클래스의 메서드를 `this.otherMethod()`로 직접 호출하면 프록시를 거치지 않고 실제 객체를 호출하기 때문에 트랜잭션 어드바이스가 적용되지 않는다. 그래서 외부에서 호출했을 때는 잘 동작하던 `REQUIRES_NEW`, `readOnly=true`, 롤백 규칙이 내부 호출에서는 조용히 무시되고, 디버깅하기 가장 까다로운 부류의 버그가 된다. 해결책은 메서드를 다른 빈으로 분리하거나, `AopContext.currentProxy()` 또는 자기 자신을 빈으로 주입(self-injection)받아 프록시를 통해 호출하는 것이다.

> 💡 **왜 중요한가**: "분명 `@Transactional`을 붙였는데 롤백이 안 된다"는 미스터리의 대부분이 이 함정이고, 코드만 봐서는 절대 보이지 않으므로 팀의 공통 지식으로 박혀 있어야 한다.
