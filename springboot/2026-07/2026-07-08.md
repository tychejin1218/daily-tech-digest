### `@Validated`를 클래스 레벨에 붙여야 `@RequestParam`, `@PathVariable`에 붙인 제약 어노테이션이 동작한다

`@NotBlank`, `@Min` 같은 Bean Validation 어노테이션을 `@RequestBody` DTO 필드에 붙이면 `@Valid`만으로 검증되지만, 컨트롤러 메서드의 `@RequestParam`이나 `@PathVariable`에 직접 붙인 제약은 무시된다. 이때는 컨트롤러 클래스에 `@Validated`(스프링 어노테이션)를 붙여야 `MethodValidationInterceptor`가 프록시를 통해 파라미터를 검증하며, 위반 시 `ConstraintViolationException`이 던져지므로 `@ExceptionHandler`도 별도로 잡아줘야 한다.

```java
@RestController
@Validated  // 이게 없으면 @Min은 그냥 무시된다
public class UserController {
    @GetMapping("/users")
    public List<User> list(@RequestParam @Min(1) int page,
                           @RequestParam @Max(100) int size) { ... }
}
```

> 💡 **왜 중요한가**: DTO 검증에만 익숙하면 파라미터 제약이 조용히 무시되는 걸 놓쳐 잘못된 입력이 그대로 서비스 계층까지 흘러간다.

### `spring.jpa.defer-datasource-initialization=true`로 Hibernate 스키마 생성 후 `data.sql`이 실행되게 하기

Spring Boot 2.5부터 `schema.sql`/`data.sql`은 기본적으로 Hibernate DDL보다 **먼저** 실행되기 때문에, `spring.jpa.hibernate.ddl-auto=create`로 테이블을 만들 계획이라면 `data.sql`이 존재하지 않는 테이블에 INSERT를 시도해 애플리케이션이 부팅되지 않는다. `spring.jpa.defer-datasource-initialization=true`를 켜면 Hibernate가 스키마를 만든 뒤에 `data.sql`을 실행하도록 순서가 뒤집힌다.

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: create-drop
    defer-datasource-initialization: true  # data.sql은 DDL 이후에 실행
  sql:
    init:
      mode: always
```

> 💡 **왜 중요한가**: Boot 2.4↔2.5 사이 초기화 순서 정책이 바뀌었기 때문에 예전 프로젝트를 올리면 원인 모를 `Table not found` 에러로 부팅이 실패한다.
