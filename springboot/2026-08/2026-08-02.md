### `@Transactional`의 `propagation = REQUIRES_NEW`는 새 커넥션을 물어 데드락과 커넥션 풀 고갈을 유발한다

부모 트랜잭션은 커밋되기 전까지 자신의 커넥션을 반납하지 않는데, `REQUIRES_NEW`로 진입한 자식 트랜잭션은 별도의 커넥션을 새로 획득한다. 즉 하나의 요청이 동시에 두 개의 커넥션을 점유하며, 이 패턴이 중첩되거나 반복 호출되면 HikariCP 풀이 순식간에 바닥나고 자기 자신을 기다리는 자가 데드락(self-deadlock)까지 발생한다. 로깅·감사·이벤트 발행처럼 "부모 롤백과 무관하게 커밋해야 하는" 최소 범위에만 사용하고, 가능하면 트랜잭션 밖으로 분리하는 것이 안전하다.

> 💡 **왜 중요한가**: 격리된 커밋을 위한 편리한 옵션처럼 보이지만, 실제로는 커넥션 풀 사이즈보다 트래픽이 낮은 환경에서도 프로덕션 장애의 단골 원인이다.

### `Spring Security`의 `HttpSecurity` 필터 체인은 `securityMatcher`로 분리해야 API/Web 인증 방식이 충돌하지 않는다

하나의 `SecurityFilterChain`에 JWT 인증과 폼 로그인, `/api/**`와 `/admin/**`을 모두 담으면 예외 처리·CSRF·세션 정책이 서로를 덮어써 401이 302로 리다이렉트되거나 CSRF 토큰이 API 요청에 강제되는 버그가 생긴다. `@Bean` 두 개로 필터 체인을 나누고 각각 `securityMatcher("/api/**")`, `securityMatcher("/admin/**")`로 스코프를 지정한 뒤 `@Order`로 우선순위를 명시해야 한다. Spring Security 6부터는 `WebSecurityConfigurerAdapter`가 제거되어 이 다중 체인 방식이 사실상 표준이다.

> 💡 **왜 중요한가**: 인증 방식이 섞인 애플리케이션에서 "왜 API가 로그인 페이지로 리다이렉트되지?"라는 미스터리의 99%는 필터 체인 분리를 안 했기 때문이다.
