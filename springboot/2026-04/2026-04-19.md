### `@ConditionalOnProperty`로 프로퍼티 기반 조건부 빈 등록하기

특정 설정값이 있을 때만 빈을 활성화하고 싶다면 `@ConditionalOnProperty(prefix = "feature.payment", name = "enabled", havingValue = "true")`를 붙이면 된다. `matchIfMissing = true`를 함께 지정하면 프로퍼티가 아예 없을 때도 기본 활성으로 동작해, 환경별로 결제/외부 연동 모듈을 켜고 끌 때 `@Profile`보다 훨씬 세밀한 제어가 가능하다.

```java
@Bean
@ConditionalOnProperty(prefix = "feature.payment", name = "enabled", havingValue = "true")
public PaymentClient paymentClient(PaymentProperties props) {
    return new PaymentClient(props);
}
```

> 💡 **왜 중요한가**: 코드를 손대지 않고 `application.yml` 한 줄로 기능 플래그를 껐다 켤 수 있어, 롤백 부담이 큰 외부 연동/신규 기능에 안전망이 된다.

### `WebTestClient`로 컨트롤러 통합 테스트를 논블로킹으로 검증하기

`@AutoConfigureWebTestClient` + `@SpringBootTest`(또는 `@WebFluxTest`, WebMVC에도 `@AutoConfigureMockMvc`처럼 붙는다) 조합이면 `MockMvc`보다 유연한 fluent API로 상태코드·헤더·JSON 바디를 한 번에 검증할 수 있다. `WebFlux`뿐 아니라 서블릿 스택에서도 동작해서 팀에서 하나의 스타일로 통일 가능하다.

```java
@SpringBootTest
@AutoConfigureWebTestClient
class OrderApiTest {
    @Autowired WebTestClient client;

    @Test void 주문_조회() {
        client.get().uri("/orders/1")
              .exchange()
              .expectStatus().isOk()
              .expectBody().jsonPath("$.status").isEqualTo("PAID");
    }
}
```

> 💡 **왜 중요한가**: `MockMvc`의 장황한 `andExpect` 체이닝 없이 JSONPath·헤더·응답 시간까지 선언적으로 검증돼 통합 테스트 가독성과 유지보수성이 크게 올라간다.
