### RAG Chunking 전략 — "512 토큰씩 자르면 되겠지"라는 안일함, 그리고 계약서 3조 2항의 '단, ~는 제외한다'가 다음 청크로 넘어가 법무 챗봇이 정반대의 답을 자신 있게 내놓는 방식

RAG 파이프라인의 정답률이 안 오르면 다들 임베딩 모델을 바꾸거나 Reranker를 넣는다. 프롬프트도 세 번쯤 갈아엎는다. 그런데 정작 원인의 60~70%는 훨씬 앞단에 있다. **Chunking**. "벡터로 무엇을 만들 것인가"라는, RAG의 가장 조용하고 가장 근본적인 결정.

시니어의 시각에서 chunking은 "전처리"가 아니다. Chunking은 **검색 단위(retrieval unit)의 정의**이고, 이것을 잘못 정의한 시스템은 뒤에 무엇을 붙여도 근본적으로 새는 배다.

#### 1. Chunking이 왜 "invisible bug"인가

Chunking 실패는 다음과 같이 조용히 온다.

- Recall@10을 올려도 정답률이 안 오른다. 정답 문서를 가져오긴 했는데, 정답 **문장**이 청크 경계에서 잘려 반쪽만 있다.
- 임베딩 모델을 OpenAI에서 Cohere로 바꿔봐도 편차가 크지 않다. 벡터 공간이 아니라 **입력 자체**가 오염되어 있으니 당연하다.
- Reranker를 넣으면 오히려 나빠진다. Reranker는 "완결된 문장"을 가정하는데, chunking이 그 가정을 깨고 있다.

가장 무서운 실패 유형은 **"조건절 분리"**다. 계약서의 "단, 다음 각 호의 어느 하나에 해당하는 경우에는 그러하지 아니하다"가 다음 청크로 넘어가면, 첫 청크만 검색된 챗봇은 정반대의 답을 **자신 있게** 낸다.

#### 2. 5가지 Chunking 전략과 그림

```
문서 원본
────────────────────────────────────────────────
"본 계약의 유효기간은 2년으로 한다. 단,
 갱신 통지가 없을 경우 자동 연장된다.
 제3조 (해지) 다음 각 호에 해당하는 경우..."
────────────────────────────────────────────────

① Fixed-size (chunk_size=100, overlap=0)
   ┌──────────────────────┐┌──────────────────────┐
   │본 계약의 유효기간은 2 ││년으로 한다. 단, 갱신 │
   │년으로 한다. 단,      ││통지가 없을 경우 자동 │
   └──────────────────────┘└──────────────────────┘
   ↑ "단, ~"의 조건이 두 청크에 갈라짐 = 재앙

② Recursive Character (LangChain 기본값)
   ["\n\n","\n",". "," "] 순으로 split
   ┌──────────────────────┐┌──────────────────────┐
   │본 계약의 유효기간은  ││단, 갱신 통지가       │
   │2년으로 한다.         ││없을 경우...          │
   └──────────────────────┘└──────────────────────┘
   ↑ 조건절이 앞 문장의 결과라는 관계가 끊김

③ Semantic Chunking (임베딩 거리 기반 split)
   ┌────────────────────────────────────────────┐
   │본 계약의 유효기간은 2년으로 한다.          │
   │단, 갱신 통지가 없을 경우 자동 연장된다.    │
   └────────────────────────────────────────────┘
   ↑ 의미상 연결된 두 문장을 함께 유지

④ Structural Chunking (문서 구조 인식)
   ┌───── 제2조 (계약기간) ─────────────────────┐
   │본 계약의 유효기간은 2년으로 한다. 단, ...  │
   └────────────────────────────────────────────┘
   ┌───── 제3조 (해지) ─────────────────────────┐
   │다음 각 호에 해당하는 경우...               │
   └────────────────────────────────────────────┘
   ↑ 조/항/호 경계를 그대로 청크 경계로 사용

⑤ Late Chunking (2024, Jina AI가 대중화)
   전체 문서를 먼저 통째로 임베딩 → token 벡터를
   나중에 pooling으로 청크화. 문맥이 임베딩에
   이미 반영된 상태로 청크가 만들어짐.
```

각 전략은 **"컨텍스트를 얼마나 보존하느냐 ↔ 인프라 비용/복잡도"** 축에서 서로 다른 위치를 차지한다.

#### 3. 실제로 어떤 회사가 무엇을 쓰는가

| 회사/시스템 | 문서 유형 | 채택한 Chunking | 왜 |
|---|---|---|---|
| **Notion AI** | 사용자 페이지 (block 트리) | **Structural** — Notion block 단위 | 사용자가 이미 heading/toggle/callout으로 논리 구조를 만들어놨다. AI가 그 구조를 다시 부수는 건 자해 |
| **Harvey AI / Casetext** | 법률 문서 (계약/판례) | **Structural + Semantic 하이브리드** — 조/항/호 경계 + 의미 결합 | 조건절 분리가 곧 오답. 법률에서 chunk_size 500은 곧 소송 |
| **GitHub Copilot Chat / Cursor** | 소스코드 | **AST 기반 Structural** — 함수/클래스 단위 | 함수 중간을 자른 청크는 문법적으로 무의미. 임베딩 노이즈만 커짐 |
| **Perplexity** | 웹 페이지 (뉴스/블로그) | **Recursive + 헤딩 인식** | 짧고 다양한 문서. 완벽함보다 스루풋이 중요 |
| **Glean (엔터프라이즈 검색)** | 위키/슬랙/구글독스 | **문서 타입별 다른 전략** — 슬랙 스레드는 스레드 단위, 위키는 heading 단위 | "만능 splitter"를 포기한 순간부터 정답률이 올라가기 시작함 |
| **한 국내 커머스 CS 챗봇 (2025 초 사례)** | FAQ/정책 문서 | **Q&A 페어 chunking** — 질문과 답을 항상 한 청크에 유지 | 예전엔 답만 검색되어 "뭐에 대한 답인지" 모르는 오답이 많았음. 청크 앞에 원 질문을 prepend하는 걸로 recall이 2배 뛰었다고 함 |

공통 패턴이 있다. **"성숙한 팀일수록 문서 타입별로 splitter가 다르다."** 초심자는 하나의 `RecursiveCharacterTextSplitter`로 모든 걸 밀지만, 그 시스템은 반드시 3~6개월 뒤에 갈아엎게 된다.

#### 4. 트레이드오프 정리

| 전략 | Recall | Precision | 구현 비용 | 인덱싱 비용 | 대표 실패 유형 |
|---|---|---|---|---|---|
| Fixed-size | 낮음 | 낮음 | 매우 낮음 | 매우 낮음 | 조건절 분리, 문장 중간 절단 |
| Recursive Character | 중간 | 중간 | 낮음 (LangChain 기본) | 낮음 | 문단 관계 소실, 표/코드에 취약 |
| Semantic | 높음 | 중간~높음 | 중간 (임베딩 호출 필요) | **높음** (문서 1개당 임베딩을 여러 번) | 임계값 튜닝 지옥, 짧은 문서에 오버킬 |
| Structural | 매우 높음 | 높음 | 높음 (문서 타입별 파서 필요) | 중간 | 파서가 못 읽는 문서(스캔 PDF 등)에 무력 |
| Late Chunking | 높음 | 높음 | 중간 | 중간~높음 (long-context 임베딩 모델 필요) | 지원 모델 제한적, 초장문(수십만 토큰)에서 여전히 splitting 필요 |

여기서 시니어가 꼭 짚을 부분: **"인덱싱 비용"은 초기에는 잘 안 보인다.** 문서 1만 건에서 Semantic Chunking을 하면 임베딩 호출이 1만 번이 아니라 **문장 수만큼(수십만 번)** 든다. Pinecone 요금은 저장 요금보다 write throughput에서 먼저 터진다. Chunking 전략은 **인프라 비용 구조**이기도 하다.

#### 5. 시니어 관점: 언제 무엇을 쓸까

```
문서 타입이 무엇인가?
│
├─ 코드 → AST 기반 Structural (함수/클래스 단위)
│        예외: README/주석 위주면 Recursive
│
├─ 법률/의료/금융 규정 → Structural + 조건절 보호
│        · 조/항/호 경계를 청크 경계로
│        · "단,", "다만,", "except", "however" 로 시작하는
│          청크는 앞 청크와 강제 병합
│        · 청크 앞에 상위 조항명(제3조 (해지) 등)을 prepend
│
├─ Q&A / FAQ / CS 로그 → Q&A pair chunking
│        질문·답변을 절대 분리하지 마라
│
├─ 위키/노트/문서 → Structural (heading 기반)
│        + 헤딩 경로(H1 > H2 > H3)를 청크 앞에 prepend
│        이걸 "Contextual Retrieval" 이라고도 함 (Anthropic, 2024)
│
├─ 뉴스/블로그/웹 → Recursive Character (~800 토큰, overlap 100)
│        정답률보다 스루풋이 우선
│
└─ 이질적/구조 없는 대량 문서 → Semantic Chunking
         단, 오프라인 인덱싱 비용을 미리 계산할 것
```

**쓰지 말아야 할 때도 있다.**

- **문서가 1천 건 이하**이고 각 문서가 짧다면 chunking 자체를 고민할 필요가 없다. 문서 전체를 하나의 청크로 두고 long-context LLM에 통째로 넣는 게 더 정확하다. Chunking은 검색이 필요할 만큼 문서가 많을 때만 의미가 있다.
- **문서가 매일 갈아엎어지는** 환경(예: 실시간 로그, 티켓)에서 Semantic Chunking을 쓰면 재인덱싱 비용에 파묻힌다. 이럴 땐 Fixed-size + overlap이 오히려 합리적이다.
- **"모든 문서에 하나의 splitter"** 를 강요받는 상황이라면, 그건 chunking 문제가 아니라 조직 문제다. 문서 타입 분류부터 하는 게 순서다.

#### 6. 자주 놓치는 것들

1. **Chunk 앞에 메타데이터를 prepend하라.** "제3조 (해지) — 다음 각 호에..." 처럼 청크가 어디에서 왔는지가 임베딩에 포함되어야 한다. Anthropic이 2024년에 발표한 Contextual Retrieval은 이걸 LLM으로 자동 생성하는 방식이었다 (recall 실패율 -35%).
2. **Overlap은 만병통치약이 아니다.** overlap 200이라고 조건절 분리가 해결되지 않는다. 오히려 중복된 청크가 top-k를 잠식해서 다양성만 떨어뜨린다.
3. **Chunking을 eval 대상으로 삼아라.** "chunking 전략 A vs B"를 동일한 임베딩·검색기 조건에서 정답률로 비교해야 한다. 프롬프트만 A/B 하는 팀은 이미 낡았다.
4. **표(table)와 코드 블록은 절대 자르지 마라.** 이 두 종류는 무조건 원자적 단위로 두고, 크기가 크면 별도 인덱스로 분리하는 게 낫다.

#### 7. 안티패턴 3종

- **"chunk_size=1000, overlap=200"을 프로덕션 값으로 그대로 두기.** 이건 LangChain 튜토리얼의 예제 값이지, 당신의 문서에 대한 정답이 아니다.
- **문서 종류에 관계없이 하나의 splitter 사용.** 위에서 봤듯, 성숙한 시스템은 반드시 문서 타입별로 다르다.
- **Chunking 결과를 사람이 한 번도 안 본다.** 인덱싱 파이프라인 끝에 "랜덤 20개 청크를 뽑아 사람이 읽어보는" 스텝을 넣어라. 문장 중간에서 잘리는 게 눈에 바로 보인다.

> 💡 **왜 중요한가**: RAG의 정답률은 임베딩 모델이 아니라 "무엇을 벡터로 만들 것인가"로 먼저 결정되고, chunking은 그 결정의 이름이다.
