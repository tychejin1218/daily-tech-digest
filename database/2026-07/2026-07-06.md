### PostgreSQL `CLUSTER` 명령어 — 물리적 행 순서를 인덱스에 맞춰 재배치해 범위 스캔 I/O 줄이기

`CLUSTER table_name USING index_name`은 지정한 인덱스 순서대로 테이블의 물리적 행 배치를 재정렬한다. 시계열 데이터나 특정 컬럼 기준으로 자주 범위 조회하는 테이블에서 디스크 페이지 접근을 순차 읽기로 바꿔 I/O가 극적으로 줄어든다. 단, 실행 중 배타 락이 걸리므로 유지보수 창에서 수행하고, 이후 INSERT/UPDATE로 다시 흐트러지므로 주기적 재실행이 필요하다.

```sql
CREATE INDEX idx_orders_created_at ON orders(created_at);
CLUSTER orders USING idx_orders_created_at;

-- 이후 클러스터링된 인덱스 정보만으로 재실행
CLUSTER orders;
```

> 💡 **왜 중요한가**: 논리적으로 같은 쿼리라도 물리적 행 배치에 따라 실제 디스크 I/O 비용이 수십 배 차이 날 수 있다.

### MySQL `EXPLAIN ANALYZE` — 예상 실행 계획이 아닌 실제 실행 시간·행수를 측정해 병목 짚기

일반 `EXPLAIN`은 옵티마이저가 예측한 계획만 보여주지만, `EXPLAIN ANALYZE`(MySQL 8.0.18+)는 쿼리를 실제로 실행하며 각 단계의 실측 시간과 처리 행수를 반환한다. 예측 행수와 실제 행수가 크게 벌어지는 노드가 병목의 원인인 경우가 많고, 통계 갱신이나 인덱스 재설계 판단의 근거가 된다.

```sql
EXPLAIN ANALYZE
SELECT o.id, u.name
FROM orders o JOIN users u ON u.id = o.user_id
WHERE o.status = 'PAID' AND o.created_at >= '2026-07-01';

-- actual time=0.021..145.3 rows=48210 loops=1
-- (예측 rows=1200 vs 실제 rows=48210 → 통계 부정확 의심)
```

> 💡 **왜 중요한가**: "예측"이 아닌 "실측"을 봐야 옵티마이저가 어디서 잘못 판단했는지 정확히 진단할 수 있다.
