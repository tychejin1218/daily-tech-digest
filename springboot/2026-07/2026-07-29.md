### `@Async` 메서드는 같은 클래스 내부 호출 시 프록시를 거치지 않아 비동기로 실행되지 않는다

Spring의 `@Async`는 `@Transactional`과 마찬가지로 프록시 기반으로 동작한다. 같은 클래스 안에서 `this.someAsyncMethod()`를 호출하면 프록시가 아닌 실제 객체를 직접 호출하기 때문에 비동기 처리가 무시되고 호출 스레드에서 동기 실행된다. 해결하려면 별도 빈으로 분리하거나 `ApplicationContext`에서 자기 자신을 다시 주입받아 호출해야 한다.

```java
@Service
public class OrderService {
    @Async
    public void sendNotification() { ... }  // ❌ 내부 호출 시 동기 실행

    public void placeOrder() {
        this.sendNotification();  // 프록시를 우회 → @Async 무시
    }
}
```

> 💡 **왜 중요한가**: 로그에는 아무 에러도 안 뜨지만 비동기가 아니라 요청 스레드를 블로킹하고 있어, 트래픽이 몰리면 커넥션 풀이 조용히 고갈된다.

---

### `WebClient`는 `RestTemplate`과 달리 기본 timeout이 없어 명시적으로 지정하지 않으면 무한 대기한다

`RestTemplate`은 기본 커넥션/리드 타임아웃 설정을 갖지 않지만 인프라 레벨(OS, LB)에서 어느 정도 잘리는 경우가 많다. 반면 `WebClient`(Reactor Netty 기반)는 명시적으로 지정하지 않으면 응답이 올 때까지 무한 대기하므로, 외부 API가 응답하지 않으면 이벤트 루프 스레드가 모두 점유되어 서비스 전체가 멈춘다. `HttpClient.responseTimeout()`과 `ConnectionProvider`의 acquire timeout을 반드시 설정해야 한다.

```java
HttpClient httpClient = HttpClient.create()
    .responseTimeout(Duration.ofSeconds(3))
    .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 2000);

WebClient webClient = WebClient.builder()
    .clientConnector(new ReactorClientHttpConnector(httpClient))
    .build();
```

> 💡 **왜 중요한가**: 장애 전파의 가장 흔한 경로는 "타임아웃 미설정 → 스레드 점유 → 커넥션 풀 고갈 → 전체 장애"이고, `WebClient`는 논블로킹이라는 이유로 이 위험을 더 과소평가한다.
