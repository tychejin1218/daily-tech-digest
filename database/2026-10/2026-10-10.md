### Database Tip 1: MySQL `GTID`(Global Transaction ID) 기반 복제 — 바이너리 로그 파일명과 포지션을 외우던 시대의 종말

전통적인 MySQL 복제는 "`mysql-bin.000042`의 `offset 15728640`부터 재생해줘" 같은 **파일+위치 좌표**로 작동했고, 페일오버 시 새 마스터의 좌표를 수작업으로 계산하다 데이터 유실·중복이 터지기 일쑤였다. GTID는 모든 트랜잭션에 `server_uuid:transaction_id`라는 **클러스터 전역 고유 ID**를 부여해, 슬레이브가 "나는 어디까지 적용했는가"를 좌표가 아닌 **ID 집합**으로 추적하게 만든다. 그 결과 `CHANGE MASTER TO MASTER_AUTO_POSITION=1` 한 줄로 페일오버가 끝나고, Orchestrator·MHA 같은 자동화 도구가 비로소 "안전하게" 작동한다.

```
[전통 복제]                        [GTID 복제]
Slave: "파일 X의 Y바이트부터"      Slave: "UUID-A:1-9999까지 적용 완료"
  ↓ 마스터 교체                       ↓ 마스터 교체
새 마스터의 Y바이트는 어디?        "UUID-A:10000부터 주세요" (끝)
  ↓                                   ↓
mysqlbinlog으로 추적 (지옥)       MASTER_AUTO_POSITION=1 (천국)
```

실무에서는 `gtid_mode=ON`, `enforce_gtid_consistency=ON`을 켜되, **CREATE TABLE ... SELECT 같은 비결정적 구문이 금지**된다는 점을 반드시 알아야 한다(트랜잭션 하나에 DDL+DML이 섞여 GTID 할당 규칙을 깨기 때문). 또한 `gtid_executed` 테이블이 **슬레이브마다 다르게 쌓이는 상황**(예: 과거에 수동으로 데이터를 넣었던 경우)에서는 `RESET MASTER`로 초기화하지 않으면 복제가 영원히 꼬이므로, 신규 슬레이브는 반드시 **백업 복원 후 `gtid_purged` 세팅**이라는 공식을 지켜야 한다.

> 💡 **왜 중요한가**: 자동 페일오버의 전제 조건이다. GTID 없이 HA를 논하는 건 "장애 나면 DBA가 새벽에 깨서 바이너리 로그 좌표를 손으로 맞추겠다"는 선언과 같다.

### Database Tip 2: PostgreSQL `pg_stat_statements` — "느린 쿼리 하나"가 아니라 "전체 쿼리 비용의 파레토 분포"를 보는 관측의 진짜 출발점

슬로우 쿼리 로그는 **임계값(예: 1초)을 넘긴 개별 쿼리**만 잡아내지만, 실제 DB를 무릎 꿇리는 범인은 "0.05초짜리를 초당 2만 번 때리는 쿼리"인 경우가 압도적으로 많다. `pg_stat_statements`는 쿼리를 **파라미터만 뺀 템플릿(`SELECT * FROM users WHERE id = $1`) 단위로 정규화**해 `calls`, `total_exec_time`, `mean_exec_time`, `rows`, `shared_blks_hit/read`를 누적 집계하며, 이 관점에서 보면 "어떤 쿼리 패턴이 DB 전체 CPU의 몇 %를 먹고 있는지"가 **단 한 번의 SELECT**로 드러난다.

```sql
-- 전체 실행 시간의 상위 10개 쿼리 패턴
SELECT
  query,
  calls,
  total_exec_time,
  mean_exec_time,
  (100 * total_exec_time / SUM(total_exec_time) OVER ())::numeric(5,2) AS pct
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

-- 실행 결과 예시:
-- query                              | calls   | total_time | pct
-- SELECT * FROM orders WHERE user_id | 892431  | 48230s     | 42.3%  ← 범인
-- SELECT COUNT(*) FROM audit_logs    | 12      | 31200s     | 27.4%  ← 느리지만 횟수 적음
```

여기서 핵심 트레이드오프: `pg_stat_statements.track = all`로 설정하면 **PL/pgSQL 내부 쿼리까지** 집계되어 애플리케이션이 호출하는 함수의 내부 병목까지 드러나지만, 쿼리 종류가 수만 개로 늘어나면 `pg_stat_statements.max`(기본 5000)에 걸려 **낡은 통계가 축출**되기 시작한다. 보통 운영 환경에서는 `max=10000`, `track=top`(기본값)으로 두고, **매일 자정에 `pg_stat_statements_reset()`을 돌려 "하루치 분포"로 리셋**한 뒤 Datadog·Grafana에 수집하는 패턴이 안정적이다. "느린 쿼리"가 아니라 "**비싼 쿼리**"를 찾는 관점의 전환이, 쿼리 튜닝의 ROI를 10배 이상 바꾼다.

> 💡 **왜 중요한가**: 튜닝 대상을 잘못 고르면 아무리 열심히 최적화해도 전체 성능은 안 바뀐다. 42%를 먹는 쿼리를 2배 빠르게 하는 게, 0.1%를 100배 빠르게 하는 것보다 압도적으로 가치 있다.
