### ReAct vs Plan-and-Execute — "Agent는 LLM + 도구 루프면 된다"는 순진함, 그리고 8번째 iteration에서 예산을 조용히 태우는 방식

---

#### 1. 오해의 시작: "Agent = while(not_done) { llm.call() }"

주니어가 처음 Agent를 만들 때 십중팔구 이렇게 짠다.

```python
while not done:
    thought = llm.think(context)
    action = llm.decide_tool(thought)
    observation = execute(action)
    context += [thought, action, observation]
    done = llm.is_finished(context)
```

이게 그 유명한 **ReAct(Reasoning + Acting)** 패턴이다. Yao et al. 2022 논문 하나로 업계 표준이 됐고, LangChain의 `AgentExecutor`가 기본으로 채택했다.

문제는 이걸 프로덕션에 올렸을 때다. 3개월 후 재무팀이 청구서를 들고 온다. "우리 이 챗봇 하나에 월 $47,000 쓰고 있는데 이거 맞아?"

로그를 열어보면 이런 게 보인다.

```
[Turn 1] Thought: 사용자가 재고 조회를 원함. inventory_api 호출.
[Turn 2] Observation: 500 error. Thought: 다시 시도해보자. inventory_api 호출.
[Turn 3] Observation: 500 error. Thought: DB에서 직접 조회. db_query 호출.
[Turn 4] Observation: permission denied. Thought: inventory_api 호출.
[Turn 5] Observation: 500 error. Thought: ...
...
[Turn 23] Thought: 사용자가 재고 조회를 원함. inventory_api 호출.
```

**ReAct가 무한 루프에 빠진 것이다.** LLM은 "직전 실패"만 보고 반응하기 때문에, 자기가 5분 전에 이미 시도해서 실패한 경로를 태연히 다시 시도한다. 컨텍스트에 실패 기록이 쌓일수록 판단은 더 흐려진다.

---

#### 2. ReAct의 3가지 구조적 결함

시니어 관점에서 ReAct의 문제는 단순히 "무한 루프 방지 코드가 없다"가 아니다. **구조 자체의 한계**다.

**(1) 근시안 (Myopic Reasoning)**
매 스텝마다 "지금 뭐 할까"만 결정한다. 전체 목표를 향한 최단 경로를 그리지 못한다. 인간 개발자라면 "재고 조회 → 없으면 창고 API → 그래도 없으면 CS 에스컬레이션"이라는 트리를 5초 만에 그리고 시작하는데, ReAct 에이전트는 매번 처음부터 다시 생각한다.

**(2) 컨텍스트 오염 (Context Rot)**
Turn이 늘어날수록 실패한 시도의 로그가 컨텍스트에 쌓인다. 30 Turn쯤 되면 프롬프트가 8k 토큰을 넘고, LLM은 "지금 뭐 하려던 거였지?"를 잊는다. Claude 4.7이 1M 컨텍스트라는 건 답이 아니다. **긴 컨텍스트는 attention의 품질을 떨어뜨린다** (lost-in-the-middle 문제, Liu et al. 2023).

**(3) 예산 예측 불가 (Unbounded Cost)**
Turn 수의 상한이 없다. "max_iterations=15"를 걸어도 그건 안전장치일 뿐 예산 계획이 아니다. 재무팀에 "이 요청은 얼마 들죠?"에 답할 수 없다.

---

#### 3. Plan-and-Execute의 반격

2023년 LangChain은 [Plan-and-Solve](https://arxiv.org/abs/2305.04091) 논문을 기반으로 새 패턴을 도입한다.

```
Step 1 (Planner LLM, 강한 모델):
  전체 계획을 한 번에 세운다. Task graph 반환.

Step 2 (Executor LLM, 저렴한 모델):
  계획의 각 노드를 실행. 실행 결과만 다음 노드에 전달.

Step 3 (Replanner, 조건부):
  실행이 실패하거나 새 정보가 들어오면 재계획.
```

핵심은 **"생각"과 "실행"을 분리했다는 점**이다.

```
┌─────────────────────────────────────────────────────────────┐
│                     ReAct (기존)                             │
│                                                              │
│   ┌────────┐ Thought  ┌────────┐ Action ┌──────────┐         │
│   │ LLM(강)│─────────>│ LLM(강)│───────>│ Tool     │         │
│   └────────┘          └────────┘        └──────────┘         │
│        ▲                                     │               │
│        └───────── Observation ───────────────┘               │
│                                                              │
│   매 Turn마다 강한(비싼) LLM 호출. 상한 없음.                  │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│                Plan-and-Execute (권장)                       │
│                                                              │
│   ┌──────────┐         ┌──────────────┐                      │
│   │ Planner  │────────>│  Task Graph  │                      │
│   │ LLM (강) │         │  (DAG)       │                      │
│   └──────────┘         └──────┬───────┘                      │
│    한 번 호출                   │                             │
│                                ▼                             │
│                    ┌───────────────────────┐                 │
│                    │ Executor LLM (저렴)   │                 │
│                    │  + Tool 병렬 실행     │                 │
│                    └───────────┬───────────┘                 │
│                                │                             │
│                                ▼ 실패/신정보 발생 시          │
│                    ┌───────────────────────┐                 │
│                    │ Replanner (조건부)    │                 │
│                    └───────────────────────┘                 │
└─────────────────────────────────────────────────────────────┘
```

이 구조의 이점:
- **Planner는 GPT-5.4 / Claude Opus 4.7 같은 강한 모델**을 한 번만 쓴다.
- **Executor는 Haiku / GPT-5.4-mini** 같은 저렴한 모델로 스텝을 처리한다.
- **Task graph가 있으니 병렬화 가능** — 독립적인 노드는 동시 실행.
- **예산 예측 가능** — 계획 단계에서 노드 수가 확정된다.

실측 사례 하나. 한 사내 챗봇 팀이 ReAct → Plan-Execute로 전환하면서:
- 평균 응답 시간 22초 → 8초 (병렬화 덕분)
- 요청당 비용 $0.14 → $0.03 (Executor에 저렴 모델)
- P99 Turn 수 40+ → 계획 노드 수 상한 12

---

#### 4. 그런데 Plan-and-Execute도 만능이 아니다

"그럼 무조건 Plan-and-Execute 쓰면 되겠네?" 아니다. **계획을 세우려면 문제 공간이 예측 가능해야 한다.**

Planner가 실패하는 시나리오:
- **탐색형 태스크**: "이 코드베이스에서 성능 병목 찾아줘" — 뭘 찾을지는 찾아봐야 안다.
- **대화형 태스크**: "사용자의 다음 반응"이 계획의 입력인데, 아직 오지 않았다.
- **환경 상호작용**: 브라우저 자동화처럼 매 스텝마다 DOM 상태가 예측 불가한 경우.

Cognition Labs의 Devin이 Plan-first 접근을 밀지만, 정작 복잡한 디버깅 태스크에서는 초기 계획을 자주 폐기하고 재계획한다. 재계획 비용이 눌러쓰면 결국 ReAct와 비슷해진다.

Anthropic의 Claude Computer Use는 이 문제를 우회한다. **"작은 ReAct 루프를 큰 Plan 노드 안에서 돌린다"** — 하이브리드.

```
Top-level Plan:
  1. 사용자 로그인 페이지 열기
  2. 이메일 입력      ┐
  3. 비밀번호 입력    ├── 각 노드는 ReAct 미니 루프
  4. 제출 버튼 클릭   ┘
  5. 대시보드 확인
```

각 노드 내부는 "스크린샷 → 좌표 계산 → 클릭" 같은 좁은 ReAct 루프. 큰 흐름은 Plan.

#### 5. 트레이드오프 매트릭스 (시니어의 결정 표)

| 상황 | ReAct | Plan-and-Execute | 하이브리드 |
|---|---|---|---|
| 태스크 스텝 수 예측 가능? | ✗ 무관 | ✓ 필요 | △ Plan 레벨만 |
| 스텝 간 의존성 강한가? | △ | ✓ (DAG로 표현) | ✓ |
| 병렬 실행 이득 있나? | ✗ 어려움 | ✓ 자연스러움 | ✓ |
| 예산 상한 필요? | ✗ (안전장치만) | ✓ | ✓ |
| 동적 환경(브라우저/게임)? | ✓ 적합 | ✗ 계획이 무의미 | ✓ 부분 적용 |
| 팀 원격 디버깅 필요? | ✗ Turn 로그 지옥 | ✓ Task graph 시각화 | ✓ |
| 프로토타입 속도 | ✓ 3시간 | ✗ 3일 | ✗ 1주 |

#### 6. 언제 어떤 걸 쓰는가 — 결정 트리

**ReAct를 써야 하는 경우**
- 프로토타입/PoC 단계 (구현 속도가 최우선)
- 태스크가 진짜로 예측 불가 (탐색적 리서치, 오픈엔드 대화)
- Turn당 비용이 무시할 만한 소규모 트래픽
- 도구가 2~3개 이하로 단순한 경우

**Plan-and-Execute를 써야 하는 경우**
- 프로덕션 트래픽, 예산 예측 필수
- 태스크가 워크플로우로 표현 가능 (RAG 파이프라인, 데이터 처리)
- 병렬화 가능한 독립 스텝이 다수
- 관찰성/재현성이 중요 (규제 산업, 감사 로그)
- Planner 비용이 Executor 절감으로 상쇄되는 요청량

**하이브리드로 가야 하는 경우**
- 큰 흐름은 정해져 있지만 각 스텝 내부가 동적 (Computer Use, 코딩 에이전트)
- Plan 노드를 "sub-agent" 단위로 위임 가능한 경우
- 실패 복구 로직이 노드별로 다른 경우

**절대 쓰지 말아야 하는 것**
- 순수 ReAct + max_iterations=100 조합: 예산 폭발 확정
- Plan-Execute + 매 스텝마다 Replan: Plan의 이점이 다 사라진다
- Multi-Agent Orchestration을 이 위에 얹기: [[multi-agent-orchestration]]에서 다뤘듯 컨텍스트 오염 폭탄

#### 7. 실제 사례

**LangChain (Plan-and-Execute 채택)**
2023년 `AgentExecutor`(ReAct)에서 `create_plan_and_execute_agent`로 마이그레이션 가이드를 냈다. 이유: 프로덕션 사용자들이 "Turn 수 예측 안 되면 못 쓴다"는 피드백을 쏟아냈다.

**OpenAI Assistants API v2 → Responses API**
초기 Assistants는 ReAct 기반이었다. 2024년 Responses API로 넘어오면서 tool call을 **명시적 병렬 배치**로 반환하는 구조로 바꿨다. 이건 사실상 "미니 Plan"이다.

**Devin (Cognition Labs)**
Planning-first 코딩 에이전트. 처음에 전체 계획을 세우고 각 스텝을 실행. 실패 시 Replan. 초기 계획 품질이 성능의 90%를 좌우한다고 CEO Scott Wu가 인터뷰에서 언급.

**AutoGPT (반면교사)**
순수 ReAct의 대표적 실패 사례. 2023년 GitHub 스타 15만 개를 넘겼지만, 실사용자 대부분이 "돈만 태우고 결과 없음"을 보고했다. 원인: 무한 루프 + 컨텍스트 오염 + 예산 상한 없음.

#### 8. 다음 단계 힌트

Plan-and-Execute를 도입하면 자연스럽게 다음 질문이 나온다:
- Planner가 참조할 "우리 시스템의 도구 카탈로그"는 어디에 두는가? → Tool Registry 패턴
- 스텝 간 상태를 어디에 저장하나? → Agent Memory (short/long-term)
- Replan 트리거는 누가 결정하나? → Supervisor 패턴

이건 [[agent-memory-patterns]], [[tool-registry-design]]에서 다룰 주제다.

---

> 💡 **왜 중요한가**: "Agent = LLM + 도구 루프"라는 게으른 정의는 프로토타입에서만 통하고, 프로덕션에서는 예산·지연·디버깅 세 축에서 동시에 무너진다 — 시니어의 일은 어떤 태스크에 ReAct를, 어떤 태스크에 Plan-and-Execute를, 어떤 경계에서 둘을 겹치는지 결정하는 것이다.
