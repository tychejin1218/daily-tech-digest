### PostgreSQL `LATERAL JOIN` — 행마다 서브쿼리를 다시 실행해 "그룹별 Top-N"을 우아하게 뽑기
일반 서브쿼리는 바깥쪽 행을 참조할 수 없지만 `LATERAL`을 붙이면 좌측 테이블의 각 행을 "변수"로 받아 서브쿼리를 매 행마다 평가할 수 있습니다. 사용자별 최근 주문 3건, 카테고리별 베스트셀러처럼 윈도우 함수 + `row_number()` 패턴으로 풀면 전체 테이블을 정렬해야 하지만, `LATERAL` + `LIMIT`은 각 사용자에 대해 인덱스로 상위 N개만 찍어 가져옵니다.

```sql
SELECT u.id, recent.*
FROM users u
LEFT JOIN LATERAL (
    SELECT id, created_at, total
    FROM orders o
    WHERE o.user_id = u.id          -- 바깥 u 참조 (LATERAL이라서 가능)
    ORDER BY o.created_at DESC
    LIMIT 3
) recent ON true;
```

> 💡 **왜 중요한가**: "그룹별 상위 N"은 윈도우 함수로 풀면 풀스캔이지만, `LATERAL` + 인덱스(`user_id, created_at DESC`)면 사용자 수만큼만 인덱스를 타고 들어가 수십~수백 배 빠릅니다.

### PostgreSQL Long-Running Transaction과 `xmin horizon` — 긴 트랜잭션 하나가 모든 테이블의 autovacuum을 마비시키는 현상
PostgreSQL MVCC는 UPDATE/DELETE된 행을 즉시 지우지 않고 dead tuple로 남겨두며, autovacuum이 "모든 활성 트랜잭션보다 오래된 dead tuple"만 회수합니다. 즉 어디선가 `BEGIN`만 해두고 30분째 idle in transaction 상태인 세션이 하나만 있어도 그 시점 이후 생긴 dead tuple은 **다른 테이블 것까지 전부** 청소가 불가능해 bloat가 쌓이고 쿼리가 점점 느려집니다. `pg_stat_activity`에서 `state = 'idle in transaction'`과 `xact_start`를 모니터링하고, `idle_in_transaction_session_timeout`으로 자동 종료를 거는 것이 필수입니다.

```sql
-- 범인 찾기: 오래된 트랜잭션 + xmin horizon 확인
SELECT pid, usename, state, xact_start, query
FROM pg_stat_activity
WHERE state IN ('idle in transaction', 'active')
ORDER BY xact_start NULLS LAST;

-- 예방: 5분 이상 idle in transaction 세션은 자동 종료
ALTER SYSTEM SET idle_in_transaction_session_timeout = '5min';
```

> 💡 **왜 중요한가**: 운영 중 갑자기 모든 쿼리가 느려지고 디스크가 부풀어오를 때 90%는 트랜잭션을 안 닫고 가버린 배치/리포트 잡 하나가 원인입니다 — 한 트랜잭션의 수명은 곧 클러스터 전체의 청소 가능 시점입니다.
