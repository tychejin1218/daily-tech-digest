### `@Valid`는 중첩 객체를 자동으로 검증하지 않는다 — 필드에도 `@Valid`를 다시 붙여야 한다
컨트롤러에서 `@RequestBody @Valid UserDto` 로 최상위 객체는 검증되지만, `UserDto` 안의 `AddressDto` 필드는 검증에서 제외된다. 중첩 필드 선언부에 `@Valid`를 명시적으로 붙여야 검증이 재귀적으로 전파된다. `@NotNull`만 있고 `@Valid`가 없으면 “필드가 `null`인지”만 확인하고 내부의 `@NotBlank`·`@Size` 같은 제약은 조용히 무시된다.

```java
public class UserDto {
    @NotBlank private String name;

    @NotNull                 // Address 자체가 null인지만 검증
    // @Valid 없음 → 아래 필드 제약은 무시됨
    private AddressDto address;
}

public class AddressDto {
    @NotBlank private String city;   // 검증되지 않음!
}
```

> 💡 **왜 중요한가**: 검증이 통과했다고 믿었지만, 중첩 필드는 아무도 검사하지 않은 채 DB에 저장되어 뒤늦게 데이터 오염으로 발견된다.

### `@RestControllerAdvice`는 필터에서 던진 예외를 잡지 못한다 — `DispatcherServlet` 안쪽에서만 동작한다
`@ExceptionHandler` 기반의 전역 예외 처리는 `DispatcherServlet`이 핸들러를 실행한 이후에만 활성화된다. 즉, `Servlet Filter`, `Spring Security` 필터 체인, 서블릿 컨테이너 자체에서 발생한 예외는 `@RestControllerAdvice`가 절대 잡지 못한다. JWT 인증 필터에서 던진 예외가 프로젝트에서 정의한 JSON 포맷이 아니라 톰캣 기본 HTML 에러 페이지로 나오는 이유가 바로 이것이며, 이를 통일하려면 `HandlerExceptionResolver`를 필터 안에서 직접 호출하거나 `ErrorController` / `AuthenticationEntryPoint`를 별도로 구현해야 한다.

```
[Client]
   ↓
[Servlet Filter] ─── 예외 발생 → @RestControllerAdvice 못 잡음 ✗
   ↓
[Spring Security Filter] ─── 예외 발생 → 못 잡음 ✗
   ↓
[DispatcherServlet]
   ↓
[HandlerInterceptor.preHandle] ─── 예외 발생 → 못 잡음 ✗
   ↓
[Controller] ─── 예외 발생 → @RestControllerAdvice 잡음 ✓
```

> 💡 **왜 중요한가**: 예외 응답 포맷이 컨트롤러 예외와 인증 예외에서 서로 달라지는 대부분의 원인이며, 프론트엔드 에러 파싱 로직이 조건 분기로 지저분해지는 근본 이유다.
