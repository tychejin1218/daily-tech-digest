### Spring Boot의 `@ConfigurationProperties`는 **`@Value`보다 강력하지만, 바인딩 실패를 조용히 삼킨다** — 그리고 불변 객체(`record`)와 함께 쓸 때 생성자 바인딩이 기본이 아니다

`@ConfigurationProperties`는 중첩된 YAML 구조를 타입 안전하게 매핑하고 IDE 자동완성까지 지원하지만, 바인딩 실패 시 기본 설정으로는 로그 한 줄 없이 `null`이나 기본값으로 조용히 넘어간다. 반드시 `@Validated`와 JSR-303 어노테이션(`@NotNull`, `@Min` 등)을 함께 걸어야 애플리케이션 시작 시점에 `BindException`으로 터뜨릴 수 있다. 또한 `record`나 불변 객체로 선언하면 setter가 없어 JavaBean 바인딩이 실패하므로, `@ConstructorBinding`을 명시하거나 Spring Boot 3.x 이상에서는 `record`일 때 자동으로 생성자 바인딩이 적용된다는 점을 알아야 한다.

```java
@ConfigurationProperties(prefix = "payment")
@Validated
public record PaymentConfig(
    @NotBlank String apiKey,
    @Min(100) int timeoutMs,
    @NotNull RetryPolicy retry
) {}
```

```
┌─────────────────────────────────────────────┐
│  application.yml                            │
│  payment:                                   │
│    api-key: ""      ← 빈 문자열              │
│    timeout-ms: 50   ← @Min(100) 위반         │
└─────────────────┬───────────────────────────┘
                  │
         ┌────────▼────────┐
         │ @Validated 없음  │ → null/0으로 바인딩, 런타임에 NPE 터짐 💣
         └─────────────────┘
         ┌────────▼────────┐
         │ @Validated 있음  │ → 시작 시점에 BindValidationException ✅
         └─────────────────┘
```

**실제 사례**: 결제 모듈의 `apiKey`가 `application-prod.yml`에서 오타(`api-key` → `apikey`)로 바인딩 실패했는데, `@Validated`가 없어서 `null`로 기동되었다. 첫 결제 요청에서 `NullPointerException`이 터지고 나서야 발견했다 — 설정 오류는 **배포 시점(fail-fast)에 터져야지 트래픽 시점에 터지면 안 된다**.

**트레이드오프**:
- `@Value`: 단일 값, 빠른 선언, SpEL 지원. 하지만 타입 안전성 ↓, 리팩토링 ↓
- `@ConfigurationProperties`: 구조화된 설정, 검증 가능, 메타데이터 생성. 하지만 보일러플레이트 ↑

> 💡 **왜 중요한가**: "설정 오류는 반드시 기동 시점에 터져야 한다"는 fail-fast 원칙을 지키지 못하면, 프로덕션에서 사용자 트래픽을 받고 나서야 문제를 발견하게 된다.

### Spring Boot의 `@Async`는 **같은 클래스 내부 호출에서 동작하지 않는다** — 그리고 반환 타입이 `void`면 예외가 조용히 사라진다

`@Async`는 AOP 프록시 기반으로 동작하므로 Self-invocation(같은 클래스 내부 메서드 호출) 시 프록시를 거치지 않아 비동기 실행이 무시된다. 더 위험한 건 반환 타입이 `void`일 때 발생한 예외가 호출자에게 전파되지 않고 기본 핸들러에서 로그조차 남지 않을 수 있다는 점이다. 반드시 `CompletableFuture<T>`를 반환하거나 `AsyncUncaughtExceptionHandler`를 등록해야 한다.

```java
@Service
public class NotificationService {

    public void sendOrderConfirmation(Order order) {
        logOrder(order);
        sendEmail(order);  // ❌ 내부 호출 — @Async 무시됨, 동기 실행
    }

    @Async
    public void sendEmail(Order order) {
        throw new RuntimeException("SMTP 서버 다운"); // 🤐 조용히 사라짐
    }
}
```

```
❌ 내부 호출 (Self-invocation)
┌──────────────────────────────────┐
│  NotificationService (실제 객체)  │
│  ┌────────────────────────────┐  │
│  │ sendOrderConfirmation()    │  │
│  │   └─> this.sendEmail()     │  │ ← 프록시 안 거침
│  │       (동기 실행)            │  │
│  └────────────────────────────┘  │
└──────────────────────────────────┘

✅ 외부 호출
Client → [Proxy] → NotificationService.sendEmail()
          ↓
    TaskExecutor로 디스패치 → 별도 스레드에서 비동기 실행
```

**해결 방법**:
1. **Self-injection**: `@Autowired private NotificationService self;` 후 `self.sendEmail(order)` 호출
2. **AspectJ 모드**: `@EnableAsync(mode = AdviceMode.ASPECTJ)` + 컴파일 타임 위빙 (복잡도 ↑)
3. **별도 Bean 분리**: `EmailService`로 책임 분리 (가장 권장 — SRP 원칙에도 부합)
4. **예외 처리**: `AsyncUncaughtExceptionHandler` 구현 + `AsyncConfigurer`에 등록

```java
@Configuration
@EnableAsync
public class AsyncConfig implements AsyncConfigurer {
    @Override
    public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
        return (ex, method, params) ->
            log.error("Async 메서드 실패: {} {}", method.getName(), ex.getMessage(), ex);
    }
}
```

**실제 사례**: 주문 확인 이메일이 "가끔 안 간다"는 CS가 올라와 조사했더니, SMTP 커넥션 타임아웃이 터지고 있었는데 `@Async void`라 로그에도 안 남고 모니터링 지표에도 안 잡혔다. `CompletableFuture<Void>`로 바꾸고 `.exceptionally()`로 핸들링하자마자 숨어있던 실패율이 드러났다.

**트레이드오프**: `@Async`의 간결함은 좋지만, **"비동기 = 예외가 사라질 수 있다"**는 걸 팀 전체가 인식해야 한다. 메시지 큐(RabbitMQ, Kafka)로 분리하는 게 더 안전한 경우가 많다.

> 💡 **왜 중요한가**: 비동기 작업의 실패는 "조용한 실패(silent failure)"가 되기 쉽고, 이는 디버깅할 수 없는 장애를 만든다 — 비동기를 쓰려면 반드시 예외 전파 경로를 설계해야 한다.
