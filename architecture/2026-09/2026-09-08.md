### Hybrid Search (Vector + Keyword) — "Semantic Search가 다 잡는다"는 순진함, 그리고 상품코드 `SKU-A2K9-BLK`를 검색한 고객이 `SKU-A2K8-BLU` 재고 페이지로 튕겨져 3주간 오배송 47건을 만든 방식

---

#### 1. 시작하는 장면 — Vector 하나로는 왜 안 되는가

2026년 4월, 국내 B2B 커머스 챗봇 팀. RAG 파이프라인 잘 돌아간다. 상품 매뉴얼, 스펙시트 다 pgvector에 임베딩해뒀고, top-5 뽑아 GPT에 넣으면 "케이블 규격이 뭐냐"는 질문에 자연스럽게 답한다. 데모 완벽. 배포.

3주 뒤 CS팀에서 티켓이 쌓인다.

> "저 `SKU-A2K9-BLK` 재고 물어봤는데 챗봇이 `SKU-A2K8-BLU` 페이지 링크 보내줬어요. 그거 발주 걸었더니 색이 다르게 왔네요."

로그 까본다. 임베딩 유사도 0.91. **`SKU-A2K9-BLK`과 `SKU-A2K8-BLU`의 코사인 유사도가 0.91이다.** 두 문자열은 사람이 보면 명백히 다른 상품이지만, `text-embedding-3-large`가 보기엔 "영문+숫자+색상코드 조합"이라는 의미적으로 거의 같은 벡터다.

이게 pure vector search의 근본 한계다. **의미는 잘 잡지만, 정확한 문자열은 흐릿하게 잡는다.**

---

#### 2. 왜 Dense Vector가 Lexical에 약한가

임베딩 모델은 학습 데이터의 통계적 분포로 문맥을 압축한다. 그래서:

| 케이스 | Pure Vector | 이유 |
|---|---|---|
| `SKU-A2K9-BLK` vs `SKU-A2K8-BLU` | 거의 동일 벡터 | 문자 구성 패턴이 같음 |
| "Python 3.11 typing bug" | 3.10 문서를 더 가깝게 판단 | 버전 숫자는 임베딩상 잡음 |
| "환불 **불가** 상품" | "환불 가능 상품" 문서 상위 노출 | 부정어(negation)가 벡터에서 희석됨 |
| 신조어/사내 코드 "ORCA-PROD-2" | 학습 데이터에 없어 사실상 랜덤 벡터 | OOV(Out-Of-Vocabulary) |
| 법률 조문 "제3조 제2항" | "제3조 제3항"과 유사 | 숫자·조문 번호 정밀도 낮음 |

반대로 BM25(전통적 keyword search, TF-IDF의 진화형)는 이 케이스들을 정확히 잡는다. 대신 **의미**는 못 잡는다. "환불" 검색하면 "리펀드"는 놓친다.

**해답은 둘을 같이 쓰는 것.** 이게 Hybrid Search다.

#### 3. 아키텍처 — 병렬 검색 + 스코어 융합

```
                     ┌─────────────────────┐
      User Query ───>│  Query Preprocessor │
                     │  (분석기/토크나이저)  │
                     └──────────┬──────────┘
                                │
                ┌───────────────┼───────────────┐
                ▼                               ▼
       ┌──────────────────┐         ┌──────────────────┐
       │  BM25 Index      │         │  Vector Index    │
       │  (Elasticsearch, │         │  (pgvector,      │
       │   OpenSearch,    │         │   Pinecone,      │
       │   Tantivy)       │         │   Weaviate)      │
       └────────┬─────────┘         └────────┬─────────┘
                │                             │
     rank_bm25=[d3, d7, d1, d9, ...]  rank_vec=[d7, d2, d4, d3, ...]
                │                             │
                └──────────────┬──────────────┘
                               ▼
                     ┌──────────────────────┐
                     │  Fusion Layer        │
                     │  · RRF (기본값)      │
                     │  · Weighted Linear   │
                     │  · Learned (ColBERT) │
                     └──────────┬───────────┘
                                ▼
                     ┌──────────────────────┐
                     │  Reranker (선택)     │  ← Cross-encoder
                     │  bge-reranker-v2     │
                     └──────────┬───────────┘
                                ▼
                       top-k → LLM Context
```

#### 4. Fusion 전략 3가지 — 실무에서 무엇을 고르는가

##### (1) RRF (Reciprocal Rank Fusion) — **디폴트로 이걸 써라**

$$\text{score}(d) = \sum_{r \in \text{rankers}} \frac{1}{k + \text{rank}_r(d)}$$

- `k`는 보통 60 (Cormack et al. 2009 원논문 값)
- **스코어 스케일이 달라도 동작한다.** BM25는 [0, ∞), 코사인은 [-1, 1]. RRF는 순위만 쓰니 무관.
- Elasticsearch 8.9+, Weaviate, OpenSearch가 네이티브 지원

##### (2) Weighted Linear — 튜닝 여지가 필요할 때

$$\text{score}(d) = \alpha \cdot \text{norm}(\text{bm25}) + (1-\alpha) \cdot \text{cosine}$$

- `α` 튜닝이 지옥이다. 도메인마다 최적값이 다르다.
- 의료/법률: `α ≈ 0.7` (lexical 강조)
- 일반 Q&A: `α ≈ 0.3` (semantic 강조)
- **주의**: BM25와 코사인은 스케일이 달라 min-max 정규화 필수. 정규화 안 하면 한쪽이 항상 이긴다.

##### (3) Learned Sparse (SPLADE / ColBERT) — 대규모/고품질 요구 시

- BM25를 학습 기반으로 대체. 여전히 sparse index지만 각 토큰에 학습된 가중치.
- Anthropic의 **Contextual Retrieval (2024)** 논문에서 BM25 + Embedding + Reranker 조합으로 검색 실패율 67% 감소 리포트.
- 구축 난이도 높음. 팀에 ML 엔지니어 없으면 하지 마라.

#### 5. 실제 사례 — 누가 왜 어떻게 썼나

##### Elastic 8.x (2023.5~)

- Kibana에 `rank: {rrf: {}}` 문법 추가. 벡터 필드와 텍스트 필드를 한 쿼리로 조인.
- **채택 이유**: 이미 Elastic 쓰는 고객이 벡터 스토어 따로 두는 걸 원치 않았다. 인덱스 하나, 백업 정책 하나, 권한 관리 하나.
- **한계**: 벡터 인덱스 성능이 전용 Vector DB보다 20~40% 느림 (HNSW ef_construction 낮음).

##### Weaviate `alpha` 파라미터

```python
client.query.get("Product", ["name", "sku"])\
    .with_hybrid(query="A2K9 블랙 케이블", alpha=0.5)\
    .with_limit(10)\
    .do()
```

- `alpha=1` 순수 vector, `alpha=0` 순수 BM25. 프로덕션에서 A/B로 도메인마다 다르게 잡는다.

##### Anthropic Contextual Retrieval (2024.9)

- Claude 팀이 발표한 RAG 개선 기법. **각 청크에 원문 문서의 요약 컨텍스트를 prepend**한 뒤 embedding + BM25 둘 다 인덱싱.
- 결과: retrieval failure rate 5.7% → 1.9% (embedding + BM25 + rerank 조합).
- **핵심 인사이트**: chunk 자체를 잘 만드는 것보다 lexical 신호를 유지하는 게 더 효과적이었다.

##### Perplexity AI 내부 검색 파이프라인

- 웹 크롤 결과를 BM25(빠른 sparse retrieval)로 후보 1000개 뽑고, dense vector로 재정렬, 마지막에 cross-encoder reranker.
- BM25를 앞에 두는 이유는 **비용**. Vector search를 수십억 문서에 first-pass로 걸면 대부분의 SaaS 벡터 DB가 폭발한다.

##### 우리 사례로 돌아오면

앞의 SKU 사고. 해결은 이렇게:

```python
# 기존 (pure vector, 실패)
docs = vector_store.similarity_search(query, k=5)

# 수정 (hybrid, RRF fusion)
bm25_hits = bm25_index.search(query, k=20)
vec_hits  = vector_store.similarity_search(query, k=20)
fused     = rrf_fuse([bm25_hits, vec_hits], k=60)[:5]
```

`SKU-A2K9-BLK`처럼 정확한 식별자는 BM25가 rank 1로 밀어올린다. RRF가 그걸 최종 top-5로 확정. 사고 재발 0건.

#### 6. 트레이드오프 — 공짜가 아니다

| 항목 | Pure Vector | Hybrid | 코멘트 |
|---|---|---|---|
| 인덱스 개수 | 1개 | **2개** | 스토리지 1.5~2배, ingestion 파이프라인 이중화 |
| 쿼리 레이턴시 | ~30ms | ~50ms (병렬) | 순차면 80ms+, 반드시 병렬로 짜라 |
| 정확도 (lexical 중요 도메인) | 60~70% | **85~92%** | 이커머스/법률/기술문서에서 격차 큼 |
| 정확도 (자연어 QA) | 88% | 89% | 거의 차이 없음. 이런 도메인은 vector만으로 충분 |
| Ops 부담 | 낮음 | **중간** | BM25 analyzer 언어별 관리 필요 |
| 튜닝 파라미터 | 없음~1개 | RRF `k` or `α` + BM25 `k1/b` | Weighted 쓰면 무한 튜닝 지옥 |
| 다국어 | 임베딩 모델 다국어면 OK | **BM25 analyzer 언어별 필요** | 한국어는 nori/mecab, 일본어는 kuromoji 필수 |

**숨은 함정**: BM25 인덱스와 vector 인덱스의 **문서 동기화**. 하나만 업데이트되고 다른 쪽이 뒤처지면 검색 결과가 뒤틀린다. Ingestion을 트랜잭셔널하게 짜거나(2PC 어려움), outbox 패턴 + 최종 일관성 허용 정책이 현실적.

#### 7. 시니어 관점 — 언제 쓰고 언제 쓰지 말 것

##### ✅ 반드시 써라

- **정확한 식별자가 도메인 언어**: 상품코드, 에러코드, 조문번호, CVE 번호, 화학식, 유전자 심볼
- **신조어/사내 용어가 많은 문서**: 임베딩 모델 학습 데이터에 없는 단어가 20% 넘으면 pure vector는 실패한다
- **다국어 혼용 문서**: 한국어 본문에 영문 API명 섞인 기술 문서. BM25가 영문 API명을 정확히 잡아준다
- **컴플라이언스/법률 도메인**: "제N조 제N항" 패턴이 vector에서 뭉개진다

##### ⚠️ 안 써도 된다

- **자연어 대화형 QA 봇** (예: 사내 HR 봇, 일상 FAQ): pure vector + reranker로 충분
- **팀에 검색 담당 엔지니어가 없을 때**: BM25 analyzer 튜닝, 인덱스 이중 운영은 생각보다 큰 오버헤드
- **문서 수 10만 미만**: hybrid의 이점이 통계적으로 유의하게 안 나온다. 그냥 좋은 embedding + reranker가 낫다

##### ❌ 쓰면 안 된다

- **완전한 자유형 사용자 쿼리 + 저품질 문서**: BM25가 노이즈만 증폭한다. 이 경우엔 query rewriting + HyDE가 더 낫다
- **극한 저지연 요구 (P99 < 50ms)**: 2개 인덱스 병렬 + fusion + (rerank)까지 붙이면 예산 초과. 이땐 quantized vector 단일 검색으로 가라

#### 8. 오늘의 결론

Vector search는 **의미의 지문**이고, BM25는 **문자의 지문**이다. 사람은 두 지문을 다 본다. **RAG도 그래야 한다.**

pure vector로 시작한 팀이 3~6개월 뒤에 반드시 만나는 벽이 lexical 정밀도다. 그때 임베딩 모델을 바꾸거나 chunk 전략을 다시 짜는 팀은 6개월을 더 잃는다. 답은 이미 40년 전에 나왔다 — TF-IDF/BM25는 사라지지 않았다. **AI 시대에 살아남은 게 아니라, AI가 오히려 그것을 다시 찾아왔다.**

Anthropic의 Contextual Retrieval 논문이 준 진짜 교훈은 "BM25가 여전히 유효하다"가 아니라, **"어떤 신호도 버리지 마라"**다. Sparse + dense + rerank, 셋 다 붙이면 5.7% → 1.9%. 각각 하나씩 뺄 때마다 실패율이 다시 튄다.

> 💡 **왜 중요한가**: RAG의 정답률을 마지막 10~15%p 끌어올리는 건 더 큰 임베딩 모델이 아니라 **버려뒀던 lexical 신호**이며, 그걸 다시 붙이는 아키텍처적 결정이 Hybrid Search다.
