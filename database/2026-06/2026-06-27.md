### 1. PostgreSQL `RETURNING` 절로 INSERT/UPDATE/DELETE 직후 값을 한 번에 회수하기
"INSERT 후 시퀀스로 생성된 PK가 필요해" 같은 시나리오에서 두 번째 `SELECT`를 날리는 건 왕복 비용도 들고 동시성도 위험하다. PostgreSQL은 `INSERT`/`UPDATE`/`DELETE` 뒤에 `RETURNING`을 붙여 영향받은 행을 그 자리에서 돌려주며, `RETURNING *`이나 임의의 표현식도 가능하다. CTE(`WITH ... AS (INSERT ... RETURNING ...)`)로 묶으면 "삽입한 행을 곧장 다른 테이블에 옮긴다" 같은 합성 연산까지 한 SQL로 끝난다.

```sql
-- 삽입과 동시에 PK·생성 시각 회수
INSERT INTO orders(customer_id, amount)
VALUES ($1, $2)
RETURNING id, created_at;

-- 삭제한 행을 archive 테이블로 옮기기 (한 트랜잭션)
WITH deleted AS (
  DELETE FROM sessions WHERE last_seen < now() - interval '30 days'
  RETURNING *
)
INSERT INTO sessions_archive SELECT * FROM deleted;
```

> 💡 **왜 중요한가**: "쓰기 → 다시 읽기"의 race condition과 추가 왕복을 한 번에 제거하며, 감사·이관 같은 합성 연산을 원자적으로 표현할 수 있다.

### 2. Hibernate 2차 캐시 `@Cache(usage = ...)` 전략 — `NONSTRICT_READ_WRITE` vs `READ_WRITE` 선택하기
2차 캐시를 켠다고 무조건 빨라지는 게 아니다. 핵심은 `@Cache`의 `usage`: `READ_ONLY`는 불변 마스터 데이터에만, `NONSTRICT_READ_WRITE`는 잠깐의 stale을 허용하는 콘텐츠에, `READ_WRITE`는 분산 락(소프트 락)으로 일관성을 지키는 트랜잭션 데이터에 적합하다. 트랜잭션 무결성이 중요한 잔액·재고 테이블에 `NONSTRICT`를 쓰면 결제 직후에도 옛 잔액이 잠시 노출되는 사고가 난다.

```java
@Entity
@org.hibernate.annotations.Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
public class Account {                 // 잔액 → 강한 일관성
    @Id Long id;
    BigDecimal balance;
}

@Entity
@org.hibernate.annotations.Cache(usage = CacheConcurrencyStrategy.NONSTRICT_READ_WRITE)
public class Category {                // 카테고리 메타 → 잠깐의 stale 허용
    @Id Long id;
    String name;
}
```

> 💡 **왜 중요한가**: 2차 캐시는 "올바른 전략"이 아니라 "엔티티별로 다른 전략"이 핵심이며, 잘못 고르면 캐시 적중률 대신 데이터 무결성을 잃는다.
