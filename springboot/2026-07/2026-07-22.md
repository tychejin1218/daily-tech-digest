### `ProblemDetail`(RFC 7807)로 API 에러 응답 표준화하기 (Spring 6+)

Spring 6부터 표준으로 지원하는 `ProblemDetail`은 RFC 7807에 정의된 `application/problem+json` 포맷의 에러 응답을 그대로 만들어준다. `@RestControllerAdvice`에서 `ResponseEntityExceptionHandler`를 상속하거나 `ProblemDetail.forStatusAndDetail(...)`을 직접 반환하면, `type`·`title`·`status`·`detail`·`instance` 필드를 갖춘 일관된 에러 스키마를 얻을 수 있다. `application.yml`에서 `spring.mvc.problemdetails.enabled=true`만 켜면 프레임워크가 던지는 예외(예: `MethodArgumentNotValidException`)도 자동으로 ProblemDetail 형태로 응답된다.

```java
@ExceptionHandler(OrderNotFoundException.class)
ProblemDetail handle(OrderNotFoundException e) {
    var pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
    pd.setType(URI.create("https://api.example.com/errors/order-not-found"));
    pd.setProperty("orderId", e.getOrderId());
    return pd;
}
```

> 💡 **왜 중요한가**: 팀·서비스마다 제각각인 `{code, message, errors[]}` 커스텀 포맷을 없애고, 클라이언트가 표준 스키마로 파싱·처리할 수 있게 만들어 준다.

### `spring.jpa.open-in-view=false`로 OSIV 끄고 트랜잭션 경계 명확히 하기

Spring Boot는 기본값 `open-in-view=true`로 시작해, HTTP 요청 전체 동안 영속성 컨텍스트(Session)를 열어두기 때문에 컨트롤러·뷰에서 지연 로딩이 "그냥 동작"한다. 하지만 그 대가로 DB 커넥션이 요청 종료까지 반환되지 않아 트래픽이 몰리면 커넥션 풀이 고갈되고, 트랜잭션 밖에서 발생한 지연 로딩 쿼리가 조용히 N+1을 만든다. `false`로 끄면 서비스 계층의 `@Transactional` 밖에서 지연 필드를 만졌을 때 `LazyInitializationException`이 즉시 터지므로, fetch 전략과 트랜잭션 경계를 강제로 설계하게 된다.

```yaml
spring:
  jpa:
    open-in-view: false
```

> 💡 **왜 중요한가**: 애플리케이션이 편의를 위해 켜둔 기본값 하나가 커넥션 홀딩 시간·쿼리 개수·장애 재현성을 모두 악화시키는 대표적인 함정이다.
