### 1. `Flow` vs `Sequence`: "콜드 스트림"의 동기 버전과 비동기 버전, 그리고 백프레셔의 차이

`Sequence`는 동기 지연 평가 스트림이고 `Flow`는 `suspend` 함수 안에서 동작하는 비동기 지연 평가 스트림이다. 둘 다 터미널 연산(`collect`, `toList`)이 호출되기 전까지 아무 일도 하지 않는 "콜드" 스트림이지만, `Flow`는 코루틴 컨텍스트를 타고 흐르며 `flowOn`으로 업스트림 디스패처를 바꾸거나 `buffer`/`conflate`로 백프레셔 전략을 선택할 수 있다. `Sequence`에서 `Thread.sleep`을 넣으면 스레드 전체가 멈추지만, `Flow`에서 `delay`를 쓰면 코루틴만 중단되고 스레드는 다른 일을 한다 — 이 지점에서 둘의 세계관이 갈린다.

```kotlin
// Sequence: 동기, 블로킹, 스레드 1개 점유
val seq = sequence {
    repeat(3) {
        Thread.sleep(100)  // 스레드 블로킹
        yield(it)
    }
}
seq.toList()  // 메인 스레드 300ms 동안 멈춤

// Flow: 비동기, 논블로킹, 스레드 반환
val flow = flow {
    repeat(3) {
        delay(100)  // 코루틴만 중단, 스레드는 반환
        emit(it)
    }
}
runBlocking {
    flow.flowOn(Dispatchers.IO)  // 업스트림을 IO에서 실행
        .buffer(capacity = 10)    // 백프레셔: 소비자가 느려도 10개까지 버퍼링
        .collect { println(it) }
}
```

| 축 | `Sequence` | `Flow` |
|---|---|---|
| 평가 시점 | 지연(Lazy) | 지연(Lazy) + 비동기 |
| 실행 모델 | 동기 | `suspend` (코루틴) |
| 백프레셔 | 없음 (풀 기반 내재) | `buffer`, `conflate`, `collectLatest` |
| 디스패처 전환 | 불가 | `flowOn` |
| 취소 | 불가능 | 코루틴 취소와 협력 |

실무에서 "DB에서 100만 건을 스트리밍으로 읽고 외부 API로 변환"하는 작업을 `Sequence`로 하면 IO 블로킹으로 스레드 하나가 통째로 잡히고, `Flow`로 하면 `flowOn(Dispatchers.IO).map { api.call(it) }`으로 스레드를 돌려주면서 흐를 수 있다. 반대로 순수 CPU 작업(메모리 내 리스트 필터링)에 `Flow`를 쓰면 코루틴 오버헤드만 늘어난다.

> 💡 **왜 중요한가**: "지연 평가"라는 공통점에 속아 `Flow`를 "비동기 Sequence"로만 보면, `flowOn`·`buffer`·취소 협력이라는 Flow의 진짜 무기를 놓치고 결국 `runBlocking`으로 감싸 스레드를 블로킹하게 된다.

### 2. `init` 블록 vs `constructor` 본문: "주 생성자에는 로직이 들어갈 수 없다"는 제약이 만드는 실행 순서의 함정

Kotlin의 주 생성자(primary constructor)는 선언만 있고 본문이 없다 — 초기화 로직은 `init` 블록이나 프로퍼티 초기화 식에 써야 한다. 그리고 이들은 **클래스 본문에 선언된 순서대로** 실행되며, 보조 생성자(secondary constructor)의 본문은 그 **이후에** 실행된다. 이 순서를 모르면 "분명 초기화했는데 NPE가 나는" 미스터리를 만난다.

```kotlin
class User(val name: String) {
    val upper = name.uppercase()   // ① 프로퍼티 초기화
    
    init {
        println("init 1: $upper")  // ② init 블록
    }
    
    val length: Int
    
    init {
        length = name.length       // ③ 두 번째 init
        println("init 2: $length")
    }
    
    constructor(name: String, age: Int) : this(name) {
        println("secondary: $age") // ④ 보조 생성자는 마지막
    }
}

User("kotlin", 10)
// init 1: KOTLIN
// init 2: 6
// secondary: 10
```

함정은 주로 상속·오버라이드와 결합될 때 터진다. 부모 생성자가 실행되는 동안 자식의 프로퍼티는 아직 초기화되지 않은 상태인데, 부모의 `init`에서 오버라이드된 메서드/프로퍼티를 호출하면 자식 쪽은 null/기본값이다.

```kotlin
open class Parent {
    open val value: String = "parent"
    init {
        println("parent init: $value")  // "parent"? 아니면 자식 값?
    }
}

class Child : Parent() {
    override val value: String = "child"
}

Child()
// parent init: null   ← 자식의 value는 아직 초기화 안 됨!
```

**실무 규칙**: `init` 블록에서 `open` 멤버를 참조하지 마라. 복잡한 초기화 로직이 필요하면 `init`에 몰아넣지 말고 팩토리 함수(`companion object`의 `operator fun invoke`나 `from()`)로 빼는 게 디버깅이 쉽다. Spring의 `@PostConstruct`를 쓸 때도 마찬가지 — 생성자/`init` 단계에서는 의존성 주입이 아직 끝나지 않은 필드가 있을 수 있으니, 주입된 빈을 사용하는 초기화는 `@PostConstruct`로 미뤄야 한다.

> 💡 **왜 중요한가**: "주 생성자 → 프로퍼티·init 블록 선언 순 → 보조 생성자" 라는 3단계 실행 순서를 모르면, 상속 구조에서 오버라이드된 프로퍼티가 null로 보이는 Kotlin 특유의 NPE를 디버깅할 수 없다.
