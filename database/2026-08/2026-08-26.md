### MySQL `Buffer Pool Instances` — 하나의 거대한 캐시가 락 경합의 병목이 되는 순간, 잘게 쪼개서 살리기

InnoDB Buffer Pool은 디스크 페이지를 메모리에 캐싱하는 InnoDB의 심장이지만, 단일 뮤텍스로 보호되기 때문에 고동시성 환경에서는 오히려 캐시 자체가 락 경합의 병목이 된다. `innodb_buffer_pool_instances`를 늘리면 Buffer Pool이 여러 개의 독립된 인스턴스로 분할되고, 페이지는 해시 기반으로 특정 인스턴스에 할당되어 각 인스턴스가 자신만의 뮤텍스/LRU/Free List를 갖게 된다. 즉 "1개의 8GB 풀 + 1개 락"이 아니라 "8개의 1GB 풀 + 8개 락"이 되어 동시 접근 시 락 경합이 극적으로 줄어든다.

```
[단일 Buffer Pool - 락 경합 발생]
       ┌──────────────────────┐
Thread1├─► ▓▓▓▓ Buffer Pool ▓▓│ ◄── 하나의 mutex
Thread2├─►      (8 GB)        │     모두가 대기
Thread3├─►                    │
Thread4└─►                    │
       └──────────────────────┘

[분할된 Buffer Pool - 병렬 처리]
Thread1 ──► [Pool #0: 1GB, mutex #0]
Thread2 ──► [Pool #1: 1GB, mutex #1]
Thread3 ──► [Pool #2: 1GB, mutex #2]  ← 서로 간섭 없음
Thread4 ──► [Pool #3: 1GB, mutex #3]
```

**실무 트레이드오프**: MySQL 5.7 이상은 Buffer Pool이 1GB 이상일 때 기본값 8을 자동 설정하지만, 각 인스턴스는 최소 1GB 이상이어야 관리 오버헤드 대비 이득이 있다. 반대로 인스턴스가 너무 많으면(예: 2GB를 32개로 쪼갬) 각 풀이 너무 작아져 캐시 히트율이 떨어지고, Adaptive Hash Index 파편화도 심해진다. 페이지가 어느 풀에 들어갈지는 해시로 결정되므로, 특정 핫 페이지가 하필 같은 풀에 몰리면 여전히 경합이 발생할 수 있다는 점도 함정.

> 💡 **왜 중요한가**: 메모리를 아무리 늘려도 CPU 코어가 다 놀고 있다면, 문제는 캐시 크기가 아니라 캐시를 지키는 락이다.

### PostgreSQL `Multixact` — 여러 트랜잭션이 같은 행을 FOR SHARE로 잠글 때 조용히 쌓이는 시한폭탄

Postgres에서 `SELECT ... FOR SHARE`나 외래키 검증 시 여러 트랜잭션이 동일 행을 공유 잠금하면, xmax 필드에 단일 XID를 쓸 수 없으므로 "이 행에 잠금을 건 트랜잭션들의 집합"을 표현하는 Multixact ID(mxid)를 별도 SLRU(`pg_multixact/`)에 기록한다. 이 mxid는 32비트 순환 카운터라 무한정 늘어나면 wraparound가 발생하고, 이를 막기 위해 `autovacuum_multixact_freeze_max_age`(기본 4억)에 도달하면 강제 anti-wraparound VACUUM이 트리거된다. 문제는 외래키가 많은 테이블에서 `SELECT ... FOR KEY SHARE`가 조용히 걸리며 mxid가 폭증할 수 있다는 것.

```
[일반 행 잠금 - 단일 XID로 충분]
Tuple xmax = XID 1042 ────► Transaction 1042가 단독으로 잠금

[Multixact - 여러 트랜잭션이 공유]
Tuple xmax = mxid 88 ────► pg_multixact/members:
                            mxid 88 = { XID 1042 (KeyShare),
                                        XID 1055 (KeyShare),
                                        XID 1067 (KeyShare) }
                            ↑ 이게 4억 개 쌓이면 wraparound 위기
```

**증상과 진단**: `pg_stat_activity`에서 `autovacuum: VACUUM ... (to prevent wraparound)`가 갑자기 뜨고 대형 테이블에서 IO가 폭주하면 mxid wraparound가 임박한 신호다. 다음 쿼리로 실시간 모니터링 가능: `SELECT datname, mxid_age(datminmxid) FROM pg_database ORDER BY 2 DESC;`. FK가 많은 부모 테이블(예: `users`, `orders`)의 자식 INSERT/UPDATE가 트래픽을 타면 이 문제가 재현되며, 해결은 (1) FK 검증이 정말 필요한지 재검토, (2) `vacuum_multixact_freeze_min_age`를 낮춰 조기 freezing 유도, (3) SLRU 크기를 늘려 캐시 미스 완화.

> 💡 **왜 중요한가**: XID wraparound만 알고 있다면 절반만 아는 것이다 — FK 많은 서비스는 Multixact가 먼저 터진다.
