### `@Transactional`은 **private 메서드와 self-invocation에서 동작하지 않는다** — 프록시 기반 AOP의 치명적 한계

Spring의 `@Transactional`은 **CGLIB/JDK 프록시가 메서드 호출을 가로채서 트랜잭션 경계를 여는 방식**으로 동작한다. 그래서 같은 클래스 내부에서 `this.method()`로 호출하거나 `private`/`final` 메서드에 붙이면 프록시를 거치지 않아 **애너테이션이 그냥 무시된다**. 더 끔찍한 것은, 컴파일 에러도 런타임 예외도 없이 **조용히 트랜잭션 없이 실행된다는 점**이다.

```java
@Service
public class OrderService {
    @Transactional
    public void placeOrder(Order o) {
        save(o);
        processPayment(o);  // ❌ self-invocation — 트랜잭션 전파 안 됨
    }

    @Transactional(propagation = REQUIRES_NEW)
    public void processPayment(Order o) { ... }  // 새 트랜잭션 안 열림
}
```

해결: `AopContext.currentProxy()`로 프록시를 꺼내 쓰거나, 메서드를 **별도 Bean으로 분리**하거나, Spring 6+에서는 `@EnableTransactionManagement(mode = AspectJ)`로 바이트코드 위빙을 쓴다.

> 💡 **왜 중요한가**: "분명히 `@Transactional` 붙였는데 롤백이 안 된다"는 전설적인 야간 호출의 90%가 self-invocation이다. 프록시 기반 AOP의 한계를 모르면 테스트에서는 멀쩡하다가 운영에서 데이터 정합성이 깨진다.

### Spring Security의 `PasswordEncoder.matches()`는 **상수 시간(constant-time) 비교를 보장하지만, `.equals()`로 비교하면 타이밍 공격에 뚫린다**

`BCryptPasswordEncoder`, `Argon2PasswordEncoder` 등 Spring의 모든 `PasswordEncoder` 구현체는 **`MessageDigest.isEqual()` 또는 그에 준하는 상수 시간 비교**를 사용한다. 비밀번호나 토큰을 검증할 때 길이가 같아도 **첫 바이트부터 끝까지 모두 비교**해서 "몇 번째 바이트에서 틀렸는지"가 응답 시간에 노출되지 않는다. 그런데 많은 개발자가 API 키나 서명 검증 시 그냥 `secret.equals(input)`을 쓰는데, 이건 **첫 다른 바이트에서 즉시 return**하므로 수백만 요청을 보내 평균 응답 시간을 측정하면 비밀번호를 **한 바이트씩 추론할 수 있다**.

```java
// ❌ 타이밍 공격 취약 — 틀린 바이트 위치에 따라 수 나노초 차이가 난다
if (storedToken.equals(requestToken)) { ... }

// ✅ 상수 시간 비교
if (MessageDigest.isEqual(storedToken.getBytes(), requestToken.getBytes())) { ... }
```

> 💡 **왜 중요한가**: 로컬 네트워크나 같은 데이터센터 안에서는 나노초 단위 차이도 측정 가능하다. 실제로 2013년 Keyczar, 2017년 Netflix의 몇몇 내부 서비스에서 이 문제로 CVE가 발급됐다. `equals()`는 비교지, 검증이 아니다.
