### 1. `let` vs `also`: "null 체크용 도구"가 아니라 "체이닝의 흐름 제어 장치"

많은 사람이 `let`을 "null-safe 호출을 위한 도구"로만 알고 있지만, 본질은 **수신 객체를 람다의 인자(`it`)로 변환해 결과값을 반환**하는 것이다. 반면 `also`는 **수신 객체 자신을 반환**하므로, 체이닝 중간에 "사이드 이펙트(로깅, 디버깅, 유효성 검증)"만 끼워 넣을 때 쓴다. 즉 `let`은 "변환이 필요할 때", `also`는 "흐름을 끊지 않고 엿볼 때"가 정확한 사용처다.

```kotlin
// let: 변환하고 결과를 넘긴다 (it → 새로운 값)
val length: Int? = user?.name?.let { it.trim().length }

// also: 자기 자신을 넘긴다 (사이드 이펙트만)
val user = User("Kim")
    .also { logger.debug("생성됨: $it") }   // 로깅
    .also { require(it.name.isNotBlank()) } // 검증
    .also { cache.put(it.id, it) }          // 캐싱
// → user 객체 그 자체가 반환됨, 체이닝 유지
```

흔한 실수는 `apply { ... }`로 로깅까지 섞는 것인데, `apply`는 `this` 기반이라 로거 호출이 수신자 메서드와 뒤섞여 **가독성이 깨진다**. "변환=let, 설정=apply, 관찰=also, 결과값만 다른 블록=run"으로 역할을 분리하면 스코프 함수 선택이 기계적으로 결정된다.

> 💡 **왜 중요한가**: 스코프 함수를 "취향"으로 쓰면 코드 리뷰에서 매번 논쟁이 나지만, "반환값(수신자/결과)" × "참조방식(it/this)"의 2×2 매트릭스로 접근하면 선택이 결정론적이 된다.

### 2. Kotlin의 `List`는 "불변"이 아니다: `ReadOnly`와 `Immutable`의 치명적 차이

Kotlin에서 `listOf(1, 2, 3)`로 만든 `List<Int>`를 "불변 리스트"라고 부르는 건 **반쯤 거짓말**이다. 정확히는 **읽기 전용 뷰(read-only view)** 일 뿐, JVM 레벨에서는 여전히 `java.util.ArrayList`이고, Java 코드나 캐스팅을 통하면 얼마든지 수정이 가능하다. 즉 `val` + `List`가 **스레드 안전 + 변경 불가**를 보장하지 않는다.

```kotlin
val readOnly: List<Int> = mutableListOf(1, 2, 3)
val mutable = readOnly as MutableList<Int>  // 런타임에 성공한다
mutable.add(4)
println(readOnly) // [1, 2, 3, 4] ← 뷰가 뚫림

// Java에서 호출 시: List<Integer> list = KotlinCode.getReadOnly();
// list.add(99); // 컴파일/런타임 모두 성공
```

진짜 불변이 필요하다면 `Collections.unmodifiableList()`, Java 9+ `List.of()`, 또는 Guava `ImmutableList`를 써야 한다. 더 안전한 대안은 **kotlinx.collections.immutable** 라이브러리의 `persistentListOf()`로, 구조적 공유를 통해 변경 시 새 인스턴스를 반환해 **진짜 불변성**을 보장한다. Spring Boot의 DTO나 캐시 키로 쓰는 컬렉션은 이 차이를 꼭 인지해야 한다.

> 💡 **왜 중요한가**: "Kotlin은 불변이 기본이다"라는 믿음으로 멀티스레드 환경에서 `List`를 공유 상태로 쓰면, Java 상호운용 지점이나 리플렉션에서 조용히 뚫려서 재현 안 되는 동시성 버그를 만든다.
