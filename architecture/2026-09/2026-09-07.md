### Agent Pattern 선택 — "ReAct 하나면 다 된다"는 오해, 그리고 5-step 태스크에 tool call 23번 태우고 답 못 낸 챗봇의 새벽

## 1. 무슨 일이 벌어졌나

한 이커머스 CS 챗봇 팀. 반품 처리 Agent를 ReAct 패턴으로 배포했다. LangChain 튜토리얼 그대로. Tool 6개(주문조회, 반품정책조회, 재고확인, 환불계산, 배송조회, 티켓생성). GPT-4o로 잘 돈다.

배포 2주 뒤, Grafana에 이상한 그래프가 뜬다.

- P50 응답시간: 4.2초 (정상)
- **P95: 47초** (헉)
- **P99: 132초 (timeout)**
- 태스크당 평균 tool call: **11.3회** (예상: 4~5회)
- 실패율: 8.7% (환불 자동화 실패 → 상담원 이관)

로그를 까본다. 5-step으로 끝나야 할 반품 태스크에 tool call이 **23번**. 무슨 일인가 봤더니:

```
Thought: 주문번호를 확인해야겠다
Action: get_order(id="12345")
Observation: {order_date: "2026-08-15", items: [...]}
Thought: 반품정책을 확인하자
Action: get_refund_policy(category="electronics")
Observation: "30일 이내 반품 가능"
Thought: 30일이 지났는지 확인해야겠다. 오늘 날짜를 알아야 하는데...
Action: get_order(id="12345")   ← 왜 또?
Observation: {order_date: "2026-08-15", ...}
Thought: 음, 다시 정책을 확인해보자
Action: get_refund_policy(category="electronics")   ← 또?
Observation: "30일 이내 반품 가능"
Thought: 30일 계산을 위해 배송일이 필요하다
Action: get_shipping(id="12345")
...
```

**ReAct가 자기가 뭘 했는지 잊어버리고 같은 tool을 반복 호출**하고 있었다. Context window에 observation이 쌓이면서 LLM이 "일단 아는 것부터 다시 확인하자" 모드로 진입한 것.

이건 ReAct의 본질적 한계다. 그리고 이걸 몰랐다는 게 시니어의 실책이다.

## 2. 세 가지 Agent Pattern 정리

Agent 패턴은 크게 3가지. 튜토리얼은 항상 ReAct만 보여줘서 착각하기 쉽다.

### 2-1. Tool Use (단순 Function Calling, 1-turn)

```
User: "주문 12345 상태 알려줘"
  ↓
LLM: [tool_call: get_order(id="12345")]
  ↓
Tool: {status: "shipped"}
  ↓
LLM: "배송 중입니다"
```

- **Loop 없음**. 1~2번 호출로 끝나는 태스크.
- OpenAI `tools` 파라미터 그대로. 예측 가능. 비용 적음.

### 2-2. ReAct (Reasoning + Acting 반복 loop)

```
Thought → Action → Observation → Thought → Action → ... → Final Answer
```

- LLM이 매 스텝마다 "다음에 뭐 할지" 스스로 판단.
- **장점**: 유연하다. 예상 못한 상황에 적응.
- **단점**: 
  - 계획이 없어서 같은 도구 반복 호출 가능
  - Observation이 쌓이면 context bloat → 초반 정보 잊음
  - 몇 번 돌지 예측 불가 → SLA 계산 어려움

### 2-3. Plan-and-Execute (Planner + Executor 분리)

```
Step 1: Planner LLM이 전체 계획 수립 (1번만)
   [1] get_order(12345)
   [2] get_shipping(12345)  
   [3] calculate_refund(...)
   [4] create_ticket(...)

Step 2: Executor가 계획을 그대로 실행
```

- **장점**: 
  - 계획이 명시적 → 감사 가능, 예측 가능
  - Executor는 작은 모델로 대체 가능 (비용↓)
  - Step 실패 시 재계획 or 재시도 명확
- **단점**: 
  - 초기 계획이 틀리면 전체가 틀림
  - 중간에 새로운 정보로 계획 수정이 어색함

## 3. 비교 다이어그램

```
┌─────────────────────────────────────────────────────────────┐
│  Tool Use (1-turn)                                          │
│  ────────────────                                           │
│  User → LLM → [tool] → LLM → Answer                         │
│  비용: ⭐   지연: ⭐   유연성: ⭐                            │
│  적합: 단순 조회, 명확한 1-step 태스크                       │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│  ReAct (반복 loop)                                          │
│  ────────────                                                │
│  User → LLM ──┐                                             │
│      ↑        ↓                                             │
│      │    [Thought]                                         │
│      │        ↓                                             │
│      │    [Action] → Tool                                   │
│      │        ↓                                             │
│      └──[Observation] ← (loop, 몇 번인지 모름)              │
│                                                              │
│  비용: ⭐⭐⭐ (loop마다 전체 context 재전송)                  │
│  지연: ⭐⭐⭐ (예측 불가)                                     │
│  유연성: ⭐⭐⭐⭐⭐                                            │
│  적합: 탐색적/개방형 태스크 (검색, 리서치)                   │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│  Plan-and-Execute (계획 → 실행 분리)                        │
│  ────────────────────────────────                           │
│  User → [Planner LLM] → 계획 (step 1,2,3,4)                 │
│                             ↓                                │
│                        [Executor]                            │
│                             ↓                                │
│                    step 1 → step 2 → step 3 → ...           │
│                             ↓                                │
│                    (실패 시 Replanner 호출)                  │
│                                                              │
│  비용: ⭐⭐ (Planner 1회 + 작은 Executor)                    │
│  지연: ⭐⭐ (예측 가능)                                       │
│  유연성: ⭐⭐⭐                                                │
│  적합: 반복적/구조적 태스크 (반품, 승인, 워크플로우)          │
└─────────────────────────────────────────────────────────────┘
```

## 4. 결정 트리 — 시니어의 판단

```
                   ┌──────────────────────┐
                   │  태스크가 1~2 스텝?  │
                   └──────────┬───────────┘
                        Yes   │   No
                    ┌─────────┴─────────┐
                    ↓                   ↓
              ┌──────────┐        ┌──────────────────┐
              │ Tool Use │        │ 스텝 순서 예측   │
              │  (단순)  │        │ 가능한가?        │
              └──────────┘        └────────┬─────────┘
                                   Yes    │   No
                              ┌───────────┴──────────┐
                              ↓                      ↓
                     ┌──────────────────┐    ┌──────────────┐
                     │ Plan-and-Execute │    │  ReAct       │
                     │ (워크플로우형)    │    │  (탐색형)     │
                     └──────────────────┘    └──────────────┘
```

**핵심 질문 하나**: "이 태스크를 사람이 한다면, 순서를 미리 종이에 적을 수 있는가?"

- 적을 수 있음 → **Plan-and-Execute**
- 봐가면서 판단해야 함 → **ReAct**
- 그냥 한 번에 답 나옴 → **Tool Use**

## 5. 실제 사례

### GitHub Copilot Workspace — Plan-and-Execute

이슈 → PR 생성 흐름. Planner가 먼저 "spec → plan → 파일별 변경사항"을 산출하고, 사용자가 승인한 뒤 Executor가 실행. **왜?** 코드 변경은 감사 가능해야 하고, 중간에 엉뚱한 파일 건드리면 안 되기 때문. ReAct였다면 "일단 파일 읽어보고... 아 이것도 읽어야겠다" 무한 루프 위험.

### Perplexity AI — ReAct 기반 검색

"이 회사의 2025 Q3 매출은?" 같은 질문. 처음에 뭘 검색해야 할지 모른다. 검색 → 결과 부족 → 다른 키워드 → 부족 → 다른 소스... 이런 탐색은 계획 불가능. ReAct가 정답.

### Anthropic Claude "Computer Use" — ReAct + 안전장치

브라우저를 클릭하는 Agent. 화면이 어떻게 바뀔지 미리 모르니 ReAct. 대신 **step 상한**(max_iterations)과 **비용 상한**을 강제로 걸어둔다. ReAct의 무한 루프를 인프라로 막는 방식.

### AutoGPT의 몰락 — 순수 ReAct의 한계

2023년 광풍이었지만 실제 프로덕션에 못 올라간 이유. "목표 → 자율 계획 → 실행"을 ReAct로만 돌렸다. 결과: task 하나에 API 500번 호출, 답 못 내고 크래시. Plan-and-Execute 개념이 정착한 계기.

## 6. 우리 팀은 뭘로 갔어야 했나

반품 처리는 스텝이 **정해져 있다**:
1. 주문 확인 → 2. 기간/정책 확인 → 3. 재고/배송 상태 → 4. 환불 금액 계산 → 5. 티켓 생성

이건 사람이 종이에 순서를 적을 수 있는 태스크. → **Plan-and-Execute**가 정답이었다.

리팩토링 후:

| 지표          | ReAct (Before) | Plan-and-Execute (After) |
|---------------|----------------|--------------------------|
| 평균 tool call | 11.3회         | 4.8회                    |
| P95 지연       | 47초           | 6.2초                    |
| 태스크당 비용  | $0.42          | $0.11                    |
| 실패율         | 8.7%           | 1.2%                     |
| 감사 로그      | "왜 이렇게 했지?" | 계획 문자열 그대로 저장 |

Planner는 GPT-4o, Executor는 GPT-4o-mini로 분리. Planner 계획을 DB에 저장하니 CS팀이 사후 "이 Agent가 왜 이런 판단을 했지?" 물을 때 계획 문자열 하나 보여주면 끝.

## 7. 트레이드오프 정리

| 관점          | Tool Use     | ReAct              | Plan-and-Execute      |
|---------------|--------------|--------------------|-----------------------|
| **비용 예측** | 정확         | 불가능             | 대략 가능             |
| **감사/설명** | 자명         | trace 다 봐야 함   | 계획 하나면 끝        |
| **적응성**    | 없음         | 최고               | 중간 (Replan 필요)    |
| **개발 난도** | 낮음         | 중간               | 높음 (Planner 설계)   |
| **모델 다운사이즈** | 어려움 | 어려움             | Executor를 작게 가능  |
| **위험 태스크**(결제/삭제) | ⭕ | ❌ (무한 루프)      | ⭕ (승인 게이트)      |

## 8. 시니어의 체크리스트

Agent 만들기 전에 반드시 답해야 하는 5가지:

1. **"이 태스크의 스텝 수 상한은?"** — 답 못 하면 ReAct 쓰지 마라
2. **"각 tool의 idempotency는?"** — `refund()`가 non-idempotent인데 ReAct 돌리면 재앙
3. **"Planner 계획을 저장할 곳이 있는가?"** — 없으면 사후 조사 불가
4. **"max_iterations, max_cost를 강제로 걸었는가?"** — Agent에게 무한 예산 주지 마라
5. **"Human-in-the-loop 지점은?"** — 환불 실행 직전엔 사람 승인 필수. Agent 판단에만 맡기지 마라

> 💡 **왜 중요한가**: Agent 패턴 선택은 "모델을 뭘로 쓸까"보다 훨씬 결정적이다 — 잘못 고른 패턴은 GPT-5로도 못 구한다.
