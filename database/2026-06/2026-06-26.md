### 1. PostgreSQL `DISTINCT ON` — "그룹별 최신 행 1개"를 윈도우 함수보다 짧고 빠르게 꺼내기

각 user_id별 마지막 주문, 각 센서별 최신 측정값처럼 "그룹당 1행"을 골라야 할 때 흔히 `ROW_NUMBER() OVER (PARTITION BY ...)` 서브쿼리를 쓰지만, PostgreSQL의 `DISTINCT ON (col)`은 같은 결과를 한 줄 문법으로 표현하며, `(user_id, created_at DESC)` 같은 인덱스가 있으면 옵티마이저가 Index Scan + Skip을 골라 윈도우 함수 플랜보다 훨씬 적은 행만 읽고 끝낸다. 단, `ORDER BY`의 선두 컬럼이 `DISTINCT ON` 컬럼과 일치해야 하며, 정렬 순서가 곧 "어떤 행을 남길지"를 결정한다는 의미론을 반드시 기억해야 한다.

> 💡 **왜 중요한가**: 같은 결과를 만드는 두 쿼리가 백만 행 테이블에서 수십 배 성능 차이를 내는 대표 사례이며, 인덱스 설계와 쿼리 문법이 함께 맞아떨어져야 효과가 나타난다.

### 2. JPA `spring.jpa.open-in-view=false` — 기본값 `true`가 컨트롤러·뷰 렌더링까지 DB 커넥션을 붙잡는 숨은 비용

Spring Boot는 OSIV(Open Session In View)를 기본 `true`로 켜두기 때문에 `@Transactional` 메서드가 끝나도 영속성 컨텍스트와 DB 커넥션이 HTTP 응답이 완성될 때까지 유지되며, 이는 컨트롤러나 JSP/Thymeleaf에서 Lazy 프록시를 안전하게 접근할 수 있다는 편의의 대가로 커넥션 점유 시간을 비정상적으로 늘려 HikariCP 풀 고갈과 응답 지연을 만든다. 운영에서는 `false`로 끄고 LAZY 로딩은 서비스 레이어 안의 `@EntityGraph`·DTO 프로젝션·`fetch join`으로 명시적으로 해결하는 것이 정석이다.

> 💡 **왜 중요한가**: 트래픽이 늘었을 때 "쿼리는 빨라졌는데도 커넥션 풀이 터지는" 원인의 1순위가 OSIV이며, 코드 변경 없이 설정 한 줄로 커넥션 점유 시간을 응답 전체 길이에서 트랜잭션 길이로 줄일 수 있다.
