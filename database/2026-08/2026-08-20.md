### MySQL `Redo Log` 순환 구조 — WAL의 심장, 그런데 왜 커밋이 갑자기 멈추는가

InnoDB의 모든 변경은 데이터 파일보다 먼저 `redo log`(`ib_logfile0`, `ib_logfile1` 또는 8.0+ `#innodb_redo/`)에 순차 기록되고, 이 로그는 정해진 크기의 링 버퍼처럼 **순환**한다. 문제는 이 링이 꽉 차기 직전이 되면 InnoDB가 **"async flush"**를 넘어 **"sync flush"** 구간에 진입해 사용자 쓰기 트랜잭션을 강제로 대기시킨다는 점이다. 즉 커밋이 갑자기 멈춘 것처럼 보이는 순간, 진짜 원인은 락도 CPU도 아니라 "체크포인트가 로그의 꼬리를 따라가지 못한 것"인 경우가 많다.

```
[write pos] ────────────►
    ┌──────────────────────────────────┐
    │ ▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░░░░░░░░░░░░░░░ │  ← Redo Log Ring
    └──────────────────────────────────┘
             ▲
        [checkpoint pos]

write pos가 checkpoint pos를 한 바퀴 돌아 따라잡기 직전:
  → innodb_lsn_checkpoint_age가 sync flush threshold 도달
  → 사용자 트랜잭션 stall (커밋 대기)
```

트레이드오프: `innodb_log_file_size`를 키우면 sync flush는 지연되지만 크래시 복구 시간이 길어지고, `innodb_flush_log_at_trx_commit=2`로 낮추면 처리량은 오르지만 OS 크래시 시 최근 1초 트랜잭션이 날아간다. 실전에서는 `SHOW ENGINE INNODB STATUS`의 **Log sequence number vs Last checkpoint at 차이**를 모니터링하고, 이 값이 로그 총 용량의 75%를 넘기 시작하면 로그 파일을 키우는 것이 정석이다.

> 💡 **왜 중요한가**: "커밋이 갑자기 느려졌다"의 원인을 락/쿼리에서만 찾다 보면 진짜 범인인 redo log 체크포인트 압박을 놓친다.

### PostgreSQL `SKIP LOCKED` — 여러 워커가 같은 큐 테이블에서 서로 밟지 않고 일감을 나눠 갖는 법

DB 테이블을 작업 큐로 쓸 때, 여러 워커가 `SELECT ... FOR UPDATE`로 잡으면 순서대로 대기하며 병렬성이 사라진다. `FOR UPDATE SKIP LOCKED`는 이미 다른 트랜잭션이 잠근 행은 **없는 것처럼 건너뛰고** 다음 행을 잡기 때문에, 별도의 브로커(Redis/Kafka) 없이 DB만으로 다중 컨슈머 큐를 안전하게 구현할 수 있다.

```sql
-- Worker A, B, C가 동시에 실행해도 서로 다른 행을 가져감
BEGIN;
SELECT id, payload
FROM job_queue
WHERE status = 'PENDING'
ORDER BY created_at
LIMIT 10
FOR UPDATE SKIP LOCKED;   -- ← 잠긴 행은 조용히 건너뜀

UPDATE job_queue SET status = 'RUNNING' WHERE id IN (...);
COMMIT;
```

주의점: `SKIP LOCKED`는 격리 수준의 **일관성을 스스로 깨는 예외 구문**이라, 같은 쿼리를 두 번 돌리면 결과가 달라진다(=idempotent 하지 않다). 그리고 워커가 죽어서 트랜잭션이 롤백되면 잠금은 풀리지만 `status='RUNNING'`으로 이미 UPDATE 됐다면 좀비 잡이 남을 수 있으므로, `visibility_timeout` 컬럼(마지막 픽업 시각)을 두고 초과분을 재큐잉하는 리퍼(reaper) 잡을 반드시 함께 운영해야 한다. MySQL 8.0+도 동일 구문을 지원한다.

> 💡 **왜 중요한가**: Kafka/RabbitMQ를 도입하기 전, "DB만으로 충분한 큐"가 필요한 순간에 이 한 구문이 시스템 복잡도를 절반으로 줄인다.
