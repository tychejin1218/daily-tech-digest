### PostgreSQL `LATERAL JOIN` — 각 행마다 서브쿼리를 실행해 Top-N per Group 우아하게 풀기

일반 `JOIN`은 두 테이블을 독립적으로 결합하지만, `LATERAL`은 왼쪽 테이블의 각 행을 오른쪽 서브쿼리가 참조할 수 있게 해준다. 사용자별 최근 주문 3건처럼 그룹당 상위 N개를 뽑는 쿼리를 윈도우 함수 없이 인덱스로 빠르게 처리할 수 있다.

```sql
SELECT u.id, u.name, recent.order_id, recent.created_at
FROM users u
CROSS JOIN LATERAL (
  SELECT o.id AS order_id, o.created_at
  FROM orders o
  WHERE o.user_id = u.id
  ORDER BY o.created_at DESC
  LIMIT 3
) AS recent;
```

`orders(user_id, created_at DESC)` 인덱스가 있다면 각 사용자마다 인덱스 상위 3건만 읽고 끝난다. `ROW_NUMBER() OVER (PARTITION BY ...)` 방식은 전체 행을 스캔·정렬해야 하지만, `LATERAL`은 `LIMIT`을 밀어넣기 때문에 데이터 볼륨과 무관하게 성능이 유지된다.

> 💡 **왜 중요한가**: 그룹별 최신 N건을 뽑는 쿼리에서 윈도우 함수의 전체 스캔을 인덱스 lookup 몇 번으로 줄일 수 있다.

### MySQL `Read View`와 `Undo Log` — MVCC가 잠금 없이 일관된 스냅샷을 보여주는 원리

InnoDB는 `REPEATABLE READ`에서 트랜잭션 시작 시점에 `Read View`(활성 트랜잭션 ID 목록)를 캡처하고, 이후 다른 트랜잭션이 수정한 행을 만나면 `Undo Log`를 거슬러 올라가 자기 스냅샷 시점의 버전을 재구성한다. 그래서 `SELECT`는 락 없이 읽고, 장기 트랜잭션이 방치되면 `Undo Log`가 계속 쌓여 `history list length`가 폭증한다.

```sql
-- 장기 트랜잭션이 만드는 undo 누적 감시
SELECT name, count FROM information_schema.innodb_metrics
WHERE name = 'trx_rseg_history_len';

-- 오래 열린 트랜잭션 색출
SELECT trx_id, trx_started, trx_query
FROM information_schema.innodb_trx
ORDER BY trx_started ASC LIMIT 10;
```

`history list length`가 수백만을 넘어가면 `SELECT`가 이전 버전을 재구성하느라 느려지고, `purge` 스레드가 따라오지 못해 디스크와 버퍼풀이 오염된다. 배치 잡이나 커넥션 풀에서 커밋 없이 열려있는 트랜잭션이 원인인 경우가 대부분이다.

> 💡 **왜 중요한가**: 원리를 알면 "쿼리는 안 바꿨는데 어제부터 느려졌다"의 진짜 원인이 어제 배포된 장기 트랜잭션임을 짚어낼 수 있다.
