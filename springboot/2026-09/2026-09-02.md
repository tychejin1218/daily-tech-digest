### `@Configuration`의 `proxyBeanMethods=false`를 모르면, 부트 시작 시간이 조용히 2배가 된다

`@Configuration` 클래스는 기본적으로 CGLIB 프록시로 감싸져서 `@Bean` 메서드 간 상호 호출 시 싱글톤을 보장한다. 하지만 이 프록시 생성 비용이 만만치 않아서, `@Bean` 메서드 간 호출이 없는 순수 설정 클래스에까지 프록시를 씌우면 부트 시작 시간과 메모리가 낭비된다. Spring Boot 자체는 대부분의 내부 `@Configuration`에 `proxyBeanMethods = false`를 명시해 **Lite 모드**로 동작한다.

```java
// ❌ 기본값 - CGLIB 프록시 생성 (Full 모드)
@Configuration
public class AppConfig {
    @Bean public Clock clock() { return Clock.systemUTC(); }
    // 다른 @Bean 메서드 호출 없음에도 프록시 생성 비용 발생
}

// ✅ Lite 모드 - 프록시 생성 안 함
@Configuration(proxyBeanMethods = false)
public class AppConfig {
    @Bean public Clock clock() { return Clock.systemUTC(); }
}
```

주의할 점은 Lite 모드에서 `@Bean` 메서드를 같은 클래스 안에서 직접 호출하면 **매번 새 인스턴스가 생성된다**는 것. 즉 싱글톤 보장이 사라진다. `@Bean` 메서드 간 의존이 있다면 반드시 파라미터로 주입받아야 한다.

> 💡 **왜 중요한가**: 마이크로서비스에서 설정 클래스가 수십 개로 늘어나면 이 작은 최적화가 부트 시간을 20~40% 단축시킨다 — 서버리스/K8s 환경에서 콜드 스타트를 좌우한다.

### `Spring Data JPA`의 `findAll(Pageable)`은 항상 `count` 쿼리를 함께 날린다 — 대용량 테이블에서 조용한 지연의 원인

페이지네이션 API를 구현할 때 `PagingAndSortingRepository.findAll(Pageable)`를 무심코 쓰면, 실제 데이터 조회 쿼리 외에 **`SELECT COUNT(*)` 쿼리가 매번 함께 실행**된다. 수백만 건 테이블에서 count 쿼리는 인덱스만으론 부족해 풀 스캔에 가까운 비용을 지불하고, 이게 API 응답시간의 80%를 차지하는 경우가 흔하다.

```java
// ❌ count 쿼리가 매번 실행됨 - 대용량 테이블에서 재앙
Page<Order> page = orderRepository.findAll(pageable);

// ✅ 방법 1: Slice로 변경 - "다음 페이지 있음" 여부만 판단, count 안 함
Slice<Order> slice = orderRepository.findByStatus(status, pageable);

// ✅ 방법 2: @Query에서 countQuery를 최적화 (JOIN 제거, 인덱스 활용)
@Query(
    value = "SELECT o FROM Order o JOIN FETCH o.items WHERE o.userId = :userId",
    countQuery = "SELECT COUNT(o) FROM Order o WHERE o.userId = :userId"
)
Page<Order> findByUserId(@Param("userId") Long userId, Pageable pageable);

// ✅ 방법 3: 커버링 인덱스로 count 자체를 빠르게
// CREATE INDEX idx_order_status ON orders(status, created_at);
```

전체 개수가 UI에 꼭 필요하지 않다면 `Slice`가 정답이다. 무한 스크롤/타임라인 UI라면 `Page` 대신 `Slice`로 바꾸는 것만으로 응답시간이 절반으로 줄어드는 경우가 많다.

> 💡 **왜 중요한가**: 페이지네이션은 "당연히 빠를 것"이라는 착각의 대표 사례 — 데이터가 커질수록 count 쿼리가 조용히 서버를 잡아먹는데, 프로파일러 없이는 원인을 찾기 어렵다.
