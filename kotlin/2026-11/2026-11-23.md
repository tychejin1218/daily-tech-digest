### 1. `tailrec` 재귀: 스택 오버플로우 없이 재귀의 우아함을 유지하는 컴파일러의 선물

Kotlin에서 깊은 재귀는 `StackOverflowError`로 끝나지만, 함수의 마지막 연산이 자기 자신 호출이라면 `tailrec` 키워드 하나로 컴파일러가 이를 while 루프로 치환해준다. 바이트코드를 디컴파일해 보면 재귀 호출이 사라지고 `goto`로 바뀐 것을 확인할 수 있다. 단, 재귀 호출이 **표현식의 마지막**이어야 하며 (`return factorial(n-1) * n` 같은 형태는 불가), try/catch 블록 안에 있으면 최적화가 적용되지 않는다.

```kotlin
tailrec fun findFixPoint(x: Double = 1.0): Double =
    if (x == Math.cos(x)) x else findFixPoint(Math.cos(x))

tailrec fun factorial(n: Long, acc: Long = 1): Long =
    if (n <= 1) acc else factorial(n - 1, acc * n)
```

> 💡 **왜 중요한가**: 함수형 스타일의 가독성과 명령형 스타일의 성능/안전성을 동시에 얻을 수 있다 — "재귀를 쓰고 싶지만 스택이 무서워서 while로 풀어쓰는" 타협을 할 필요가 없어진다.

### 2. `Result<T>`와 `runCatching`: 예외를 "값"으로 다루는 Kotlin의 함수형 에러 핸들링

try/catch는 제어 흐름이 끊기고 반환 타입에 실패 가능성이 드러나지 않지만, `Result<T>`는 성공/실패를 하나의 값으로 감싸 **타입 시스템에 명시**한다. `runCatching { ... }`으로 예외를 캐치해 `Result`로 변환하고, `map`/`fold`/`getOrElse`/`recover`로 체이닝한다. 단, 주의할 점은 `Result`는 **함수의 반환 타입으로 쓰지 말라는 것이 공식 가이드** — JVM에서 unboxing 비용이 있고, `CancellationException`까지 삼켜 코루틴 취소를 무력화시킬 수 있기 때문이다. 그래서 코루틴 안에서는 `runCatching` 대신 명시적 try/catch 혹은 `Result` 전용 wrapper 라이브러리(Arrow의 `Either`)를 쓰는 게 권장된다.

```kotlin
fun parseConfig(raw: String): Result<Config> = runCatching {
    Json.decodeFromString<Config>(raw)
}

parseConfig(input)
    .map { it.copy(timeout = it.timeout.coerceAtMost(30_000)) }
    .onFailure { logger.warn("설정 파싱 실패", it) }
    .getOrDefault(Config.DEFAULT)
```

> 💡 **왜 중요한가**: "이 함수는 실패할 수 있다"를 주석이나 javadoc이 아닌 **반환 타입**으로 강제함으로써, 호출자가 실패 처리를 잊어버릴 수 없게 만든다 — 단, 코루틴 경계에서는 `CancellationException`을 삼키지 않도록 별도의 주의가 필요하다.
