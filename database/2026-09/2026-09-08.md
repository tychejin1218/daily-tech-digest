### PostgreSQL `EXPLAIN (BUFFERS)` — 실행 시간이 아니라 "몇 페이지를 읽었는가"로 쿼리를 진단하기

`EXPLAIN ANALYZE`가 "얼마나 걸렸는가"를 알려준다면, `EXPLAIN (ANALYZE, BUFFERS)`는 "shared hit(캐시 히트) / read(디스크 읽기) / dirtied(더럽힌 페이지)"를 노드별로 쪼개서 보여준다. 실행 시간은 서버 부하나 캐시 상태에 따라 요동치지만, 페이지 읽은 개수는 결정적(deterministic)이라 튜닝 전후를 비교할 때 훨씬 정직한 지표가 된다. 특히 `Buffers: shared read=` 숫자가 크다면 인덱스가 없거나, 있어도 안 타는 것 — 시간 대신 이 숫자를 줄이는 게 최적화의 진짜 목표다.

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT * FROM orders WHERE user_id = 42 AND status = 'PAID';

-- Seq Scan on orders  (actual time=12.3..245.1 rows=17 loops=1)
--   Filter: ((user_id = 42) AND (status = 'PAID'))
--   Rows Removed by Filter: 1,499,983
--   Buffers: shared hit=1024 read=48576   ← 페이지 5만 개를 읽어서 17행 반환
```

> 💡 **왜 중요한가**: 실행 시간은 "이번엔 왜 빠르지/느리지"를 남기지만, 페이지 카운트는 "이 쿼리는 구조적으로 얼마나 비싼가"를 남긴다 — 후자가 튜닝의 진짜 기준이다.

### MySQL `Index Condition Pushdown (ICP)` — WHERE 조건을 스토리지 엔진까지 밀어넣어 테이블 접근을 줄이는 최적화

전통적인 인덱스 스캔은 "인덱스에서 PK 찾기 → 테이블 페이지 읽기 → WHERE 조건 필터링" 순서로 도는데, ICP는 인덱스에 포함된 컬럼 조건을 스토리지 엔진(InnoDB) 레벨에서 먼저 걸러버린 다음, 살아남은 행만 테이블에서 읽어온다. 즉 인덱스에 있지만 인덱스의 선두 컬럼이 아니라 옵티마이저가 원래는 "테이블 읽고 나서 판단"할 조건을, "테이블 읽기 전에 판단"으로 바꿔준다. `EXPLAIN`에서 `Extra: Using index condition`이 뜨면 활성화된 것이고, 이게 없으면 불필요한 랜덤 I/O가 폭발한다.

```sql
-- 인덱스: (last_name, first_name) 복합
SELECT * FROM users
WHERE last_name LIKE 'K%'    -- 인덱스 선두 컬럼: 범위 스캔 시작
  AND first_name = 'Jinyeong'; -- 인덱스에 있지만 선두가 아님

-- ICP OFF: last_name='K%' 매칭 5만 건 → 테이블 5만 번 접근 → first_name 필터링
-- ICP ON:  last_name='K%' + first_name='Jinyeong' 인덱스에서 미리 걸러냄 → 테이블 접근 12번
```

> 💡 **왜 중요한가**: 인덱스를 "탔다"고 안심하지 마라 — ICP가 꺼져 있으면 인덱스 매칭 건수만큼 테이블 랜덤 I/O가 발생하고, 이게 대부분의 "인덱스 있는데 왜 느려요?"의 정답이다.
