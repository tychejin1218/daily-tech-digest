### `@Cacheable`의 `self-invocation` 함정 — 같은 클래스 내부 호출은 캐시를 완전히 무시한다

`@Cacheable`은 Spring AOP 프록시 기반이라 **외부에서 프록시를 통해 호출**될 때만 동작한다. 같은 클래스 내부에서 `this.getUser()`처럼 호출하면 프록시를 거치지 않고 실체 객체의 메서드가 그대로 실행되므로, 캐시 조회도 저장도 일어나지 않는다. `@Transactional`, `@Async`, `@Retryable` 등 모든 프록시 기반 어노테이션이 동일한 함정을 공유한다.

```java
@Service
public class UserService {

    @Cacheable("users")
    public User getUser(Long id) {
        return userRepository.findById(id).orElseThrow();
    }

    // ❌ 캐시 무시됨 — 매번 DB 조회
    public List<User> getUsers(List<Long> ids) {
        return ids.stream()
                  .map(this::getUser)  // this = 실체 객체, 프록시 아님
                  .toList();
    }
}
```

```
[외부 호출]                       [내부 호출]
Client → Proxy → getUser()      Client → Proxy → getUsers()
         ↓ (캐시 확인)                    ↓
         Target.getUser()                Target.getUsers()
         ✅ 캐시 동작                       ↓ this.getUser()
                                          ❌ 프록시 우회
                                          ❌ 캐시 미동작
```

**해결책 3가지 트레이드오프**:

| 방법 | 장점 | 단점 |
|------|------|------|
| 클래스 분리 (권장) | 명확한 책임 분리 | 클래스 하나 더 생김 |
| `AopContext.currentProxy()` | 같은 클래스에서 해결 | `exposeProxy = true` 설정 필요, 결합도 증가 |
| Self-injection (`@Autowired private UserService self`) | 간단함 | 순환 참조처럼 보여 리뷰어를 혼란시킴 |

```java
// ✅ 해결: 자기 자신을 프록시로 주입
@Service
public class UserService {
    @Autowired @Lazy
    private UserService self;  // 프록시로 주입됨

    public List<User> getUsers(List<Long> ids) {
        return ids.stream()
                  .map(self::getUser)  // ✅ 프록시 경유, 캐시 동작
                  .toList();
    }
}
```

**실제 사례**: 상품 목록 페이지에서 100개 상품의 카테고리를 조회하는데 `getCategory()`가 `@Cacheable`이었지만 같은 서비스 내부에서 스트림으로 호출. 캐시 히트율 0%, DB에 초당 수천 쿼리가 쏟아지고서야 원인 발견. 로그로도 안 잡혀서 프로파일러로 겨우 추적.

> 💡 **왜 중요한가**: `@Cacheable`을 붙였다는 이유만으로 "캐시된다"고 믿는 순간, 진짜 캐시되는지 검증하지 않게 되고 프로덕션 부하가 몇 배로 튀어도 원인을 못 찾는다.

### `@RequestBody` DTO에 `final` 필드 + `@NoArgsConstructor`가 조용히 `null`을 만드는 이유

Jackson은 기본적으로 **리플렉션으로 필드에 직접 값을 주입**한다. Lombok의 `@RequiredArgsConstructor`로 만든 생성자가 있어도, `@NoArgsConstructor(force = true)`가 우선순위를 가지거나 Jackson이 기본 생성자를 찾으면 필드가 `null`/`0`으로 초기화된 채 객체가 만들어질 수 있다. `final` 필드는 리플렉션으로 다시 세팅되긴 하지만, `record`가 아닌 이상 **Jackson이 어떤 생성자를 선택하는지 명시적으로 통제하지 않으면 예측 불가**하다.

```java
// ❌ 위험한 패턴 — 어떤 생성자가 선택될지 불명확
@Getter
@NoArgsConstructor(force = true)   // Jackson이 이걸 쓰면 → 모든 필드 null
@AllArgsConstructor
public class UserRequest {
    private final String name;
    private final Integer age;
}

// 요청: {"name": "홍길동", "age": 30}
// 결과: name=null, age=null (Jackson 버전/설정에 따라)
```

```
[Jackson 역직렬화 과정]

JSON 파싱
   ↓
생성자 선택
   ├─ @JsonCreator 있음? → 명시된 생성자 사용 ✅
   ├─ 기본 생성자만 있음? → 기본 생성자 + 필드 주입
   └─ 여러 생성자 있음? → ???  (버전마다 다름)
                          ↓
                    force=true라면 null로 초기화
                    이후 세터/필드 주입 시도
                    → 필드가 final이면 실패할 수도, 성공할 수도
```

**3가지 안전한 대안**:

```java
// ✅ 방법 1: record (Java 16+)
public record UserRequest(String name, Integer age) {}

// ✅ 방법 2: @JsonCreator로 명시적 지정
public class UserRequest {
    private final String name;
    private final Integer age;

    @JsonCreator
    public UserRequest(
        @JsonProperty("name") String name,
        @JsonProperty("age") Integer age
    ) {
        this.name = name;
        this.age = age;
    }
}

// ✅ 방법 3: Jackson 모듈 등록 (Spring Boot 자동 등록됨)
// jackson-module-parameter-names + -parameters 컴파일 옵션
public class UserRequest {
    private final String name;
    private final Integer age;

    // 파라미터 이름이 JSON 키와 일치하면 자동 매핑
    public UserRequest(String name, Integer age) { ... }
}
```

**함정 비교표**:

| 패턴 | 동작 | 위험도 |
|------|------|--------|
| `record` | 정식 컴포넌트 접근자 사용 | 안전 |
| `@JsonCreator` 명시 | 개발자 의도대로 | 안전 |
| Lombok `@AllArgsConstructor` + `-parameters` | 이름 매칭 성공 | 안전 |
| Lombok `@NoArgsConstructor(force=true)` | 필드 null 초기화 | **위험** |
| Lombok `@Data` (기본 생성자 + 세터) | 세터로 주입 (final 불가) | 주의 |

**실제 사례**: `@NoArgsConstructor(force = true)`를 IDE 자동 완성으로 추가한 후, 요청 필드가 조용히 `null`로 들어와 NPE가 서비스 계층에서 터짐. 컨트롤러 로그에는 요청이 정상 수신된 걸로 찍혀서 클라이언트 잘못인 줄 알고 반나절 소비.

> 💡 **왜 중요한가**: DTO 역직렬화는 "그냥 되는 것"처럼 보이지만, 생성자 선택 로직은 Jackson 버전·Lombok 설정·컴파일 옵션의 3중 조합에 의존하며, 조용히 실패하면 프로덕션에서만 발현된다.
