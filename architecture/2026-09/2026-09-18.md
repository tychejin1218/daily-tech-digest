### Chunking 전략 — "그냥 500자로 자르면 되지"라는 순진함, 그리고 법무팀이 3주 검토한 계약서 조항이 문장 한복판에서 잘려 챗봇이 "해당 계약에 위약금 조항은 없습니다"를 사장님 앞에서 자신 있게 답변한 새벽

## 1. 왜 이 문제가 RAG의 뿌리인가

RAG 파이프라인의 다른 모든 요소 — 임베딩 모델, Vector DB, Reranker, Hybrid Search, Query Rewriting — 이 아무리 좋아도, **chunk 자체가 잘못 잘려 있으면 시스템은 원리적으로 정답을 찾을 수 없다.** 정답이 들어있는 문서 조각이 이미 "정답 없는 조각"으로 변형돼 인덱스에 들어가 있기 때문이다.

시니어 관점에서 이렇게 정리하자:

> Retrieval의 상한선은 embedding 품질이 아니라 **chunking 품질**이 결정한다.
> Embedding은 이미 있는 의미를 벡터로 옮길 뿐이고, chunking은 **의미의 단위 자체를 정의**하는 작업이다.

그런데 대부분의 팀은 이 결정을 `RecursiveCharacterTextSplitter(chunk_size=1000, overlap=200)` 한 줄로 끝낸다. 이게 왜 위험한지 하나씩 보자.

---

## 2. 사고 회로: "왜 chunking이 필요한가"부터 다시

Chunking을 하는 이유는 3가지가 겹쳐 있다. 대부분의 팀이 이 3가지를 구분하지 않고 하나의 값(chunk_size=1000)으로 뭉뚱그린다.

| 목적 | 제약 | 적정 크기 결정 요인 |
|---|---|---|
| **Embedding 품질 확보** | Embedding 모델의 context window (보통 512~8192 token). 너무 길면 벡터가 "평균화"돼서 특정 세부 사실을 잃음 | 모델의 "sweet spot" (ada-002는 ~512 token, voyage-3는 ~1024 token) |
| **Retrieval 정밀도** | 너무 크면 무관한 내용이 섞여 관련성 점수가 희석됨. 너무 작으면 문맥이 잘려서 의미 파편화 | 문서의 "의미 단위" (문단, 절, 조항) |
| **LLM Context 절약** | Top-k 개의 chunk를 프롬프트에 넣어야 하므로, chunk가 크면 top-k를 줄여야 함 | LLM context window / top-k / 프롬프트 여유 공간 |

이 3가지 목적은 **서로 상충한다**. Embedding은 짧을수록 정밀하고, Retrieval은 적당한 문맥이 필요하고, LLM은 큰 청크에 answer가 온전히 담기길 원한다. Chunking 전략의 본질은 이 세 축의 트레이드오프를 어떻게 해소할 것인가다.

## 3. Chunking 전략의 스펙트럼

```
[순진함]                                                      [엔지니어링]
   │                                                              │
   ▼                                                              ▼
Fixed-size ──> Recursive ──> Document-aware ──> Semantic ──> Parent-Child
(N자 자르기)   (구분자 우선)   (구조 인식)         (의미 경계)    (검색/전달 분리)
   │              │                │                │              │
문서 파괴      문단 보존 시도    Markdown/PDF      Embedding으로   작은 청크로 찾고
                                구조 활용         의미 경계 탐지  큰 청크로 전달
```

각 전략을 시니어가 알아야 할 수준에서 파헤쳐 보자.

### 3.1 Fixed-size Chunking (기저의 죄)

```python
chunks = [text[i:i+1000] for i in range(0, len(text), 800)]  # overlap 200
```

**언제 이걸 쓰나**: 프로토타입, 데모, 데이터가 정말 균질한 경우 (예: 트윗 스트림, 로그 라인).

**왜 프로덕션에서 죽나**:
- 문장 중간에서 잘림 → embedding이 "반쪽 문장"의 의미를 학습
- 조항/표/코드 블록의 경계를 무시 → 계약서 위약금 조항이 3개 chunk에 나뉘어 어느 것도 "위약금"이라는 온전한 의미를 갖지 못함
- Retrieval에서 "위약금은?" 질의 시, 정답을 담은 chunk가 아니라 "위약금이 아니라"로 시작하는 chunk가 top-1에 뽑히는 사고

### 3.2 Recursive Chunking (LangChain 기본값의 함정)

```python
RecursiveCharacterTextSplitter(
    separators=["\n\n", "\n", " ", ""],
    chunk_size=1000,
    chunk_overlap=200,
)
```

문단 단위로 우선 자르고, 크면 문장, 그것도 크면 단어, 마지막엔 문자. 대부분의 팀이 여기서 멈춘다.

**개선점**: Fixed-size보다는 문장 경계를 존중.
**여전한 문제**:
- `chunk_size`가 절대적 기준이라 **긴 조항**은 여전히 중간에서 잘림
- **표(Table)**의 행이 문단으로 인식되지 않아 파괴됨
- **코드 블록**이 공백으로 잘리면 구문 오류 발생, embedding이 "코드가 아닌 텍스트"로 처리
- 한국어의 경우 `\n\n`이 없는 문서(PDF에서 추출한 텍스트)에서는 사실상 fixed-size로 퇴화

### 3.3 Document-aware Chunking (구조를 살리는 첫걸음)

문서 타입별로 파서를 다르게 쓴다:

| 문서 타입 | 자르는 단위 | 도구 |
|---|---|---|
| Markdown | `#`, `##`, `###` 헤더 | `MarkdownHeaderTextSplitter` |
| HTML | `<h1>`, `<section>`, `<div>` | `HTMLHeaderTextSplitter`, `unstructured` |
| PDF | 페이지/섹션/표 | `Unstructured`, `LlamaParse`, `Azure Document Intelligence` |
| 코드 | 함수/클래스 (AST 기반) | `tree-sitter`, `LanguageParser` |
| 법률 문서 | 조항/항/호 (정규식) | 커스텀 파서 |

**이 단계부터 chunk에 metadata를 붙이기 시작해야 한다**:

```json
{
  "content": "제12조 (위약금) ① 갑이 계약을 임의로 해지할 경우...",
  "metadata": {
    "doc_id": "contract-2025-Q3-XX",
    "section": "제12조",
    "section_title": "위약금",
    "chapter": "제4장 계약의 해지",
    "page": 8,
    "version": "v2.1",
    "effective_date": "2025-07-01"
  }
}
```

**왜 metadata가 중요한가**: Hybrid Search의 필터링, Reranker의 시그널, 그리고 LLM에게 "이 정보는 계약서 제12조에서 왔습니다"라고 인용할 근거를 준다. Hallucination을 잡는 첫 방어선이다.

### 3.4 Semantic Chunking (의미 경계로 자른다)

각 문장을 embedding하고, **인접 문장의 코사인 유사도가 크게 떨어지는 지점**을 경계로 삼는다.

```
문장1 ──sim=0.87── 문장2 ──sim=0.85── 문장3 ──sim=0.31── 문장4 ──sim=0.89── 문장5
                                              ▲
                                       여기가 chunk 경계
```

**장점**: 주제가 바뀌는 지점을 자동으로 찾아냄. "위약금 조항"과 "손해배상 조항"이 자연스럽게 분리됨.

**단점**:
- Ingestion 비용 폭증 (문서마다 문장 단위 embedding 필요)
- 임베딩 모델의 sensitivity에 따라 결과가 크게 달라짐
- 짧은 문서에서는 오히려 과분할

**실제로 쓰나**: Anthropic이 자사 문서 검색용으로 실험한 결과, semantic chunking이 recursive 대비 recall@10에서 5~8%p 개선. 다만 ingestion 비용이 4배 증가. **대용량 정적 문서(법률, 논문, 매뉴얼)에는 유효, 실시간 문서 인덱싱에는 부담.**

### 3.5 Parent-Child Chunking (검색 단위와 전달 단위의 분리) — **시니어가 반드시 알아야 할 패턴**

이 전략이 나머지 모든 chunking 논쟁의 절반을 해소한다.

**아이디어**:
- **검색용 chunk (child)**: 작게 (예: 200 token). Embedding 정밀도 극대화.
- **컨텍스트 전달용 chunk (parent)**: 크게 (예: 2000 token). LLM에 온전한 문맥 제공.
- 검색은 child로 하고, **hit한 child의 부모 chunk를 LLM에 전달**한다.

```
[Ingestion]
  Document
     │
     ├─ Parent Chunk A (문단 전체, 2000 tok) ────┐
     │    ├─ Child A-1 (한 문장, 150 tok) ──┐    │
     │    ├─ Child A-2                    │    │
     │    └─ Child A-3                    │    │
     │                                    ▼    │
     │                            [Vector Index] │
     │                                    │    │
     └─ Parent Chunk B ...                │    │
                                          │    │
[Retrieval]                               │    │
  Query ──embed──> search Vector Index ◄──┘    │
                        │                      │
                        ▼                      │
                   Child A-2 (top-1)           │
                        │                      │
                        └── lookup parent ─────┘
                                    │
                                    ▼
                             Parent Chunk A
                                    │
                                    ▼
                              LLM Context
```

**왜 이게 강력한가**:
- Embedding은 짧은 chunk로 정밀하게 → "위약금은 계약 종료 후 30일 이내에 지급한다"라는 딱 그 문장이 top-1에 뽑힘
- LLM은 그 문장이 속한 조항 전체를 받음 → "제12조 전체 문맥" 위에서 답변 생성
- Top-k를 줄일 수 있음 → 프롬프트 비용/latency 절감

**실제 프로덕션 사례**:
- **LangChain의 `ParentDocumentRetriever`**: 이 패턴을 표준화. 실제 엔터프라이즈 RAG의 사실상 기본값.
- **Notion Q&A**: Notion 페이지의 block 단위로 child, 페이지 단위로 parent. 사용자가 "회의록에서 결정된 예산 항목 알려줘" 물으면 특정 bullet이 hit하고 회의록 전체 섹션이 컨텍스트로 전달됨.
- **국내 A사 법률 리서치 챗봇** (익명): 조문 단위 parent, 조문 내 문장 단위 child. Semantic chunking 대비 ingestion 비용 1/3, recall@5 동등.

### 3.6 Contextual Retrieval (Anthropic 2024) — Parent-Child의 진화형

Anthropic이 2024년 9월 발표한 방식. 각 chunk를 embedding하기 전에 **LLM으로 "이 chunk가 문서 전체에서 어떤 맥락인지 한 문장으로 설명"을 붙인다**.

```
Original chunk: "위약금은 계약 종료 후 30일 이내에 지급한다."

Contextualized:
"이 조항은 XX주식회사와 YY법인 간 소프트웨어 라이선스 계약서(v2.1, 2025-07-01 발효)의
제12조 위약금 규정 중 지급 시기에 관한 부분이다.
위약금은 계약 종료 후 30일 이내에 지급한다."
```

Anthropic 자체 벤치마크에서 실패율(failed retrievals)이 **35% 감소**. Reranker와 결합 시 67% 감소.

**단점**: Ingestion 시 chunk당 LLM 호출 1회 필요. 대용량 코퍼스에서 비용 폭증 (100만 chunk × Haiku 호출 ≈ $500~$1000). **Prompt Caching으로 문서 전체를 캐싱해서 비용을 90% 절감하는 것이 핵심 팁**.

## 4. Chunking 파라미터를 결정하는 시니어의 사고 프레임

```
                    ┌─────────────────────────────┐
                    │  1. 답변할 질문의 "정보 단위"?  │
                    │  (사실 1개? 조항 전체? 절차?) │
                    └───────────────┬─────────────┘
                                    │
                    ┌───────────────▼─────────────┐
                    │  2. 원본 문서의 "의미 단위"?  │
                    │  (문단? 조항? 페이지? 챕터?)  │
                    └───────────────┬─────────────┘
                                    │
                    ┌───────────────▼─────────────┐
                    │ 3. Embedding 모델 sweet spot? │
                    │ (ada-002: 512, voyage: 1024)  │
                    └───────────────┬─────────────┘
                                    │
                    ┌───────────────▼─────────────┐
                    │ 4. LLM에 몇 개 넘길 것인가?   │
                    │ (top-k × chunk_size < 유효 ctx) │
                    └───────────────┬─────────────┘
                                    │
                                    ▼
                     [chunking 전략 & 파라미터 결정]
```

**절대 하지 말 것**: "일단 1000자로 하고 나중에 튜닝하자"는 관성. Chunking을 바꾸면 **인덱스 전체 재구축**이 필요하다. 5억 벡터를 재임베딩하며 3일간 정확도가 랜덤에 수렴하는 경험은 [[embedding-model-versioning]]에서 이미 다뤘다. Chunking 변경도 정확히 같은 급의 사건이다.

## 6. 언제 쓰고 언제 쓰면 안 되는가

### 반드시 정교한 chunking을 써야 하는 경우
- **법률/의료/금융 문서**: 한 문장의 오독이 소송/의료사고/규제 위반으로 이어짐 → Parent-Child + Contextual 조합, metadata 필수
- **매뉴얼/절차 문서**: "다음 단계"의 연결성이 중요 → Document-aware + Semantic
- **장문의 계약서/논문**: 조항/섹션 구조가 명확 → Document-aware가 필수, Recursive는 절대 금지
- **다국어/한국어 PDF**: 개행 정보가 손실됨 → 파서 선택이 chunker 선택보다 중요 (`LlamaParse`, `Upstage Document AI` 등)

### 굳이 정교화하지 않아도 되는 경우
- **FAQ 데이터**: 이미 Q-A 쌍으로 구조화됨 → Q + A를 하나의 chunk로. Chunking 논쟁 자체가 무의미
- **짧은 스니펫 코퍼스** (트윗, 상품 설명, 리뷰): 문서 하나가 이미 하나의 chunk. 자르지 마라
- **프로토타입/PoC**: Recursive 기본값으로 시작. 다만 "본 서비스 전에 무조건 재검토"를 팀 문화로

### 함정 (시니어가 반드시 경계할 것)
- **"큰 chunk가 좋다"는 착각**: LLM context가 커졌으니 chunk도 키우면 되지 않냐? → Embedding이 평균화돼 특정 사실을 못 잡음. Retrieval 정밀도가 무너짐.
- **"작을수록 정밀하다"는 착각**: chunk를 100 token으로 쪼갰더니 문맥이 없어서 LLM이 "답을 알 수 없다"만 반복.
- **overlap으로 다 해결된다는 착각**: overlap 200은 문장 경계 문제를 완화할 뿐, 조항 경계나 표 경계 문제는 해결 못 함. 게다가 인덱스 크기와 중복 검색만 늘어남.
- **chunking을 한 번 정하면 안 바꿔도 된다는 착각**: 사용자 질의 패턴이 바뀌면 chunking도 바뀌어야 한다. **RAG 시스템에서 chunking은 코드가 아니라 하이퍼파라미터다** — 정기적 평가와 재튜닝이 필요.

## 7. 검증: chunking이 잘 됐는지 어떻게 아나

Chunking 품질은 최종 답변 품질에 녹아들어 원인을 특정하기 어렵다. 다음 지표를 분리해서 추적해야 한다:

| 지표 | 정의 | 도구 |
|---|---|---|
| **Chunk Coherence** | 한 chunk 안의 문장들이 한 주제인가 (LLM-as-judge) | 커스텀, RAGAS |
| **Chunk Completeness** | 정답이 chunk 내부에 온전히 담기는가 | Golden set 수동 검증 |
| **Retrieval Recall@k** | 정답 chunk가 top-k에 들어오는가 | RAGAS, TruLens |
| **Answer Faithfulness** | LLM 답변이 chunk 내용에 근거하는가 | RAGAS `faithfulness` |

[[llm-evaluation-regression-testing]]에서 다룬 대로, **chunking 변경도 프롬프트 변경과 동일하게 regression test 대상**이다. "chunk_size를 800→1200으로 바꿨더니 벤치마크가 +2%p"라는 결과 하나로 배포하면, 특정 유형의 질의(긴 조항 검색)에서만 정확도가 무너지는 실패를 놓친다.

## 8. 최소 실전 조합 (2026년 기준 권장)

**엔터프라이즈 문서 RAG를 처음 만든다면**:

1. **파서**: 문서 타입별로 분리 (Markdown/PDF/HTML), PDF는 `LlamaParse` 또는 `Upstage`
2. **Chunking**: Document-aware → Parent-Child
   - Parent: 섹션/조항 단위 (~2000 token)
   - Child: 문장 2~3개 단위 (~200 token)
3. **Metadata**: `doc_id`, `section`, `version`, `effective_date`, `access_level` 필수
4. **Contextual prefix**: 여유 예산이 있으면 Anthropic 방식 도입, Prompt Caching으로 비용 절감
5. **검증**: Golden set 100개로 recall@5, faithfulness 모니터링, 월 1회 재평가

이 5단계를 지키면 대부분의 RAG 실패 사례(엉뚱한 조항 인용, 잘린 문장, 오래된 문서 참조)의 80%가 사라진다.

---

> 💡 **왜 중요한가**: RAG의 정확도는 embedding 모델을 바꿔도 5%p 오르지만, chunking을 제대로 하면 30%p 오른다 — 시스템의 상한선을 결정하는 것은 벡터가 아니라 **자르는 방식**이다.
