### `@Cacheable(sync = true)`로 캐시 stampede(쇄도) 방지하기

여러 스레드가 동시에 캐시 미스(miss)를 일으키면 같은 비싼 연산(DB 조회, 외부 API 호출)이 동시 다발적으로 실행되어 백엔드에 부하가 몰리는 stampede 현상이 발생합니다. `@Cacheable(sync = true)` 옵션을 켜면 Spring이 캐시 키 단위로 락을 걸어 동일 키에 대해 단 하나의 스레드만 실제 메서드를 실행하고, 나머지는 그 결과를 기다린 뒤 동일한 값을 받아갑니다. 단, `unless`/`condition`/다중 캐시(`cacheNames`가 2개 이상)와는 함께 사용할 수 없다는 제약이 있습니다.

```java
@Cacheable(cacheNames = "products", key = "#id", sync = true)
public Product findProduct(Long id) {
    return productRepository.findById(id).orElseThrow();
}
```

> 💡 **왜 중요한가**: 트래픽 급증이나 인기 상품 노출 같은 hot key 상황에서 캐시 만료 직후 동시 요청이 DB로 쏟아져 장애로 번지는 것을 한 줄 옵션으로 막을 수 있습니다.

### `@PostFilter`로 Spring Security가 반환 컬렉션을 권한에 따라 자동 필터링하기

서비스가 컬렉션을 반환할 때 "사용자가 볼 수 있는 항목만" 남기는 로직을 직접 작성하면 누락·중복이 잦고 테스트도 어렵습니다. `@PostFilter`는 메서드 반환값(Collection/Stream/Array)을 순회하며 SpEL이 `true`로 평가된 요소만 통과시키는 선언적 필터로, `filterObject` 변수로 각 요소에 접근하고 `hasRole()`·`@beanName.method()` 같은 보안 표현식을 그대로 사용할 수 있습니다. 단, 큰 컬렉션에 대해서는 전체를 로드한 뒤 필터링하므로 페이지네이션이 필요한 경우 쿼리 레벨에서 거르는 편이 낫습니다.

```java
@PostFilter("filterObject.ownerId == authentication.principal.id or hasRole('ADMIN')")
public List<Document> findAllDocuments() {
    return documentRepository.findAll();
}
```

> 💡 **왜 중요한가**: 권한 검사 로직이 도메인 코드에서 사라지고 메타데이터로 분리되어, 보안 정책 변경 시 어노테이션만 수정하면 되며 누락된 검사 지점도 일관되게 추적할 수 있습니다.
