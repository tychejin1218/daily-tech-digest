### `@Transactional`의 `rollbackFor` 기본값은 `RuntimeException`뿐, `checked exception`은 커밋된다

Spring의 `@Transactional`은 기본적으로 `RuntimeException`과 `Error`만 롤백 대상으로 삼는다. `IOException`, `SQLException` 같은 checked exception이 발생해도 트랜잭션은 **정상 커밋**되며, DB 상태가 어중간하게 남는 유령 데이터가 생긴다. 이를 막으려면 `@Transactional(rollbackFor = Exception.class)`를 명시하거나, 아예 checked exception을 던지지 않는 설계를 하거나, `throw new RuntimeException(e)`로 래핑해야 한다.

```java
@Transactional  // 함정: IOException은 롤백 안 됨
public void uploadAndSave(MultipartFile file) throws IOException {
    fileRepository.save(new FileEntity(file.getOriginalFilename()));
    file.transferTo(new File("/tmp/upload"));  // ← IOException 발생
    // ↑ 예외 나도 fileRepository.save()는 커밋됨. DB엔 있는데 파일은 없음
}

@Transactional(rollbackFor = Exception.class)  // 해결
public void uploadAndSafe(MultipartFile file) throws IOException { ... }
```

> 💡 **왜 중요한가**: "예외 던졌으니 롤백되겠지"라는 상식적 기대가 checked exception에서만 조용히 배신당하고, 그 결과는 "DB에는 있는데 실제로는 없는" 유령 데이터라는 최악의 데이터 불일치로 이어진다.

### `@Primary`와 `@Qualifier`를 같이 쓰면 `@Qualifier`가 이긴다 — 그리고 이걸 몰라서 잘못된 빈이 주입된다

같은 타입의 빈이 여러 개일 때 `@Primary`는 "특별한 지정이 없으면 나를 써라"라는 **디폴트 규칙**이고, `@Qualifier`는 "이걸 명시적으로 골라라"라는 **명시적 지정**이다. 둘이 충돌하면 `@Qualifier`가 우선하는데, 문제는 `@Qualifier("이름오타")`를 써도 컴파일 에러가 안 나고 런타임에 `NoSuchBeanDefinitionException`이 터진다는 점이다. 더 위험한 케이스는 `@Qualifier` 이름이 우연히 다른 빈과 일치할 때 — 의도한 `@Primary` 빈이 아닌 엉뚱한 빈이 주입되고 아무도 눈치채지 못한다.

```java
@Primary @Bean("mysqlDataSource")
public DataSource mysql() { ... }

@Bean("readReplicaDataSource")
public DataSource replica() { ... }

// 실수: @Qualifier가 @Primary를 오버라이드해서 replica가 주입됨
@Autowired
@Qualifier("readReplicaDataSource")
private DataSource dataSource;  // 쓰기 쿼리가 replica로 날아가는 사고
```

> 💡 **왜 중요한가**: `@Primary`를 걸어놨으니 안전하다고 착각하지만, 팀원 누군가 `@Qualifier`를 무심코 추가하는 순간 우선순위가 뒤집혀 쓰기 트래픽이 읽기 전용 replica로 흘러가는 조용한 프로덕션 사고가 벌어진다.
