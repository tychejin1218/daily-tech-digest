### PostgreSQL `SKIP LOCKED` — 다중 워커 큐에서 같은 행을 두 번 처리하지 않게 하기

`SELECT ... FOR UPDATE SKIP LOCKED`는 다른 트랜잭션이 이미 잠근 행을 건너뛰고 잠글 수 있는 행만 반환한다. Redis·Kafka 없이 순수 RDB만으로 안전한 작업 큐를 구현할 수 있어, 워커가 여러 개여도 각자 다른 행을 잡아 병렬 처리하고 중복 소비가 발생하지 않는다.

```sql
-- 워커가 처리할 작업 하나를 원자적으로 선점
BEGIN;
SELECT id, payload
  FROM jobs
 WHERE status = 'pending'
 ORDER BY created_at
 LIMIT 1
 FOR UPDATE SKIP LOCKED;   -- 이미 잠긴 행은 스킵

UPDATE jobs SET status = 'processing' WHERE id = :id;
COMMIT;
```

`NOWAIT`은 락을 기다리다 즉시 에러를 던지지만, `SKIP LOCKED`는 조용히 다음 후보로 넘어가기 때문에 폴링 워커의 CPU 낭비 없이 자연스러운 로드 밸런싱이 된다. PostgreSQL 9.5+ / MySQL 8.0+ 모두 지원.

> 💡 **왜 중요한가**: 별도 메시지 브로커 도입 없이도 RDB 트랜잭션 하나로 "정확히 한 번 처리"되는 큐를 만들 수 있다.

### JPA `@DynamicUpdate` — 변경된 컬럼만 `UPDATE`문에 포함시켜 인덱스·트리거 부하 줄이기

Hibernate는 기본적으로 엔티티의 모든 컬럼을 `UPDATE` SQL에 포함시키는데, `@DynamicUpdate`를 붙이면 dirty checking으로 실제 변경된 컬럼만 골라 SQL을 재생성한다. 100개 컬럼 중 1개만 바꿔도 `UPDATE t SET c1=?, c2=? ... c100=? WHERE id=?`가 나가던 문제가 사라진다.

```java
@Entity
@DynamicUpdate
public class Product {
    @Id private Long id;
    private String name;
    private BigDecimal price;   // 이 필드만 변경했다면
    private String description; // 이 필드는 UPDATE에서 제외됨
    // ... 수십 개 컬럼
}
```

트리거·감사 로그가 컬럼 변경을 기준으로 동작하는 테이블, 인덱스가 많이 걸린 넓은 테이블에서 특히 효과가 크다. 다만 SQL이 매번 다르게 생성되어 DB의 statement cache 히트율이 떨어지므로, 컬럼이 적은 좁은 테이블에는 오히려 손해다.

> 💡 **왜 중요한가**: 넓은 테이블에서 불필요한 컬럼 갱신으로 인한 인덱스 재계산·트리거 오작동·리플리케이션 대역폭 낭비를 한 줄 어노테이션으로 막는다.
