### 1. `@HttpExchange` 인터페이스로 선언적 HTTP 클라이언트 만들기 (Spring 6+)

`WebClient`나 `RestClient`로 외부 API 호출 코드를 직접 짜는 대신, 인터페이스에 `@HttpExchange`·`@GetExchange`·`@PostExchange`를 선언하고 `HttpServiceProxyFactory`로 프록시를 생성하면 Feign과 유사한 타입 안전 클라이언트가 만들어집니다. 메서드 시그니처가 곧 API 계약이 되므로 호출부가 깔끔해지고, 어댑터(`RestClientAdapter`/`WebClientAdapter`)만 바꾸면 동기/비동기 전환도 한 줄로 끝납니다.

```java
public interface UserApiClient {
    @GetExchange("/users/{id}")
    User findById(@PathVariable Long id);
}

@Bean
UserApiClient userApiClient(RestClient.Builder builder) {
    RestClient client = builder.baseUrl("https://api.example.com").build();
    return HttpServiceProxyFactory.builderFor(RestClientAdapter.create(client))
            .build()
            .createClient(UserApiClient.class);
}
```

> 💡 **왜 중요한가**: 호출 코드가 URL·헤더 빌더 보일러플레이트 없이 도메인 메서드로 표현되어 가독성과 테스트 용이성이 동시에 좋아집니다.

### 2. JPA `@Lock(LockModeType.PESSIMISTIC_WRITE)`로 재고/잔액 같은 경쟁 조건 차단하기

낙관적 락(`@Version`)만으로 막기 어려운 “읽고-수정-쓰기” 시나리오(재고 차감, 포인트 차감, 좌석 선점 등)는 Repository 메서드에 `@Lock(LockModeType.PESSIMISTIC_WRITE)`을 붙여 DB 행 단위 `SELECT ... FOR UPDATE`로 직접 잠그면 안전합니다. 다만 트랜잭션 범위를 짧게 유지하고, `jakarta.persistence.lock.timeout` 힌트로 대기 시간을 제한해야 전체 트래픽이 락 대기로 멈추는 사태를 피할 수 있습니다.

```java
public interface StockRepository extends JpaRepository<Stock, Long> {
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))
    @Query("select s from Stock s where s.id = :id")
    Optional<Stock> findByIdForUpdate(@Param("id") Long id);
}
```

> 💡 **왜 중요한가**: 충돌 빈도가 높은 자원에서는 낙관적 락 재시도 비용보다 비관적 락의 직렬화가 더 저렴하고, 데이터 정합성을 DB 계층에서 단번에 보장할 수 있습니다.
