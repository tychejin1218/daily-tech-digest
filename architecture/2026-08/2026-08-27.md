### LLM Routing/Fallback — "OpenAI 하나면 다 된다"는 배짱, 그리고 오전 9시 Azure East US 리전 장애로 전체 챗봇이 27분간 백지가 된 방식

#### 1. 왜 이 이야기를 하는가

프로덕션에 LLM을 붙일 때 백엔드 팀이 가장 먼저 저지르는 실수는 두 개다.

- **가용성 착시**: "OpenAI가 설마 죽겠어?" — 2023-11-08 OpenAI 6시간 다운, 2024년 이후 Azure OpenAI 리전 부분 장애 다수. 단일 provider = 단일 실패 지점.
- **비용 착시**: "GPT-4-turbo 하나로 다 처리하자, 심플하게" — 월말에 청구서 보면 요약 요청 하나에 $0.03이 붙고, 트래픽 스파이크 한 번에 예산 40% 초과. FAQ 응답에 GPT-4를 쓰는 건 `SELECT id FROM users WHERE id=1`에 Snowflake를 쓰는 것과 같다.

LLM Routing과 Fallback은 서로 다른 문제를 푸는 두 축이다. 시니어는 이걸 반드시 **분리해서** 설계해야 한다.

| 축 | 최적화 대상 | 트리거 | 결정 시점 |
|---|---|---|---|
| **Routing** | 비용 / 품질 / 지연 | 요청 특성 (task, length, user tier) | **요청 진입 시 (proactive)** |
| **Fallback** | 가용성 | 에러 / 타임아웃 / rate limit | **호출 실패 시 (reactive)** |

이 둘을 하나의 if-else로 짜기 시작하는 순간 코드가 무너진다. Gateway 층에서 두 개의 다른 정책으로 관리해야 한다.

#### 2. 전체 그림

```
                    ┌─────────────────────────────────────────┐
                    │           LLM Gateway (Envoy/Kong)      │
                    │                                         │
   Request ──▶      │  ┌──────────────┐   ┌───────────────┐   │
   (user tier,      │  │   Router     │──▶│   Executor    │   │
    task type,      │  │  (Classifier)│   │ (with Fallback│   │
    max_cost)       │  └──────────────┘   │    Chain)     │   │
                    │         │           └───────┬───────┘   │
                    │         │                   │           │
                    │    ┌────▼────┐         ┌────▼─────┐     │
                    │    │ Policy  │         │ Circuit  │     │
                    │    │  Table  │         │ Breaker  │     │
                    │    └─────────┘         └──────────┘     │
                    └────────────┬────────────────────────────┘
                                 │
        ┌────────────────────────┼────────────────────────┐
        ▼                        ▼                        ▼
┌──────────────┐        ┌──────────────┐         ┌──────────────┐
│ Azure OpenAI │        │  Anthropic   │         │   Bedrock    │
│  (East US)   │        │  (Claude)    │         │  (Haiku)     │
│  Primary     │        │  Fallback-1  │         │  Fallback-2  │
└──────────────┘        └──────────────┘         └──────────────┘
        │                        │                        │
        └────────────────────────┴────────────────────────┘
                                 │
                          ┌──────▼───────┐
                          │  Telemetry   │
                          │ (LangFuse /  │
                          │  Datadog)    │
                          └──────────────┘
```

- **Router**는 요청을 보고 "누구한테 보낼까"를 정한다 (비용/품질).
- **Executor**는 실제로 호출하고, 실패하면 **Fallback Chain**을 탄다 (가용성).
- 둘 다 **Gateway 층**에 있어야지, 애플리케이션 코드에 흩뿌려지면 안 된다. (이건 이미 다룬 [[llm_gateway]] 전제)

#### 3. Routing 패턴 4가지

##### (a) Cascade Routing — "일단 작은 놈부터 던져봐"

```
Request ──▶ Haiku (small, fast, $)
             │
             ├─ Confidence >= 0.9 ──▶ 응답
             │
             └─ Confidence <  0.9 ──▶ Claude Sonnet (medium, $$)
                                       │
                                       └─ 재판단 ──▶ Opus (large, $$$)
```

- **핵심 아이디어**: 대부분의 요청은 저렴한 모델로 충분하다. 어려운 것만 escalate.
- **문제**: "Confidence"를 어떻게 정의하느냐. Log-probs? Self-reflection? Judge 모델?
  - 실무에선 **log-probability 기반** 또는 **verifier 모델** 두 가지가 주류.
- **효과**: 상용 데이터 기준 요청의 60~80%가 작은 모델에서 종결됨 → 비용 3~5배 절감.
- **함정**: cascade 자체가 2번 호출되면 오히려 비싸진다. Escalation ratio를 대시보드에서 반드시 추적.

##### (b) Classifier Routing — "요청 성격부터 파악"

```python
class RouteDecision(BaseModel):
    task_type: Literal["chitchat", "code", "reasoning", "summarize"]
    complexity: Literal["low", "med", "high"]

# 아주 작은 모델(Haiku, Gemini Flash)로 분류만 시킨다
decision = classifier_llm.classify(request)

route_table = {
    ("chitchat",  "low"):  "gpt-4o-mini",
    ("code",      "high"): "claude-opus-4",
    ("reasoning", "high"): "o1-preview",
    ("summarize", "low"):  "gemini-1.5-flash",
    # ...
}
```

- **RouteLLM**(오픈소스), **Martian**(SaaS)이 이 카테고리.
- **트레이드오프**: 분류 자체에도 지연/비용이 붙는다 (~100ms, ~$0.0001). 대신 잘못 라우팅되면 재시도 비용 > 분류 비용.
- **언제 유효**: 트래픽 종류가 매우 이질적일 때 (예: 사내 통합 어시스턴트). 단일 태스크 챗봇에선 오버엔지니어링.

##### (c) User-Tier Routing — "돈 내는 사람은 좋은 모델"

- Free 유저 → Haiku
- Pro 유저 → Sonnet
- Enterprise → Opus + 자체 fine-tuned

가장 단순하지만 가장 강력한 라우팅. Perplexity, Cursor, ChatGPT 다 이 방식.

##### (d) Latency-based Routing — "지금 이 리전 응답이 느려"

- p99 latency를 모니터링해서 느린 provider는 자동으로 트래픽 감소.
- Envoy의 **outlier detection**과 동일한 개념을 LLM 트래픽에 적용.

#### 4. Fallback Chain 설계

Fallback은 Routing보다 훨씬 더 실수하기 쉽다. 세 가지 원칙:

##### 원칙 1: 실패 종류별로 다르게 반응해야 한다

```
┌─────────────────────┬─────────────────────────────┐
│ 실패 종류           │ 반응                        │
├─────────────────────┼─────────────────────────────┤
│ 5xx / 네트워크      │ 즉시 fallback provider      │
│ 429 (rate limit)    │ 백오프 후 재시도, N번 후 F  │
│ 400 / context 초과  │ 절대 fallback 하지 말 것    │
│                     │ (다른 모델에서도 실패)      │
│ Timeout             │ 즉시 fallback               │
│ Content filter      │ 사용자에게 에러 노출        │
└─────────────────────┴─────────────────────────────┘
```

**가장 흔한 실수**: `400 context length exceeded`를 fallback 대상에 넣으면, Claude → GPT-4 → Gemini 순으로 3번 다 실패하고 결국 응답까지 8초 걸린다. 사용자는 그냥 "느리다"고 이탈.

##### 원칙 2: Circuit Breaker와 반드시 결합

- 특정 provider의 실패율이 임계치를 넘으면 일정 시간 아예 skip.
- Netflix Hystrix / resilience4j 개념 그대로.
- 이걸 안 넣으면 provider 장애 시 매 요청마다 "죽은 provider → 타임아웃 30초 → fallback"으로 처음 요청부터 지연이 30초 붙는다.

```
State: CLOSED  ──(실패율 > 50%)──▶  OPEN  ──(30s 후)──▶  HALF_OPEN
   ▲                                                        │
   └────────────────(테스트 요청 성공)──────────────────────┘
```

##### 원칙 3: Fallback도 관찰 가능해야 한다

- Fallback이 조용히 성공하면 아무도 primary가 죽은 걸 모른다.
- Datadog / [[langfuse]]에 반드시 `fallback_triggered=true` 태그.
- 알림은 "primary 실패율 > X%" 기준, 사용자 응답 성공률 기준이 아니다.

#### 5. 실제 사례

| 회사 | Routing 전략 | Fallback 전략 |
|---|---|---|
| **Perplexity** | 짧은 쿼리는 자체 fine-tuned Sonar, 긴 리서치는 GPT-4/Claude, Pro는 사용자 선택 가능 | Multi-provider (Azure OpenAI + Anthropic + 자체 인프라) |
| **Notion AI** | 요약/번역은 Haiku급, "Ask AI" 복잡 질문은 Sonnet/GPT-4 | Anthropic ↔ OpenAI 상호 fallback (2023 OpenAI 다운 이후 강화) |
| **Cursor** | Tab completion은 자체 fast model, "Compose"는 Claude Sonnet, "Agent"는 Opus | Anthropic → OpenAI → Deepseek 순 |
| **OpenRouter** | 이 자체가 Routing/Fallback을 제품화. "auto" 라우터가 요청 특성 보고 100+ 모델 중 선택 | 명시적 fallback 체인을 사용자가 config로 지정 |
| **GitHub Copilot** | 코드 컴플리션은 자체 튜닝 모델, Chat은 GPT-4o, Enterprise는 옵션 | Azure OpenAI 다중 리전 → OpenAI 직접 |

특히 주목할 만한 건 **OpenRouter**의 접근이다. 이들은 Routing/Fallback을 "인프라 개별 팀이 만들 게 아니라 SaaS로 사면 되는 것"으로 포지셔닝했다. 실제로 스타트업의 90%는 자체 gateway 짓는 것보다 OpenRouter 붙이는 게 더 빠르고 싸다.

#### 6. 트레이드오프

| 얻는 것 | 잃는 것 |
|---|---|
| 비용 30~70% 절감 (cascade 효과) | Router 자체가 새로운 실패 지점 |
| Provider 장애 시 가용성 유지 | 응답 일관성 저하 (모델마다 톤/포맷 다름) |
| Rate limit 우회 | 프롬프트 이식성 문제 (동일 프롬프트가 모델마다 다르게 반응) |
| 모델별 강점 활용 | Eval 복잡도 폭발 (모델 × 프롬프트 × 라우팅 조합) |
| Vendor lock-in 완화 | 관찰 가능성 부담 (어떤 요청이 어느 모델로 갔는지 추적) |

**응답 일관성 문제**가 실무에서 가장 뼈아프다. 예:
- Primary(Claude)는 마크다운으로 응답, Fallback(GPT-4)은 plain text. 프론트가 렌더링을 깨뜨림.
- 해결: Gateway 층에서 **응답 정규화**를 강제해야 한다. 프롬프트에 output schema를 못 박고, structured output(JSON mode)를 provider별로 매핑.

#### 7. 언제 도입하고 언제 도입하지 말 것

**도입해야 할 때**
- 프로덕션 트래픽이 하루 10만 요청 이상 → 비용 최적화 효과가 명확
- SLA가 99.9% 이상 필요 → 단일 provider로는 물리적으로 불가능 (OpenAI 자체 SLA가 99.9%)
- 요청 특성이 이질적 (짧은 FAQ + 긴 문서 요약이 섞임) → cascade가 큰 효과
- Enterprise 계약이 있어서 provider 다양화 자체가 협상 카드가 됨

**도입하지 말 것 (또는 미룰 것)**
- MVP 단계 → 그냥 GPT-4o 하나로 시작. Routing은 트래픽 데이터가 쌓인 후.
- 태스크가 단일 (예: 코드 리뷰 봇 하나) → 라우터 이득이 없음.
- 응답 일관성이 결정적으로 중요 (법률 자문, 의료) → 모델 스위칭이 오히려 리스크.
- Eval 파이프라인이 없음 → 라우팅 잘못돼도 감지 못한다. [[llm_eval_pipeline]] 먼저 갖추고 시작.

#### 8. 시니어가 놓치기 쉬운 지점

1. **Fallback 순서를 "선호도"가 아니라 "실패 상관성"으로 정하라.** OpenAI와 Azure OpenAI를 fallback으로 걸어놓는 팀이 많은데, 이 둘은 같은 인프라(Azure)에 상당 부분 의존한다. 진짜 다중화가 아니다. **Anthropic ↔ Google ↔ OpenAI**처럼 상관관계가 낮은 조합이 진짜 fallback.

2. **비용 라우팅은 "요청 단위"가 아니라 "세션 단위"로 봐야 한다.** 대화형 챗봇에서 첫 메시지만 Haiku, 이후는 Sonnet 이런 식으로 하면 컨텍스트가 뒤섞이며 응답 품질이 무너진다. 세션 시작 시점에 라우팅 결정을 고정하는 게 안전.

3. **Fallback 통계가 없으면 fallback은 없는 것과 같다.** 매주 fallback trigger 횟수, primary 실패 원인 분포를 리뷰하지 않으면, 언젠가 fallback도 조용히 죽어있다. "요청은 성공했는데 3개월간 모든 응답이 fallback provider에서 나왔다"는 실제 있는 사례.

4. **`temperature`, `max_tokens`, `stop` 파라미터가 provider마다 미묘하게 다르다.** Anthropic의 `stop_sequences` vs OpenAI의 `stop`, 토큰 세는 방식 차이. Gateway가 이걸 흡수 안 해주면 fallback 시점에 응답이 이상해진다.

---

> 💡 **왜 중요한가**: LLM은 이미 "선택적 의존성"이 아니라 "필수 인프라"다. DB에 Primary-Replica 없이 프로덕션 못 돌리듯, LLM도 단일 provider로는 프로덕션이 아니다 — Routing은 비용을, Fallback은 잠을 지켜준다.
