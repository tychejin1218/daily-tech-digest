### MySQL `Optimizer Hints`로 실행 계획 강제하기 — 통계가 왜곡됐을 때의 응급 처방

옵티마이저가 잘못된 인덱스를 선택하거나 조인 순서를 뒤집을 때 `/*+ ... */` 힌트로 실행 계획을 직접 지정할 수 있다. `SELECT /*+ INDEX(orders idx_created_at) JOIN_ORDER(users, orders) */ ...` 처럼 특정 인덱스 강제, 조인 순서 고정, `NO_MERGE`로 뷰 병합 차단 등이 가능하며, 세션·쿼리 단위로만 적용되어 스키마 변경 없이 즉시 되돌릴 수 있다.

```sql
SELECT /*+ INDEX(o idx_user_status) NO_BNL(u) */
       u.name, o.amount
  FROM users u JOIN orders o ON o.user_id = u.id
 WHERE o.status = 'PAID' AND u.region = 'KR';
```

> 💡 **왜 중요한가**: 통계가 뒤틀렸거나 옵티마이저가 오판할 때, 인덱스 재생성이나 쿼리 리라이팅 없이 곧바로 문제 쿼리를 안정화시킬 수 있는 마지막 안전장치다.

### PostgreSQL `FILTER` 절 — `CASE WHEN` 없이 조건부 집계를 깔끔하게 표현하기

`COUNT(*) FILTER (WHERE status = 'PAID')` 처럼 집계 함수에 개별 필터를 붙일 수 있어, `SUM(CASE WHEN ... THEN 1 ELSE 0 END)` 패턴을 대체한다. 가독성이 좋아질 뿐 아니라 옵티마이저가 조건을 명확히 인식해 실행 계획도 개선되며, 여러 상태를 한 번의 스캔으로 집계할 때 특히 효율적이다.

```sql
SELECT
  COUNT(*) FILTER (WHERE status = 'PAID')     AS paid_count,
  COUNT(*) FILTER (WHERE status = 'REFUNDED') AS refunded_count,
  SUM(amount) FILTER (WHERE created_at >= now() - interval '7 days') AS recent_revenue
FROM orders;
```

> 💡 **왜 중요한가**: 대시보드용 다중 상태 집계 쿼리에서 테이블을 한 번만 스캔하면서도, 중첩된 `CASE`로 뒤덮인 SQL을 한눈에 읽히는 표현으로 바꿔준다.
