### 1. `by` 위임 패턴: "상속 없이 재사용"하는 Kotlin의 숨겨진 조립 도구

Kotlin의 `by` 키워드는 두 얼굴을 가진다. 클래스 레벨에서는 **인터페이스 위임**(`class MyList(list: List<Int>) : List<Int> by list`)으로 상속 대신 조립을 강제하고, 프로퍼티 레벨에서는 **프로퍼티 위임**(`by lazy`, `by Delegates.observable`, `by map`)으로 getter/setter 로직을 외부 객체에 떠넘긴다. Java에서라면 100줄짜리 Decorator 패턴이 Kotlin에서는 한 줄로 끝난다는 뜻이다.

```kotlin
// 인터페이스 위임: Repository의 모든 메서드를 자동 위임, 로깅만 추가
class LoggingUserRepository(
    private val delegate: UserRepository
) : UserRepository by delegate {
    override fun findById(id: Long): User? {
        println("findById($id) 호출됨")
        return delegate.findById(id)
    }
}

// 프로퍼티 위임: Map을 DTO처럼 사용
class UserConfig(map: Map<String, Any?>) {
    val name: String by map
    val age: Int by map
}
```

실무에서는 **Repository 데코레이터**(캐싱, 로깅, 메트릭), **Spring Security의 UserDetails 래핑**, **설정 객체를 Map/Properties로부터 타입 안전하게 꺼내기** 같은 패턴에 자주 쓰인다. 트레이드오프는 **디버깅이 어려워진다**는 것 — IDE에서 메서드 정의로 점프하면 위임 대상이 아니라 `by` 선언으로 간다.

> 💡 **왜 중요한가**: "상속보다 조합을 선호하라"는 OOP 격언을, Kotlin은 보일러플레이트 없이 언어 레벨에서 강제한다.

### 2. `init` 블록 vs 보조 생성자: "객체 생성의 순서"를 정확히 이해하기

Kotlin의 클래스는 주 생성자(primary constructor), `init` 블록, 보조 생성자(secondary constructor)라는 세 가지 초기화 지점을 가진다. 많은 개발자가 `init`을 "생성자처럼" 생각하지만, 실행 순서는 **프로퍼티 초기화 식 → init 블록 → 보조 생성자 본문** 순서로, 선언된 위치의 순서를 따른다. 이 순서를 잘못 이해하면 **NPE가 생성자에서 터지는** 당혹스러운 버그가 발생한다.

```kotlin
class User(val name: String) {
    val upperName: String = name.uppercase()  // 1. 프로퍼티 초기화
    
    init {
        println("첫 번째 init: $upperName")   // 2. 선언 순서대로 실행
    }
    
    val greeting: String = "Hello, $name"      // 3. 프로퍼티 초기화 (순서 중요!)
    
    init {
        println("두 번째 init: $greeting")     // 4. 두 번째 init
    }
    
    // 보조 생성자: 주 생성자를 반드시 호출해야 함
    constructor(name: String, age: Int) : this(name) {
        println("보조 생성자: age=$age")        // 5. 마지막에 실행
    }
}
```

실무에서 자주 터지는 함정은 **`open` 클래스의 `init`에서 `open` 프로퍼티를 참조하는 경우**다. 자식 클래스가 해당 프로퍼티를 오버라이드하면, 부모 생성자가 실행되는 시점에 자식의 프로퍼티는 아직 초기화되지 않아 `null`이 된다(JVM의 생성자 호출 순서 때문). 그래서 **생성자/init에서 `open` 멤버 호출 금지**는 Effective Java 시절부터 내려오는 철칙이다.

> 💡 **왜 중요한가**: Spring Bean, JPA Entity, Jackson 역직렬화가 전부 "생성자 순서"에 의존하기 때문에, 이 순서를 모르면 "분명히 초기화했는데 null이 뜨는" 유령 버그를 만난다.
