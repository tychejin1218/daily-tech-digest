### 1. 커스텀 Hook을 두 컴포넌트에서 쓰면 state가 "공유"될 거라 착각하는 함정 — Hook은 "로직 재사용"이지 "인스턴스 공유"가 아니다

`useAuth()` 같은 커스텀 Hook을 `Header`와 `Sidebar`에서 각각 호출하면, 둘은 **같은 state를 보는 게 아니라 "각자 독립된 state 인스턴스"를 가진다**. 커스텀 Hook은 내부적으로 `useState`를 호출할 뿐이고, `useState`는 호출된 컴포넌트마다 별도의 저장소를 만든다. 전역적으로 "하나의 값"을 공유하려면 Context, Zustand, Redux 같은 "외부 저장소"를 끼워 넣어야 하며, 커스텀 Hook 자체는 그저 재사용 가능한 "레시피"일 뿐이다.

> 💡 **왜 중요한가**: "같은 Hook = 같은 state"라는 직관이 깨지는 순간, 로그인 상태가 헤더에만 반영되고 사이드바에는 반영 안 되는 유령 버그가 생긴다. Hook의 본질은 "함수 재사용"이지 "싱글톤"이 아니다.

### 2. `useId`를 써야 하는 진짜 이유 — `Math.random()`으로 만든 ID는 SSR hydration을 조용히 파괴한다

`<label htmlFor={id}>`에 쓸 유니크 ID를 `Math.random()`이나 `nanoid()`로 만드는 순간, **서버에서 렌더링한 HTML의 ID와 클라이언트에서 재생성된 ID가 달라져 hydration mismatch 에러가 터진다**. React 18의 `useId()`는 "컴포넌트 트리에서의 위치"를 기반으로 ID를 생성해서, 서버와 클라이언트가 **같은 ID 문자열**(`:r0:`, `:r1:` 같은)을 보장한다. 단, 리스트 아이템의 `key`에는 쓰면 안 된다 — 그건 "렌더 위치"가 아니라 "데이터 정체성"이어야 하기 때문이다.

> 💡 **왜 중요한가**: SSR 환경에서 ID 하나 잘못 만들면 접근성(label-input 연결), 폼 포커스, 스크린 리더가 전부 깨지는데, 에러는 콘솔 경고로만 조용히 뜬다. `useId`는 "접근성 ID 전용 도구"이지 범용 유니크 키 생성기가 아니라는 선을 알고 쓰는 게 핵심이다.
