### 1. React.memo의 함정: props가 바뀌지 않아도 리렌더링되는 진짜 이유

`React.memo`로 컴포넌트를 감쌌는데도 리렌더링이 멈추지 않는다면, 십중팔구 props로 전달되는 **객체/배열/함수의 참조가 매번 새로 생성**되고 있기 때문이다. `<Child data={{ id: 1 }} />` 처럼 인라인 객체를 넘기거나 `onClick={() => handleClick()}` 처럼 인라인 함수를 넘기면, 부모가 리렌더링될 때마다 새로운 참조가 만들어져서 `memo`의 얕은 비교(shallow comparison)가 항상 실패한다.

```jsx
// ❌ 매 렌더마다 새 객체/함수 참조 생성 → memo 무력화
function Parent() {
  const [count, setCount] = useState(0);
  return (
    <>
      <button onClick={() => setCount(c => c + 1)}>+</button>
      <Child config={{ theme: 'dark' }} onSave={() => console.log('save')} />
    </>
  );
}
const Child = React.memo(({ config, onSave }) => {
  console.log('Child 렌더됨'); // count 바뀔 때마다 찍힘
  return <div>{config.theme}</div>;
});

// ✅ useMemo + useCallback으로 참조 고정
function Parent() {
  const [count, setCount] = useState(0);
  const config = useMemo(() => ({ theme: 'dark' }), []);
  const onSave = useCallback(() => console.log('save'), []);
  return (
    <>
      <button onClick={() => setCount(c => c + 1)}>+</button>
      <Child config={config} onSave={onSave} />
    </>
  );
}
```

```
Parent 리렌더 (count 변경)
    │
    ├─ { theme: 'dark' } ──→ 새 객체 {0xA1}  ❌ 이전 {0xB2}와 다름
    ├─ () => console.log  ──→ 새 함수 {0xA2}  ❌ 이전 {0xB3}과 다름
    │
    ▼
React.memo 얕은 비교: Object.is(prev.config, next.config) === false
    │
    ▼
Child 리렌더 발생 (memo 무력화)
```

**실무 트레이드오프**: 모든 props에 `useMemo`/`useCallback`을 바르는 건 오히려 안티패턴이다. memo로 감쌀 가치가 있는 건 ① 자식 트리가 무거운 경우 ② 리스트 아이템처럼 반복 렌더링되는 경우뿐. 가벼운 컴포넌트는 그냥 리렌더링하게 두는 게 메모리/코드복잡도 측면에서 이득이다. React 19의 React Compiler가 상용화되면 이 고민 자체가 사라질 예정이다.

> 💡 **왜 중요한가**: `React.memo`는 "props가 안 바뀌면 안 그린다"가 아니라 "props **참조**가 안 바뀌면 안 그린다"이며, 이 차이를 모르면 memo를 아무리 발라도 성능 개선은 0이다.

### 2. useEffect의 cleanup 함수: 메모리 누수와 "좀비 상태 업데이트"의 방어선

`useEffect`가 반환하는 cleanup 함수는 **다음 effect가 실행되기 직전**과 **컴포넌트가 언마운트될 때** 호출된다. 이걸 안 쓰면 비동기 요청이 끝났을 때 이미 언마운트된 컴포넌트의 setState가 호출되거나(좀비 업데이트), 이벤트 리스너/타이머/구독이 쌓여서 메모리 누수가 발생한다.

```jsx
// ❌ cleanup 없음 → 언마운트 후에도 fetch 결과 반영 시도 + 리스너 누적
function UserProfile({ userId }) {
  const [user, setUser] = useState(null);
  useEffect(() => {
    fetch(`/api/users/${userId}`)
      .then(r => r.json())
      .then(data => setUser(data)); // 언마운트 후 호출 가능

    window.addEventListener('resize', handleResize); // 영원히 안 떨어짐
  }, [userId]);
}

// ✅ AbortController + removeEventListener로 안전하게 정리
function UserProfile({ userId }) {
  const [user, setUser] = useState(null);
  useEffect(() => {
    const controller = new AbortController();
    fetch(`/api/users/${userId}`, { signal: controller.signal })
      .then(r => r.json())
      .then(data => setUser(data))
      .catch(err => {
        if (err.name !== 'AbortError') console.error(err);
      });

    const handleResize = () => console.log('resize');
    window.addEventListener('resize', handleResize);

    return () => {
      controller.abort();           // 진행 중인 fetch 취소
      window.removeEventListener('resize', handleResize);
    };
  }, [userId]);
}
```

```
userId: "A" 로 effect 실행
    │
    ├─ fetch("/api/users/A") 시작 ──┐
    ├─ resize 리스너 등록           │
    │                                │ (2초 걸림)
userId: "B" 로 변경                  │
    │                                │
    ├─ cleanup 실행                  │
    │   ├─ controller.abort() ───────┘ fetch 취소됨 ✅
    │   └─ removeEventListener      ✅
    │
    └─ 새 effect 실행
        ├─ fetch("/api/users/B") 시작
        └─ resize 리스너 등록
```

**React 18 Strict Mode 주의점**: 개발 모드에서는 effect가 **의도적으로 2번 실행**된다(마운트 → cleanup → 재마운트). cleanup이 제대로 안 짜여 있으면 이 단계에서 즉시 버그가 터지므로, 오히려 "cleanup 누락 감지기" 역할을 한다. 프로덕션에서는 1번만 실행되니 놀랄 필요 없다.

> 💡 **왜 중요한가**: cleanup은 선택이 아니라 비동기/구독/타이머/리스너를 쓰는 모든 effect의 **필수 규약**이며, 이걸 빠뜨리면 조용히 메모리가 새고 "Can't perform a React state update on an unmounted component" 경고가 쏟아진다.
