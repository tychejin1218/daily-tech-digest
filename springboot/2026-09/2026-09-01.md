### `@Async` 메서드에 `@Transactional`을 붙이면 트랜잭션이 **다른 스레드**에서 열린다 — 호출자의 트랜잭션과 완전히 단절된다

`@Async`는 프록시로 새 스레드에 작업을 던지고, 그 스레드에서 `@Transactional`이 새로 시작된다. 호출자가 아직 커밋하지 않은 데이터를 비동기 메서드가 조회하면 **아직 존재하지 않는 데이터**를 찾는 셈이 된다. "저장 직후 비동기로 후처리했더니 `EntityNotFoundException`이 뜨는" 미스터리의 정체.

```
[Thread-A: 호출자 트랜잭션]
  save(entity)  ← 아직 커밋 전, DB에 flush만 됨
      │
      └─► asyncService.process(entity.id)  ← 프록시가 Thread-B로 던짐
              │
[Thread-B: @Async + @Transactional]
              └─► findById(id) → null (커넥션 B는 A의 미커밋 데이터를 못 봄)
                  ※ 격리 수준이 READ_COMMITTED이므로 당연한 결과
```

**해결책 3가지**:
1. `TransactionSynchronizationManager.registerSynchronization()`으로 **커밋 후**에 비동기 호출
2. `@TransactionalEventListener(phase = AFTER_COMMIT)` + `ApplicationEventPublisher` 조합
3. 비동기 메서드에 ID만 넘기고, 호출부에서 명시적으로 `flush()` + 커밋 완료 보장

> 💡 **왜 중요한가**: "저장했는데 왜 안 보여?"라는 버그의 90%는 트랜잭션 경계와 스레드 경계를 혼동한 결과다.

### `@Value`로 주입한 값은 **최초 주입 시점**에 고정된다 — `@RefreshScope` 없이는 런타임 변경이 반영되지 않는다

`@Value("${my.property}")`는 빈 초기화 시 딱 한 번 파싱되어 필드에 박힌다. Spring Cloud Config나 외부 설정 서버에서 값을 바꿔도, 애플리케이션을 재기동하지 않는 한 그 빈은 **옛날 값**을 계속 들고 산다. "설정을 바꿨는데 왜 안 먹혀?"의 원인.

```
[초기화 시점]
  application.yml: my.timeout=5000
       │
       ▼
  @Value 주입 → this.timeout = 5000  (필드에 박제)

[런타임에 설정 변경]
  Config Server: my.timeout=10000
       │
       ▼
  Environment는 갱신됨 (환경만 바뀜)
       │
       ▼
  하지만 this.timeout은 여전히 5000  ← 필드는 안 바뀜
```

**대안**:
- `@RefreshScope` + Actuator `/refresh` 엔드포인트 (Spring Cloud)
- `Environment.getProperty()`를 매번 호출 (성능 손해)
- `@ConfigurationProperties` + `ContextRefresher.refresh()` (Spring Cloud)
- 정적 값이라면 `@Value`, 동적 값이라면 `Environment` 주입 후 조회

**트레이드오프**: `@RefreshScope`는 매 요청마다 프록시를 거쳐 빈을 다시 만들 수 있으므로, hot path에는 부적합. 값이 자주 바뀌지 않는다면 그냥 재기동이 답인 경우도 많다.

> 💡 **왜 중요한가**: "설정 서버 붙였는데 왜 실시간으로 안 바뀌지?"라고 3시간 헤매게 만드는 함정 — `@Value`는 스냅샷일 뿐이다.
