### 1. Context API의 숨겨진 비용: "값이 안 바뀌어도" 모든 하위 컴포넌트가 리렌더링되는 이유

Context의 `value` prop에 매번 새 객체(`value={{ user, setUser }}`)를 넘기면, 실제 데이터가 동일해도 참조가 바뀌어 Provider 아래 모든 Consumer가 리렌더링된다. React는 `Object.is`로 value 변경을 감지하기 때문에 `useMemo`로 래핑하거나, 자주 바뀌는 값과 안정적인 값을 **두 개의 Context로 분리**(상태용/디스패처용)하는 것이 실무 정답이다. Redux나 Zustand가 "선택적 구독(selector)"을 핵심 기능으로 내세우는 이유가 바로 이 Context의 전파 비용 때문이다.

```jsx
// ❌ 매 렌더마다 새 객체 → 모든 Consumer 리렌더
<UserContext.Provider value={{ user, setUser }}>

// ✅ 참조 안정화 또는 Context 분리
const value = useMemo(() => ({ user, setUser }), [user]);
```

> 💡 **왜 중요한가**: "Context만 쓰면 되지 왜 Redux?"라는 질문에 답하려면, Context가 "구독 최적화가 없는 전역 변수"임을 먼저 이해해야 한다.

### 2. React 18의 Automatic Batching: Promise/setTimeout 안에서도 setState가 한 번에 묶이는 변화

React 17까지는 이벤트 핸들러 내부의 `setState`만 자동 배칭되고, `setTimeout`·`Promise.then`·`fetch` 콜백 안의 `setState`는 각각 개별 렌더를 유발했다. React 18의 `createRoot`를 쓰면 **모든 비동기 컨텍스트에서 setState가 자동으로 묶여** 단 한 번만 리렌더된다. 반대로 즉시 반영이 필요한 극히 드문 경우엔 `flushSync`로 배칭을 명시적으로 해제해야 하며, 레거시 `ReactDOM.render`에서 `createRoot`로 마이그레이션할 때 "렌더 횟수에 의존한 테스트"가 깨지는 원인이 바로 이것이다.

```jsx
// React 18 createRoot 기준
setTimeout(() => {
  setCount(c => c + 1);   // 리렌더 1회만 발생
  setFlag(f => !f);       // 위와 묶임 (17에서는 2회 리렌더였음)
}, 1000);
```

> 💡 **왜 중요한가**: "왜 똑같은 코드인데 React 18로 올렸더니 렌더 횟수가 줄었지?"의 답. 성능 개선인 동시에, 중간 상태를 읽는 로직이 숨어있던 버그를 드러내는 양날의 검이다.
