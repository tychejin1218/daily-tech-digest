### Database Tip 1: PostgreSQL `pg_stat_statements`와 쿼리 지문(Query Fingerprint) — 파라미터가 달라도 "같은 모양의 쿼리"를 하나로 묶어 CPU/IO를 집계하는 숨은 관측 창구

`pg_stat_statements`는 쿼리 텍스트를 그대로 저장하지 않고 상수와 리터럴을 `$1, $2`로 정규화한 **쿼리 지문(queryid)** 단위로 호출 횟수, 총 실행 시간, 평균 시간, 공유 버퍼 히트/미스, 임시 파일 바이트까지 누적한다. 즉 `WHERE user_id = 1`과 `WHERE user_id = 999`는 동일한 queryid로 집계되므로, "어떤 쿼리가 전체 DB 시간의 몇 %를 먹고 있는가"를 처음으로 정량화할 수 있다. 다만 `pg_stat_statements_reset()`을 호출하지 않으면 지표가 "DB 재시작 이후 누적"이므로, 배포 직후 회귀 감지에는 **차분(delta) 기반 스냅샷**이 필수다.

```
애플리케이션                   PostgreSQL
    │
    │ SELECT ... WHERE id = 1
    │ SELECT ... WHERE id = 2    ──► Parser ──► Normalizer
    │ SELECT ... WHERE id = 3                        │
    ▼                                                ▼
                                       queryid = 0xABCD (동일 지문)
                                                ├── calls: 3
                                                ├── total_exec_time: 15ms
                                                ├── shared_blks_hit: 120
                                                └── temp_blks_written: 0
```

**실전 활용 — Top N 쿼리 뽑기**

```sql
SELECT
  queryid,
  calls,
  round(total_exec_time::numeric, 2)      AS total_ms,
  round(mean_exec_time::numeric, 2)       AS mean_ms,
  round(100.0 * total_exec_time
        / sum(total_exec_time) OVER (), 2) AS pct,
  rows,
  shared_blks_hit,
  shared_blks_read,
  temp_blks_written,
  left(query, 80) AS query_snippet
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

**트레이드오프**

| 축 | APM(Datadog/NewRelic) | `pg_stat_statements` |
|---|---|---|
| 수집 지점 | 애플리케이션 → DB 왕복 시간 | DB 내부 실행 시간만 |
| 샘플링 | 보통 샘플링(1~10%) | 100% 집계(오버헤드 ~1%) |
| 비용 | 유료, 트래픽 비례 과금 | 무료, 확장 모듈 1개 |
| 쿼리 플랜 | 보통 미포함 | 없음 → `auto_explain`과 조합 필요 |

**실패 사례**: 배포 직후 CPU가 40%→85%로 튀었는데 슬로우 쿼리 로그에는 아무것도 안 걸렸다. `long_query_time=1s`인데 실제 범인은 **"2ms × 50,000회/분"** 짜리 N+1 쿼리였기 때문. `pg_stat_statements`의 `calls * mean_exec_time` 랭킹을 보고서야 원인이 드러났다 — 슬로우 쿼리 로그는 "느린 한 방"만 잡고, 지문 집계는 "작지만 잦은" 쿼리를 잡는다.

> 💡 **왜 중요한가**: 슬로우 쿼리 로그가 못 잡는 "N+1 같은 작지만 잦은 쿼리"의 누적 비용을 queryid 단위로 묶어 가시화하는 유일한 공짜 창구이기 때문이다.

### Database Tip 2: MySQL `Doublewrite Buffer` — 8KB InnoDB 페이지를 16KB 디스크 섹터에 쓸 때 발생하는 "찢어진 페이지(Torn Page)"를 막는 두 번 쓰기 보험

InnoDB 페이지는 16KB인데 리눅스 파일시스템과 디스크의 원자적 쓰기 단위(섹터)는 보통 4KB 또는 512B다. 즉 OS가 16KB 페이지를 디스크에 내려쓰는 도중 전원이 꺼지면 **앞 4KB만 새 데이터, 뒤 12KB는 옛 데이터**인 "찢어진 페이지"가 남는다. Redo Log는 "이 페이지의 이 오프셋을 이렇게 바꿔라"라는 **논리적 변경분**만 들고 있어서, 기반 페이지 자체가 깨져 있으면 재적용할 수 없다 — 이 상황을 복구하는 것이 Doublewrite Buffer다.

```
                   ┌────────────────────────────────┐
                   │  Buffer Pool (더티 페이지 16KB) │
                   └──────────────┬─────────────────┘
                                  │ ① 플러시 시작
                                  ▼
            ┌───────────────────────────────────────┐
            │  Doublewrite Buffer (시스템 테이블스페이스) │
            │  ─ 16KB 페이지 전체를 순차 쓰기 + fsync    │
            └──────────────┬────────────────────────┘
                           │ ② fsync 완료 후
                           ▼
            ┌───────────────────────────────────────┐
            │  실제 데이터 파일(.ibd) — 랜덤 I/O 위치      │
            │  ─ 여기서 찢어지면? → DWB에서 복구          │
            └───────────────────────────────────────┘

크래시 복구 시나리오:
  (A) DWB는 멀쩡, 데이터 파일이 찢어짐 → DWB에서 통째로 복원 → Redo 재적용
  (B) DWB가 찢어짐, 데이터 파일은 멀쩡 → 데이터 파일 유지 → Redo 재적용
  (C) 둘 다 멀쩡 → 그대로 Redo 재적용
```

**끄면 안 되는 이유와 끌 수 있는 조건**

- `innodb_doublewrite = OFF`로 꺼면 쓰기 I/O가 약 10~20% 감소하지만, 전원 장애 시 **데이터 파일 손상 → 백업에서 복원 외엔 방법 없음**.
- 다만 다음 중 하나에 해당하면 안전하게 OFF 가능:
  - ZFS/Btrfs처럼 **Copy-on-Write 파일시스템**을 쓰는 경우 (파일시스템이 원자적 쓰기 보장)
  - **16KB 원자적 쓰기를 보장하는 엔터프라이즈 SSD** (Fusion-io, NVMe의 `Atomic Write` 지원 장치)
  - 복제본(replica)이고 손상 시 **재구축이 저렴한** 경우

**MySQL 8.0.20+ 개선**: Doublewrite Buffer를 시스템 테이블스페이스에서 분리해 **별도 파일**(`#ib_16384_0.dblwr`)로 떼어냈다. 덕분에 데이터 파일과 다른 디스크에 배치할 수 있어 I/O 병목이 완화되고, 샤드별로 DWB 파일 수를 조정할 수 있게 됐다 (`innodb_doublewrite_files`).

**관측 포인트**:
```sql
SHOW GLOBAL STATUS LIKE 'Innodb_dblwr%';
-- Innodb_dblwr_writes       : DWB에 기록된 횟수
-- Innodb_dblwr_pages_written: DWB에 쓴 페이지 수
-- 비율 = pages_written / writes → 한 번에 몰아서 쓰는 페이지 수 (높을수록 효율적)
```

> 💡 **왜 중요한가**: Redo Log만으로는 복구할 수 없는 "디스크 쓰기 중 전원 끊김" 시나리오를 막는 마지막 보험이고, SSD/파일시스템 특성에 따라 끄고 켜는 판단이 I/O 비용과 직결되기 때문이다.
