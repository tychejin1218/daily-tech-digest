### MySQL `Online DDL`의 `ALGORITHM=INSTANT` — 수 TB 테이블에 컬럼을 추가해도 락 없이 밀리초 만에 끝내기

MySQL 8.0.12부터 도입된 `ALTER TABLE ... ALGORITHM=INSTANT`는 테이블 메타데이터만 수정하고 실제 데이터 페이지를 재작성하지 않는다. 기존 `INPLACE`가 여전히 테이블을 통째로 복사·재빌드하며 몇 시간씩 걸리던 컬럼 추가·삭제·이름 변경 작업이, 이제는 `information_schema`의 스키마 버전만 올리는 O(1) 연산으로 끝난다. 다만 컬럼 순서 변경, `AUTO_INCREMENT` 수정, `PRIMARY KEY` 변경 같은 작업은 여전히 `COPY`로 폴백하므로 반드시 `ALGORITHM=INSTANT, LOCK=NONE`을 명시해 실패 시 즉시 에러를 내도록 강제해야 한다.

```sql
-- 5억 행 테이블에 컬럼 추가가 0.02초
ALTER TABLE orders
  ADD COLUMN refund_reason VARCHAR(200) NULL,
  ALGORITHM=INSTANT, LOCK=NONE;

-- 폴백을 명시적으로 막기 — INSTANT 불가능하면 즉시 실패
-- 실패해야 예상 못 한 다운타임을 피할 수 있음
```

| 작업 | INSTANT | INPLACE | COPY |
|------|---------|---------|------|
| 컬럼 추가 (맨 뒤) | ✅ 밀리초 | 데이터 재작성 | 전체 복사 |
| 컬럼 삭제 | ✅ 8.0.29+ | 재작성 | 전체 복사 |
| 컬럼 순서 변경 | ❌ | 재작성 | 전체 복사 |
| `NULL → NOT NULL` | ❌ | 데이터 검증 | 전체 복사 |

> 💡 **왜 중요한가**: 운영 중인 대용량 테이블에서 "컬럼 하나 추가"가 5시간 락과 리플리카 지연을 부르던 시대의 종말 — `ALGORITHM=INSTANT` 명시 여부가 배포 창을 새벽 3시로 미룰지 업무 시간에 끝낼지를 가른다.

### PostgreSQL `Skip Locked` — 큐 테이블에서 락 대기 없이 다음 작업만 골라 잡기

`SELECT ... FOR UPDATE SKIP LOCKED`는 이미 다른 트랜잭션이 잠근 행을 "대기하지 않고 그냥 건너뛰는" 락 획득 방식이다. 워커 100개가 동일한 `jobs` 테이블을 폴링할 때, 기존 `FOR UPDATE`는 첫 워커가 잡은 행 뒤로 나머지 99개가 줄을 서지만 `SKIP LOCKED`는 각자 다른 행을 즉시 낚아채 병렬 처리가 선형적으로 스케일한다. Redis·Kafka 같은 별도 큐 인프라 없이 PostgreSQL만으로 초당 수만 건 처리하는 작업 큐를 구현할 수 있는 결정적 기능이다.

```sql
-- 워커가 다음 작업 하나를 원자적으로 획득
BEGIN;
SELECT id, payload
FROM jobs
WHERE status = 'pending'
  AND scheduled_at <= NOW()
ORDER BY scheduled_at
FOR UPDATE SKIP LOCKED  -- 잠긴 행은 안 보이는 척 넘어감
LIMIT 1;

UPDATE jobs SET status = 'processing', worker_id = $1 WHERE id = $2;
COMMIT;
```

```
┌─ 워커 A ─┐  SELECT ... SKIP LOCKED LIMIT 1  → row #1 획득
├─ 워커 B ─┤  SELECT ... SKIP LOCKED LIMIT 1  → row #2 획득 (row #1 스킵)
├─ 워커 C ─┤  SELECT ... SKIP LOCKED LIMIT 1  → row #3 획득
└─ 워커 D ─┘  SELECT ... SKIP LOCKED LIMIT 1  → row #4 획득
             ↑ 아무도 대기 없이 서로 다른 행을 잡음
```

**주의점**: `SKIP LOCKED`는 격리 수준의 일관성 보장을 일부 포기한다 — 잠긴 행이 실제로는 커밋 후 조건에 안 맞을 수도 있다. 그래서 큐 작업 획득처럼 "정확히 그 행이 아니어도 다른 행이면 OK"인 시나리오에만 써야 하고, 재고 차감처럼 특정 행을 반드시 봐야 하는 상황엔 절대 쓰면 안 된다.

> 💡 **왜 중요한가**: PostgreSQL 단독으로 Sidekiq·Celery·SQS 수준의 작업 큐를 구현할 수 있게 만드는 기능 — 인프라 하나 줄이면서 트랜잭션 무결성까지 얻는 흔치 않은 선택지.
