### Agent 시스템의 ReAct 루프 — "Thought → Action → Observation"이 무한 반복에 빠질 때

LLM에 도구(Tool)를 붙이면 "스스로 판단해서 API를 호출하는 에이전트"가 된다. ReAct(Reasoning + Acting) 패턴은 이 아이디어를 정형화한 것이다. 모델이 매 스텝마다 **Thought(추론) → Action(도구 호출) → Observation(결과 관찰)** 을 반복하며 목표에 수렴한다. LangChain, AutoGPT, Anthropic의 Computer Use, OpenAI Assistants API — 모두 이 루프의 변형이다.

문제는 "루프가 언제 끝나느냐"이다. 시니어가 이 시스템을 프로덕션에 올릴 때 마주치는 진짜 이슈는 정확도가 아니라 **비용 폭발, 무한 루프, 부분 실패**다.

#### ReAct 루프의 기본 구조

```
┌─────────────────────────────────────────────────────────┐
│  User: "지난 3개월 매출 상위 5개 지점의 재고 현황 알려줘"  │
└──────────────────────────┬──────────────────────────────┘
                           ▼
              ┌────────────────────────┐
              │   LLM (Planner)        │◄──────────┐
              │                        │           │
              │  Thought: 매출부터     │           │
              │  조회해야 함           │           │
              └──────────┬─────────────┘           │
                         │ Action:                 │
                         │ query_sales(90d)        │
                         ▼                         │
              ┌────────────────────────┐           │
              │   Tool Executor        │           │
              │  (SQL / API / RAG)     │           │
              └──────────┬─────────────┘           │
                         │ Observation:            │
                         │ [지점A: 12억, ...]      │
                         └─────────────────────────┘
                         (다음 스텝 반복)
                         ▼
                    (재고 조회 → 조합 → 최종 답)
```

한 요청에 LLM 호출이 5~20번 발생한다. 여기서 두 가지가 폭발한다.

#### 함정 1: 무한 루프 — "모델이 자기 실수를 인정하지 않는다"

Tool이 에러를 반환하면 모델은 대개 "다시 시도"를 선택한다. 문제는 **같은 파라미터로 같은 실수를 반복**하는 경우가 많다는 점이다.

```
Thought: SQL로 조회하자
Action: run_sql("SELECT ... FROM sale WHERE ...")  ← 오타(sale)
Observation: Error: table "sale" does not exist
Thought: 쿼리를 다시 시도하자
Action: run_sql("SELECT ... FROM sale WHERE ...")  ← 또 같은 오타
Observation: Error: ...
Thought: 재시도가 필요하다
Action: run_sql("SELECT ... FROM sale WHERE ...")
... (30번 반복 후 토큰 리밋으로 강제 종료)
```

이런 케이스가 실제로 프로덕션 비용의 대부분을 잡아먹는다. 방어선은 세 겹으로 쌓아야 한다.

1. **Step Budget**: 최대 스텝 수(예: 10). 초과 시 강제 종료 후 사용자에게 부분 결과 반환
2. **Loop Detector**: 최근 N개 Action의 해시가 반복되면 즉시 중단
3. **Cost Budget**: 요청당 토큰/달러 상한. Anthropic API의 `stop_reason: "max_tokens"` 를 catch하는 것과 별개로 애플리케이션 레벨에서 누적 비용 추적 필수

#### 함정 2: Tool 스키마가 모델을 배신한다

ReAct의 성패는 Tool 설명(description) 품질에 90% 달려 있다. `get_user(user_id)` 라는 이름만으론 모델이 "user_id에 이메일을 넣어도 되나?" 를 알 수 없다. 프로덕션에선 아래 규칙을 지킨다.

- **When to use / When NOT to use** 를 description에 명시
- 파라미터마다 예시 값 포함 (`user_id: 정수, 예: 12345`)
- **에러 메시지에 다음 액션 힌트를 실어라**: `"User not found. Try search_user(email) to find by email."` — 모델이 다음 스텝을 스스로 찾게 된다

#### 함정 3: 도구가 부작용(Side Effect)을 가진다

읽기 도구(`query_sales`)는 재시도해도 안전하다. 하지만 `send_email`, `create_order`, `refund_payment` 같은 쓰기 도구는 재시도가 곧 중복 실행이다. 시니어는 여기서 두 가지를 강제한다.

1. **Idempotency Key**: 모든 쓰기 도구는 클라이언트가 생성한 UUID를 받고, 서버가 24시간 dedupe
2. **Human-in-the-Loop**: 금액/사용자 데이터 변경 액션은 자동 실행이 아니라 승인 큐로 보낸다. Anthropic Computer Use, AWS Bedrock Agents 모두 이 패턴을 권장한다

#### 트레이드오프: ReAct vs. Planning vs. 단순 함수 호출

| 패턴 | 장점 | 단점 | 언제 |
|---|---|---|---|
| **단순 Function Calling** (1턴) | 예측 가능, 저비용 | 다단계 추론 불가 | 단일 도구로 끝나는 태스크 |
| **ReAct** (매 스텝 판단) | 유연, 에러 복구 가능 | 무한 루프 위험, 비용↑ | 탐색이 필요한 태스크 |
| **Plan-and-Execute** (계획 먼저) | 병렬 실행 가능, 비용 예측 | 계획 수정이 어려움 | 결정된 워크플로우 |

**실제 사례**:
- **GitHub Copilot Workspace**는 Plan-and-Execute를 택했다. 코드 변경은 계획을 먼저 사용자에게 보여주고 승인받아야 하기 때문이다. ReAct처럼 즉흥적으로 파일을 수정하면 되돌리기 어렵다.
- **Perplexity의 검색 에이전트**는 ReAct에 가깝다. "검색 → 결과 부족하면 재검색"이 자연스럽고, 모든 도구가 읽기 전용이라 재시도 비용이 낮다.
- **Cursor의 Agent Mode**는 하이브리드다. 큰 그림은 Plan으로 잡고, 파일별 편집은 ReAct 루프로 돈다.

#### 시니어의 관점: 언제 쓰고, 언제 쓰면 안 되는가

**써야 할 때**:
- 워크플로우가 사전에 결정되지 않고, 이전 스텝 결과에 따라 다음 도구가 달라질 때
- 도구가 대부분 읽기 전용이거나 idempotent할 때
- 지연(latency)보다 정확성이 중요한 백오피스/분석 태스크

**쓰지 말아야 할 때**:
- **실시간 응답이 필요한 사용자 대면 API** — 5~10턴 루프는 최소 10~30초 걸린다. 이럴 땐 단일 Function Call + Fallback으로 충분하다.
- **결정된 워크플로우** — 순서가 정해져 있다면 그냥 코드로 짜라. LLM에게 "다음 스텝을 정하라"고 시키는 건 낭비다.
- **금융 트랜잭션의 자동 승인** — LLM 판단만으로 돈이 움직여선 안 된다. Human-in-the-Loop 없이 ReAct를 붙이는 순간 감사(audit) 지옥이 열린다.

프로덕션에서 ReAct를 성공적으로 굴리는 팀들은 공통적으로 이렇게 말한다: **"에이전트를 똑똑하게 만드는 것보다, 언제 멈출지 정확히 아는 게 더 중요하다."**

> 💡 **왜 중요한가**: ReAct 에이전트의 실패는 정확도가 아니라 무한 루프·비용 폭발·부작용에서 오며, 시니어는 "얼마나 잘 추론하는가"가 아니라 "얼마나 잘 멈추는가"로 시스템을 설계한다.
