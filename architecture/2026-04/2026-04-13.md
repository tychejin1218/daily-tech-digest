### Clean Architecture 4계층 — "의존성의 방향"이 곧 아키텍처의 본질이다

시니어 백엔드가 Clean Architecture를 배울 때 가장 흔히 오해하는 지점은 "4개의 원(Entities, Use Cases, Interface Adapters, Frameworks & Drivers)을 그리는 것"이 목적이라고 생각하는 것이다. 사실 Robert C. Martin이 2012년 블로그 글에서 이 4계층을 제안한 이유는 단 하나, **의존성은 항상 바깥에서 안쪽으로만 흐른다(The Dependency Rule)** 는 규칙을 시각화하기 위해서였다. 계층 수는 4개일 수도, 5개일 수도, 3개일 수도 있다. 중요한 것은 원의 개수가 아니라 **화살표의 방향**이다.

#### 4계층의 실체

```
        ┌───────────────────────────────────────────────┐
        │  Frameworks & Drivers                         │
        │  (Spring MVC, JPA, Kafka Client, Redis SDK)   │
        │  ┌─────────────────────────────────────────┐  │
        │  │  Interface Adapters                     │  │
        │  │  (Controller, Presenter, Gateway,       │  │
        │  │   Repository 구현체, DTO ↔ Domain 변환) │  │
        │  │  ┌───────────────────────────────────┐  │  │
        │  │  │  Use Cases (Application)          │  │  │
        │  │  │  - OrderPlacementUseCase          │  │  │
        │  │  │  - 트랜잭션 경계, 오케스트레이션  │  │  │
        │  │  │  ┌─────────────────────────────┐  │  │  │
        │  │  │  │  Entities (Enterprise)      │  │  │  │
        │  │  │  │  - Order, Money, Policy     │  │  │  │
        │  │  │  │  - 비즈니스 불변식(Invariant)│  │  │  │
        │  │  │  └─────────────────────────────┘  │  │  │
        │  │  └───────────────────────────────────┘  │  │
        │  └─────────────────────────────────────────┘  │
        └───────────────────────────────────────────────┘

        의존성 방향: 바깥(외부 세계) ──▶ 안쪽(도메인)
        데이터 흐름: 양방향 (요청은 안으로, 응답은 밖으로)
```

- **Entities**: 회사가 망해도 살아남는 규칙. 예: "주문 금액은 음수가 될 수 없다", "환불은 결제 완료 상태에서만 가능하다". Spring도 JPA도 모른다.
- **Use Cases**: 애플리케이션 고유의 시나리오. 예: "주문을 접수하고 재고를 차감한 뒤 결제 이벤트를 발행한다". 어떤 DB인지, 어떤 메시지 브로커인지 모른다.
- **Interface Adapters**: 안쪽 언어(도메인)와 바깥 언어(HTTP/SQL/JSON)를 통역. Controller가 여기 산다.
- **Frameworks & Drivers**: Spring Boot 자체, JPA 구현, Kafka Producer, Redis 클라이언트. 갈아끼워도 안쪽은 몰라야 한다.

#### 핵심 메커니즘: 의존성 역전(DIP)

Use Case가 DB를 호출해야 하는데 "안쪽이 바깥을 몰라야 한다"면 어떻게 하나? 답은 **인터페이스를 안쪽에 두고, 구현을 바깥에 두는 것**이다.

```java
// application/port/out (Use Cases 계층)
public interface LoadOrderPort {
    Optional<Order> loadById(OrderId id);
}

// application (Use Cases 계층)
public class PlaceOrderUseCase {
    private final LoadOrderPort loadOrderPort;   // 안쪽이 정의한 인터페이스
    private final SaveOrderPort saveOrderPort;
    // Spring, JPA는 여기 등장하지 않는다
}

// adapter/persistence (Interface Adapters 계층)
@Repository
class OrderJpaAdapter implements LoadOrderPort, SaveOrderPort {
    private final OrderJpaRepository jpaRepo;    // 바깥이 안쪽 인터페이스를 구현
    // JPA는 여기서만 등장
}
```

Hexagonal의 Port/Adapter 개념을 이미 배웠다면 눈치챘겠지만, **Clean Architecture의 "Interface Adapters" 계층은 Hexagonal의 "Adapter"와 정확히 같은 위치**다. Uncle Bob 본인도 "Hexagonal, Onion, Clean은 같은 아이디어의 다른 표현"이라고 명시했다. 차이는 강조점일 뿐:
- Hexagonal: **육각형** 그림으로 "포트가 여러 개일 수 있다"를 강조
- Onion: **양파** 층 그림으로 "도메인이 최중심"을 강조
- Clean: **동심원**으로 "의존성 규칙 하나가 전부"를 강조

#### 트레이드오프

| 얻는 것 | 잃는 것 |
|---|---|
| 프레임워크 교체 가능 (Spring→Micronaut, JPA→JDBC) | 파일 수 2~3배 증가 (DTO, Mapper, Port, Adapter) |
| Use Case 단위 테스트가 Mock 없이 InMemory로 가능 | CRUD 위주 도메인에서는 "빈 껍데기" 클래스 남발 |
| 비즈니스 규칙이 한곳(Entities)에 응집 | 팀 전체가 규칙을 이해해야 유지 가능, 신입 온보딩 비용↑ |
| 대규모 리팩터링 시 폭발 반경(blast radius) 축소 | 초기 개발 속도 20~30% 저하 (도입 초기) |

#### 실제 사례

- **Netflix (Java 백엔드 일부 서비스)**: 결제·구독 같은 도메인 로직 무거운 서비스는 Clean Architecture 구조를 채택. 프레임워크(RxJava→Reactor 전환, Guice→Spring 이관)를 여러 번 교체하면서도 도메인 코드는 거의 손대지 않은 것이 알려져 있다.
- **토스(비바리퍼블리카)**: 결제·송금 도메인에서 Hexagonal(=Clean) 구조 적극 사용. 이유는 "PG사·은행 어댑터가 계속 바뀌는데 정산 규칙은 절대 바뀌면 안 되기 때문". 도메인은 순수 Kotlin, 어댑터만 Spring이다.
- **당근마켓 채팅 서버**: 초기 CRUD 위주여서 Clean을 도입하지 않았다가, 채팅방·거래·신고 등 도메인 규칙이 얽히자 뒤늦게 리팩터링. "복잡도가 낮을 땐 오버엔지니어링이었을 것"이라는 팀의 회고가 유명하다.
- **반대 사례 — 초기 스타트업 MVP**: Basecamp의 DHH가 "우리는 Rails Way를 따르고 Clean Architecture를 쓰지 않는다"고 공개적으로 밝힌 것이 대표적. ActiveRecord가 도메인·영속성을 다 갖고 있어 프레임워크 종속이 극단적이지만, 그 대신 개발 속도가 미친 듯이 빠르다. **도메인 복잡도가 낮고 프레임워크를 바꿀 계획이 없다면 Clean은 순손실**이다.

#### 언제 쓰고 언제 쓰면 안 되는가

**써야 할 때**
- 비즈니스 규칙이 UI/DB보다 오래 살 것이 확실할 때 (금융·정산·보험·물류)
- 외부 시스템(PG, 은행, 배송사) 어댑터가 자주 바뀔 때
- 서비스 수명이 5년 이상 예상되고 프레임워크 마이그레이션이 예상될 때
- Use Case 단위 테스트를 "DB 없이 초 단위로" 돌려야 할 때 (CI 파이프라인 압축)

**쓰지 말아야 할 때**
- MVP 단계, PoC, 3개월 안에 살아남을지 모르는 프로덕트
- 어드민 CRUD 화면 100개 찍어내는 사내 도구 — Repository→Service→Controller 3계층이 오히려 정답
- 팀 규모가 3명 이하이고 도메인 전문가가 개발자와 동일인일 때
- 이미 ActiveRecord 스타일 프레임워크(Rails, Django, Laravel)에 올라탄 코드베이스 — 문화가 안 맞는다

시니어의 판단 기준은 결국 하나다. **"도메인 규칙이 프레임워크보다 오래 살 것인가?"** 이 질문에 "Yes"라면 Clean, "No"거나 "모르겠다"면 3계층이다. 4개의 원을 그리기 전에 이 질문부터 답해야 한다.

> 💡 **왜 중요한가**: Clean Architecture의 본질은 계층 수가 아니라 "의존성은 도메인을 향해서만 흐른다"는 단 하나의 규칙이며, 이 규칙을 지키면 프레임워크는 갈아끼울 수 있는 부품이 되고, 지키지 않으면 프레임워크가 곧 아키텍처가 된다.
