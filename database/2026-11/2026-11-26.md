### Database Tip 1: PostgreSQL `VACUUM`과 `autovacuum` — MVCC가 남긴 "죽은 튜플(Dead Tuple)"을 청소하지 않으면 테이블이 조용히 비대해지는 숨은 쓰레기 수거기

PostgreSQL은 UPDATE/DELETE 시 데이터를 즉시 지우지 않고 "죽은 튜플"로 표시만 해둔 뒤, `VACUUM`이 와서 공간을 회수한다. 문제는 autovacuum 임계값(`autovacuum_vacuum_scale_factor` 기본 0.2 = 테이블의 20%)이 커서, 1억 행 테이블은 2천만 행이 썩을 때까지 청소가 시작되지 않고, 그 사이 테이블/인덱스가 Bloat로 부풀어 쿼리 플래너는 느려진 통계를 보고 잘못된 플랜을 뽑는다. 거대 테이블은 `autovacuum_vacuum_scale_factor = 0.01`, `autovacuum_vacuum_cost_limit`을 상향, 핫 테이블은 테이블별 `ALTER TABLE ... SET (autovacuum_vacuum_scale_factor = 0.02)`로 개별 튜닝해야 하며, `VACUUM FULL`은 ACCESS EXCLUSIVE 락을 잡으므로 운영 중엔 `pg_repack`으로 온라인 재구성한다.

```
UPDATE user SET name='B' WHERE id=1
┌─────────────────────────────────────┐
│ Heap Page                            │
│ ┌──────────────┐  ┌──────────────┐  │
│ │ id=1, 'A'    │  │ id=1, 'B'    │  │
│ │ xmax=100 ❌  │  │ xmin=101 ✅  │  │
│ │ (Dead Tuple) │  │ (Live Tuple) │  │
│ └──────────────┘  └──────────────┘  │
└─────────────────────────────────────┘
          ↓ autovacuum 임계 미달 시
┌─────────────────────────────────────┐
│ Dead Tuple이 계속 쌓여 Bloat 발생     │
│ → Seq Scan 범위 증가, 플래너 오판     │
│ → TXID Wraparound 위험(20억 트랜잭션)│
└─────────────────────────────────────┘
          ↓ VACUUM 실행
┌─────────────────────────────────────┐
│ Dead Tuple 공간 회수 → FSM에 등록     │
│ (테이블 크기는 줄지 않음, 재사용 가능) │
└─────────────────────────────────────┘
```

**실제 사례**: GitLab이 2017년 데이터 유실 사고 이후 공개한 포스트모템에서 `pg_toast` 테이블의 bloat가 원인 중 하나로 지목됐다. Sentry도 블로그에서 `events` 테이블의 autovacuum 튜닝 실패로 쿼리가 10배 느려진 사례를 공유했다.

**트레이드오프**: autovacuum을 공격적으로 돌리면 I/O를 상시 점유해 피크 쿼리 성능을 갉아먹고, 느슨하게 두면 bloat와 TXID Wraparound(대참사: DB가 읽기 전용으로 강제 전환)가 기다린다. "쓰기 많은 테이블은 별도 튜닝"이 정답이지, 글로벌 설정 하나로 해결되지 않는다.

> 💡 **왜 중요한가**: MVCC는 공짜가 아니다 — "지웠는데 디스크가 안 줄어든다"는 질문의 90%는 VACUUM을 이해 못 한 데서 나온다.

### Database Tip 2: JPA `OSIV`(Open Session In View) — HTTP 응답 렌더링까지 DB 커넥션을 쥐고 있는, Spring Boot의 "기본값이 성능 지뢰"인 숨은 트랜잭션 확장

Spring Boot는 `spring.jpa.open-in-view=true`가 **기본값**으로, 요청이 들어온 순간부터 View 렌더링(JSON 직렬화 포함)이 끝날 때까지 DB 커넥션과 영속성 컨텍스트를 유지한다. 이 덕에 Controller에서 LazyLoading이 "마법처럼" 동작하지만, 대신 **커넥션 점유 시간이 서비스 로직 시간이 아니라 응답 시간 전체**로 늘어나 커넥션 풀 고갈이 발생한다. 외부 API 호출이나 느린 View 렌더링이 있는 순간, HikariCP 풀(기본 10개)이 순식간에 바닥나고 모든 요청이 `Connection is not available` 에러로 쓰러진다.

```
[ OSIV = true (Spring Boot 기본값) ]
HTTP Request
    │
    ├─[Filter] ─── Hibernate Session OPEN ──┐
    │                                         │ ← 커넥션 점유 시작
    │   [Controller]                          │
    │   [Service] @Transactional              │
    │   [Repository]                          │
    │   @Transactional 끝 (커밋)              │ ← 커넥션 반환 안 함!
    │                                         │
    │   [Controller] user.getOrders() ← Lazy  │ ← 트랜잭션 밖 쿼리 발생
    │   [View] Jackson JSON 직렬화            │
    │   [외부 API 호출 500ms]                 │ ← 이 시간도 커넥션 점유
    │                                         │
    └─[Filter] ── Hibernate Session CLOSE ───┘ ← 이제야 반환
HTTP Response

[ OSIV = false (권장) ]
    ├─ @Transactional 시작 ──── 커넥션 점유 시작
    │   Service / Repository
    └─ @Transactional 끝 ────── 커넥션 즉시 반환
       Controller / View → Lazy 접근 시 LazyInitializationException
```

**실제 사례**: 김영한 님의 "실전! 스프링 부트와 JPA 활용" 강의에서 가장 강조하는 포인트 중 하나이자, 우아한형제들·토스·카카오 테크 블로그에서 반복적으로 등장하는 장애 유형이다. 트래픽 10배 증가 시 DB CPU는 20%인데 커넥션 풀이 100% 점유되어 서비스가 멈추는 전형적 패턴이다.

**트레이드오프**: `open-in-view=false`로 끄면 커넥션 효율은 극대화되지만, Controller/View에서 Lazy 필드 접근 시 즉시 `LazyInitializationException`이 터진다. 해결책은 **Service 계층에서 DTO로 변환 후 반환**(Projection, `@EntityGraph`, Fetch Join)하는 규칙을 팀 전체가 지키는 것 — 즉 OSIV를 끈다는 건 "아키텍처 규율"을 도입한다는 뜻이다. 토이 프로젝트는 켜두는 게 편하지만, 트래픽을 받는 서비스는 반드시 꺼야 한다.

> 💡 **왜 중요한가**: Spring Boot의 "기본값"이 항상 "운영 환경 정답"은 아니다 — OSIV는 개발 편의를 위해 켜져 있지만, 커넥션 풀 장애의 숨은 주범이다.
