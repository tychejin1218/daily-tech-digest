### Database Tip 1: PostgreSQL `CLUSTER`와 물리적 정렬의 일회성 — 인덱스 순서대로 테이블을 재배치해 "Correlation=1"을 만드는 숨은 디스크 레이아웃 최적화

PostgreSQL에서 `CLUSTER table USING index`는 테이블의 물리적 행 순서를 특정 인덱스 순서에 맞춰 재작성하는 명령이다. `pg_stats.correlation`이 1에 가까워지면 범위 스캔 시 디스크에서 읽어야 할 페이지 수가 급감하는데, 시계열 데이터처럼 `created_at BETWEEN ...` 쿼리가 많은 테이블에서 랜덤 I/O가 순차 I/O로 바뀌어 수십 배 빨라진다. 하지만 함정은 **"일회성"이라는 점** — 이후 INSERT/UPDATE는 다시 랜덤 위치에 쓰이므로 correlation이 서서히 무너지고, 재클러스터링 시 `ACCESS EXCLUSIVE LOCK`이 걸려 테이블 전체가 블록된다. MySQL InnoDB의 자동 클러스터드 인덱스와 달리 **PostgreSQL은 힙 테이블이 기본**이라, 수동 CLUSTER는 "한 번만 효과 있는 디스크 정렬 스냅샷"에 가깝다.

```
                  Heap (물리적 순서)         Index Scan 비용
                  ┌────────────────┐
CLUSTER 전:       │ 5 │ 2 │ 8 │ 1 │       → 범위 쿼리 시
                  │ 3 │ 7 │ 4 │ 6 │         페이지 4개 모두 읽음
                  └────────────────┘         (랜덤 I/O 💥)

                  ┌────────────────┐
CLUSTER 후:       │ 1 │ 2 │ 3 │ 4 │       → 1~4 범위 쿼리 시
                  │ 5 │ 6 │ 7 │ 8 │         페이지 1개만 읽음
                  └────────────────┘         (순차 I/O ⚡)

이후 INSERT  →    │ 1 │ 2 │ 3 │ 4 │ 9 │   ← correlation 다시 무너짐
                  │ 5 │ 6 │ 7 │ 8 │10 │      재클러스터링 필요
```

> 💡 **왜 중요한가**: 인덱스는 "찾는 속도"를 결정하지만, 물리적 정렬은 "읽는 속도"를 결정한다 — 같은 인덱스라도 correlation이 0.1이냐 0.9냐에 따라 범위 쿼리 성능이 10배 이상 갈린다.

### Database Tip 2: JPA `@BatchSize`와 Hibernate `default_batch_fetch_size` — N+1을 "완전 제거"가 아닌 "N/K+1"로 줄이는 현실적 타협점

JPA의 N+1 문제를 Fetch Join으로 해결하려다 보면 페이징 불가, `MultipleBagFetchException`, 카티전 곱 폭발 같은 벽에 부딪힌다. `@BatchSize(size = 100)` 또는 `hibernate.default_batch_fetch_size=100` 설정은 **지연 로딩을 유지하면서** 프록시 초기화 시점에 `WHERE id IN (?, ?, ..., ?)` 형태로 묶어서 조회하는 방식 — N번의 쿼리가 N/100 + 1번으로 줄어든다. Fetch Join이 "하나의 거대한 JOIN"이라면 BatchSize는 "여러 개의 작은 IN절 쿼리"로, **페이징과 공존 가능**하고 컬렉션이 여러 개여도 깨지지 않는다는 결정적 장점이 있다. 다만 `IN` 절 파라미터 수가 Oracle의 1000개 제한에 걸리거나, 실행 계획 캐시가 파라미터 개수별로 분기되어 메모리를 먹는 함정이 있어 **"무조건 1000"이 아니라 쿼리 패턴에 맞춰 50~500 사이를 튜닝**해야 한다.

```
사용자 10명 조회 → 각자의 주문 목록 로딩

[Fetch Join]
SELECT u.*, o.* FROM users u LEFT JOIN orders o ON ...
   → 카티전 곱 (주문 평균 50개면 500행 전송)
   → 페이징 불가 (DB에서 distinct 후 메모리 페이징)
   → 컬렉션 2개면 MultipleBagFetchException 💥

[BatchSize = 100]
SELECT * FROM users WHERE ...                 ← 1번
SELECT * FROM orders WHERE user_id IN (?,?,?,?,?,?,?,?,?,?)  ← 1번
   → 총 2쿼리, 페이징 정상 동작
   → 컬렉션 여러 개도 각각 IN 절로 처리 ✅

[순수 Lazy Loading]
SELECT * FROM users ...                       ← 1번
SELECT * FROM orders WHERE user_id = ?        ← 10번 (N+1)
   → 총 11쿼리 💀
```

> 💡 **왜 중요한가**: Fetch Join이 "이상적인 해법"이라면 BatchSize는 "현실적인 해법" — 페이징이 필요하거나 컬렉션이 여러 개인 실무 쿼리에서는 오히려 BatchSize가 유일한 정답인 경우가 많다.
