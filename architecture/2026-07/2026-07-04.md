### REST API 설계 원칙 — "리소스 중심 사고"가 만드는 API의 수명

REST는 현업에서 가장 많이 오용되는 단어입니다. 대부분의 팀은 "HTTP + JSON"을 REST라고 부르지만, 이는 Roy Fielding이 2000년 박사 논문에서 정의한 REST의 껍데기만 취한 것입니다. 시니어 관점에서 REST를 다시 본다는 것은, "왜 리소스 중심 사고가 API의 수명을 결정하는가"를 이해하는 것입니다.

#### 1. REST의 6가지 제약 — 대부분 무시되는 것들

Fielding이 정의한 REST는 아키텍처 스타일이고, 6가지 제약(Constraints)의 집합입니다.

1. **Client-Server** — 관심사 분리
2. **Stateless** — 서버는 클라이언트 세션 상태를 보관하지 않음 (JWT를 택하는 이유가 여기 있음)
3. **Cacheable** — 응답은 명시적으로 캐시 가능/불가능을 선언
4. **Uniform Interface** — 자원 식별, 표현을 통한 조작, self-descriptive 메시지, HATEOAS
5. **Layered System** — 클라이언트는 중간 계층(프록시·게이트웨이·LB)의 존재를 몰라야 함
6. **Code on Demand** (옵션) — 서버가 실행 가능한 코드 전송

실무에서 진짜 지켜지는 건 1, 2, 5 정도입니다. 특히 4번의 HATEOAS는 거의 지켜지지 않습니다. 즉, 세상에는 "REST"라 자칭하는 API가 넘쳐나지만, Fielding의 정의를 만족하는 API는 극소수입니다.

#### 2. Richardson Maturity Model — 당신의 API는 몇 단계인가

Leonard Richardson이 제안한 REST의 성숙도 모델입니다. 팀의 API가 어디에 있는지 진단하는 도구로 유용합니다.

```
Level 3 │ HATEOAS
        │   응답에 다음 가능한 action의 링크가 포함됨
        │   { "id": 42, "status": "pending",
        │     "_links": { "cancel": "/orders/42/cancel" } }
        ├─────────────────────────────────────────────────
Level 2 │ HTTP 메서드 & 상태코드의 의미 활용
        │   GET/POST/PUT/DELETE, 200/201/404/409 …
        ├─────────────────────────────────────────────────
Level 1 │ Resources
        │   /orders, /users/{id} 처럼 자원별 URI 분리
        ├─────────────────────────────────────────────────
Level 0 │ Swamp of POX (Plain Old XML/JSON)
        │   /api 하나의 엔드포인트에 POST로 모든 것
```

대부분의 "REST API"는 Level 2에서 멈춥니다. Level 3(HATEOAS)까지 실제로 도달한 대표적 사례는 GitHub API, PayPal API 정도입니다. Level 3는 이론적으로 아름답지만, 클라이언트 SDK를 하드코딩하는 현실에서는 오버헤드가 커서 채택률이 낮습니다.

#### 3. 자원(Resource) 설계 — 동사가 아닌 명사로

REST의 핵심 사고 전환은 "행위(procedure)"가 아니라 **"자원과 그 상태 변화"**로 시스템을 표현하는 것입니다.

```
[RPC 스타일 — Anti-pattern]        [Resource 스타일 — REST]
POST /createOrder                  POST   /orders
POST /cancelOrder                  DELETE /orders/{id}
POST /getOrderById                 GET    /orders/{id}
POST /updateOrderStatus            PATCH  /orders/{id}
```

관계는 서브 리소스로 표현합니다:

```
GET  /users/{id}/orders          # 특정 사용자의 주문 목록
POST /orders/{id}/refunds        # 주문에 대한 환불 생성
```

**"동사가 꼭 필요할 때"의 타협** — 도메인 액션이 CRUD로 자연스럽게 매핑되지 않는 경우(승인, 재시도, 배치 실행 등)엔 명시적 액션 리소스를 만듭니다:

```
POST /orders/{id}/actions/cancel
POST /jobs/{id}/actions/retry
```

Stripe API가 이 패턴을 채택한 이유는, 결제 도메인은 순수 CRUD로 표현되지 않는 상태 전이가 많기 때문입니다.

#### 4. HTTP 메서드/상태코드의 의미론

시니어에게 중요한 건 표를 외우는 게 아니라 **속성(Safe/Idempotent)의 의미**입니다.

| 메서드 | 의미 | Safe | Idempotent |
|---|---|---|---|
| GET | 조회 | O | O |
| POST | 생성/비멱등 액션 | X | X |
| PUT | 전체 교체 | X | O |
| PATCH | 부분 수정 | X | △ (설계에 따라) |
| DELETE | 삭제 | X | O |

**멱등성이 왜 실전에서 중요한가**: 네트워크 재시도 안전성 때문입니다. 결제 요청이 타임아웃 났을 때, POST를 그냥 재시도하면 이중 결제가 납니다. Stripe는 `Idempotency-Key` 헤더로 이 문제를 우아하게 풀었는데, 이는 REST 표준이 아니라 **REST의 한계를 도메인 지식으로 보완**한 사례입니다.

**상태코드는 계약이다**:
- `401 Unauthorized` (인증 안 됨) vs `403 Forbidden` (권한 없음) — 이 둘을 섞어 쓰면 클라이언트가 재로그인 로직을 만들 수 없습니다.
- `404 Not Found` vs `410 Gone` — 후자는 "있었지만 이제 없다"를 명시.
- `409 Conflict` — 이미 취소된 주문을 다시 취소할 때. 상태 전이의 위반은 4xx로, 서버 버그는 5xx로.
- `422 Unprocessable Entity` — 문법은 맞지만 비즈니스 규칙 위반.
- `429 Too Many Requests` — Rate limiting. `Retry-After` 헤더와 함께.

에러 응답 스키마는 [RFC 7807 (Problem Details for HTTP APIs)](https://datatracker.ietf.org/doc/html/rfc7807)로 통일하는 것이 표준적 선택입니다.

#### 5. 실제 사례 — 그들은 왜 그렇게 설계했나

- **Stripe** — Resource + Action 혼합, `Idempotency-Key` 헤더, cursor 기반 pagination, `expand` 파라미터로 관계 리소스 lazy loading. **재시도 안전성과 결제 정합성이 최우선**이었기 때문. 이들이 REST 원리를 100% 지키지 않은 이유는, 도메인 요구가 원칙보다 우선했기 때문입니다.
- **GitHub** — Richardson Level 3 (HATEOAS) 채택. 응답에 `_links`로 다음 액션 안내. **개발자 생태계에서 discoverability가 중요**했기 때문. Octokit 같은 SDK가 이 링크를 활용해 자동 페이지네이션을 구현합니다.
- **Slack** — RPC 스타일 유지 (`chat.postMessage`, `users.info`). "REST 원리주의를 버린" 대표적 사례. 이유는 도메인이 명확히 동사 중심이고, 다국어 SDK 자동 생성이 편하기 때문. 즉 **일관성과 SDK 생성 편의가 REST 순수성보다 우선**한 판단.
- **Twitter (v1 → v2)** — 초기 API의 리소스 설계 실수(트윗과 사용자 관계 모델링)를 v2에서 field expansion과 리소스 그래프로 재설계. **한 번 잘못 설계한 API가 얼마나 오래 발목을 잡는지** 보여주는 반면교사.
- **Amazon** — 2002년 Bezos의 유명한 "API Mandate"로 모든 팀 간 통신을 서비스 인터페이스로 강제. 이 결정이 20년 뒤 AWS의 기반이 되었습니다. **잘 설계된 인터페이스가 조직 확장성 자체를 결정**한 사례.

#### 6. 트레이드오프 — 언제 쓰고 언제 쓰면 안 되는가

**REST가 잘 맞을 때**
- 자원이 명확히 정의되는 CRUD 중심 시스템 (커머스, CMS, 예약)
- 외부에 오래 공개할 퍼블릭 API — 캐싱, 프록시, 게이트웨이 등 HTTP 인프라를 그대로 활용 가능
- 다양한 클라이언트(웹/모바일/서드파티)가 접근하는 경우
- 조직이 크고 팀 간 계약이 중요한 경우 — HTTP 시맨틱이 공통 언어 역할

**REST가 안 맞을 때**
- 워크플로우/절차 중심 도메인 (승인 결재, 배치 오케스트레이션) — 리소스 억지 매핑이 부자연스러움
- 서비스 간 내부 통신 — **gRPC가 더 빠르고 스키마 안전**. 넷플릭스·구글이 내부적으로 gRPC를 쓰는 이유.
- 클라이언트마다 필요한 필드가 크게 다른 경우 — **GraphQL이 유리** (Facebook·GitHub·Shopify가 REST와 병행하는 이유)
- 실시간 양방향 통신 — WebSocket/SSE
- 대용량 스트리밍 — 프로토콜 오버헤드가 부담

**Anti-pattern 체크리스트**
- URL에 동사가 있다 (`/getUser`) → 리소스로 재설계
- 모든 응답이 `200 OK`고, 성공/실패는 body의 `success` 필드로 판단한다 → 상태코드 의미 활용
- 실패 응답 스키마가 엔드포인트마다 다르다 → RFC 7807로 통일
- 페이지네이션이 offset뿐이다 → 대용량엔 cursor 기반 필요 (데이터 삽입/삭제 시 offset은 중복·누락 발생)
- POST에 재시도 안전성이 없다 → Idempotency-Key 도입 검토
- 버전이 URL에만 있다 (`/v1/…`) → 헤더 기반 버저닝, Content Negotiation도 함께 검토

#### 7. 시니어 관점 — API는 데이터베이스 스키마보다 오래 산다

내부 코드는 언제든 리팩터링할 수 있지만, **한번 공개된 API는 되돌리기 어렵습니다**. 특히 외부 클라이언트가 있는 순간, 그 API는 조직의 계약이 되고 유지보수 비용이 코드보다 훨씬 큽니다.

모놀리스 단계에서도 REST 원칙으로 API를 설계해두면, 훗날 시스템이 커져 마이크로서비스로 쪼갤 때 **리소스 경계가 곧 서비스 경계 후보**가 됩니다. 반대로 RPC 스타일로 무분별하게 만들어두면, 도메인 경계가 흐려져 분리 비용이 폭발합니다. 즉 지금 잘 그린 리소스 지도가 미래의 서비스 경계도라는 뜻입니다.

REST를 종교로 삼지 마세요. Stripe·Slack이 보여준 것처럼 원칙과 실용의 균형을 찾는 게 시니어의 판단입니다. 다만 **트레이드오프를 이해한 후에 원칙을 벗어나는 것**과, **원칙 자체를 몰라 벗어나는 것**은 완전히 다릅니다.

> 💡 **왜 중요한가**: API는 코드보다 오래 살아남기 때문에, "리소스 중심 사고"로 설계해두면 시스템이 성장할 때 인터페이스 계약이 확장의 발목을 잡지 않는다.
