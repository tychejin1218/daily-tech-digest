### JPA `N+1` 쿼리와 `@EntityGraph` — 즉시 로딩도 페치 조인도 아닌, 상황별로 그래프를 갈아끼우는 스위치

`FetchType.LAZY`로 두면 N+1이 터지고, `EAGER`로 바꾸면 항상 조인이 붙어 리스트 조회까지 무거워진다. `@EntityGraph`는 이 이분법을 깨는 도구로, **엔티티 매핑은 LAZY로 유지하되 특정 쿼리 메서드에서만 필요한 연관관계를 즉시 로딩으로 승격**시킨다. `@Query` + `fetch join`과 달리 페이징 경고(HHH000104)를 피하기 위해 `EntityGraphType.LOAD`와 `FETCH`를 골라 쓸 수 있다는 게 핵심.

```java
public interface OrderRepository extends JpaRepository<Order, Long> {

    // 리스트 화면: 회원만 함께 로딩 (아이템은 지연)
    @EntityGraph(attributePaths = {"member"})
    List<Order> findAll();

    // 상세 화면: 아이템 + 상품까지 한 번에 로딩
    @EntityGraph(attributePaths = {"member", "orderItems", "orderItems.item"})
    Optional<Order> findWithDetailsById(Long id);
}
```

동일한 `Order` 엔티티라도 **호출하는 쿼리 메서드에 따라 로딩 그래프가 달라진다**. 리스트에서는 `member`만, 상세에서는 `orderItems`까지 조인 SQL이 자동 생성된다. 하나의 매핑에 여러 로딩 전략을 공존시키는 유일한 표준 방법.

```
[LAZY 매핑만] → 리스트에서 N+1
[EAGER 매핑]  → 상세는 OK지만 리스트도 무거움 + 페이징 시 In-Memory Paging 경고
[@EntityGraph] → 상황별로 필요한 것만 승격 ✅
```

> 💡 **왜 중요한가**: N+1 방지를 위해 엔티티 매핑을 `EAGER`로 바꾸는 순간, 다른 모든 조회 쿼리가 함께 무거워진다 — `@EntityGraph`는 매핑을 건드리지 않고 **쿼리별로만** 로딩 전략을 오버라이드하는 유일한 스위치다.

### MySQL `Prefix Index` — VARCHAR(255) 컬럼 전체를 인덱싱하지 않고 앞 N글자만 잘라서 인덱스로 쓰는 절충안

이메일이나 URL처럼 긴 문자열 컬럼에 그냥 인덱스를 걸면, 인덱스 페이지 하나에 담기는 엔트리 수가 줄어 **트리 높이가 늘고 랜덤 I/O가 증가**한다. Prefix Index는 `INDEX(email(20))`처럼 **앞 20바이트만 인덱싱**해서 인덱스 크기를 극적으로 줄이면서도 대부분의 검색 선택도를 유지하는 기법이다.

```sql
-- ❌ 나쁜 예: VARCHAR(255) 전체 인덱싱 (인덱스 페이지가 두꺼워짐)
CREATE INDEX idx_email ON users(email);

-- ✅ 좋은 예: 앞 20자만으로 충분한 선택도 확보
CREATE INDEX idx_email_prefix ON users(email(20));

-- 적정 prefix 길이 찾기: 전체 대비 유니크율 확인
SELECT
    COUNT(DISTINCT LEFT(email, 10)) / COUNT(DISTINCT email) AS sel_10,
    COUNT(DISTINCT LEFT(email, 15)) / COUNT(DISTINCT email) AS sel_15,
    COUNT(DISTINCT LEFT(email, 20)) / COUNT(DISTINCT email) AS sel_20
FROM users;
-- 0.95 이상이면 실전에서 쓸만한 선택도
```

**함정**: Prefix Index로는 `ORDER BY email`이 인덱스 순서를 그대로 못 쓴다(뒷글자가 잘려서). 그리고 Covering Index도 성립하지 않는다 — 옵티마이저는 잘린 부분 뒤를 확인하려고 결국 테이블 로우를 읽어야 한다.

```
전체 인덱스: [aaa@example.com][aaa@example.co.kr][aab@example.com]... 
              ↑ 페이지당 100개 엔트리, 트리 높이 4

Prefix(6):   [aaa@ex][aaa@ex][aab@ex]... 
              ↑ 페이지당 500개 엔트리, 트리 높이 3
              ↑ 인덱스 크기 1/5, 스캔 속도 향상
              ↑ 대신 정렬/커버링은 포기
```

> 💡 **왜 중요한가**: "긴 컬럼 = 인덱스를 걸까 말까"의 이분법에서 벗어나는 제3의 선택지 — 인덱스 크기와 선택도를 저울질해서 **필요한 만큼만 인덱싱하는 절충 설계**를 가능하게 한다.
