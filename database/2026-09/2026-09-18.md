### PostgreSQL `LISTEN/NOTIFY` — DB가 직접 쏘는 실시간 이벤트, Redis Pub/Sub이 필요 없는 순간

트랜잭션 안에서 `NOTIFY channel, 'payload'`를 호출하면 커밋 시점에 같은 채널을 `LISTEN` 중인 모든 세션에 페이로드가 푸시된다. Kafka/Redis 없이 "주문 상태 변경 → 웹소켓 브로드캐스트" 같은 파이프라인을 DB 하나로 끝낼 수 있다는 뜻이다. 단, 페이로드는 8000바이트 제한이고, 리스너가 죽어있는 동안 발행된 메시지는 **영구히 유실**된다 — At-most-once 세만틱이다.

```sql
-- 트리거로 자동 발행
CREATE OR REPLACE FUNCTION notify_order_change() RETURNS trigger AS $$
BEGIN
  PERFORM pg_notify('order_events',
    json_build_object('id', NEW.id, 'status', NEW.status)::text);
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_order_notify
  AFTER UPDATE OF status ON orders
  FOR EACH ROW EXECUTE FUNCTION notify_order_change();
```

```
[Client A]  UPDATE orders SET status='PAID' WHERE id=42;
     │
     │ COMMIT
     ▼
[PostgreSQL] ──NOTIFY order_events──┐
                                    ├─► [App 1] LISTEN order_events → WebSocket push
                                    ├─► [App 2] LISTEN order_events → 캐시 무효화
                                    └─► [App 3] (죽어있음) → 메시지 영구 유실 ❌
```

**함정**: `NOTIFY`는 트랜잭션 커밋 시점에만 실제 전송된다. 롤백되면 알림도 사라진다 — 이건 오히려 축복이지만, "커밋 전 미리 알림 보내기"는 불가능하다. 그리고 리스너가 페이로드를 처리하는 속도가 느리면 `pg_notification_queue_usage()`가 100%에 도달해 **모든 커밋이 블록된다**. 배달 보장이 필요하면 Outbox 테이블 + `NOTIFY`로 "새 행 있음" 신호만 보내고, 실제 데이터는 리스너가 폴링해서 읽는 하이브리드 패턴을 써라.

> 💡 **왜 중요한가**: 초당 수백 건 이하의 이벤트라면 Redis/Kafka 도입 없이 DB 하나로 실시간 파이프라인을 만들 수 있지만, "유실 없음"을 원하는 순간 이 패턴은 즉시 무너진다 — 인프라 절감과 배달 보장의 트레이드오프를 아는 것이 핵심이다.

### MySQL `SELECT ... FOR UPDATE SKIP LOCKED` — 워커 큐를 DB 테이블로 만드는 8.0의 비장의 카드

작업 큐 테이블에서 여러 워커가 동시에 `SELECT ... FOR UPDATE`로 다음 작업을 꺼내려 하면, 전통적으로는 첫 번째 워커가 락을 잡고 나머지는 **대기**한다 — 사실상 직렬화된다. `SKIP LOCKED`는 "이미 락 걸린 행은 건너뛰고 다음 걸 잡아라"라는 지시로, N개의 워커가 진짜 병렬로 서로 다른 작업을 집어간다. RabbitMQ/SQS 없이 DB 테이블 하나로 분산 작업 큐를 구현할 수 있다는 뜻이다.

```sql
-- 워커가 작업 하나 집기
START TRANSACTION;

SELECT id, payload FROM job_queue
WHERE status = 'PENDING'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;   -- 다른 워커가 잡은 행은 스킵

-- ... 실제 작업 수행 ...

UPDATE job_queue SET status = 'DONE' WHERE id = ?;
COMMIT;
```

```
job_queue 테이블 (status='PENDING'인 행들)
┌────┬─────────────┐
│ id │ payload     │
├────┼─────────────┤
│ 1  │ send_email  │ ◄── Worker A: FOR UPDATE (락 잡음)
│ 2  │ resize_img  │ ◄── Worker B: SKIP LOCKED → id=1 스킵, id=2 집음
│ 3  │ gen_report  │ ◄── Worker C: id=1,2 스킵, id=3 집음
│ 4  │ send_push   │
└────┴─────────────┘

FOR UPDATE만 썼다면? Worker B, C는 A가 커밋할 때까지 대기 → 처리량 = 1x
SKIP LOCKED 쓰면?      Worker A, B, C 병렬 처리 → 처리량 = 3x
```

**함정 1**: `SKIP LOCKED`는 트랜잭션 격리 수준의 "일관된 스냅샷"을 깨는 예외적 동작이다. 같은 트랜잭션에서 두 번 조회하면 결과가 다를 수 있다. **함정 2**: 워커가 죽으면 잡아둔 작업은 트랜잭션 롤백으로 자동 해제되지만, "너무 오래 걸리는 작업"을 감지하려면 `visibility_timeout` 컬럼과 주기적인 리클레임 배치가 필요하다. **함정 3**: PostgreSQL도 9.5부터 지원한다 — MySQL은 8.0.1부터.

> 💡 **왜 중요한가**: "메시지 큐 도입"이라는 인프라 결정을 미룰 수 있다 — 초당 수천 건 이하의 작업 처리량이라면 DB 테이블 + `SKIP LOCKED`가 운영 복잡도를 극적으로 낮춘다. 다만 "메시지 배달 보장", "재시도 정책", "DLQ"를 직접 구현해야 하므로, 규모가 커지면 결국 전용 큐로 이관해야 한다는 지점도 알아야 한다.
