### 12-Factor App의 12번째 요소 "Admin Processes" — 왜 "일회성 작업"이 프로덕션을 가장 자주 죽이는가

12-Factor App을 배우면 대부분 개발자들은 앞쪽 요소들(Codebase, Dependencies, Config, Backing Services)에 집중한다. 그러나 시니어가 되면 마지막 12번째 요소인 **Admin Processes**(관리자 프로세스)가 실제로는 가장 다루기 까다롭고, 가장 자주 장애의 근원이 된다는 것을 깨닫게 된다. DB 마이그레이션, 데이터 백필(backfill), 일회성 스크립트, 배치 작업 — 이것들이 "왜 12-Factor의 마지막 원칙"으로 자리잡았는지, 그리고 클라우드 네이티브 시대에 왜 이 원칙이 오히려 더 중요해졌는지를 파고들어야 한다.

#### 12-Factor의 마지막 원칙이 말하는 것

원문은 다음과 같이 짧다: *"Run admin/management tasks as one-off processes."* — 관리 작업을 **애플리케이션과 동일한 코드베이스, 동일한 릴리스, 동일한 환경 변수, 동일한 의존성**으로 실행하라는 것이다. 얼핏 보면 당연해 보이지만, 실제 현장에서는 이 원칙이 거의 지켜지지 않는다.

전형적인 안티패턴:

```
개발자 노트북 → SSH로 프로덕션 접속 → psql로 직접 접속 → UPDATE 쿼리 실행
        ↑
   "5분만 걸리니까 그냥 여기서 돌리자"
        ↓
   결과: 어떤 코드가 어떤 데이터를 바꿨는지 아무도 모름
        스키마 변경은 되었지만 코드 배포는 안 됨
        롤백 불가, 감사 로그 없음, 재현 불가
```

#### 클라우드 네이티브 시대에 이 문제가 더 심각해지는 이유

컨테이너와 Kubernetes 환경에서는 "일회성 작업"의 정의 자체가 흔들린다. Pod는 상태를 가지지 않고, 노드는 언제든 사라질 수 있으며, 배포는 롤링(rolling)으로 진행된다. 이 환경에서 admin 작업을 잘못 실행하면 다음과 같은 문제가 발생한다:

```
┌─────────────────────────────────────────────────────────┐
│           프로덕션 배포 파이프라인 (문제 상황)          │
└─────────────────────────────────────────────────────────┘

  [Deploy v2.0] ──┬──> Pod-A (v2.0) ──> DB (스키마 v1)  ❌ 컬럼 없음
                  ├──> Pod-B (v1.0) ──> DB (스키마 v1)  ✅
                  └──> Pod-C (v1.0) ──> DB (스키마 v1)  ✅

  롤링 배포 중 개발자가 psql 접속해서 "ALTER TABLE"실행
                  ↓
  [잠깐의 시간] Pod-B, Pod-C (v1.0) ──> DB (스키마 v2)  ❌ 이전 코드는 새 컬럼 몰라
                  ↓
  전체 에러율 폭증, 롤백도 불가 (스키마는 이미 바뀜)
```

#### 올바른 Admin Process 실행 방식

12-Factor가 말하는 "동일한 환경"을 Kubernetes에서 구현한다면 다음과 같다:

```yaml
# Kubernetes Job으로 admin task 실행 (동일 이미지, 동일 config)
apiVersion: batch/v1
kind: Job
metadata:
  name: user-email-backfill-20260708
spec:
  ttlSecondsAfterFinished: 86400  # 24시간 후 자동 정리
  backoffLimit: 2
  template:
    spec:
      containers:
      - name: backfill
        image: myapp:v2.3.1        # 프로덕션과 동일한 이미지
        command: ["java", "-jar", "app.jar", "--task=backfill-emails"]
        envFrom:
        - configMapRef:
            name: myapp-config     # 동일한 설정
        - secretRef:
            name: myapp-secrets    # 동일한 시크릿
      restartPolicy: OnFailure
```

핵심은 **admin 코드가 애플리케이션 코드베이스 안에 존재**하며, `--task=` 같은 진입점으로 분기된다는 점이다. Spring Boot라면 `CommandLineRunner` 또는 프로파일별 `@Component`로 구현할 수 있다:

```java
@Component
@Profile("task-backfill-emails")
public class EmailBackfillTask implements CommandLineRunner {

    private final UserRepository userRepository;
    private final EmailNormalizer normalizer;

    @Override
    public void run(String... args) throws Exception {
        // 청크 단위 처리, 진행률 로깅, 중단 지점 저장
        long lastId = loadCheckpoint();
        while (true) {
            List<User> batch = userRepository.findByIdGreaterThanOrderByIdAsc(
                lastId, PageRequest.of(0, 1000));
            if (batch.isEmpty()) break;

            batch.forEach(u -> u.setEmail(normalizer.normalize(u.getEmail())));
            userRepository.saveAll(batch);
            lastId = batch.get(batch.size() - 1).getId();
            saveCheckpoint(lastId);  // 재실행 가능성 확보
        }
    }
}
```

#### 트레이드오프

| 접근법 | 장점 | 단점 |
|---|---|---|
| **SSH로 직접 실행** | 즉시 실행, 유연함 | 감사 불가, 재현 불가, 환경 불일치 |
| **별도 admin 저장소** | 관심사 분리 | 애플리케이션 스키마/도메인과 불일치 위험 |
| **12-Factor 방식 (동일 이미지 + Job)** | 감사·재현·롤백 가능, 환경 일치 | 초기 셋업 비용, 배포 파이프라인에 통합 필요 |
| **Serverless (Lambda/Cloud Run Jobs)** | 인프라 관리 불필요 | 콜드 스타트, 실행 시간 제한, 로컬 재현 어려움 |

#### 실제 사례

**GitLab의 데이터베이스 마이그레이션 정책**: GitLab은 자체 문서에서 "post-deployment migration"과 "regular migration"을 엄격히 구분한다. 컬럼 추가 같은 하위 호환 변경은 배포 전에, 컬럼 삭제 같은 위험 작업은 배포가 완료되고 **모든 인스턴스가 새 코드로 전환된 뒤**에만 실행되도록 별도 파이프라인으로 분리했다. 이는 위 다이어그램의 "롤링 배포 중 스키마 불일치" 문제를 정면으로 해결한 사례다.

**Shopify의 Maintenance Tasks gem**: Shopify는 Rails 애플리케이션에서 일회성 작업을 표준화하기 위해 `maintenance_tasks`라는 오픈소스 라이브러리를 만들었다. 모든 admin 작업은 애플리케이션 코드베이스의 클래스로 정의되고, 관리 UI에서 실행·중단·재개가 가능하며, 완전한 실행 로그가 남는다. "SSH 접속해서 rails console 실행" 문화를 조직 차원에서 뿌리 뽑기 위한 결정이었다.

**Netflix의 "No SSH" 원칙**: Netflix는 프로덕션 인스턴스에 SSH 접속 자체를 원천 차단한다. 모든 진단·수정 작업은 애플리케이션이 노출한 관리 엔드포인트(actuator 유사) 또는 별도로 배포된 원격 작업 시스템(Titus, Meson)을 통해 실행된다. 이는 12-Factor의 원칙을 조직 정책으로 강제화한 극단적 사례다.

#### 시니어의 관점: 언제 쓰고 언제 쓰면 안 되는가

**반드시 12-Factor 방식으로 해야 하는 경우**:
- 데이터 변경이 수반되는 모든 작업 (백필, 정리, 마이그레이션)
- 여러 팀원이 재실행할 가능성이 있는 작업
- 감사 요구사항이 있는 도메인 (금융, 의료, 개인정보)
- 실행 시간이 몇 분 이상 걸리는 작업 (중간 실패 시 재개가 필요)

**예외적으로 즉석 실행이 정당화되는 경우**:
- 관측성 목적의 **읽기 전용** 쿼리 (그마저도 read replica에)
- 프로덕션이 이미 장애 상태이고 초 단위 대응이 필요할 때 (사후 반드시 회고)
- 스테이징/개발 환경 (하지만 프로덕션과 습관이 갈라지는 순간 재앙의 씨앗)

**함정**: "이번 한 번만"이라는 말은 조직 문화에서 가장 위험한 문장이다. 한 번 SSH로 UPDATE를 실행하는 순간, 그 팀의 모든 개발자에게 "이렇게 해도 된다"는 신호가 전달된다. 12-Factor의 마지막 원칙은 기술적 지침이라기보다 **조직의 규율**에 가깝다.

> 💡 **왜 중요한가**: 애플리케이션 코드는 정교하게 배포 파이프라인을 통과시키면서 "잠깐의 admin 작업"은 SSH로 처리하는 순간, 12-Factor의 모든 앞선 원칙이 무의미해진다 — 재현 가능성·환경 일치·감사 추적성이라는 클라우드 네이티브의 근간이 그 한 줄의 UPDATE로 무너진다.
