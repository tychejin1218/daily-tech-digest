### MySQL `Isolation Level`과 `REPEATABLE READ`의 함정 — 팬텀 리드는 막지만, 로스트 업데이트는 못 막는다

MySQL InnoDB의 기본 격리 수준인 `REPEATABLE READ`는 트랜잭션 내에서 같은 SELECT를 반복해도 같은 결과를 보장하지만, 이는 "스냅샷 읽기"에 한정된 이야기다. `SELECT` 후 `UPDATE`로 값을 덮어쓰는 패턴에서는 두 트랜잭션이 동시에 낡은 값을 읽고 각자 덮어써서 하나의 갱신이 통째로 사라지는 **Lost Update**가 여전히 발생한다. 진짜로 안전하려면 `SELECT ... FOR UPDATE`로 락을 걸거나, 낙관적 락(`WHERE version = ?`)으로 갱신 시점에 검증해야 한다.

```sql
-- 위험한 패턴 (REPEATABLE READ에서도 Lost Update 발생)
SELECT balance FROM account WHERE id = 1;  -- 트랜잭션 A, B 모두 100 읽음
UPDATE account SET balance = 90 WHERE id = 1;  -- A: 100→90
UPDATE account SET balance = 80 WHERE id = 1;  -- B: 100→80 (A의 차감 소실)

-- 안전한 패턴 1: 비관적 락
SELECT balance FROM account WHERE id = 1 FOR UPDATE;

-- 안전한 패턴 2: 낙관적 락
UPDATE account SET balance = ?, version = version + 1
WHERE id = 1 AND version = ?;
```

> 💡 **왜 중요한가**: "격리 수준을 높였으니 동시성 문제는 없다"는 착각은 결제·재고·포인트 시스템에서 원인 모를 잔액 불일치로 이어지며, 격리 수준은 읽기 일관성일 뿐 쓰기 경합의 해결책이 아니라는 사실을 반드시 구분해야 한다.

### JPA `@DynamicUpdate` — 변경된 컬럼만 UPDATE 문에 담는, 기본 동작이 아닌 옵션

Hibernate는 기본적으로 엔티티의 필드 하나만 바뀌어도 **모든 컬럼을 포함한 UPDATE 문**을 날린다. 이는 PreparedStatement 캐싱을 극대화하기 위한 설계지만, 컬럼이 30개가 넘는 넓은 테이블이나 `TEXT`/`JSON` 컬럼이 섞인 엔티티에서는 매번 거대한 쿼리가 네트워크로 나가고 불필요한 컬럼까지 리두 로그에 기록된다. `@DynamicUpdate`를 붙이면 실제 변경된 컬럼만 골라 UPDATE에 포함시켜, 쿼리 크기와 로그 부하를 극적으로 줄일 수 있다.

```java
@Entity
@DynamicUpdate  // 변경된 컬럼만 UPDATE에 포함
public class Article {
    @Id private Long id;
    private String title;
    private String author;

    @Column(columnDefinition = "TEXT")
    private String content;  // 수백 KB

    @Column(columnDefinition = "JSON")
    private String metadata;
}

// title만 바꿔도 기본 동작: UPDATE article SET title=?, author=?, content=?, metadata=? WHERE id=?
// @DynamicUpdate 적용: UPDATE article SET title=? WHERE id=?
```

트레이드오프: PreparedStatement가 매 UPDATE마다 달라져 DB 측 실행 계획 캐시 재사용률이 떨어진다. 즉, **좁고 자주 갱신되는 테이블**에는 오히려 손해고, **넓고 일부만 갱신되는 테이블**에서만 이득이다.

> 💡 **왜 중요한가**: "왜 title 하나 바꿨는데 슬로우 쿼리 로그에 100KB짜리 UPDATE가 찍히지?"라는 질문의 답은 Hibernate의 기본 정책에 있으며, 이는 성능 문제가 아니라 아키텍처 선택의 문제라는 점을 인지해야 대응이 달라진다.
