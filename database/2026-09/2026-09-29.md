### PostgreSQL `LATERAL JOIN` — 서브쿼리에서 "바깥 행"을 참조할 수 있게 만드는, "Top-N per Group"의 우아한 정답

일반 서브쿼리는 바깥 쿼리의 컬럼을 참조할 수 없지만, `LATERAL`을 붙이면 "왼쪽 테이블의 각 행마다 오른쪽 서브쿼리를 실행"하는 상관 서브쿼리로 변신한다. "카테고리별 최신 게시글 3개", "유저별 마지막 주문 1건" 같은 Top-N per Group 문제를 윈도우 함수 `ROW_NUMBER()` 없이도 인덱스를 그대로 활용하며 훨씬 깔끔하게 풀어낸다.

```sql
-- ❌ 윈도우 함수: 전체 스캔 후 필터링 (인덱스 활용 제한적)
SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY category_id ORDER BY created_at DESC) AS rn
  FROM posts
) t WHERE rn <= 3;

-- ✅ LATERAL JOIN: 카테고리마다 posts 인덱스로 Top 3만 정확히 뽑음
SELECT c.id, p.*
FROM categories c
CROSS JOIN LATERAL (
  SELECT * FROM posts
  WHERE category_id = c.id          -- 바깥 c.id 참조!
  ORDER BY created_at DESC
  LIMIT 3
) p;
-- 인덱스: (category_id, created_at DESC) 있으면 각 카테고리당 3행만 읽음
```

특히 카테고리 수가 적고 posts가 억 단위일 때 `LATERAL`이 압도적으로 빠르다 (Nested Loop + Index Scan). 반대로 카테고리가 많으면 윈도우 함수가 유리 — 항상 `EXPLAIN`으로 확인하라. `LEFT JOIN LATERAL`을 쓰면 매칭이 없어도 왼쪽 행이 보존된다.

> 💡 **왜 중요한가**: "그룹별 상위 N개"는 실무에서 매일 만나는 패턴인데, 대부분 윈도우 함수로 풀다가 인덱스를 못 태워서 느려진다 — `LATERAL`은 인덱스를 그대로 살리는 정공법이다.

### MySQL `FOUND_ROWS()`의 함정과 `SQL_CALC_FOUND_ROWS`의 죽음 — 페이지네이션의 "총 개수"를 구하는 진짜 방법

옛날 MySQL 튜토리얼에 자주 등장하는 `SELECT SQL_CALC_FOUND_ROWS ... LIMIT 20; SELECT FOUND_ROWS();`는 MySQL 8.0.17에서 **deprecated**됐고, 벤치마크상 별도 `COUNT(*)` 쿼리보다 오히려 느리다. 이유는 LIMIT을 무시하고 전체 결과셋을 끝까지 만들어야 하기 때문 — 인덱스 최적화, 조기 종료, 커버링 인덱스의 이점을 모두 포기한다.

```sql
-- ❌ 옛날 방식 (8.0.17+ deprecated, 느림)
SELECT SQL_CALC_FOUND_ROWS * FROM posts WHERE status='published'
ORDER BY created_at DESC LIMIT 20;
SELECT FOUND_ROWS();

-- ✅ 별도 COUNT 쿼리 (빠름, 인덱스 커버 가능)
SELECT * FROM posts WHERE status='published'
ORDER BY created_at DESC LIMIT 20;
SELECT COUNT(*) FROM posts WHERE status='published';
-- 인덱스 (status, created_at)가 있으면 Using index로 끝남

-- ✅✅ 더 나은 선택: Keyset Pagination (총 개수 아예 안 보여줌)
SELECT * FROM posts
WHERE status='published' AND created_at < :last_created_at
ORDER BY created_at DESC LIMIT 20;
-- 100만 페이지 뒤로 가도 상수 시간, OFFSET 지옥 탈출
```

정말로 정확한 총 개수가 필요한가? 구글도, 트위터도 "약 1,234,000개" 같은 근사치를 보여준다 — 대규모 테이블에서 정확한 `COUNT(*)`는 상수 시간이 아니다. 근사치로 충분하다면 `information_schema.tables.table_rows`나 PostgreSQL의 `pg_class.reltuples`를 활용하라.

> 💡 **왜 중요한가**: 페이지네이션의 "총 개수"는 UX 요구사항인 척하지만, 사실 성능의 최대 적이다 — 정말 필요한지부터 다시 물어야 한다.
