### Day 134. LLM Prompt Versioning & Rollback — "프롬프트? Git에 커밋하면 되죠"라는 치명적 순진함, 그리고 영업팀 긴급 요청으로 이메일 생성 프롬프트 한 줄을 `friendly` → `professional`로 바꿔 배포한 금요일 오후, 월요일 아침 "저희 거래 끊을까 해요"라는 메일 7통이 영업 VP 받은편지함에 쌓이고, 롤백하려 `git revert`를 치니 같은 PR에 묶인 **결제 모듈 버그픽스**까지 함께 되돌아가 결제 실패율이 0.8% → 11%로 튀어 CS 큐 800건이 쌓인 월요일 오전 10:17

---

#### 0. "프롬프트는 그냥 문자열인데 뭐가 어렵죠?" — 금요일 오후 16:42의 Slack

마케팅 리드에게서 멘션이 왔다.

> "영업 이메일 자동 생성이 너무 캐주얼해요. B2B 엔터프라이즈 톤으로 좀 바꿔주세요. 다음 주 월요일 캠페인 나가야 해요."

주니어 개발자가 15분 만에 PR을 올렸다.

```diff
# services/email_generator.py
- SYSTEM_PROMPT = "You are a friendly sales assistant. Write warm, conversational emails..."
+ SYSTEM_PROMPT = "You are a professional B2B sales expert. Write formal, business-appropriate emails..."
```

같은 PR에는 결제 모듈의 멀쩡한 버그픽스 2개가 묶여 있었다 (QA가 이미 승인한 상태). 금요일 17:30 배포. 주말은 조용했다.

**월요일 오전 09:55**, 영업 VP의 받은편지함이 폭발했다.

- "This email reads like a legal notice. Are we being audited?"
- "저희 담당자 바뀌었나요? 이전 톤이 더 좋았는데..."
- "We'll be reconsidering our renewal. Please remove us from your list."

이메일 1,247건이 주말에 발송됐고, 그중 수신 거부가 83건, "거래 재검토" 회신이 7건이었다. ARR $240K 거래 1건 포함.

**월요일 오전 10:12**, CTO가 Slack에 긴급 호출.

> "지금 당장 금요일 이전으로 롤백하세요."

개발자가 `git revert <PR hash>`를 실행했다. 10:17에 배포 완료. 그런데...

**10:23**, 결제 알림이 쏟아지기 시작했다. 결제 실패율이 평소 0.8%에서 **11%**로 튀었다. 같은 PR에 묶여 되돌아간 결제 버그픽스 2개 때문이었다. CS 큐에 "결제 안 돼요" 티켓이 **40분 만에 800건** 쌓였다.

"프롬프트 한 줄 바꾸는 게 왜 이렇게 어렵죠?" 주니어가 묻자, 시니어가 한숨을 쉬었다.

> "그게 코드 배포 사이클에 묶여 있어서요. 프롬프트는 **데이터**지 **코드**가 아닌데, 우리가 코드처럼 다뤘거든요."

#### 1. 왜 "Git 커밋"으로는 부족한가 — 프롬프트가 코드와 다른 4가지 이유

| 축 | 애플리케이션 코드 | LLM 프롬프트 |
|---|---|---|
| **변경 주기** | 주/월 단위 | **시간/일 단위** (카피라이팅, 톤 조정, few-shot 추가) |
| **변경 주체** | 개발자만 | PM, 마케터, 도메인 전문가 (**비개발자 포함**) |
| **배포 비용** | CI/CD 파이프라인 전체 | 이상적으로는 **0초 (hot-swap)** |
| **검증 방식** | 단위 테스트 (deterministic) | **Eval Set + 샘플 비교** (stochastic) |
| **롤백 단위** | PR / Commit | **프롬프트 단독** (다른 코드와 독립) |

프롬프트를 소스코드 안의 문자열 상수로 박아두면 이 4가지가 **전부** 코드 배포 사이클에 종속된다. 마케터가 톤을 바꾸고 싶으면 티켓 → PR → 리뷰 → 배포 → 롤아웃을 거쳐야 하고, 롤백은 결제 모듈 버그픽스까지 같이 되돌리는 재앙이 된다.

핵심은 **"프롬프트는 데이터이며, 코드와 독립된 릴리스 사이클을 가져야 한다"**는 것이다.

#### 2. 안티패턴: "소스코드 임베디드 프롬프트" vs 목표 아키텍처

```
┌───────────────────────── 안티패턴 (금요일의 재앙) ─────────────────────────┐
│                                                                           │
│  [email_generator.py]                                                     │
│      SYSTEM_PROMPT = "You are..."  ◄── hard-coded                         │
│           │                                                               │
│           ▼                                                               │
│      llm.chat(prompt=SYSTEM_PROMPT + user_input)                          │
│                                                                           │
│  문제:                                                                    │
│    - 변경 = 코드 배포                                                     │
│    - A/B test 불가                                                        │
│    - 롤백 = 코드 revert (collateral damage)                               │
│    - 비개발자 수정 불가                                                   │
│    - 어떤 요청이 어떤 버전으로 처리됐는지 트레이스 불가                   │
│                                                                           │
└───────────────────────────────────────────────────────────────────────────┘

┌─────────────────────── 목표: Prompt Registry 아키텍처 ────────────────────┐
│                                                                           │
│   [Marketing/PM]                [Developer]                               │
│         │                            │                                    │
│         │ edit via UI                │ reference by name                  │
│         ▼                            ▼                                    │
│   ┌──────────────────────────────────────────┐                            │
│   │     Prompt Registry (external SoT)        │                           │
│   │                                           │                           │
│   │  email_gen@v1.3.0  "friendly..."          │                           │
│   │  email_gen@v1.4.0  "professional..."      │                           │
│   │  email_gen@production  ──► alias: v1.3.0  │  ◄── hot-swap             │
│   │  email_gen@canary      ──► alias: v1.4.0  │                           │
│   │                                           │                           │
│   │  + Eval Set, Diff, Approval, Audit Log    │                           │
│   └──────────────┬───────────────────────────┘                            │
│                  │                                                        │
│    ┌─────────────┼──────────────┐                                         │
│    ▼             ▼              ▼                                         │
│  [App]        [LLM Gateway]  [Observability]                              │
│                  │              │                                         │
│                  ▼              ▼                                         │
│       prompt_name + user_input  trace 기록:                               │
│       → 95% v1.3.0 (prod)        - prompt_name                            │
│       → 5%  v1.4.0 (canary)      - prompt_version                         │
│                                  - rendered_prompt_hash                   │
└───────────────────────────────────────────────────────────────────────────┘
```

**이 아키텍처가 금요일의 재앙을 어떻게 막는가**:

1. 마케터가 UI에서 프롬프트를 바꾼다 → `email_gen@v1.4.0` 생성, **배포 없음**
2. 먼저 5% canary로 라우팅 (A/B)
3. 83건의 거부율이 **2시간 만에** Eval 대시보드에 뜸
4. 롤백 = alias 포인터만 바꿈: `production → v1.3.0`, **5초 내 완료**
5. 결제 모듈과 완전히 독립된 사이클

#### 3. 핵심 구성요소 5가지

##### (1) Prompt as a First-Class Resource — 네임스페이스 + Semver

프롬프트도 코드의 라이브러리처럼 다룬다.

```yaml
# prompt registry entry
name: email_generator.sales_outreach
version: 1.4.0
model: claude-sonnet-4-6
template: |
  You are a professional B2B sales expert...
  
  Target customer: {{customer_profile}}
  Previous interaction: {{last_touch}}
  
  Write an email that...
variables:
  - customer_profile: {type: string, required: true}
  - last_touch: {type: string, required: false}
metadata:
  owner: marketing-team
  created_by: jane@company.com
  created_at: 2026-11-07T14:30:00Z
  approved_by: sales-vp@company.com
  eval_set: sales_email_quality_v2
```

- **버전은 Semver**: breaking change (변수 추가/삭제) = major, 톤 조정 = minor, 오타 = patch
- **별칭(alias)로 환경 분리**: `production`, `canary`, `shadow`
- **승인자(approved_by)**: B2B 톤 변경 같은 비즈니스 임팩트 큰 건은 도메인 오너 서명 필수

##### (2) Rendered Prompt Hash — "실제로 모델에 들어간 문자열"의 지문

버전 이름만으로는 부족하다. 변수 치환 후 **실제 LLM에 들어간 문자열의 SHA256**을 trace에 기록해야 "어떤 요청이 어떤 상태의 프롬프트로 처리됐는지" 재현 가능하다.

```python
rendered = template.render(customer_profile="...", last_touch="...")
trace.log({
    "prompt_name": "email_generator.sales_outreach",
    "prompt_version": "1.4.0",
    "rendered_hash": sha256(rendered).hexdigest()[:12],
    "model": "claude-sonnet-4-6",
    "model_params": {"temperature": 0.7, "max_tokens": 1024}
})
```

왜 중요한가? "같은 v1.4.0인데도 고객 프로필에 공백이 섞인 케이스만 톤이 이상했다"는 패턴은 **rendered_hash를 그룹바이**해야 보인다. 버전만 봐서는 보이지 않는다.

##### (3) Canary + Alias 기반 롤아웃

프롬프트 배포는 **코드 배포가 아니라 포인터 전환**이다.

```python
# LLM Gateway 내부 라우팅
def route_prompt(prompt_name: str, request_id: str) -> PromptVersion:
    config = registry.get_rollout_config(prompt_name)
    # {"production": "v1.3.0", "canary": "v1.4.0", "canary_pct": 5}
    
    if hash(request_id) % 100 < config["canary_pct"]:
        return registry.load(prompt_name, config["canary"])
    return registry.load(prompt_name, config["production"])
```

- **1% → 5% → 25% → 100%** 단계적 롤아웃
- 각 단계에서 Eval 메트릭 (helpfulness, tone match, 거부율) 비교
- 롤백은 `canary_pct: 0`만 세팅 — **1초**

##### (4) Eval Set — 프롬프트의 "단위 테스트"

프롬프트를 바꿀 때마다 **고정된 테스트 입력 50~200건**을 돌려서 결과를 비교한다.

```python
# eval_sets/sales_email_quality_v2.yaml
test_cases:
  - id: enterprise_cold_outreach
    inputs:
      customer_profile: "Fortune 500 CFO, financial services"
      last_touch: null
    assertions:
      - type: llm_judge
        criterion: "Email maintains professional but warm tone"
        threshold: 4.0  # out of 5
      - type: contains_not
        value: ["Hey there", "What's up"]
      - type: length_between
        min: 80, max: 200  # words
```

PR 올라오면 CI가 자동으로:
1. 신버전 프롬프트로 전체 eval set 실행
2. 구버전과 결과 diff
3. **회귀 발견 시 머지 차단**

금요일의 사고는 eval set만 있었어도 "formal 변경이 B2B 거래 재검토 뉘앙스를 유발한다"는 걸 배포 전에 LLM-as-judge가 잡았을 가능성이 높다.

##### (5) 감사 로그 + 인간 승인 게이트

```
[Audit Log]
2026-11-07 14:30  jane@company.com  CREATED  email_gen v1.4.0
2026-11-07 15:12  sales-vp@         APPROVED (business-impact: HIGH)
2026-11-07 16:00  system             CANARY  5% → v1.4.0
2026-11-10 10:19  oncall@            ROLLBACK production → v1.3.0 (reason: 83 unsubscribes, 7 renewal reviews)
```

프롬프트가 데이터라 해도, "매출에 직접 영향 주는 톤 변경"은 **비즈니스 오너 승인 게이트**를 둬야 한다. 코드 리뷰는 개발자가 하지만, 영업 이메일 톤 승인은 영업 VP가 해야 맞다.

#### 4. 저장소 선택: 어디에 프롬프트를 두나?

| 옵션 | 장점 | 단점 | 언제 |
|---|---|---|---|
| **Git 리포 (yaml/json)** | 코드 리뷰, diff, 무료 | 비개발자 접근 불가, hot-swap 안 됨, CI 배포 필요 | 프로토타입, 프롬프트 수가 <10개, 변경 주기 주 1회 이하 |
| **DB 테이블 + 자체 관리 UI** | 완전한 통제, 사내 시스템 통합 | **구축/유지 비용 큼** (승인, diff, eval 다 자체 구현) | 규제 산업 (금융, 의료), 외부 SaaS 금지 환경 |
| **LangSmith / LangFuse / PromptLayer** | UI, 승인, eval, trace 통합 제공 | 벤더 lock-in, 월 비용 ($100~$2,000), 민감 프롬프트 외부 유출 리스크 | 프롬프트 수 >20개, 비개발자 편집, trace 통합 필요 |
| **Feature Flag 서비스 (LaunchDarkly 등 재활용)** | 기존 canary/rollout 인프라 활용 | 긴 문자열 저장에 최적화 안 됨, diff UI 빈약 | 이미 FF 조직 전체 표준이고 프롬프트 수 적을 때 |

**실무 가이드**: 프롬프트 5개 이하면 Git yaml로 시작 → 20개 넘으면 LangFuse/LangSmith → 금융·의료는 자체 구축 (이 순서로 성장하는 게 자연스럽다).

#### 5. 실제 사례

**GitHub Copilot (2023 블로그)**: 프롬프트를 "prompt crafting library"로 분리하고 모델 버전별로 다른 프롬프트를 매핑하는 테이블을 유지. 모델 업그레이드 시 프롬프트도 함께 롤아웃/롤백. 이 분리 덕분에 Codex → GPT-3.5 → GPT-4 전환이 **코드 배포 없이** 비율 조정만으로 진행됨.

**Notion AI**: 2023년 "Q&A" 기능 배포 시 프롬프트를 PromptLayer에 외부화. PM이 "답변이 너무 길다"는 유저 피드백 받은 날, **개발자 호출 없이** PM이 직접 톤 조정 후 5% canary → 다음 날 100% 전환. 평균 응답 길이 40% 감소, 만족도 +12%p.

**Shopify Sidekick (2024)**: 각 상점 카테고리별 (패션, 전자제품, 식품...) 프롬프트를 버전 관리. 블랙프라이데이 전주, "할인 추천 톤" 프롬프트의 전자제품 버전만 캐너리로 올리다 전환율 하락 감지 → **10분 내 롤백**. 같은 저장소의 다른 카테고리는 영향 없음.

**실패 사례 (익명)**: 2024년 어느 핀테크 스타트업. 챗봇 응답에서 "guaranteed return" 같은 표현을 금지하는 프롬프트 수정이 Git PR로 들어갔는데, 같은 PR에 묶인 다른 리팩터링 때문에 머지가 2주 지연. 그동안 챗봇이 100+ 유저에게 "고수익 보장" 뉘앙스 응답을 보내 **FINRA 경고 서한**을 받음. 사후 분석: "프롬프트 변경을 코드 배포와 분리했어야 했다"가 1순위 액션 아이템.

#### 6. 트레이드오프 — 공짜 점심은 없다

| 트레이드오프 | 설명 |
|---|---|
| **민첩성 ↔ 통제** | hot-swap이 쉬운 만큼, 아무나 바꾸면 금요일의 재앙이 반복된다. **승인 게이트**를 꼭 둬야 하지만 너무 빡세면 민첩성이 죽는다. 비즈니스 임팩트 등급(low/med/high)으로 차등 승인 설계 |
| **외부 의존 ↔ 신뢰성** | LangFuse/PromptLayer 장애 시 "프롬프트를 못 불러와서 서비스 다운"이 될 수 있다. → **런타임 캐시 + 정적 fallback 번들** 필수 |
| **버전 폭발 ↔ 추적성** | 하루 5번 바꾸면 한 달에 150 버전. 90일 이상 미사용 버전은 **archive → cold storage**로 자동 정리하되, trace와 매칭 가능하도록 rendered_hash는 보존 |
| **A/B 분할 ↔ 통계 유의성** | canary 5%로 돌려도 하루 요청이 500건이면 통계 유의성 확보 전에 성급한 롤백/승격을 할 수 있다. → **최소 샘플 수 + Bayesian early stopping** 규칙 |
| **보안** | 프롬프트가 외부 SaaS에 가면 **시스템 프롬프트에 박힌 내부 규칙·용어·전략**이 외부로 유출된다. 민감 프롬프트는 self-hosted or on-prem |

#### 7. 시니어 관점: 언제 쓰고 언제 쓰면 안 되는가

**도입해야 할 때**
- 프로덕션 LLM 기능이 **2개 이상**이고, 각각 프롬프트가 분리돼 있을 때
- **비개발자 (PM, 마케터, 도메인 전문가)**가 프롬프트를 수정해야 할 때
- A/B 테스트로 프롬프트 품질 비교를 하고 싶을 때
- 사고 발생 시 "어떤 버전의 프롬프트가 어떤 요청을 처리했나" **재현 가능성**이 필요할 때 (규제 산업, 고객 응대)
- 프롬프트 변경 주기가 **주 1회 이상**일 때

**아직 쓰면 안 되는 때**
- MVP 단계, 프롬프트 1~2개, 변경이 월 1회 이하 → Git yaml 하나로 충분. 오버엔지니어링
- 팀이 LLM Observability(trace, eval) 기반을 아직 안 갖춘 상태 → 먼저 그걸 구축. Versioning은 Observability 위에 얹히는 레이어
- 프롬프트 변경에 비즈니스 오너 없음 → 승인 게이트가 없으면 민첩성만 커지고 사고 확률도 같이 커진다. "누가 책임질 것인가"가 먼저
- **자체 UI 만들겠다는 야심** — PromptLayer/LangFuse 같은 제품이 수년간 쌓은 UX를 재발명하는 데 3개월 날리지 말 것. 규제 때문이 아니면 사지 말고 만들지 말라의 반대: **만들지 말고 사라**

---

#### 8. 체크리스트 — 월요일 아침에 바로 시작하는 5단계

1. **인벤토리**: 지금 코드베이스에서 `SYSTEM_PROMPT =`, `prompt =`, `You are...`를 grep해서 하드코딩된 프롬프트 리스트업 (보통 10개 넘는다)
2. **분류**: 각 프롬프트를 (변경 주기 × 비즈니스 임팩트) 매트릭스로 분류 → 상위 3개부터 외부화
3. **네이밍**: `<domain>.<usecase>` 규칙 정하기 (예: `email.sales_outreach`, `support.ticket_summary`)
4. **Trace 통합**: 모든 LLM 호출에 `prompt_name`, `prompt_version`, `rendered_hash` 로깅 (이게 안 되면 롤백도 측정도 못 함)
5. **최소 Eval Set**: 각 프롬프트당 10~20개 테스트 케이스부터. 완벽할 필요 없음. CI에 걸어서 **회귀만 잡아도** 충분한 가치

---

> 💡 **왜 중요한가**: 프롬프트는 코드가 아니라 **데이터**이며, 코드와 독립된 릴리스 사이클·롤백 경로·감사 추적을 가져야 비로소 LLM 기능을 "소프트웨어처럼" 운영할 수 있다 — 그걸 안 하면 금요일 오후의 한 줄 수정이 월요일 아침 결제 모듈을 같이 끌고 죽는다.
