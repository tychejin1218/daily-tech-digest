### Database Tip 1: MySQL `Buffer Pool`의 Young/Old 리스트 — "한 번 쓰고 버릴 대용량 스캔"이 캐시를 밀어내지 못하게 막는 LRU의 이중 구조

InnoDB의 Buffer Pool은 단순 LRU가 아니라 **Young(최근 자주 쓰는 핫 페이지)과 Old(새로 들어온 콜드 페이지)** 두 영역으로 분리된 리스트다. 새 페이지는 LRU의 맨 앞이 아닌 **Old 영역의 선두(기본 37% 지점)** 에 삽입되고, `innodb_old_blocks_time`(기본 1000ms) 안에 다시 접근되지 않으면 Young으로 승격되지 못한 채 조용히 밀려난다. 덕분에 `SELECT * FROM huge_table` 같은 **일회성 풀스캔**이 수만 페이지를 쏟아넣어도 핫 데이터는 Young 영역에서 안전하게 보존된다.

> 💡 **왜 중요한가**: 야간 배치 하나가 Buffer Pool을 통째로 날려 다음 날 아침 서비스 응답이 10배 느려지는 "캐시 오염(Cache Pollution)" 사고를 막는 InnoDB의 숨은 방어선이기 때문이다.

### Database Tip 2: JPA `@Version` 낙관적 잠금 — DB 락을 걸지 않고도 "덮어쓰기 사고"를 감지하는 `WHERE version = ?`의 숨은 트릭

`@Version` 필드를 엔티티에 선언하면 Hibernate가 모든 UPDATE 문에 **`WHERE id = ? AND version = ?`** 조건을 붙이고 SET 절에서 `version = version + 1`을 자동 추가한다. 두 트랜잭션이 동시에 같은 행을 수정하려 하면 **나중에 커밋하는 쪽의 UPDATE가 0 rows affected로 실패**하고 Hibernate는 `OptimisticLockException`을 던진다. 비관적 락(`SELECT ... FOR UPDATE`)과 달리 **DB 레벨 잠금을 전혀 걸지 않기 때문에** 읽기가 압도적으로 많은 환경에서 처리량이 수십 배 차이 난다.

> 💡 **왜 중요한가**: "A가 재고 10개 확인 → B가 재고 10개 확인 → 둘 다 1개 차감"처럼 **읽은 뒤 쓰는 패턴(Read-Modify-Write)의 Lost Update**를 락 경합 없이 탐지하는, 분산 환경에서 사실상 유일하게 확장 가능한 동시성 제어 수단이기 때문이다.
