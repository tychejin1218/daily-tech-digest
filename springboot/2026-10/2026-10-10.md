### `@Autowired` 필드 주입은 **final을 쓸 수 없고, 순환 참조를 런타임까지 숨긴다**

Spring 4.3부터 생성자가 하나면 `@Autowired`를 생략할 수 있지만, 여전히 필드 주입(`@Autowired private XxxService service;`)을 쓰는 코드가 많다. 필드 주입은 `final` 키워드를 붙일 수 없어 불변성이 깨지고, 순환 참조가 있어도 애플리케이션이 **일단 뜬 뒤 호출 시점에 터진다**. 생성자 주입으로 바꾸면 Spring이 **기동 시점에 순환 참조를 감지하고 바로 실패**시킨다.

```java
// 나쁜 예: 순환 참조가 런타임까지 숨겨짐
@Service
public class OrderService {
    @Autowired private PaymentService paymentService;  // final 불가
}

// 좋은 예: 기동 시 순환 참조 즉시 감지
@Service
@RequiredArgsConstructor
public class OrderService {
    private final PaymentService paymentService;  // 불변 + 테스트 용이
}
```

> 💡 **왜 중요한가**: 필드 주입은 "일단 돌아가게" 만들지만, 생성자 주입은 "애초에 잘못된 구조를 만들 수 없게" 만든다 — 설계 문제를 컴파일/기동 시점으로 당긴다.

---

### `@Modifying` 쿼리 후에는 **영속성 컨텍스트가 여전히 옛날 데이터를 들고 있다**

`@Modifying`이 붙은 JPQL/네이티브 UPDATE·DELETE는 DB에는 바로 반영되지만, **1차 캐시(영속성 컨텍스트)와는 동기화되지 않는다**. 같은 트랜잭션 안에서 벌크 업데이트 후 엔티티를 다시 조회하면 **DB가 아닌 캐시에 있는 변경 전 값**이 반환되어 디버깅이 지옥이 된다. `clearAutomatically = true`나 `flushAutomatically = true`를 명시해야 안전하다.

```java
// 함정: 업데이트 후 조회 시 옛날 값이 그대로 나옴
@Modifying
@Query("UPDATE User u SET u.status = 'INACTIVE' WHERE u.lastLogin < :date")
int deactivateInactive(@Param("date") LocalDate date);

// 안전: 쿼리 실행 후 영속성 컨텍스트 자동 정리
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("UPDATE User u SET u.status = 'INACTIVE' WHERE u.lastLogin < :date")
int deactivateInactive(@Param("date") LocalDate date);
```

> 💡 **왜 중요한가**: ORM이 "DB와 자바 객체를 하나로 보이게" 해주는 추상화는, 벌크 연산 앞에서 조용히 깨진다 — 그리고 테스트는 멀쩡히 통과한다.
