### `@Transactional`의 `rollbackFor`를 지정하지 않으면 **Checked Exception은 롤백되지 않는다**

Spring의 `@Transactional`은 기본적으로 `RuntimeException`과 `Error`에 대해서만 롤백한다. `IOException`이나 `SQLException` 같은 Checked Exception이 터져도 트랜잭션은 **그대로 커밋**되므로, 외부 I/O 실패 후에도 DB에는 반쪽짜리 데이터가 남는다.

```java
// ❌ 함정: IOException이 터져도 커밋된다
@Transactional
public void processOrder(Order order) throws IOException {
    orderRepository.save(order);
    externalApiClient.notify(order); // IOException 발생 가능
}

// ✅ 명시적으로 지정
@Transactional(rollbackFor = Exception.class)
public void processOrder(Order order) throws IOException { ... }
```

> 💡 **왜 중요한가**: "예외가 터지면 롤백되겠지"라는 당연한 믿음이 Checked Exception에서는 깨진다. 결제, 외부 API 연동처럼 Checked Exception을 던지는 코드에서는 반드시 `rollbackFor`를 명시해야 데이터 정합성이 보장된다.

### `Bean Validation`의 `@Valid`는 **중첩 객체에 자동 전파되지 않는다** — `@Valid`를 또 붙여야 한다

`@RequestBody @Valid`는 최상위 DTO의 필드만 검증한다. DTO 내부에 또 다른 객체가 있다면, 그 필드에 `@Valid`를 다시 붙이지 않는 한 중첩 객체의 제약 조건(`@NotBlank`, `@Email` 등)은 **완전히 무시된다**.

```java
public class OrderRequest {
    @NotNull
    private Long userId;

    // ❌ @Valid 없으면 Address 내부 검증 안 됨
    private Address address;

    // ✅ 중첩 검증 활성화
    @Valid
    @NotNull
    private Address address;
}

public class Address {
    @NotBlank  // @Valid 없으면 무시됨
    private String city;
}
```

> 💡 **왜 중요한가**: 필드 하나가 유효성 검증을 뚫고 DB까지 흘러가면, 그 데이터는 영원히 "검증을 통과한 척하는 쓰레기"가 된다. 중첩 DTO가 많은 복잡한 요청(주문, 배송, 결제 정보가 함께 오는 API)에서 가장 자주 발생하는 보안·데이터 품질 사고다.
