### PostgreSQL `pg_stat_statements` — 실제 프로덕션 쿼리 부하를 정규화해서 병목 찾기

`shared_preload_libraries`에 등록해두면 실행된 모든 쿼리를 파라미터가 제거된 정규화 형태로 집계해 `total_exec_time`, `calls`, `mean_exec_time`, `rows`, `shared_blks_hit`/`read` 같은 지표를 누적한다. `EXPLAIN`은 특정 쿼리 한 방을 분석할 때 쓰지만, "지난 24시간 동안 어떤 쿼리가 CPU를 가장 많이 먹었나"는 이 뷰에서만 답이 나온다.

```sql
-- postgresql.conf: shared_preload_libraries = 'pg_stat_statements'
CREATE EXTENSION pg_stat_statements;

SELECT queryid,
       calls,
       round(total_exec_time::numeric, 2) AS total_ms,
       round(mean_exec_time::numeric, 2)  AS mean_ms,
       round((100 * total_exec_time / sum(total_exec_time) OVER ())::numeric, 1) AS pct,
       query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;

SELECT pg_stat_statements_reset();  -- 배포 전후 비교할 때
```

`mean_ms`가 낮아도 `calls`가 폭발적으로 많으면 `pct`가 상위권에 뜨는데, 이런 "빠르지만 자주 호출되는" 쿼리는 프로파일러 없이는 못 잡는다. APM으로 잡히지 않는 배치·크론·리포트 쿼리도 그대로 잡히는 게 강점.

> 💡 **왜 중요한가**: "느린 쿼리"가 아니라 "누적 부하가 큰 쿼리"를 정량적으로 지목해줘야 튜닝 순서를 정할 수 있다.

### JPA `@Version` 낙관적 락 — `UPDATE ... WHERE version = ?`으로 lost update 원천 차단하기

동일 엔티티를 여러 트랜잭션이 동시에 수정할 때 DB 락 없이 `UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?` 형태로 갱신을 시도해, 조건 불일치로 0행이 갱신되면 Hibernate가 `OptimisticLockException`을 던진다. 비관적 락(`SELECT ... FOR UPDATE`)이 대기·데드락을 유발하는 상황에서 짧은 읽기-수정-쓰기 사이클에 훨씬 잘 맞는다.

```java
@Entity
class Order {
    @Id Long id;
    @Version Long version;  // Long / Integer / Timestamp 가능
    int quantity;
}

// 컨트롤러/서비스에서 재시도로 감싸는 게 정석
@Retryable(retryFor = ObjectOptimisticLockingFailureException.class,
           maxAttempts = 3, backoff = @Backoff(delay = 50))
@Transactional
public void decrement(Long id) {
    Order o = repo.findById(id).orElseThrow();
    o.setQuantity(o.getQuantity() - 1);  // flush 시점에 version 검사
}
```

핵심은 "예외가 던져지면 재시도" 흐름을 클라이언트가 아닌 서버에서 책임지는 것. 재시도 정책 없이 `@Version`만 붙이면 사용자에게 500이 그대로 노출된다. 충돌률이 낮은 도메인(주문·프로필·설정)에 특히 잘 맞고, 충돌률이 높으면 오히려 비관적 락이 낫다.

> 💡 **왜 중요한가**: 대부분의 "왜 재고가 마이너스가 됐냐" 사고는 트랜잭션 격리 수준이 아니라 lost update이고, `@Version` 한 줄이 이를 구조적으로 막는다.
