### Hybrid Search — "Vector Search만 있으면 충분하다"는 오만, 그리고 BM25가 25년 지나도 여전히 밥값 하는 이유

## 1. 도발: "벡터가 의미를 이해한다"는 문장에 숨은 거짓말

RAG를 처음 만들면 대개 이런 코드로 시작한다.

```python
docs = vector_db.similarity_search(query, k=5)
answer = llm.generate(context=docs, question=query)
```

그리고 데모에서는 잘 돈다. "사용자 인증 실패" 같은 자연어 질문에 관련 문서를 잘 찾아온다. 그래서 팀은 결론을 내린다. **"임베딩이 의미를 이해하니까, 옛날 검색(BM25/TF-IDF)은 이제 필요 없다."**

그리고 프로덕션에서 이 쿼리가 들어온다.

> "ORA-01555 에러 해결 방법"

벡터 검색은 `ORA-01555`를 다루는 문서가 아니라 "Oracle 에러 해결", "데이터베이스 트러블슈팅" 같은 **의미상 비슷한** 문서를 상위에 올린다. 정작 `ORA-01555`라는 정확한 토큰이 들어간 문서는 6위, 12위에 있다. 답변은 그럴싸하지만 틀렸다.

**임베딩은 의미는 잡지만 "고유명사, 코드, ID, 버전, 오타"에 약하다.** 벡터 공간에서 `ORA-01555`와 `ORA-01554`는 이웃이다. 인간에게는 전혀 다른 에러인데.

여기서 팀이 두 번째로 배우는 진실이 있다. **BM25는 죽지 않았다. 벡터의 사각지대를 정확히 커버한다.**

---

## 2. Hybrid Search가 뭔가

두 개의 검색 엔진을 **동시에** 돌리고, 결과를 **하나의 랭킹**으로 합친다.

- **Dense (Vector)**: 임베딩 유사도 — 의미(semantic) 검색. "인증 실패" ≒ "로그인 안 됨"을 이해.
- **Sparse (Keyword/BM25)**: 토큰 매칭 — 어휘(lexical) 검색. `ORA-01555`, `v2.3.1`, `kubectl` 같은 리터럴에 강함.

```
┌──────────────────────────────────────────────────────────────┐
│                       User Query                             │
│              "ORA-01555 undo tablespace 문제"                │
└───────────────┬──────────────────────────┬───────────────────┘
                │                          │
      ┌─────────▼─────────┐      ┌─────────▼─────────┐
      │  Embedding Model  │      │   Tokenizer +     │
      │  (dense vector)   │      │   BM25 Index      │
      └─────────┬─────────┘      └─────────┬─────────┘
                │                          │
      ┌─────────▼─────────┐      ┌─────────▼─────────┐
      │   Vector Search   │      │  Keyword Search   │
      │   top-K (k=50)    │      │   top-K (k=50)    │
      └─────────┬─────────┘      └─────────┬─────────┘
                │                          │
                └──────────┬───────────────┘
                           │
                ┌──────────▼──────────┐
                │   Fusion (RRF or    │  ← 여기가 핵심
                │   Weighted Sum)     │
                └──────────┬──────────┘
                           │
                ┌──────────▼──────────┐
                │   Re-ranker         │  (Optional, Cross-Encoder)
                │   (Cohere/BGE)      │
                └──────────┬──────────┘
                           │
                        top-5 → LLM
```

두 검색기는 **다른 언어**로 문서를 순위 매긴다. 벡터는 코사인 유사도(0~1), BM25는 정규화되지 않은 점수(0~수십). **이 둘을 어떻게 합치느냐가 Hybrid Search의 진짜 문제다.**

---

## 3. 합치는 법 1: 가중치 합 (그리고 왜 이게 대부분 실패하는가)

가장 나이브한 접근.

```python
final_score = α * vector_score + (1 - α) * bm25_score
```

**왜 잘 안 되는가:**

1. **스케일 문제**: 벡터 점수는 [0, 1], BM25는 [0, ∞). 정규화하지 않으면 한쪽이 지배한다.
2. **α 튜닝 지옥**: 쿼리마다 최적 α가 다르다. 코드 검색은 α=0.2가 좋고, 자연어 질문은 α=0.7이 좋다. **정적 α는 항상 어느 한쪽에서 손해**를 본다.
3. **분포 왜곡**: BM25는 흔한 토큰이 많은 문서에 급격한 점수를 준다. 정규화 후에도 heavy-tail이 남는다.

프로덕션에서 이걸 그대로 쓰는 팀은 드물다. 대신 다들 **RRF**로 도망간다.

---

## 4. 합치는 법 2: Reciprocal Rank Fusion (RRF) — 왜 이게 사실상 표준이 됐는가

**점수를 버리고, 순위(rank)만 쓴다.**

```
RRF_score(d) = Σ (1 / (k + rank_i(d)))
                i ∈ retrievers
```

- `rank_i(d)`: 검색기 i에서 문서 d의 순위 (1위, 2위, ...)
- `k`: 상수 (보통 60). 상위 문서에 지나친 가중을 주지 않는 완충 장치.

**왜 이게 지배적인가:**

- 점수 스케일 정규화가 필요 없다. 순위만 있으면 된다.
- 하이퍼파라미터가 사실상 하나(`k`)뿐이고, `k=60`이 대부분 잘 돈다 (Cormack et al. 2009 원논문에서 경험적으로 발견).
- 검색기를 3개, 4개로 늘려도 그대로 확장된다.

Elasticsearch 8.x, Weaviate, Vespa, Qdrant, Milvus, OpenSearch, pgvector + tsvector 조합까지 — **거의 모두가 RRF를 기본 fusion으로 채택**했다. 이유는 단순하다. **다른 방법이 튜닝 비용 대비 잘 안 이긴다.**

## 5. 실제 사례: 누가 왜 이걸 쓰는가

### Elastic — "우리는 20년 BM25 회사인데 왜 벡터를 붙였나"
Elastic은 검색 시장 지배자였지만, RAG 붐 이후 "벡터 DB로 갈아탄다"는 이탈이 시작됐다. 대응은 명확했다. **BM25 위에 HNSW를 얹고 RRF로 묶는다.** 8.9부터 native RRF를 제공. Elastic의 논리: "당신 회사 문서에는 이미 SKU, 제품코드, 에러코드, 사번이 잔뜩 있다. 벡터 단독으로는 이걸 못 찾는다. 우리는 처음부터 이걸 할 줄 안다."

### Vespa — Yahoo/Perplexity가 왜 이걸 고집하는가
Perplexity가 검색 백엔드로 Vespa를 쓴다. 이유는 **한 노드 안에서 sparse + dense + tensor 랭킹을 native로 동시에 계산**하기 때문. Pinecone + Elastic을 따로 굴리면 2-hop 네트워크가 생기고 P99가 튄다. Vespa는 하나의 인덱스에서 두 신호를 다 뽑는다.

### Weaviate — Hybrid를 "1 파라미터"로 팔다
Weaviate는 `hybrid(query, alpha=0.5)` 한 줄이면 끝난다. 내부적으로 BM25 + Vector를 돌리고 RRF/Relative Score Fusion 중 선택. 개발자 편의성으로 승부하는 전략.

### GitHub Code Search — 왜 순수 벡터로 안 갔는가
"함수 이름 검색"에서는 BM25가 압도적이다. `getUserById`를 벡터로 찾으면 `fetchUser`, `loadPerson` 같은 잡음이 상위에 온다. GitHub는 **심볼 매칭(exact) + 의미 검색(vector)을 병렬**로 돌리고 rerank한다. 코드 검색은 hybrid가 아니면 답이 없다.

### Notion AI / Linear — 자연어 위주 도메인
반대로 자연어 위주의 회의록/이슈 도메인에서는 벡터의 비중을 높인다(α↑). 하지만 여전히 BM25를 완전히 끄지 않는다. 사용자가 "PROJ-1234 관련 논의"라고 물었을 때 리터럴 매칭이 필요하기 때문.

## 6. Re-ranker: Hybrid의 "결승전 심판"

Hybrid에서 top-50을 뽑았다고 해도, LLM 컨텍스트에는 top-5만 들어간다. 이 최종 컷을 **Cross-Encoder Re-ranker**가 한다.

- 1차 검색(Retrieval): Bi-encoder(빠름, 부정확) — 벡터 + BM25로 top-50
- 2차 랭킹(Re-rank): Cross-encoder(느림, 정확) — 쿼리-문서 쌍을 하나의 모델로 계산해 top-5

Cohere Rerank, BGE-Reranker, Jina Reranker가 대표적. **비용은 top-50 문서에 대한 별도 모델 호출**이지만, RAG 정답률(faithfulness)에서 +10~20%p를 얻는 경우가 흔하다.

시니어 관점에서 이건 별도 아키텍처 결정이다. **Hybrid Search + Reranker는 다른 문제**다. Hybrid는 recall(놓치지 않기), Rerank는 precision(정확히 고르기).

## 7. 트레이드오프 표

| 축 | 순수 Vector | 순수 BM25 | Hybrid + RRF |
|---|---|---|---|
| 의미 이해 | 최상 | 없음 | 상 |
| 리터럴 매칭 (ID, 코드, 오타) | 약함 | 최상 | 상 |
| 인프라 복잡도 | 낮음 (1 인덱스) | 낮음 (1 인덱스) | 높음 (2 인덱스 + fusion) |
| 인덱스 크기 | 크다 (float32×d) | 작다 (역색인) | 둘 다 필요 |
| 쿼리 레이턴시 | 5~30ms | 1~10ms | 두 검색 병렬 후 fusion (~30~50ms) |
| 튜닝 파라미터 | 임베딩 모델 | tokenizer, k1, b | 위 전부 + fusion α or k |
| Cold-start(신규 문서) | 임베딩 지연 | 즉시 | 벡터 쪽만 지연 |
| 다국어 | 임베딩 모델에 종속 | tokenizer 필요 (한국어 특히) | 둘 다 필요 |

**숨은 함정 — 한국어 도메인**: BM25는 tokenizer에 성능이 좌우된다. 형태소 분석(nori, mecab)을 쓰지 않으면 "결제하다/결제한다/결제되었다"가 다 다른 토큰이 되어 리콜이 폭락한다. 반면 임베딩은 이걸 다 잡는다. **한국어에서 Hybrid의 α 최적값은 영어보다 벡터 쪽으로 치우친다.**

## 8. 언제 쓰고, 언제 쓰면 안 되는가

### 써야 하는 경우
- **도메인에 고유 식별자가 많다**: 에러코드, SKU, 사번, 티켓ID, 함수명, 버전 문자열
- **검색 실패 비용이 크다**: 법률/의료/금융 — 놓친 문서 하나가 오답을 만든다
- **다양한 쿼리 유형**: 사용자가 자연어와 리터럴을 섞어 던진다 ("ORA-01555 발생 시 undo 관리 전략")
- **RAG 프로덕션**: 데모를 넘어 실제 서비스면 사실상 필수

### 쓰지 말아야 하는 경우
- **문서가 순수 자연어이고 리터럴이 거의 없다**: 상담 로그, 회의록, 스토리 요약 → 벡터만으로 충분한 경우가 많다
- **레이턴시 P99가 30ms 미만이어야 한다**: 두 검색 병렬 + fusion + rerank는 이 예산에 안 맞는다
- **팀에 검색 엔지니어링 인력이 없다**: BM25 tokenizer, 임베딩 모델 선택, α/k 튜닝, rerank 모델 도입 — 무시 못 할 운영 비용. 이 경우 Weaviate/Vespa 같은 "hybrid를 API 한 줄로 파는" 매니지드를 쓰는 게 낫다
- **인덱스 갱신이 실시간이고, 벡터 임베딩 지연을 감당 못 한다**: BM25는 즉시 색인, 벡터는 임베딩 큐가 필요하다 — 뉴스 속보/실시간 알림 도메인에서는 이 지연이 UX를 깬다

## 9. 시니어 관점의 실전 체크리스트

1. **먼저 BM25만으로 baseline을 만들어라.** 이걸 안 하면 Hybrid의 개선을 측정할 수 없다.
2. **평가셋(Golden Set)이 없으면 시작하지 마라.** α나 fusion 방식을 무엇으로 정할 것인가? 감으로? — 답은 없다. 최소 100~200 쿼리 정답셋으로 nDCG/Recall@k를 재라.
3. **RRF부터 시작하라. 나중에 needs가 명확해지면 weighted로 넘어가라.** 반대 순서는 함정이다.
4. **Reranker 도입은 별도 실험으로 분리하라.** Hybrid과 Rerank를 동시에 켜서 결과가 좋아졌다면, 어느 쪽 공헌인지 모른다.
5. **로그를 남겨라**: 각 쿼리에 대해 vector top-K, bm25 top-K, fusion 후 순위, 최종 LLM 인용 문서를 다 남겨야 한다. 이게 없으면 [[llm-observability]] 단계에서 사후 분석이 불가능하다.

---

> 💡 **왜 중요한가**: 벡터 검색은 의미를 이해하지만 리터럴에 눈이 멀고, BM25는 리터럴에 강하지만 의미에 귀가 먹었다 — 프로덕션 RAG는 이 두 사각지대를 서로 메우는 Hybrid Search 없이 절대 완성되지 않는다.
