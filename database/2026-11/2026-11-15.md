### Database Tip 1: PostgreSQL `Autovacuum`의 `Dead Tuple` 임계치와 `Bloat` — "DELETE 안 했는데 테이블이 커지는" MVCC의 숨은 청구서

PostgreSQL의 UPDATE는 "기존 행을 수정"하는 게 아니라 **새 버전을 추가하고 기존 버전을 Dead Tuple로 마킹**하는 방식이다. Autovacuum이 이 Dead Tuple을 회수하지 않으면 테이블과 인덱스가 "실제 데이터보다 2~10배 부풀어 오르는" Bloat이 발생하며, `autovacuum_vacuum_scale_factor=0.2`(기본값)는 **1억 행 테이블에서 2천만 개의 Dead Tuple이 쌓일 때까지 청소를 미루는** 재앙이다. 대용량 테이블일수록 `scale_factor`를 0.01로 낮추고 `vacuum_cost_limit`을 올려 **더 자주, 더 공격적으로** 청소해야 한다.

```
UPDATE users SET name='B' WHERE id=1;

Before Autovacuum:
┌─────────────────────────────────────┐
│ id=1, name='A' (xmax=100) ← Dead    │  ← 공간 차지 중
│ id=1, name='B' (xmin=100) ← Live    │
└─────────────────────────────────────┘
         ↓ 100만 번 UPDATE 반복
┌─────────────────────────────────────┐
│ Dead × 999,999                      │  ← 테이블 Bloat
│ Live × 1                            │
└─────────────────────────────────────┘
                ↓
    테이블 크기: 1GB → 10GB
    Index Scan도 Dead Tuple 거쳐감 → 느려짐
```

**Trade-off**: 공격적 Autovacuum은 I/O 부담 증가, 보수적 설정은 Bloat 누적. OLTP 핫 테이블은 테이블별 `ALTER TABLE ... SET (autovacuum_vacuum_scale_factor = 0.01)`로 개별 튜닝.

> 💡 **왜 중요한가**: "DELETE도 안 했는데 왜 테이블이 커지지?"라는 질문의 99%는 Autovacuum 설정 실패다. Bloat은 느린 쿼리뿐 아니라 백업 시간, 디스크 비용, 복제 지연까지 선형적으로 악화시킨다.

### Database Tip 2: MySQL `Gap Lock`과 `Next-Key Lock` — REPEATABLE READ에서 "존재하지 않는 행"까지 잠가버리는 Phantom Read 방어 장치

InnoDB의 기본 격리 수준인 REPEATABLE READ는 **인덱스 레코드 사이의 "빈 공간(Gap)"까지 잠가서** 다른 트랜잭션의 INSERT를 차단한다. `SELECT * FROM users WHERE age BETWEEN 20 AND 30 FOR UPDATE`는 실제 행뿐만 아니라 **20~30 범위 전체의 Gap을 잠그므로**, 다른 세션에서 `INSERT age=25`를 시도하면 데드락 없이 조용히 블로킹된다. 심지어 **존재하지 않는 행을 WHERE로 조회해도 Gap Lock이 걸려서** 운영 중인 서비스에서 "뜬금없는 Lock wait timeout"을 만들어낸다.

```
Session A (REPEATABLE READ):
SELECT * FROM users WHERE id BETWEEN 10 AND 20 FOR UPDATE;

Index:  ... [5] [15] [25] ...
              ↑  ↑   ↑
              │  │   └─ Gap Lock: (15, 25)
              │  └───── Record Lock: 15
              └──────── Gap Lock: (5, 15)
                        = Next-Key Lock

Session B:
INSERT INTO users(id) VALUES(12);  ← 블로킹! (10~20 Gap 잠김)
INSERT INTO users(id) VALUES(8);   ← 블로킹! (5~15 Gap 잠김)
INSERT INTO users(id) VALUES(4);   ← OK (5 미만은 자유)
```

**해결책**: 
- Phantom Read가 필요 없으면 `READ COMMITTED`로 변경 (Gap Lock 비활성화, 단 바이너리 로그는 `ROW` 포맷 필수)
- 범위 UPDATE/DELETE 대신 **PK 단건 조회**로 쪼개기
- `innodb_locks_unsafe_for_binlog=1` (Deprecated, 하위 호환용)

> 💡 **왜 중요한가**: "왜 INSERT가 멈추지? 대상 행도 없는데?"라는 미스터리 데드락의 범인은 거의 Gap Lock이다. MySQL이 PostgreSQL과 결정적으로 다른 지점이며, 격리 수준 선택이 처리량을 10배 가르는 숨은 변수다.
