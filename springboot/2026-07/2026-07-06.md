### `@Async` 메서드를 같은 클래스 내부에서 호출하면 프록시를 거치지 않아 비동기로 동작하지 않는다

Spring AOP는 프록시 기반이라 `this.asyncMethod()` 같은 self-invocation은 프록시를 우회해 동기 실행된다. 해결하려면 별도 빈으로 분리하거나, `AopContext.currentProxy()`로 프록시를 명시적으로 획득하거나, `ApplicationContext`에서 자기 자신을 다시 주입받아 호출해야 한다.

```java
@Service
public class OrderService {
    @Async
    public void notify() { /* self-invocation 시 동기 실행됨 */ }

    public void process() {
        notify(); // ❌ 프록시 우회 → 동기
    }
}
```

> 💡 **왜 중요한가**: `@Async`, `@Transactional`, `@Cacheable` 등 프록시 기반 어노테이션이 "왜 안 먹지?" 상황의 8할은 self-invocation이다.

### `WebClient`의 `.block()`을 서블릿 스레드에서 남발하면 리액티브의 이점이 사라지고 오히려 스레드가 더 낭비된다

MVC 환경에서 `WebClient`를 쓸 때 결과를 기다리려고 `.block()`을 호출하면, 원래 이벤트 루프에서 처리될 IO가 서블릿 스레드를 붙잡아 두는 형태가 된다. 결과적으로 톰캣 스레드 + Reactor Netty 스레드를 이중으로 점유하게 되므로, 동기가 필요하면 차라리 `RestClient`(Spring 6.1+)를 쓰고, 진짜 논블로킹이 필요할 때만 `Mono/Flux`로 체이닝을 유지해야 한다.

```java
// ❌ 스레드 낭비 — 톰캣 스레드가 block 상태로 대기
String body = webClient.get().uri("/api").retrieve().bodyToMono(String.class).block();

// ✅ 동기 호출이면 RestClient가 정답
String body = restClient.get().uri("/api").retrieve().body(String.class);
```

> 💡 **왜 중요한가**: WebClient는 "빠른 HTTP 클라이언트"가 아니라 "논블로킹 파이프라인에서 쓰는 클라이언트"이며, 잘못 쓰면 RestTemplate보다도 리소스 효율이 나빠진다.
