### PostgreSQL `CLUSTER` + `pg_repack` — 물리적 행 순서를 인덱스에 맞춰 재정렬해 I/O 줄이기

시계열·범위 조회가 잦은 테이블에서 힙의 물리적 순서가 인덱스 순서와 어긋나면 같은 페이지를 여러 번 읽어야 해서 버퍼 히트율이 급락한다. `CLUSTER table USING idx`는 인덱스 순서대로 힙을 재작성해 연속된 범위 스캔이 인접 페이지에서 끝나도록 만들지만 ACCESS EXCLUSIVE 락이 걸리므로, 운영 환경에서는 온라인으로 동일 효과를 내는 `pg_repack` 확장을 쓰는 것이 정석이다.

```sql
-- 오프라인 (락 필요)
CLUSTER orders USING idx_orders_created_at;

-- 온라인 (pg_repack 확장, 무중단)
-- $ pg_repack -h localhost -d shop -t orders -o created_at
```

> 💡 **왜 중요한가**: 인덱스만 잘 만들어도 힙 페이지가 흩어져 있으면 실제 디스크 I/O는 몇 배로 늘어난다.

### MySQL `EXPLAIN ANALYZE`의 `actual time=` 읽는 법 — 예측이 아닌 실제 실행 시간으로 튜닝하기

기존 `EXPLAIN`은 옵티마이저의 추정치만 보여줘서 통계가 어긋난 쿼리에서는 오해를 부른다. MySQL 8.0+의 `EXPLAIN ANALYZE`는 실제로 쿼리를 실행하며 각 iterator마다 `actual time=시작..끝 rows=N loops=M` 형식으로 소요 시간을 출력하는데, `끝 * loops` 값이 상위로 갈수록 커지는 지점이 진짜 병목이다.

```sql
EXPLAIN ANALYZE
SELECT o.id, u.name
FROM orders o JOIN users u ON u.id = o.user_id
WHERE o.created_at >= '2026-04-01';
-- -> Nested loop inner join  (actual time=0.12..48.3 rows=1520 loops=1)
--     -> Index range scan on o  (actual time=0.05..2.1 rows=1520 loops=1)
--     -> Single-row index lookup on u  (actual time=0.02..0.03 rows=1 loops=1520)
```

> 💡 **왜 중요한가**: `rows` 추정치가 실제와 10배 이상 벌어져 있으면 통계 갱신(`ANALYZE TABLE`)이나 인덱스 재설계가 필요하다는 신호다.
