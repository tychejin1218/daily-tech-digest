### Database Tip 1: PostgreSQL `TOAST`(The Oversized-Attribute Storage Technique) — 8KB 페이지에 안 들어가는 거대 컬럼을 "조용히 쪼개서 숨겨두는" 투명 압축 창고

PostgreSQL의 한 페이지는 8KB로 고정되어 있는데, JSONB·TEXT·BYTEA 같은 거대 컬럼이 들어오면 TOAST가 자동으로 압축하거나 외부 테이블(`pg_toast_*`)로 떼어내 포인터만 본문에 남긴다. 문제는 `SELECT *`로 TOAST 컬럼을 끌어오는 순간 **디토스트(de-TOAST) 비용**이 눈덩이처럼 불어나고, 특히 `ORDER BY`·`DISTINCT`가 TOAST 컬럼을 건드리면 디스크 정렬로 떨어진다는 점이다. 그래서 거대 JSONB를 다룰 땐 필요한 키만 `->>'field'`로 뽑거나 `EXTERNAL` 저장 전략으로 압축을 꺼서 CPU를 아끼는 선택도 실무에서 자주 쓴다.

```
┌───────────── 메인 테이블 (8KB page) ─────────────┐
│ id │ name │ meta_ptr ──────┐                    │
└────────────────────────────┼────────────────────┘
                             ▼
                   ┌──── pg_toast_12345 ────┐
                   │ chunk_id │ seq │ data  │  ← 2KB씩 압축 분할
                   └────────────────────────┘
```

| 저장 전략     | 압축 | 외부 저장 | 언제 쓰나                    |
| ------------- | ---- | --------- | ---------------------------- |
| `PLAIN`       | ❌   | ❌        | 숫자/짧은 타입 (강제)        |
| `EXTENDED`    | ✅   | ✅        | **기본값** (TEXT/JSONB 등)   |
| `EXTERNAL`    | ❌   | ✅        | CPU는 아끼고 디스크는 쓰고   |
| `MAIN`        | ✅   | ❌        | 가능하면 본문에, 크면 외부로 |

> 💡 **왜 중요한가**: `SELECT *` 한 번이 왜 갑자기 100배 느려지는지 설명하지 못하면, 거대 JSONB를 쓰는 서비스는 CPU가 디토스트에 갈려 나가는 이유를 끝까지 못 찾는다.

### Database Tip 2: MySQL `innodb_flush_log_at_trx_commit`과 `sync_binlog` — 커밋 1건의 내구성을 "디스크 fsync 2번"으로 바꾸는 트랜잭션 성능의 숨은 다이얼

MySQL은 커밋할 때 **InnoDB redo log**(트랜잭션 복구용)와 **binlog**(복제·PITR용) 두 개를 디스크에 내려써야 "진짜 커밋"이 된다. `innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`이면 커밋마다 fsync가 2번 호출되는데, SSD도 이 조합에서는 초당 수천 커밋이 한계고 **그룹 커밋(binlog group commit)**이 없으면 TPS가 10배 떨어진다. 반대로 `=2`, `=0`으로 내리면 TPS는 폭발하지만 OS 크래시 시 **마지막 1초 트랜잭션이 통째로 증발**하거나, 더 치명적으로 **마스터와 슬레이브의 데이터가 어긋나는 상황**이 조용히 발생한다.

```
커밋 플로우 (Durable = 1,1)
┌─ App commit ─┐
│   BEGIN      │
│   INSERT     │     redo log buf ──► fsync #1 ──► ✅ InnoDB durable
│   COMMIT ────┼──►  binlog buf   ──► fsync #2 ──► ✅ Replica safe
└──────────────┘                                   ▲
                                                   └ 두 번 다 내려써야
                                                     "진짜 커밋"
```

| 조합      | 내구성                 | TPS 영향    | 리스크                          |
| --------- | ---------------------- | ----------- | ------------------------------- |
| `1` + `1` | **ACID 완전 준수**     | 느림 (기본) | 없음                            |
| `2` + `1` | OS 크래시 시 1초 유실  | 2~3배 ↑     | mysqld 크래시엔 안전            |
| `0` + `N` | 최대 1초치 트랜잭션 유실 | 5~10배 ↑  | mysqld 크래시에도 유실          |
| `1` + `0` | InnoDB는 OK, **binlog 유실** | 빠름  | **복제 깨짐, PITR 불가**        |

> 💡 **왜 중요한가**: "왜 벤치마크에선 5만 TPS인데 운영에선 5천 TPS냐"의 답은 거의 대부분 이 두 플래그이고, 함부로 내리면 장애 복구 시 데이터가 서로 다른 복제본을 보게 된다.
