### MySQL `Generated Column` + 인덱스 — 계산식에 인덱스를 걸어 함수 호출로 인한 풀스캔을 없애는 우아한 우회로

`WHERE YEAR(created_at) = 2026`이나 `WHERE JSON_EXTRACT(data, '$.status') = 'A'` 같은 함수 기반 조건은 컬럼 인덱스를 무력화한다. `Generated Column`은 이런 표현식을 "가상의 컬럼"으로 미리 정의하고, 그 위에 인덱스를 얹어 옵티마이저가 자동으로 인덱스 스캔을 선택하게 만드는 기법이다. `VIRTUAL`은 저장 없이 계산만, `STORED`는 물리적으로 저장하되 인덱스 유지 비용이 붙는다.

```sql
-- ❌ 함수 사용으로 인덱스 무력화, 풀스캔
SELECT * FROM orders WHERE YEAR(created_at) = 2026;

-- ✅ Generated Column + 인덱스로 인덱스 스캔
ALTER TABLE orders
  ADD COLUMN created_year INT AS (YEAR(created_at)) VIRTUAL,
  ADD INDEX idx_created_year (created_year);

SELECT * FROM orders WHERE created_year = 2026;  -- 인덱스 태움

-- JSON 필드도 마찬가지
ALTER TABLE events
  ADD COLUMN status VARCHAR(20) AS (JSON_UNQUOTE(JSON_EXTRACT(data, '$.status'))) VIRTUAL,
  ADD INDEX idx_status (status);
```

MySQL 8.0.13+는 심지어 `Functional Index`로 이 과정을 한 줄에 압축한다: `CREATE INDEX idx ON orders ((YEAR(created_at)));`. 내부적으로 숨겨진 Generated Column을 만들어주는 문법 설탕이다.

```
[함수 기반 WHERE의 진화]
  YEAR(created_at) = 2026
    ↓ 옛날: 풀스캔 (인덱스 무력)
    ↓ 8.0.13+: 함수 인덱스 = 숨은 Generated Column + 인덱스
    ↓ 옵티마이저: created_year = 2026 으로 자동 재작성 → 인덱스 스캔
```

트레이드오프는 명확하다. `VIRTUAL`은 저장 공간을 안 쓰지만 조회 시마다 계산하고, `STORED`는 쓰기 시 계산해서 저장하니 UPDATE 비용이 커진다. 인덱스를 걸려면 어차피 값이 어딘가 저장되어야 하니 인덱스 컬럼은 사실상 STORED와 유사하게 동작한다. **핵심은 "쿼리를 못 바꾸는 상황(레거시, ORM 자동 생성 쿼리)에서 옵티마이저에게 새 인덱스 선택지를 만들어주는 무기"라는 점.**

> 💡 **왜 중요한가**: 이미 굳어진 쿼리 패턴을 건드리지 않고, 스키마 쪽에서 인덱스 후보를 하나 더 만들어 옵티마이저를 유도하는 "무침습 최적화"의 대표 기법이다.

### PostgreSQL `BRIN Index` — B-Tree의 1/1000 크기로 억 단위 시계열을 스캔하는 "블록 범위" 인덱스

`BRIN(Block Range Index)`은 데이터가 물리적으로 정렬되어 있을 때, 블록 단위로 "이 블록의 min/max 값"만 저장하는 초경량 인덱스다. B-Tree가 모든 행을 인덱싱하는 반면 BRIN은 예를 들어 128블록마다 요약 하나만 남긴다. 10억 행 로그 테이블에서 B-Tree가 20GB일 때 BRIN은 20MB 수준이다.

```sql
-- 시계열 로그 테이블 (created_at 순으로 INSERT되어 물리적으로 정렬)
CREATE TABLE access_logs (
    id BIGSERIAL,
    created_at TIMESTAMPTZ,
    user_id INT,
    payload JSONB
);

-- B-Tree: 20GB (10억 행 기준)
CREATE INDEX idx_btree_created ON access_logs (created_at);

-- BRIN: 20MB (1000배 작음)
CREATE INDEX idx_brin_created ON access_logs USING BRIN (created_at)
  WITH (pages_per_range = 128);

-- 범위 조회 시 BRIN이 "이 블록 범위는 스킵"을 빠르게 판단
SELECT * FROM access_logs
 WHERE created_at BETWEEN '2026-09-01' AND '2026-09-07';
```

전제 조건은 딱 하나: **컬럼 값이 물리적 저장 순서와 상관관계가 높아야 한다.** 로그처럼 시간순 append-only 테이블이나, 순차적으로 커지는 ID 컬럼이 완벽한 후보다. UPDATE가 잦아 물리적 순서가 흐트러진 테이블에선 min/max 범위가 넓어져 사실상 풀스캔이 된다(`pg_stats`의 `correlation` 값을 먼저 확인하자, 1.0에 가까울수록 좋음).

```
[B-Tree vs BRIN 개념도]
B-Tree (모든 행 인덱싱):
  [행1→위치] [행2→위치] [행3→위치] ... [행10억→위치]  ← 20GB

BRIN (블록 범위 요약):
  블록 0~127:   min=2026-01-01, max=2026-01-05
  블록 128~255: min=2026-01-05, max=2026-01-10
  블록 256~383: min=2026-01-10, max=2026-01-15
  ...                                                    ← 20MB
  
  쿼리: created_at = '2026-01-08'
    → 블록 128~255만 실제 스캔, 나머지 전부 스킵
```

핵심 트레이드오프: 조회 성능은 B-Tree보다 살짝 느리지만(블록 범위 안에서는 순차 스캔), 인덱스 크기와 유지비용이 극단적으로 작다. 캐시 히트율도 훨씬 좋아진다(인덱스 자체가 메모리에 통째로 들어감). **"조회 latency 몇 ms를 포기하고 인덱스 크기와 INSERT 성능을 극한으로 얻는" 시계열/로그 테이블의 전용 무기다.**

> 💡 **왜 중요한가**: 로그·이벤트·시계열처럼 append-only이고 시간순으로 쌓이는 대용량 테이블에서는 B-Tree가 오히려 낭비다. BRIN은 "물리적 정렬"이라는 데이터 특성을 인덱스 설계에 그대로 반영한 드문 사례.
