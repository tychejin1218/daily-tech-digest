### MySQL `ANALYZE TABLE`의 히스토그램 통계 — 카디널리티가 왜곡된 컬럼의 실행 계획 바로잡기

MySQL 8.0부터는 `ANALYZE TABLE ... UPDATE HISTOGRAM ON column`으로 특정 컬럼의 값 분포를 히스토그램으로 저장할 수 있다. 인덱스가 없는 컬럼이나 데이터 편향(skew)이 심한 컬럼에서 옵티마이저가 "모든 값이 균등 분포한다"고 오판하는 문제를 정면으로 해결한다. 예를 들어 `status` 컬럼의 값이 `ACTIVE` 99%, `DELETED` 1%처럼 극단적으로 치우친 경우, 히스토그램 없이는 옵티마이저가 `WHERE status='DELETED'` 쿼리에도 풀 스캔을 선택하기 쉽다.

```sql
-- 20개 버킷으로 히스토그램 생성 (기본 100, 최대 1024)
ANALYZE TABLE orders UPDATE HISTOGRAM ON status, region WITH 20 BUCKETS;

-- 확인
SELECT histogram FROM information_schema.column_statistics
 WHERE table_name = 'orders' AND column_name = 'status';

-- 제거
ANALYZE TABLE orders DROP HISTOGRAM ON status;
```

핵심은 **인덱스를 만들지 않고도 옵티마이저에 분포 정보를 주입**한다는 점이다. 인덱스는 유지 비용(INSERT/UPDATE 오버헤드, 스토리지)이 있지만, 히스토그램은 정적 통계라 쓰기 비용이 없다. 다만 자동 갱신이 안 되므로 데이터 분포가 바뀌면 재실행해야 한다.

> 💡 **왜 중요한가**: 인덱스를 추가할 수 없는 저카디널리티 컬럼(성별, 상태값, 등급)에서 옵티마이저가 잘못된 조인 순서를 고를 때, 히스토그램 하나로 실행 계획 자체가 뒤집힌다.

### PostgreSQL `Partial Index` — 전체 행의 1%만 인덱싱해 크기·쓰기 비용을 극단적으로 줄이기

`CREATE INDEX ... WHERE 조건`으로 특정 조건을 만족하는 행만 인덱스에 포함시킬 수 있다. 이커머스의 "미결제 주문", SaaS의 "삭제되지 않은 유저", 큐 테이블의 "처리 대기 작업"처럼 **전체의 극소수만 자주 조회되는 패턴**에 이상적이다. 인덱스 크기가 1/100로 줄어들면 캐시 히트율이 올라가고, `INSERT`/`UPDATE` 시 인덱스 갱신 비용도 조건에 해당하지 않는 행에 대해서는 발생하지 않는다.

```sql
-- 미처리 주문만 인덱싱 (전체 1억 건 중 5만 건)
CREATE INDEX idx_orders_pending
    ON orders (created_at)
 WHERE status = 'PENDING';

-- 이 쿼리는 partial index를 자동으로 사용
SELECT * FROM orders
 WHERE status = 'PENDING' AND created_at > now() - interval '1 hour';

-- soft delete 패턴에도 유용
CREATE UNIQUE INDEX idx_users_email_active
    ON users (email)
 WHERE deleted_at IS NULL;  -- 삭제된 이메일은 재사용 허용
```

주의점은 **쿼리의 `WHERE` 조건이 인덱스의 `WHERE` 조건을 논리적으로 포함해야** 옵티마이저가 이 인덱스를 쓴다는 것. `status = 'PENDING'`을 생략하면 partial index가 무시된다. 두 번째 예시처럼 `UNIQUE` 제약과 결합하면 "활성 유저 중 이메일 유일" 같은 조건부 유니크 제약을 우아하게 표현할 수 있다.

> 💡 **왜 중요한가**: 인덱스는 크기가 곧 성능이다 — 자주 쿼리되는 1%만 담은 인덱스는 전체 인덱스보다 100배 빠르게 캐시에 올라가고, 쓰기 오버헤드도 그만큼 사라진다.
