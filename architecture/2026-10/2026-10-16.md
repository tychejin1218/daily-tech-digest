### ReAct 패턴 — "CoT로 생각 잘 시키면 되지"라는 순진함, 그리고 LLM이 외부 조회 Tool을 호출한 뒤 반환값을 못 믿고 같은 Tool을 7번 재호출하다 Rate Limit에 걸려 CS 챗봇이 "조회 중입니다"만 2분간 띄우고 세션 타임아웃된 월요일 새벽

ReAct(Reasoning + Acting)는 Yao et al.이 2022년 ICLR에서 발표한 Agent 설계 패턴이다. 한 문장으로 요약하면:

> **LLM이 매 step마다 `Thought(생각) → Action(도구 호출) → Observation(결과)` 를 반복하며, 다음 step을 모델 스스로 결정한다.**

이전 Lv4·Lv5에서 Multi-Agent Orchestration, Tool Routing, Semantic Cache를 다뤘다. 그런데 그 위에 올라서는 "Agent가 한 턴 안에서 어떻게 생각하고 행동할 것인가"는 Supervisor-Worker 토폴로지와는 다른 층위의 문제다. Multi-Agent가 "역할을 어떻게 쪼갤 것인가"라면, ReAct는 "한 Agent 안에서 CoT에 손발을 어떻게 달아줄 것인가"다.

---

#### 1. 왜 CoT만으론 안 되는가

CoT(Chain-of-Thought)는 "머릿속 추론"만 한다. 모델 안에 든 지식과 사용자가 넣어준 context만으로 결론을 내린다. 다음 질문에서 CoT는 반드시 실패한다:

- "지금 ORD-20261016-7812 주문 환불 가능해?" → 모델은 **2026-10-16의 주문 상태**를 알지 못한다
- "서울 강남구 오늘 미세먼지 수치는?" → 모델은 **실시간 데이터**를 알지 못한다
- "47 * 1823.5 / 0.0713 는?" → 모델은 **긴 수식 계산**에 체계적으로 틀린다

CoT는 **폐쇄형 추론**, ReAct는 **개방형 추론**이다. CoT가 "혼자 수능 문제 푸는 학생"이라면, ReAct는 "책상 위에 계산기·DB 터미널·구글이 열려 있는 상태의 상담원"이다.

```
┌─────────────────────────────────────────────────┐
│  CoT:                                            │
│     User → [LLM: 생각 → 생각 → 답]                │
│     (외부 세계와 단절)                            │
├─────────────────────────────────────────────────┤
│  ReAct:                                          │
│     User → [LLM: 생각] → Tool → Obs              │
│            → [LLM: 생각] → Tool → Obs            │
│            → [LLM: 답]                            │
│     (매 step마다 외부에 손이 닿음)                │
└─────────────────────────────────────────────────┘
```

---

#### 2. ReAct 루프 — 실제 흐름

```
User: "주문 ORD-20261016-7812 환불 가능해?"
                   │
                   ▼
 ┌──────────────────────────────────────┐
 │ Step 1 Thought                        │
 │ "환불 가부는 주문일자·결제수단에 달림. │
 │  먼저 주문 조회부터."                  │
 └──────────────┬───────────────────────┘
                ▼
 ┌──────────────────────────────────────┐
 │ Step 1 Action                         │
 │ get_order(order_id="ORD-...-7812")    │
 └──────────────┬───────────────────────┘
                ▼
 ┌──────────────────────────────────────┐
 │ Step 1 Observation                    │
 │ {order_date:"2026-10-10",             │
 │  payment:"card", amount:59000,        │
 │  status:"delivered"}                  │
 └──────────────┬───────────────────────┘
                ▼
 ┌──────────────────────────────────────┐
 │ Step 2 Thought                        │
 │ "6일 전 배송 완료. 정책 확인 필요."     │
 └──────────────┬───────────────────────┘
                ▼
 ┌──────────────────────────────────────┐
 │ Step 2 Action                         │
 │ get_refund_policy(category="general") │
 └──────────────┬───────────────────────┘
                ▼
 ┌──────────────────────────────────────┐
 │ Step 2 Observation                    │
 │ "배송완료 후 7일 이내 환불 가능,       │
 │  카드결제는 승인취소 3~5영업일"         │
 └──────────────┬───────────────────────┘
                ▼
 ┌──────────────────────────────────────┐
 │ Final Answer                          │
 │ "환불 가능합니다. 카드 승인취소로       │
 │  3~5영업일 내 처리됩니다."              │
 └──────────────────────────────────────┘
```

핵심은 **Step 2의 Thought가 Step 1의 Observation을 보고 결정된다**는 점이다. 다음 Action이 미리 정해져 있지 않다. 이것이 ReAct를 **Dynamic**하게 만들고, 동시에 **제어 불능 리스크**를 만든다.

---

#### 3. ReAct vs Plan-and-Execute vs CoT

Agent 설계에서 자주 비교되는 세 가지 패턴을 정리하면:

| 축 | CoT | ReAct | Plan-and-Execute |
|---|---|---|---|
| 외부 Tool 호출 | ❌ | ✅ 매 step | ✅ 사전 계획된 step |
| 의사결정 시점 | 1회 (답 생성) | N회 (매 step) | 2단계 (Plan 1회 + Execute N회) |
| Latency | 가장 빠름 | step 수에 비례 | Plan 1회 + 병렬 가능 |
| Token 비용 | 저 | 고 (매 step에 전체 history) | 중 (Plan은 1회) |
| 중간 실패 복구 | — | 다음 Thought로 재시도 | Replan 필요 |
| 적합 과제 | 수학·논리·분류 | 탐색적·대화형 | 다단계 작업·보고서 생성 |
| 디버깅 난이도 | 낮음 | 중간 (Trace가 선형) | 높음 (Plan 자체 디버깅) |
| 폭주 가능성 | 없음 | **매우 높음** (무한 루프) | 낮음 (step 수 사전 고정) |

ReAct의 치명적 약점은 **"다음 step을 LLM이 매번 결정한다"**는 바로 그 점이다. Plan-and-Execute(BabyAGI, LangChain Plan-and-Execute Agent 등)가 등장한 이유가 여기 있다. "계획은 미리 세우고, 실행만 반복"하면 폭주를 막기 쉽다.

#### 4. 실전 사례

**사례 1: Anthropic Tool Use (2024~) — ReAct의 상용화**
Claude의 Tool Use API는 사실상 "구조화된 ReAct"다. `tool_use` block이 Action, `tool_result` block이 Observation, 그 다음 턴의 reasoning이 Thought다. 다만 ReAct 논문의 자유형식 텍스트 파싱(`Action: get_order[...]`)을 JSON schema 강제로 바꾼 것이 핵심 개량이다. 자유형식 파싱이 20~30% 깨지던 걸 schema validation으로 거의 0에 가깝게 떨어뜨렸다.

**사례 2: Perplexity (2023~2024) — ReAct를 Latency로 밀어낸 케이스**
Perplexity는 초기에 ReAct 스타일을 썼다가, 사용자 질의 응답에 평균 4~6초가 걸리는 문제로 "**Search → Rerank → Answer**"의 고정 3-step 파이프라인으로 전환했다. ReAct의 유연성보다 **p95 latency 2초**가 제품으로 더 중요했기 때문이다. 교훈: **ReAct는 "어떤 경로로 가야 할지 모를 때"의 패턴이지, 경로가 정해진 workflow엔 과잉이다.**

**사례 3: 국내 L 커머스 (2025) — Observation 불신 루프 사고**
CS 챗봇을 ReAct로 올렸는데, "주문 조회 Tool이 가끔 캐시 미스로 `{}`를 리턴"하는 상황이 생겼다. LLM은 Observation을 보고 "응답이 비어있다, 다시 조회해야겠다"는 Thought를 반복했고, **같은 `get_order`를 6초 안에 14번 호출**해 사내 Order Service의 Rate Limiter(10req/sec per client)에 걸렸다. CS 챗봇은 "조회 중입니다"만 띄우다 WebSocket 세션 타임아웃. 포스트모템 결론: **"Agent에게 재시도 판단을 맡기지 말고, Tool wrapper에서 결정적으로(deterministic) 재시도·실패를 반환하라."** 이후 모든 Tool에 "같은 argument로 90초 안에 2회 이상 호출 시 cache된 결과 또는 명시적 error 반환" 규칙을 넣었다.

**사례 4: AutoGPT / BabyAGI (2023) — ReAct의 끝판왕이 왜 망했나**
AutoGPT는 "ReAct를 끝까지 가져가 보자"의 극단이었다. 결과는 유명한 **무한 루프**다. "다음 할 일을 뭘로 할까"를 LLM이 매번 결정하다 보니, "할 일 목록 재정비"를 할 일 목록에 추가하고, 그걸 다시 재정비하는 루프에 빠졌다. 교훈: **ReAct는 반드시 (1) Max step limit, (2) 중복 Action detection, (3) 외부 budget(토큰·시간·돈) 상한과 함께 써야 한다.** 이 셋 중 하나라도 빠지면 사고 난다.

**사례 5: Cursor / Claude Code (2024~2026) — ReAct를 "일부 영역에서만" 쓰는 설계**
IDE Agent들은 코드 탐색 단계(`Grep`, `Read`, `Glob`)에선 ReAct를 쓰지만, 코드 수정 단계(`Edit`, `Write`)에선 **사용자 확인**을 끼워 ReAct 루프를 끊는다. "모델이 다음 step을 결정"하는 자유도를 전부 모델에게 주지 않고, **blast radius가 큰 Action 앞에는 사람 또는 결정적 로직을 삽입**하는 하이브리드다. 이 설계가 "AI Agent가 알아서 다 한다"는 수사와 실제 production 안정성 사이의 간극을 메우는 현재의 best practice다.

#### 5. 함정과 안티패턴

**함정 1. Observation을 못 믿는 루프**
사례 3의 L 커머스. LLM은 "결과가 이상한데?" 싶으면 같은 Tool을 재호출한다. **Tool 응답은 LLM에게 "결정적"으로 보이도록 설계**해야 한다. 빈 응답, null, 애매한 에러는 Thought를 혼란시킨다.

**함정 2. Thought가 Token을 삼킨다**
매 step의 prompt에 과거 Thought/Action/Observation 전체 history가 들어간다. 10 step만 돌아도 20K token을 쉽게 넘긴다. 특히 Observation에 큰 JSON이 들어오면 폭발한다. 해법: **Observation summarization** (큰 응답을 LLM이 요약해 history에 넣기) 또는 **selective history** (지난 N step만 유지).

**함정 3. Tool 설계가 너무 가늘다**
`get_user`, `get_order`, `get_payment`, `get_shipping`을 다 쪼개 두면 ReAct가 한 질문에 4~5 step을 돈다. **"CS 상담에 자주 쓰이는 조합"을 **composite Tool**로 묶는 것**이 token과 latency 둘 다 아낀다. 예: `get_order_context(order_id)` 하나가 user+order+payment+shipping을 다 반환.

**함정 4. Max step 없이 production에 올린다**
AutoGPT의 반복. `max_iterations=10` 같은 하드 리밋은 선택이 아니라 필수다. 리밋 초과 시 "지금까지의 Thought를 종합한 best-effort 답변"을 돌려주는 fallback도 함께.

**함정 5. ReAct를 모든 질문에 쓴다**
"환불 정책 알려주세요" 같은 **RAG 1회로 끝날 질문**에 ReAct를 돌리는 건 낭비다. 의도 분류 단계(`should_use_agent`) 하나 두고, 단순 질의는 RAG로, 복합 질의만 ReAct로 라우팅한다. Perplexity 교훈과 같은 맥락.

---

#### 6. ✅ 언제 쓰는가 / ❌ 언제 안 쓰는가

**✅ 반드시 ReAct로 가야 하는 경우**
- 질의마다 **다른 조합의 Tool**이 필요하다 ("어제 결제된 주문 중 환불 가능한 것들"에는 get_orders → filter → get_refund_policy 조합이 필요하고, 다음 질의는 또 다를 수 있다)
- 중간 결과에 따라 **다음 action이 달라진다** (주문 상태가 "배송중"이면 배송 조회, "결제실패"면 결제 로그 조회)
- 탐색형 과제 (코드 디버깅, 데이터 분석)

**❌ 쓰면 안 되는 경우**
- 응답 **p95 latency < 2초**가 SLA인 서비스 (ReAct는 step당 LLM 호출 1회가 더해진다)
- 처리 경로가 **사전에 정해진** workflow (주문 생성 flow 같은 결정적 비즈니스 로직)
- **외부 비용·blast radius**가 큰 Action이 포함된 상황에 사람 확인 지점을 못 만들 때 (대량 메일 발송, DB write, 결제)

**⚠️ 신중해야 하는 경우**
- 하루 **100만 호출 이상**의 챗봇: Thought token이 비용의 60~70%를 차지한다. 반드시 "ReAct로 가야 하는 질의 비율"을 측정하고, 나머지는 RAG-only로 돌려야 수지가 맞는다
- Tool이 **외부 벤더 API**인 경우: Rate limit과 과금을 모델 결정에 맡기지 말고 Tool wrapper에서 통제

---

> 💡 **왜 중요한가**: ReAct는 "LLM에게 손발을 달아주는" 가장 보편적 패턴이지만, 그 손발을 어디까지 자유롭게 둘지가 Agent 제품의 안정성·비용·latency를 결정한다 — 이 결정이 바로 백엔드 엔지니어의 몫이다.
