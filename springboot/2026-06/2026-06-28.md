### `@ConfigurationProperties` 클래스에 `record`를 쓰면 `@ConstructorBinding` 없이도 불변 프로퍼티 바인딩이 된다

Spring Boot 3부터는 `@ConfigurationProperties`가 붙은 클래스가 단일 생성자를 가지면 자동으로 생성자 바인딩을 사용한다. `record`는 정의 자체가 단일 생성자이므로 `@ConstructorBinding` 어노테이션 없이 그대로 불변 설정 객체로 쓸 수 있고, setter도 필요 없다.

```java
@ConfigurationProperties(prefix = "app.mail")
public record MailProperties(
    String host,
    int port,
    Duration connectTimeout,
    List<String> allowedDomains
) {}
```

`@EnableConfigurationProperties(MailProperties.class)` 또는 `@ConfigurationPropertiesScan`으로 등록만 하면 된다. 필드 하나라도 누락되면 `null`/기본값이 아니라 애플리케이션 기동이 실패하도록 검증도 자연스럽게 강제된다.

> 💡 **왜 중요한가**: 설정 객체를 불변으로 만들면 런타임에 누가 바꿀 여지가 사라져, 프로퍼티가 조용히 뒤바뀌는 버그를 원천 차단한다.

### `SecurityFilterChain` Bean 방식이 `WebSecurityConfigurerAdapter`를 대체한 후 필터 순서는 `@Order`로 제어한다

Spring Security 5.7+ / Spring Boot 3에서는 `WebSecurityConfigurerAdapter`가 제거되고 `SecurityFilterChain`을 `@Bean`으로 여러 개 등록하는 방식이 표준이다. 여러 체인이 있을 때 `securityMatcher`로 URL 범위를 나누고, 어느 체인이 먼저 매칭되는지가 중요한데 이건 `@Order`로 명시적으로 제어해야 한다.

```java
@Bean
@Order(1)
SecurityFilterChain apiChain(HttpSecurity http) throws Exception {
    return http
        .securityMatcher("/api/**")
        .authorizeHttpRequests(a -> a.anyRequest().hasRole("API"))
        .csrf(csrf -> csrf.disable())
        .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
        .build();
}

@Bean
@Order(2)
SecurityFilterChain webChain(HttpSecurity http) throws Exception {
    return http
        .authorizeHttpRequests(a -> a.anyRequest().authenticated())
        .formLogin(Customizer.withDefaults())
        .build();
}
```

`@Order`를 안 붙이면 Spring이 임의 순서로 매칭해 `/api/**` 요청이 웹 체인에 잡혀 CSRF 실패나 리다이렉트가 발생할 수 있다.

> 💡 **왜 중요한가**: 다중 `SecurityFilterChain`은 순서가 곧 정책이며, 순서를 놓치면 STATELESS API가 CSRF 토큰을 요구받거나 로그인 페이지로 리다이렉트되는 사고가 난다.
