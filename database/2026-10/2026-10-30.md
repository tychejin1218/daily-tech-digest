### Database Tip 1: MySQL `Doublewrite Buffer` — "같은 페이지를 두 번 쓰는 낭비"가 사실은 `torn page`로부터 InnoDB를 지키는 유일한 보험

InnoDB는 16KB 페이지를 데이터 파일에 쓰기 **전에** 먼저 공유 테이블스페이스의 doublewrite buffer(연속된 128페이지=2MB 블록)에 통째로 복사한 뒤 fsync하고, 그 다음에서야 실제 `.ibd` 파일에 쓴다. OS/디스크의 쓰기 단위(보통 4KB)와 InnoDB 페이지 크기(16KB)가 어긋나 쓰기 도중 crash가 나면 "절반만 기록된 페이지(torn page)"가 생기는데, redo log는 **변경 분량(diff)만** 들고 있어서 깨진 페이지 자체를 복구할 수 없다. doublewrite buffer가 그 "원본 사본"을 보관하고 있어서, 복구 시 깨진 페이지를 사본으로 덮어쓴 뒤 redo log를 재적용한다.

```
Buffer Pool (dirty page)
      │
      │ 16KB page
      ▼
┌─────────────────────┐   fsync    ┌─────────────────────┐
│ Doublewrite Buffer  │ ─────────▶ │  Data File (.ibd)   │
│ (연속 2MB 블록, 순차)│            │  (랜덤 위치, 16KB)   │
└─────────────────────┘            └─────────────────────┘
      ▲                                     ▲
      └── crash 발생 시 "원본 페이지" 보존 ──┘ ← redo log가 못 고치는 영역
```

실제 사례: AWS Aurora는 스토리지 레이어가 4KB 원자적 쓰기를 보장하므로 `innodb_doublewrite=0`으로 꺼둔다. 반면 로컬 SSD/EBS 환경에서 "성능 올리겠다"고 이걸 끄면 전원 장애 한 번에 테이블이 복구 불능이 된다. 쓰기 I/O가 2배가 되지만 doublewrite 영역은 **연속된 순차 쓰기**라 실제 오버헤드는 5~10% 수준이고, MySQL 8.0.20부터는 `innodb_doublewrite_dir`로 doublewrite 파일을 별도 디스크(NVMe)에 분리해 그마저도 줄일 수 있다.

> 💡 **왜 중요한가**: redo log는 "변경 로그"일 뿐 "깨진 페이지 자체"는 복구하지 못한다 — torn page를 막는 건 doublewrite buffer가 유일하다.

### Database Tip 2: JPA `OSIV`(Open Session In View) — Spring Boot가 기본으로 켜둔 "View에서도 Lazy Loading 되는 편리함"이 커넥션 풀을 질식시키는 함정

OSIV는 영속성 컨텍스트(Hibernate Session)와 DB 커넥션을 Controller 진입 전부터 **HTTP 응답 렌더링이 끝날 때까지** 유지하는 Spring의 기본 전략이다(`spring.jpa.open-in-view=true`). 덕분에 Controller/View에서 `user.getOrders()` 같은 Lazy Loading이 `LazyInitializationException` 없이 동작하지만, 그 대가로 **뷰 렌더링·외부 API 호출·네트워크 지연까지 커넥션을 쥔 채** 기다리게 된다. "트랜잭션은 끝났는데 커넥션은 아직 안 돌려줬다"는 조용한 누수가 바로 이것.

```
요청 유입
  │
  ▼
[OpenEntityManagerInViewFilter] ◀── 여기서 Session 열고 Connection 획득
  │
  ├─▶ Controller
  │     │
  │     ├─▶ Service (@Transactional 시작 ─── 끝)   ← 트랜잭션은 여기서 종료
  │     │
  │     ├─▶ 외부 결제 API 호출 (2초)                 ← 그런데 Connection은 여전히 점유 중
  │     │
  │     └─▶ View Rendering (50ms)
  │
  ▼
[Filter 종료] ◀── 여기서야 Session 닫힘 + Connection 반납
```

실제 사례: 트래픽 급증 시 "DB는 멀쩡한데 애플리케이션에서 `HikariPool-1 - Connection is not available, request timed out after 30000ms`" 에러가 터지는 전형적 원인. 커넥션 풀 50개짜리 서버에서 외부 결제 API 호출이 2초만 걸려도 초당 25건 이상 들어오면 즉시 고갈된다. 해결은 `spring.jpa.open-in-view=false`로 끈 뒤, Service 레이어에서 `JOIN FETCH`/`@EntityGraph`/DTO Projection으로 **필요한 연관관계를 트랜잭션 안에서 미리 로드**하는 것 — 이게 사실 올바른 레이어 분리다.

> 💡 **왜 중요한가**: 커넥션 풀을 아무리 늘려도, OSIV가 켜져 있으면 "DB 작업 종료 후의 네트워크 I/O 시간"만큼 풀이 점유되어 TPS가 커넥션 수가 아니라 **뷰 렌더링 시간**에 묶인다.
