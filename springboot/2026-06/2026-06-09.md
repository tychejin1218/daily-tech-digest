### `ProblemDetail`로 RFC 7807 표준 에러 응답 만들기 (Spring 6+)

`@RestControllerAdvice`에서 직접 만든 커스텀 에러 DTO 대신 `ProblemDetail.forStatusAndDetail(...)`을 반환하면 `application/problem+json` 미디어 타입과 `type/title/status/detail/instance` 필드를 갖춘 표준 응답이 자동 생성된다. `setProperty()`로 `errorCode`, `traceId` 같은 도메인 필드를 확장할 수 있고, `ResponseEntityExceptionHandler`를 상속하면 `MethodArgumentNotValidException`까지 일관된 포맷으로 묶을 수 있다.

```java
@ExceptionHandler(OrderNotFoundException.class)
ProblemDetail handle(OrderNotFoundException e) {
    ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
    pd.setType(URI.create("https://api.example.com/errors/order-not-found"));
    pd.setProperty("errorCode", "ORDER_404");
    return pd;
}
```

> 💡 **왜 중요한가**: 프로젝트마다 제각각이던 에러 응답 스키마를 업계 표준(RFC 7807)으로 통일해 클라이언트·OpenAPI 문서·관측 도구 간 호환성을 확보할 수 있다.

### `spring.threads.virtual.enabled=true`로 가상 스레드(Virtual Threads) 활성화 (Spring Boot 3.2+, Java 21)

이 한 줄 프로퍼티를 켜면 Tomcat 요청 처리, `@Async`, `TaskExecutor`, `@Scheduled` 등이 플랫폼 스레드 풀 대신 JVM 가상 스레드로 동작한다. 블로킹 I/O가 많은 전통적인 MVC 서비스에서 스레드 풀 고갈 없이 동시성을 대폭 끌어올릴 수 있어, WebFlux로 전환하지 않고도 높은 처리량을 얻는 가장 저렴한 길이다.

```yaml
spring:
  threads:
    virtual:
      enabled: true
```

> 💡 **왜 중요한가**: 기존 명령형(MVC) 코드를 한 줄도 바꾸지 않고 "스레드당 1요청" 모델의 동시성 한계를 사실상 제거할 수 있다. 단, `synchronized` 블록과 ThreadLocal 캐싱은 핀닝(pinning)을 유발하므로 `ReentrantLock`으로 점진 교체를 검토해야 한다.
