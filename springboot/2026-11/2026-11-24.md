### 1. Spring Boot의 `@Valid`는 **중첩된 객체를 자동으로 검증해주지 않는다** — 중첩 필드에 `@Valid`를 또 붙여줘야 한다

`@RequestBody @Valid UserDto` 처럼 최상위에만 `@Valid`를 붙이면, DTO 내부에 품은 `AddressDto` 같은 중첩 객체의 `@NotBlank`, `@Size` 같은 제약은 **깡그리 무시된다**. "분명히 주소도 Not Blank인데 왜 빈 문자열이 통과하지?"의 범인이 이것. 중첩 필드에 `@Valid`를 함께 붙여야 재귀적으로 Bean Validation이 돌아간다.

```java
public class UserDto {
    @NotBlank String name;

    @Valid                  // ← 이거 없으면 AddressDto 내부 검증은 전부 스킵됨
    @NotNull
    AddressDto address;
}
```

컬렉션도 똑같다. `List<@Valid ItemDto>` 또는 `@Valid List<ItemDto>` 로 선언하지 않으면 원소 하나하나는 검증 대상에서 빠진다.

> 💡 **왜 중요한가**: 검증이 "되고 있는 것처럼 보이는데" 실제로는 반쪽만 돌고 있는 상태는, 테스트 커버리지로도 잘 안 잡히고 운영에서 더티 데이터로 터진다.

### 2. Spring Boot의 `HandlerInterceptor`는 **`@RestControllerAdvice`보다 먼저 실행되지만, 컨트롤러에서 터진 예외는 `afterCompletion`에서만 볼 수 있다**

인터셉터의 생명주기는 `preHandle` → 컨트롤러 → `postHandle` → `afterCompletion` 순이다. 그런데 컨트롤러에서 예외가 터지면 **`postHandle`은 건너뛰고 `afterCompletion`으로 바로 점프한다**. 즉, "응답 로깅"을 `postHandle`에 넣어두면, 예외 케이스에서는 로그가 한 줄도 남지 않는다.

```java
@Override
public void postHandle(..., ModelAndView mv) {
    // 컨트롤러에서 예외 터지면 여기 안 들어옴
    log.info("response ok");
}

@Override
public void afterCompletion(..., Exception ex) {
    // 예외 발생 시에도 호출됨. ex 파라미터로 원인 확인 가능
    if (ex != null) log.error("handler failed", ex);
}
```

더 미묘한 건, `@RestControllerAdvice`가 예외를 **잡아서 정상 응답으로 변환한 경우** `afterCompletion`의 `ex` 파라미터는 `null`로 들어온다 — 이미 Spring MVC가 "성공"으로 간주하기 때문. 그래서 "예외 발생 횟수 메트릭"을 `afterCompletion`의 `ex != null`로 세면 실제보다 훨씬 적게 집계된다.

> 💡 **왜 중요한가**: 관측성(observability)을 책임지는 레이어가 조용히 이벤트를 놓치면, 그 뒤에 쌓는 모든 알림·대시보드·SLO가 거짓말을 하기 시작한다.
