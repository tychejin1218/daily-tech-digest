### Spring의 `@ControllerAdvice`는 **모든 컨트롤러에 적용되지만, 패키지/애노테이션/타입으로 범위를 좁힐 수 있다**

`@ControllerAdvice`는 기본적으로 애플리케이션 내 모든 `@Controller`에 전역으로 적용된다. 하지만 `basePackages`, `annotations`, `assignableTypes` 속성으로 적용 범위를 명시적으로 분리할 수 있다 — 예를 들어 REST API용 예외 처리와 어드민 백오피스용 예외 처리를 각각 다른 `@ControllerAdvice`로 분리하면, 어드민에서 터진 예외가 API 클라이언트에게 HTML 에러 페이지로 나가는 사고를 막을 수 있다.

```java
@RestControllerAdvice(basePackages = "com.example.api")
public class ApiExceptionHandler { ... }

@ControllerAdvice(annotations = AdminController.class)
public class AdminExceptionHandler { ... }
```

> 💡 **왜 중요한가**: 전역 예외 처리를 "하나로 통일"하려는 유혹이 큰데, 실제로는 응답 포맷(JSON vs HTML)과 노출 정보(스택트레이스 vs 사용자 친화 메시지)가 영역마다 달라야 하고, 범위 분리를 안 하면 보안 사고로 직결된다.

### `@Valid`는 **중첩 객체(nested object)에 자동으로 전파되지 않는다** — 각 필드마다 다시 `@Valid`를 붙여야 한다

컨트롤러 파라미터에 `@Valid`를 붙여도 DTO 내부의 중첩 객체 필드까지 자동으로 검증이 내려가지 않는다. 중첩된 필드 위에 다시 `@Valid`를 명시적으로 선언해야 그 하위 필드의 `@NotNull`, `@Size` 같은 제약이 동작한다. 리스트나 `Map` 안의 요소도 마찬가지로 `List<@Valid Item>`처럼 제네릭 파라미터에 `@Valid`를 걸어야 한다.

```java
public class OrderRequest {
    @NotNull
    private String orderId;

    @Valid  // 이게 없으면 Address 내부의 @NotBlank가 무시된다
    private Address address;

    @Valid  // 리스트 요소 검증도 명시 필요
    private List<OrderItem> items;
}
```

> 💡 **왜 중요한가**: "최상위에 `@Valid` 붙였으니 다 검증되겠지"라는 가정이 가장 흔한 실수다 — 중첩 필드 검증이 빠지면 null이나 잘못된 값이 그대로 서비스 계층과 DB까지 흘러들어가고, 디버깅할 때는 "분명 `@NotNull` 걸었는데?"라며 한참 헤매게 된다.
