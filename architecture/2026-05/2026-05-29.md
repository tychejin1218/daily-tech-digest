### CQRS + Event Sourcing 조합 — 왜 이 둘은 "서로를 완성"시키는가, 그리고 왜 함께 쓰면 지옥이 되는가

CQRS와 Event Sourcing(ES)은 각각 독립적으로 존재 가능한 패턴이다. CQRS는 읽기와 쓰기를 분리하고, ES는 상태 대신 사건을 저장한다. 그런데 실무에서 이 둘은 유독 "짝을 이뤄" 등장한다. Axon Framework, EventStore, Marten 같은 도구들이 아예 두 패턴을 한 번에 지원하도록 설계되어 있을 정도다. 왜 그런가? 그리고 왜 그럼에도 불구하고 시니어들은 "쉽게 조합하지 마라"고 말하는가?

#### 각 패턴 홀로 쓸 때의 결정적 결함

**CQRS만 쓸 때의 문제**: 읽기 모델과 쓰기 모델을 나눴다면, 쓰기 발생 시 읽기 모델을 갱신해야 한다. 이 갱신을 어떻게 트리거할 것인가? 트랜잭션 안에서 두 DB를 동시 커밋하면 [[2pc-limitation]]으로 회귀한다. Outbox로 이벤트를 발행해 읽기 측이 구독하면 그럭저럭 동작하지만, **쓰기 모델은 여전히 "현재 상태"를 저장하는 CRUD**다. 새로운 읽기 모델(예: 매출 분석용 시계열 뷰)이 필요할 때, 과거 데이터를 재구성할 소스가 없다. Insert 로그를 뒤져야 한다.

**ES만 쓸 때의 문제**: 이벤트 스트림에서 현재 상태를 재생하려면 매번 aggregate의 모든 이벤트를 읽어 fold해야 한다. "주문 목록을 사용자별로 최근 순 20개 보여줘"라는 흔한 쿼리 하나도 재앙이다. `Order` 이벤트 스트림 전체를 스캔한 뒤 사용자별로 그룹핑? 불가능하다. 스냅샷으로 완화할 수 있지만 조회 패턴이 다양해질수록 무너진다.

#### 두 패턴이 만나면 서로의 결함을 정확히 메운다

```
       ┌─────────────────────────────────────┐
       │           Command Side (쓰기)         │
       │                                     │
   Cmd │  ┌──────────┐    append   ┌───────┐ │
──────►│  │Aggregate │────────────►│ Event │ │
       │  │(도메인로직)│              │ Store │ │
       │  └──────────┘             └───┬───┘ │
       └──────────────────────────────┼──────┘
                                      │ 이벤트 스트림
                                      │ (append-only, 순서 보장)
                                      ▼
       ┌──────────────────────────────────────┐
       │        Projection / Read Side (읽기)  │
       │                                      │
       │  ┌───────────┐    ┌───────────┐      │
       │  │Projector A│    │Projector B│  ... │
       │  └─────┬─────┘    └─────┬─────┘      │
       │        ▼                ▼            │
       │  ┌──────────┐     ┌──────────┐       │
       │  │주문요약뷰 │     │매출분석뷰 │       │
       │  │(RDB)     │     │(TSDB)    │       │
       │  └────┬─────┘     └────┬─────┘       │
       │       ▲                ▲             │
       │       │ Query          │ Query       │
       └───────┼────────────────┼─────────────┘
               │                │
             Client A         Client B
```

핵심 통찰은 **"이벤트 스트림이 유일한 진실의 원천(Single Source of Truth)이고, 읽기 모델은 그로부터 파생된 물질화된 뷰(materialized view)"** 라는 것이다.

- ES의 문제(읽기가 지옥) → CQRS의 읽기 모델이 해결한다. 읽기 최적화된 별도 저장소에 미리 프로젝션해 두면 조회는 단순 SELECT.
- CQRS의 문제(읽기 모델을 어떻게 채울까) → ES가 해결한다. 이벤트 스트림을 재생하기만 하면 어떤 읽기 모델이든 만들 수 있다. 심지어 **6개월 후 새로 필요해진 읽기 모델도, 과거 이벤트를 재생해서 채울 수 있다.**

이것이 "만나기로 운명 지어진" 이유다. CQRS는 "읽기 모델을 어떻게 채울지"를 규정하지 않고, ES는 "이벤트를 어디에 쓸지"를 규정하지 않는다. 두 패턴은 서로가 남겨둔 빈칸을 정확히 채운다.

#### 결정적 실무 이점: "새로운 뷰의 무료 추가"

이 조합이 진짜 위력을 발휘하는 순간은 **비즈니스 요구가 사후에 바뀔 때**다.

- 예: 초기에 `주문요약뷰`만 만들었는데, 1년 뒤 데이터 팀이 "결제 방법별 재구매 주기 분석"이 필요해졌다. 전통 CRUD 시스템이면? "그런 정보는 안 남겼는데요" 라며 이제부터 수집 시작해야 한다. ES+CQRS 시스템이면? **1년치 이벤트를 재생해서 새 프로젝션을 만들면 끝.**
- 이걸 실무에서 강력히 활용한 사례가 **Walmart의 재고 시스템**이다. 재고 상태를 저장하는 대신 "입고/출고/조정" 이벤트를 저장하고, 다양한 창고·채널·회계 부서의 뷰를 각자 프로젝션한다. 회계가 "3개월 전 특정 시점의 재고 스냅샷"을 요구하면 그 시점까지 이벤트를 재생하면 된다.
- **LMAX 거래소**는 CQRS+ES를 극한까지 밀어붙인 대표 사례다. 초당 6백만 건의 주문을 처리하기 위해 쓰기 측은 단일 스레드 이벤트 처리(Disruptor 패턴)로 극단적으로 단순화하고, 읽기 뷰는 이벤트 스트림을 소비하는 별도 프로세스들이 각자 최적화된 형태로 관리한다.

#### 사이드 이펙트: 이벤트가 도메인 언어의 중심이 된다

DDD 관점에서 흥미로운 부수 효과가 있다. CQRS+ES를 하면 개발자가 "**상태**"가 아니라 "**행위**"로 도메인을 사고하기 시작한다.

- CRUD식 사고: `Order.status = "PAID"; Order.paidAt = now(); Order.paymentMethod = "CARD"` — 무엇이 왜 일어났는지 잃어버림.
- 이벤트식 사고: `OrderPaid(orderId, method=CARD, amount=15000, paidAt=now())` — 사건의 의도가 그대로 남음.

이 차이가 나중에 "왜 이 주문의 상태가 이렇게 됐지?" 라는 감사(audit)·디버깅에서 결정적으로 벌어진다. 상태만 있는 시스템은 "지금 이 상태다"만 안다. 이벤트가 있는 시스템은 "어제 14:23:01에 결제 성공, 14:23:07에 재고 부족으로 취소 요청, 14:23:09에 환불" 이라는 **인과의 시간축**을 통째로 보관한다. 금융·헬스케어·물류 등 "언제 무엇이 왜 바뀌었는지"가 규제 요건인 도메인에서는 사실상 유일한 답이다.

#### 트레이드오프 — 이 조합이 만드는 새로운 종류의 복잡성

두 패턴을 합치면 각 패턴의 함정이 곱해진다.

| 항목 | CQRS 단독 | ES 단독 | CQRS+ES |
|------|----------|---------|---------|
| 학습 곡선 | 중 | 상 | **최상** |
| Eventual consistency 노출 | 있음 | 없음(모델상) | **있음, 그리고 더 눈에 띔** |
| 이벤트 스키마 진화 | 문제 없음 | 어렵다 | **매우 어렵다** |
| 프로젝션 재생성 | 필요 없음 | 필요 | **필수, 그리고 자주 필요** |
| 디버깅 | 보통 | 어려움 | **매우 어려움 (재생하지 않으면 상태 알 수 없음)** |
| 감사·시계열 분석 | 약함 | 강함 | **최강** |

특히 세 가지가 실전에서 시니어를 괴롭힌다.

1. **이벤트 스키마 진화**: 5년치 이벤트가 쌓인 상태에서 `OrderPaid`에 `currency` 필드를 추가하려면? 과거 이벤트는 그 필드가 없다. Upcaster(과거 이벤트를 새 버전으로 변환하는 함수)를 짜야 한다. 이걸 안 짜면 어느 날 프로젝션 재생이 예외로 죽는다.
2. **읽기 모델 재구성 시간**: 이벤트가 수억 건 쌓이면 새 프로젝션을 만들 때 몇 시간~며칠이 걸린다. 이 시간 동안 새 뷰는 "미완성 상태"다. 스냅샷·병렬 처리·delta replay 등의 최적화가 필수다.
3. **트랜잭션 경계의 재정의**: "주문하면 즉시 마이페이지에 뜬다"가 아니다. 이벤트가 발행되고 프로젝터가 소비하는 수백 ms 지연이 항상 존재한다. UX 설계 단계부터 이 지연을 반영해야 한다(낙관적 UI 업데이트, 명령 결과에 임시 ID 반환 등).

#### 시니어의 관점: 언제 쓰고, 언제 쓰면 안 되는가

**쓸 만한 상황**:
- **감사·규제가 강제되는 도메인** — 금융 거래, 의료 기록, 물류 이동 이력. "왜 이렇게 됐는가"를 몇 년 뒤에도 재구성할 수 있어야 한다.
- **읽기 요구가 예측 불가능하고 다양한 도메인** — 이커머스의 분석/추천/재고/회계처럼 같은 이벤트를 여러 관점에서 소비해야 하는 경우.
- **시계열 특성이 본질인 도메인** — 재고 이동, IoT 센서 데이터, 게임 플레이 로그.
- **쓰기 로직이 복잡한 도메인(=DDD가 유효한 영역)** — 이벤트가 도메인 언어와 자연스럽게 맞물릴 때.

**쓰면 안 되는 상황**:
- **단순 CRUD 위주 시스템** — 관리자 페이지, 사내 툴, 마스터 데이터 관리. 여기에 CQRS+ES를 얹으면 순전히 자기 만족이다.
- **팀에 ES 경험자가 없는 상태에서 신규 서비스 전체를 이 방식으로 짜려는 시도** — 첫 6개월은 순조롭다가 스키마 진화·프로젝션 재생성 이슈가 터지는 순간 대혼란. 도입한다면 **한 개의 핵심 aggregate부터** 시작하라.
- **강한 즉시 일관성이 UX 요구인 도메인** — "결제 즉시 잔액이 정확히 반영되어야 하고 조회 즉시 반영이 필수"라면 별도 뷰를 굳이 만들 이유가 없다. 그냥 하나의 트랜잭션 DB를 써라.
- **소규모 트래픽** — CQRS+ES의 성능/확장 이점은 규모가 클 때 나온다. 초당 수십 건 처리하는 서비스에 이걸 얹는 건 오버엔지니어링.

**황금률**: "CQRS만 도입할 것인가, ES까지 갈 것인가"는 별개의 판단이다. CQRS는 상대적으로 저비용으로 얻는 이점이 크지만, ES를 얹는 순간 팀 전체가 새로운 사고 방식·도구·운영 지식을 익혀야 한다. 대부분의 팀은 **먼저 CQRS + Outbox로 시작해 읽기/쓰기 분리를 소화한 뒤, "이 도메인은 진짜 이벤트 스트림이 유일한 진실이어야 한다"는 확신이 생겼을 때 ES를 도입**하는 경로가 안전하다. 처음부터 CQRS+ES 풀 세트를 도입한 팀 중 상당수는 3년 안에 "그때 왜 이렇게 시작했지"를 후회한다.

> 💡 **왜 중요한가**: CQRS+ES는 "이벤트 스트림을 유일한 진실로 두면, 어떤 읽기 모델이든 사후에 만들 수 있다"는 급진적 자유를 주지만, 그 자유의 대가로 스키마 진화·프로젝션 재생성·최종 일관성이라는 복잡성을 팀 전체에 영구히 부과한다 — 그래서 도입 여부는 기술 판단이 아니라 조직 판단이다.
