### PostgreSQL `GIN Index`와 `pg_trgm` — `LIKE '%검색어%'`를 인덱스로 태우는, 앞뒤 와일드카드의 해방구

`LIKE 'abc%'`는 B-Tree 인덱스를 타지만, `LIKE '%abc%'`는 인덱스를 못 타서 무조건 Full Scan이 된다. 이건 B-Tree가 "접두어 정렬" 구조라서 생기는 근본적 한계인데, PostgreSQL의 `pg_trgm` 확장을 켜고 GIN 인덱스를 만들면 문자열을 3-gram(trigram)으로 쪼개서 인덱싱하기 때문에 앞뒤 와일드카드 검색도 인덱스를 탄다. `CREATE INDEX idx_name ON users USING GIN (name gin_trgm_ops);` 한 줄이면 "홍길동"이 "길동", "홍길", "동홍" 어느 조각으로 들어와도 후보를 좁힌 뒤 정확도 필터링을 한다.

```sql
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_users_name_trgm ON users USING GIN (name gin_trgm_ops);

-- 이제 이 쿼리도 인덱스를 탄다
SELECT * FROM users WHERE name LIKE '%길동%';
-- 또는 유사도 검색도 가능
SELECT * FROM users WHERE name % '홍길순' ORDER BY similarity(name, '홍길순') DESC;
```

**트레이드오프**: GIN 인덱스는 B-Tree보다 3~10배 크고, INSERT/UPDATE 시 인덱스 갱신 비용이 비싸다(GIN은 "포스팅 리스트"를 갱신하는 구조라 쓰기가 느림). 대신 `fastupdate=on` 옵션으로 갱신을 지연시켜 완화할 수 있다. Elasticsearch를 도입할 만큼 검색이 핵심이 아니라면, "이 정도면 충분한 부분 검색"에는 GIN + pg_trgm이 인프라 하나를 통째로 줄여준다.

> 💡 **왜 중요한가**: "%검색어%가 느려서 Elasticsearch를 도입해야 한다"는 판단의 90%는 GIN + pg_trgm으로 해결된다. 별도 검색 엔진의 운영 비용을 감당할 만큼 트래픽이 크지 않다면, DB 안에서 끝내는 게 정답이다.

### JPA `@DynamicUpdate` — 변경된 컬럼만 UPDATE하는, 넓은 테이블의 조용한 성능 튜닝

기본 JPA/Hibernate는 엔티티의 필드 하나만 바꿔도 `UPDATE users SET name=?, email=?, age=?, address=?, ... WHERE id=?`처럼 모든 컬럼을 SET 절에 넣는다. 이유는 성능 — SQL을 미리 캐싱해두고 재사용하려는 최적화다. 하지만 컬럼이 30개 넘는 넓은 테이블이거나, `TEXT`/`BLOB` 같은 큰 컬럼이 섞여 있거나, 특정 컬럼에 인덱스나 트리거가 걸려 있다면 이 "전체 UPDATE"가 오히려 독이 된다. `@DynamicUpdate`를 붙이면 실제로 변경된(dirty) 컬럼만 SET 절에 포함시킨다.

```java
@Entity
@DynamicUpdate  // 변경된 컬럼만 UPDATE 문에 포함
public class Article {
    @Id private Long id;
    private String title;
    
    @Column(columnDefinition = "TEXT")
    private String content;  // 큰 컬럼 — title만 바꿀 때 이걸 다시 안 쓰게 됨
    
    private int viewCount;
    // ... 30개 컬럼
}

// title만 바꿨을 때:
// 기본:        UPDATE article SET title=?, content=?, view_count=?, ... WHERE id=?
// @DynamicUpdate: UPDATE article SET title=? WHERE id=?
```

**주의점**: 매 UPDATE마다 SQL을 동적 생성하므로 CPU 오버헤드가 생긴다(캐시 못함). 그래서 Hibernate는 이 옵션을 기본값으로 안 만들었다. 좁은 테이블(컬럼 10개 이하)이나 대부분의 필드가 함께 바뀌는 엔티티에는 오히려 손해다. "특정 컬럼만 자주 바꾸는 넓은 테이블"에만 선택적으로 붙이는 게 정석 — 특히 `LOB` 컬럼이 포함된 게시글/상품 엔티티에서 조회수만 올리는 경우 극적인 효과가 있다.

> 💡 **왜 중요한가**: "왜 조회수 하나 올렸는데 replication lag이 튀지?"의 답이 여기 있을 수 있다. binlog에 매번 전체 row가 실려 나가면 네트워크와 슬레이브 적용 비용이 몇 배로 뛴다.
