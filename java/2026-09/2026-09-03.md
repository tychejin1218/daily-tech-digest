### 1. `Collectors.filtering(predicate, downstream)`로 `groupingBy` 이후 필터 대신 그룹핑 전 필터 관성 벗어나기 (Java 9 정식)

`stream().filter().collect(groupingBy(...))`로 그룹핑하면 필터에서 걸러진 키는 결과 맵에서 아예 사라진다. 부서별 고연봉자 수를 세려는데 고연봉자가 없는 부서가 통째로 빠져버리는 함정이 대표적이다. `groupingBy(Employee::dept, filtering(e -> e.salary() > 10000, counting()))`으로 감싸면 모든 부서가 키로 남고 조건에 안 맞으면 `0`으로 집계된다.

```java
Map<String, Long> byDept = employees.stream()
    .collect(Collectors.groupingBy(
        Employee::dept,
        Collectors.filtering(e -> e.salary() > 10_000, Collectors.counting())
    ));
```

> 💡 **왜 중요한가**: "필터 → 집계"와 "집계 → 필터"는 결과 집합의 키 목록이 달라진다. 리포트·대시보드에서 "0건인 카테고리도 표시"가 요구사항일 때, 이걸 모르면 UI에서 누락된 그룹을 뒤늦게 발견하고 SQL로 우회하는 낭비가 생긴다.

### 2. `ScopedValue.where(KEY, value).run(...)`로 `ThreadLocal`의 메모리 누수·가상 스레드 지옥에서 벗어나기 (Java 21 프리뷰, JEP 446 / 24 정식화 진행)

요청 컨텍스트(사용자 ID, 트레이스 ID)를 스레드에 심을 때 `ThreadLocal`을 쓰면 값이 명시적으로 지워지지 않아 스레드풀에서 누수가 나고, 가상 스레드처럼 초당 수백만 개가 뜨는 환경에서는 맵 엔트리가 폭발한다. `ScopedValue`는 불변이고 스코프가 끝나면 자동으로 사라져 누수 자체가 구조적으로 불가능하다.

```java
private static final ScopedValue<String> USER_ID = ScopedValue.newInstance();

ScopedValue.where(USER_ID, "u-42").run(() -> {
    service.process();  // 이 콜스택 내부에서만 USER_ID.get() = "u-42"
});
// 스코프 종료 시점에 자동 해제, remove() 호출 불필요
```

> 💡 **왜 중요한가**: 가상 스레드 시대에는 "일회용 스레드"가 표준이다. `ThreadLocal.remove()`를 finally에서 빠뜨리는 버그로 프로덕션 힙이 부풀어 오르는 사고를 원천 차단하는, JEP가 명시적으로 노린 대체재다.
