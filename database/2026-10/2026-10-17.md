### Database Tip 1: MySQL `Online DDL`의 세 가지 모드 — `ALTER TABLE`이 테이블을 몇 시간 잠그던 시대를 끝낸 숨은 혁명

운영 중인 1억 행 테이블에 컬럼 하나 추가하려다 "ALTER TABLE이 2시간째 돌고 있는데 서비스가 멈춰 있다"는 공포를 겪어본 적 있다면, MySQL 5.6부터 도입된 `Online DDL`의 `ALGORITHM`과 `LOCK` 옵션을 반드시 알아야 한다. `ALGORITHM`은 `COPY`(테이블 전체 복사, 가장 느리고 긴 락), `INPLACE`(원본 테이블 자리에서 수정, 대부분 DML 허용), `INSTANT`(메타데이터만 수정, 밀리초 단위 완료)로 나뉘며, MySQL 8.0부터는 컬럼 추가/삭제, 기본값 변경, 컬럼 이름 변경 상당수가 `INSTANT`로 처리된다.

```sql
-- 위험: 암묵적으로 COPY가 선택될 수 있음 (수 시간 락)
ALTER TABLE orders ADD COLUMN memo VARCHAR(255);

-- 안전: INSTANT 강제 → 실패하면 즉시 에러로 알림
ALTER TABLE orders 
  ADD COLUMN memo VARCHAR(255), 
  ALGORITHM=INSTANT, LOCK=NONE;

-- INSTANT 불가 시 INPLACE 폴백 (예: 인덱스 추가)
ALTER TABLE orders 
  ADD INDEX idx_user_id (user_id), 
  ALGORITHM=INPLACE, LOCK=NONE;
```

| 모드 | 테이블 복사 | DML 허용 | 소요 시간 | 적용 예 |
|---|---|---|---|---|
| `COPY` | O | X (읽기만) | 수십 분~수 시간 | 컬럼 타입 변경 (일부) |
| `INPLACE` | X | O | 수 분~수십 분 | 인덱스 추가/삭제 |
| `INSTANT` | X | O | 밀리초 | 컬럼 추가, 기본값 변경 |

**함정**: `ALGORITHM`을 명시하지 않으면 MySQL이 알아서 "가장 가벼운 방법"을 고르지만, 조건이 안 맞으면 조용히 `COPY`로 떨어진다. 운영에서는 반드시 `ALGORITHM=INSTANT, LOCK=NONE`을 명시해서 "불가능하면 실패해라"로 안전장치를 걸어라. 실패하면 `pt-online-schema-change`나 `gh-ost` 같은 외부 툴로 우회하면 된다.

> 💡 **왜 중요한가**: 24/7 서비스에서 `ALTER TABLE` 한 줄이 몇 시간의 다운타임을 만들 수 있는지 없는지는 `ALGORITHM` 옵션 하나로 갈린다 — 모르고 쓰면 사고, 알고 쓰면 밀리초.

### Database Tip 2: JPA `@DynamicUpdate` — "모든 컬럼을 다 UPDATE" 하는 Hibernate의 숨은 비효율을 끄는 스위치

JPA의 기본 UPDATE 쿼리는 엔티티에 바뀐 필드가 하나뿐이어도 **모든 컬럼을 UPDATE 문에 포함**시킨다. 이는 Hibernate가 SQL을 **애플리케이션 시작 시점에 미리 생성해두고 PreparedStatement로 캐싱**하기 때문인데, 컬럼이 20개인 엔티티에서 `name`만 바꿔도 20개 전부를 UPDATE하므로 로그 분석도 어렵고, 바이너리 로그 복제 트래픽도 불어나며, 컬럼 중 하나라도 인덱스가 걸려 있으면 **불필요한 인덱스 갱신**까지 유발한다.

```java
// 기본: 모든 컬럼 UPDATE
@Entity
public class Member {
    @Id private Long id;
    private String name;
    private String email;
    private String address;
    // ... 20개 컬럼
}
// 실제 쿼리: UPDATE member SET name=?, email=?, address=?, ... WHERE id=?

// @DynamicUpdate: 변경된 컬럼만 UPDATE
@Entity
@DynamicUpdate
public class Member {
    @Id private Long id;
    private String name;
    // ...
}
// member.setName("new"); 호출 시
// 실제 쿼리: UPDATE member SET name=? WHERE id=?
```

**트레이드오프**:
- **득**: UPDATE 로그가 명확해지고, 인덱스 갱신·바이너리 로그·네트워크 트래픽이 모두 감소. 특히 **TEXT/BLOB 같은 대용량 컬럼이 섞인 테이블**에서 효과가 극적.
- **실**: 매번 SQL을 동적으로 생성하므로 PreparedStatement 캐시 효율이 떨어진다. 컬럼 수가 적거나 거의 모든 필드가 매번 바뀌는 엔티티라면 오히려 손해.

**적용 기준**: 컬럼이 10개 이상이면서 보통 1~3개만 변경되는 엔티티, 또는 LOB 컬럼이 섞인 엔티티에만 선별적으로 붙여라. 모든 엔티티에 디폴트로 바르는 것은 안티패턴이다. `@DynamicInsert`도 비슷하게 있지만, INSERT는 보통 모든 컬럼이 채워지므로 효과가 제한적이다.

> 💡 **왜 중요한가**: JPA의 "모든 컬럼 UPDATE"는 성능 이슈가 아닌 **운영 가시성과 복제 안정성**의 이슈 — 바이너리 로그를 읽을 때 어떤 필드가 실제로 바뀌었는지 알 수 없고, 리더-팔로워 복제 지연의 숨은 원인이 된다.
