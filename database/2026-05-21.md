### 1. PostgreSQL `LATERAL JOIN` — 각 행마다 상관 서브쿼리를 실행해 "그룹별 Top-N" 깔끔하게 풀기

`LATERAL`은 오른쪽 서브쿼리가 왼쪽 테이블의 컬럼을 참조할 수 있게 해주는 JOIN 형태로, "사용자별 최근 주문 3건"처럼 윈도우 함수(`ROW_NUMBER()`)로 풀면 전체 행을 정렬해야 하는 쿼리를 각 행에 대해 인덱스 기반 `LIMIT` 서브쿼리로 바꿔준다. 특히 `users` 수는 적고 `orders`가 거대할 때, `(user_id, created_at DESC)` 인덱스와 결합하면 전체 스캔 없이 그룹별로 인덱스 끝부분만 잘라 읽어 극적인 성능 차이를 만든다.

```sql
SELECT u.id, o.*
FROM users u
LEFT JOIN LATERAL (
  SELECT * FROM orders o
  WHERE o.user_id = u.id
  ORDER BY o.created_at DESC
  LIMIT 3
) o ON true;
```

> 💡 **왜 중요한가**: "그룹별 최신 N건" 같은 패턴에서 윈도우 함수 풀이는 전체 정렬을 강제하지만, `LATERAL`은 인덱스 끝부분만 읽어 데이터가 커질수록 비용 차이가 기하급수적으로 벌어진다.

### 2. PostgreSQL Partial Index — `WHERE` 절이 붙은 인덱스로 크기·유지비용 한 자릿수로 줄이기

Partial Index는 인덱스 정의에 `WHERE` 절을 붙여 **일부 행만 색인**하는 기능으로, "활성 사용자(`is_active = true`)", "미처리 작업(`status = 'PENDING'`)"처럼 한쪽으로 심하게 치우친 컬럼에서 진가를 발휘한다. 인덱스 크기가 줄어 캐시 적중률이 올라가고, INSERT/UPDATE 시 인덱스 갱신 대상도 줄어 쓰기 성능까지 개선되는데, 단 쿼리의 `WHERE` 조건이 인덱스 정의의 술어를 **포함**해야 옵티마이저가 해당 인덱스를 선택한다는 점에 유의해야 한다.

```sql
-- 전체 1억건 중 'PENDING' 작업은 0.1% 미만일 때
CREATE INDEX idx_jobs_pending ON jobs (created_at)
  WHERE status = 'PENDING';

-- 이 쿼리만 인덱스를 탄다 (status 조건이 일치해야 함)
SELECT * FROM jobs WHERE status = 'PENDING' ORDER BY created_at LIMIT 10;
```

> 💡 **왜 중요한가**: 일반 인덱스가 1억 행을 모두 색인하는 동안 Partial Index는 의미 있는 0.1%만 색인해, 동일한 쿼리에 대해 인덱스 크기·메모리·쓰기 비용을 한 자릿수로 줄여준다.
