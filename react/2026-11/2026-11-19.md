### 1. `useLayoutEffect` vs `useEffect`: "화면이 깜빡이는" 문제의 진짜 원인 — 브라우저가 paint하기 전에 끼어드는 유일한 Hook

`useEffect`는 브라우저가 화면을 **그린 후** 비동기로 실행되고, `useLayoutEffect`는 브라우저가 화면을 **그리기 전** 동기로 실행된다. "DOM을 측정해서 스타일을 다시 계산하는" 경우(툴팁 위치, 스크롤 복원, 모달 중앙 정렬)에 `useEffect`를 쓰면 유저는 "틀린 위치 → 올바른 위치"가 한 프레임 동안 깜빡이는 걸 본다.

> 💡 **왜 중요한가**: DOM 측정 후 즉시 보정이 필요한 코드에서 `useEffect`를 쓰면 반드시 깜빡임이 생긴다. "레이아웃 계산 → 렌더" 사이클에 끼어들 수 있는 Hook은 `useLayoutEffect` 하나뿐이다.

**브라우저 렌더링 사이클과 두 Hook의 타이밍**

```
React 커밋 (DOM 변경)
      │
      ├─▶ useLayoutEffect 실행 (동기, paint 블로킹)
      │       │
      │       └─▶ setState 하면 다시 렌더 → 다시 커밋
      │
      ▼
   브라우저 paint (화면에 그림)
      │
      ▼
   useEffect 실행 (비동기, paint 이후)
          │
          └─▶ setState 하면 "이미 그려진 화면"을 수정 → 깜빡임
```

**실제 사례: 툴팁 위치 보정**

```tsx
// ❌ useEffect: 틀린 위치로 1프레임 그려진 뒤 보정됨 → 깜빡임
function Tooltip({ targetRef }) {
  const [pos, setPos] = useState({ top: 0, left: 0 });
  useEffect(() => {
    const rect = targetRef.current.getBoundingClientRect();
    setPos({ top: rect.bottom, left: rect.left });
  }, []);
  return <div style={{ position: 'fixed', ...pos }}>툴팁</div>;
}

// ✅ useLayoutEffect: paint 전에 보정 완료 → 깜빡임 없음
useLayoutEffect(() => {
  const rect = targetRef.current.getBoundingClientRect();
  setPos({ top: rect.bottom, left: rect.left });
}, []);
```

**트레이드오프**

| 항목 | `useEffect` | `useLayoutEffect` |
|------|-------------|-------------------|
| 실행 시점 | paint 이후 (비동기) | paint 이전 (동기) |
| 성능 영향 | 없음 | paint 블로킹 → 느리면 체감 렉 |
| SSR | 안전 | 서버에서 경고 발생 (서버엔 레이아웃 없음) |
| 기본 선택 | **이걸 써라** | DOM 측정→보정일 때만 |

**실무 규칙**: 95%는 `useEffect`가 맞다. "유저가 깜빡임을 본다"가 재현되는 순간에만 `useLayoutEffect`로 바꿔라. 역순으로 쓰면 paint 블로킹으로 애플리케이션 전체가 무거워진다.

### 2. Context `Provider`의 `value={{ ... }}`는 지뢰다 — 매 렌더마다 "새 객체"가 모든 consumer를 통째로 리렌더링시키는 함정

`<Ctx.Provider value={{ user, setUser }}>`처럼 JSX에서 객체 리터럴을 넘기면, **부모가 리렌더링될 때마다 새 객체 참조가 만들어진다**. React는 `Object.is`로 value를 비교하므로 "값은 똑같아도" 모든 consumer가 리렌더링된다. Context를 "전역 상태"로 쓰려다 "앱 전체 리렌더링 폭탄"으로 변하는 가장 흔한 함정이다.

> 💡 **왜 중요한가**: Context는 리렌더링 범위를 좁히는 도구가 아니라 **"prop 전달 생략"** 도구다. value 참조가 바뀌면 consumer 전부가 따라 바뀌므로, value 안정화와 Context 분리가 성능의 전부다.

**문제의 메커니즘**

```
App 리렌더
  │
  ├─ { user, setUser } 객체 리터럴 → "새 참조" 생성
  │
  ▼
<Ctx.Provider value={새 참조}>
  │
  ├─▶ Object.is(이전 value, 새 value) === false
  │
  ▼
모든 useContext(Ctx) consumer 리렌더 (user가 안 바뀌어도!)
```

**실제 사례: 로그인 유저 Context**

```tsx
// ❌ 타이핑 한 번마다 화면 전체 리렌더
function App() {
  const [user, setUser] = useState(null);
  const [query, setQuery] = useState(''); // 이게 바뀌면

  return (
    <UserCtx.Provider value={{ user, setUser }}> {/* value가 새 참조 */}
      <SearchBar value={query} onChange={setQuery} />
      <HeavyDashboard />     {/* user 안 바뀌어도 리렌더 */}
      <HugeSidebar />        {/* user 안 바뀌어도 리렌더 */}
    </UserCtx.Provider>
  );
}
```

**해결책 3가지 — 상황에 맞춰 골라 써라**

**① `useMemo`로 value 참조 안정화 (가장 쉬움)**

```tsx
const value = useMemo(() => ({ user, setUser }), [user]);
return <UserCtx.Provider value={value}>...</UserCtx.Provider>;
```

**② "읽기 Context"와 "쓰기 Context" 분리 (리렌더 범위 극소화)**

```tsx
// user가 바뀔 때만 리렌더되는 consumer와
// setUser만 쓰는 consumer(절대 리렌더 안 됨)를 분리
<UserStateCtx.Provider value={user}>
  <UserDispatchCtx.Provider value={setUser}>
    {children}
  </UserDispatchCtx.Provider>
</UserStateCtx.Provider>
```

**③ 외부 스토어로 이관 (Zustand/Jotai) — Context가 "과했던" 경우**

고주파로 바뀌는 상태(스크롤 위치, 입력값, 타이머)는 Context가 아니라 외부 스토어 + `useSyncExternalStore` 기반 라이브러리가 맞다. Context는 "자주 안 바뀌는 정체성 정보"(테마, 로케일, 로그인 유저)에 최적화돼 있다.

**트레이드오프**

| 전략 | 리렌더 범위 | 코드 복잡도 | 적합한 상황 |
|------|-------------|-------------|-------------|
| `useMemo` value | consumer 전체 | 낮음 | 상태 변경이 드물 때 |
| State/Dispatch 분리 | 실제 쓰는 쪽만 | 중간 | 쓰기만 하는 consumer가 많을 때 |
| 외부 스토어 | selector 단위 | 높음 | 고주파 업데이트, 대규모 앱 |

**실무 체크리스트**: Provider를 만들 때 `value=` 뒤에 `{{`(객체 리터럴)이나 `[`(배열 리터럴)이 바로 붙어 있으면 90% 버그다. 즉시 `useMemo`로 감싸거나 Context를 두 개로 쪼개라.
