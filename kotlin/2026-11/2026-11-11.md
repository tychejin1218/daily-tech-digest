### 1. `tailrec`: 재귀의 우아함과 반복문의 성능을 동시에

`tailrec` 키워드는 꼬리 재귀 함수를 컴파일 시점에 반복문(while)으로 변환해주는 Kotlin의 최적화 장치다. 재귀 호출이 함수의 "마지막 연산"일 때만 사용 가능하며, StackOverflowError 걱정 없이 재귀의 선언적 아름다움을 유지할 수 있다. 팩토리얼, 리스트 순회, 수렴 알고리즘(뉴턴법) 같은 곳에서 Java 개발자가 포기했던 "재귀 로망"을 되살려준다.

```kotlin
// 일반 재귀 — 10,000번만 돌려도 StackOverflowError
fun factorial(n: Long, acc: Long = 1): Long =
    if (n <= 1) acc else factorial(n - 1, n * acc)

// tailrec — 컴파일러가 while 루프로 변환
tailrec fun factorialSafe(n: Long, acc: Long = 1): Long =
    if (n <= 1) acc else factorialSafe(n - 1, n * acc)

// 실전 예시: 리스트에서 조건 만족하는 첫 요소 찾기
tailrec fun <T> List<T>.findOrNull(predicate: (T) -> Boolean): T? =
    when {
        isEmpty() -> null
        predicate(first()) -> first()
        else -> drop(1).findOrNull(predicate)
    }
```

**주의**: `return factorial(n-1) * n` 처럼 재귀 호출 결과에 추가 연산이 붙으면 컴파일러가 경고를 띄우며 최적화하지 못한다. 반드시 **마지막 연산이 자기 자신 호출**이어야 한다.

> 💡 **왜 중요한가**: 재귀는 도메인(트리 순회, DP, 파서)을 코드에 그대로 투영하는 가장 직관적 표현이지만, JVM에선 스택 오버플로우 때문에 금기시돼왔다. `tailrec`은 "표현력은 재귀처럼, 성능은 반복문처럼"을 한 키워드로 보장한다.

### 2. `Result<T>`: 예외를 "값"으로 다루는 함수형 에러 핸들링

Kotlin의 `Result<T>`는 성공/실패를 하나의 타입으로 표현하는 컨테이너로, try-catch로 흩어지던 예외 처리를 체이닝 가능한 흐름으로 바꿔준다. `runCatching { ... }` 으로 감싸면 예외가 자동으로 `Result.failure`로 포획되고, `map`/`fold`/`recover`/`getOrElse` 같은 조합자로 선언적 처리가 가능하다. Rust의 `Result`, Scala의 `Try`에서 영감을 받은 설계로, 특히 API 응답 파싱이나 외부 호출 체인에서 코드가 극적으로 깔끔해진다.

```kotlin
// Before — try-catch 지옥
fun fetchUser(id: Long): User? {
    return try {
        val raw = api.call(id)
        try { parse(raw) } catch (e: Exception) { null }
    } catch (e: IOException) { null }
}

// After — Result 체이닝
fun fetchUser(id: Long): Result<User> =
    runCatching { api.call(id) }
        .mapCatching { parse(it) }
        .recover { e ->
            logger.warn("fallback for $id", e)
            cachedUser(id)
        }

// 소비 측 — fold로 성공/실패 한 번에 분기
val message = fetchUser(42).fold(
    onSuccess = { "환영합니다, ${it.name}" },
    onFailure = { "조회 실패: ${it.message}" }
)
```

**주의**: `Result`는 **반환 타입**에는 쓰되 **함수 파라미터나 프로퍼티 타입**으로는 쓰지 말라는 것이 공식 가이드다(코루틴의 `Result`와 혼선 방지 + 설계적으로 "에러는 경계에서만 흐름 전환"을 권장). 또한 `CancellationException`은 `runCatching`이 **다시 던진다** — 코루틴 취소 전파가 깨지지 않도록 하기 위함이다.

> 💡 **왜 중요한가**: Java 체크 예외의 대안을 찾던 개발자들이 가장 그리워하던 패턴이다. `Result`는 "에러를 숨기지 않으면서도 흐름을 끊지 않는" 중간 지대를 제공해, 특히 외부 I/O가 많은 백엔드 서비스 계층에서 가독성과 안정성을 동시에 끌어올린다.
