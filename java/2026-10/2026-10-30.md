### 1. `Collectors.filtering(predicate, downstream)` (Java 9 정식)로 `groupingBy` 안에서 필터링할 때 바깥 `stream.filter()`로 먼저 거르고 그룹핑하는 관성 벗어나기

`stream.filter(cond).collect(groupingBy(key))` 패턴은 **필터링 후 사라진 키가 결과 맵에서 아예 빠진다**. 전체 키를 유지한 채 각 그룹 내부에서만 필터링하고 싶다면 `groupingBy(key, filtering(cond, toList()))`를 써야 "조건에 맞는 요소가 하나도 없는 그룹"도 빈 리스트로 결과에 남는다. 전자는 "값이 존재하는 키만", 후자는 "모든 키 보존, 값만 필터링"이라는 전혀 다른 의미론이다.

```java
// 관성: 매출 100만 이상 주문만 사용자별로 그룹핑 → 매출 작은 사용자는 맵에서 사라짐
Map<Long, List<Order>> big = orders.stream()
    .filter(o -> o.amount() >= 1_000_000)
    .collect(groupingBy(Order::userId));

// 개선: 전체 사용자 키는 유지하면서 그룹 내부에서만 필터링
Map<Long, List<Order>> big = orders.stream()
    .collect(groupingBy(
        Order::userId,
        filtering(o -> o.amount() >= 1_000_000, toList())
    ));
// 매출 100만 미만만 가진 사용자도 key에 남고 value는 빈 리스트
```

> 💡 **왜 중요한가**: "조건에 안 맞는 그룹을 결과에서 빼는 것"과 "그룹은 유지하고 값만 비우는 것"은 다운스트림 로직(평균 계산, UI 렌더링)에서 NPE와 "왜 이 사용자가 안 보이지?" 버그로 직결된다.

### 2. `Thread.ofVirtual().start(task)` (Java 21 정식, JEP 444)로 I/O 블로킹 태스크마다 `Executors.newFixedThreadPool(N)` 풀 사이즈 튜닝에 매달리는 관성 벗어나기

플랫폼 스레드는 OS 스레드 1:1 매핑이라 수천 개 뜨면 메모리/컨텍스트 스위칭 비용으로 터지기 때문에 풀로 상한을 두고 큐에 쌓는 게 정석이었다. **가상 스레드는 JVM이 캐리어 스레드 위에서 M:N으로 스케줄링하므로 수십만 개를 띄워도 괜찮고**, I/O 블로킹 시 캐리어를 자동 반납한다. 결과적으로 "한 요청 = 한 스레드" 모델을 풀 튜닝 없이 그대로 쓸 수 있다.

```java
// 관성: 외부 API 호출 1000건 → 풀 사이즈 몇으로? 큐 길이는? 계속 고민
ExecutorService pool = Executors.newFixedThreadPool(50);
List<Future<Response>> results = urls.stream()
    .map(url -> pool.submit(() -> httpClient.send(url)))
    .toList();

// 개선: 가상 스레드 ExecutorService — 요청당 하나씩 그냥 뿌림
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<Response>> results = urls.stream()
        .map(url -> executor.submit(() -> httpClient.send(url)))
        .toList();
} // AutoCloseable, 모든 태스크 완료까지 대기
```

단, **`synchronized` 블록 안에서 블로킹하면 캐리어를 핀(pin)해버려 효과가 반감**되므로 `ReentrantLock`으로 바꿔야 하고, CPU 바운드 작업은 여전히 플랫폼 스레드 풀이 유리하다.

> 💡 **왜 중요한가**: "스레드풀 사이즈 N을 뭘로 할지"는 지난 20년간 자바 서버 튜닝의 숙제였는데, I/O 중심 워크로드에서는 가상 스레드가 이 문제를 질문 자체로 소거한다 — 단 `synchronized`가 숨은 지뢰라는 걸 모르면 효과를 못 본다.
