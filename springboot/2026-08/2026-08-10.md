### `@Async` 메서드의 반환값이 `void`나 `CompletableFuture`가 아니면 예외를 잡을 방법이 없다

`@Async`가 붙은 메서드는 별도 스레드에서 실행되기 때문에 호출 스레드로 예외가 전파되지 않는다. 반환 타입이 `void`면 `AsyncUncaughtExceptionHandler`를 등록해야 잡을 수 있고, 그 외 일반 객체 반환은 예외가 로그조차 남지 않고 사라진다. 오직 `CompletableFuture`(또는 `Future`) 반환일 때만 `.get()`이나 `.exceptionally()`로 예외를 회수할 수 있다.

```java
// ❌ 예외가 조용히 사라진다
@Async
public String doWork() {
    throw new RuntimeException("silent death");
}

// ✅ CompletableFuture로 예외 전파
@Async
public CompletableFuture<String> doWork() {
    return CompletableFuture.completedFuture("ok");
}

// ✅ void는 전역 핸들러로 잡기
@Configuration
@EnableAsync
public class AsyncConfig implements AsyncConfigurer {
    @Override
    public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
        return (ex, method, params) -> log.error("async fail: {}", method, ex);
    }
}
```

> 💡 **왜 중요한가**: 비동기 처리에서 예외가 삼켜지면 결제 실패, 알림 누락 같은 치명적 버그가 프로덕션에서 원인 불명으로 반복된다.

### `@ControllerAdvice`의 `basePackages` 없이 여러 개를 등록하면 `@Order`로 우선순위를 정해야 한다

`@RestControllerAdvice`를 여러 개 만들어 계층별로 예외 처리를 나누는 경우, Spring은 등록된 어드바이스를 순회하며 첫 매칭을 사용한다. 이때 `@Order` 없이는 순서가 스캔 순서에 따라 비결정적으로 결정되어, 공통 `Exception.class` 핸들러가 도메인 특화 핸들러보다 먼저 잡히는 사고가 난다. 도메인별로 `basePackages`나 `annotations`로 스코프를 좁히거나, `@Order(Ordered.HIGHEST_PRECEDENCE)`로 명시적으로 순서를 지정해야 한다.

```java
// ✅ 도메인 특화 어드바이스가 먼저 매칭되도록
@RestControllerAdvice(basePackages = "com.shop.payment")
@Order(1)
public class PaymentExceptionAdvice {
    @ExceptionHandler(PaymentException.class)
    public ResponseEntity<?> handle(PaymentException e) { ... }
}

@RestControllerAdvice
@Order(Ordered.LOWEST_PRECEDENCE)  // 폴백은 반드시 마지막
public class GlobalExceptionAdvice {
    @ExceptionHandler(Exception.class)
    public ResponseEntity<?> handle(Exception e) { ... }
}
```

> 💡 **왜 중요한가**: 순서를 명시하지 않으면 배포 환경(JAR 스캔 순서)에 따라 어드바이스 우선순위가 바뀌어, 로컬에선 정상이지만 운영에선 엉뚱한 에러 응답이 나가는 재현 불가능한 버그가 생긴다.
