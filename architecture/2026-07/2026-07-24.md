### Hybrid Search — "벡터만 쓰면 왜 '정확히 그 단어'를 못 찾는가"라는 배신, BM25와 임베딩을 다시 합치는 검색 아키텍처

RAG를 처음 만들 때 대부분의 팀이 이런 경험을 한다. Vector DB에 문서를 잔뜩 넣고, 코사인 유사도로 top-k를 뽑고, LLM에 컨텍스트로 넘긴다. 데모는 완벽하다. "결제 실패 원인은?" 같은 의미적 질문에 놀랍도록 잘 답한다. 그런데 실사용자가 들어오는 순간 이상한 리포트가 쌓인다. **"에러코드 `PAY_9042` 검색했는데 관련 없는 문서만 나와요"**, **"제품명 'ATLAS-K7'을 정확히 쳤는데 왜 못 찾죠?"**, **"내 이름 '박진영' 검색이 왜 '박진혁'보다 뒤에 나와요?"**

임베딩 모델은 **의미(semantic)** 는 잘 잡지만 **어휘의 정확한 일치(lexical)** 에는 놀랄 만큼 약하다. `PAY_9042`와 `PAY_9041`은 벡터 공간에서 거의 붙어 있고, 희귀 고유명사(브랜드명, 사람 이름, 코드값)는 학습 데이터에 거의 없어서 임베딩이 무의미한 방향을 가리킨다. 반대로 옛날 방식인 BM25/TF-IDF 같은 키워드 검색은 정확한 토큰 일치엔 강하지만 "환불 방법"과 "돈 돌려받기"를 다른 문서로 취급한다. 둘 다 반쪽짜리다. **Hybrid Search는 이 두 검색을 병렬로 돌리고 결과를 다시 합쳐서 하나의 랭킹으로 만드는 아키텍처다.**

```
                   ┌─────────────────────────────────────┐
                   │           Query: "PAY_9042 결제 실패" │
                   └────────────────┬────────────────────┘
                                    │
                ┌───────────────────┴───────────────────┐
                ▼                                       ▼
    ┌────────────────────┐                  ┌─────────────────────┐
    │  Sparse Retriever  │                  │  Dense Retriever    │
    │  (BM25 / Elastic)  │                  │  (Embedding + ANN)  │
    │                    │                  │                     │
    │  토큰 정확 매칭      │                  │  의미 유사도         │
    │  PAY_9042 → 5건    │                  │  "결제 실패" → 50건 │
    └─────────┬──────────┘                  └──────────┬──────────┘
              │ top-k (score_bm25)                     │ top-k (score_cos)
              └───────────────────┬────────────────────┘
                                  ▼
                    ┌──────────────────────────┐
                    │   Fusion (RRF or Weighted)│
                    │                          │
                    │   RRF: 1/(k+rank)의 합    │
                    │   Weighted: α·s1 + β·s2  │
                    └────────────┬─────────────┘
                                 ▼
                    ┌──────────────────────────┐
                    │   Reranker (Cross-Encoder)│  ← 선택적, 정확도 크게↑
                    │   (bge-reranker, Cohere) │
                    └────────────┬─────────────┘
                                 ▼
                          top-n → LLM Context
```

**두 검색의 스코어를 어떻게 합칠 것인가**가 이 아키텍처의 핵심 설계 결정이다. 순진하게 `final = α * bm25 + β * cosine`으로 가중합하면 곧바로 실패한다. BM25 점수는 문서 길이·코퍼스 통계에 따라 0~50 사이를 오가고, 코사인 유사도는 -1~1이다. 스케일이 다른 두 값을 그냥 더하면 항상 한쪽이 우세해진다. min-max 정규화도 쿼리마다 분포가 달라서 불안정하다. 그래서 프로덕션에서는 **Reciprocal Rank Fusion(RRF)** 이 사실상 표준이다. 각 검색의 **점수 대신 순위(rank)** 만 써서 `score = Σ 1/(k + rank_i)` (보통 k=60)로 합친다. 스케일이 없어져 두 신호가 대등하게 섞이고, 튜닝할 파라미터도 사실상 k 하나뿐이다. Elasticsearch 8.9+, Weaviate, Vespa가 모두 RRF를 네이티브로 지원한다.

여기서 한 단계 더 나아간 게 **2-stage retrieval + reranker** 다. Hybrid로 뽑은 top-100을 **cross-encoder**(쿼리와 문서를 함께 넣어 관련도를 뽑는 무거운 모델, 예: `bge-reranker-large`, Cohere Rerank)로 다시 채점해 top-5~10을 뽑는다. Bi-encoder(임베딩)는 문서와 쿼리를 각자 벡터화한 뒤 내적만 계산해서 빠르지만 정보 손실이 크다. Cross-encoder는 문서 하나마다 forward pass가 필요해 느리지만, top-100 정도의 좁은 후보군에만 돌리면 지연은 100~300ms에 그친다. 실제 벤치마크(BEIR, MTEB)에서 Hybrid + Rerank는 순수 벡터 검색 대비 nDCG@10이 15~30%p 오르는 경우가 흔하다.

**실제 사례**로 넘어가자. **Elastic**은 자사의 Search AI 플랫폼에서 BM25(20년 이상 검증된 자사 코어)와 dense vector를 RRF로 묶는 것을 공식 권장 패턴으로 제시한다. 자기 강점인 lexical search를 버리지 않고 벡터를 더한 게 정답이었다는 걸 인정한 셈이다. **Weaviate**는 `alpha` 파라미터(0=순수 키워드, 1=순수 벡터)로 hybrid 쿼리를 한 줄로 지원하고, 대부분의 프로덕션 유저가 alpha=0.5~0.7 사이를 쓴다. **Notion AI**의 Q&A는 초창기 순수 임베딩 검색을 쓰다가 "특정 페이지 제목이나 인물명을 검색하면 못 찾는다"는 불만이 폭주해, BM25 신호를 다시 넣고 나서야 사용자 만족도가 올라갔다는 회고를 공유했다. **Shopify**의 상품 검색은 SKU·제품 코드 같은 정확 매칭이 매출과 직결되기 때문에 임베딩만으로는 절대 불가능하다고 판단하고 처음부터 Hybrid + Learned Sparse(SPLADE) 조합을 택했다. **Anthropic Claude Code** 자체도 코드 검색에서 함수명·심볼 같은 어휘 신호를 유지하기 위해 ripgrep(정확 매칭)과 의미 기반 검색을 함께 쓰는 걸 기본 설계로 삼는다.

**트레이드오프**는 명확하다. Hybrid의 대가는 **두 개의 인덱스를 함께 운영해야 한다**는 것이다. Elasticsearch/OpenSearch 같은 sparse 엔진과 Pinecone/Weaviate/pgvector 같은 dense 엔진을 별도로 유지하면, 문서 추가 시 두 쪽에 모두 색인해야 하고 두 저장소의 일관성(한쪽만 성공하면 결과가 왜곡됨)을 관리해야 한다. Weaviate·Vespa·Elasticsearch처럼 한 엔진에서 둘 다 지원하는 스택을 쓰면 이 문제가 줄지만, 그 대신 특정 벤더에 락인된다. 지연도 늘어난다. 두 검색은 병렬로 돌릴 수 있지만 fusion + reranker까지 붙이면 순수 벡터 대비 P99 지연이 2~4배가 되기 쉽고, reranker의 GPU 비용도 만만치 않다. 그리고 무엇보다, **평가가 갑자기 어려워진다**. α·β·k·top-n·reranker threshold 같은 하이퍼파라미터가 늘어나 오프라인 eval 셋(정답 문서가 라벨링된 QA pair)이 없으면 튜닝 방향을 잃는다.

**시니어 백엔드 관점에서 언제 쓰고 언제 쓰지 말아야 하는가.** 써야 하는 경우: (1) 코퍼스에 **에러 코드·제품 SKU·인물명·버전 문자열** 같은 고유 토큰이 많을 때 — 임베딩이 절대 못 잡는다. (2) 사용자가 **긴 자연어**(“어제 밤에 결제 안 됐던 그 케이스”)와 **정확한 키워드**(`err_code=9042`)를 섞어 던지는 검색 UI. (3) 도메인 특화 용어가 많아 범용 임베딩이 미묘한 뉘앙스를 놓치는 법률·의료·금융. 쓰지 말아야 할 경우: (1) 코퍼스가 **작고**(수천 건 이하) 쿼리 트래픽도 낮은 초기 프로토타입 — 순수 벡터 하나로도 충분하고 인프라 복잡도만 늘어난다. (2) 응답 지연 예산이 **P99 < 100ms**로 빡빡한 실시간 UX — 두 인덱스 + fusion + rerank는 그 예산에 안 들어간다. (3) 오프라인 **eval 셋을 만들 여력이 없는** 팀 — 튜닝할 손잡이만 늘고 검증 못하는 최악의 상태가 된다. **"먼저 순수 벡터로 시작하고, 놓치는 쿼리 패턴이 20% 이상 관측되면 그때 sparse를 얹는다"** 가 실무의 정답이다. 처음부터 Hybrid를 깔면 대개 과설계다.

> 💡 **왜 중요한가**: 벡터 검색은 "의미가 비슷한 것"에는 강하지만 "정확히 그 단어"에는 약하다는 근본적 비대칭이 있고, Hybrid Search는 이 비대칭을 인정하고 두 검색을 RRF로 합쳐 서로의 사각지대를 메우는, RAG 프로덕션의 사실상 표준 리트리벌 아키텍처다.
