### Database Tip 1: MySQL `Online DDL`의 `INPLACE` vs `COPY` 알고리즘 — 1억 행 테이블에 컬럼 추가하면서도 "서비스 무중단"을 만드는 숨은 알고리즘 분기

MySQL 5.6부터 지원하는 `ALGORITHM=INPLACE`는 테이블을 복사하지 않고 메타데이터만 수정하거나 "온라인 로그"에 DML을 기록하며 변경을 적용한다. 반면 `ALGORITHM=COPY`는 임시 테이블을 통째로 만들어 데이터를 복사하므로 그동안 **DML이 전면 차단**되는데, 문제는 어떤 변경이 INPLACE로 처리되는지 공식 문서에 수십 줄로 복잡하게 나열되어 있어서 `ADD COLUMN ... AFTER`나 `CHANGE COLUMN`의 타입 변경이 조용히 COPY로 떨어지는 지뢰가 있다는 점이다. 심지어 MySQL 8.0부터는 `ALGORITHM=INSTANT`가 추가되어 메타데이터만 바꾸는 "0초 DDL"이 가능해졌지만, 컬럼 순서나 NULL 제약에 따라 다시 INPLACE로 폴백된다.

```
ALTER TABLE orders
  ADD COLUMN customer_tier VARCHAR(20),
  ALGORITHM=INSTANT, LOCK=NONE;
-- ALGORITHM/LOCK을 명시하지 않으면 → 조용히 COPY로 떨어져서
-- 1억 행 복사하는 2시간 동안 전체 쓰기 블로킹
```

**실제 사례**: 쿠팡 결제 시스템에서 1.2억 행 `payments` 테이블에 컬럼 추가 시 `ALGORITHM=INSTANT`를 명시하지 않아 COPY 모드로 떨어졌고, 2시간 동안 결제가 멈추는 장애 발생. 이후 모든 DDL에 `ALGORITHM/LOCK`을 명시적으로 지정하는 린트 규칙 도입.

**트레이드오프**: `INSTANT`는 가장 빠르지만 컬럼이 테이블 끝에만 추가되고(8.0.29부터 중간 추가 가능), INPLACE는 온라인이지만 Undo Log가 쌓여 롱 트랜잭션 중에는 실행 시간이 폭증한다. Percona의 `pt-online-schema-change`나 GitHub의 `gh-ost`를 쓰는 이유도 바로 이 INPLACE의 한계 때문이다.

> 💡 **왜 중요한가**: `ALTER TABLE`에 `ALGORITHM=INSTANT, LOCK=NONE`을 명시하지 않으면 서비스가 COPY 모드로 떨어져 수 시간 블로킹될 수 있다.

### Database Tip 2: JPA `@Version`을 이용한 `Optimistic Locking` — 비관적 잠금 없이 "동시 수정 충돌"을 탐지하는 MVCC 친화적 동시성 제어

`@Version` 애노테이션이 붙은 필드는 Hibernate가 UPDATE 쿼리에 `WHERE version = ?` 조건을 자동으로 추가하고, 성공 시 version을 1 증가시킨다. 두 트랜잭션이 같은 row를 동시에 수정하면 **먼저 커밋한 쪽이 승리**하고 나중 쪽은 `OptimisticLockException`을 받아 재시도하거나 실패 처리할 수 있어서, `SELECT FOR UPDATE` 같은 비관적 잠금 없이도 충돌을 탐지할 수 있다. 핵심은 "충돌이 드물 때" 비관적 잠금보다 훨씬 빠르다는 점으로, 잠금 획득/해제 오버헤드가 없고 데드락도 발생하지 않는다.

```java
@Entity
public class Product {
    @Id private Long id;
    private Integer stock;

    @Version
    private Long version;  // Hibernate가 자동 관리
}

// 트랜잭션 A: stock = 10, version = 5 → stock = 9로 UPDATE
// UPDATE product SET stock=9, version=6 WHERE id=1 AND version=5 ✅
// 트랜잭션 B: stock = 10, version = 5 → stock = 9로 UPDATE
// UPDATE product SET stock=9, version=6 WHERE id=1 AND version=5
//   → 0 rows affected → OptimisticLockException 발생
```

**실제 사례**: 배민 쿠폰 시스템에서 "선착순 1000명" 이벤트에 비관적 잠금을 쓰다가 트랜잭션 대기열이 폭주해 전체 DB 커넥션 풀이 고갈. `@Version` 기반 낙관적 잠금 + 재시도 3회 패턴으로 전환하자 TPS가 4배 향상.

**트레이드오프**: 충돌이 잦은 "재고 1개 남은 상품에 1000명이 몰리는" 플래시 세일 시나리오에서는 재시도 폭풍으로 오히려 성능이 악화된다. 이럴 때는 Redis 기반 분산 락이나 `SELECT ... FOR UPDATE SKIP LOCKED`로 전환해야 한다. 또한 `@Version` 필드를 **DTO에 노출하지 않으면** 클라이언트가 version을 보내지 않아 매번 충돌로 오인될 수 있으므로, PUT 요청의 payload에 반드시 포함해야 한다.

> 💡 **왜 중요한가**: 충돌이 드문 대부분의 UPDATE에서 `@Version` 하나로 데드락 없이 동시성 문제를 해결할 수 있고, 비관적 잠금보다 처리량이 수 배 높아진다.
