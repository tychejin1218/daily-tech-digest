### 1. PostgreSQL `INCLUDE` 절 Covering Index — Index-Only Scan으로 테이블 접근 자체를 없애기

`CREATE INDEX ... ON t(a, b) INCLUDE (c, d)` 처럼 키 컬럼 뒤에 비-키 컬럼을 붙이면, 인덱스 페이지에 `c`, `d` 값이 함께 저장된다. 옵티마이저가 Index-Only Scan을 선택하면 힙(테이블) 페이지를 아예 읽지 않고 인덱스만으로 결과를 만들어내므로 I/O가 한 자릿수까지 줄어든다. 다중 컬럼 인덱스에 비-키 컬럼을 넣을 때와 달리, `INCLUDE` 컬럼은 정렬·검색에 쓰이지 않아 인덱스 트리 높이를 키우지 않고 유니크 제약과도 충돌하지 않는다.

> 💡 **왜 중요한가**: 자주 `SELECT a, b, c FROM t WHERE a = ?` 같은 쿼리에서 `c` 하나 때문에 테이블을 또 읽고 있다면, `INCLUDE (c)`만 추가해도 힙 접근을 0으로 만들 수 있다.

### 2. Hibernate `@DynamicUpdate` — 변경되지 않은 컬럼까지 매번 UPDATE 문에 넣는 함정

기본 Hibernate는 엔티티의 모든 컬럼을 SET 절에 박아 캐시된 UPDATE 문 하나를 재사용한다. 컬럼이 50개인 테이블에서 `lastLoginAt`만 바꿔도 50개 컬럼이 전부 UPDATE되며, 이로 인해 ① 관련 없는 컬럼의 인덱스가 불필요하게 갱신되고 ② BEFORE UPDATE 트리거가 모든 컬럼이 바뀐 것으로 오판하며 ③ 감사(audit) 로그가 노이즈로 가득 찬다. `@DynamicUpdate`를 붙이면 매번 dirty checking 결과로 SQL을 생성하므로 실제 변경 컬럼만 SET 절에 포함된다.

> 💡 **왜 중요한가**: 컬럼이 많거나 트리거·인덱스가 붙은 테이블에서는 “한 컬럼만 바꿨는데 락 경합이 심하다”는 증상의 진짜 원인이 이 기본 동작일 때가 많다 — SQL 캐시 손해를 감수하더라도 켜는 게 낫다.
