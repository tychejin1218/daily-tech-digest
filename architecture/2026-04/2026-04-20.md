### Outbox 패턴 — "DB 커밋과 메시지 발행 사이의 원자성"을 만드는 유일하게 실용적인 방법

MSA에서 가장 흔하게 마주치는 함정은 이렇다. 주문 서비스가 `orders` 테이블에 INSERT하고, 곧바로 Kafka에 `OrderCreated` 이벤트를 발행한다. 겉보기엔 자연스럽지만, 이 두 동작은 **서로 다른 저장소에 대한 두 번의 쓰기**다. DB 커밋은 성공했는데 브로커 발행이 실패하면? 반대로 브로커에 이벤트는 나갔는데 DB 커밋이 롤백되면? 재고 서비스는 존재하지 않는 주문을 처리하고, 배송 서비스는 발생하지 않은 이벤트를 영원히 기다린다. 이것이 **dual write problem**이며, Outbox 패턴은 이 문제를 "이벤트를 메시지 브로커가 아니라 자기 DB에 먼저 쓴다"는 발상의 전환으로 해결한다.

#### 핵심 아이디어: 이벤트도 도메인 데이터의 일부다

```
[전통적인 dual write — 위험]
                                                    ┌──> DB commit OK
Service ──┬──> INSERT orders ─────────────┐         │    Kafka publish FAIL
          │                                ├── ❌ ──┤    → 유실
          └──> kafkaTemplate.send(event) ──┘         └──> DB rollback
                                                         Kafka published OK
                                                         → 유령 이벤트

[Outbox 패턴 — 안전]
                          ┌─────────── 같은 로컬 트랜잭션 ───────────┐
Service ──> BEGIN TX ──> INSERT orders ──> INSERT outbox_events ──> COMMIT
                          └────────────────────────────────────────┘
                                            │
                                            │ (별도 프로세스)
                                            ▼
                          ┌─────────────────────────────────┐
                          │  Message Relay                  │
                          │  1. outbox_events 폴링 or CDC   │
                          │  2. Kafka publish               │
                          │  3. published_at = NOW() 마킹   │
                          └─────────────────────────────────┘
                                            │
                                            ▼
                                     Kafka topic
```

주문 저장과 이벤트 저장을 **동일한 로컬 ACID 트랜잭션** 안에서 처리한다. 이벤트 발행은 별도의 릴레이 프로세스가 outbox 테이블을 읽어 브로커로 옮긴다. DB 커밋이 실패하면 이벤트도 함께 롤백되고, 커밋이 성공하면 이벤트는 반드시 outbox에 남아있다 — 발행이 언젠가는 일어난다.

#### 스키마와 코드

```sql
CREATE TABLE outbox_events (
    id            BIGSERIAL PRIMARY KEY,
    aggregate_id  VARCHAR(64) NOT NULL,      -- 파티셔닝 키 (순서 보장용)
    event_type    VARCHAR(128) NOT NULL,     -- "OrderCreated"
    payload       JSONB NOT NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    published_at  TIMESTAMPTZ                -- NULL이면 미발행
);
CREATE INDEX idx_outbox_unpublished ON outbox_events (created_at)
    WHERE published_at IS NULL;
```

```java
@Transactional
public Order placeOrder(PlaceOrderCommand cmd) {
    Order order = orderRepository.save(Order.of(cmd));

    OutboxEvent event = OutboxEvent.builder()
        .aggregateId(order.getId().toString())
        .eventType("OrderCreated")
        .payload(objectMapper.writeValueAsString(new OrderCreatedEvent(order)))
        .build();
    outboxRepository.save(event);   // 같은 트랜잭션

    return order;
}
```

#### 릴레이 방식: Polling vs CDC

| 방식 | 장점 | 단점 | 적합한 경우 |
|------|------|------|-------------|
| **Polling Publisher** | 구현 단순, 인프라 최소 | DB 부하, 지연(폴링 주기), 스케일 아웃 시 락 필요 | 소규모 트래픽, 인프라 팀 없음 |
| **Transaction Log Tailing (CDC)** | 실시간에 가까움, DB 부하 미미, 애플리케이션 코드 무침습 | Debezium 등 별도 스택 운영, WAL 슬롯 관리 | 대규모, 저지연 요구 |

Debezium은 PostgreSQL WAL 또는 MySQL binlog를 읽어 outbox 테이블의 INSERT를 감지하고 Kafka로 흘려보낸다. Confluent가 공식 문서로 밀고 있는 방식이며 "Outbox Event Router" SMT를 통해 페이로드를 그대로 Kafka 토픽에 매핑한다.

#### At-least-once 그리고 반드시 따라오는 멱등성

Outbox는 **at-least-once** 보장이지 exactly-once가 아니다. 릴레이가 Kafka에 publish 후 `published_at` 업데이트 전에 죽으면 재기동 시 같은 이벤트를 다시 발행한다. 따라서 **소비자 쪽 멱등성 설계는 필수**다. 이벤트에 안정적인 `event_id`(예: outbox row의 PK)를 실어 보내고, 소비자는 처리된 event_id를 저장해 중복을 걸러낸다. 이 규칙을 놓치면 재고가 두 번 차감되고, 결제가 두 번 승인되는 대참사가 생긴다.

#### 실제 사례

- **Shopify**는 자체 블로그(2023)에서 주문/결제 파이프라인에 outbox + Kafka + Debezium 조합을 채택했다고 밝혔다. dual write 시절 특정 장애 상황에서 결제-주문 상태 불일치가 반복적으로 발생했고, outbox 도입 후 근본적으로 사라졌다는 회고.
- **Wix**는 "Reliable Microservices Data Exchange with Transactional Outbox" 아티클에서 수백 개 서비스가 동일한 outbox 라이브러리(Greyhound)를 공유해 표준화한 케이스를 공개했다.
- **Uber**의 Cadence/Temporal 도입 이전 결제 시스템도 유사한 outbox-like 패턴을 썼는데, 여기서 얻은 교훈이 결국 Saga Orchestrator를 별도 워크플로 엔진으로 뽑아내는 결정으로 이어졌다.

#### 순서 보장 트릭

Kafka에서 파티션 내 순서만 보장되므로 `aggregate_id`를 파티셔닝 키로 쓰면 **동일 주문에 대한 이벤트 순서는 보장**된다. 릴레이가 여러 인스턴스로 스케일 아웃할 때는 outbox 테이블을 `SELECT ... FOR UPDATE SKIP LOCKED` 로 잠그거나, aggregate_id 해시로 릴레이 워커를 샤딩한다. 이 처리를 안 하면 두 릴레이가 같은 row를 동시에 발행해 순서가 뒤바뀐다.

#### 언제 쓰고, 언제 쓰면 안 되는가

**쓸 때**
- 도메인 상태 변경이 반드시 다른 서비스로 전파되어야 하는 경우 (주문→재고→배송, 결제→정산→회계)
- Saga의 각 스텝에서 커맨드/이벤트 전송의 안전한 원자성이 필요할 때
- CDC 인프라가 있거나 도입 여력이 있을 때 — 그 순간 Outbox는 거의 공짜에 가까워진다

**쓰지 말아야 할 때**
- 이벤트가 유실되어도 상관없는 로그/메트릭성 신호 — 오히려 DB 부하만 만든다
- 단일 서비스 내부 이벤트로 도메인 이벤트가 소비되고 끝나는 경우 — Spring `ApplicationEventPublisher` + `@TransactionalEventListener(AFTER_COMMIT)` 정도로 충분
- Aggregate 하나의 커밋에서 100개씩 이벤트를 만드는 초고빈도 도메인 — outbox 테이블이 병목이 되면 로그 기반 이벤트 소싱(WAL을 이벤트로 직접 사용)을 검토

#### 함정 체크리스트

1. **`published_at`을 남기지 않고 delete로 처리** → 감사/재처리 불가. soft-mark 후 파티션 스위칭이나 배치 삭제로 정리.
2. **릴레이가 이벤트 직렬화를 직접 함** → 스키마 변경이 릴레이 배포에 묶인다. payload는 서비스가 완성해 넣고 릴레이는 그대로만 옮기게 한다.
3. **outbox 테이블에 인덱스 없음** → 폴링 쿼리가 풀스캔. 위 예시처럼 부분 인덱스 필수.
4. **트랜잭션 밖에서 outbox INSERT** → Outbox 패턴을 도입한 의미가 사라진다. 코드 리뷰 룰로 못박아야 한다.

> 💡 **왜 중요한가**: MSA에서 "DB에 저장했지만 이벤트는 못 보냈다"는 dual write 실패는 우아한 아키텍처를 무너뜨리는 가장 흔한 원인이며, Outbox는 이걸 로컬 트랜잭션 하나로 되돌려 놓는 사실상 유일한 표준 해법이다.
