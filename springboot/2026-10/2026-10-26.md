### `@Builder`를 Lombok으로 엔티티에 붙이면 **모든 필드를 받는 생성자가 자동으로 `public`이 된다** — JPA의 `protected` 기본 생성자 규약과 캡슐화가 동시에 무너진다

`@Builder`는 내부적으로 `@AllArgsConstructor`를 호출하는데, 접근 제어자를 지정하지 않으면 `public`으로 열린다. 그 결과 ID나 생성일시처럼 외부에서 절대 세팅되면 안 되는 필드까지 빌더로 주입 가능해져서, 테스트에서 편하게 쓰다가 실제 비즈니스 로직에서도 똑같이 쓰이기 시작한다. 해결책은 `@Builder(access = AccessLevel.PRIVATE)` + 정적 팩토리 메서드 조합, 또는 필드 레벨에 `@Builder.Default`와 함께 생성자를 명시적으로 제한하는 것.

```java
// ❌ 위험 — 외부에서 id, createdAt까지 다 넣을 수 있음
@Entity
@Builder
public class Order {
    @Id @GeneratedValue
    private Long id;
    private LocalDateTime createdAt;
    private String customerName;
}

// 어디선가 이런 코드가 가능해진다
Order.builder().id(999L).createdAt(LocalDateTime.MIN).customerName("x").build();

// ✅ 안전 — 빌더를 숨기고 의도된 팩토리만 노출
@Entity
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Order {
    @Id @GeneratedValue private Long id;
    private LocalDateTime createdAt;
    private String customerName;

    @Builder(access = AccessLevel.PRIVATE)
    private Order(String customerName) {
        this.customerName = customerName;
        this.createdAt = LocalDateTime.now();
    }

    public static Order place(String customerName) {
        return Order.builder().customerName(customerName).build();
    }
}
```

> 💡 **왜 중요한가**: "편의성"으로 붙인 어노테이션 하나가 도메인의 불변식을 뚫는 백도어가 되고, 테스트가 production 코드의 설계를 역으로 오염시킨다.

### `WebMvcTest`는 **`@Component`, `@Service`, `@Repository` 빈을 로드하지 않는다** — 그래서 컨트롤러 테스트가 "빠른" 것이고, 그래서 통합 테스트와 다른 버그를 숨긴다

`@WebMvcTest`는 MVC 레이어(`@Controller`, `@ControllerAdvice`, `Filter`, `HandlerInterceptor`, `WebMvcConfigurer`)만 스캔한다. 서비스 레이어는 전부 `@MockBean`으로 수동 주입해야 하고, 안 하면 `UnsatisfiedDependencyException`이 뜬다. 반대 이야기도 있다 — 글로벌하게 등록된 `@ControllerAdvice`는 자동 로드되지만, 특정 패키지에만 적용되는 Advice의 설정 클래스(`@Configuration`)는 로드되지 않아서 테스트에서는 예외 변환이 "조용히" 다르게 동작한다.

```java
// ❌ 함정 — ArgumentResolver가 서비스를 쓰는데 로드가 안 됨
@WebMvcTest(OrderController.class)
class OrderControllerTest {
    @Autowired MockMvc mvc;
    @MockBean OrderService orderService;
    // CurrentUserArgumentResolver가 UserService를 참조하면
    // UnsatisfiedDependencyException이 터진다
}

// ✅ 명시적으로 필요한 것을 선언
@WebMvcTest(controllers = OrderController.class)
@Import({CurrentUserArgumentResolver.class, GlobalExceptionHandler.class})
class OrderControllerTest {
    @Autowired MockMvc mvc;
    @MockBean OrderService orderService;
    @MockBean UserService userService; // ArgumentResolver가 쓰는 것
}
```

운영 환경과 테스트 환경의 격차는 보통 이런 "자동으로 로드되지 않는 설정"에서 나온다. 특히 `SecurityFilterChain`은 `@WebMvcTest`에서 자동 적용되는데, `spring-security-test`의 `@WithMockUser`를 안 쓰면 모든 요청이 401로 떨어져서 "컨트롤러 로직"을 전혀 못 본 채 테스트가 통과하는 함정이 생긴다.

> 💡 **왜 중요한가**: 테스트 슬라이스의 경계를 모르면 "로컬에선 통과, 프로덕션에선 터지는" 가장 흔한 패턴에 걸린다 — 특히 보안 필터와 예외 핸들러처럼 "눈에 안 보이는 미들웨어"에서.
