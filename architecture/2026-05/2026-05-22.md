### CQRS — "읽기와 쓰기는 같은 모델을 쓸 이유가 없다"는 급진적 분리

CQRS(Command Query Responsibility Segregation)는 **하나의 도메인 모델로 읽기와 쓰기를 모두 처리하려는 관성**을 깨는 패턴이다. 쓰기는 비즈니스 규칙과 불변식을 지키기 위해 정규화된 애그리게이트가 필요하지만, 읽기는 화면에 맞춰 조인 없이 즉시 뿌릴 수 있는 뷰가 필요하다. 이 두 요구가 실은 다른 문제라는 인식에서 CQRS는 출발한다. 쓰기 모델(Command)과 읽기 모델(Query)을 **물리적으로 다른 저장소**에 두고, 쓰기 이벤트로 읽기 모델을 갱신한다.

Lv2에서 배운 CRUD 리포지토리는 하나의 엔티티에 대해 `save()`와 `findAll()`이 공존한다. 이 구조는 도메인이 단순할 땐 편하지만, "주문 페이지에 노출할 20개 필드 중 15개가 다른 애그리게이트에서 온다"는 순간 무너진다. JPA로 풀려고 하면 fetch join 지옥, N+1, DTO 프로젝션이 뒤엉킨다. CQRS는 이 문제를 "읽기 전용 뷰 테이블을 미리 만들어 두자"로 해결한다.

```
┌─────────────────────────────────────────────────────────────┐
│                        Client                                │
└──────────────┬──────────────────────────┬───────────────────┘
       Command │ (POST/PUT/DELETE)  Query │ (GET)
               ▼                          ▼
      ┌────────────────┐        ┌────────────────────┐
      │  Write Model   │        │   Read Model       │
      │  (Aggregate)   │        │  (Materialized     │
      │  정규화 DB     │        │   View, Denormal.) │
      │  PostgreSQL    │        │  Elasticsearch/    │
      │                │        │  Redis/Read Replica│
      └───────┬────────┘        └─────────▲──────────┘
              │ Event                     │ Projection
              │ (OrderPlaced,             │ (읽기 모델 갱신)
              │  OrderShipped)            │
              ▼                           │
      ┌─────────────────────────────────────────────┐
      │     Event Bus (Kafka / Outbox 소비)         │
      └─────────────────────────────────────────────┘
```

핵심은 **읽기 모델은 항상 "결과적 일관성(eventual consistency)"** 이라는 점이다. 쓰기가 커밋된 뒤 이벤트를 발행하고, 프로젝터(Projector)가 이를 소비해 읽기 모델을 갱신하는 사이에 **수 밀리초~수 초의 지연**이 생긴다. 사용자가 주문을 넣고 바로 목록 페이지로 이동했을 때 자기 주문이 안 보일 수 있다. 이걸 UX로 감추거나(낙관적 렌더링), 클라이언트에 이벤트 버전을 반환해 폴링하도록 설계해야 한다.

**Event Sourcing 없이도 CQRS는 성립한다.** 흔한 오해가 "CQRS는 반드시 ES와 세트"라는 것인데, 쓰기 저장소는 여전히 상태 기반 정규화 테이블이어도 되고, 커밋 후 이벤트만 발행하면 된다. ES + CQRS 조합은 극단적 감사 요구가 있을 때만 쓴다. 대부분의 실무는 "정규화 RDB + 이벤트 발행 + 읽기 전용 뷰 저장소"로 충분하다.

**트레이드오프**:

| 관점 | 얻는 것 | 잃는 것 |
|------|---------|---------|
| 성능 | 읽기 요청이 조인·집계 없이 O(1). 읽기/쓰기 독립 스케일 | 저장소 이중화 비용, 프로젝터 인프라 |
| 모델 | 쓰기는 불변식에 집중, 읽기는 화면에 집중 | 개발자 인지 부담(모델 2벌) |
| 일관성 | 강한 일관성이 필요없는 조회에 최적 | Read-after-write 문제, 사용자 혼란 |
| 유연성 | 새 화면 = 새 프로젝션만 추가 | 프로젝션 재구축 시 이벤트 리플레이 필요 |

**실제 사례**:
- **넷플릭스 시청 이력**: 쓰기는 Cassandra(수십억 이벤트 append), 읽기는 별도 프로젝션으로 "최근 본 목록", "이어보기", "추천 학습용 특성"을 각각 만든다. 하나의 이벤트가 3개 이상의 읽기 뷰로 분기한다.
- **쿠팡 주문 조회**: 주문 도메인은 MySQL에 있지만, "내 주문 목록" 화면은 Elasticsearch 프로젝션에서 서빙한다. 상품명·배송상태·리뷰 여부까지 조인 없이 한 번에 나온다.
- **뱅크샐러드 자산 대시보드**: 계좌별 트랜잭션은 원장 DB에 정규화되어 있고, "이번 달 카테고리별 소비" 같은 대시보드 위젯은 각각의 프로젝션 테이블로 미리 계산된다.

**언제 쓰는가**:
- 읽기 대 쓰기 비율이 **10:1 이상**이고, 읽기 쿼리가 여러 애그리게이트를 가로지를 때
- 화면마다 요구하는 필드 조합이 크게 다를 때 (관리자 화면 vs 고객 화면)
- 이미 이벤트 드리븐 아키텍처가 있고 Outbox로 이벤트를 안정적으로 발행 중일 때

**언제 쓰면 안 되는가**:
- CRUD 애드민 화면, 사내 툴 — 복잡도만 늘고 얻는 게 없다
- Read-after-write 강한 일관성이 반드시 필요한 도메인(잔액, 재고 차감 결과) — 이건 쓰기 모델에서 직접 읽어야 한다
- 팀에 이벤트 발행/소비 운영 경험이 없을 때 — 프로젝션 재구축, 순서 보장, 재처리 실패 대응이 만만치 않다

**시니어 관점의 판단 기준**: CQRS는 "성능이 안 나와서" 도입하는 게 아니라 "**모델이 두 갈래로 자연스럽게 갈라지고 있는데 억지로 하나로 붙들고 있어서 코드가 뒤틀리기 시작할 때**" 도입하는 것이다. `OrderReadDto`, `OrderListView`, `OrderAdminProjection` 같은 클래스가 이미 5개 이상 늘어나 있고 각자 다른 쿼리를 짜고 있다면, 이미 CQRS를 하고 있는데 이름을 안 붙였을 뿐이다. 그때 정식으로 분리하면 된다.

> 💡 **왜 중요한가**: "하나의 도메인 모델이 모든 요구를 만족시켜야 한다"는 가정을 버리는 순간, 읽기 성능과 쓰기 무결성을 동시에 얻을 수 있다.
