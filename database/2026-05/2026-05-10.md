### PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)` — 예측 비용이 아닌 실제 I/O로 쿼리 진단하기

`EXPLAIN`만 쓰면 옵티마이저의 추정치만 보이지만, `ANALYZE`를 더하면 실제 실행 시간과 실제 row 수를 함께 볼 수 있고, `BUFFERS`까지 붙이면 각 노드에서 읽은 shared/temp 블록 수가 노출된다. `shared hit`이 많으면 캐시에서 잘 풀린 것이고 `shared read`가 폭증하면 디스크에서 끌어온 것이라, 추정 비용이 아닌 실제 병목 지점을 정확히 찾을 수 있다.

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT * FROM orders WHERE customer_id = 42 AND created_at > now() - interval '7 days';
```

> 💡 **왜 중요한가**: "추정 row 1건인데 실제 100만 건" 같은 통계 왜곡과 캐시 미스로 인한 지연을 동시에 잡아내, 인덱스 추가/통계 갱신 중 어떤 처방이 맞는지 판단할 수 있다.

### JPA `@Version` 낙관적 락(Optimistic Locking) — `SELECT ... FOR UPDATE` 없이 동시 수정 충돌 감지하기

엔티티에 `@Version private Long version;` 필드를 두면 Hibernate가 `UPDATE ... WHERE id = ? AND version = ?` 형태로 SQL을 만들고, 다른 트랜잭션이 먼저 커밋해서 버전이 바뀌면 `OptimisticLockException`이 터진다. 락을 잡지 않으므로 읽기 동시성을 막지 않고, 충돌이 드문 시나리오(주문 상태 변경, 프로필 수정 등)에서 비관적 락보다 훨씬 가볍다.

```java
@Entity
class Account {
    @Id Long id;
    @Version Long version;
    BigDecimal balance;
}
```

> 💡 **왜 중요한가**: 읽기 시점에 락을 걸지 않아 throughput이 높고, 잃어버린 갱신(lost update) 문제를 DB 레벨에서 안전하게 감지할 수 있어 분산/멀티 인스턴스 환경에서 특히 유용하다.
