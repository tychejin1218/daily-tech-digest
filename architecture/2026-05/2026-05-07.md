### Strangler Fig 패턴 — 레거시를 "덮어 죽이는" 방식으로 MSA 전환하기

10년 된 모놀리스를 MSA로 바꾸라는 지시를 받았을 때, 신입은 "리라이트"를 떠올리고 시니어는 "리라이트만은 절대 안 된다"고 답한다. Netflix가 2008년 DB 데이터 손상 사고 이후 7년에 걸쳐 AWS로 이전한 방식, Amazon이 Obidos 모놀리스에서 서비스 지향으로 넘어간 방식, Shopify가 여전히 부분적으로 사용 중인 방식 — 이 모두의 공통 이름이 **Strangler Fig(교살무화과)** 다. Martin Fowler가 호주 열대우림에서 숙주 나무를 감싸고 자라 결국 죽여버리는 무화과나무를 보고 붙인 이름으로, 핵심은 **"레거시를 멈추지 않고, 그 위를 감싸 자라나며, 마지막에 안쪽이 비어도 무너지지 않는 상태로 만든다"** 는 점이다.

```
[Phase 0: 모놀리스]        [Phase 1: 프록시 삽입]       [Phase 2: 부분 이관]
                                                       
   ┌──────────────┐        ┌──────────────┐          ┌──────────────┐
   │              │        │  Facade/     │          │  Facade/     │
   │              │        │  Router      │          │  Router      │
   │  Monolith    │◄──     │  (Nginx/GW)  │◄──       │  (Nginx/GW)  │
   │              │        └──────┬───────┘          └──┬────────┬──┘
   │  All logic   │               │                     │        │
   │              │               ▼                     ▼        ▼
   └──────────────┘        ┌──────────────┐      ┌──────────┐ ┌────────┐
                           │  Monolith    │      │ Monolith │ │ Order  │
                           │  (unchanged) │      │ (-Order) │ │ Svc    │
                           └──────────────┘      └──────────┘ └────────┘

[Phase 3: 지속 이관]                        [Phase N: 모놀리스 소멸]
                                             
   ┌──────────────┐                          ┌──────────────┐
   │  Facade      │                          │  API Gateway │
   └──┬─┬─┬─┬─┬───┘                          └─┬─┬─┬─┬─┬────┘
      │ │ │ │ │                                │ │ │ │ │
      ▼ ▼ ▼ ▼ ▼                                ▼ ▼ ▼ ▼ ▼
    Order Pay User ...Monolith(잔여)         모든 도메인 서비스
                     (관리자 페이지 정도만)  (레거시 폐기됨)
```

#### 왜 리라이트가 아니라 Strangler Fig인가

리라이트는 **"현재 시스템을 완벽히 이해했다"** 는 오만한 전제 위에 선다. 실제로는 다음이 모두 실패한다.

1. **비즈니스는 멈추지 않는다** — 2년짜리 리라이트 도중에도 결제 정책은 매달 바뀐다. 두 코드베이스를 동시에 유지하다 지친 팀은 리라이트를 포기한다(Netscape Navigator, Basecamp Classic 등이 겪은 실패).
2. **암묵지가 코드에 박혀 있다** — "왜 이 if 문이 있지?" 하고 지웠다가 5년 전 특정 파트너사 계약 조항이 무너진다.
3. **"완성될 때까지 배포 불가"는 피드백을 죽인다** — 실사용자의 반응 없이 만든 시스템은 반드시 틀린다.

Strangler Fig는 반대로 간다. **매주 조금씩 배포되고, 매주 실제 트래픽을 받고, 언제든 롤백된다.** 2년 뒤 완성이 아니라, 다음 주에도 가치가 나온다.

#### 실전 진행 단계

**1단계: Facade 삽입** — 클라이언트와 모놀리스 사이에 프록시 계층(Nginx, API Gateway, 혹은 Backend-for-Frontend)을 넣는다. 아직 모든 요청은 그대로 모놀리스로 흘러간다. 이 단계가 없으면 나머지가 시작될 수 없다.

**2단계: "가장자리부터" 절단** — 처음 뽑아낼 서비스는 반드시 **의존성이 얕은 리프(leaf) 도메인**이어야 한다. 알림, 이미지 리사이징, 검색 색인처럼 남에게 의존하지만 남이 의존하지 않는 것. 결제나 사용자 인증부터 손대는 팀은 6개월 안에 되돌아온다.

**3단계: 데이터 이관 전략 결정** — 여기가 진짜 함정이다. 세 가지 선택지 중 하나여야 한다.
- **읽기 분리만 먼저** — 새 서비스가 모놀리스 DB를 read-only로 붙고, 쓰기는 계속 모놀리스가. 리스크는 낮지만 진짜 분리는 아니다.
- **CDC로 양방향 동기화** — Debezium 등으로 모놀리스 DB의 변경을 새 서비스로 스트리밍. 이중 쓰기(dual write) 함정을 피하고 [[outbox-pattern]] 원칙과 결이 같다.
- **한 방향으로 소유권 이관** — 쓰기 권한이 특정 시점에 새 서비스로 완전히 넘어간다. 가장 깨끗하지만 다운타임 계획이 필요.

**4단계: 트래픽 점진 전환** — Facade에서 특정 엔드포인트, 특정 사용자 비율, 특정 지역부터 새 서비스로 라우팅. Feature flag + [[idempotency-design]] 이 있어야 안전하게 되돌릴 수 있다.

**5단계: 검증 & 폐기** — Shadow traffic(모놀리스와 새 서비스에 동시 호출 후 결과 비교), 이후 코드 삭제. **"삭제"** 가 이 패턴의 완성이다. 이 단계를 건너뛴 팀은 2배의 시스템을 영원히 운영한다.

#### 트레이드오프 — 시니어가 알아야 할 것

| 축 | Strangler Fig | 리라이트(Big Bang) |
|---|---|---|
| 리스크 | 낮음, 롤백 가능 | 극도로 높음 |
| 총 소요 기간 | 김 (2~5년) | 계획상 짧음, 실제로는 더 김 |
| 조직 부담 | 지속적 컨텍스트 스위칭 | 병렬 팀 필요, 협업 붕괴 |
| 성과 가시성 | 매주 | 프로젝트 종료 시(가끔은 영영 없음) |
| 최종 아키텍처 자유도 | 레거시 제약이 어느 정도 남음 | 백지에서 설계 가능(단, 도달 확률 낮음) |

**Strangler Fig의 진짜 비용은 "동시에 두 시스템을 이해해야 하는 개발자의 인지 부담"** 이다. 이걸 견디는 유일한 방법은 **Facade 계층에서 이관 상태를 코드가 아니라 설정(라우팅 룰)으로 표현**하는 것이다. `if (feature.flag.newOrderSvc)`가 코드 곳곳에 흩어지는 순간 팀은 무너진다.

#### 언제 쓰고 언제 쓰면 안 되는가

**써야 한다면:**
- 시스템이 **살아있는 상태로** 계속 매출을 만들고 있다
- 변경이 리스크 큰 부분과 안전한 부분으로 **자연스레 나뉜다**
- 조직이 최소 1~2년의 인내심을 가질 수 있다
- 이미 CI/CD, 관측성, [[idempotency-design]] 기반이 있다

**쓰지 말아야 한다면:**
- 모놀리스가 이미 죽어가고, 어차피 사용자가 별로 없다 → 그냥 새로 짜라
- 도메인이 5년 안에 완전히 뒤집힐 예정이다 → 이관에 쓰는 시간이 낭비
- **팀에 도메인 이해가 없다** → 어떤 조각부터 뽑아야 할지 모르는 상태로 시작하면 무작위 조각을 뽑게 되고, 그건 리라이트보다 나쁘다
- Facade 계층을 넣을 조직적 권한이 없다(예: 인프라 팀이 협조 안 함) → 시작 자체가 불가능

#### 실제 사례의 교훈

- **Netflix**는 2008년 대규모 DB 손상 사고 이후 "모놀리스 위에 새 API를 얹고, 오래된 것부터 하나씩 죽인다"는 전략으로 7년을 갔다. 완성 시점을 미리 발표하지 않은 것이 성공의 열쇠였다.
- **Amazon**은 유명한 2002년 Bezos의 "모든 팀은 서비스 인터페이스로만 소통하라" 명령 이후에도, 실제로는 서비스 하나 뽑아내는 데 수개월씩 걸리는 Strangler Fig 방식으로 진행했다.
- **국내 커머스 A사**는 반대로 "1년 안에 MSA 전환 완료" 목표를 세웠다가 18개월 뒤 원복했다. 이유: 결제부터 손댔고, Facade가 없어 클라이언트별로 이관 상태가 달랐다.

시니어의 결론: **Strangler Fig는 기술 패턴이 아니라 조직 패턴이다.** 코드보다 라우팅 설정, 라우팅 설정보다 소유권 이관 결정, 그리고 무엇보다 "**폐기까지 완주할 조직의 인내**"가 이 패턴의 진짜 자산이다.

> 💡 **왜 중요한가**: 레거시 시스템의 MSA 전환은 리라이트가 아니라 "매주 배포되며 서서히 죽어가는 이관"으로만 성공한다 — Strangler Fig는 그 유일하게 검증된 조직적 전략이다.
