### Database Tip 1: MySQL `Online DDL`의 `ALGORITHM=INSTANT` — 수백 GB 테이블에 컬럼을 "0.01초"에 추가하는 메타데이터 조작의 마법

MySQL 8.0부터 `ALTER TABLE ... ADD COLUMN ... ALGORITHM=INSTANT`는 실제 데이터 페이지를 건드리지 않고 데이터 사전(`data dictionary`)의 메타데이터만 수정해 DDL을 끝낸다. INPLACE 알고리즘이 테이블 전체를 재구성하며 몇 시간 동안 쓰기를 잠그는 동안, INSTANT는 수백 GB 테이블에도 0.01초 만에 완료되고 커넥션 블로킹도 없다. 단, 컬럼은 반드시 테이블 "끝"에 추가되어야 하고(`AFTER` 지정 금지), `NOT NULL` 컬럼은 기본값이 있어야 하며, 테이블당 INSTANT ADD 횟수에 상한(기본 64)이 있다는 숨은 제약이 있다.

> 💡 **왜 중요한가**: "컬럼 하나 추가하는데 서비스를 2시간 멈춰야 한다"는 운영 지옥이, 알고리즘 한 줄로 즉시 사라진다. 단 제약을 모르면 자동으로 INPLACE로 fallback되어 똑같이 멈춘다.

### Database Tip 2: JPA `@DynamicUpdate`와 `@DynamicInsert` — 변경되지 않은 컬럼까지 UPDATE 문에 끌고 가는 Hibernate의 숨은 낭비

Hibernate는 기본적으로 엔티티의 UPDATE 쿼리를 애플리케이션 시작 시점에 "모든 컬럼"으로 미리 캐싱해둔다. 즉, 50개 컬럼 중 1개만 바꿔도 `UPDATE user SET name=?, email=?, address=?, ... WHERE id=?`가 날아가 네트워크·바이너리 로그·레플리케이션 트래픽을 통째로 잡아먹고, 실수로 다른 컬럼의 Dirty Checking 스냅샷이 깨지면 멀쩡한 값을 자기 자신으로 덮어쓴다. `@DynamicUpdate`를 붙이면 Hibernate가 매 UPDATE마다 실제로 변경된 컬럼만 포함한 쿼리를 동적으로 생성해, 특히 `BLOB`/`TEXT`/`JSON` 컬럼이 섞인 와이드 테이블에서 극적인 성능·네트워크 절감 효과를 낸다.

> 💡 **왜 중요한가**: PreparedStatement 캐시 재사용률은 떨어지지만, 와이드 테이블에서는 "매번 전체 컬럼을 네트워크로 보내는 비용"이 훨씬 크다. 특히 레플리케이션 지연과 바이너리 로그 폭증의 숨은 범인이 바로 이 기본값이다.
