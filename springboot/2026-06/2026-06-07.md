### `@DynamicPropertySource`로 Testcontainers 컨테이너 포트를 스프링 프로퍼티에 동적으로 주입하기

Testcontainers는 매 테스트 실행마다 랜덤 포트로 컨테이너를 띄우기 때문에 `application.yml`에 하드코딩된 `spring.datasource.url`로는 접속이 불가능하다. `@DynamicPropertySource`가 붙은 static 메서드는 `ApplicationContext` 초기화 직전에 실행되어 컨테이너의 실제 JDBC URL·포트·자격증명을 스프링 환경으로 밀어 넣을 수 있고, `DynamicPropertyRegistry`가 `Supplier`를 받기 때문에 컨테이너가 lazy하게 시작되어도 안전하다.

```java
@SpringBootTest
@Testcontainers
class OrderRepositoryIT {
    @Container
    static PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>("postgres:16-alpine");

    @DynamicPropertySource
    static void registerProps(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }
}
```

> 💡 **왜 중요한가**: `@TestPropertySource`나 `application-test.yml`은 값이 고정되어 랜덤 포트를 쓰는 컨테이너와 근본적으로 호환되지 않는다.

### `HandlerInterceptor`의 `preHandle`에서 `HandlerMethod` 캐스팅 전 반드시 타입 체크가 필요한 이유

인터셉터는 컨트롤러 핸들러뿐 아니라 정적 리소스 요청(`ResourceHttpRequestHandler`)이나 존재하지 않는 경로에도 호출되므로, `(HandlerMethod) handler`로 무조건 캐스팅하면 `ClassCastException`이 발생한다. 특히 SpringDoc·Swagger UI를 함께 쓰는 프로젝트에서 `/swagger-ui/**` 요청이 인터셉터를 통과하며 이 문제가 자주 터진다.

```java
@Override
public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
    if (!(handler instanceof HandlerMethod handlerMethod)) {
        return true;  // 정적 리소스 등은 통과
    }
    RequireRole annotation = handlerMethod.getMethodAnnotation(RequireRole.class);
    // ... 권한 체크 로직
    return true;
}
```

> 💡 **왜 중요한가**: 인터셉터의 `handler` 파라미터 타입이 `Object`인 데는 이유가 있으며, 캐스팅 전 `instanceof` 검사가 프로덕션 500 에러를 막는 최소 방어선이다.
