### `@Async`는 **같은 클래스 내부 호출에서 동작하지 않는다** — 그리고 반환 타입이 `void`면 예외가 조용히 삼켜진다

`@Async`도 `@Transactional`과 똑같이 프록시 기반 AOP라서, 같은 빈 내부에서 `this.asyncMethod()`로 호출하면 프록시를 거치지 않고 그냥 동기 실행된다. 더 치명적인 건 반환 타입이 `void`일 때인데, 비동기 스레드에서 터진 예외는 호출자에게 전파되지 않고 로그조차 남지 않는다 — 반드시 `CompletableFuture<T>`로 반환하거나 `AsyncUncaughtExceptionHandler`를 등록해야 한다.

```
Controller ──> OrderService.placeOrder()
                     │
                     ├─ this.sendEmail()  ❌ 프록시 우회, 동기 실행
                     │
                     └─ emailService.send() ✅ 다른 빈 → 프록시 → 비동기
                                │
                                └─ void 반환 + 예외 → 🔇 조용히 사라짐
```

실무 사례: 주문 완료 후 이메일 발송을 `@Async`로 돌렸는데, 같은 서비스 내부 호출이라 트랜잭션이 끝나기 전에 동기 실행됐다. DB에 커밋도 안 된 주문 ID로 이메일 쿼리를 날려 "주문을 찾을 수 없다"는 알림이 고객에게 발송된 사건이 있었다. 트레이드오프: 별도 빈으로 분리하면 깔끔하지만 작은 서비스에서는 과한 구조가 되고, `AopContext.currentProxy()`로 우회할 수 있지만 `exposeProxy=true` 설정이 필요하며 테스트가 복잡해진다.

> 💡 **왜 중요한가**: 비동기 작업이 "조용히 실패"하는 건 운영 환경에서 가장 추적하기 어려운 종류의 버그다 — 로그도 없고, 알림도 없고, 사용자만 기능이 안 된다고 CS에 전화한다.

### `@ConfigurationProperties`의 바인딩은 **setter가 있어야 동작한다** — 하지만 `@ConstructorBinding`을 쓰면 불변 객체가 된다

`@Value`로 설정값을 하나씩 주입받는 방식은 타입 안전성도 없고 묶음 검증(`@Validated`)도 안 되는 반면, `@ConfigurationProperties`는 `application.yml`의 계층 구조를 그대로 객체로 바인딩한다. 다만 Spring Boot 2.x까지는 반드시 setter가 필요해 불변성이 깨졌는데, Spring Boot 3.x에서는 생성자 바인딩이 기본이라 `record`나 `final` 필드로 완전한 불변 설정 객체를 만들 수 있다.

```
application.yml                 →  AppProperties.java
─────────────────────────────       ──────────────────────────────
app:                                @ConfigurationProperties("app")
  retry:                            public record AppProperties(
    max-attempts: 3                     RetryConfig retry,
    backoff-ms: 500                     CacheConfig cache
  cache:                              ) {}
    ttl: 60s                        
    size: 1000                      // kebab-case → camelCase 자동 변환
                                    // Duration/DataSize 등 특수 타입 지원
```

실무 팁: `@Validated`와 함께 쓰면 애플리케이션 시작 시점에 설정값 검증이 실패해 **배포가 롤백**된다 — 잘못된 설정으로 서비스가 뜬 뒤 트래픽 받다가 터지는 것보다 훨씬 안전하다. 또한 `Duration`, `DataSize`, `List<T>`, `Map<K,V>`를 네이티브로 바인딩해주기 때문에 `"500ms"`, `"10MB"` 같은 사람이 읽는 포맷을 그대로 쓸 수 있다. 트레이드오프: 설정 하나 추가할 때마다 클래스를 수정해야 해서 피드백 루프가 약간 느리지만, 그 대가로 IDE 자동완성과 컴파일 타임 안전성을 얻는다.

> 💡 **왜 중요한가**: 설정 오류로 인한 장애의 70%는 "오타"가 아니라 "타입/구조 불일치"다 — `@Value("${app.retry.maxAttempt}")` (오타)는 런타임에 null이 되지만, 생성자 바인딩은 시작 즉시 터진다.
