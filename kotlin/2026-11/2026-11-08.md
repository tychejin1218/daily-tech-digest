### 1. `reified` 제네릭: "런타임에 사라지는 타입"을 되살리는 inline의 비밀 무기

Java의 제네릭은 컴파일 후 타입이 지워져(type erasure) `T::class.java` 같은 호출이 불가능하지만, Kotlin은 `inline fun <reified T>`로 람다와 함께 타입 정보까지 바이트코드에 박아 넣는다. 덕분에 `objectMapper.readValue<User>(json)`처럼 `Class<T>`를 인자로 넘기지 않고도 역직렬화가 가능하고, `fragment.arguments<MyArgs>()` 같은 깔끔한 API를 만들 수 있다. 단, `reified`는 반드시 `inline` 함수와 짝을 이뤄야 하며, 런타임에 동적으로 결정되는 타입에는 사용할 수 없다.

```kotlin
// Before: Java 스타일, Class<T>를 명시적으로 넘겨야 함
fun <T> parse(json: String, clazz: Class<T>): T = mapper.readValue(json, clazz)
val user = parse(json, User::class.java)

// After: reified로 타입을 추론
inline fun <reified T> parse(json: String): T = mapper.readValue(json, T::class.java)
val user = parse<User>(json)  // 또는 val user: User = parse(json)
```

> 💡 **왜 중요한가**: Jackson, Retrofit, Koin 등 "타입 기반 DI/직렬화" 라이브러리의 Kotlin DSL이 자연스러운 이유가 바로 `reified`이며, 이걸 알아야 직접 라이브러리를 Kotlin-friendly하게 설계할 수 있다.

### 2. `companion object`는 "Java의 static이 아니다": 왜 Kotlin은 더 돌아가는 길을 택했나

Java의 `static`은 클래스에 묶인 전역 함수지만, Kotlin의 `companion object`는 **외부 클래스 안에 존재하는 싱글턴 객체**다. 즉 `User.create()`는 사실 `User.Companion.create()`의 축약형이며, Companion 자체가 인터페이스를 구현하거나 확장 함수를 받을 수 있는 **일급 객체**다. 이 차이 때문에 Spring의 `@JvmStatic` 없이 Java에서 호출하면 `User.Companion.create()`로 어색해지고, Mockito로 static mocking을 할 때도 Java의 static과 다르게 동작한다.

```kotlin
class UserService {
    companion object Factory : Logger {   // 인터페이스 구현 가능!
        @JvmStatic  // Java 상호운용: User.create() 형태로 호출 가능
        fun create(name: String) = UserService()
        
        const val MAX_RETRY = 3  // 진짜 static final 상수
    }
}

// Kotlin에서: UserService.create()
// Java에서 @JvmStatic 없으면: UserService.Factory.create() 또는 UserService.Companion.create()
```

> 💡 **왜 중요한가**: "Java 개발자가 Kotlin으로 넘어와서 가장 많이 실수하는 지점"이자, Spring Boot + Kotlin에서 `@JvmStatic`, `const val`, `@JvmField`를 언제 붙여야 하는지 판단하는 기준이 된다.
