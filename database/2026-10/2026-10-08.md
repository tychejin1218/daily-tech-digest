### Database Tip 1: MySQL `innodb_file_per_table` — 테이블 하나당 하나의 파일, 공간 회수와 백업 유연성의 토대

InnoDB는 기본값으로 각 테이블(과 인덱스)을 독립된 `.ibd` 파일에 저장하는데, 이 설정이 꺼져 있으면 모든 데이터가 `ibdata1` 공유 테이블스페이스에 뭉쳐 들어가 한번 커지면 다시 줄어들지 않는다. `innodb_file_per_table=ON` 상태에서는 `DROP TABLE`이나 `TRUNCATE`가 실제로 디스크 공간을 OS에 반환하며, `ALTER TABLE ... TABLESPACE`로 테이블 단위 이동/백업/복사가 가능해진다. 운영 중 "디스크는 비었는데 `ibdata1`만 100GB"인 비극은 거의 대부분 이 플래그의 과거 OFF 설정에서 비롯된다.

```sql
-- 현재 상태 확인
SHOW VARIABLES LIKE 'innodb_file_per_table';

-- 테이블별 실제 파일 크기 확인 (data_length + index_length는 메타데이터 기준)
SELECT 
    table_name,
    ROUND(data_length/1024/1024, 2) AS data_mb,
    ROUND(index_length/1024/1024, 2) AS index_mb,
    ROUND(data_free/1024/1024, 2) AS free_mb  -- 회수 가능한 조각화 공간
FROM information_schema.tables 
WHERE table_schema = 'mydb'
ORDER BY data_length DESC;

-- 조각화된 공간 회수 (테이블 재구축)
OPTIMIZE TABLE orders;  -- 또는 ALTER TABLE orders ENGINE=InnoDB;
```

**결정적인 함정**: `DELETE`로 수억 건 지워도 `.ibd` 파일 크기는 그대로다. InnoDB는 지운 자리를 "재사용 가능한 공간"으로만 표시하지, OS에 반환하지 않는다. `data_free` 컬럼이 수십 GB를 가리키는데 디스크는 계속 꽉 차 있다면 `OPTIMIZE TABLE` 또는 `pt-online-schema-change`로 재구축해야 비로소 회수된다.

> 💡 **왜 중요한가**: 디스크 공간 회수, 테이블 단위 이식성, 백업 전략의 유연성이 모두 이 하나의 설정에서 출발하기 때문에 — "왜 지웠는데 안 줄어들죠?"의 90%는 여기서 끝난다.

### Database Tip 2: JPA `@BatchSize` — N+1을 "N개"가 아닌 "N/batchSize개" 쿼리로 압축하는 중도적 해법

Lazy 로딩이 N+1을 일으킬 때 `Fetch Join`은 카티션 곱과 페이지네이션 깨짐 문제가 있고, `@EntityGraph`도 OneToMany 두 개 이상에서는 한계가 있다. 반면 `@BatchSize`는 Lazy를 유지하되 "같은 종류의 Lazy 참조가 N개 쌓이면, IN절로 묶어서 한 번에 조회"하는 전략을 쓴다. 1000개 주문의 회원을 각각 조회하던 쿼리가 `batchSize=100`이면 10번의 `WHERE member_id IN (?, ?, ..., ?)` 쿼리로 줄어든다.

```java
@Entity
public class Order {
    @ManyToOne(fetch = FetchType.LAZY)
    @BatchSize(size = 100)  // 엔티티 레벨 대신 필드 레벨에 선언
    private Member member;
    
    @OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
    @BatchSize(size = 100)  // 컬렉션에도 적용 가능
    private List<OrderItem> items;
}

// 또는 글로벌 설정 (application.yml)
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 100  // 모든 Lazy 참조에 일괄 적용
```

**실행 결과 비교** (주문 1000개 조회 → 회원 접근):
```
@BatchSize 없음:    SELECT ... FROM member WHERE id = ?  × 1000번
@BatchSize(100):   SELECT ... FROM member WHERE id IN (?, ... 100개)  × 10번
```

**선택 기준**:
| 상황 | 권장 방법 |
|------|-----------|
| ToOne 1개 + 페이지네이션 X | `Fetch Join` |
| ToOne + ToMany 1개 | `@EntityGraph` 또는 `Fetch Join` |
| 페이지네이션 + ToMany | `@BatchSize` (Fetch Join 금지) |
| ToMany 2개 이상 | `@BatchSize` 거의 유일한 답 |

**함정**: `batchSize`를 1000 이상으로 과하게 올리면 Oracle의 `IN절 1000개 제한`에 걸리거나, MySQL의 쿼리 플랜이 비효율적으로 바뀔 수 있다. 보통 **100~500 사이**가 안전지대이며, Hibernate 6부터는 `IN` 대신 `ARRAY` 바인딩으로 더 똑똑하게 처리한다.

> 💡 **왜 중요한가**: Fetch Join이 쓸 수 없는 상황(페이지네이션, 다중 Collection)에서 N+1을 현실적으로 압축할 수 있는 "유일한 중도적 무기"이기 때문에 — 선택이 아니라 생존 도구다.
