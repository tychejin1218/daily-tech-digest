### LLM Gateway 패턴 — "OpenAI SDK 직접 호출하면 되지"라는 순진함, 그리고 GPT-4o Azure US-East 리전이 4시간 39분 다운된 새벽 서비스 12개가 동시에 죽었는데 각 팀이 자기 코드에 하드코딩한 API 키와 재시도 로직을 뜯어고치는 데만 6시간이 걸려 CTO가 "우리 회사에 LLM 통합 담당자가 12명이나 있었네?"라고 임원 회의에서 씁쓸하게 웃은 새벽

---

#### "SDK 직접 호출"이 왜 지옥이 되는가

주니어의 코드:

```python
from openai import OpenAI
client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))

response = client.chat.completions.create(
    model="gpt-4o",
    messages=[...],
)
```

이 코드는 PoC에서는 완벽하다. 문제는 이게 12개 마이크로서비스, 40명의 개발자, 6개월 뒤의 시점이다.

시니어가 이 코드를 보면 즉시 7가지 지뢰가 보인다:

1. **모델 교체 시 12개 서비스 배포** — GPT-4o가 GPT-5로 갈아엎어질 때
2. **Provider 장애 시 개별 서비스마다 fallback 코드 필요** — Azure US-East 다운
3. **비용 추적 불가** — 어느 서비스가 어느 프롬프트로 얼마 쓰는지 아무도 모름
4. **Rate Limit이 서비스마다 다르게 걸림** — 5개 서비스가 동시에 429를 만남
5. **PII 마스킹이 각 팀 재량** — 어떤 팀은 하고, 어떤 팀은 안 하고
6. **A/B 테스트 불가** — 새 모델을 부분 트래픽에 태우려면 12곳을 배포
7. **감사 로그 파편화** — 금감원이 "지난 3월 이 답변의 원본 프롬프트 주세요" 요청 시

이 7개 중 하나만 터져도 새벽 3시 콜이 온다. 12개가 다 잠재해 있다.

---

#### LLM Gateway의 정체 — "LLM 콜을 위한 API Gateway"

전통 아키텍처에서 API Gateway가 뭘 했는지 떠올려보라: 인증, Rate Limit, 라우팅, 관측, 캐싱, 요청 변환. **LLM Gateway는 이걸 LLM 호출 계층에서 다시 하는 것**이다. 다만 도메인 특성상 추가되는 게 많다.

```
┌──────────────────────────────────────────────────────────────────┐
│                    Application Services                          │
│   [ChatBot]  [Summarizer]  [Classifier]  [Agent-1] [Agent-2]     │
└────────────────────────┬─────────────────────────────────────────┘
                         │ OpenAI-compatible protocol
                         │ (기존 SDK 그대로 씀)
                         ▼
        ┌────────────────────────────────────┐
        │         LLM Gateway                │
        │  ┌──────────────────────────────┐  │
        │  │  1. Auth & Tenant Isolation  │  │
        │  ├──────────────────────────────┤  │
        │  │  2. PII Redaction (Pre)      │  │
        │  ├──────────────────────────────┤  │
        │  │  3. Semantic Cache Lookup    │──┼──► Redis/Cache
        │  ├──────────────────────────────┤  │
        │  │  4. Prompt Registry Fetch    │──┼──► Prompt Store
        │  ├──────────────────────────────┤  │
        │  │  5. Routing Rule Engine      │  │
        │  │     - Model alias resolve    │  │
        │  │     - Cost-based routing     │  │
        │  │     - A/B split              │  │
        │  ├──────────────────────────────┤  │
        │  │  6. Rate Limit / Quota       │  │
        │  ├──────────────────────────────┤  │
        │  │  7. Guardrail (Pre)          │  │
        │  ├──────────────────────────────┤  │
        │  │  8. Provider Adapter         │  │
        │  └───┬──────────┬───────┬───────┘  │
        │      │          │       │          │
        │  Fallback Chain │       │          │
        │  Circuit Breaker│       │          │
        └──────┼──────────┼───────┼──────────┘
               ▼          ▼       ▼
          [Azure OAI] [Bedrock] [Vertex] [자체 vLLM]
               │          │       │
        ┌──────┼──────────┼───────┼──────────┐
        │  9. Response Guardrail (Post)      │
        │ 10. PII Redaction (Post)           │
        │ 11. Trace Emit (LangFuse/OTel)     │
        │ 12. Cost Ledger Write              │
        │ 13. Semantic Cache Write           │
        └────────────────────────────────────┘
```

핵심은 **OpenAI-compatible protocol**을 유지하는 것이다. 애플리케이션은 자기가 게이트웨이를 부르는지 OpenAI를 직접 부르는지 몰라야 한다. 그래야 도입 저항이 사라진다.

---

#### 4가지 핵심 책임 (시니어가 반드시 이해할 것)

##### ① Model Alias Layer — "gpt-4o"가 아니라 "chat-premium"

애플리케이션 코드는 **논리적 별칭(alias)** 만 쓴다.

```python
# ❌ Bad
model="gpt-4o"

# ✅ Good
model="chat-premium"   # gateway가 alias → 실물 모델로 해석
```

Gateway 설정:

```yaml
aliases:
  chat-premium:
    primary: azure/gpt-4o-2024-08-06
    fallback:
      - bedrock/claude-3-5-sonnet-20241022
      - openai/gpt-4o-2024-08-06
    ab_split:
      - model: azure/gpt-4o-mini
        weight: 5   # 5% 트래픽으로 성능 관측
```

이 한 겹으로 **모델 교체가 배포에서 설정 변경으로 격하**된다. GPT-4o → GPT-5 갈아엎기가 12개 서비스 배포 → 게이트웨이 config 한 줄로 바뀐다. 이게 이 패턴의 가장 큰 ROI다.

##### ② Fallback Chain & Circuit Breaker

Provider는 반드시 죽는다. 2023년 11월 OpenAI 12시간 다운, 2024년 6월 Azure OAI EU-West 6시간 다운, 2025년 2월 Anthropic Bedrock US-East 3시간 다운 — 시니어라면 이걸 다 겪었다.

Fallback 규칙은 단순히 "primary 실패 시 secondary"가 아니다:

| 오류 유형 | 대응 |
|----------|------|
| `429 Rate Limit` | 즉시 secondary provider로 fallback |
| `503 Service Unavailable` | Circuit Breaker Open → 30초 secondary |
| `500 Internal` | 재시도 1회 후 fallback |
| `context_length_exceeded` | **fallback 금지** (재요청해도 같은 결과) |
| `content_filter` | **fallback 금지** (정책 우회 위험) |
| Timeout | 재시도 1회 후 fallback |

특히 **content filter 오류에 fallback을 걸면 안 된다**는 게 시니어의 감각이다. Azure가 거부한 요청을 Bedrock으로 우회하면 안전 정책을 뚫는 게이트웨이가 되어버린다.

##### ③ Cost Governance — CFO가 물어보기 전에 답을 만들어놔라

각 요청마다 4가지가 span에 태그되어야 한다:

- `tenant_id` (어느 팀/고객)
- `feature_id` (어느 기능, ex. `summarizer.v3`)
- `prompt_version` (어느 프롬프트 버전)
- `model` (실제 라우팅된 모델)

이 4개가 있으면 나중에 CFO가 "지난달 GPT-4o 청구서 $84,000 어디서 나온 거지?"를 물었을 때 **10분 안에** 답이 나온다. 없으면 3주간 로그 파싱하다가 결국 못 찾는다.

##### ④ Streaming Passthrough

여기서 많은 게이트웨이가 넘어진다. LLM 응답은 SSE(Server-Sent Events) 스트림이다. 게이트웨이가 응답을 다 받은 뒤 넘겨주면 UX가 무너진다 (첫 토큰까지 15초 대기).

시니어의 답: **스트림은 통과시키되, 각 청크를 tap해서 usage/cost/guardrail을 백그라운드에서 처리**한다. 사용자 UX는 건드리지 않고, 최종 chunk가 오면 `finish_reason`과 `usage`를 잡아 ledger에 기록한다.

#### 실제 사례

##### 사례 1: **Uber GenAI Gateway** (2024 tech blog)

Uber는 초기에 각 팀이 OpenAI/Vertex/Anthropic을 자유롭게 붙였다. 6개월 뒤 결과: **비용 추적 불가, 컴플라이언스 감사 실패, 재해복구 없음**. 2024년 GenAI Gateway를 사내 표준으로 강제했고, 모든 LLM 호출이 이 게이트웨이를 통과하도록 API Gateway 레벨에서 차단했다. 도입 3개월 만에 월 LLM 비용을 **23%** 줄였다. 원인은 A/B 라우팅으로 저비용 모델이 충분한 태스크를 자동 라우팅한 것.

##### 사례 2: **LiteLLM Proxy** (오픈소스, 2023~)

100+ Provider를 OpenAI 프로토콜로 통일한 오픈소스. 국내 스타트업들이 가장 많이 쓴다. 다만 **엔터프라이즈 요구사항(감사 로그, PII 마스킹, SSO)이 약해서** 규모가 커지면 자체 게이트웨이로 갈아탄다. "PoC는 LiteLLM, 프로덕션은 자체 구축"이 국내 시니어들의 정석 답변이 되어가고 있다.

##### 사례 3: **Portkey / Kong AI Gateway** (2024~)

Portkey는 SaaS로, Kong은 자기네 API Gateway에 AI 플러그인을 붙였다. **기존 API Gateway 팀이 있는 회사는 Kong AI가 편하다** (운영 도구·모니터링·SSO를 재활용). API Gateway 팀이 없는 스타트업은 Portkey SaaS가 빠르다.

##### 사례 4: **국내 F 금융지주 (2025)** — Big Bang 도입의 대가

Gateway 없이 12개 계열사 챗봇이 각자 OpenAI 직접 호출로 6개월 운영. 금감원 감사에서 "지난 4월 15일 03:17에 A 고객에게 나간 답변의 원본 프롬프트를 30분 안에 제출하라" 요구를 받았고 **불가능하다는 답을 하는 순간 감독 강도가 3단계 격상**됐다. 그 다음 분기에 사내 LLM Gateway를 만들었지만, 이미 3개 자회사가 자체 게이트웨이를 만든 뒤였고 지금도 통합 협상 중이다.

교훈: **Gateway는 첫 서비스가 프로덕션 나가기 전에 세워야 한다.** 나중에 세우면 게이트웨이 만드는 게 아니라 **12개 서비스의 게이트웨이 마이그레이션**을 해야 한다.

##### 사례 5: **Anthropic 내부** (공개된 부분)

Anthropic도 자사 모델을 자사 서비스가 쓸 때 내부 게이트웨이를 거친다. 이유는 성능이나 라우팅이 아니라 **감사와 실험**이다. Claude 새 버전을 내부에 dogfooding할 때 게이트웨이의 alias만 바꿔서 배포 없이 롤아웃한다.

#### 트레이드오프

| 항목 | Direct SDK | LLM Gateway |
|------|-----------|-------------|
| 초기 도입 비용 | 0 | 3~6주 (자체 구축) or SaaS 비용 |
| 첫 토큰 지연 | 100~300ms | +10~30ms |
| 모델 교체 비용 | N개 서비스 배포 | 설정 한 줄 |
| Provider 장애 대응 | 서비스별 개별 fallback | 중앙에서 일괄 |
| 비용 가시성 | 청구서 총액만 | 팀/기능/프롬프트 단위 |
| 감사 대응 | 불가능~수 주 | 수 분 |
| SPOF | 없음 (분산) | **있음 (게이트웨이 다운 = 전멸)** |
| A/B 테스트 | 코드 배포 필요 | 설정만 |
| 개발자 학습 곡선 | 낮음 | 낮음 (프로토콜 유지 시) |

**최대 리스크는 SPOF다.** 그래서 게이트웨이 자체가 다중 리전, 다중 인스턴스, Circuit Breaker로 무장되어야 한다. 게이트웨이 다운이 전체 챗봇 다운이 되는 것보다 차라리 임시로 게이트웨이를 우회하는 emergency bypass path가 필요할 수도 있다 (컴플라이언스와 협의).

#### 언제 도입하고, 언제 도입하지 않는가

##### ✅ 반드시 도입해야 하는 경우

- **LLM 통합 서비스가 3개 이상**이 되는 순간
- **Multi-provider**를 이미 쓰고 있거나 쓸 예정
- **컴플라이언스/감사 대상 산업** (금융, 의료, 공공)
- **월 LLM 비용이 $5,000 이상** (가시성 없으면 통제 불가)
- **A/B 실험이 잦은 조직** (프롬프트/모델 교체가 주 단위)

##### ⚠️ 신중해야 하는 경우

- 팀이 3명 이하, LLM 기능이 1개인 초기 스타트업 — 오버엔지니어링
- p50 응답 지연이 매우 크리티컬(<100ms 목표) — 게이트웨이 hop이 부담

##### ❌ 지금 도입하지 말아야 하는 경우

- **PoC 단계** — LiteLLM proxy로 충분
- **단일 provider, 단일 서비스, 비 규제 산업** — 정말로 SDK 직접 호출이 답
- **게이트웨이를 유지할 팀이 없다** — 하다가 방치되면 오히려 지옥

#### 함정 (시니어가 반드시 경계할 것)

##### 함정 1. 게이트웨이를 "LLM 프록시"로 착각

Provider 라우팅만 하고 관측/거버넌스를 안 붙이면 그냥 **지연시간만 늘어난 프록시**다. Gateway의 본질은 라우팅이 아니라 **책임의 중앙화**다. 라우팅만 하려면 그냥 LiteLLM 붙여라.

##### 함정 2. Alias를 안 쓰고 실물 모델명 통과

Gateway를 세우고도 앱 코드에 `"gpt-4o"`가 그대로 남아있으면 모델 교체 시 여전히 배포해야 한다. Gateway 도입과 동시에 **실물 모델명 사용을 CI에서 금지**해라. `grep -r "gpt-4" src/` 가 걸리면 PR 리젝트.

##### 함정 3. Fallback 체인이 무한 재시도

Primary→Secondary→Tertiary 모두 실패 시 Primary로 다시 재시도하는 로직이 들어가면 장애 시 **자기 시스템이 자기를 DDoS**한다. Circuit Breaker의 `half-open` 상태를 명확히 하고, 전체 fallback 시도는 3회 이내로 잘라라.

##### 함정 4. PII 마스킹을 게이트웨이에만 의존

Gateway에서 PII를 마스킹해도 **애플리케이션 로그에는 원본이 남는다**. Gateway 도입이 애플리케이션 코드의 PII 처리를 면제시켜주지 않는다. 이걸 "우리는 게이트웨이가 처리해요"라고 자신 있게 답했다가 개인정보보호위원회 조사에서 무너진 회사가 2025년에만 국내 3곳이다.

##### 함정 5. Streaming을 지원 안 함

Gateway v1을 non-streaming으로만 만들면 챗봇 팀이 "우리는 못 붙여요"라며 우회한다. **첫 릴리즈부터 streaming SSE passthrough를 지원해라.** 이거 안 되면 도입률 30% 넘기기 힘들다.

##### 함정 6. 감사 로그를 자기 자신에게 씀

Gateway가 자기 요청 로그를 자기 DB에 쓰면, Gateway가 다운되는 순간 감사 로그도 유실된다. **로그는 반드시 별도 sink** (Kafka, S3, 관리형 관측 서비스) 로 fire-and-forget으로 보내라.

##### 함정 7. Emergency Bypass 없음

Gateway가 다운되면 전 서비스가 죽는다. **컴플라이언스 팀과 사전 합의된 "긴급 우회 절차"** 가 있어야 한다. 예: SRE가 특정 서비스 계정만 직접 provider로 호출할 수 있는 pre-approved break-glass credential. 이건 만들어놓기만 하고 절대 안 써야 하는 것이지만, 없으면 SEV1 상황에서 CTO가 자기 노트북으로 API 키 배포하는 사태가 벌어진다.

---

> 💡 **왜 중요한가**: LLM Gateway는 "LLM을 위한 API Gateway"가 아니라 **"AI 기능의 거버넌스·비용·재해복구·감사·실험을 강제하는 유일한 아키텍처적 지점"** 이며, 이걸 첫 서비스가 프로덕션 나가기 전에 세우지 않으면 나중엔 게이트웨이를 만드는 게 아니라 12개 서비스의 마이그레이션을 해야 한다.
