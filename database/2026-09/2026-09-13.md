### MySQL `Gap Lock`과 `Next-Key Lock` — 존재하지 않는 행에도 락을 거는, `REPEATABLE READ`의 숨은 무기

`InnoDB`의 `REPEATABLE READ`는 팬텀 리드를 막기 위해 실제 행뿐 아니라 "행과 행 사이의 공간(gap)"에도 락을 건다. 예를 들어 `SELECT ... WHERE id BETWEEN 10 AND 20 FOR UPDATE`를 실행하면, id=10~20 사이에 존재하지 않는 값(예: id=15)에도 INSERT를 막는 갭 락이 걸린다. 이 때문에 배치 잡 두 개가 서로 다른 범위를 다루는데도 데드락이 나거나, INSERT가 미스터리하게 대기하는 현상이 발생한다.

```sql
-- 세션 A
BEGIN;
SELECT * FROM orders WHERE user_id BETWEEN 100 AND 200 FOR UPDATE;
-- user_id 100~200 범위 전체에 Next-Key Lock

-- 세션 B (블로킹됨!)
INSERT INTO orders (user_id, ...) VALUES (150, ...);
-- 실제로 존재하지 않는 user_id=150인데도 갭 락 때문에 대기
```

해결책은 세 가지다: (1) 격리 수준을 `READ COMMITTED`로 낮춰 갭 락을 비활성화, (2) 유니크 인덱스 기반의 정확한 등가 조건(`WHERE id = ?`)만 사용해 갭 락 회피, (3) 락 범위를 최소화하도록 인덱스를 재설계. 특히 세컨더리 인덱스에서 스캔이 넓게 걸리면 갭 락도 넓어지므로, 배치 쿼리는 반드시 `EXPLAIN`으로 실제 스캔 범위를 확인해야 한다.

> 💡 **왜 중요한가**: "동시 INSERT인데 왜 데드락이지?"의 90%는 존재하지 않는 행에 걸린 갭 락 때문이다.

### JPA `@BatchSize`와 `hibernate.default_batch_fetch_size` — N+1을 페치 조인 없이 "IN 절 한 방"으로 접는 우회로

`@EntityGraph`나 페치 조인은 카티션 곱과 페이지네이션 붕괴 문제를 일으킨다. `@BatchSize(size = 100)`는 지연 로딩을 유지하면서, 프록시 초기화가 필요한 시점에 여러 엔티티의 연관관계를 `WHERE parent_id IN (?, ?, ..., ?)` 한 방으로 묶어서 조회한다. N+1이 N/100+1로 줄어드는 것이다.

```java
@Entity
public class Team {
    @OneToMany(mappedBy = "team", fetch = FetchType.LAZY)
    @BatchSize(size = 100)
    private List<Member> members;
}

// 또는 전역 설정 (application.yml)
// spring.jpa.properties.hibernate.default_batch_fetch_size: 100
```

핵심은 페치 조인의 대안이 아니라 "보완"이라는 점이다. 페이지네이션이 필요한 컬렉션 조회에는 페치 조인을 못 쓰지만(메모리에서 페이징하는 경고와 함께), `@BatchSize`는 페이지네이션과 공존한다. 사이즈는 보통 `100~1000`이 적정선이며, 너무 크면 IN 절 파싱 비용과 옵티마이저 통계 왜곡이 커지고, 너무 작으면 여전히 라운드트립이 많아진다. Oracle처럼 IN 절 파라미터 제한(1000개)이 있는 DB에서는 반드시 그 이하로 설정해야 한다.

> 💡 **왜 중요한가**: 페치 조인이 만능이 아니고, 컬렉션 페이지네이션이 얽힌 실무에서는 `@BatchSize`가 유일한 정답인 경우가 많다.
