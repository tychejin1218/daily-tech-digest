### 1. `Files.mismatch(path1, path2)`로 두 파일 바이트 비교의 수동 스트림 관성 벗어나기 (Java 12 정식)

두 파일의 내용이 같은지 확인할 때 `InputStream` 두 개를 열고 버퍼 단위로 읽어 비교하는 보일러플레이트를 반복하곤 하죠. `Files.mismatch(path1, path2)`는 첫 번째로 다른 바이트의 위치(long)를 반환하고, 두 파일이 완전히 동일하면 `-1L`을 반환합니다. 내부적으로 크기 먼저 비교 → 메모리 매핑 활용 등 최적화가 들어있어서 직접 짠 루프보다 빠르고 정확합니다.

```java
// AS-IS: try-with-resources 이중 중첩 + 버퍼 루프 지옥
public boolean isSameFile(Path a, Path b) throws IOException {
    if (Files.size(a) != Files.size(b)) return false;
    try (InputStream in1 = Files.newInputStream(a);
         InputStream in2 = Files.newInputStream(b)) {
        byte[] buf1 = new byte[8192];
        byte[] buf2 = new byte[8192];
        int n;
        while ((n = in1.read(buf1)) > 0) {
            if (in2.read(buf2) != n) return false;
            if (!Arrays.equals(buf1, 0, n, buf2, 0, n)) return false;
        }
        return true;
    }
}

// TO-BE: 한 줄
public boolean isSameFile(Path a, Path b) throws IOException {
    return Files.mismatch(a, b) == -1L;
}

// 보너스: 어디서 달라졌는지도 알 수 있음 (로그, 진단용)
long diffAt = Files.mismatch(expected, actual);
if (diffAt != -1L) log.warn("파일이 {}번째 바이트부터 다릅니다", diffAt);
```

**⚠️ 트레이드오프**: `mismatch`는 "동일 여부"에는 완벽하지만 "무엇이 어떻게 다른지"의 컨텍스트(diff)는 주지 않습니다. 텍스트 파일의 라인 단위 diff가 필요하면 여전히 `java-diff-utils` 같은 라이브러리가 필요합니다. 또한 대용량 파일에서는 이 메서드도 O(n)이라는 점은 변하지 않아요 — 캐시된 해시(SHA-256 등) 비교가 필요한 상황도 별개입니다.

> 💡 **왜 중요한가**: 파일 동일성 검증은 배포 후 검증·설정 파일 동기화·테스트 픽스처 비교 등에서 흔한데, 직접 짠 버퍼 루프는 크기 조기 종료·EOF 처리 버그가 반복적으로 재발합니다. JDK가 이미 최적화한 메서드를 쓰는 게 정답입니다.

### 2. `Thread.ofVirtual().name("prefix-", 0).factory()`로 가상 스레드에 이름 붙여 디버깅 지옥 벗어나기 (Java 21 정식)

가상 스레드를 `Executors.newVirtualThreadPerTaskExecutor()`로 무심코 쓰면 스레드 덤프에서 `VirtualThread[#12345]/runnable` 같은 익명 이름만 나와서 어떤 작업이 어디서 블로킹됐는지 찾기가 지옥입니다. `Thread.ofVirtual().name(prefix, startIndex)`로 접두사와 카운터를 지정한 `ThreadFactory`를 만들면 `order-processor-0`, `order-processor-1` 같이 자동 넘버링되어 로그·프로파일러·`jcmd Thread.dump_to_file` 결과에서 즉시 식별됩니다.

```java
// AS-IS: 익명 가상 스레드 → 스레드 덤프 보고 울고 싶어짐
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    orders.forEach(order -> executor.submit(() -> process(order)));
}
// jcmd 결과: VirtualThread[#48291]/runnable  ← 이게 뭔지 알 방법이 없음

// TO-BE: 이름 있는 팩토리
ThreadFactory factory = Thread.ofVirtual()
    .name("order-processor-", 0)   // order-processor-0, -1, -2 ...
    .factory();

try (var executor = Executors.newThreadPerTaskExecutor(factory)) {
    orders.forEach(order -> executor.submit(() -> process(order)));
}
// jcmd 결과: VirtualThread[#48291,order-processor-42]/runnable ← 즉시 식별 가능

// 응용: MDC(로그 컨텍스트)와 결합하면 요청 추적이 더 쉬워짐
ThreadFactory factory = Thread.ofVirtual()
    .name("http-req-", 0)
    .inheritInheritableThreadLocals(false)  // 명시적으로 상속 차단 (권장)
    .factory();
```

**핵심 포인트 — 왜 익명이 문제인가**:
- 가상 스레드는 수천~수만 개가 동시에 뜨는 게 정상 → 익명이면 스레드 덤프가 `#1`, `#2`, `#3`... 무의미한 숫자 나열
- 캐리어 스레드(`ForkJoinPool-1-worker-N`)와 가상 스레드가 섞여 나와서 어떤 워크로드가 문제인지 구분 안 됨
- 프로파일러(JFR, async-profiler)에서 태스크 유형별 집계가 불가능

**⚠️ 흔한 오해**: 이름을 붙인다고 성능 오버헤드가 있는 건 아닙니다 — 이름은 그냥 문자열 필드일 뿐이고, 가상 스레드의 경량성(스택 리사이즈, 마운트/언마운트)에 영향을 주지 않아요. 오히려 프로덕션 진단 비용을 크게 낮춥니다.

> 💡 **왜 중요한가**: 가상 스레드 도입의 진짜 병목은 "만드는 방법"이 아니라 "장애 났을 때 뭐가 어디서 막혔는지 추적하는 방법"입니다. 이름은 무료 관측성(observability)이니 처음부터 붙이세요.
