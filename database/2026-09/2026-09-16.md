### MySQL `InnoDB Adaptive Hash Index` — B-Tree 위에 얹힌 "학습하는 해시 캐시"의 양날의 검

InnoDB는 자주 접근되는 인덱스 페이지를 감지해서, 자동으로 B-Tree 위에 해시 인덱스를 만들어 `O(log N)`을 `O(1)`로 단축시킨다. 문제는 이 학습 과정 자체가 `btr_search_latch`라는 전역 락을 잡기 때문에, 동시성이 높은 OLTP 환경에서는 오히려 컨텍스트 스위칭과 락 경합으로 성능이 역전된다는 점. Percona 벤치마크에서 32코어 이상 서버에서는 `innodb_adaptive_hash_index=OFF`가 15~20% 더 빠른 경우가 흔하다.

```
[일반 조회]                    [AHI 활성화 후]
Root Page → Branch → Leaf      Hash Table → Leaf
   (3~4 page reads)               (1 lookup)

BUT 동시 접근 시:
Thread1 ─┐
Thread2 ─┼→ btr_search_latch (전역 락) → 병목!
Thread3 ─┘
```

> 💡 **왜 중요한가**: "MySQL이 알아서 최적화해준다"는 옵션이 오히려 스케일 아웃의 발목을 잡을 수 있다. 코어가 많아질수록 `SHOW ENGINE INNODB STATUS`에서 `SEMAPHORES` 섹션의 `btr_search_latch` 대기를 반드시 확인하라.

### PostgreSQL `Partial Index` — "전체 행의 1%만 인덱싱"하는 조건부 인덱스

Partial Index는 `WHERE` 절이 붙은 인덱스로, 특정 조건을 만족하는 행만 인덱싱한다. 예를 들어 `CREATE INDEX idx_orders_pending ON orders(created_at) WHERE status = 'PENDING'`은 "처리 대기" 상태의 주문(전체의 1~2%)만 인덱스에 넣기 때문에, 크기는 1/100로 줄고 캐시 히트율은 폭발적으로 상승한다. 핵심은 쿼리에서 반드시 인덱스 정의와 동일한 조건을 `WHERE`에 명시해야 옵티마이저가 이 인덱스를 선택한다는 점.

```sql
-- 전체 인덱스: 1000만 행 × 8바이트 = 80MB
CREATE INDEX idx_all ON orders(created_at);

-- Partial Index: 10만 행 × 8바이트 = 800KB (100배 축소)
CREATE INDEX idx_pending ON orders(created_at)
WHERE status = 'PENDING';

-- ✅ 이 쿼리는 partial index 사용
SELECT * FROM orders WHERE status = 'PENDING' ORDER BY created_at;

-- ❌ 이 쿼리는 partial index 못 씀 (조건 불일치)
SELECT * FROM orders WHERE status IN ('PENDING', 'PAID');
```

> 💡 **왜 중요한가**: "논리적 삭제(soft delete)", "미처리 큐", "활성 사용자"처럼 **한쪽으로 데이터가 크게 편중된 컬럼**에서 극적인 효과가 난다. 큰 테이블에 무작정 풀 인덱스를 만들기 전에, 쿼리가 실제로 조회하는 데이터의 카디널리티부터 확인하라.
