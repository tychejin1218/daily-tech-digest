### PostgreSQL `pg_bouncer`의 Transaction Pooling — 커넥션은 재활용되지만, 세션 상태는 증발한다

PostgreSQL은 커넥션 하나당 프로세스 하나를 만드는 구조라, 커넥션 수가 곧 메모리 비용이 된다. `pg_bouncer`의 Transaction Pooling 모드는 트랜잭션이 끝날 때마다 커넥션을 풀에 반납해서 수천 개의 클라이언트가 수십 개의 실제 커넥션을 공유하게 만든다. 문제는 세션 상태 — `SET LOCAL`이 아닌 `SET`, prepared statement, temporary table, advisory lock, `LISTEN/NOTIFY` — 이 모두 다음 트랜잭션에서는 다른 백엔드로 배정되기 때문에 **조용히 사라지거나 다른 세션에 새어나간다**.

```
[클라이언트 A] --tx1--> [백엔드 #7] SET search_path=tenant_a  <- 반납
[클라이언트 A] --tx2--> [백엔드 #3] search_path=public         <- 사라짐!
[클라이언트 B] --tx3--> [백엔드 #7] search_path=tenant_a       <- 유출!
```

가장 자주 터지는 사고 — Spring Boot 앱이 `HikariCP` 뒤에 `pg_bouncer`를 두고, JPA가 서버사이드 prepared statement를 캐싱하는 경우다. 백엔드가 바뀌면 `prepared statement "S_1" does not exist` 에러가 재현 불가능하게 튄다. 해결책은 JDBC URL에 `prepareThreshold=0` 또는 `preferQueryMode=simple`, 또는 `pg_bouncer` 1.21+ 의 `server_prepared_statements` 옵션.

> 💡 **왜 중요한가**: 커넥션 풀링을 도입하면 성능은 얻지만, "세션 = 커넥션" 이라는 암묵적 가정 위에 서 있던 모든 기능이 조용히 무너진다.

### MySQL `Online DDL`의 함정 — `ALGORITHM=INPLACE`도 결국 메타데이터 락을 잡는 순간이 있다

MySQL 5.6+ 의 Online DDL은 `ALTER TABLE`이 실행되는 동안에도 DML(INSERT/UPDATE/DELETE)을 받을 수 있게 해주지만, "온라인"이라는 이름과 달리 **시작과 끝에 반드시 짧은 순간 MDL(Metadata Lock)을 배타적으로 잡는다**. 이 순간에 장시간 실행 중인 트랜잭션이 하나라도 해당 테이블을 참조하고 있으면, ALTER는 그 트랜잭션이 끝날 때까지 대기하고, 그 뒤에 도착한 모든 쿼리는 ALTER 뒤에 줄을 서게 된다 — 이른바 **MDL 대기 폭포**.

```
T=0   [SELECT ... FROM users] (5분짜리 리포트 쿼리, 여전히 실행 중)
T=10  [ALTER TABLE users ADD COLUMN ...]  <- MDL 대기 시작
T=11  [INSERT INTO users ...]             <- ALTER 뒤에 대기
T=12  [SELECT ... FROM users]             <- 대기
T=15  [SELECT ... FROM users]             <- 대기 (커넥션 풀 고갈 시작)
...
T=5분 리포트 쿼리 종료 → ALTER 시작 → 밀린 수천 쿼리 폭발
```

즉, ALTER 자체는 online이라도 **운영 환경에서 앱 전체를 멈출 수 있다**. 그래서 실무에서는 `lock_wait_timeout`을 짧게(예: 3초) 설정해서 ALTER가 대기를 포기하고 실패하게 만들고, 재시도 루프를 돌리거나, 아예 `pt-online-schema-change` / `gh-ost` 같은 트리거·바이너리로그 기반 툴을 쓴다. AWS RDS에서 새벽 트래픽 적은 시간에 인덱스 하나 추가하려다 서비스 전체가 멎는 대표적 패턴이 바로 이것이다.

> 💡 **왜 중요한가**: "Online DDL이니까 안전하다"는 문서 한 줄을 믿고 배포한 팀은, 오래된 트랜잭션 하나 때문에 앱 전체가 멎는 경험을 반드시 한 번은 하게 된다.
