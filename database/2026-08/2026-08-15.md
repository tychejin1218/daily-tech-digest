### MySQL `Doublewrite Buffer` — 페이지 절반만 디스크에 쓰인 순간(torn page)에도 데이터를 지켜내는 InnoDB의 이중 안전장치

InnoDB의 페이지 크기는 16KB지만 대부분의 파일시스템/디스크 섹터의 원자적 쓰기 단위는 4KB 이하다. 크래시가 하필 16KB를 쓰는 도중에 발생하면 페이지 절반만 저장된 "찢어진 페이지(torn page)"가 생기고, 이 경우 redo log는 "변경분"만 갖고 있어서 복구조차 불가능하다. Doublewrite Buffer는 실제 데이터 파일에 쓰기 전에 시스템 테이블스페이스의 연속된 영역(기본 128 페이지)에 먼저 순차 기록해두는 방식으로, 크래시 리커버리 시 이 사본을 원본으로 사용해 반드시 온전한 16KB를 복원한다.

```
[정상 흐름]
Buffer Pool → Doublewrite Buffer(순차 쓰기) → Data File(랜덤 쓰기)
                    ↑ fsync                        ↑ fsync

[크래시 시나리오]
Data File의 페이지가 찢어짐(torn) 감지
  → Doublewrite Buffer에서 온전한 사본 읽음
  → Data File 복구 → redo log 적용
```

실무 함정: "쓰기가 두 번 일어나니 성능이 절반?"이라는 오해가 흔한데, 실제로는 Doublewrite는 **순차 I/O**라 오버헤드가 5~10% 수준이다. 반면 `innodb_doublewrite=0`으로 껐다가 크래시가 나면 InnoDB가 시작조차 못 하는 참사가 벌어진다. NVMe에서 원자적 16KB 쓰기를 보장하는 하드웨어(FusionIO, 일부 엔터프라이즈 SSD)를 쓰거나, ZFS/Btrfs처럼 CoW 파일시스템 위에서 돌릴 때만 끄는 것이 정석. MySQL 8.0.20부터는 Doublewrite 파일이 시스템 테이블스페이스에서 분리되어(`#ib_16384_0.dblwr`) 병렬성이 크게 개선됐다.

> 💡 **왜 중요한가**: redo log가 만능이라는 착각을 깨는 지점 — 스토리지의 물리적 쓰기 단위와 DB의 논리적 쓰기 단위가 다르기 때문에 "로그만 있으면 복구된다"는 명제는 Doublewrite 없이는 성립하지 않는다.

### PostgreSQL `Visibility Map` — VACUUM이 "이 페이지는 볼 필요 없다"를 기억해서 Index-Only Scan을 가능하게 하는 비밀 파일

PostgreSQL의 MVCC는 각 튜플이 "누구에게 보이는지"를 xmin/xmax로 판단하는데, 이걸 매번 확인하려면 힙 튜플을 직접 읽어야 한다. 즉 인덱스에 원하는 컬럼이 다 있어도 "이 튜플이 지금 나에게 보이나?"를 확인하려고 힙을 방문해야 하니 Covering Index가 무력화된다. Visibility Map(`.vm` 파일)은 페이지 단위로 "이 페이지의 모든 튜플이 모든 트랜잭션에 visible한가?"를 1비트로 기록하고, VACUUM이 이 비트를 세워두면 옵티마이저가 **힙 방문 없이 인덱스만으로 답을 돌려주는 Index-Only Scan**을 선택할 수 있게 된다.

```
[VM 비트 없음]
Index Scan → 힙 튜플 읽기 (visibility 체크) → 결과 반환
             ↑ Random I/O 폭발

[VM 비트 있음 (all-visible)]
Index Scan → VM 확인 (all-visible 페이지) → 힙 스킵 → 결과 반환
             ↑ 1비트만 읽음
```

실무 함정: `CREATE INDEX ... INCLUDE (col)`로 covering index를 만들어놨는데도 `EXPLAIN`이 여전히 Index Scan(Index-Only Scan이 아님)을 고르는 순간이 있다. 원인은 대부분 **VACUUM이 최근에 안 돌았다**는 것 — UPDATE/INSERT가 활발한 테이블은 VM 비트가 계속 꺼지고, autovacuum이 따라잡지 못하면 Index-Only Scan은 이론상만 존재하는 옵션이 된다. `pg_visibility` 확장으로 `SELECT * FROM pg_visibility_map('mytable')`을 찍어보면 all_visible 비율을 확인할 수 있고, 이 비율이 낮으면 `VACUUM (INDEX_CLEANUP ON) mytable`을 수동으로 돌리거나 `autovacuum_vacuum_scale_factor`를 낮춰야 한다. 더 흥미로운 반전은 `EXPLAIN (ANALYZE, BUFFERS)`에서 "Heap Fetches: N"이 0이 아니면 사실상 Index-Only Scan의 이점을 못 살리고 있다는 신호라는 점.

> 💡 **왜 중요한가**: PostgreSQL에서 "Covering Index를 만들어도 왜 힙을 읽는가"라는 미스터리의 90%는 Visibility Map이 원인이며, MVCC의 대가(cost)가 인덱스 설계에까지 침투한다는 것을 보여준다.
