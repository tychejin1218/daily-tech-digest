### Circuit Breaker — "실패한 서비스를 계속 부르는 것이 왜 시스템 전체를 죽이는가"에 대한 회로 차단기적 해법

분산 시스템에서 가장 뼈아픈 진실 하나. **다운스트림 서비스 하나가 느려지면, 그것을 호출하는 상위 서비스가 먼저 죽는다.** 다운스트림은 그저 느릴 뿐인데, 상위는 스레드 풀이 고갈되어 완전히 응답 불능이 된다. 이것이 바로 **cascading failure(연쇄 장애)**의 본질이고, Circuit Breaker가 존재하는 이유다.

#### 왜 "그냥 타임아웃"으로는 부족한가

시니어 개발자라면 이 질문에 답할 수 있어야 한다: "타임아웃을 500ms로 걸어두면 되는 것 아닌가?"

답은 "아니오"다. 문제는 이렇다. 결제 서비스가 죽어가는 상황을 가정하자. 평소 20ms 응답이던 서비스가 이제 3초씩 걸리고, 그중 절반은 500 에러다. 주문 서비스는 결제 서비스를 호출한다. 타임아웃은 걸어뒀다. 하지만:

- 초당 1,000건의 주문 요청이 들어온다
- 각 요청이 결제 호출에서 500ms(타임아웃) 대기한다
- 주문 서비스의 톰캣 스레드 풀은 200개
- 400ms만 지나도 스레드 풀이 고갈된다
- **주문 서비스는 결제와 무관한 요청(예: 주문 조회)조차 처리하지 못한다**

즉, 다운스트림 장애가 상위 서비스의 **전체 처리 용량**을 잠식한다. 결제만 못 하면 되는데 조회도 못 하는 상황. 이걸 우리는 "**failure amplification(장애 증폭)**"이라 부른다.

Circuit Breaker의 통찰은 명료하다. **"이미 죽어있다고 알고 있는 서비스는 부르지 말고 즉시 실패시켜라."** 100ms 만에 실패하는 것이 500ms 대기 후 실패하는 것보다 시스템 전체에는 훨씬 이롭다.

#### 상태 머신의 삼각형: Closed → Open → Half-Open

Circuit Breaker의 심장은 3-state finite state machine이다.

```
                    ┌─────────────────────────────┐
                    │                             │
                    │    실패율 > 임계치          │
                    ▼                             │
        ┌──────────────────┐         ┌────────────────────┐
        │     CLOSED       │────────▶│       OPEN         │
        │  (정상 통과)      │         │  (즉시 실패 반환)   │
        └──────────────────┘         └────────────────────┘
                    ▲                             │
                    │ 성공률 회복                  │ wait duration
                    │                             │ (예: 30초) 경과
                    │                             ▼
                    │                 ┌────────────────────┐
                    └─────────────────│    HALF-OPEN       │
                     실패 시 재 Open   │  (제한된 호출 허용) │
                                     └────────────────────┘
```

- **CLOSED**: 정상 상태. 모든 호출이 통과한다. 실패는 카운트되며 sliding window로 실패율을 관측한다.
- **OPEN**: 임계치 초과. **호출을 시도조차 하지 않고** `CallNotPermittedException`을 즉시 던진다. 다운스트림에 요청이 가지 않으므로 회복할 시간을 준다.
- **HALF-OPEN**: 대기 시간이 지나면 소수(예: 10개)의 요청만 통과시켜 서비스가 회복됐는지 **탐침(probe)**한다. 회복됐으면 Closed, 여전히 실패하면 Open으로.

핵심은 **HALF-OPEN**의 존재다. 회로가 한 번 열리면 언제 닫아야 하는지가 문제인데, 시간이 지났다고 해서 다시 트래픽을 전부 흘리면 다시 죽인다. 소량 탐침 후 판단하는 것이 실용적 해답이다.

#### Resilience4j 구현: 실전 코드

Netflix Hystrix는 2018년 유지보수 중단됐고, 이제 JVM 진영의 사실상 표준은 **Resilience4j**다. 함수형이고 lightweight하며, Spring Boot 3와 잘 어울린다.

```java
@Configuration
public class ResilienceConfig {
    @Bean
    public CircuitBreakerRegistry circuitBreakerRegistry() {
        CircuitBreakerConfig config = CircuitBreakerConfig.custom()
            .slidingWindowType(SlidingWindowType.COUNT_BASED)
            .slidingWindowSize(20)              // 최근 20개 호출 기준
            .minimumNumberOfCalls(10)           // 판단에 필요한 최소 호출 수
            .failureRateThreshold(50.0f)        // 실패율 50% 넘으면 Open
            .slowCallRateThreshold(80.0f)       // 느린 호출 비율 80% 넘어도 Open
            .slowCallDurationThreshold(Duration.ofSeconds(2))
            .waitDurationInOpenState(Duration.ofSeconds(30))
            .permittedNumberOfCallsInHalfOpenState(5)
            .automaticTransitionFromOpenToHalfOpenEnabled(true)
            .build();
        return CircuitBreakerRegistry.of(config);
    }
}

@Service
public class PaymentClient {
    @CircuitBreaker(name = "payment", fallbackMethod = "fallbackPay")
    public PaymentResult pay(PaymentRequest req) {
        return paymentApi.call(req);            // 실제 HTTP/gRPC 호출
    }

    private PaymentResult fallbackPay(PaymentRequest req, Throwable t) {
        if (t instanceof CallNotPermittedException) {
            // 회로가 열려있어 즉시 실패한 경우
            return PaymentResult.deferred(req);  // 나중에 재처리하도록 큐잉
        }
        throw new PaymentUnavailableException(t);
    }
}
```

여기서 시니어가 주목해야 할 설정 두 가지:

1. **`slowCallRateThreshold`**: 실패뿐 아니라 **느린 성공**도 회로를 열게 한다. 이게 정말 중요하다. HTTP 200을 반환하지만 5초 걸리는 서비스는 사실상 죽어있는 것이다. 실패율만 보면 이를 놓친다.
2. **`minimumNumberOfCalls`**: 트래픽이 적을 때 1-2번 실패로 회로가 열리는 것을 방지. 통계적으로 유의미한 표본이 모여야 판단한다.

#### 트레이드오프: 만병통치약이 아니다

**얻는 것**
- Cascading failure 방지
- 실패한 서비스에 회복 시간 부여 (retry storm 억제)
- 상위 서비스의 리소스 보호 (thread pool, connection pool)
- 명시적 fallback 지점 제공

**잃는 것과 함정**
- **False positive**: 네트워크 일시 blip으로 회로가 열리면 정상 서비스가 30초간 차단된다. 임계치 튜닝이 어렵다.
- **State 공유 문제**: 인스턴스별로 상태를 가지므로 A 인스턴스는 Open, B 인스턴스는 Closed일 수 있다. Redis 같은 곳에 상태를 공유할 수도 있지만, 그건 그것대로 SPOF를 만든다. **일반적으론 인스턴스별 로컬 상태가 정답**이다.
- **Fallback이 진짜 문제**: 회로가 열렸을 때 무엇을 반환할 것인가? 캐시된 값? 빈 응답? 에러? 이 설계가 훨씬 어렵다. Circuit Breaker를 붙였지만 fallback이 다시 실패하면 아무 의미가 없다.
- **테스트하기 어렵다**: 실제 다운스트림 장애를 재현하기 힘들다. Chaos Engineering(예: Chaos Monkey)이 필요한 이유.

#### 실제 사례: Netflix와 그 이후

Netflix는 2011년경 자사 스트리밍 서비스에서 이 문제를 겪었다. 마이크로서비스가 수백 개로 늘어나면서 하나의 서비스 장애가 UI 전체를 마비시켰다. 그들이 만든 게 **Hystrix**였고, 이는 2010년대 중반 MSA 아키텍처의 필수 라이브러리가 됐다. Netflix의 홈 화면은 수십 개 마이크로서비스를 조합하는데, 추천 서비스가 죽어도 "인기 콘텐츠" fallback을 보여주며 화면은 살아있다.

**Amazon**은 더 근본적이다. 각 서비스 팀이 자기 fallback을 직접 정의해야 하고, 이는 SLA 계약의 일부다. "Recommendation 서비스가 죽으면 Product 페이지는 어떻게 보이는가?"에 답이 없는 팀은 릴리즈를 못 한다.

반대로 **Kubernetes 시대에는 Service Mesh(Istio, Linkerd)로 옮겨가는 추세**다. Istio는 Envoy proxy에서 circuit breaking을 처리하므로 애플리케이션 코드에 Resilience4j 같은 라이브러리를 넣을 필요가 없다. 언어 중립적이고, 정책을 중앙에서 관리한다. 하지만 **application-level의 세밀한 fallback 로직**(캐시로 대체, 큐잉 등)은 여전히 애플리케이션 안에서 해야 한다. 그래서 실무에서는 둘을 함께 쓴다: **Service Mesh는 인프라 수준의 circuit breaking, Resilience4j는 비즈니스 수준의 graceful degradation**.

#### 언제 쓰고, 언제 쓰면 안 되는가

**써야 할 때**
- 외부 API 호출 (결제 게이트웨이, 알림 서비스, 3rd-party)
- 신뢰도가 낮거나 SLA가 없는 다운스트림
- 실패해도 부분적 응답이 유의미한 경우 (추천, 개인화, 광고)
- Fan-out이 큰 aggregation 지점

**쓰지 말아야 할 때**
- **동기적으로 반드시 성공해야 하는 크리티컬 경로** (예: 계좌 이체의 잔액 차감). 여기선 회로가 열려도 "그냥 실패"가 답이 아니다. 재시도와 큐잉이 답이다.
- **트래픽이 극히 적은 서비스**. 통계적 유의성이 없어 임계치가 무의미하다. 단순 재시도 + 타임아웃으로 충분.
- **Fallback 설계가 어렵거나 불가능한 경우**. 회로만 열리고 결국 500 반환한다면 그냥 타임아웃과 동일하다.
- **DB 호출**. DB는 circuit breaker 대상이 아니다. Connection pool과 statement timeout으로 관리해야 한다. 회로가 열리면 서비스 전체가 무의미해진다.

#### 시니어의 관점

주니어는 "Resilience4j 붙이면 안정성 확보"라고 생각한다. 시니어는 이렇게 본다: **Circuit Breaker는 실패를 "빠르게" 만드는 도구지, 실패를 없애는 도구가 아니다.** 진짜 질문은 "회로가 열렸을 때 사용자에게 무엇을 보여줄 것인가"이고, 이 답은 라이브러리가 아니라 **비즈니스 요구사항**에서 나온다. 결제가 실패했을 때 "재시도해주세요"를 보여줄 것인가, 결제 없이 주문 접수만 하고 나중에 재청구할 것인가. 이 결정을 안 하고 붙이는 Circuit Breaker는 그냥 예쁜 500 에러 생성기일 뿐이다.

또 하나. **Circuit Breaker는 Bulkhead, Rate Limiter, Retry와 함께 써야 진짜 효과가 난다.** Retry만 있으면 retry storm이 나고, Bulkhead만 있으면 격리는 되지만 fail-fast가 안 된다. Resilience4j의 진짜 힘은 이들을 조합할 수 있다는 것이다: `Retry → CircuitBreaker → Bulkhead → TimeLimiter` 순으로 데코레이터를 쌓는 게 일반적 패턴이다.

> 💡 **왜 중요한가**: Circuit Breaker는 "실패를 없애는 마법"이 아니라, 죽어가는 다운스트림 때문에 상위 서비스가 함께 죽는 cascading failure를 끊어내는 유일하게 실용적인 방법이다.
