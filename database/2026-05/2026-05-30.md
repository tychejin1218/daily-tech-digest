### PostgreSQL `EXCLUDE` 제약 — 겹치는 예약·기간을 DB 레벨에서 원천 차단하기

회의실 예약, 좌석 배정처럼 "같은 리소스에 대해 시간 범위가 겹치면 안 되는" 요구사항을 애플리케이션 락 없이 제약조건 하나로 해결한다. `btree_gist` 확장을 켜고 `EXCLUDE USING gist (room_id WITH =, during WITH &&)`로 선언하면, 겹치는 `tsrange`를 넣는 순간 DB가 `INSERT`를 거부한다.

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE reservation (
  id     bigserial PRIMARY KEY,
  room_id int NOT NULL,
  during tsrange NOT NULL,
  EXCLUDE USING gist (room_id WITH =, during WITH &&)
);
```

애플리케이션에서 "먼저 SELECT로 겹침 체크 → INSERT" 패턴은 동시성 하에서 반드시 뚫린다. `EXCLUDE`는 인덱스 기반으로 원자적으로 검사하므로, 두 요청이 동시에 도착해도 하나만 성공한다.

> 💡 **왜 중요한가**: "겹치면 안 된다"는 도메인 규칙은 애플리케이션이 아니라 DB가 지켜야 진짜로 지켜진다.

### MySQL `covering index` — 테이블 접근 없이 인덱스만으로 쿼리 끝내기

`SELECT`가 필요로 하는 모든 컬럼이 인덱스에 포함되어 있으면, 옵티마이저는 실제 행(clustered index)에 접근하지 않고 인덱스 리프 노드만 읽어 응답한다. `EXPLAIN`의 `Extra` 컬럼에 `Using index`가 뜨면 커버링이 성공한 것이고, 랜덤 I/O가 사라져 응답 시간이 수 배에서 수십 배까지 줄어든다.

```sql
-- status로 필터, created_at으로 정렬, id·title만 조회
CREATE INDEX idx_covering ON orders (status, created_at, id, title);

EXPLAIN SELECT id, title FROM orders
WHERE status = 'PAID' ORDER BY created_at DESC LIMIT 20;
-- Extra: Using index  ← 테이블 조회 0회
```

WHERE·ORDER BY·SELECT 컬럼 순서를 인덱스 설계에 함께 반영하는 것이 핵심이며, 무작정 컬럼을 넣지 말고 실제 hot query에 맞춰 좁게 만들어야 쓰기 비용과 균형이 맞는다.

> 💡 **왜 중요한가**: 인덱스는 "찾는" 도구를 넘어 "다 담아 반환하는" 도구로 쓸 때 진짜 위력을 낸다.
