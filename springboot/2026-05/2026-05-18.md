### 1. `ApplicationContextRunner`로 자동 구성(Auto-configuration) 단위 테스트하기

`@SpringBootTest`로 전체 컨텍스트를 띄우지 않고도 `ApplicationContextRunner`를 쓰면 자동 구성 클래스가 의도한 조건(`@ConditionalOnProperty`, `@ConditionalOnMissingBean` 등)에 따라 빈을 올리거나 내리는지 밀리초 단위로 검증할 수 있습니다. `withUserConfiguration`, `withPropertyValues`, `withClassLoader(new FilteredClassLoader(...))`를 조합하면 클래스패스 존재 여부까지 시뮬레이션할 수 있어 스타터/라이브러리 개발에 특히 유용합니다.

```java
new ApplicationContextRunner()
    .withConfiguration(AutoConfigurations.of(MyAutoConfiguration.class))
    .withPropertyValues("my.feature.enabled=true")
    .run(context -> assertThat(context).hasSingleBean(MyService.class));
```

> 💡 **왜 중요한가**: 전체 컨텍스트 부팅 없이 자동 구성의 조건 분기 전부를 빠르게 검증할 수 있어, 라이브러리/공통 모듈의 회귀 테스트 비용을 크게 낮춰 줍니다.

### 2. `SecurityFilterChain`을 여러 개로 분리해 경로별 보안 정책 차등 적용하기

Spring Security 6에서는 `SecurityFilterChain` 빈을 여러 개 등록하고 `securityMatcher`로 매칭 경로를 지정한 뒤 `@Order`로 평가 순서를 정할 수 있습니다. 예를 들어 `/api/**`는 JWT 리소스 서버로, `/admin/**`은 폼 로그인으로, `/actuator/**`은 Basic 인증으로 각각 분리하면 한 필터 체인에 분기 로직을 욱여넣지 않아도 됩니다.

```java
@Bean @Order(1)
SecurityFilterChain api(HttpSecurity http) throws Exception {
    return http.securityMatcher("/api/**")
        .authorizeHttpRequests(a -> a.anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
        .csrf(CsrfConfigurer::disable)
        .build();
}
```

> 💡 **왜 중요한가**: 인증 방식이 섞인 애플리케이션에서 각 영역의 보안 정책을 독립적으로 진화시킬 수 있어, 설정 변경의 폭발 반경(blast radius)을 크게 줄여 줍니다.
