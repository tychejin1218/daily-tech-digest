### 1. `Collectors.toUnmodifiableMap(keyMapper, valueMapper)`로 `Collectors.toMap` 후 `Map.copyOf()` 이중 처리 관성 벗어나기 (Java 10 정식)

`stream.collect(Collectors.toMap(k, v))` 후 `Map.copyOf(result)`로 감싸는 두 단계 처리는 중간 가변 맵을 한 번 만들고 다시 복사하는 낭비를 유발한다. `Collectors.toUnmodifiableMap(keyMapper, valueMapper)`는 처음부터 불변 맵을 조립하므로 중간 HashMap 할당이 사라지고, 중복 키가 있으면 즉시 `IllegalStateException`으로 실패해 조용한 덮어쓰기 버그도 예방된다. 병합이 필요하면 3-인자 오버로드 `toUnmodifiableMap(k, v, mergeFunction)`을 쓰면 되고, `null` 키/값은 아예 거부되므로 방어적 검증도 자동으로 걸린다.

```java
// 관성적 코드 — 가변 맵 생성 후 불변 복사 (2단계)
Map<String, Long> mutable = users.stream()
    .collect(Collectors.toMap(User::name, User::id));
Map<String, Long> result = Map.copyOf(mutable);

// 개선 — 처음부터 불변 조립 (1단계)
Map<String, Long> result = users.stream()
    .collect(Collectors.toUnmodifiableMap(User::name, User::id));
```

> 💡 **왜 중요한가**: "불변 맵을 만들자"는 의도가 코드 한 줄에 명시적으로 드러나면서 중간 할당·중복 키 조용한 덮어쓰기·null 유입이라는 세 함정을 동시에 차단한다.

### 2. `Optional.or(() -> Optional.of(...))`로 `orElseGet` 후 재래핑 관성 벗어나기 (Java 9 정식)

`Optional`이 비었을 때 **다른 `Optional`을 반환하는 fallback**을 걸고 싶은데, 관성적으로 `opt.orElseGet(() -> fetchDefault())` 후 결과를 다시 `Optional.ofNullable()`로 감싸는 코드를 자주 본다. `Optional.or(Supplier<Optional<T>>)`는 이 상황을 위한 정식 API로, 첫 `Optional`이 비었을 때만 지연 평가로 두 번째 `Optional`을 반환한다. 여러 소스에서 순차적으로 조회하는 fallback 체인(캐시 → DB → 외부 API)을 표현할 때 특히 강력하며, `Optional.empty()`가 반환돼도 그대로 전파되므로 "찾지 못함" 상태를 자연스럽게 유지한다.

```java
// 관성적 코드 — orElseGet 후 재래핑
Optional<User> user = findInCache(id);
if (user.isEmpty()) {
    User dbUser = findInDb(id).orElseGet(() -> fetchFromApi(id).orElse(null));
    user = Optional.ofNullable(dbUser);
}

// 개선 — or 체인
Optional<User> user = findInCache(id)
    .or(() -> findInDb(id))
    .or(() -> fetchFromApi(id));
```

> 💡 **왜 중요한가**: fallback 체인이 좌→우 데이터 흐름 한 줄로 읽히고, 각 단계가 `Optional`을 반환하는 계약을 지키면 "empty 전파"가 자동으로 보장돼 `null` 오염 위험이 사라진다.
