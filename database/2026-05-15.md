### Redis `SCAN` — 운영 환경에서 `KEYS` 대신 안전하게 키 순회하기

Redis의 `KEYS *` 명령은 모든 키를 한 번에 스캔하면서 단일 스레드를 블로킹하기 때문에, 키가 수백만 개인 운영 환경에서는 서비스 전체가 멈출 수 있습니다. `SCAN`은 커서 기반으로 키를 일정 개수(`COUNT`)씩 점진적으로 순회하므로 다른 명령을 차단하지 않으며, `MATCH` 패턴과 함께 사용해 특정 prefix의 키만 안전하게 조회할 수 있습니다. 단, 순회 중에 추가/삭제된 키는 결과에 포함되거나 누락될 수 있다는 약한 일관성을 갖는다는 점은 알아두어야 합니다.

> 💡 **왜 중요한가**: `KEYS` 한 번 잘못 실행하면 프로덕션 Redis가 수 초~수십 초간 멈춰 장애로 이어진다.

### MySQL `ON DUPLICATE KEY UPDATE` vs PostgreSQL `INSERT ... ON CONFLICT` — 안전한 UPSERT 패턴

애플리케이션에서 `SELECT` 후 `INSERT`/`UPDATE`를 분기하는 방식은 동시성 환경에서 race condition으로 중복 키 예외나 데이터 유실이 발생하기 쉽습니다. MySQL은 `INSERT ... ON DUPLICATE KEY UPDATE`, PostgreSQL은 `INSERT ... ON CONFLICT (col) DO UPDATE SET ...` 구문으로 유니크 제약 충돌 시 원자적으로 UPDATE를 수행할 수 있어 안전합니다. 다만 MySQL은 충돌 시에도 AUTO_INCREMENT 값을 소모하므로 PK 점프가 발생할 수 있고, PostgreSQL은 `EXCLUDED.column`으로 새로 들어올 값을 참조한다는 점에서 문법 차이를 주의해야 합니다.

> 💡 **왜 중요한가**: 동시성 환경에서 "있으면 업데이트, 없으면 삽입"을 애플리케이션 로직으로 구현하면 거의 항상 깨진다 — DB의 원자적 UPSERT를 써야 한다.
