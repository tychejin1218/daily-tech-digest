### PostgreSQL `GENERATED ALWAYS AS ... STORED` 컬럼 — 파생 값을 DB가 계산·유지하게 하기

풀네임, 총액, 검색용 소문자 컬럼처럼 다른 컬럼에서 파생되는 값을 애플리케이션이 매번 계산해 저장하면 로직 분산·불일치가 생긴다. `GENERATED ALWAYS AS (expression) STORED` 컬럼은 DB가 삽입/갱신 시 자동 계산해 저장하고, 인덱스도 걸 수 있어 `LOWER(email)` 같은 함수 인덱스 대신 깔끔하게 대체할 수 있다.

```sql
ALTER TABLE users
  ADD COLUMN email_lower text
  GENERATED ALWAYS AS (LOWER(email)) STORED;

CREATE INDEX idx_users_email_lower ON users(email_lower);

-- INSERT/UPDATE 시 email_lower는 자동 채워짐
INSERT INTO users(email) VALUES ('User@Example.COM');
SELECT email_lower FROM users; -- 'user@example.com'
```

애플리케이션 코드가 실수로 소문자 변환을 빼먹어도 DB가 일관성을 보장하며, 트리거보다 가볍고 뷰보다 인덱싱이 자유롭다.

> 💡 **왜 중요한가**: 파생 데이터의 일관성 책임을 애플리케이션에서 DB로 옮겨, 어느 경로로 데이터가 들어와도 무결성이 깨지지 않는다.

### MySQL InnoDB Gap Lock — `REPEATABLE READ`에서 팬텀 리드를 막는 숨은 잠금

InnoDB의 기본 격리 수준 `REPEATABLE READ`에서 `SELECT ... FOR UPDATE`나 UPDATE는 조건에 걸린 행뿐 아니라 **행과 행 사이의 간격(gap)** 까지 잠근다. 이 gap lock 덕분에 다른 트랜잭션이 그 범위에 새 행을 INSERT하지 못해 팬텀 리드가 방지되지만, 원치 않는 데드락·INSERT 대기의 원인이 되기도 한다.

```sql
-- 트랜잭션 A
BEGIN;
SELECT * FROM orders WHERE user_id BETWEEN 100 AND 200 FOR UPDATE;
-- user_id 100~200 사이의 gap도 잠김

-- 트랜잭션 B
INSERT INTO orders(user_id, ...) VALUES (150, ...);
-- ⏳ A가 커밋할 때까지 대기 (gap이 잠겨 있음)
```

정확 매칭(`WHERE id = 1`)에 유니크 인덱스가 걸려 있다면 gap lock이 생략되므로, 인덱스 설계와 검색 조건을 명확히 하면 잠금 범위를 줄일 수 있다. 데드락 로그에 `lock_mode X locks gap before rec`이 보이면 gap lock이 원인이다.

> 💡 **왜 중요한가**: `SELECT ... FOR UPDATE`가 왜 관계없어 보이는 INSERT를 막는지 이해해야, 격리 수준·인덱스 튜닝으로 대기와 데드락을 근본적으로 줄일 수 있다.
