### 단일 DB 구조 — "하나의 진실 소스"가 주는 축복과 저주

모놀리스 아키텍처에서 가장 자주 마주치지만 가장 얕게 이해되는 주제입니다. "DB 하나 두면 되지 뭐가 어려워?"라는 반응이 흔한데, 시니어 관점에서 보면 **"단일 DB를 언제까지 유지할 것인가"** 는 시스템 수명 전체를 관통하는 아키텍처 결정입니다.

---

#### 1. "단일 DB"의 정확한 정의

단일 DB 구조란 **하나의 물리적(또는 논리적) 데이터베이스 인스턴스가 시스템의 모든 상태(state)를 담당하는 구조**입니다. 애플리케이션 서버는 여러 대여도 상관없습니다. 핵심은 **"쓰기 가능한 마스터가 하나"**, **"트랜잭션 경계가 DB 전역에서 성립"**, **"조인이 자유롭다"** 는 세 가지 성질입니다.

```
┌──────────┐   ┌──────────┐   ┌──────────┐
│  App #1  │   │  App #2  │   │  App #3  │
└────┬─────┘   └────┬─────┘   └────┬─────┘
     │              │              │
     └──────────────┼──────────────┘
                    │
                    ▼
         ┌────────────────────┐
         │   Single Database  │  ← 유일한 진실 소스(SSoT)
         │   (Primary/Master) │     ACID 전역 보장
         │                    │     JOIN 자유
         └────────────────────┘
```

여기에 **읽기 전용 리플리카** 몇 대를 붙여도 "단일 DB"라고 부를 수 있습니다. 쓰기 마스터가 하나면 논리적으로는 단일 DB입니다. 이 구분은 나중에 샤딩·CQRS를 배울 때 다시 등장합니다.

---

#### 2. 단일 DB가 주는 5가지 축복

##### (1) 트랜잭션 경계가 "공짜"다
서비스 레이어에서 `@Transactional` 하나 걸면 주문·재고·결제·로그가 한 커밋에 묶입니다. 분산 환경에서는 이 한 줄이 사가(Saga), 2PC, 이벤트 소싱으로 부풀어 오릅니다.

##### (2) JOIN이 자유롭다
```sql
SELECT o.id, u.name, p.title, c.name
FROM orders o
JOIN users u ON o.user_id = u.id
JOIN products p ON o.product_id = p.id
JOIN categories c ON p.category_id = c.id
WHERE o.created_at > NOW() - INTERVAL 7 DAY;
```
분산 DB에서 이걸 하려면 애플리케이션 레벨 조인(N+1 지옥)이나 데이터 웨어하우스로 우회해야 합니다.

##### (3) 강한 일관성(Strong Consistency)이 기본값
"방금 저장한 데이터를 방금 조회한다"는 요구가 무료입니다. 최종 일관성(eventual consistency)을 설계·설명·디버깅할 필요가 없습니다.

##### (4) 스키마·마이그레이션이 단순
Flyway/Liquibase 스크립트 하나면 끝. 여러 DB의 스키마 버전을 맞추는 오케스트레이션이 없습니다.

##### (5) 백업·복구·모니터링 지점이 하나
장애 시 "어디부터 봐야 하지?"의 답이 명확합니다. 운영 인력 1명이 커버 가능한 이유입니다.

---

#### 3. 단일 DB가 무너지는 4가지 지점

##### (1) 쓰기 처리량의 한계 (Write Bottleneck)
읽기는 리플리카로 스케일 아웃되지만, **쓰기는 마스터의 CPU/IO/네트워크·디스크 한도까지만** 갑니다. 통상 잘 튜닝된 PostgreSQL/MySQL 마스터는 초당 수천~수만 트랜잭션이 상한선입니다.

##### (2) 스키마가 조직 병목이 된다
팀이 10개 넘어가는 순간, 하나의 `users` 테이블에 20개 팀이 컬럼을 추가하려 대기 줄을 섭니다. 이게 **콘웨이 법칙(Conway's Law)이 DB에서 발현되는 순간** 입니다.

##### (3) 장애 반경(Blast Radius)이 100%
DB가 다운되면 서비스 전체가 다운됩니다. "사용자 프로필 조회만 안 되면 될 걸, 결제까지 다 죽어버리는" 상황이 생깁니다.

##### (4) 배포·마이그레이션 시 전체 정지
`ALTER TABLE`로 1억 row짜리 테이블에 컬럼을 추가하는 순간 서비스 전체가 락(lock)에 걸립니다. `pg_repack`, `pt-online-schema-change` 같은 도구로 완화는 가능하지만 근본적으로는 스케일링 한계입니다.

---

#### 4. 실제 사례 — "언제까지 단일 DB로 버틸 수 있는가"

| 회사 | 단일 DB 유지 규모 | 교훈 |
|---|---|---|
| **Stack Overflow** | 월 13억 페이지뷰까지 **단일 SQL Server** (2016년 기준) | 수직 확장(vertical scaling) + SSD + 캐싱으로 놀랄 만큼 오래 버틴다 |
| **Basecamp (37signals)** | 지금도 대부분 단일 MySQL | DHH가 공개적으로 "distributed monolith보다 낫다"고 옹호 |
| **Shopify** | 초기 ~2014년까지 단일 MySQL, 이후 **팟(Pod) 단위 샤딩**으로 이전 | 쇼핑몰별로 데이터를 물리적으로 분리, 각 팟은 여전히 "단일 DB" 성질 유지 |
| **GitHub** | 2010년대 중반까지 단일 MySQL 클러스터, 이후 **Vitess 기반 샤딩** | 단일 DB로 유니콘 규모까지 갔다가 필요할 때 쪼갬 |
| **Instagram** | 인수 당시 단일 PostgreSQL, 이후 기능별 분리 → 샤딩 | "가능한 한 오래 단일로" 전략의 대표 사례 |

공통 패턴: **모두 단일 DB로 시작해서, 정말 아플 때만 쪼갰습니다.** 처음부터 마이크로서비스·다중 DB로 간 스타트업 대부분은 조기 최적화(premature optimization)의 대가를 치렀습니다.

---

#### 5. 시니어 관점 — 언제 쓰고 언제 쓰면 안 되는가

##### ✅ 단일 DB를 유지해야 할 때
- **DAU 100만 미만, 초당 수백 write 이하** — 잘 튜닝하면 수직 확장으로 충분합니다.
- **팀이 하나~작은 여러 팀** — 스키마 소유권 다툼이 아직 없습니다.
- **비즈니스 도메인이 강하게 얽혀있는 초기** — 도메인 경계가 확정되지 않은 상태에서 DB를 쪼개면 나중에 되돌리는 데 6개월이 사라집니다.
- **트랜잭션 경계가 도메인의 본질일 때** — 결제, 재고, 회계 시스템은 강한 일관성이 곧 요구사항입니다.

##### ❌ 단일 DB를 고집하면 안 될 때
- **워크로드 성격이 극단적으로 다를 때** — OLTP(주문)와 OLAP(리포팅)를 한 DB에서 돌리면 리포트 하나가 프로덕션을 죽입니다. 최소한 리플리카/DW로 분리해야 합니다.
- **명확히 독립적인 바운디드 컨텍스트가 여럿일 때** — 예: 채팅 서비스와 결제 서비스가 조인할 일이 없다면 굳이 한 DB에 둘 이유가 없습니다.
- **글로벌 리전 서비스** — 지연 시간 요구가 있는 순간 단일 DB는 물리적으로 불가능합니다.
- **팀이 20개 이상, 스키마 변경 리드타임이 주(week) 단위로 늘어날 때** — 이건 기술 문제가 아니라 조직 문제이며, 답은 DB 분리입니다.

##### 시니어의 판단 프레임
> "단일 DB의 한계를 만나기 전까지는 절대 쪼개지 마라. 대신 **한계가 어디쯤 오는지 상시 계측**하라."

구체적으로:
- 마스터 CPU 사용률이 지속적으로 60% 이상 → 6개월 안에 대응 시작
- P99 쿼리 지연이 우상향 → 슬로우 쿼리 리팩터/인덱스 튜닝 우선
- 스키마 변경 리뷰 대기가 스프린트를 넘김 → **DB가 아니라 팀 구조를 먼저 의심**

---

> 💡 **왜 중요한가**: 단일 DB는 "당장 편한 선택"이 아니라 "시스템이 성숙해질 시간을 벌어주는 전략"이며, 이를 언제 벗어날지는 아키텍트의 가장 큰 판단 중 하나입니다.
