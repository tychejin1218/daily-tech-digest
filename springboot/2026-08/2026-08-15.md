### `HandlerInterceptor`의 `preHandle`에서 `false`를 반환해도 응답 본문이 없으면 클라이언트는 빈 200 OK를 받는다
Spring MVC의 `HandlerInterceptor.preHandle`이 `false`를 반환하면 컨트롤러 실행이 중단되지만, 응답 상태 코드나 본문을 직접 세팅하지 않으면 기본값인 `200 OK`가 그대로 나간다. 인증 실패나 rate limit 차단 로직을 인터셉터에 넣었는데 클라이언트 입장에서는 "성공했는데 데이터가 비어있음"으로 오해되는 사고가 흔히 발생한다. 반드시 `response.setStatus(401)` 같은 상태 코드 설정과 에러 페이로드 write를 함께 해야 한다.

> 💡 **왜 중요한가**: 인터셉터의 반환값은 "다음 체인 실행 여부"만 제어할 뿐, HTTP 응답 시맨틱은 개발자가 직접 책임져야 하기 때문이다.

### `@SpringBootTest`의 `webEnvironment = RANDOM_PORT`는 실제 톰캣을 띄우므로 `MockMvc`가 아닌 `TestRestTemplate`/`WebTestClient`를 써야 한다
`@SpringBootTest(webEnvironment = RANDOM_PORT)`는 서블릿 컨테이너를 실제로 부팅시켜 별도 스레드에서 요청을 처리한다. 이 상태에서 `MockMvc`를 주입받아 호출하면 톰캣을 우회한 별개의 요청 경로로 흘러가 필터 체인, 서블릿 컨테이너 레벨 인코딩, `HttpServletRequest` 속성이 실제 운영 환경과 달라진다. 반면 `MOCK` 환경에서는 톰캣이 뜨지 않아 `TestRestTemplate`이 연결에 실패한다 — 두 도구는 상호 배타적이다.

> 💡 **왜 중요한가**: 테스트 환경 설정과 요청 도구를 잘못 조합하면 "테스트는 통과하는데 실제 요청 흐름은 검증되지 않은" 위험한 그린 상태에 빠진다.
