### 1. Keyset Pagination(커서 기반 페이지네이션) — `OFFSET` 깊은 페이지의 성능 붕괴 피하기

`LIMIT ... OFFSET 100000`은 앞의 10만 행을 **읽고 버린 뒤** 다음 행을 반환하므로, 페이지가 뒤로 갈수록 선형적으로 느려진다. 대신 마지막으로 본 행의 정렬 키를 조건으로 넘겨 `WHERE (created_at, id) < (:lastCreatedAt, :lastId) ORDER BY created_at DESC, id DESC LIMIT 20`처럼 쓰면, 인덱스를 타고 곧장 시작 위치로 점프하므로 몇 페이지를 넘기든 일정한 속도를 유지한다. 정렬 키에 복합 인덱스를 걸고, 중복 값에 대비해 항상 고유 컬럼(보통 PK)을 tie-breaker로 함께 비교하는 것이 핵심이다.

> 💡 **왜 중요한가**: 무한 스크롤·대용량 목록에서 `OFFSET`은 뒤 페이지일수록 점점 느려지지만, 키셋 방식은 페이지 위치와 무관하게 항상 동일한 응답 속도를 보장한다.

### 2. Hibernate `hibernate.jdbc.batch_size` + `reWriteBatchedInserts` — 대량 INSERT를 네트워크 왕복 한 번으로 묶기

JPA로 엔티티 수천 건을 저장하면 기본적으로 INSERT 문이 한 건씩 따로 실행되어 DB 왕복이 건수만큼 발생한다. `hibernate.jdbc.batch_size=500`을 켜면 여러 INSERT를 JDBC 배치로 묶어 한 번에 전송하고(단, IDENTITY 전략은 배치가 불가능하므로 SEQUENCE/`pooled` 할당자를 써야 한다), PostgreSQL이라면 JDBC URL에 `reWriteBatchedInserts=true`를 추가해 배치를 단일 다중 행 INSERT로 재작성하면 효과가 극대화된다. 또한 루프 중간에 주기적으로 `flush()` + `clear()`를 호출해 1차 캐시가 무한정 쌓이지 않게 비워줘야 OOM을 피할 수 있다.

> 💡 **왜 중요한가**: 설정 한두 줄과 식별자 전략 변경만으로 수천 번의 DB 왕복이 수십 번으로 줄어, 배치/마이그레이션 작업 시간이 수십 배 단축된다.
