### 1. useId: "같은 컴포넌트를 두 번 렌더링했을 때" label-input 연결이 꼬이는 문제의 해결사

폼 컴포넌트에서 `<label htmlFor="email">`처럼 ID를 하드코딩하면, 같은 컴포넌트를 한 페이지에 두 번 쓸 때 ID가 충돌해서 라벨을 클릭해도 엉뚱한 input에 포커스가 간다. `Math.random()`이나 전역 카운터로 ID를 만들면 SSR hydration 시 서버/클라이언트 ID가 달라져 미스매치 경고가 뜨는데, React 18의 `useId()`는 컴포넌트 트리 위치 기반으로 안정적인 유니크 ID를 생성해 이 두 문제를 동시에 해결한다.

```jsx
function EmailField() {
  const id = useId();
  return (
    <>
      <label htmlFor={id}>이메일</label>
      <input id={id} type="email" />
    </>
  );
}
// <EmailField />를 두 번 렌더링해도 각각 ":r0:", ":r1:" 같은 고유 ID 생성
```

> 💡 **왜 중요한가**: 접근성(a11y)과 SSR hydration 안정성을 동시에 챙기는 유일한 공식 API이며, 폼 라이브러리(react-hook-form, Radix UI 등)가 내부적으로 반드시 쓰는 기본기다.

### 2. 커스텀 Hook의 "이름 규칙"은 린터용이 아니다: `use` 접두사가 없으면 React가 Hook 규칙을 추적하지 못한다

커스텀 Hook을 `getUser()`, `fetchData()`처럼 지으면 동작은 하는 것 같아도 React 컴파일러와 ESLint `react-hooks/rules-of-hooks`가 내부의 `useState`, `useEffect`를 "일반 함수 호출"로 오인해 조건부 호출 검증을 건너뛴다. 결과적으로 `if (조건) getUser()` 같은 코드가 린트를 통과하지만 런타임에 Hook 순서가 깨져 "Rendered fewer hooks than expected" 에러가 터진다.

```jsx
// ❌ 린터가 Hook으로 인식 못함 → 조건부 호출 경고 없음
function getUser(id) {
  const [user, setUser] = useState(null);  // 위험!
  useEffect(() => { /* ... */ }, [id]);
  return user;
}

// ✅ use 접두사 → Hook 규칙 강제 적용
function useUser(id) {
  const [user, setUser] = useState(null);
  useEffect(() => { /* ... */ }, [id]);
  return user;
}
```

> 💡 **왜 중요한가**: `use` 접두사는 단순 컨벤션이 아니라 React의 **정적 분석 계약(contract)** 이며, 이를 어기면 Hook 규칙 위반을 런타임에서야 발견하게 되는 지뢰를 심는 셈이다.
