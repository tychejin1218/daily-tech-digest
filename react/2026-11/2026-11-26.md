### 1. `useEffect`의 cleanup 함수가 "다음 effect 실행 전"에 호출된다는 함정 — 의존성이 바뀔 때마다 구독이 "해제 후 재구독"된다

많은 개발자가 `useEffect`의 cleanup을 "컴포넌트 언마운트 시에만 실행되는 뒷정리"로 오해한다. 실제로는 **의존성 배열이 바뀌어 effect가 재실행되기 직전**에도 cleanup이 먼저 호출되고, 그 후에 새 effect가 실행된다. 즉 WebSocket 구독, 이벤트 리스너, setInterval 같은 리소스는 "매 렌더마다 해제 → 재설정"되는 라이프사이클을 가진다.

```jsx
useEffect(() => {
  const socket = new WebSocket(url);  // ← url 바뀔 때마다 새 socket
  socket.onmessage = handleMessage;

  return () => {
    socket.close();  // ← 다음 effect 실행 직전에 호출됨 (언마운트 아님!)
  };
}, [url]);  // url이 바뀌면: 이전 socket.close() → 새 WebSocket 생성
```

이 메커니즘을 이해하지 못하면 "왜 구독이 중복으로 걸리지?" 또는 "왜 setInterval이 두 번 실행되지?" 같은 버그를 디버깅할 수 없다. React 18의 StrictMode는 개발 환경에서 effect를 의도적으로 두 번 실행해 이 cleanup 누락을 노출시킨다 — 즉 **cleanup은 선택이 아니라 effect의 필수 짝**이다.

> 💡 **왜 중요한가**: cleanup은 "언마운트 처리"가 아니라 "effect 재실행 전의 리소스 해제"이며, 이를 빠뜨리면 메모리 누수와 좀비 구독이 프로덕션에서 조용히 쌓인다.

### 2. `startTransition`과 `useDeferredValue`의 결정적 차이 — "state 업데이트를 미루는" 쪽과 "값의 반영을 미루는" 쪽

둘 다 React 18의 Concurrent 기능이고 "무거운 렌더링을 미룬다"는 점에서 비슷해 보이지만, **제어 지점이 정반대다**. `startTransition`은 **state 업데이트를 하는 쪽**(이벤트 핸들러)에서 "이 업데이트는 급하지 않다"고 선언하는 방식이고, `useDeferredValue`는 **값을 받는 쪽**(자식 컴포넌트)에서 "이 값의 반영이 늦어도 된다"고 선언하는 방식이다.

```jsx
// startTransition: 업데이트하는 쪽에서 제어 (내 코드가 setState 호출자)
function SearchInput() {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState([]);

  const handleChange = (e) => {
    setQuery(e.target.value);  // urgent (input 반응성 유지)
    startTransition(() => {
      setResults(heavySearch(e.target.value));  // non-urgent
    });
  };
}

// useDeferredValue: 받는 쪽에서 제어 (내가 받은 prop을 제어 못할 때)
function SearchResults({ query }) {  // ← query는 부모가 준 값
  const deferredQuery = useDeferredValue(query);  // 늦게 반영되는 복사본
  const results = useMemo(() => heavySearch(deferredQuery), [deferredQuery]);
  return <List items={results} />;
}
```

즉 **내가 setState를 호출하는 쪽이면 `startTransition`을, 남이 준 prop을 받는 쪽이면 `useDeferredValue`를** 쓴다. 라이브러리 컴포넌트처럼 외부에서 들어온 값은 내가 `setState` 호출 시점을 제어할 수 없으니 `useDeferredValue`가 유일한 선택지가 된다.

> 💡 **왜 중요한가**: 둘을 "동일한 기능의 두 가지 API"로 착각하면 제어할 수 없는 prop에 `startTransition`을 쓰려다 막히고, 반대로 내 setState에 `useDeferredValue`를 쓰려다 불필요한 간접 레이어를 만든다.
