### 1. `StringTemplate.STR."\{expr}"` 대신 `String.formatted()` 유지 — 템플릿 프리뷰에 의존하는 관성 벗어나기

Java 21~23에서 프리뷰로 등장한 String Templates(JEP 430)는 Java 23에서 **철회(withdrawn)** 되었고, Java 24/25에서도 재도입되지 않았다. 블로그 글만 보고 `STR."Hello \{name}"` 문법을 운영 코드에 넣었다면, JDK 업그레이드 시 컴파일 자체가 깨진다. 지금 시점에서 안전한 선택은 Java 15 정식인 `"Hello %s".formatted(name)` 또는 로그 프레임워크의 `{}` 플레이스홀더다.

```java
// ❌ Java 21~23 preview, Java 24+ 에서 사라짐
String msg = STR."User \{user.name()} logged in at \{Instant.now()}";

// ✅ Java 15+ 정식, 영원히 동작
String msg = "User %s logged in at %s".formatted(user.name(), Instant.now());

// ✅ 로그라면 아예 포매팅 자체를 프레임워크에 위임
log.info("User {} logged in at {}", user.name(), Instant.now());
```

JEP의 상태 전이(Preview → Second Preview → Standard)는 보장되지 않는다. **Preview 기능을 운영 코드에 쓰려면 "철회될 수 있다"는 전제를 깔고 써야 한다.** 특히 Amber 프로젝트 산하 문법 기능들은 설계 피드백에 따라 통째로 갈아엎히는 선례가 반복됐다.

> 💡 **왜 중요한가**: "Java N preview 기능 블로그를 보고 바로 도입" 관성은 JDK 업그레이드 때 기술 부채가 되어 돌아온다 — 특히 Amber(문법) 계열은 Loom/Panama 같은 런타임 JEP보다 철회 리스크가 훨씬 크다.

### 2. `Collectors.teeing(down1, down2, merger)` (Java 12 정식)로 "스트림을 두 번 돌리거나 중간 리스트로 받아서 두 집계" 관성 벗어나기

평균을 내려고 합계와 개수를 따로 구하거나, 최솟값·최댓값을 동시에 뽑으려고 스트림을 두 번 소비하거나 리스트로 받아서 재집계하는 코드는 아주 흔한 관성이다. `Collectors.teeing`은 **두 개의 다운스트림 콜렉터에 같은 요소를 동시에 흘려보내고**, 마지막에 BiFunction으로 합쳐주는 전용 콜렉터다. 한 번의 스트림 통과로 두 집계를 묶을 수 있다.

```java
// ❌ 스트림 두 번 소비 또는 중간 리스트 생성
List<Order> orders = fetchOrders();
long count = orders.stream().filter(Order::isPaid).count();
BigDecimal sum = orders.stream()
    .filter(Order::isPaid)
    .map(Order::amount)
    .reduce(BigDecimal.ZERO, BigDecimal::add);
Stats stats = new Stats(count, sum);

// ✅ Java 12+ 한 번의 스트림 통과로 두 집계 동시 수행
Stats stats = fetchOrders().stream()
    .filter(Order::isPaid)
    .collect(Collectors.teeing(
        Collectors.counting(),
        Collectors.mapping(Order::amount,
            Collectors.reducing(BigDecimal.ZERO, BigDecimal::add)),
        Stats::new
    ));

// ✅ min/max 동시 추출도 자연스럽게
Range<LocalDate> range = events.stream()
    .collect(Collectors.teeing(
        Collectors.minBy(Comparator.comparing(Event::at)),
        Collectors.maxBy(Comparator.comparing(Event::at)),
        (min, max) -> new Range<>(min.orElseThrow().at(), max.orElseThrow().at())
    ));
```

내부적으로 요소마다 두 콜렉터의 accumulator가 함께 호출되기 때문에 **O(2N)이 아니라 O(N)에 두 집계가 끝난다**. 실시간 지표 집계·대시보드 계산처럼 "하나의 데이터 피드에서 여러 통계를 뽑는" 패턴에서 특히 깔끔하다. 다만 다운스트림이 3개 이상이면 teeing 중첩이 되므로, 그 지점부터는 `record Accumulator`를 들고 `reduce`로 가는 게 더 읽기 쉽다.

> 💡 **왜 중요한가**: 평균·범위·히스토그램 같은 "같은 입력에 대한 두 집계"는 운영 지표 코드에서 매일 나오는 패턴 — teeing을 모르면 스트림 두 번 돌리거나 중간 컬렉션을 거쳐 메모리와 CPU를 두 배로 쓰게 된다.
