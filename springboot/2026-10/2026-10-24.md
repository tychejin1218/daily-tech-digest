### `@Transactional(readOnly = true)`는 **단순한 힌트가 아니다** — JPA에서 플러시 모드를 꺼서 더티 체킹 비용을 날리고, 복제본 라우팅까지 바꾼다

조회 전용 서비스 메서드에 `@Transactional(readOnly = true)`를 붙이면 Hibernate가 `FlushMode.MANUAL`로 전환해 영속성 컨텍스트의 스냅샷 비교(더티 체킹)를 건너뛴다. 또한 `AbstractRoutingDataSource` 기반의 Read/Write 분리 구조에서는 이 플래그가 복제본(Read Replica) 라우팅의 결정 키가 되므로, 빠뜨리면 조회 트래픽이 전부 Primary로 쏠려 마스터 CPU가 터진다. "성능 때문에 붙인다"는 설명보다 "스냅샷을 안 떠서 메모리와 CPU가 둘 다 절약된다"가 정확하다.

> 💡 **왜 중요한가**: readOnly를 안 붙인 조회 메서드 하나가 트래픽 피크에 마스터 DB를 다운시킨 장애 리포트는 한두 건이 아니다 — 심지어 쓰기 쿼리 한 줄 없어도 그렇다.

---

### `application.yml`의 `spring.jpa.open-in-view`는 **기본값이 `true`** — 뷰 렌더링이 끝날 때까지 DB 커넥션을 쥐고 있다

OSIV(Open Session In View)가 켜져 있으면 컨트롤러가 응답을 다 그리는 순간까지 영속성 컨텍스트와 DB 커넥션이 유지된다. API 응답 직렬화 중에 Lazy 로딩이 터져도 `LazyInitializationException`이 안 나와서 "편하다"는 착각을 주지만, 외부 API 호출이 섞인 컨트롤러에서는 커넥션 풀이 외부 레이턴시만큼 묶여서 커넥션 고갈로 전체 서비스가 멈춘다. Spring Boot는 켜두고 WARN 로그만 남기므로, 서비스 레이어에서 Fetch Join이나 DTO Projection으로 로딩을 끝내고 `open-in-view: false`로 끄는 것이 운영 표준이다.

> 💡 **왜 중요한가**: 평소엔 멀쩡하다가 외부 API 하나가 느려지는 순간 커넥션 풀이 터지면서 전체 API가 500을 뱉기 시작한다 — 범인은 OSIV인데 로그에는 "DB 커넥션 획득 실패"만 찍혀서 추적에 하루가 날아간다.
