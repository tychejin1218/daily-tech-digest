#### 0. 그날 아침의 재구성

수요일 23:40, 신입 PM이 신규 챗봇의 톤 테스트를 위해 로컬에서 Python 스크립트를 돌렸다.

```python
while True:
    resp = openai.chat.completions.create(

        messages=[{"role":"user","content": random_prompt()}]

    print(resp.choices[0].message.content)
```

의도는 "100번 정도 돌려보고 로그 보기". 실제로는 `break` 조건이 없었고, 노트북은 밤새 켜져 있었다. OpenAI SDK는 조직 공용 API Key를 쓰고 있었고, 그 키는 PM의 `.env` 파일에 평문으로 복사되어 있었다.

목요일 07:20, 재무팀 Slack에 Visa 사기 알림이 떴다. 07:48, OpenAI Billing Dashboard를 열자 **TPM 그래프가 평평한 천장을 찍고 있었다 — rate limit에 걸릴 때까지 올라간 호출량**. 08:14, CFO가 "이 돈 어느 팀이 썼는지 당장 보고해"라고 CTO에게 DM을 보냈다.

CTO는 대답할 수 없었다. 조직 전체가 **API Key 3개**(`prod`, `dev`, `experiments`)로 돌아가고 있었고, **누가 어떤 호출을 했는지에 대한 어떠한 기록도 없었기 때문이다**.

#### 1. 왜 "각 팀이 SDK 직접 호출"은 반드시 무너지는가

| 문제 | 서비스 직접 호출 방식 | 현실의 사고 |
|---|---|---|
| 비용 추적 | OpenAI 콘솔의 단일 라인 아이템 | "어느 팀이 썼냐"에 답 불가 → 예산 통제 불가 |
| Rate Limit | 각 서비스가 독립 재시도 → thundering herd | TPM 10만 중 챗봇 한 팀이 9.8만 소모, 결제팀 요약 기능 전면 중단 |
| 키 관리 | `.env` 복붙, GitHub 사고 년 2건 기본 | 전 직원이 rotate 당하는 금요일 밤 |
| PII 필터링 | 각 팀이 자체 구현 (또는 안 함) | 주민번호가 그대로 OpenAI 로그에 남음 |
| 모델 교체 | 각 서비스 코드 수정 → 배포 N번 | `gpt-4o` → `gpt-4o-2024-11-20` 교체에 2주 |
| 감사 추적 | 없음 | 법무팀의 "어제 15시 요청 로그 주세요"에 "없는데요" |
| 폴백/재시도 | 각 팀이 중구난방으로 구현 | OpenAI 47분 장애에 어떤 팀은 살고 어떤 팀은 죽음 |

> 백엔드 관점에서 이건 **"각 마이크로서비스가 DB에 직접 붙던 2010년대 초의 Enterprise Service Bus 이전 시대"와 정확히 같은 구조**다. 당시 해법은 API Gateway였다. LLM도 같은 지점에 도달했다.

#### 2. LLM Gateway란 무엇인가

**모든 LLM 호출이 반드시 통과하는 단일 프록시 레이어**. API Gateway (Kong, Zuul) 의 LLM 버전이라고 보면 된다.

```
┌─────────────────────────────────────────────────────────────┐
│                    서비스 레이어                              │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐   │
│  │ 챗봇팀    │  │ 요약팀    │  │ 검색팀    │  │ 내부 PoC │   │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘  └────┬─────┘   │
└───────┼─────────────┼─────────────┼─────────────┼──────────┘
        │             │             │             │
        │ OpenAI 호환 │ API (팀별 가상 키)         │
        ▼             ▼             ▼             ▼
┌─────────────────────────────────────────────────────────────┐
│                   LLM Gateway                                │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ 1. Auth (팀 단위 Virtual Key → 실제 Provider Key)      │   │
│  │ 2. Rate Limit (팀/사용자별 TPM, RPM, 일 예산)          │   │
│  │ 3. PII Scrub (주민번호/카드번호 정규식 + NER)          │   │
│  │ 4. Routing (gpt-4o / claude / 자체모델 선택)           │   │
│  │ 5. Semantic Cache (앞 Day 139 참조)                    │   │
│  │ 6. Fallback (OpenAI 장애 → Bedrock 자동 스위치)        │   │
│  │ 7. Observability (요청/응답/비용/latency 전부 기록)     │   │
│  │ 8. Prompt Firewall (jailbreak/프롬프트 인젝션 탐지)     │   │
│  └──────────────────────────────────────────────────────┘   │
└──────────┬────────────┬────────────┬────────────┬───────────┘
           ▼            ▼            ▼            ▼
      ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐
      │ OpenAI  │  │Anthropic│  │ Bedrock │  │ vLLM    │
      └─────────┘  └─────────┘  └─────────┘  └─────────┘
```

서비스는 **OpenAI SDK를 그대로 쓰되 `base_url`만 Gateway로 바꾼다**. 이게 핵심 설계다.

```python
# 서비스 코드 (변경점: base_url + 팀 전용 키)
client = OpenAI(
    base_url="https://llm-gateway.corp.internal/v1",
    api_key="team_chatbot_vk_a9f3..."  # 가상 키. 진짜 OpenAI 키 아님
)
```

#### 3. 핵심 기능 ① Virtual Key — 돈과 책임을 분리하는 장치

**Virtual Key**는 Gateway가 발급하는 가짜 API 키다. 서비스는 이것만 안다. Gateway는 내부적으로 매핑한다:

```
team_chatbot_vk_a9f3...  →  OpenAI 실제 키 sk-proj-xxx
                            + 월 예산 $3,000
                            + 허용 모델: [gpt-4o-mini, gpt-4o]
                            + TPM 한도: 50,000
                            + 소유자: chatbot-team@company.com
                            + Slack 알림: #chatbot-ops
```

**이 구조로 얻는 것**:
- 유출 시 Gateway에서 즉시 revoke → OpenAI 콘솔 접근 불필요
- 팀별 비용이 **처음부터** 분리됨 → 재무팀 질문에 즉답 가능
- 예산 80% 도달 시 자동 Slack 알림, 100% 시 자동 차단

위 사고의 PM이 Virtual Key를 썼다면: **$3,000 한도에서 호출 차단, 06:00경 Slack 알림, 재무팀 콜 없음**.

#### 4. 핵심 기능 ② Semantic Routing — 질문 난이도에 맞춰 모델 선택

Gateway 레이어에서 **분류기(classifier)** 를 돌려 요청을 라우팅한다.

```
"오늘 날씨 어때?"              → gpt-4o-mini  ($0.00015/1K)
"이 계약서 리스크 분석해줘"      → claude-sonnet ($0.003/1K)
"Python 코드 리뷰 해줘"         → claude-sonnet
"고마워요"                      → 캐시된 템플릿 응답 (0원)
```

앞서 Day 136(LLM Routing & Fallback)에서 다룬 패턴을 **각 서비스가 구현하는 대신 Gateway가 공통 제공**하는 것이 포인트다. 챗봇팀이 "우리는 품질 우선", 분석팀이 "우리는 비용 우선"처럼 **정책만 선언**하면 된다.

#### 5. 핵심 기능 ③ Streaming을 깨지 않고 통과시키기 (가장 어려운 지점)

LLM 응답은 **Server-Sent Events (SSE)** 스트리밍이 기본이다. Gateway가 어설프게 설계되면 여기서 무너진다.

❌ **잘못된 구현**: Gateway가 전체 응답을 버퍼링해서 로그 찍고 한 번에 반환 → 사용자 경험 완전 파괴 (타이핑 효과 사라짐, 첫 토큰까지 15초)

✅ **올바른 구현**: SSE chunk를 **pass-through 하면서 동시에 비동기로 집계**

```
클라이언트 ←── chunk pass-through ──── Gateway ←── chunk ── Provider
                                        │
                                        └─▶ 비동기 buffer
                                               │
                                               ▼
                                        [완료 시] 토큰 집계, 비용 계산,
                                                 Observability 기록,
                                                 PII 재스캔
```

여기서 `Content-Length` 헤더를 건드리지 않는 것, `Transfer-Encoding: chunked`를 유지하는 것, OpenAI SDK가 기대하는 `data: [DONE]` sentinel을 꼭 흘려보내는 것 — 이 세 가지를 틀리면 **클라이언트 SDK가 조용히 응답을 반토막만 받고도 success를 반환**한다.

#### 6. 트레이드오프 — 공짜가 아니다

| 얻는 것 | 잃는 것 |
|---|---|
| 비용 통제, 보안 통제 | **추가 latency** (평균 20~80ms, 자체 캐시로 상쇄 가능) |
| 팀별 가시성 | **단일 장애점 (SPOF)** → HA 필수, 리전 이중화 |
| 통일된 PII/Audit | **플랫폼팀 운영 비용** (전담 2~3명) |
| 모델 교체 유연성 | **최신 모델 기능 lag** (gpt-4o가 새 feature 내면 Gateway가 지원할 때까지 못 씀) |
| Prompt Injection 방어 | **스트리밍 복잡도**, 긴 context window 메모리 압박 |

> 가장 자주 과소평가되는 비용: **"Gateway가 지원하지 않는 최신 파라미터 때문에 서비스팀이 우회로를 만들다가 Gateway의 존재 이유를 무너뜨리는"** 조직적 실패. Gateway 팀은 provider SDK 업데이트를 **48시간 내 반영하는 SLA**를 반드시 선언해야 한다.

#### 7. 실제 사례

**Cloudflare AI Gateway (2023~)**  
엣지에서 OpenAI/Anthropic/Workers AI를 통합 프록시. 캐시, Rate Limit, Log를 한 번에 제공. 선택 이유: Cloudflare는 이미 전 세계에 엣지 노드를 갖고 있어 **latency overhead를 네트워크 지름길로 상쇄**함.

**Portkey, LiteLLM, Helicone (OSS/SaaS)**  
자체 구축 전 1차 평가 대상. LiteLLM은 특히 "OpenAI SDK 호환 프록시"의 사실상 표준. **직원 100~500명 규모 조직은 90% 이상이 여기서 시작하면 된다**.

**Microsoft 내부 Gateway (AOAI 기반)**  
GitHub Copilot 포함 수십 개 내부 제품이 단일 Gateway를 통과. 선택 이유: 각 팀이 Azure Subscription을 따로 쓰면 **quota 협상이 불가능**. Gateway가 pooled quota를 중앙에서 분배.

**Netflix의 Metaflow + Model Serving**  
전통적 ML이었지만 LLM 시대 들어 동일 패턴으로 확장. 핵심은 **"플랫폼팀이 제공하는 SDK만으로 모든 호출이 통과"** — 이게 지켜지면 사후 감사가 가능해짐.

**토스, 쿠팡 (추정)**  
공식 공개는 없지만, 이 규모의 조직이 LLM을 쓰면서 Gateway를 두지 않는 선택지는 사실상 존재하지 않는다. 금융/커머스는 **PII 스크러빙과 감사 로그가 법적 요구사항**.

#### 8. 시니어 백엔드의 판단 기준 — 언제 쓰고, 언제 쓰면 안 되는가

**지금 당장 도입해야 하는 신호**
- LLM을 호출하는 서비스가 **3개 이상**이거나 곧 3개가 된다
- 월 LLM 비용이 **$5,000을 넘겼다** (팀별 비용 분배 질문이 시작됨)
- 금융/의료/공공 등 **PII 감사 로그가 법적 요구**
- OpenAI 장애 한 번이라도 겪어봤다 (폴백 니즈 체감)
- API Key가 **3개 이상 돌아다니고 있다**

**아직 쓰면 안 되는 신호**
- 단일 팀, 단일 제품, PoC 단계 → **LiteLLM 라이브러리 임포트**로 충분. 서버 띄우지 마라.
- 극단적 latency 요구 (실시간 음성 agent, p99 < 100ms) → Gateway hop이 깨짐. **엣지 배포 또는 직호출** 고려.
- 플랫폼팀이 없거나 전담할 사람이 없음 → Gateway는 운영 비용이다. **관리할 사람 없이 세우면 반드시 SPOF로 변한다**.

**중간 전략: SaaS로 시작**  
Portkey/Helicone에 월 $200 쓰고 운영 부담 없이 **가시성 먼저 확보**. 비용/규모가 임계치를 넘으면 self-host로 이전. 많은 시니어가 이 경로를 추천한다 — 첫 구축을 자체로 하면 거의 반드시 1차 설계에서 **스트리밍 또는 폴백을 깨뜨리고 재작업**한다.

> 💡 **왜 중요한가**: LLM Gateway는 "모델이 뭘 할 수 있는가"의 문제가 아니라 **"조직이 LLM을 쓰면서도 파산·유출·감사실패 없이 살아남는가"의 문제** — 즉 LLM 시대의 API Gateway이자, 플랫폼팀이 비즈니스에 증명해야 하는 **첫 번째 거버넌스 자산**이다.
