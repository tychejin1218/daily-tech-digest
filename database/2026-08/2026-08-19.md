### MySQL `Optimizer Trace` — 옵티마이저가 "왜 그 실행 계획을 골랐는지" 직접 물어보기

`EXPLAIN`은 결과만 보여주지만 `optimizer_trace`는 옵티마이저가 후보 계획들을 비교하고 비용을 계산한 전 과정을 JSON으로 뱉어낸다. `SET optimizer_trace='enabled=on'` 후 쿼리를 실행하면 `INFORMATION_SCHEMA.OPTIMIZER_TRACE`에서 각 인덱스의 예상 rows, cost, 왜 특정 인덱스가 탈락했는지까지 볼 수 있다. "이 쿼리 분명 인덱스 있는데 왜 풀스캔 타지?"의 답이 여기에 있다.

```sql
SET optimizer_trace='enabled=on';
SELECT * FROM orders WHERE user_id = 100 AND status = 'PAID';
SELECT trace FROM INFORMATION_SCHEMA.OPTIMIZER_TRACE\G
-- "range_scan_alternatives" 섹션에서 각 인덱스 후보의 cost 비교
-- "rows_estimation"에서 실제로 몇 행을 예상했는지 확인
```

트레이스를 보면 옵티마이저가 통계 오차 때문에 실제로는 100행짜리 인덱스 스캔을 100만행으로 착각해 풀스캔을 골랐다는 사실이 드러난다. `ANALYZE TABLE`로 통계를 갱신하거나 `FORCE INDEX`로 강제하는 근거가 이 트레이스다. 다만 트레이스 자체가 쿼리당 수 KB의 메모리를 먹으므로 프로덕션에서는 세션 단위로만 켜야 한다.

```
[EXPLAIN]           [OPTIMIZER_TRACE]
"인덱스 안 씀"  →  "왜 안 썼는지 이유 6가지 + 비용 계산식 전체"
"rows: 500000"  →  "이 500000이 통계 기반 추정임을 실제 값과 비교"
```

> 💡 **왜 중요한가**: `EXPLAIN`으로 "안 좋은 계획"은 알 수 있어도 "왜 옵티마이저가 그걸 골랐는지"는 알 수 없다. 트레이스는 인덱스 힌트가 필요한지, 통계 갱신이 답인지, 쿼리 재작성이 답인지를 근거 있게 결정하게 해준다.

### PostgreSQL `pg_stat_statements` — "느린 쿼리 하나"가 아니라 "누적으로 서버를 죽이는 쿼리"를 찾는 법

느린 쿼리 로그는 개별 실행이 임계값을 넘긴 쿼리만 잡지만, 실제 프로덕션을 마비시키는 건 "1ms짜리인데 초당 5만 번 실행되는 쿼리"인 경우가 더 많다. `pg_stat_statements` 확장은 쿼리를 파라미터 제거한 형태로 정규화해서 `total_exec_time`, `calls`, `mean_exec_time`, `rows`, `shared_blks_hit/read`를 누적 집계한다.

```sql
-- 서버 전체에서 CPU 시간 가장 많이 잡아먹는 쿼리 TOP 10
SELECT query, calls, total_exec_time, mean_exec_time,
       shared_blks_read, shared_blks_hit
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

-- 캐시 히트율이 낮은 쿼리 (디스크 I/O 유발 주범)
SELECT query, calls,
       shared_blks_hit::float / NULLIF(shared_blks_hit + shared_blks_read, 0) AS hit_ratio
FROM pg_stat_statements
WHERE shared_blks_read > 10000
ORDER BY hit_ratio ASC;
```

관점을 `mean_exec_time`(평균이 느린 쿼리)에서 `total_exec_time = calls × mean`(서버 자원을 실제로 먹는 쿼리)으로 바꾸는 순간 최적화 우선순위가 완전히 달라진다. 평균 0.5ms인데 하루 1억 번 호출되는 캐시 조회 쿼리가 6분짜리 배치 쿼리보다 더 많은 CPU를 쓰고 있는 경우가 흔하다.

```
[슬로우 쿼리 로그 관점]    [pg_stat_statements 관점]
"이 쿼리 5초 걸림!"     →  "이 5초짜리는 하루 3번 실행"
                           "이 2ms짜리는 하루 5000만 번 실행 → 총 100분"
                           → 후자를 먼저 잡아라
```

> 💡 **왜 중요한가**: "느린 쿼리"와 "서버를 죽이는 쿼리"는 다르다. 슬로우 로그만 보고 최적화하면 정작 CPU의 70%를 먹는 초고속-초빈도 쿼리를 놓친다.
