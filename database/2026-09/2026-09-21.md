### PostgreSQL `pg_stat_statements` — "느린 쿼리 하나"가 아니라, "누적 시간이 가장 큰 쿼리 패턴"을 찾는 진짜 병목 탐지기

`slow_query_log`는 "1초 넘는 쿼리"만 잡지만, 진짜 병목은 0.05초짜리가 하루 1억 번 실행되는 쿼리인 경우가 많다. `pg_stat_statements`는 쿼리를 파라미터 제거된 "정규화된 패턴"으로 묶어서 `total_exec_time`, `calls`, `mean_exec_time`, `rows`를 누적 집계한다. 즉, "가장 오래 걸리는 개별 쿼리"가 아니라 "시스템 전체에서 누적 CPU를 가장 많이 먹는 패턴"을 찾을 수 있다는 뜻이다.

```sql
-- postgresql.conf: shared_preload_libraries = 'pg_stat_statements'
CREATE EXTENSION pg_stat_statements;

-- 시스템 전체에서 총 실행 시간이 가장 긴 쿼리 TOP 10
SELECT
    substring(query, 1, 80) AS query,
    calls,
    round(total_exec_time::numeric, 2) AS total_ms,
    round(mean_exec_time::numeric, 2) AS mean_ms,
    round((100 * total_exec_time / sum(total_exec_time) OVER ())::numeric, 2) AS pct
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

핵심은 `pct` 컬럼이다. 단일 쿼리 튜닝은 "이 쿼리를 100ms → 10ms로 줄였다"에서 끝나지만, `pg_stat_statements`는 "이 패턴이 전체 DB 시간의 43%를 차지한다"를 보여준다. 후자를 10%로 줄이면 시스템 전체 처리량이 문자 그대로 배가 된다. `pg_stat_statements_reset()`으로 주기적으로 리셋하고, 배포 전후 diff를 뜨면 "이 배포로 인해 어떤 쿼리 패턴이 새로 생겼는지"까지 잡을 수 있다.

> 💡 **왜 중요한가**: "느린 쿼리 하나 잡기"는 이벤트 대응이고, "누적 시간 상위 패턴 잡기"는 용량 계획이다 — 스케일 아웃 전에 먼저 봐야 할 지표다.

### MySQL `Online DDL`과 `ALGORITHM=INSTANT` — 1억 행 테이블에 컬럼 추가를 "메타데이터만 바꿔서" 1초 만에 끝내는 8.0의 신무기

과거 MySQL에서 `ALTER TABLE ... ADD COLUMN`은 테이블을 통째로 복사(`ALGORITHM=COPY`)하거나, 그나마 나은 `INPLACE`도 전체 행을 재작성해서 1억 행이면 수 시간 락+디스크 폭발이 일반적이었다. MySQL 8.0.12부터는 `ALGORITHM=INSTANT`가 도입되어, 컬럼 추가/드롭/이름 변경 같은 특정 DDL을 **테이블 데이터를 건드리지 않고 데이터 딕셔너리만 갱신**한다. 실행 시간은 행 수와 무관하게 상수 시간이다.

```sql
-- 1억 행 테이블에도 즉시 완료 (0.1초 이하)
ALTER TABLE orders
  ADD COLUMN discount_rate DECIMAL(5,2) DEFAULT 0.00
  ALGORITHM=INSTANT, LOCK=NONE;

-- 어떤 DDL이 INSTANT인지 확인
-- 지원: ADD COLUMN(맨 뒤), DROP COLUMN(8.0.29+), RENAME COLUMN, 
--       SET/DROP DEFAULT, MODIFY ENUM 값 추가
-- 미지원: 컬럼 순서 지정(AFTER), PK/인덱스 변경, 컬럼 타입 변경

-- INSTANT ADD 이력 확인 (8.0.29+)
SELECT NAME, INSTANT_COLS 
FROM INFORMATION_SCHEMA.INNODB_TABLES 
WHERE NAME = 'mydb/orders';
```

단, 함정이 있다. `INSTANT`로 추가된 컬럼은 실제 행 데이터에 물리적으로 존재하지 않고, 조회 시 "기본값 오버레이" 방식으로 채워진다. 즉, 대량 `UPDATE`가 발생하면 그때 진짜로 행이 재작성되며 성능 특성이 바뀔 수 있다. 또 MySQL 8.0.29 이전엔 INSTANT ADD는 **테이블당 한 번만** 가능했고, 8.0.29+에서 다중 지원되지만 여전히 위치 지정 불가 등의 제약이 있다. `pt-online-schema-change`나 `gh-ost` 같은 외부 도구를 쓰기 전에, "이 DDL이 INSTANT로 되는지"부터 확인하는 습관이 배포 다운타임을 없앤다.

> 💡 **왜 중요한가**: 서비스 중단 없는 스키마 변경은 더 이상 "고급 DBA의 마법"이 아니라, 지원 여부만 알면 되는 문법 한 줄의 문제다 — 모르면 밤샘 마이그레이션, 알면 커피 한 잔.
