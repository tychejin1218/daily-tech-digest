### 1. `inline fun <reified T>` vs `KClass<T>`: "제네릭을 런타임에 살려두는" 두 가지 방법, 그리고 성능의 거래

Kotlin에서 런타임에 제네릭 타입을 다루는 방법은 두 가지다. `reified`는 inline 함수와 결합해 컴파일 타임에 타입을 "복사해 심어넣는" 방식이고, `KClass<T>`는 `Class.forName`처럼 메타데이터 객체를 명시적으로 전달받는 방식이다. 전자는 호출부가 뚱뚱해지는 대신 `T::class.java`를 그냥 쓸 수 있고, 후자는 바이트코드 비대화 없이 유연하지만 `fromJson(json, User::class.java)`처럼 명시적 전달이 필요하다.

```kotlin
// ① reified: 호출부가 자연스럽지만 inline 비용을 치름
inline fun <reified T> Gson.fromJson(json: String): T =
    fromJson(json, T::class.java)

val user = gson.fromJson<User>(jsonString)  // 깔끔

// ② KClass: 유연하지만 타입을 명시적으로 넘겨야 함
fun <T : Any> Gson.fromJson(json: String, clazz: KClass<T>): T =
    fromJson(json, clazz.java)

val user = gson.fromJson(jsonString, User::class)  // 타입 전달 필요
```

```
[reified]                           [KClass<T>]
호출부 A ─┐                          호출부 A ─┐
호출부 B ─┼→ 각자 바이트코드 복제     호출부 B ─┼→ 함수 1개 공유 + KClass 인자
호출부 C ─┘   (inline 비용 ↑)        호출부 C ─┘   (런타임 전달 비용)
```

**트레이드오프**:
- `reified`: 호출부가 많으면 바이트코드 비대화, 공개 라이브러리 API로 쓰면 ABI 안정성 저하
- `KClass<T>`: 호출부가 지저분해지지만 리플렉션 캐싱, 전략 패턴, DI 등록 등 "타입을 변수로 저장"해야 하는 경우에 유일한 답

실무 기준: **"호출자가 매번 다른 타입으로 호출하는가"** → `reified`, **"타입이 변수로 흘러다니는가(Map<KClass, Handler>)"** → `KClass<T>`.

> 💡 **왜 중요한가**: `reified`는 편해 보여서 남발하기 쉽지만, 공개 SDK에서 쓰면 호출자 바이트코드를 강제로 부풀리는 "강요된 비용"이 된다. ObjectMapper나 Handler 레지스트리처럼 타입을 저장·검색해야 하는 구조에서는 `KClass<T>`가 설계적으로 더 정직하다.

### 2. `operator fun invoke`: 클래스를 "함수처럼" 호출하는 Kotlin의 문법 설탕, 그리고 UseCase 패턴의 비밀

`operator fun invoke`를 정의하면 **객체를 함수처럼 호출**할 수 있다. `userUseCase.execute(id)`가 아니라 `userUseCase(id)`가 가능해지는 것. Clean Architecture의 UseCase 패턴, 함수형 DSL, Factory에서 암묵적으로 쓰이지만, 그 본질은 "**상태를 가진 람다**"를 만드는 것이다.

```kotlin
// ① 전형적인 UseCase 패턴
class GetUserUseCase(
    private val userRepository: UserRepository,
    private val cache: UserCache,
) {
    operator fun invoke(userId: Long): User =
        cache.get(userId) ?: userRepository.findById(userId).also {
            cache.put(userId, it)
        }
}

// 호출부가 "함수 호출"처럼 보임
@Service
class UserService(private val getUser: GetUserUseCase) {
    fun handle(id: Long) = getUser(id)  // getUser.invoke(id) 와 동일
}
```

**왜 그냥 `fun execute()`로 안 쓰고 `invoke`를 쓰는가?**

```
[fun execute()]                     [operator fun invoke()]
UseCase = "객체 + 메서드"            UseCase = "호출 가능한 단위"
                                    
getUser.execute(id)                 getUser(id)
├─ 객체 지향적 관점                  ├─ 함수형 관점
└─ "이 객체의 동작을 호출"           └─ "이것은 그냥 함수다"
                                    
                                    → 람다로 치환 가능
                                    → 고차 함수에 넘기기 자연스러움
                                    val fn: (Long) -> User = getUser
```

**주의할 함정**:
- `invoke`는 **오버로드 가능**하다. `invoke(id: Long)`, `invoke(name: String)` 둘 다 정의하면 호출부에서 `getUser(1L)`과 `getUser("kim")`이 자동 분기된다. 편해 보이지만 **가독성을 해친다**.
- 코루틴과 결합할 때는 `suspend operator fun invoke`로 선언해야 하며, 이때는 함수 타입이 `suspend (Long) -> User`로 바뀐다.
- `companion object`에 `invoke`를 넣으면 **생성자처럼 보이는 팩토리**가 된다 (`UserId("kim")` ← 사실은 `UserId.Companion.invoke("kim")`).

```kotlin
class UserId private constructor(val value: String) {
    companion object {
        operator fun invoke(raw: String): UserId {
            require(raw.isNotBlank()) { "blank id" }
            return UserId(raw)
        }
    }
}

val id = UserId("kim")  // 생성자처럼 보이지만 사실은 검증 팩토리
```

> 💡 **왜 중요한가**: `invoke`를 "그냥 간결한 호출"로만 이해하면 `execute()`의 더 명시적인 버전으로 끝나지만, 본질은 **"객체를 함수 타입으로 취급 가능하게 만드는 것"**이다. 이것이 UseCase를 `(Input) -> Output` 람다로 테스트하거나 DI 없이 조합할 수 있게 해주고, Kotlin의 함수형 설계가 객체 지향과 자연스럽게 섞이는 지점이다.
