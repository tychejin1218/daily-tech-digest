### `@Observed` + Micrometer로 메서드 단위 관측성(트레이싱·메트릭) 한 번에 계측하기

Spring Boot 3.2+에서는 `@Observed(name = "order.place")`만 붙이면 Micrometer Observation API가 해당 메서드 호출을 span(트레이싱)과 timer(메트릭)로 동시에 기록한다. 별도의 `@Timed`/`@NewSpan`을 겹쳐 붙일 필요 없이 하나의 어노테이션이 OpenTelemetry·Zipkin·Prometheus로 자동 전파된다.

```kotlin
@Configuration
class ObservationConfig {
    @Bean
    fun observedAspect(registry: ObservationRegistry) = ObservedAspect(registry)
}

@Service
class OrderService {
    @Observed(name = "order.place", contextualName = "place-order",
              lowCardinalityKeyValues = ["channel", "web"])
    fun place(cmd: PlaceOrder): OrderId { /* ... */ }
}
```

> 💡 **왜 중요한가**: 트레이싱 라이브러리와 메트릭 라이브러리가 분리되어 있던 시절의 이중 계측 코드를 걷어내고, 관측성 API를 한 축으로 통일할 수 있다.

### `spring.task.execution.pool.*` 튜닝 없이 `@Async` 쓰면 요청 폭주에 그대로 무너진다

Spring Boot의 기본 `TaskExecutor`는 core 8 / queue `Integer.MAX_VALUE`라 큐가 무한히 쌓이며 힙만 부풀리고, max-size는 사실상 발동되지 않는다. `application.yml`에서 큐 용량을 명시하고 `rejection-policy`를 지정해야 백프레셔가 동작한다.

```yaml
spring:
  task:
    execution:
      pool:
        core-size: 16
        max-size: 64
        queue-capacity: 200
        keep-alive: 60s
      thread-name-prefix: async-
      shutdown:
        await-termination: true
        await-termination-period: 20s
```

`RejectedExecutionHandler`를 `CallerRunsPolicy`로 두면 큐가 가득 찼을 때 호출 스레드에서 실행되어 자연스러운 백프레셔가 걸린다.

> 💡 **왜 중요한가**: 기본값을 그대로 두면 트래픽 스파이크 시 태스크가 무한 큐잉되어 OOM으로 이어지지만, 큐 용량과 거절 정책만 잡아도 시스템이 스스로 부하를 조절한다.
