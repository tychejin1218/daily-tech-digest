### MySQL `innodb_flush_log_at_trx_commit` — 커밋 1건당 fsync 1번, 성능과 내구성의 다이얼을 직접 돌리기

InnoDB는 트랜잭션 커밋 시점마다 redo log를 디스크에 강제 동기화(fsync)하는데, 이 파라미터가 그 동작을 제어한다. `1`(기본)은 커밋마다 fsync — ACID 완전 보장이지만 초당 커밋 수가 fsync 지연에 묶인다. `2`는 커밋 시 OS 페이지 캐시에만 쓰고 1초마다 fsync — OS 크래시 시 최대 1초 손실, 하지만 처리량이 3~10배 뛴다. `0`은 아예 1초마다 커밋 여부 무관 fsync — MySQL 프로세스 죽어도 1초 유실.

```sql
-- 배치 잡, 로그성 데이터: 2로 낮춰 처리량 확보
SET GLOBAL innodb_flush_log_at_trx_commit = 2;

-- 금융/결제: 1 유지, 대신 SSD/NVMe + binlog group commit로 fsync 자체를 빠르게
```

실무에서 흔한 실수: "우리 서버 왜 이렇게 느려요?" → 알고 보니 `sync_binlog=1` + `innodb_flush_log_at_trx_commit=1` 조합인데 HDD를 쓰고 있음. fsync 한 번에 10ms, 초당 100 커밋이 상한이다. 반대로 `2`로 바꿔놓고 "왜 재부팅 후 데이터가 사라졌지?" 하는 것도 매우 위험한 반대 방향 실수.

> 💡 **왜 중요한가**: TPS가 안 나오는 원인의 절반은 CPU도 인덱스도 아닌 fsync 대기이며, 이 다이얼 하나가 내구성과 처리량 사이에서 실제로 어디에 서 있는지를 결정한다.

### JPA `OSIV(Open Session In View)` — 컨트롤러/뷰까지 영속성 컨텍스트를 늘려두는 스프링의 기본값, 편리함의 대가

Spring Boot는 `spring.jpa.open-in-view=true`가 기본값이라, HTTP 요청이 컨트롤러에 진입할 때 영속성 컨텍스트를 열고 뷰 렌더링이 끝날 때까지 유지한다. 덕분에 컨트롤러에서 `order.getItems()` 같은 Lazy Loading이 그냥 동작하지만, DB 커넥션도 그동안 계속 붙잡고 있다는 뜻이다. 트래픽이 몰리면 커넥션 풀 고갈 + 외부 API 호출 중에도 커넥션 점유가 겹쳐 조용히 병목이 된다.

```yaml
# application.yml
spring:
  jpa:
    open-in-view: false  # 시작 시 WARN 로그 사라진다면 → 이 설정 안 한 것
```

OFF로 바꾸면 서비스 레이어(트랜잭션 종료) 이후 Lazy 접근 시 `LazyInitializationException`이 터진다. 해결책은 **서비스에서 필요한 데이터를 미리 fetch join / DTO projection으로 뽑아오기** — 결국 "어디까지가 트랜잭션 경계인가"를 명시적으로 설계하게 만든다. 유명 백엔드 팀들이 신규 프로젝트에서 OSIV=false를 표준으로 삼는 이유다.

트레이드오프: OFF는 성능·경계 명확성↑, 개발 편의성↓. ON은 프로토타이핑 속도↑, 프로덕션 스케일에서 커넥션 풀 튜닝 지옥↓.

> 💡 **왜 중요한가**: "커넥션 풀을 아무리 늘려도 왜 자꾸 timeout이 나지?"의 답이 대체로 OSIV=true이며, 이 한 줄 설정이 트랜잭션 경계와 아키텍처 사고방식을 통째로 바꾼다.
