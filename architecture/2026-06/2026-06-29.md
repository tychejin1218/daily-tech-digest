### 레이어드 아키텍처: Controller-Service-Repository의 본질과 함정

레이어드 아키텍처는 "요청이 들어오면 위에서 아래로 흘러간다"는 단순한 원칙으로 동작하지만, 그 단순함을 유지하기 위한 규약은 의외로 엄격하다. 단순히 디렉터리 세 개를 만드는 것이 아니라, **의존성 방향·계층 책임·트랜잭션 경계** 세 가지 약속이 깨지는 순간 모놀리스는 빅 머드볼(Big Ball of Mud)로 변한다.

#### 각 계층의 책임 — "무엇을 하지 않는가"로 정의된다

| 계층 | 역할 | 절대 하지 말아야 할 것 |
|------|------|----------------------|
| **Controller** | HTTP 요청/응답 변환, 입력 검증, 인증/인가 위임 | 비즈니스 로직, 트랜잭션 시작, 도메인 객체 직접 노출 |
| **Service** | 유스케이스 단위 비즈니스 로직, 트랜잭션 경계 | HTTP·세션·쿠키 직접 접근, SQL 직접 작성 |
| **Repository** | 영속성(persistence) 추상화, 도메인 단위 CRUD | 비즈니스 규칙 판단, 다른 도메인 Service 호출 |

핵심은 **"각 계층이 무엇을 모르는가"**가 명확해야 한다는 점이다. Controller는 DB가 PostgreSQL인지 MongoDB인지 몰라야 하고, Service는 호출자가 REST인지 gRPC인지 몰라야 하며, Repository는 어떤 유스케이스에서 호출되는지 몰라야 한다.

#### 의존성 방향 — 단방향이 무너지면 끝이다

```
┌─────────────────────────────────────────────────┐
│  HTTP Request                                   │
│       │                                         │
│       ▼                                         │
│  ┌──────────────┐   DTO(Request/Response)       │
│  │  Controller  │                               │
│  └──────┬───────┘                               │
│         │ Service 인터페이스에 의존              │
│         ▼                                       │
│  ┌──────────────┐   @Transactional 경계         │
│  │   Service    │                               │
│  └──────┬───────┘                               │
│         │ Repository 인터페이스에 의존           │
│         ▼                                       │
│  ┌──────────────┐                               │
│  │  Repository  │   Entity(JPA), Row Mapper     │
│  └──────┬───────┘                               │
│         │                                       │
│         ▼                                       │
│  ┌──────────────┐                               │
│  │   Database   │                               │
│  └──────────────┘                               │
│                                                 │
│  ❌ Repository → Service 호출 금지              │
│  ❌ Controller → Repository 직접 호출 금지       │
│  ❌ Service A → Controller B 호출 금지           │
└─────────────────────────────────────────────────┘
```

특히 **Repository에서 Service를 호출하는 역방향 의존**은 초보 코드베이스에서 가장 흔하게 나타나는 안티패턴이다. "주문 조회 시 사용자 정보도 같이 채워서 줘야지" 같은 욕심에 `OrderRepository` 안에서 `UserService`를 호출하면, 그 순간 트랜잭션·캐시·테스트 격리가 모두 깨진다. 이런 종류의 조립은 Service 계층에서만 일어나야 한다.

#### 트랜잭션 경계 = Service 메서드 = 유스케이스

레이어드 아키텍처에서 가장 자주 놓치는 부분이 **트랜잭션 경계와 유스케이스 경계의 일치**다. `@Transactional`을 Repository에 거는 순간 N개의 Repository 호출이 N개의 트랜잭션으로 쪼개져 부분 실패가 발생한다. Controller에 거는 순간 HTTP 응답 직렬화까지 트랜잭션 안에 들어와 LazyInitializationException과 커넥션 점유 시간 폭증의 원인이 된다.

```java
@Service
public class OrderService {

    private final OrderRepository orderRepo;
    private final StockRepository stockRepo;
    private final PaymentClient paymentClient;

    // 트랜잭션 = "주문 생성"이라는 유스케이스 1개
    @Transactional
    public OrderResult placeOrder(PlaceOrderCommand cmd) {
        Stock stock = stockRepo.findByItemId(cmd.itemId());
        stock.decrease(cmd.quantity());          // 도메인 규칙은 Entity 안에
        Order order = Order.create(cmd);
        orderRepo.save(order);
        // 외부 API 호출은 트랜잭션 경계 밖이 원칙 (커넥션 점유 방지)
        return OrderResult.from(order);
    }
}
```

> 외부 API 호출(`paymentClient.charge()`)을 `@Transactional` 안에 넣으면 DB 커넥션을 잡은 채 네트워크 I/O를 기다리게 되어, 트래픽이 몰리면 커넥션 풀이 가장 먼저 터진다. 시니어 코드 리뷰에서 99%는 이걸 잡아낸다.

#### 트레이드오프 — 단순함의 대가

| 장점 | 단점 |
|------|------|
| 학습 곡선이 낮고 신규 입사자 온보딩이 빠름 | 도메인이 복잡해지면 Service 계층이 비대해짐(God Service) |
| Spring/Django/Rails 등 대부분 프레임워크 기본 구조 | 횡단 관심사(권한·이벤트·캐시)가 Service에 침투하기 쉬움 |
| 계층별 단위 테스트가 명확 | 도메인 로직이 Service에 흩어져 절차지향 코드로 회귀하기 쉬움 |
| CRUD 위주 시스템에서 생산성 최고 | 계층 횡단(cross-cutting) 변경 시 Controller/Service/DTO/Entity 4곳을 동시에 수정 |

특히 마지막 항목, **"필드 하나 추가하려고 4개 파일을 수정해야 한다"**는 불편함은 단점이 아니라 **레이어드 아키텍처의 본질적 비용**이다. 이 비용을 줄이려고 Entity를 Controller까지 그대로 노출하는 순간 결합도가 폭발하니, 차라리 비용을 받아들이는 편이 낫다.

#### 실제 사례 — 왜 여전히 표준인가

- **Netflix 초기 모놀리스(2008년 이전)**: 단일 Java EE 모놀리스로 Controller-Service-DAO 3계층. DVD 대여 도메인이 단순했기 때문에 충분했고, 스트리밍 트래픽 폭증 전까지 이 구조로 버텼다. **즉, 도메인이 안정적이고 트래픽이 단일 머신으로 감당 가능하면 굳이 헥사고날/DDD로 갈 이유가 없다.**
- **Spring PetClinic(공식 레퍼런스)**: 20년 가까이 Controller-Service-Repository 3계층을 유지. Spring 팀이 "이 구조면 충분하다"고 보여주는 의도적 메시지.
- **국내 사례 — 우아한형제들 초기 배민**: 주문/결제 도메인이 단순했던 시절 전형적인 3계층 모놀리스로 시작했고, 트래픽·도메인 복잡도가 임계점을 넘은 뒤에야 헥사고날·이벤트 기반으로 점진적 이동. 처음부터 복잡하게 가지 않았다는 점이 중요하다.
- **반례 — 토스 송금 도메인**: 도메인 규칙(한도·이상거래·정산)이 매우 복잡해 초기부터 Service에 로직이 몰리는 것을 경계하고 도메인 모델 중심 설계로 출발했다. **도메인 복잡도가 높으면 3계층은 시작점이 아니라 함정이 된다.**

#### 시니어 관점 — 언제 쓰고, 언제 쓰면 안 되는가

**쓸 때**
- 도메인 규칙보다 데이터 입출력(CRUD)이 중심인 시스템 (사내 어드민, 백오피스, 단순 API 게이트웨이)
- 팀 규모가 작고(2~7명) 도메인 지식이 코드 외에 별도 전문가에 집중되어 있지 않을 때
- MVP·PoC 단계에서 도메인 경계가 아직 불확실할 때 — **처음부터 헥사고날로 가는 건 YAGNI다**
- 트래픽이 단일 인스턴스(또는 수평 확장된 동일 모놀리스 N대)로 감당되는 규모

**쓰지 말아야 할 때**
- 도메인 규칙이 복잡하고 비즈니스 사이드(기획·정산·법무)의 요구가 끊임없이 바뀌는 영역 — Service가 5천 줄짜리 God Object가 되는 미래가 확정적
- 외부 시스템 의존이 많아 포트/어댑터 분리가 필요한 경우 (결제 PG 3~4개 동시 연동, 외부 알림 채널 다수)
- 동일 비즈니스 로직을 REST·gRPC·배치·이벤트 컨슈머 등 **여러 입출력 경로**에서 호출해야 할 때 — Controller에 종속된 흐름이 발목을 잡음
- 도메인 모델을 ORM Entity와 분리해야 할 강한 이유가 있을 때(불변성, 도메인 이벤트, Aggregate 일관성)

요약하면 레이어드 아키텍처는 **"도메인 복잡도가 낮거나 안정적일 때 최적"**이며, 복잡도가 임계점을 넘는 시점에 헥사고날/클린 아키텍처로 점진적으로 옮겨가는 출발점이다. 시니어가 가져야 할 감각은 "3계층을 잘 짜는 능력"이 아니라 **"3계층의 한계가 어디서 드러나는지 감지하고, 그 시점에 다음 패턴으로 넘어가는 판단력"**이다.

> 💡 **왜 중요한가**: 레이어드 아키텍처의 본질은 "폴더 3개"가 아니라 단방향 의존성·트랜잭션 경계·계층 책임이라는 세 가지 약속이며, 이 약속이 깨지는 지점이 곧 다음 아키텍처로 넘어가야 할 신호다.
