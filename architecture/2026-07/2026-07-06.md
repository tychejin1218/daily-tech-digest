### Multi-region Active-Active — "지구는 둥글고, 지연은 빛의 속도로 제한된다"는 물리 법칙 앞에서 다시 짓는 가용성

Active-Passive는 쉽다. 한쪽은 트래픽을 받고, 다른 쪽은 조용히 대기한다. 장애가 나면 DNS를 돌리고, RTO 5분, RPO 1분을 목표로 한다. 문제는 "돌린다"는 그 순간이다. 대기 중이던 리전은 실전에서 검증된 적이 없고, Failover 스크립트는 3년 전에 마지막으로 돌려봤으며, DB Replica는 lag이 얼마나 밀려 있는지 아무도 모른다. 시니어가 Active-Passive를 신뢰하지 않는 이유는 여기 있다 — **평소에 안 쓰는 것은 필요할 때 반드시 고장 나 있다.**

Active-Active는 이 문제를 다르게 접근한다. 두 리전(혹은 그 이상)이 **동시에** 라이브 트래픽을 받는다. 하나가 죽으면 다른 하나가 이미 절반의 트래픽을 처리하고 있으므로 "돌린다"는 순간 자체가 존재하지 않는다. Failover가 아니라 Load Shifting이다. 검증된 적 없는 경로를 타지 않는다.

하지만 이 우아함의 대가는 **분산 시스템의 근본 문제를 정면으로 마주해야 한다**는 것이다. 두 리전이 동시에 쓰기를 받는다면, 같은 사용자가 서울과 버지니아에 동시에 로그인하고 프로필을 수정하면 어느 것이 진짜인가? 이 질문에 답할 수 없다면 Active-Active를 도입해선 안 된다.

```
                   ┌─────────────── GeoDNS / Anycast ────────────────┐
                   │  (지연 기반 라우팅 + 헬스체크)                    │
                   └──────────┬──────────────────────┬────────────────┘
                              │                      │
                    ┌─────────▼──────────┐  ┌────────▼─────────┐
                    │   Region: SEOUL    │  │  Region: VIRGINIA │
                    │  ┌──────────────┐  │  │  ┌──────────────┐ │
                    │  │  API + Cache │  │  │  │  API + Cache │ │
                    │  └──────┬───────┘  │  │  └──────┬───────┘ │
                    │         │          │  │         │         │
                    │  ┌──────▼───────┐  │  │  ┌──────▼───────┐ │
                    │  │  Local DB    │◀─┼──┼─▶│  Local DB    │ │
                    │  └──────────────┘  │  │  └──────────────┘ │
                    └────────────────────┘  └───────────────────┘
                              ▲                      ▲
                              └── Cross-region ──────┘
                                  Replication (async)
                                  → 지연 40~180ms, 충돌 가능성 항상 존재
```

**핵심 트레이드오프는 CAP의 P를 강제로 상수 취급하는 순간 시작된다.** 리전 간 네트워크는 언젠가 반드시 끊긴다(Partition은 옵션이 아니다). 그러면 남는 선택은 두 가지다.

1. **CP를 택한다** — 파티션이 나면 한쪽은 쓰기를 거부한다. 즉 그 리전에서 사용자는 "죄송합니다" 화면을 본다. 가용성이 깨진다. Active-Active로 얻으려던 것을 잃는다.
2. **AP를 택한다** — 양쪽 모두 로컬로 쓰기를 받고, 나중에 충돌을 해결한다. 이때 필요한 것이 CRDT(Conflict-Free Replicated Data Type)나 Last-Write-Wins, 혹은 도메인 로직 기반 머지다.

시니어의 판단은 여기서 갈린다. **도메인 데이터의 성격에 따라 CP/AP를 다르게 배치**해야 한다.

| 데이터 종류 | 전략 | 이유 |
|---|---|---|
| 결제, 재고, 계정 잔액 | Single-Region Writer + Read Replica | 충돌이 곧 돈. 강한 일관성 필요 |
| 프로필, 설정, 게시글 | Regional Write + Async Replication (LWW) | 최종적 일관성으로 충분 |
| 카트, 세션 | Sticky Region (사용자를 한 리전에 고정) | 충돌 자체를 발생시키지 않음 |
| 로그, 이벤트 | 각 리전 독립 저장 + 중앙 집계 | 애초에 충돌 개념 없음 |

**실제 사례를 보면 이 판단이 얼마나 어려운지 드러난다.**

- **Netflix**는 완전한 Active-Active를 구현했지만, 그 대가로 EVCache(Memcached 기반) 위에 자체 Cross-region 복제 계층을 만들고, Cassandra의 튜너블 컨시스턴시를 극도로 세밀하게 조정했다. Netflix가 이걸 감당할 수 있는 이유는 "잠깐의 데이터 불일치가 인생을 망치지 않는" 도메인(비디오 스트리밍)이기 때문이다.
- **AWS DynamoDB Global Tables**는 Multi-Region Multi-Active를 관리형으로 제공하지만, 명시적으로 **Last-Writer-Wins**를 채택했다. 그리고 문서 어디에도 "결제에 쓰세요"라고 적혀 있지 않다.
- **Google Spanner**는 정반대의 길을 갔다 — TrueTime API(원자시계 + GPS)로 전 세계 시각을 동기화해 **CP + 낮은 지연**을 달성했다. 하지만 이건 구글이 데이터센터에 원자시계를 박아넣을 수 있기 때문에 가능한 해법이지, 일반 기업의 선택지가 아니다.
- **Stripe**는 결제 도메인의 특성상 오랫동안 Single-Region 우위를 유지했고, Active-Active 대신 리전 내부의 극단적 다중화(다중 AZ + Cell 아키텍처)로 가용성을 확보했다. "돈은 두 곳에서 동시에 쓰이지 않는다"는 원칙을 지킨 것이다.

**언제 쓰는가:**
- 사용자가 전 세계에 분산되어 있고, 지역별 지연이 UX에 직접 영향을 준다 (스트리밍, 소셜, 게임)
- RTO가 초 단위여야 한다 (Failover 몇 분이 매출 수천만 원)
- 컴플라이언스로 데이터 지역성(EU 사용자 데이터는 EU에)이 강제된다
- 쓰기 워크로드의 대부분이 **자연스럽게 리전별로 파티션 가능한** 도메인이다 (사용자가 대체로 자기 리전에서만 쓴다)

**언제 쓰면 안 되는가:**
- 강한 트랜잭션 일관성이 필요한 도메인이 시스템의 심장부다 (금융, 재고, 예약)
- 팀에 분산 시스템을 디버깅해본 사람이 없다 — Active-Active의 진짜 비용은 **장애가 났을 때 원인을 찾을 수 있느냐**에서 나온다
- 트래픽이 아직 단일 리전으로 충분히 감당된다 — 조기 도입은 순수한 자해다
- 데이터 모델이 충돌 해결을 고려하지 않고 설계되어 있다 (auto-increment PK, 낙관적 락 없음 등)

시니어의 관점에서 가장 중요한 통찰은 이것이다. **Active-Active는 가용성 아키텍처가 아니라 데이터 아키텍처다.** 로드밸런서와 DNS는 표면일 뿐, 진짜 결정은 "이 테이블의 이 컬럼이 두 리전에서 동시에 수정되면 무엇을 진실로 삼을 것인가"에서 이뤄진다. 이 질문에 도메인 전문가와 함께 답할 수 없다면, 아무리 좋은 인프라를 깔아도 Active-Active는 언젠가 데이터 정합성 사고로 무너진다. 반대로 이 질문에 답할 수 있다면, 인프라는 그저 그 답을 코드로 옮기는 과정일 뿐이다.

> 💡 **왜 중요한가**: Multi-region Active-Active의 본질은 리전 이중화가 아니라 "충돌을 도메인 수준에서 어떻게 정의하고 해소할 것인가"이며, 이 결정을 인프라 팀에 위임하는 순간 프로젝트는 실패한다.
