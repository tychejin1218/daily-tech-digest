### 1. Spring Boot의 `@ControllerAdvice`는 **패키지/어노테이션으로 범위를 제한하지 않으면 전역으로 작동한다** — 그래서 공용 라이브러리의 핸들러가 네 컨트롤러의 예외를 조용히 가로챈다

`@ControllerAdvice`를 아무 속성 없이 선언하면 **모든 컨트롤러의 예외**를 잡는다. 문제는 사내 공통 모듈이나 외부 라이브러리가 `@ControllerAdvice`를 노출하고 있을 때인데, 의존성을 추가하는 순간 네가 모르는 예외 핸들러가 끼어들어 `MethodArgumentNotValidException`이나 `AccessDeniedException`을 가로채 **다른 응답 포맷**으로 바꿔버린다. 범위를 좁히려면 `basePackages`, `annotations = RestController.class`, 또는 `assignableTypes`를 반드시 명시하고, `@Order`로 우선순위를 통제해야 한다.

```java
// 위험: 전역으로 모든 컨트롤러에 적용됨
@ControllerAdvice
public class GlobalExceptionHandler { ... }

// 안전: 내 패키지의 REST 컨트롤러에만 적용
@RestControllerAdvice(
    basePackages = "com.daekyo.api",
    annotations = RestController.class
)
@Order(Ordered.HIGHEST_PRECEDENCE)
public class ApiExceptionHandler { ... }
```

실제로 겪는 전형적인 사고는 이렇다 — Spring Boot Admin 클라이언트나 사내 공통 모듈을 추가했는데 갑자기 400 응답의 JSON 구조가 바뀌어 프론트가 깨진다. 디버거를 붙여보면 네가 쓴 적도 없는 라이브러리의 `ExceptionHandler`가 먼저 매칭된 것이다. `@Order(Ordered.HIGHEST_PRECEDENCE)`를 걸어두면 내 핸들러가 먼저 선택된다.

> 💡 **왜 중요한가**: 전역 예외 핸들러의 "전역"은 생각보다 넓어서, 범위를 좁히지 않으면 **의존성 하나 추가한 순간 API 응답 계약이 조용히 바뀐다**.

### 2. Spring Data JPA의 `save()`는 **INSERT를 보장하지 않는다** — ID가 할당된 엔티티를 넘기면 `SELECT` 후 `UPDATE`가 나가고, 최악의 경우 쿼리가 2배로 늘어난다

`JpaRepository.save()`의 실제 동작은 `SimpleJpaRepository` 안에서 `isNew()`를 호출해 **신규인지 아닌지 판단**한 뒤, 신규면 `persist()`, 아니면 `merge()`를 호출한다. `merge()`는 영속성 컨텍스트에 해당 엔티티가 없으면 **DB에서 SELECT로 먼저 조회**한 다음 변경사항을 반영한다. 그래서 외부에서 받은 DTO를 엔티티로 변환해 ID가 세팅된 채로 `save()`를 호출하면, 네가 원한 건 INSERT였는데 실제로는 `SELECT + UPDATE` 두 번의 쿼리가 나간다.

```java
// 안티패턴: 벌크 "삽입"인데 실제로는 SELECT N번 + UPDATE N번
public void importUsers(List<UserDto> dtos) {
    for (UserDto dto : dtos) {
        User user = new User();
        user.setId(dto.getId());   // 외부 시스템이 준 ID
        user.setName(dto.getName());
        userRepository.save(user); // merge() → SELECT + UPDATE
    }
}

// 해결 1: Persistable 구현해서 isNew()를 직접 제어
@Entity
public class User implements Persistable<Long> {
    @Id private Long id;

    @Transient
    private boolean isNew = true;

    @Override public boolean isNew() { return isNew; }

    @PostLoad @PostPersist
    void markNotNew() { this.isNew = false; }
}

// 해결 2: EntityManager.persist()를 직접 호출
entityManager.persist(user); // 무조건 INSERT, 중복 ID면 예외
```

판별 기준의 진실은 더 미묘하다 — ID 필드가 **primitive(`long`)면 0일 때 신규**, **wrapper(`Long`)면 null일 때 신규**로 본다. `@Version` 필드가 있으면 그 값의 null 여부가 우선된다. 외부 ID를 받아쓰는 도메인(주문번호, 주민번호, UUID)에서는 이 규칙이 전부 어긋나기 때문에 `Persistable`을 구현하거나 `EntityManager`를 직접 쓰는 게 안전하다.

> 💡 **왜 중요한가**: `save()`의 의미는 "저장"이 아니라 "병합"이라서, 외부 ID 기반 도메인에서는 **매 호출마다 쿼리가 정확히 2배로 터지며 조용히 느려진다**.
