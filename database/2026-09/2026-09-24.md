### MySQL `Gap Lock`과 `Next-Key Lock` — 존재하지 않는 행에도 락이 걸리는 REPEATABLE READ의 숨은 무기

InnoDB의 `REPEATABLE READ`는 스냅샷 격리(MVCC)만으로 Phantom Read를 완전히 막지 못하기 때문에, `SELECT ... FOR UPDATE`나 `UPDATE ... WHERE`에서 조건에 걸리는 인덱스 구간의 "빈 공간(Gap)"에도 락을 겁니다. 예를 들어 `WHERE age BETWEEN 20 AND 30`으로 락을 걸면 아직 존재하지 않는 `age = 25`인 행의 INSERT까지 블록되는데, 이는 팬텀을 막는 대신 무관해 보이는 INSERT가 대기하는 데드락의 주요 원인이 됩니다. `READ COMMITTED`로 격리 수준을 낮추면 Gap Lock이 사라져 락 경합은 줄지만, 팬텀과 `binlog_format=STATEMENT` 복제 이슈가 다시 열리므로 트레이드오프를 명확히 이해해야 합니다.

> 💡 **왜 중요한가**: "왜 INSERT가 갑자기 데드락이 나지?"의 90%는 다른 세션의 범위 UPDATE가 걸어둔 Gap Lock 때문이며, `SHOW ENGINE INNODB STATUS`에서 `lock_mode X locks gap before rec`를 읽을 줄 알아야 진단이 가능하다.

### JPA `OSIV (Open Session In View)` — 컨트롤러에서도 Lazy Loading이 되는 스프링 부트 기본값의 조용한 대가

Spring Boot는 기본적으로 `spring.jpa.open-in-view=true`로 켜져 있어서, HTTP 요청이 끝날 때까지 영속성 컨텍스트(EntityManager)를 열어두어 뷰 렌더링 시점에도 Lazy Loading이 동작하게 만듭니다. 편리해 보이지만 대가는 큽니다 — DB 커넥션이 서비스 트랜잭션 종료 이후에도 요청이 끝날 때까지 홀드되어, 외부 API 호출이 5초 걸리는 컨트롤러가 있으면 그 5초 동안 커넥션 하나가 잡혀 있고, HikariCP 풀이 순식간에 고갈됩니다. 프로덕션에서는 `false`로 끄고 `@EntityGraph`나 DTO Projection으로 필요한 연관을 서비스 계층에서 명시적으로 로딩하는 것이 정석입니다.

> 💡 **왜 중요한가**: "트래픽이 조금만 늘면 커넥션 풀이 죽어요"의 흔한 범인이 OSIV이며, 이를 끄는 순간 숨어있던 `LazyInitializationException`이 우수수 터지면서 실제로 팀이 연관 로딩을 설계했는지가 드러난다.
