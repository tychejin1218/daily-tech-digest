### PostgreSQL `EXPLAIN (BUFFERS)` — 쿼리가 실제로 읽은 페이지 수로 I/O 병목 짚기

`EXPLAIN ANALYZE`가 시간만 보여준다면, `EXPLAIN (ANALYZE, BUFFERS)`는 각 노드가 공유 버퍼(shared hit)와 디스크(read)에서 몇 페이지를 읽었는지 함께 출력한다. `Buffers: shared hit=12 read=48932`처럼 read 값이 크면 캐시 미스가 발생한 것이므로, 인덱스 튜닝 전에 워킹셋 크기나 `effective_cache_size`부터 점검해야 한다.

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT * FROM orders WHERE customer_id = 42 AND created_at > '2026-01-01';
-- Index Scan using idx_orders_customer_created on orders
--   Buffers: shared hit=8 read=1523
--   -> read 값이 크면 디스크 I/O 병목
```

> 💡 **왜 중요한가**: 실행 시간만 보면 캐시 워밍업에 속기 쉽지만, 버퍼 통계는 쿼리의 실제 I/O 비용을 정직하게 드러낸다.

### JPA `@BatchSize`로 N+1 문제를 IN 쿼리로 뭉치기

`@OneToMany(fetch = LAZY)` 컬렉션을 순회하면 부모 100개당 자식 SELECT가 100번 나가는 N+1이 터진다. Hibernate의 `@BatchSize(size = 50)`을 컬렉션이나 엔티티에 붙이면, 프록시 초기화 시점에 미로드 부모들을 모아 `WHERE parent_id IN (?, ?, ..., ?)` 한 방으로 로드해 쿼리 수를 부모/50번으로 줄인다.

```java
@Entity
public class Team {
    @OneToMany(mappedBy = "team", fetch = FetchType.LAZY)
    @BatchSize(size = 50)
    private List<Member> members;
}
// teams.forEach(t -> t.getMembers().size());
// → SELECT ... WHERE team_id IN (?, ?, ..., ?) -- 50개씩 묶어 발사
```

`JOIN FETCH`와 달리 페이징이나 다중 컬렉션 조합에서 카티션 곱을 만들지 않아, 리스트 뷰처럼 부모+자식을 부분적으로만 쓰는 화면에 특히 잘 맞는다.

> 💡 **왜 중요한가**: `JOIN FETCH`가 부담스러운 페이징·다중 컬렉션 상황에서도 N+1을 실용적인 IN 쿼리 몇 방으로 압축할 수 있다.
