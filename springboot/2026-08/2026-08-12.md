### `@Scheduled`와 `@Async`를 함께 쓰면 스케줄러 스레드 풀이 병목의 진짜 원인이 된다

`@EnableScheduling`은 기본적으로 **단일 스레드 스케줄러(`ThreadPoolTaskScheduler`, pool size 1)**를 사용한다. 즉, 여러 개의 `@Scheduled` 메서드가 등록되어 있어도 하나가 오래 걸리면 나머지는 대기하며, 심지어 `cron = "0 * * * * *"` 같은 매분 실행 잡이 밀리기 시작한다. 이를 회피하려고 `@Async`를 붙이는 경우가 많은데, `@Async`의 기본 실행자는 `SimpleAsyncTaskExecutor`로 **매번 새 스레드를 생성**해서 OOM을 유발한다.

```java
// ❌ 위험 - 단일 스레드 스케줄러 + 무제한 스레드 생성
@Scheduled(fixedRate = 1000)
@Async
public void poll() { /* 오래 걸리는 작업 */ }

// ✅ 명시적 풀 설정
@Configuration
@EnableScheduling
@EnableAsync
public class SchedulerConfig implements SchedulingConfigurer {
    @Override
    public void configureTasks(ScheduledTaskRegistrar registrar) {
        ThreadPoolTaskScheduler scheduler = new ThreadPoolTaskScheduler();
        scheduler.setPoolSize(10);
        scheduler.setThreadNamePrefix("scheduled-");
        scheduler.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        scheduler.initialize();
        registrar.setTaskScheduler(scheduler);
    }

    @Bean(name = "asyncExecutor")
    public Executor asyncExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(8);
        executor.setMaxPoolSize(32);
        executor.setQueueCapacity(500);
        executor.setThreadNamePrefix("async-");
        return executor;
    }
}
```

> 💡 **왜 중요한가**: 배치성 잡 하나가 밀리면 조용히 전체 스케줄 체인이 무너지고, `@Async` 기본값은 프로덕션에서 스레드 폭발로 이어져 새벽에 페이징을 받게 만든다.

### JPA `save()`가 `INSERT`가 아니라 `SELECT + UPDATE`로 나가는 함정

`JpaRepository.save()`는 `EntityManager.persist()`가 아니라 `SimpleJpaRepository`에서 **엔티티가 new인지 판단**한 뒤 new면 `persist()`, 아니면 `merge()`를 호출한다. 문제는 `@GeneratedValue` 없이 **ID를 직접 할당**하는 도메인(예: UUID, 자연키)의 경우 Spring이 "ID가 이미 있으니 기존 엔티티"라고 판단해 `merge()` → **불필요한 SELECT 쿼리 1회 추가** 후 INSERT를 날린다는 점이다.

```java
// ❌ 신규 저장인데 SELECT가 먼저 나감
@Entity
public class Order {
    @Id private String id;  // UUID 직접 할당
    // ...
}
orderRepository.save(new Order(UUID.randomUUID().toString(), ...));
// → SELECT ... WHERE id = ? (없음 확인)
// → INSERT INTO orders ...

// ✅ Persistable 구현으로 명시적으로 신규 여부 알림
@Entity
public class Order implements Persistable<String> {
    @Id private String id;
    @Transient private boolean isNew = true;

    @Override public boolean isNew() { return isNew; }

    @PostPersist @PostLoad
    void markNotNew() { this.isNew = false; }
}
// → INSERT만 실행 (SELECT 없음)
```

> 💡 **왜 중요한가**: 벌크 저장 시 이 함정 하나로 쿼리 수가 2배로 뛰어 초당 수천 건 처리하는 API의 DB 부하가 소리 없이 두 배가 된다 — APM에서 잡히지 않는 대표적인 "느린 저장" 원인이다.
