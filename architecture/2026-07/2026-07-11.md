### 로드 밸런싱 알고리즘의 함정 — "골고루 나누면 골고루 처리된다"는 착각과, Round Robin이 프로덕션에서 무너지는 순간

로드 밸런서를 처음 배울 때는 이렇게 말한다. "여러 서버로 요청을 골고루 나눠주는 장치". 그래서 대부분 Round Robin(RR)을 기본값으로 켜두고 넘어간다. 하지만 이 문장에는 조용한 거짓말이 하나 숨어 있다 — "요청은 모두 같은 비용"이라는 전제. 프로덕션에서는 이 전제가 거의 항상 깨진다. 그리고 그 순간, RR은 "골고루 나누는 알고리즘"이 아니라 "골고루 죽이는 알고리즘"이 된다.

#### 문제의 본질: 요청 비용의 분포는 균등하지 않다

같은 `/api/orders` 엔드포인트라도 어떤 요청은 5ms, 어떤 요청은 5초가 걸린다. 첫 페이지 조회는 캐시 히트로 즉시 반환되고, 특정 사용자의 대량 주문 이력 조회는 DB 풀 스캔을 유발한다. RR은 이 차이를 모른다. 요청 카운터만 증가시킬 뿐이다.

```
시나리오: 4대 서버, RR로 분배
느린 요청(5s)이 5% 비율로 유입, 나머지 95%는 빠른 요청(50ms)

시간이 흐르면:
Server A: [빠름][느림-처리중.....................][빠름 대기][빠름 대기]...
Server B: [빠름][빠름][빠름][빠름][느림-처리중....][빠름 대기]...
Server C: [빠름][빠름][느림-처리중...][빠름][빠름][빠름]...
Server D: [빠름][느림-처리중...][느림-처리중...] ← 우연히 느린 요청 몰림

결과: D는 큐가 쌓여 응답 지연 → 타임아웃 → 서킷 오픈
     A, B, C는 놀고 있음
```

RR이 요청을 "골고루" 나눈다는 것은 **개수**의 관점에서만 사실이다. **작업량(load)**의 관점에서는 편차가 폭발한다. 이 편차는 P50이 아니라 P99에서 튄다. 그리고 SLO는 P99로 잰다.

#### 대안 1: Least Connections — "지금 바쁜 애한테 안 보내면 되잖아?"

가장 직관적인 해법. 각 백엔드의 활성 연결 수를 세서 가장 적은 곳으로 보낸다. HAProxy, Nginx, AWS ALB 모두 지원한다.

하지만 여기에도 함정이 있다.

1. **연결 수 ≠ 부하**. HTTP/2, gRPC 환경에서는 하나의 커넥션에 수백 개의 스트림이 흐른다. "연결 하나"가 실제로 얼마나 바쁜지 알 수 없다.
2. **관측 지연**. LB가 각 백엔드의 연결 수를 알려면 어딘가에서 카운팅해야 한다. 자기 자신을 통과한 연결만 세면 되지만, LB가 여러 대라면 다른 LB가 보낸 요청은 안 보인다 → 각 LB가 자기 관점에서만 "least"를 판단하며 같은 서버로 몰릴 수 있다(**herd effect**).

#### 대안 2: Least Outstanding Requests (LOR) — Envoy/gRPC의 기본값

"현재 응답 대기 중인 요청 수가 가장 적은 백엔드로". Least Connections보다 정확하다. 스트림 단위로 세기 때문. Envoy 사이드카를 쓰는 Service Mesh 환경에서는 이게 표준이다.

하지만 클라이언트 사이드 LB(Envoy가 각 파드에 붙어 있는 구조)에서는 **각 사이드카가 로컬 관점만 본다**. 100개의 클라이언트 사이드카가 모두 "지금 B가 가장 한가해"라고 동시에 판단하면 → B로 100개가 몰린다. 그 다음 순간 B가 가장 바쁘고 C가 가장 한가해 보인다 → C로 100개가 몰린다. **진동(oscillation)**이 발생한다.

#### 대안 3: Power of Two Choices (P2C) — 진동을 죽이는 무작위성

이론적으로 아름다운 알고리즘. 매번 요청을 라우팅할 때:

1. 백엔드 풀에서 **랜덤으로 2개**를 뽑는다.
2. 그중 부하가 적은 쪽을 선택한다.

놀랍게도 이 단순한 규칙이 "가장 부하 적은 곳을 항상 선택"하는 것보다 실제로 더 균등한 분포를 만든다. **최대 큐 길이**가 로그 스케일로 줄어든다는 수학적 결과가 있다(Mitzenmacher, 2001). 무작위성이 herd effect와 진동을 자연스럽게 흡수하기 때문이다.

Netflix의 Ribbon 이후 gRPC-LB, Finagle, Twitter Server 등이 이 계열 알고리즘을 채택했다. Linkerd의 EWMA(Exponentially Weighted Moving Average) 기반 P2C가 대표적이다 — 두 후보 중 "최근 응답 시간이 짧은 쪽"을 고른다.

#### 대안 4: Consistent Hashing — "같은 사용자는 같은 서버로"

캐시 히트율이 중요한 시스템(세션 스티키, 로컬 캐시, DB 커넥션 풀 재사용)에서는 부하 균등보다 **지역성(locality)**이 더 중요하다. 이때 쓰는 것이 Consistent Hashing.

```
      해시 링 (0 ~ 2^32)
           ┌────────┐
      Srv A│        │Srv B
           │  ●──┐  │
       req1│     ▼  │
           │  ●──→Srv C
           │        │
      Srv D│        │
           └────────┘

req1의 hash가 Srv C 구간 → 항상 C로 라우팅
Srv C가 죽으면 → 다음 노드(D)로 자동 이동
Srv 추가/제거 시 재분배량 = 1/N 수준
```

Discord가 "수백만 명이 접속한 채널"을 특정 노드로 몰아주는 데 이 알고리즘을 쓴다. 채널 ID 해시가 결정하기 때문에 같은 채널의 모든 메시지가 같은 노드에서 처리되고, 로컬 상태를 유지할 수 있다.

**함정**: 특정 해시 구간에 트래픽이 몰리면(예: BTS 팬 채널) 그 노드만 죽는다. 이를 **hot spot** 문제라 한다. 완화책은 **Bounded-load Consistent Hashing** (Google, 2016) — 각 노드의 부하가 평균의 1+ε배를 넘으면 다음 노드로 흘려보낸다.

#### 트레이드오프 정리

| 알고리즘 | 균등성 | 지역성 | 상태 필요 | 추천 시나리오 |
|---|---|---|---|---|
| Round Robin | 낮음(요청비용 편차 시) | 없음 | 없음 | 요청 비용이 균일한 stateless 서비스 |
| Weighted RR | 중간 | 없음 | 정적 가중치 | 서버 스펙이 다를 때 |
| Least Connections | 중간 | 없음 | 실시간 카운트 | HTTP/1.1, 짧은 연결 |
| Least Outstanding Requests | 높음 | 없음 | 실시간 카운트 | gRPC, HTTP/2, Service Mesh |
| Power of Two Choices | 매우 높음 | 없음 | 랜덤 + 카운트 | 클라이언트 사이드 LB, 분산 LB 다수 |
| Consistent Hashing | 낮음(핫스팟) | 매우 높음 | 해시 함수 | 캐시, 세션, 샤딩 |

#### 실제 사례: Netflix Zuul → Zuul 2의 알고리즘 교체

Netflix는 초기 Zuul(블로킹 IO + RR)에서 트래픽 급증 시 **일부 백엔드만 큐가 쌓이는** 문제를 반복적으로 겪었다. Zuul 2로 재작성하면서 넌블로킹 IO와 함께 **Choice-of-2 with server utilization**(P2C의 변형)을 도입했다. 서버 자체가 리포트하는 CPU/큐 깊이 지표를 두 후보 서버 중 비교해서 결정한다. RR 대비 P99가 눈에 띄게 안정화됐다.

#### 시니어의 관점: 언제 어떤 것을 쓰는가

- **RR을 유지해도 되는 경우**: 요청 처리 시간의 표준편차가 평균의 20% 이내로 작고, 백엔드 스펙이 동일하며, 초기 구성이라 관측 인프라가 없을 때. "일단 켜두고 관측부터 붙이는" 실용적 선택.
- **RR을 반드시 버려야 하는 경우**: P99와 P50의 격차가 10배 이상 벌어질 때, 또는 GC pause/DB 슬로우 쿼리처럼 **일시적으로 느려지는 백엔드**가 존재할 때. RR은 이 상태의 서버에도 정확히 1/N씩 계속 밀어넣기 때문에 회복을 방해한다.
- **Least Connections/LOR로 옮길 때 주의**: LB가 여러 대라면 각자 로컬 관점만 본다는 사실을 잊지 말 것. herd effect가 두렵다면 P2C를 얹거나, Envoy의 `slow_start` 옵션으로 새 백엔드가 갑자기 트래픽을 다 받는 걸 방지해야 한다.
- **Consistent Hashing은 로드밸런싱이 아니라 라우팅이다**: 균등 분산이 목표라면 오답이다. "같은 키는 같은 노드로"라는 요구가 명시적으로 있을 때만 쓴다. 그리고 반드시 bounded-load 변형을 고려해라 — 순수 CH는 핫스팟에 무방비다.
- **알고리즘을 바꿔도 관측 없이는 검증 불가**: LB 알고리즘 변경은 P99, 백엔드별 큐 깊이, GC 시간, 커넥션 풀 사용률까지 다차원으로 봐야 한다. 알고리즘을 바꾸고 "느낌상 좋아진 것 같다"고 결론짓는 순간, 다음 인시던트가 예약된다.

로드 밸런서의 알고리즘 선택은 "네트워크 설정"이 아니라 **아키텍처 결정**이다. 요청 비용 분포, 백엔드의 상태성, 캐시 지역성, LB의 배치 구조가 함께 얽힌 문제이기 때문이다. 기본값을 그대로 두는 것도 결정이다 — 다만 그것이 결정이라는 사실을 알고 두어야 한다.

> 💡 **왜 중요한가**: Round Robin은 요청 개수를 균등하게 나눌 뿐 부하를 균등하게 나누지 않으며, 요청 비용의 편차가 큰 실제 프로덕션에서는 P99와 서킷 오픈 사고의 숨은 원인이 된다.
