### DTO·Entity·VO 분리: 도메인 경계를 지키는 객체의 역할극

레이어드 아키텍처를 도입하고 트랜잭션 경계까지 Service에 잘 그어 놓아도, **객체가 레이어를 넘나들며 정체성을 잃는 순간** 모든 설계가 무너진다. `User` 엔티티가 Controller까지 그대로 흘러나가는 코드, JSON 응답 스펙이 바뀌었다고 DB 스키마가 따라 흔들리는 코드 — 이 모든 게 DTO/Entity/VO 구분 실패에서 출발한다.

#### 1. 각 객체의 존재 이유

| 객체 | 한 줄 정의 | 변경의 동기(Reason to Change) | 생명주기 |
|---|---|---|---|
| **Entity** | DB 테이블에 대응되는 영속 객체. 식별자(ID)로 동일성 판단 | 도메인 규칙·스키마 변경 | DB row와 동기화 |
| **DTO** (Data Transfer Object) | 레이어/프로세스 경계를 넘는 데이터 운반체. **로직 없음**, 동등성은 필드값 | API 스펙·외부 인터페이스 변경 | 요청·응답 단위 |
| **VO** (Value Object) | 식별자 없이 **값 자체로 동일성**을 갖는 불변 도메인 개념 (`Money`, `Email`, `Address`) | 도메인 의미 변경 | 메서드 내부에서 짧게 생성·소멸 |

핵심은 "이 객체가 **왜 바뀌어야 하는가**(Single Reason to Change)"이다. Entity는 DB 때문에, DTO는 API 때문에, VO는 도메인 규칙 때문에 바뀐다. 변경 동기가 다른데 같은 객체를 쓰면 한쪽 변경이 다른 쪽을 끌고 들어간다.

#### 2. 흐름 다이어그램

```
 ┌───────────┐  RequestDTO     ┌─────────┐  Entity/VO    ┌──────────┐
 │ Client    │ ───────────────▶│Controller│──────────────▶│ Service  │
 │ (Browser, │                 │          │               │ (Domain) │
 │  Mobile)  │ ◀─────────────  │          │ ◀──────────── │          │
 └───────────┘  ResponseDTO    └─────────┘  Entity/VO    └────┬─────┘
                                                              │ Entity
                                                              ▼
                                                       ┌──────────┐
                                                       │Repository│
                                                       └────┬─────┘
                                                            │
                                                            ▼  ORM mapping
                                                          [ DB ]

 ▷ Request/Response DTO : Web 레이어 경계에서만 살아 있음
 ▷ Entity              : Service ↔ Repository 사이를 흐름 (트랜잭션 안)
 ▷ VO (Email, Money…)  : Entity의 필드 또는 Service 내부에서 사용
```

원칙은 단순하다. **Entity는 Service 레이어를 벗어나지 않는다.** Controller는 RequestDTO를 받아 Service에 넘기고, Service가 반환한 Entity(또는 도메인 결과)를 ResponseDTO로 매핑한 뒤 돌려준다.

#### 3. 자주 보는 안티패턴

**(A) Entity를 그대로 응답으로 노출**
```java
@GetMapping("/users/{id}")
public User getUser(@PathVariable Long id) {
    return userRepository.findById(id).orElseThrow();
}
```
- 비밀번호 해시·내부 플래그가 그대로 새어 나간다.
- DB 컬럼명을 바꾸면 모바일 앱 호환이 깨진다.
- JPA의 경우 Lazy 프록시가 직렬화되며 `LazyInitializationException` 또는 의도치 않은 N+1 발생.

**(B) DTO를 도메인 로직 운반에 사용**
```java
// Service 내부에서
public void chargePoint(PointChargeDto dto) {
    if (dto.getAmount() < 0) throw ...;   // 도메인 규칙이 DTO에 묶임
    user.setPoint(user.getPoint() + dto.getAmount());
}
```
- DTO 필드 검증과 도메인 규칙이 뒤섞여, API가 추가되면 같은 규칙이 여러 DTO에 복붙된다.
- `Money` VO를 도입했다면 `Money.of(dto.getAmount())` 단계에서 음수가 차단되며, 규칙은 한 곳(VO 생성자)에 모인다.

**(C) "VO 같이 생긴" 가변 객체**
```java
public class Money {
    private long amount;
    public void setAmount(long a) { this.amount = a; }
}
```
- VO의 본질은 **불변성 + 값 동등성**. setter가 있으면 그건 그냥 mini-Entity다.
- 불변이 깨지면 같은 `Money` 인스턴스를 공유하는 두 주문이 동시에 망가질 수 있다.

#### 4. 트레이드오프

| 관점 | 분리할 때 얻는 것 | 분리할 때 잃는 것 |
|---|---|---|
| **변경 격리** | API·DB·도메인 규칙이 서로 독립적으로 진화 가능 | 객체·매핑 코드 증가 (3~4배) |
| **보안** | 응답 필드가 명시적이라 민감 정보 누출 위험↓ | DTO 누락 시 응답이 빈 객체로 나가는 사고 |
| **성능** | 응답에 필요한 필드만 select 가능 (`projection`) | 매핑 비용, 객체 할당 증가 |
| **테스트** | 도메인 테스트가 HTTP·JSON과 무관해짐 | 전체 흐름 테스트 작성량 증가 |
| **팀 협업** | 프론트엔드는 DTO 스펙만, 백엔드는 도메인만 봐도 됨 | 매퍼(MapStruct 등) 학습 비용 |

**MapStruct, ModelMapper** 같은 도구가 매핑 보일러플레이트를 줄여주지만, 시니어 관점에서는 **수동 매퍼를 한 번 거치는 비용**이 오히려 변경 영향 범위를 가시화해주는 장점이 더 크다는 의견도 많다 (특히 응답 구조가 자주 바뀌는 B2C).

#### 5. 실제 사례

- **카카오페이 결제 도메인**: `Money`, `Currency`, `AccountNumber` 같은 VO를 광범위하게 쓴다. 금액 계산 버그가 곧 사고로 이어지므로, `Money.add(Money)`처럼 타입 시스템이 단위·통화를 강제하게 만들어야 `long amount` 두 개를 더하다 통화가 섞이는 종류의 실수가 컴파일 단계에서 막힌다.
- **네이버 검색/광고 백오피스**: 내부 어드민과 외부 광고주 API가 같은 도메인을 다루지만, 어드민용 ResponseDTO에는 운영 지표가 포함되고 외부용은 정산 금액만 노출된다. Entity를 그대로 노출했다면 권한별 응답 분리가 불가능했다.
- **라인(LINE) 메신저**: 메시지 Entity는 server-side에만 존재하고, 모바일 클라이언트는 Protocol Buffers DTO로만 통신한다. Entity 스키마가 분기되어도(샤딩, 콜드 스토리지 분리) 클라이언트 프로토콜은 그대로 유지된다 — DTO가 **인터페이스 안정성의 방패** 역할을 한다.
- **반례 — 토이/사내 어드민**: 사용자가 10명이고 API와 DB가 1:1로 대응되는 사내 툴에서 DTO를 만드는 건 순수한 비용이다. 이런 경우 Spring Data REST나 `@JsonView`로 노출 필드만 제한하는 게 더 합리적이다.

#### 6. 시니어가 결정하는 지점: 언제 쓰고, 언제 쓰지 말 것인가

**쓴다 (분리한다)**
- 외부에 공개되는 API가 있는 시스템 (모바일/파트너사/공개 API)
- 도메인 규칙이 "음수 금지", "이메일 형식" 수준을 넘어 응집된 의미를 가질 때 → VO 도입
- 멀티 채널(웹/앱/배치)에서 같은 도메인을 다른 형태로 보여줘야 할 때
- Entity 직렬화로 인한 사고(권한·민감정보 누출, 순환참조)를 한 번이라도 경험한 팀

**쓰지 않는다 (또는 미룬다)**
- 1주일 안에 폐기될 PoC, 해커톤 코드
- 내부 운영용 CRUD 어드민 (대신 필드 화이트리스트로 통제)
- 팀이 3명 이하이고 API와 DB가 사실상 1:1인 단계 — 분리는 **고통이 보일 때** 도입하는 게 ROI가 좋다

**가장 흔한 시니어급 함정**: "DTO를 만들었으니 분리했다"고 착각하는 것. DTO 필드가 Entity 필드와 **이름·타입·구조까지 동일**하다면 그건 분리가 아니라 복사다. 진짜 분리는 *DTO에는 있는데 Entity에는 없는 필드*(예: `displayName` = `firstName + " " + lastName`)와 *Entity에는 있는데 DTO에는 없는 필드*(예: `passwordHash`, `internalScore`)가 동시에 존재할 때 의미를 갖는다.

> 💡 **왜 중요한가**: DTO·Entity·VO를 구분하는 것은 객체를 늘리는 일이 아니라, **변경의 동기를 분리해 한쪽 세계의 흔들림이 다른 쪽으로 번지지 않게 만드는 일**이다.
