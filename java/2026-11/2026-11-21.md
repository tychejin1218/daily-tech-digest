### 1. `InputStream.transferTo(outputStream)` (Java 9 정식, JEP 213)로 스트림 간 복사하기 — `byte[] buf = new byte[8192]` 할당하고 `while ((n = in.read(buf)) != -1) out.write(buf, 0, n);` 손수 돌리는 관성 벗어나기

파일 업로드 프록시, 멀티파트 응답 중계, S3 다운로드 후 재전송처럼 "읽어서 그대로 흘려보내는" 코드에서 수동 버퍼 루프를 쓰면 매번 버퍼 크기·반환값 -1 체크·`IOException` 전파를 손으로 조립하게 된다. `in.transferTo(out)`은 JDK 내부에서 최적 버퍼로 복사하고 총 전송 바이트를 `long`으로 돌려주며, `FileInputStream → FileOutputStream` 같은 경우 `FileChannel.transferTo`로 제로카피 경로를 타기도 한다. `Files.copy(in, path)`, `response.getBody().transferTo(servletOut)` 같은 패턴을 찾을 수 있다면 그게 바로 교체 지점.

> 💡 **왜 중요한가**: 수동 루프는 "읽고-쓰기" 두 줄에 버그가 섞여도 티가 안 나지만, `transferTo`는 의도("스트림 A를 B로 전부 흘려라")가 그대로 코드로 드러나서 리뷰·장애 분석 속도가 달라진다.

### 2. `SequencedCollection.getFirst() / getLast() / reversed()` (Java 21 정식, JEP 431)로 순서 있는 컬렉션의 양 끝 다루기 — `list.get(0)` / `list.get(list.size() - 1)` / `Collections.reverse(new ArrayList<>(list))` 섞어 쓰는 관성 벗어나기

`List`, `LinkedHashMap.sequencedKeySet()`, `LinkedHashSet` 모두 삽입 순서가 있는데도, 그동안 "첫 원소"는 `list.get(0)`, `Set`은 `iterator().next()`, 역순은 `ListIterator`나 새 리스트 복사로 제각각이었다. Java 21부터 `SequencedCollection`/`SequencedMap` 인터페이스가 추가되면서 `getFirst()`, `getLast()`, `addFirst()`, `addLast()`, `reversed()`가 통일 API로 뚫렸고, 비어 있으면 `NoSuchElementException`이 명시적으로 터져 "인덱스 -1" 같은 암묵적 실패보다 디버깅이 깔끔하다. 특히 `reversed()`는 **원본을 복사하지 않고 뷰**를 돌려주므로 역순 순회 때 메모리 할당이 사라진다.

> 💡 **왜 중요한가**: "최근 N개를 반대로 보여줘" 같은 요구를 `List`/`LinkedHashSet`/`LinkedHashMap` 어디서든 같은 메서드 이름으로 쓸 수 있다는 건, 컬렉션 타입이 바뀔 때마다 호출 코드를 손대지 않아도 된다는 뜻이다.
