### Database Tip 1: PostgreSQL `Index-Only Scan`과 `Visibility Map` — 테이블을 아예 건드리지 않고 인덱스만으로 쿼리를 끝내는 MVCC의 숨은 지름길

PostgreSQL은 MVCC 특성상 "이 튜플이 현재 트랜잭션에게 보이는가?"를 확인하기 위해 보통 인덱스 조회 후 반드시 Heap을 한 번 더 방문해야 한다(`Index Scan`). 하지만 `Visibility Map`(VM)이 "이 페이지의 모든 튜플이 모든 트랜잭션에게 보인다"고 표시해두면, PostgreSQL은 Heap 접근을 생략하고 인덱스만으로 결과를 돌려주는 `Index-Only Scan`으로 전환한다. 문제는 `VACUUM`이 돌지 않으면 VM이 갱신되지 않아 커버링 인덱스를 만들어놔도 계속 `Heap Fetches`가 발생한다는 점이다.

```
일반 Index Scan:
  [Index B+Tree] ──► [Heap Page] (가시성 체크)
       ▲                ▲
   한 번 I/O         또 한 번 I/O

Index-Only Scan (VM이 all-visible일 때):
  [Index B+Tree] ──► [Visibility Map bit=1] ──► 끝!
       ▲                     ▲
   한 번 I/O             메모리 8KB당 2bit
```

```sql
-- 커버링 인덱스 생성 (PG 11+)
CREATE INDEX idx_orders_covering
  ON orders (user_id) INCLUDE (amount, status);

EXPLAIN (ANALYZE, BUFFERS)
SELECT amount, status FROM orders WHERE user_id = 42;

-- VACUUM 전: Heap Fetches: 1523  ← 인덱스만 봐도 됐는데 Heap 1523번 터치
-- VACUUM 후: Heap Fetches: 0     ← 진짜 Index-Only Scan
```

실무에서 "INCLUDE로 커버링 인덱스 만들었는데 왜 안 빨라져?"라는 질문의 90%는 `autovacuum`이 느려서 VM이 최신이 아니기 때문이다. `pg_stat_user_tables`의 `n_dead_tup`이 높다면 VM이 낡았다는 신호다.

> 💡 **왜 중요한가**: 커버링 인덱스는 "만드는 것"이 아니라 "VM이 갱신된 상태로 유지하는 것"까지가 완성이며, VACUUM 전략이 곧 Index-Only Scan 적중률이다.

### Database Tip 2: JPA `@BatchSize`와 `hibernate.default_batch_fetch_size` — N+1을 `JOIN FETCH` 없이 "N/batch_size+1"로 압축하는 숨은 IN 절 전략

N+1 문제 해결책으로 `JOIN FETCH`나 `@EntityGraph`가 유명하지만, 페이징이 필요하거나 Cartesian Product이 폭발하는 ToMany 관계에서는 쓸 수 없다(`HHH000104: firstResult/maxResults specified with collection fetch; applying in memory`). 이때 `@BatchSize(size=100)` 또는 글로벌 설정 `hibernate.default_batch_fetch_size=100`을 켜면, Hibernate가 Lazy 프록시 초기화를 미루다가 접근 시점에 **아직 초기화 안 된 프록시들의 ID를 모아** `WHERE id IN (?, ?, ..., ?)` 한 방으로 처리한다.

```
N+1 (기본):
  SELECT * FROM team;                        -- 1번
  SELECT * FROM member WHERE team_id = 1;    -- N번
  SELECT * FROM member WHERE team_id = 2;
  ... (100개 팀이면 101번 쿼리)

@BatchSize(size=100):
  SELECT * FROM team;                                      -- 1번
  SELECT * FROM member WHERE team_id IN (1,2,...,100);     -- 1번
  (100개 팀이면 2번 쿼리로 끝)
```

```java
// 1) 엔티티 레벨
@OneToMany(mappedBy = "team", fetch = FetchType.LAZY)
@BatchSize(size = 100)
private List<Member> members;

// 2) 또는 글로벌 (application.yml)
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 100
```

주의할 함정 세 가지: ① `size`가 너무 크면 Oracle의 `IN` 절 1000개 제한에 걸린다(100~500 권장). ② `JOIN FETCH`와 섞어 쓰면 `JOIN FETCH`가 우선되어 BatchSize가 무시된다. ③ PostgreSQL은 IN 절이 길어지면 플래너 비용이 올라가므로 통계를 다시 확인해야 한다.

> 💡 **왜 중요한가**: 페이징·ToMany 조합에서 `JOIN FETCH`를 쓸 수 없을 때, `@BatchSize`는 "코드 한 줄로 쿼리 수를 100배 줄이는" 거의 유일한 현실적 해법이다.
