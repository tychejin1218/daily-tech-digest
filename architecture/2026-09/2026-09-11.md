### Multi-Agent Orchestration — "Agent 하나로 부족하면 여러 개 붙이면 되지"라는 순진함, 그리고 5개 agent가 서로 pass-the-buck하며 하룻밤에 $12,000 태우고 결론 못 낸 새벽

---

#### 시작하기 전에 — 왜 이 주제가 함정인가

Plan-and-Execute까지 배우면 자연스러운 다음 생각이 있다.

> "Planner 1개 + Executor 1개로 되면, Planner 1개 + Executor 5개(각자 전문화)로 나누면 훨씬 잘 되지 않을까?"

이 순진한 확장이 만드는 참사가 있다. 2025년 초 실리콘밸리의 한 시리즈 B 스타트업(레거시 코드 자동 리팩토링 서비스)이 정확히 이 함정에 빠졌다. **"Architect agent + Code writer agent + Reviewer agent + Test writer agent + Documenter agent"** 5-agent 파이프라인을 붙였는데, 어느 새벽 Reviewer가 Code writer에게 "이거 다시 짜"를 던지고 Code writer가 다시 짜서 넘기면 Reviewer가 또 "다시 짜"를 던지는 무한 반복이 벌어졌다. 아침에 확인하니 **한 PR에 GPT-4 tokens $12,000 소진, 최종 결과물은 empty diff**. 그날 오후 CTO가 "우린 왜 Cursor를 못 이기지?"를 되뇌인 게 시작이었다.

Multi-Agent는 "Agent를 더 붙이면 더 똑똑해진다"는 가정 위에 서 있는데, 이 가정은 **틀렸다**. 오히려 대부분의 실무 문제에서 Multi-Agent는 Single-Agent보다 느리고, 비싸고, 관측 불가능하다. 그럼 언제 써야 하는가? 이게 오늘의 진짜 질문이다.

---

#### 1. Multi-Agent Orchestration이 실제로 뭔가

정의부터 정확히 하자. **"여러 LLM 호출을 순차적으로 하는 것"은 Multi-Agent가 아니다.** 그건 그냥 pipeline이다. Multi-Agent의 정의는 이렇다:

> **자율적 판단 권한을 가진 두 개 이상의 agent가, 공유 상태(shared state) 또는 메시지를 주고받으며, 각자의 goal을 향해 협력/경쟁하는 시스템**

핵심은 "자율적 판단 권한"이다. Agent A가 Agent B에게 무엇을 시킬지, 결과를 받았을 때 다시 요청할지, 언제 멈출지를 **LLM이 결정**한다. 이게 hard-coded pipeline과의 결정적 차이고, 동시에 통제 불가능성의 근원이다.

#### 3. 진짜 문제 — Multi-Agent의 4가지 실패 모드

##### 3-1. Coordination Overhead (조정 비용 폭발)

Agent가 N개면, 각 agent는 다른 agent들의 상태/결과를 context에 담아야 한다. 즉 **context가 O(N²)로 증가**한다.

| Agent 수 | 평균 turn당 context tokens | 5턴 대화 총 비용 (GPT-4 기준) |
|---------|----------------------------|-------------------------------|
| 1       | 4K                         | ~$0.60                        |
| 3       | 12K (각자 서로의 결과 공유) | ~$5.40                        |
| 5       | 32K                        | ~$24                          |
| 10      | 90K+ (context window 위험) | ~$135, 그리고 truncation 시작 |

Cursor가 초기에 multi-agent를 실험했다가 **single-agent + long-context Claude**로 회귀한 이유가 이거다. Agent끼리 상태 넘기느라 태우는 token이 문제 풀이에 쓰는 token을 초과한다.

##### 3-2. Diffusion of Responsibility (책임의 확산)

"이건 내 담당 아닌 것 같은데?"를 LLM이 정중하게 반복한다.

실제 로그 예시 (익명화):

```
[Architect] → [CodeWriter]: "auth 모듈을 리팩토링해줘"
[CodeWriter]: "구조 결정이 필요합니다. Architect에게 위임합니다."
[Architect]: "구현 세부는 CodeWriter 담당입니다."
[CodeWriter]: "요구사항이 모호합니다. PM agent에게 확인 요청."
[PM]: "기술 판단은 Architect가..."
```

**5턴, $8 소비, empty diff.** 이 패턴이 위의 $12,000 참사의 정체다.

##### 3-3. Consensus Drift (합의 표류)

Debate 패턴에서 특히 심각하다. Advocate와 Critic이 각자 "합리적인 반박"을 반복하다 보면, N턴 후 **원래 질문과 무관한 지점**에서 합의가 이뤄진다. Anthropic이 2024년 발표한 multi-agent research에서 관찰한 현상: "Agent들이 서로에게 지나치게 예의 바르게(sycophantic) 반응하며, N=6 이상에서 정답률이 오히려 하락."

##### 3-4. Debugging Blackhole

Single-agent에서는 trace가 선형이다. Multi-agent에서는 trace가 **DAG 또는 cycle**이 된다. LangSmith/LangFuse도 이걸 100% 시각화 못 한다. "왜 잘못된 답이 나왔지?"를 추적하는 데 개발자 하루가 사라진다.

#### 4. 실제 사례 — 성공과 실패

##### ✅ 성공: **Devin (Cognition Labs) — Hierarchical, 매우 좁은 도메인**

Devin은 "SWE 태스크 자동 수행" 하나에만 집중한다. Planner가 태스크를 쪼개고, Executor가 shell/browser를 통해 실행하고, Verifier가 결과 검증. **각 agent의 역할과 tool이 명확히 분리**되어 있고, **상태는 파일시스템에 저장**되어 context 폭발을 회피한다.

##### ✅ 성공: **AWS Bedrock Agents (Supervisor 패턴)**

"고객 문의 → intent 분류 → 각 도메인별 전문 agent로 라우팅" 같은 **fan-out은 있지만 fan-in이 없는** 구조. Supervisor가 딱 한 번 라우팅하고 끝. 이건 사실상 dynamic routing이지 진짜 multi-agent가 아니지만, "잘 되는 multi-agent"의 대부분이 이 형태다.

##### ❌ 실패: **AutoGen (Microsoft Research, 2023 초기 버전)**

논문 데모는 훌륭했지만 프로덕션 도입한 기업들이 대거 후퇴. 문제는 **group chat 패턴의 non-determinism**. 같은 입력에 같은 결과가 안 나오고, 실패 시 재현이 불가능. Microsoft 자체도 2024년 이후 **AutoGen Studio + magentic-one**으로 방향을 틀며 supervisor 강화.

##### ❌ 실패: **BabyAGI / AutoGPT의 계승자들**

"목표 던지면 스스로 계획하고 실행하는 자율 agent"의 이상은 여전히 미완. **명확한 termination condition이 없기 때문**에 자기 자신에게 무한히 sub-task를 생성하며 credit card만 태운다.

##### 🤔 애매: **CrewAI — 조직 은유의 함정**

"CEO / Manager / Worker" 은유가 직관적이라 도입이 쉽다. 하지만 **인간 조직의 계층은 정보 비대칭과 권한 분리로 작동**하는데, LLM 사이엔 그 둘이 없다. 결국 "직함만 있는 동일한 GPT-4 호출 5개"가 되기 십상. 데모용으론 훌륭하지만 프로덕션에선 supervisor 패턴으로 단순화해야 산다.

#### 5. 시니어 관점 결정 트리 — 언제 쓰고 언제 안 쓰는가

```
                    "Multi-Agent로 갈까?"
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
       Yes if ALL true:        No if ANY true:
              │                       │
    ─ 태스크가 명확히          ─ Single agent + long
      독립적 sub-task로 분리     context로 안 되는지
      가능한가? (병렬성)         먼저 시도했는가?
                                     │
    ─ 각 agent가 서로 다른      ─ 문제가 5턴 이하로
      tool/권한/데이터 접근을     풀리는가?
      가져야 하는가?
                                ─ Latency SLA가 3초 미만?
    ─ 실패 격리(fault           
      isolation)가 필요한가?    ─ 재현성이 중요한가?
      (한 agent 실패해도         (금융, 의료, 법률)
      다른 agent 계속)          
                                ─ 비용이 사용량에 비례해
    ─ 최소 10K 요청/일           빠르게 성장해야 하는가?
      규모라 오케스트레이션
      복잡성을 상각할 수 있는가?
```

##### 시니어의 실전 판단 기준 3가지

**1) "이 태스크를 신입 개발자 5명에게 시킨다면 정말 5명이 필요한가?"**
답이 "사실 시니어 1명이 하는 게 나은데"라면 single-agent가 정답이다. Multi-agent도 마찬가지다.

**2) "termination이 명확한가?"**
"언제 이 agent 시스템이 멈추는가?"를 3초 안에 답할 수 없으면 만들지 마라. Max iteration은 안전장치이지 설계가 아니다.

**3) "실패 시 어느 agent 책임인가?"**
Postmortem을 상상해봤을 때 "Reviewer가 잘못했는지 CodeWriter가 잘못했는지 모르겠다"가 나오면, 그 시스템은 운영 불가능하다.

#### 6. 그럼 뭘 해야 하나 — 대안 3가지

| 대안 | 언제 |
|------|------|
| **Single agent + more tools** | 대부분의 경우. Claude 3.5+ 는 20+ tool call도 안정적으로 처리 |
| **Static pipeline** (agent 아님) | 순서가 고정되어 있다면. Airflow/Temporal로 오케스트레이션 |
| **Supervisor with 2-3 workers, no worker-to-worker communication** | 진짜 multi-agent가 필요한 최소 형태 |

**"진짜 multi-agent가 필요하다"의 진짜 조건은 하나다: 병렬성이 latency 절감으로 이어지는 경우.** 예: 100개 문서를 각각 요약해서 취합하는 map-reduce. 이건 병렬 fan-out으로 실제 시간이 줄어든다. 나머진 대부분 "single agent + longer context"가 이긴다.

---

#### 7. 마지막 함정 — "Agent Framework를 먼저 고르지 마라"

LangGraph, CrewAI, AutoGen, Swarm 중 뭘 쓸지 먼저 결정하고 아키텍처를 짜면 필패한다. **아키텍처가 먼저, 프레임워크는 그다음**이다. 대부분의 실무 문제는:

- Supervisor 1개 + Worker 2~3개
- 상태는 외부 저장소(Redis/Postgres)에 명시적으로
- Worker 간 직접 통신 금지
- Max iteration 하드코딩

이 정도만 지키면 vanilla Python + LLM SDK로 200줄이면 충분하다. 프레임워크는 "우리 팀의 진짜 문제가 상태 관리인지, 관측성인지, 재시도인지"를 겪어본 후에 골라도 늦지 않다.

---

> 💡 **왜 중요한가**: Multi-Agent는 "agent를 더하면 더 똑똑해진다"는 직관이 틀린 영역이라, 시니어는 팀이 이 유혹에 빠지기 전에 "single-agent + long context로 먼저 시도했는가?"를 물어 $12,000짜리 새벽을 예방하는 사람이다.
