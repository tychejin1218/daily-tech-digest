### PostgreSQL `HOT (Heap-Only Tuple) Update` — 인덱스를 건드리지 않는 UPDATE의 조건, 그리고 `FILLFACTOR`가 왜 100이 아닌가

PostgreSQL의 MVCC는 UPDATE가 사실상 "새 튜플 INSERT + 옛 튜플 dead 표시"이기 때문에, 원칙적으로는 모든 인덱스에도 새 튜플을 가리키는 엔트리를 추가해야 한다. 하지만 **변경된 컬럼이 인덱스에 포함되지 않고**, **같은 페이지 안에 새 튜플을 넣을 공간이 있으면** HOT Update가 발동해서 인덱스는 갱신하지 않고 옛 튜플에서 새 튜플로 포인터만 이어붙인다. 이 "같은 페이지의 공간"을 확보하기 위한 장치가 바로 `FILLFACTOR`로, 기본값 100은 페이지를 꽉 채워버려 HOT Update를 원천 차단하므로, UPDATE가 잦은 테이블은 `FILLFACTOR=80~90`으로 낮춰 페이지에 여유 공간을 남겨두는 것이 정석이다.

```sql
-- UPDATE가 잦은 테이블: 페이지에 20% 여유 공간 확보
ALTER TABLE orders SET (FILLFACTOR = 80);
-- 기존 데이터에 적용하려면 재구성 필요
VACUUM FULL orders;  -- 또는 CLUSTER

-- HOT Update가 발동했는지 확인
SELECT relname, n_tup_upd, n_tup_hot_upd,
       ROUND(100.0 * n_tup_hot_upd / NULLIF(n_tup_upd, 0), 2) AS hot_ratio_pct
FROM pg_stat_user_tables
WHERE relname = 'orders';
-- hot_ratio_pct가 90% 이상이면 건강, 50% 미만이면 인덱스 재점검
```

```
[일반 UPDATE - FILLFACTOR=100]                [HOT Update - FILLFACTOR=80]
Page A (100% 참): 새 튜플 못 들어감              Page A (80% 참): 여유공간 O
  ├─ old tuple (dead)                            ├─ old tuple (dead) ──┐
Page B: 새 튜플                                  ├─ new tuple ◄────────┘ (HOT chain)
  └─ new tuple                                   └─ 인덱스 갱신 X → I/O 절감
     └─ 모든 인덱스 재작성 → I/O 폭발
```

실무에서 `updated_at`처럼 매번 바뀌지만 인덱스는 안 걸린 컬럼이 있다면 HOT 후보이고, 반대로 UPDATE 대상 컬럼이 인덱스에 하나라도 걸려 있으면 HOT은 즉시 무효화된다. "왜 UPDATE만 하는데 인덱스 팽창(index bloat)이 이렇게 심하지?"의 답은 대부분 `FILLFACTOR=100` + 인덱스 컬럼 UPDATE 조합이다.

> 💡 **왜 중요한가**: MVCC 환경에서 UPDATE 성능은 "쿼리 튜닝"이 아니라 "물리적 페이지 레이아웃"이 결정하며, HOT 비율은 인덱스 팽창과 VACUUM 부하를 좌우하는 조기 경보 지표다.

### MySQL `LIMIT 1000000, 20`의 지옥 — Deep Pagination과 Seek Method(Keyset Pagination)

`ORDER BY id LIMIT 1000000, 20`은 "100만 개를 읽고 버린 뒤 20개만 반환"하는 쿼리다. MySQL은 OFFSET을 만족시키기 위해 **앞의 100만 행을 실제로 읽어야만** 하므로, 페이지 번호가 커질수록 응답 시간이 선형으로 증가하다가 뒷페이지에서는 초 단위로 폭발한다. 해결책은 OFFSET을 버리고 마지막으로 본 행의 정렬 키 값을 기준으로 "그 이후"를 조회하는 **Seek Method(Keyset Pagination)** 로, 정렬 컬럼에 인덱스만 있으면 페이지가 몇 번이든 항상 상수 시간에 20건을 가져온다.

```sql
-- ❌ Offset Pagination: 뒷페이지로 갈수록 느려짐
SELECT id, title, created_at
FROM articles
ORDER BY created_at DESC, id DESC
LIMIT 1000000, 20;
-- → 100만 행을 읽고 버린 뒤 20건 반환 (수 초 소요)

-- ✅ Seek Method: 마지막으로 본 (created_at, id)를 커서로 사용
SELECT id, title, created_at
FROM articles
WHERE (created_at, id) < ('2026-09-14 10:23:11', 8472913)
ORDER BY created_at DESC, id DESC
LIMIT 20;
-- → 인덱스 (created_at DESC, id DESC)로 20건만 읽음 (수 ms)
```

```
[Offset Pagination]              [Seek Method]
페이지 1:   [1~20]     빠름       페이지 1:   커서 없음 → 최신 20건
페이지 100: [~2000]    보통       페이지 100: 커서 이후 20건
페이지 5만: [~100만]   💀 폭발    페이지 5만: 커서 이후 20건 ← 항상 O(log N + 20)
         └─ OFFSET만큼 실제로 읽음       └─ 인덱스 트리 진입점 이동만
```

Seek Method의 트레이드오프는 (1) "임의의 페이지 번호로 점프" 기능이 사라진다는 점(무한 스크롤 UX에는 완벽하지만 "127페이지로 가기" UI에는 부적합), (2) 정렬 키가 유니크하지 않으면 `(created_at, id)` 같은 복합 커서가 필요하다는 점이다. 실무에서 관리자 페이지에 "마지막 페이지" 버튼을 눌렀다가 DB가 뻗는 사고는 대부분 OFFSET 페이지네이션 때문이며, 페이스북/트위터/인스타그램의 무한 스크롤이 전부 Seek Method인 이유이기도 하다.

> 💡 **왜 중요한가**: 페이지네이션은 UI 패턴이지만 성능 특성은 완전히 다르며, 데이터가 100만 건을 넘어가는 순간 OFFSET은 반드시 장애의 진원지가 된다.
