### `@EventListener`의 `@TransactionalEventListener`를 모르면, 이벤트 핸들러가 **롤백된 트랜잭션의 데이터**를 처리한다

`@EventListener`로 등록한 핸들러는 `publishEvent()`가 호출되는 즉시 실행되기 때문에, 아직 커밋되지 않은 트랜잭션 내부의 데이터를 그대로 읽고 후속 작업(이메일 발송, 외부 API 호출, 메시지 큐 발행)을 수행한다. 문제는 이후에 트랜잭션이 롤백되면 DB에는 데이터가 없는데 이메일은 이미 나갔거나, 결제 승인 API는 이미 호출된 상태가 된다는 점이다. `@TransactionalEventListener(phase = AFTER_COMMIT)`을 쓰면 커밋 이후에만 핸들러가 실행되어 "존재하지 않는 데이터를 처리하는" 유령 이벤트를 원천 차단할 수 있다.

```
[일반 @EventListener]                    [@TransactionalEventListener AFTER_COMMIT]
   ┌──────────────────┐                     ┌──────────────────┐
   │ @Transactional   │                     │ @Transactional   │
   │  save(order)     │                     │  save(order)     │
   │  publishEvent()──┼──► 즉시 실행 ❌     │  publishEvent()──┼──► 큐에 대기
   │  throw ex        │    (이메일 발송)    │  throw ex        │    (실행 X)
   └──────────────────┘                     └──────────────────┘
        ROLLBACK                                  ROLLBACK
   DB엔 주문 없음                            DB엔 주문 없음
   근데 이메일은 갔음 💀                      이메일도 안 나감 ✅
```

**실제 사례**: 주문 생성 후 `@EventListener`로 재고 차감 API를 호출했는데, 주문 트랜잭션이 유니크 제약 위반으로 롤백되면서 "존재하지 않는 주문의 재고만 계속 차감되는" 이슈. 재고가 마이너스가 되어서야 발견됨.

**트레이드오프**: `AFTER_COMMIT`은 커밋 후에 실행되므로, 핸들러 실패 시 원본 트랜잭션을 되돌릴 수 없다 → 반드시 재시도 큐(Outbox 패턴)와 조합해야 진짜 안전하다. `BEFORE_COMMIT`은 커밋 직전에 실행되어 실패 시 롤백 가능하지만, 이벤트 핸들러가 DB 작업을 하면 같은 트랜잭션에 묶여 성능이 나빠진다.

> 💡 **왜 중요한가**: "이벤트 발행 = DB 커밋 완료"라는 착각은 프로덕션에서 데이터 정합성 사고를 만드는 가장 조용한 원인이다.

### `@Async`의 반환 타입이 `void`면 예외가 **완전히 사라진다** — 로그조차 남지 않는다

`@Async` 메서드가 `void`를 반환하면 호출 스레드는 즉시 리턴받고, 실제 작업 스레드에서 발생한 예외는 붙잡을 주체가 없어 그대로 삼켜진다. 기본 `SimpleAsyncUncaughtExceptionHandler`가 `WARN` 레벨로 로그를 찍긴 하지만, 로그 레벨 설정이나 로그 어그리게이터 필터에 걸려 관측되지 않는 경우가 대부분이다. `CompletableFuture<Void>`로 반환 타입만 바꿔도 `.exceptionally()` 또는 커스텀 `AsyncUncaughtExceptionHandler`로 예외를 반드시 잡아낼 수 있다.

```
[반환 타입: void]                          [반환 타입: CompletableFuture<Void>]
   caller ──► asyncMethod()                   caller ──► asyncMethod()
              │                                          │
              └─ throw RuntimeException                  └─ throw RuntimeException
                        │                                          │
                        ▼                                          ▼
                  ┌──────────┐                              ┌──────────────┐
                  │ 삼켜짐 💀 │                              │ Future에 저장 │
                  │ (WARN 로그 │                              │ .exceptionally│
                  │  묻히기 쉬움)│                              │  으로 처리 가능│
                  └──────────┘                              └──────────────┘
```

**실제 사례**: 결제 완료 후 `@Async void sendReceipt()`로 영수증 발송 → SMTP 서버 일시 장애로 예외 발생 → 로그 레벨이 `INFO`로 설정돼 있어 `WARN`이 안 남음 → 3일간 영수증 미발송을 CS 문의로만 발견. 반환 타입만 `CompletableFuture<Void>`로 바꾸고 전역 `AsyncUncaughtExceptionHandler`를 등록하니 Sentry에 바로 알림이 왔다.

**트레이드오프**: `CompletableFuture` 반환은 호출자가 `.get()`이나 `.join()`을 실수로 호출하면 비동기의 의미가 사라진다 → 팀 컨벤션으로 "리턴값을 절대 대기하지 말 것"을 못 박거나, 정말 fire-and-forget이면 `AsyncUncaughtExceptionHandler`를 반드시 커스텀 등록하는 것이 안전하다.

> 💡 **왜 중요한가**: "예외가 발생했는데 아무도 몰랐다"는 프로덕션 사고 원인 1위 — `@Async void`는 그 원인을 코드에 심어놓는 것과 같다.
