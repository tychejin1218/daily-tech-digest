### 1. `lateinit` vs `by lazy`: "나중에 초기화"의 두 얼굴, 그리고 Spring에서 왜 `lateinit`을 쓰는가

Kotlin에서 "선언 시점에 값을 줄 수 없는" 프로퍼티를 다루는 두 가지 방법이다. `lateinit var`는 **가변(var) + non-null + 외부에서 주입**되는 값에 쓰고(스레드 안전 보장 X, 재할당 가능), `by lazy`는 **불변(val) + 최초 접근 시 계산**되는 값에 쓴다(기본 `LazyThreadSafetyMode.SYNCHRONIZED`로 스레드 안전). Spring에서 `@Autowired lateinit var userService: UserService`가 흔한 이유는 DI 컨테이너가 생성자 호출 이후 필드를 주입하기 때문에 "선언 시점엔 null이지만 사용 시점엔 절대 null이 아닌" 상황에 딱 맞기 때문이다. 다만 **생성자 주입이 가능하다면 `lateinit`보다 생성자 주입이 우선**이다 — 불변성과 테스트 용이성을 모두 얻을 수 있기 때문.

```kotlin
// ❌ 필드 주입 (옛날 스타일)
class OrderService {
    @Autowired lateinit var paymentClient: PaymentClient
    // 접근 전까지 미초기화면 UninitializedPropertyAccessException
}

// ✅ 생성자 주입 (권장)
class OrderService(private val paymentClient: PaymentClient)

// by lazy: 비싼 초기화를 "실제 사용될 때까지" 미룬다
class ReportGenerator {
    private val heavyTemplate: Template by lazy {
        loadFromDisk("report-template.xml")  // 최초 접근 시 1회만 실행
    }
}
```

`::propertyName.isInitialized`로 초기화 여부를 체크할 수 있지만, 이 코드가 필요하다는 건 보통 설계가 잘못됐다는 신호다.

> 💡 **왜 중요한가**: `lateinit`을 "null을 피하는 편리한 트릭"으로 쓰면 `UninitializedPropertyAccessException`이라는 NullPointerException보다 더 추적하기 어려운 런타임 에러를 만나게 된다 — "언제 초기화되는가"를 설계 단계에서 명확히 해야 하는 이유.

### 2. `object` 선언: Kotlin에서 싱글톤을 만드는 "언어 수준" 지원, 그러나 Spring 빈과 혼동하지 마라

Kotlin의 `object` 키워드는 **클래스 정의 + 단일 인스턴스 생성**을 한 번에 처리하는 언어 기능이다. Java의 `enum Singleton { INSTANCE; }` 트릭이나 이중 체크 락킹 같은 보일러플레이트 없이 **JVM 클래스 로더가 보장하는 스레드 안전한 싱글톤**을 얻는다. 내부적으론 `private static final INSTANCE` 필드와 `private` 생성자로 컴파일된다.

```kotlin
// 1. object 선언 — 언어 수준 싱글톤
object DateFormatter {
    private val formatter = DateTimeFormatter.ISO_LOCAL_DATE
    fun format(date: LocalDate): String = date.format(formatter)
}
DateFormatter.format(LocalDate.now())  // 클래스명으로 바로 접근

// 2. 익명 object — Java의 익명 클래스 대체
button.addListener(object : ClickListener {
    override fun onClick() { println("clicked") }
})

// 3. Spring과 함께 쓸 때 — ❌ 이렇게 하면 안 된다
@Service
object UserService {  // Spring은 object를 빈으로 등록할 수 없다
    fun findById(id: Long): User = ...
}

// ✅ Spring 빈은 평범한 class로
@Service
class UserService(private val repo: UserRepository) {
    fun findById(id: Long): User = repo.findById(id)
}
```

**언제 `object`를 쓰고, 언제 Spring `@Component`를 쓰는가?**
- `object`: 상태가 없는 유틸리티, 상수 모음, DSL 빌더, 전략 패턴의 구체 구현 — **의존성이 없는 것**
- `@Component`/`@Service`: DI가 필요하거나, 트랜잭션/AOP가 걸리거나, 테스트 시 mocking이 필요한 것

| 구분 | `object` | `@Component class` |
|------|----------|-------------------|
| 인스턴스 관리 | JVM 클래스 로더 | Spring 컨테이너 |
| DI 가능? | ❌ (생성자 불가) | ✅ |
| Mocking | 어려움 (MockK의 `mockkObject` 필요) | 쉬움 |
| 트랜잭션/AOP | ❌ (프록시 불가) | ✅ |

> 💡 **왜 중요한가**: "싱글톤이니까 `object`로 만들자"는 발상은 DI 컨테이너의 존재 이유를 무시하는 것 — Spring 환경에선 **테스트 가능성과 AOP 지원이 생명**이고, `object`는 그 둘을 모두 포기한다. 유틸성 코드와 비즈니스 로직을 분리하는 감각이 Kotlin + Spring의 첫 번째 관문이다.
