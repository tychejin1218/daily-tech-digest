### 3-Tier 아키텍처 — "레이어(Layer)"와 "티어(Tier)"를 헷갈리지 마라

주니어와 시니어를 가르는 질문 하나. **"Controller-Service-Repository로 나눈 스프링 부트 앱을 하나의 JAR로 EC2 한 대에 띄우면, 이건 3-tier 아키텍처인가요?"**

정답은 **"3-layer지만 1-tier"** 다. 이 구분을 흐릿하게 알고 있으면, "우리는 이미 3-tier니까 확장성 걱정 없어요"라는 재앙급 오해가 회의실을 지배하게 된다.

---

#### 1. Layer는 논리, Tier는 물리다

이미 배운 **레이어드 아키텍처**(Controller-Service-Repository)는 **코드 조직의 논리적 분리**다. 같은 JVM 안에서 메서드 호출로 서로를 부른다. 반면 **3-tier 아키텍처**는 **배포·프로세스·물리 머신 경계**로 나눈 것이다. Tier 사이의 호출은 반드시 **네트워크**를 타야 한다.

| 구분 | Layer | Tier |
|---|---|---|
| 성격 | 논리적 (코드 조직) | 물리적 (배포 단위) |
| 경계 | 패키지·클래스 | 프로세스·머신·네트워크 |
| 호출 방식 | 메서드 호출 (in-process) | RPC/HTTP/JDBC (out-of-process) |
| 실패 모드 | NullPointerException 정도 | 네트워크 단절, 타임아웃, 부분 실패 |
| 확장 단위 | 없음 (같이 배포) | Tier 단위로 독립 확장 |

**핵심**: N-layer 앱은 1-tier로도, N-tier로도 배포될 수 있다. 코드 구조가 물리 구조를 강제하지 않는다.

---

#### 2. 고전적 3-Tier의 구조

```
┌─────────────────────────────────────────────────────────────┐
│  Tier 1: Presentation Tier                                  │
│  - 브라우저, 모바일 앱, 데스크톱 클라이언트                    │
│  - 사용자 입력·출력, UI 렌더링만 담당                          │
└──────────────────────┬──────────────────────────────────────┘
                       │ HTTP/HTTPS (네트워크 경계)
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  Tier 2: Application Tier (=Logic/Middle Tier)              │
│  - WAS (Tomcat, IIS, WebLogic 등)                            │
│  - 비즈니스 로직, 트랜잭션 경계, 인증·인가                     │
│  - ★ 내부는 Controller-Service-Repository 레이어드 구조       │
└──────────────────────┬──────────────────────────────────────┘
                       │ JDBC/ODBC (네트워크 경계)
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  Tier 3: Data Tier                                          │
│  - RDBMS (Oracle, PostgreSQL, MySQL)                        │
│  - 영속화, 무결성 제약, 인덱스                                │
└─────────────────────────────────────────────────────────────┘
```

Tier 2 내부에는 여전히 우리가 배운 Controller-Service-Repository **레이어**가 살아 있다. 즉, **3-tier 안에 N-layer가 중첩**된다.

---

#### 3. 왜 굳이 물리적으로 쪼갰나 — 90년대의 맥락

3-tier는 1990년대 중반, **2-tier "클라이언트/서버" 모델의 실패**에서 태어났다.

당시 대세였던 클라이언트/서버 구조는 이랬다:

```
┌────────────────────┐       ┌────────────────────┐
│  Fat Client        │ ────► │  Database Server   │
│  (VB, PowerBuilder)│  SQL  │  (Oracle, Sybase)  │
│  비즈니스 로직 포함  │       │  Stored Proc 포함  │
└────────────────────┘       └────────────────────┘
```

문제가 터졌다:
- **배포 지옥**: 로직 수정 시 수천 대 데스크톱에 EXE를 재배포해야 함
- **DB 커넥션 폭증**: 클라이언트 1대 = DB 커넥션 1개. 1,000명 접속 = 1,000 커넥션
- **보안 구멍**: 클라이언트가 DB 자격증명을 들고 다님
- **로직 분산**: 같은 규칙이 VB 코드와 Stored Procedure에 이중으로 존재

**중간(Middle) Tier**를 끼워 넣어 이 문제를 한 번에 풀었다:
- 배포는 서버만 → 클라이언트는 얇게(Thin Client, 곧 브라우저)
- 커넥션 풀 → DB 커넥션은 수십 개로 충분
- DB 자격증명은 서버가 보관
- 로직은 Middle Tier에 단일화

이게 2000년대 초 **J2EE(WebLogic, WebSphere)**, **.NET Enterprise**, **Java Applet → JSP/Servlet** 대이동의 배경이다.

#### 4. 실제 사례

**은행 코어뱅킹 (예: 국내 시중은행 차세대 프로젝트)**
- Tier 1: 창구단말/ATM/인터넷뱅킹
- Tier 2: 채널계 WAS 팜 (Tuxedo, WebLogic) — 계정계와 분리된 별도 존
- Tier 3: 계정계 메인프레임 + Oracle RAC

왜? **규제(전자금융감독규정)** 가 물리적 망 분리와 계층별 방화벽을 요구하기 때문. 여기서 3-tier는 성능이 아니라 **감사·규정 준수**의 산물이다.

**초창기 Amazon.com (모놀리스 시절, ~2001년 이전)**
- Tier 1: 브라우저
- Tier 2: Obidos (거대 C++ 모놀리스, 수십 대 웹서버)
- Tier 3: Oracle 단일 인스턴스

트래픽이 폭증하며 Tier 2의 모놀리스가 병목이 되자 **SOA → 마이크로서비스**로 전환했다. 이때 "3-tier의 Tier 2를 여러 서비스로 쪼갠 것"이지, 3-tier 자체를 폐기한 게 아니다.

**전형적 스타트업 초기 (지금도 유효)**
- Tier 1: React SPA (Vercel/CloudFront)
- Tier 2: Spring Boot API 서버 (ECS/EC2)
- Tier 3: RDS PostgreSQL

Tier 2 안은 여전히 Controller-Service-Repository. **가장 지루하고, 가장 잘 작동하는 조합**이다.

---

#### 5. 트레이드오프

| 장점 | 대가 |
|---|---|
| Tier별 독립 확장 (WAS만 오토스케일) | 네트워크 홉이 늘어 **지연(latency) 증가** |
| Tier별 독립 배포·재시작 | 부분 실패 시나리오 발생 (WAS는 살고 DB만 죽는 등) |
| 보안 경계 분리 (DMZ, 내부망) | 네트워크·방화벽 설정 복잡도 |
| 클라이언트 얇게 유지 | Tier 2가 여전히 단일 장애점(SPOF) — 스케일 아웃하지 않으면 |
| Middle Tier에서 커넥션 풀링 | Tier 2 재기동 시 세션·캐시 유실 (세션 스토어 별도 필요) |

**주의**: 3-tier는 **"확장성이 좋다"기보다는 "확장 가능한 지점을 만들어준다"**. Tier 2를 EC2 1대에 띄우면 여전히 SPOF다. Tier가 나뉘어 있다는 사실만으로 확장되는 게 아니라, 각 Tier가 **stateless**하게 설계돼 있고 로드밸런서가 앞에 있어야 실제 확장이 된다.

---

#### 6. 시니어 관점 — 언제 쓰고, 언제 안 쓰나

**쓴다**
- 웹 기반 비즈니스 앱의 **기본값**. 특별한 이유가 없다면 여기서 시작
- 규제 산업 (금융, 의료, 공공): 망 분리 자체가 요구사항
- 클라이언트가 여럿(웹+모바일+파트너 API)일 때 — Tier 2가 공통 진입점

**안 쓰거나 변형한다**
- **초저지연 요구** (HFT, 실시간 게임 서버): 네트워크 홉이 곧 죽음. Tier를 합치거나 Tier 2와 Tier 3 사이를 in-memory DB로 대체
- **CLI/배치 전용 도구**: Presentation Tier가 무의미. Tier 2와 Tier 3만 있으면 됨
- **Edge/Serverless 아키텍처**: Tier 경계가 지역·요청 단위로 흩어져 전통적 3-tier 모델이 잘 안 맞음 (다음 단계에서 다룸)
- **CQRS/이벤트 소싱이 중심인 시스템**: 데이터 흐름이 3-tier의 요청/응답 축과 어긋남 (Lv2 이후 영역)

**가장 흔한 실수**: 팀이 Controller-Service-Repository로 코드를 나눠놓고 "우리는 3-tier"라고 부르는 것. 이건 **1-tier / 3-layer**다. 이걸 혼동하면 "우리는 이미 확장 가능한 구조"라 착각해 로드밸런서·세션 스토어·DB 이중화 같은 진짜 확장 작업을 미루게 된다.

---

> 💡 **왜 중요한가**: "Layer는 논리, Tier는 물리"라는 구분이 흐릿하면, 코드 구조를 아무리 잘 나눠도 배포·확장·장애 격리에서 얻는 게 없다는 사실을 놓치게 된다.
