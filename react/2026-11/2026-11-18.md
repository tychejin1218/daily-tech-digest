### 1. `key`에 `index`를 쓰면 안 되는 "진짜" 이유 — React는 key로 "같은 컴포넌트인지"를 판단한다

리스트를 렌더링할 때 `key={index}`를 쓰면 배열 중간에 항목을 삽입/삭제했을 때 React는 "같은 자리에 있는 항목은 같은 컴포넌트"로 착각한다. 그 결과 `useState`로 들고 있던 내부 상태(입력 값, 포커스, 애니메이션 진행도)가 "엉뚱한 항목"으로 옮겨 붙는다. React의 재조정(reconciliation)은 "같은 부모 아래서 같은 key를 가진 노드"를 같은 인스턴스로 간주하기 때문에, key는 "DOM 재사용 여부"를 넘어 "컴포넌트 신원(identity)"을 결정하는 식별자다.

```jsx
// 🚨 버그: 맨 앞에 항목을 추가하면 모든 input의 값이 한 칸씩 밀려 보인다
{items.map((item, i) => <ItemRow key={i} item={item} />)}

// ✅ 안정적인 ID 사용 — 항목이 어디로 이동해도 상태가 따라간다
{items.map((item) => <ItemRow key={item.id} item={item} />)}
```

| key 선택 | 중간 삽입 | 중간 삭제 | 정렬 변경 | 내부 state 보존 |
|----------|----------|----------|----------|----------------|
| `index` | ❌ 밀림 | ❌ 밀림 | ❌ 뒤섞임 | ❌ 엉뚱한 곳으로 |
| 안정적 ID | ✅ | ✅ | ✅ | ✅ |
| `Math.random()` | ❌ 매 렌더마다 재마운트 | - | - | ❌ 전부 초기화 |

> 💡 **왜 중요한가**: `key`는 "성능 힌트"가 아니라 "이 컴포넌트가 같은 컴포넌트인가"를 정의하는 React의 신원 시스템 — 잘못 쓰면 상태가 다른 행으로 순간이동하는 유령 버그가 생긴다.

### 2. `useState`의 초기값에 "함수 호출"을 직접 쓰면 매 렌더마다 실행된다 — "lazy initializer"의 정체

`useState(expensiveCompute())`는 초기값이 첫 렌더에만 "사용"되지만, `expensiveCompute()` 자체는 **매 렌더마다 호출된다**. React는 반환값을 버릴 뿐, 함수 실행 자체를 막아주지 않는다. `localStorage.getItem()`, JSON 파싱, 큰 배열 생성 같은 비싼 작업을 초기값으로 쓰면 리렌더링마다 조용히 CPU를 낭비한다. 해결책은 "값"이 아니라 "값을 만드는 함수"를 넘기는 **lazy initializer** 패턴이다.

```jsx
// 🚨 매 렌더마다 localStorage 읽고 JSON.parse — 수백 번 실행됨
const [cart, setCart] = useState(JSON.parse(localStorage.getItem('cart') || '[]'));

// ✅ 함수를 넘기면 "최초 1회"만 실행됨 — 함수 참조만 기다렸다가 호출
const [cart, setCart] = useState(() => JSON.parse(localStorage.getItem('cart') || '[]'));
```

```
useState(값)        → 매 렌더: expensiveCompute() 실행 → 결과 버림 → 저장된 state 반환
useState(() => 값)  → 1회만:   함수 호출 → 결과 저장
                      2회차+:  함수 호출 X → 저장된 state 바로 반환
```

같은 패턴이 `useReducer(reducer, initialArg, init)`의 세 번째 인자(init 함수)에도 존재한다. "초기화 비용이 보이지 않는 이유"는 React가 값을 반환하는 시점만 보여주고, 그 값을 만드는 데 얼마나 썼는지는 숨기기 때문이다.

> 💡 **왜 중요한가**: "첫 렌더에만 쓰이는 값"이라는 직관과 달리, 함수 호출 결과를 직접 넘기면 **매 렌더마다 비용이 발생**한다 — 느린 페이지의 원인이 리렌더 로직이 아니라 "초기화 코드"인 경우가 의외로 많다.
