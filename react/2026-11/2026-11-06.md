### 1. useLayoutEffect vs useEffect: "깜빡임"을 없애는 동기 실행의 비밀

`useEffect`는 브라우저 페인트 **이후** 비동기로 실행되지만, `useLayoutEffect`는 DOM 변경 직후 페인트 **직전**에 동기로 실행된다. 툴팁 위치 계산, 스크롤 복원, 요소 크기 측정처럼 "렌더 결과를 보고 다시 DOM을 수정해야 하는" 경우 `useEffect`를 쓰면 사용자가 잘못된 위치의 UI를 한 프레임 보게 되어 깜빡임(flicker)이 발생한다.

```jsx
// ❌ 깜빡임 발생: 0,0에 렌더 → 페인트 → 측정 → 재배치
useEffect(() => {
  const rect = ref.current.getBoundingClientRect();
  setPosition({ top: rect.top - 10 });
}, []);

// ✅ 페인트 전에 위치 보정 완료
useLayoutEffect(() => {
  const rect = ref.current.getBoundingClientRect();
  setPosition({ top: rect.top - 10 });
}, []);
```

| 구분 | useEffect | useLayoutEffect |
|------|-----------|-----------------|
| 실행 시점 | 페인트 **후** (비동기) | 페인트 **전** (동기) |
| 메인 스레드 블로킹 | 안 함 | 함 (느리면 체감됨) |
| SSR | 안전 | 경고 발생 (window 없음) |
| 용도 | 데이터 fetch, 구독 | DOM 측정, 위치 보정 |

> 💡 **왜 중요한가**: "DOM을 읽고 바로 다시 쓰는" 작업은 `useLayoutEffect`가 아니면 반드시 1프레임 깜빡인다 — 사용자 경험의 품질이 여기서 갈린다.

### 2. key에 index 쓰지 마라: "입력창이 뒤섞이는" 리스트 렌더링 버그의 정체

React는 `key`로 리스트 항목의 **정체성(identity)** 을 추적한다. `key={index}`를 쓰면 배열 순서가 바뀌거나 중간에 항목이 삽입/삭제될 때, React는 "같은 자리 = 같은 컴포넌트"로 착각해 **DOM은 재사용하고 내부 state만 엉뚱한 항목에 붙어버린다**. 특히 `<input>`, 체크박스, 포커스 상태가 있는 리스트에서 치명적이다.

```jsx
// ❌ 앞에 항목을 추가하면 모든 input 값이 한 칸씩 밀림
{todos.map((todo, i) => (
  <TodoItem key={i} todo={todo} />
))}

// ✅ 항목 고유 id로 정체성 추적
{todos.map((todo) => (
  <TodoItem key={todo.id} todo={todo} />
))}
```

**언제 index를 써도 괜찮은가?** 아래 3가지를 **모두** 만족할 때만:
1. 리스트가 정적이다 (재정렬/삽입/삭제 없음)
2. 항목에 state나 ref가 없다
3. 항목에 고유 id를 만들 방법이 없다

| 상황 | 증상 |
|------|------|
| 리스트 앞에 항목 추가 | 입력값이 한 칸씩 밀려서 표시됨 |
| 리스트 정렬 변경 | 체크박스 상태가 엉뚱한 항목에 붙음 |
| 중간 항목 삭제 | 포커스/애니메이션 상태 뒤섞임 |
| 서버에서 재조회 | 불필요한 전체 리마운트로 성능 저하 |

> 💡 **왜 중요한가**: `key`는 "스타일링용 식별자"가 아니라 "React의 재조정(reconciliation) 알고리즘에 주는 지문(fingerprint)"이다 — 지문이 틀리면 React는 조용히 잘못된 컴포넌트를 재사용한다.
