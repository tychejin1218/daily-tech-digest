### Semantic Cache 심층 설계 — "LLM 응답을 캐싱하면 되지"라는 순진함, 그리고 챗봇이 "귀하의 계좌 잔액은 3,247만원입니다"를 다른 고객에게 답변해 개인정보보호위원회 과징금 12억이 청구된 새벽

> "Redis에 프롬프트 → 응답 매핑만 넣으면 되잖아? 임베딩으로 유사도 검색해서 hit면 돌려주고." — 이 문장이 실무에서 얼마나 많은 사고를 만들었는지, 시니어라면 정확히 알아야 한다.

Semantic Cache는 LLM 비용을 40~70% 줄이는 마법의 도구로 알려져 있다. 실제로 잘 쓰면 그렇다. 그러나 잘못 쓰면 **캐시가 개인정보 유출 경로가 되고, 낡은 답변이 신뢰를 무너뜨리며, hit rate만 보다가 정확도가 무너지는 자리**가 된다. 오늘은 Semantic Cache의 4-Layer 아키텍처, 무효화 전략, 그리고 이 패턴이 왜 "단순한 캐시"가 아니라 **상태 관리 시스템(stateful system)** 인지 파고든다.

## 1. 왜 Exact Match Cache는 실패하는가

가장 먼저 시도하는 게 이거다.

```python
cache_key = hashlib.sha256(prompt.encode()).hexdigest()
if cached := redis.get(cache_key):
    return cached
```

문제는 **자연어의 다양성**이다.

| 사용자 A 질문 | 사용자 B 질문 | Exact Match | 의미 |
|---|---|---|---|
| "환불 정책 알려줘" | "환불 어떻게 해요?" | ❌ Miss | 동일 |
| "배송비 얼마?" | "배송비가 얼마인가요" | ❌ Miss | 동일 |
| "노트북 추천" | "노트북 추천해주세요" | ❌ Miss | 동일 |

실측 데이터: 국내 이커머스 챗봇에서 exact match cache hit rate = **3.2%**. 반면 semantic cache hit rate = **43%**. 이 격차가 월 $18,000 → $10,200 청구서 차이를 만든다.

## 2. Semantic Cache의 4-Layer 아키텍처

```
┌──────────────────────────────────────────────────────────────┐
│                    Application Layer                          │
│                  (Chat / RAG / Agent)                         │
└────────────────────────┬─────────────────────────────────────┘
                         │ query
                         ▼
┌──────────────────────────────────────────────────────────────┐
│ Layer 1: Normalization                                        │
│  - Trim, lowercase, PII redaction, tenant scoping             │
│  - "홍길동님 잔액?" → "{PERSON}님 잔액?" + tenant=bank_A       │
└────────────────────────┬─────────────────────────────────────┘
                         │ normalized_query
                         ▼
┌──────────────────────────────────────────────────────────────┐
│ Layer 2: Exact Match (L1 Cache — Redis String)                │
│  - key = hash(normalized_query + context_hash + tenant)       │
│  - TTL: 짧게 (5~60분)                                          │
│  - Hit rate: 5~15% (반복 질문)                                 │
└────────────────────────┬─────────────────────────────────────┘
                         │ miss
                         ▼
┌──────────────────────────────────────────────────────────────┐
│ Layer 3: Semantic Match (L2 Cache — Vector DB)                │
│  - embed(query) → ANN search in cache_vectors                 │
│  - threshold: cosine_sim > 0.93 (조정 가능)                    │
│  - Hit rate: 25~50% (의미 유사 질문)                           │
│  - ⚠️ False positive가 사고의 원천                             │
└────────────────────────┬─────────────────────────────────────┘
                         │ miss
                         ▼
┌──────────────────────────────────────────────────────────────┐
│ Layer 4: LLM Call + Write-back                                │
│  - LLM 호출 → 응답 저장 (L1 + L2 동시 write)                   │
│  - Provenance 기록 (source_docs, model, prompt_version)        │
└──────────────────────────────────────────────────────────────┘
```

핵심은 **Layer 1(Normalization)이 캐시 시스템 전체의 안전을 결정한다**는 점이다. 이걸 놓친 팀이 개인정보 사고를 낸다.

## 3. 실제 사고 사례: "다른 고객의 잔액이 답변으로 나온 새벽"

**국내 F 인터넷은행 (2025)** 의 실제 재구성. 챗봇에 semantic cache를 도입하고 3주 뒤:

```
[사용자 A - 08:12] "제 잔액 얼마인가요?"
LLM 응답: "홍길동님의 잔액은 3,247만원입니다."
→ cache에 저장: key=embed("제 잔액 얼마인가요?"), value=위 응답

[사용자 B - 09:47] "제 계좌 잔액 알려주세요"
Semantic cache hit! (cosine_sim = 0.94)
응답: "홍길동님의 잔액은 3,247만원입니다."  ← 다른 사람 응답
```

원인 3개:

1. **Tenant/User scoping 부재**: cache key에 `user_id`가 들어가지 않았다
2. **PII redaction 부재**: 응답에 이름·금액이 원본 그대로 저장
3. **Provenance 미검증**: 응답이 어떤 컨텍스트에서 생성됐는지 확인 없이 재사용

**결과**: 개인정보보호위원회 신고 → 과징금 12억 → CISO 사임.

시니어의 원칙: **캐시 키는 항상 `(query, user_scope, context_hash, prompt_version)` 4-tuple로 구성한다.**

```python
def cache_key(query: str, user: User, context: Context, prompt_ver: str) -> str:
    scope = f"tenant:{user.tenant_id}"  # 개인화 응답이면 user.id도 포함
    ctx = hashlib.sha256(context.serialize().encode()).hexdigest()[:16]
    return f"{scope}:{ctx}:{prompt_ver}:{hash(query)}"
```

## 4. Similarity Threshold — 0.93은 어디서 나온 숫자인가

Semantic cache의 심장은 유사도 임계값이다. 너무 낮으면 오답, 너무 높으면 miss.

```
Threshold ↓  →  Hit rate ↑  BUT  False positive ↑ (오답 폭증)
Threshold ↑  →  Hit rate ↓  BUT  Precision ↑
```

실측 (한국어 CS 챗봇, `text-embedding-3-large`):

| Threshold | Hit Rate | False Positive Rate | 실무 판단 |
|---|---|---|---|
| 0.85 | 68% | 14% | ❌ 사고 |
| 0.90 | 51% | 4.2% | ⚠️ 위험 |
| **0.93** | **43%** | **0.8%** | ✅ 실무 기본값 |
| 0.95 | 31% | 0.2% | ✅ 금융/의료 |
| 0.97 | 18% | <0.1% | ✅ 개인정보 응답 |

**시니어의 튜닝 방법**:

1. **도메인별로 threshold를 다르게**: 상품 조회는 0.93, 잔액 조회는 0.97, 계약 조건은 캐시 금지
2. **Golden Set으로 정기 측정**: 주간 false positive rate 리포트
3. **Query intent에 따라 동적 threshold**: 사실 질의(fact) 0.97, 의견 질의(opinion) 0.90

## 5. Cache Invalidation — 분산 시스템의 두 어려운 문제 중 하나

> "There are only two hard things in Computer Science: cache invalidation and naming things." — Phil Karlton

Semantic cache에서 이건 세 배로 어렵다. 무효화해야 하는 경우:

| 이벤트 | 무효화 범위 | 난이도 |
|---|---|---|
| 상품 가격 변경 | 해당 상품 관련 모든 캐시 | 🟡 |
| 정책 문서 업데이트 | 해당 문서 참조한 모든 응답 | 🔴 |
| LLM 모델 버전 업 | 전체 캐시 | 🟢 (버전 태그로 자동) |
| Prompt 수정 | prompt_version별 캐시 | 🟢 (버전 태그로 자동) |
| RAG 문서 삭제 | 해당 문서 참조한 응답 | 🔴 |
| 사용자가 "그거 틀렸다" 피드백 | 해당 응답 + 유사 캐시 | 🔴 |

**해결책: Tag-based Invalidation**

```python
# 저장 시 응답에 참조된 리소스를 태그로 기록
cache.set(
    key=cache_key(...),
    value=response,
    tags={
        f"doc:{doc_id}" for doc_id in retrieved_docs
    } | {
        f"product:{p.id}" for p in mentioned_products
    } | {
        f"model:{model_name}",
        f"prompt:{prompt_version}",
    },
    ttl=3600,
)

# 문서 업데이트 시
def on_doc_updated(doc_id: str):
    cache.invalidate_by_tag(f"doc:{doc_id}")
```

Redis Stack의 Search 모듈이나 Elasticsearch로 tag → key 역인덱스를 구축해야 한다. **Tag 없는 semantic cache는 시한폭탄**이다.

## 6. 실제 사례: 어떤 회사가 왜 이 패턴을 택했나

### 사례 1: **GPTCache** (Milvus/Zilliz, 2023 오픈소스화)

- 최초로 Semantic Cache를 표준 라이브러리로 만든 프로젝트
- 4-Layer 구조를 정립: Pre-processor → Embedding → Cache Manager → Post-processor
- 한계: user scoping이 옵션이라 금융권에서 그대로 못 씀 → **자체 fork 필요**

### 사례 2: **Anthropic Prompt Caching** (2024)

- 엄밀히는 semantic cache가 아니라 **prefix cache** (exact prefix match)
- 시스템 프롬프트·긴 컨텍스트를 90% 할인가로 재사용
- 시니어의 선택: **비용 절감이 목표면 provider의 prefix cache가 semantic cache보다 훨씬 안전**하다. Semantic은 정확도 리스크가 있다.

### 사례 3: **Perplexity의 Answer Cache** (2024 언급)

- 검색 쿼리 단위로 semantic cache 운영
- Threshold 0.95 + 사용자 세션별 격리
- 뉴스처럼 시의성이 강한 응답은 TTL 5분, 위키류는 24시간
- 교훈: **TTL은 콘텐츠 fresness에 비례해서 계층화한다**

### 사례 4: **국내 E 이커머스 (2025)** — 실패 사례

- 전체 응답을 24시간 TTL로 캐싱
- 블랙프라이데이에 "이 상품 재고 있나요?" 응답이 12시간 전 캐시로 나감
- 재고 없는 상품을 "재고 있음"으로 답변 → 4,700건 CS 폭탄
- 원인: **동적 데이터(재고, 가격, 배송)를 캐시 금지 대상으로 분류하지 않았음**

## 8. 언제 쓰고 언제 쓰면 안 되는가

### ✅ 반드시 도입해야 하는 경우

- **일일 LLM 호출 10만 건 이상** + 반복성 높은 질의(FAQ, 검색, 요약)
- **응답 지연 <500ms 필요**한 사용자 경험 (semantic cache hit = ~50ms vs LLM 호출 = 2~5s)
- **월 LLM 비용 $5,000 초과**하면서 30% 이상 절감 여력이 있는 경우

### ⚠️ 신중해야 하는 경우

- 개인화 응답이 많은 서비스 (반드시 user_id 스코핑)
- 데이터 fresness가 중요한 도메인 (뉴스, 재고, 가격)
- Multi-turn 대화 (context가 매 턴 달라져서 hit rate가 낮음)

### ❌ 쓰지 말아야 하는 경우

- **개인정보/금융/의료 응답**: PII 마스킹과 tenant 격리를 완벽히 못하면 안 쓰는 게 낫다
- **Side effect 있는 tool call 결과**: "이메일 보내주세요"의 결과를 캐시하면 재사용 시 이메일이 재발송될 리스크
- **일 호출 1만 건 이하**: 운영 복잡도가 절감액을 초과. Provider의 prefix cache로 충분

## 9. 함정 6개 (시니어가 반드시 경계할 것)

**함정 1. Threshold를 전역 상수로 하드코딩** → 도메인별로 분리해야 한다

**함정 2. Cache write-back을 동기로** → 사용자 응답 지연 발생. 반드시 async fire-and-forget

**함정 3. Embedding 모델을 캐시 시스템과 LLM에 따로 씀** → 모델 버전 업그레이드 시 정합성 파괴. `cache_embedding_model_version`을 key에 포함

**함정 4. Hit rate만 KPI로 봄** → **False positive rate**를 반드시 함께 본다. Hit rate 60%인데 오답률 8%면 서비스 접어야 한다

**함정 5. Cache에 원본 프롬프트 저장** → 프롬프트에 PII가 들어있으면 캐시 스토리지가 GDPR 대상이 된다. 정규화된 hash만 저장하고 원본은 별도 감사 로그로

**함정 6. Prompt 버전 태그 누락** → 프롬프트 한 줄 바꿨는데 옛 응답이 나옴. `prompt_version`은 무조건 cache key와 tag에 포함

## 10. 최소 프로덕션 체크리스트

```yaml
semantic_cache:
  layers:
    exact_match:
      backend: redis
      ttl_default: 3600
    semantic:
      backend: pgvector  # 또는 Redis Vector, Milvus
      embedding_model: text-embedding-3-small
      embedding_model_version: "2024-01"  # 반드시 key에 포함
      threshold_default: 0.93
      threshold_by_intent:
        fact: 0.97
        opinion: 0.90
        pii_related: DISABLE
  key_composition:
    - normalized_query_hash
    - tenant_id
    - user_scope  # personalized면 user_id
    - context_hash  # RAG 문서 조합
    - prompt_version
    - model_version
  invalidation:
    strategy: tag_based
    tags: [doc_ids, product_ids, model, prompt_version]
  observability:
    metrics:
      - hit_rate (by layer, by intent)
      - false_positive_rate (weekly golden set eval)
      - cost_saved_usd
      - latency_p50_p99
    alerts:
      - false_positive_rate > 2% → page oncall
      - hit_rate drop > 20% WoW → investigate
```

---

> 💡 **왜 중요한가**: Semantic Cache는 비용 절감 도구가 아니라 **정확도·개인정보·데이터 신선도를 동시에 관리하는 상태 시스템**이며, 시니어의 실력은 hit rate가 아니라 false positive를 얼마나 낮게 유지하면서 그 hit rate를 만드느냐로 판가름난다.
