### MySQL `LOCK IN SHARE MODE` vs `FOR UPDATE` — 읽기 잠금의 미묘한 차이가 데드락을 부르는 순간

같은 SELECT 잠금이지만 `LOCK IN SHARE MODE`는 S락(공유), `FOR UPDATE`는 X락(배타)을 건다. 두 트랜잭션이 동시에 `LOCK IN SHARE MODE`로 같은 행을 읽은 뒤 각자 UPDATE를 시도하면 서로의 S락을 X락으로 승격해야 해서 **데드락**이 터진다. "읽기니까 가볍겠지"라는 착각이 프로덕션에서 가장 자주 만나는 데드락 패턴이다.

```
[TX-A] SELECT ... LOCK IN SHARE MODE  → S락 획득
[TX-B] SELECT ... LOCK IN SHARE MODE  → S락 획득 (공유 가능)
[TX-A] UPDATE ...                     → X락 승격 시도 (TX-B의 S락 대기)
[TX-B] UPDATE ...                     → X락 승격 시도 (TX-A의 S락 대기)
                                      → 💥 Deadlock detected
```

**실전 처방**: "읽고 나서 그 행을 조건부 업데이트" 패턴이면 처음부터 `FOR UPDATE`로 X락을 잡거나, MySQL 8.0+의 `FOR UPDATE SKIP LOCKED` / `FOR UPDATE NOWAIT`로 대기 자체를 제거해라. `LOCK IN SHARE MODE`는 "정말 읽기만 하고 끝낼 참조 무결성 체크"에만 써야 안전하다.

> 💡 **왜 중요한가**: S락 → X락 승격 데드락은 코드 리뷰로는 절대 안 보이고 트래픽이 몰릴 때만 터져서, 락 종류의 선택이 곧 장애 확률이다.

### PostgreSQL `Multixact ID Wraparound` — `SELECT FOR SHARE` 남발이 만드는 조용한 시한폭탄

PostgreSQL은 여러 트랜잭션이 같은 행에 공유 락을 걸면 **MultiXact ID**라는 별도 카운터로 관리한다. 이 카운터는 32bit라 약 20억 개 소진 시 `wraparound` 위험에 빠지고, 그전에 autovacuum이 `pg_multixact/` 디렉터리를 정리하지 못하면 디스크가 폭발하거나 DB가 **강제로 read-only** 모드로 들어간다. FK 제약이 걸린 테이블에서 대량 INSERT/UPDATE만 해도 내부적으로 부모 행에 공유 락이 걸려 MultiXact가 폭증한다.

```sql
-- 위험 신호 감지: MultiXact 소진율 모니터링
SELECT datname,
       age(datminmxid) AS mxid_age,
       2^31 - age(datminmxid) AS remaining_before_wraparound
FROM pg_database
ORDER BY mxid_age DESC;

-- autovacuum_multixact_freeze_max_age (기본 4억) 대비
-- age가 70% 넘어가면 이미 경고 단계
```

**실전 처방**: FK가 많은 스키마에서 `autovacuum_multixact_freeze_max_age`를 낮춰(예: 2억) 조기 정리를 유도하고, `pg_stat_activity`에서 오래 살아있는 트랜잭션(long-running query)을 즉시 킬해라. Idle-in-transaction이 몇 시간 방치되면 vacuum이 MultiXact를 못 지워 wraparound으로 직행한다.

> 💡 **왜 중요한가**: MultiXact wraparound는 "천천히 다가오는 총알"이라 CPU/메모리 지표에는 안 잡히고, 터지는 순간 서비스 전체가 read-only로 전환되는 최악의 장애 유형이다.
