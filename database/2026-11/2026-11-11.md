### Database Tip 1: PostgreSQL `BRIN`(Block Range Index) — B-Tree보다 1000배 작은 크기로 "시계열 수십억 행"을 훑는 블록 단위 인덱스

`BRIN`은 테이블을 128페이지(1MB) 단위 "블록 레인지"로 나누고, 각 범위의 min/max 값만 저장하는 극도로 가벼운 인덱스다. 10억 행 timestamp 컬럼에 B-Tree를 걸면 20GB가 필요하지만 BRIN은 겨우 20MB로 끝난다. 단, 물리적 저장 순서와 값의 순서가 "상관관계"를 가져야(append-only 로그, 시계열) 효과를 보며, UPDATE가 난무하는 OLTP 테이블에선 블록 레인지가 쪼개져 성능이 무너진다.

```sql
-- 10억 행 로그 테이블: B-Tree 20GB vs BRIN 20MB
CREATE INDEX idx_logs_brin ON logs USING BRIN (created_at)
  WITH (pages_per_range = 128);

-- 시계열 범위 쿼리에 B-Tree 급 성능, 저장비용은 0.1%
SELECT * FROM logs WHERE created_at BETWEEN '2026-11-01' AND '2026-11-11';
```

```
B-Tree:  [페이지별 포인터] → 20GB (전체 행 수에 비례)
BRIN:    [1MB 레인지의 min/max만]
         Range 0: min=2026-01-01, max=2026-01-05
         Range 1: min=2026-01-05, max=2026-01-10
         → 범위 쿼리 시 "이 레인지는 스킵" 판단만 하면 끝
```

> 💡 **왜 중요한가**: 시계열/로그 테이블에서 "인덱스가 테이블보다 커지는 역설"을 피하면서도 범위 쿼리는 수백 배 빨라지는, OLTP와 OLAP의 경계에 있는 Postgres 고유 무기다.

### Database Tip 2: JPA `@Transactional(readOnly = true)` — 단순한 "읽기 전용 힌트"가 Hibernate 내부에서 `Dirty Checking`을 통째로 끄는 숨은 최적화

`readOnly = true`를 붙이면 Spring이 `FlushMode`를 `MANUAL`로 바꿔 커밋 시점의 자동 flush를 생략하고, Hibernate는 영속 객체의 "스냅샷"조차 뜨지 않아 메모리와 CPU를 절약한다. 또한 `TransactionSynchronizationManager`가 이를 감지해 MySQL/PostgreSQL JDBC 드라이버에 `Connection.setReadOnly(true)`를 전달, 리플리카 라우팅(`LazyConnectionDataSourceProxy` + `AbstractRoutingDataSource`)의 결정 키로 쓰인다. 조회 전용 서비스에 안 붙이는 건 "성능 반값 세일을 거부하는 것"과 같다.

```java
@Transactional(readOnly = true)  // Dirty Check 생략 + Replica 라우팅
public List<OrderDto> findRecentOrders(Long userId) {
    return orderRepository.findByUserId(userId);  // 스냅샷 X, flush X
}

// AbstractRoutingDataSource가 readOnly 플래그로 분기
protected Object determineCurrentLookupKey() {
    return TransactionSynchronizationManager.isCurrentTransactionReadOnly()
        ? "replica" : "primary";
}
```

```
일반 @Transactional:  Entity 로드 → 스냅샷 복사 → commit 시 비교 → flush
readOnly=true:        Entity 로드 → (스냅샷 생략) → commit 시 아무것도 안 함
                      ↓
                      메모리 절반, CPU 30%↓, Replica DB로 트래픽 분산
```

> 💡 **왜 중요한가**: 전체 트래픽의 80~90%를 차지하는 조회 쿼리에 한 줄만 추가하면 Dirty Checking 오버헤드 제거 + 읽기 전용 리플리카 분산이 공짜로 따라오는, 가성비 최상의 JPA 튜닝 스위치다.
