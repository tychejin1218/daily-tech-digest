### PostgreSQL `LATERAL JOIN` — 각 행마다 상관 서브쿼리를 조인처럼 다루기
`LATERAL`을 붙이면 오른쪽 서브쿼리가 왼쪽 테이블의 컬럼을 참조할 수 있어, "각 사용자별 최근 주문 3건"처럼 그룹별 Top-N 문제를 서브쿼리 중첩 없이 깔끔하게 풀 수 있다. `ORDER BY ... LIMIT` 조합을 그대로 활용할 수 있고, 옵티마이저가 인덱스를 이용한 Nested Loop로 잘 풀어주기 때문에 윈도우 함수 `ROW_NUMBER()` 기반 방식보다 빠른 경우가 많다.

```sql
SELECT u.id, o.id AS order_id, o.created_at
FROM users u
LEFT JOIN LATERAL (
  SELECT id, created_at
  FROM orders
  WHERE user_id = u.id
  ORDER BY created_at DESC
  LIMIT 3
) o ON true;
```

> 💡 **왜 중요한가**: 그룹별 Top-N을 윈도우 함수 없이 인덱스 친화적으로 풀 수 있는 거의 유일한 표준 SQL 패턴이다.

### JPA `@EntityGraph` — 쿼리 단위로 페치 전략을 선언적으로 갈아 끼우기
연관관계는 기본적으로 `LAZY`로 두되, 특정 API에서만 필요한 연관을 `@EntityGraph(attributePaths = {...})`로 지정하면 그 조회에 한해 `LEFT JOIN FETCH`가 자동 삽입되어 N+1을 없앨 수 있다. `JOIN FETCH`를 JPQL에 직접 박는 방식보다 재사용성과 조합성이 좋고, 리포지토리 메서드마다 다른 페치 그래프를 붙일 수 있어 화면별 최적화에 특히 유용하다.

```java
@EntityGraph(attributePaths = {"orders", "orders.items"})
@Query("select u from User u where u.id = :id")
Optional<User> findWithOrdersById(@Param("id") Long id);
```

> 💡 **왜 중요한가**: "연관은 LAZY, 필요할 때만 FETCH"라는 원칙을 엔티티 매핑을 건드리지 않고 쿼리 단위로 강제할 수 있다.
