### MySQL `OPTIMIZER_TRACE` — 옵티마이저가 "왜 그 실행 계획을 골랐는지" 영혼까지 들여다보는 X-RAY

`EXPLAIN`이 "뭘 할 건지"를 보여준다면, `OPTIMIZER_TRACE`는 "왜 그걸 고르고 다른 건 버렸는지"의 비용 계산까지 JSON으로 토해낸다. `SET optimizer_trace="enabled=on"` 후 쿼리를 실행하고 `SELECT * FROM information_schema.OPTIMIZER_TRACE`를 보면, 각 인덱스별 추정 비용(`cost`), 선택된 접근 방식(`access_type`), 거부된 플랜의 사유까지 모두 드러난다. "왜 분명히 더 좋은 인덱스가 있는데 풀스캔을 타지?"라는 미스터리를 풀 때 유일한 해답지다.

```sql
SET optimizer_trace="enabled=on";
SELECT * FROM orders WHERE user_id = 42 AND status = 'PAID';
SELECT TRACE FROM information_schema.OPTIMIZER_TRACE\G
-- "rows_estimation": [{ "table": "orders",
--   "range_analysis": { "analyzing_range_alternatives": [
--     { "index": "idx_user", "cost": 15.2, "chosen": true },
--     { "index": "idx_status", "cost": 8923.1, "rows": 450000, "cause": "cost" }
--   ]}}]
SET optimizer_trace="enabled=off";
```

함정은 trace 자체가 메모리를 먹는다는 것 — 기본 `optimizer_trace_max_mem_size=1MB`를 넘기면 뒷부분이 잘려서 `"MISSING_BYTES_BEYOND_MAX_MEM_SIZE"`가 찍힌다. 복잡한 조인은 16MB까지 올려야 전체가 보인다. 운영에서는 특정 세션에서만 켜고, 반드시 끄자. 통계가 틀어져서 옵티마이저가 "비싼 인덱스"를 고르는 순간, `ANALYZE TABLE`로 재수집할지 힌트로 강제할지의 판단 근거가 바로 이 트레이스에 있다.

> 💡 **왜 중요한가**: `EXPLAIN`이 "결과"라면 `OPTIMIZER_TRACE`는 "근거"다. 비용 기반 옵티마이저와 싸울 땐 추측이 아니라 숫자로 반박해야 한다.

### JPA `@SQLDelete`와 `@Where` — 실제 DELETE 없이 "삭제된 척"하는 Soft Delete의 선언적 구현

`@SQLDelete(sql = "UPDATE users SET deleted_at = NOW() WHERE id = ?")`를 엔티티에 붙이면, `entityManager.remove()`나 `repository.delete()`가 실제로는 UPDATE 쿼리로 바뀐다. 여기에 `@Where(clause = "deleted_at IS NULL")`을 더하면 모든 SELECT에 자동으로 조건이 붙어, 삭제된 행이 조회에서 투명하게 사라진다. 애플리케이션 코드는 "삭제한다"고 쓰지만, DB는 "숨긴다" — 서비스 레이어 전체를 soft delete로 뜯어고치지 않고도 선언 하나로 전환하는 방법이다.

```java
@Entity
@SQLDelete(sql = "UPDATE users SET deleted_at = CURRENT_TIMESTAMP WHERE id = ?")
@Where(clause = "deleted_at IS NULL")
public class User {
    @Id private Long id;
    private LocalDateTime deletedAt;
}

// userRepository.delete(user); 
// → 실제 쿼리: UPDATE users SET deleted_at = NOW() WHERE id = 42
// userRepository.findAll(); 
// → 실제 쿼리: SELECT ... FROM users WHERE deleted_at IS NULL
```

지뢰는 세 군데 — ① `@Where`는 연관관계 조회(Lazy Loading)에도 적용되지만, Native Query에는 안 붙으므로 리포트성 쿼리에서 "유령 행"이 튀어나올 수 있다. ② Unique 제약과 충돌한다. `email` UK를 걸어뒀다면 같은 이메일로 재가입이 불가능해지므로, `UNIQUE (email, deleted_at)` 같은 복합 제약으로 바꾸거나 PostgreSQL의 Partial Index를 써야 한다. ③ Hibernate 6부터 `@Where`는 `@SQLRestriction`으로 이름이 바뀌었다 — 신규 프로젝트는 새 이름을 쓰자. 그리고 "정말로 지워야 하는 데이터"(GDPR 삭제 요청 등)는 soft delete로 처리하면 안 된다 — 하드 삭제 경로를 별도로 둬야 한다.

> 💡 **왜 중요한가**: Soft delete는 "컬럼 하나 추가"가 아니라 조회/제약/감사 로그 전체에 스며드는 설계 결정이다. 선언으로 전환할 수 있다는 건, 반대로 선언 하나로 조용히 깨질 수도 있다는 뜻이다.
