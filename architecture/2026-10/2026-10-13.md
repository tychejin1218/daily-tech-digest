### Prompt Versioning & Registry — "프롬프트는 그냥 문자열 아니냐"는 순진함, 그리고 PM이 Slack에서 "여기 한 줄만 더 공손하게 바꿔주세요" 메시지 하나로 롤백 포인트가 증발한 채 1,200만 호출의 톤이 야금야금 바뀌어 3주 뒤 CS 민원 폭주가 터진 월요일 새벽

---

#### 1. 문제 상황: "프롬프트는 코드다"로 시작해서 "프롬프트는 데이터다"로 끝나는 혼란

Lv5 Day 108까지 당신은 LLM Eval 자동화, Multi-Agent Orchestration, Hybrid Search를 다뤘다. 이제 이런 질문이 남는다.

**"Eval에서 95점 받은 그 프롬프트, 지금 production에 올라가 있는 거랑 같은 거 맞아?"**

이 질문에 "git log 보면 돼요"라고 답하는 팀은 1주일 안에 사고를 낸다. 왜냐하면 프롬프트는 코드와 세 가지가 결정적으로 다르기 때문이다.

| 축 | 코드 | 프롬프트 |
|---|---|---|
| 변경 주체 | 개발자 | **PM, 운영자, 프롬프트 엔지니어, 때로는 법무팀** |
| 변경 빈도 | 주 단위 | **일 단위, 때로는 시간 단위** |
| 평가 방식 | 결정론적 (unit test) | 확률적 (Eval set + LLM-as-Judge) |
| 롤백 비용 | 재배포 1분 | 재배포 1분 + **"어제 응답 품질로 돌아왔다"를 어떻게 증명?** |
| 실패 양상 | 500 에러 | **"응답이 묘하게 공격적이다"** — 조용히 썩음 |

프롬프트를 코드 안의 `const SYSTEM_PROMPT = "..."` 로 박아두는 순간, PM은 Slack으로 "여기 한 줄만 바꿔주세요"를 보내고, 개발자는 PR 하나 더 만드는 게 귀찮아서 그냥 운영 DB의 설정 테이블에 넣기 시작하고, 그 설정 테이블은 git에 없고, 3주 뒤 "최근에 뭐 바꿨어요?"에 아무도 답을 못 한다.

---

#### 2. Prompt Registry가 해결하는 것

Prompt Registry는 **"프롬프트를 1급 artifact로 승격시키는 저장소"** 다. Docker Registry가 이미지에 하는 일을, Prompt Registry가 프롬프트에 한다.

```
┌──────────────────────────────────────────────────────────────────────┐
│                      Prompt Registry 아키텍처                        │
└──────────────────────────────────────────────────────────────────────┘

   [PM/프롬프트 엔지니어]              [개발자]              [Eval 파이프라인]
         │                             │                           │
         │ ① 수정 (Web UI)              │ ② SDK로 조회              │ ③ 자동 Eval
         ▼                             ▼                           ▼
   ┌─────────────────────────────────────────────────────────────────┐
   │                    Prompt Registry                              │
   │                                                                 │
   │  ┌─────────────────────────────────────────────────────────┐   │
   │  │  prompt: refund_policy_bot                              │   │
   │  │  ├─ v2.3.1  (production)  ← tag: @prod                  │   │
   │  │  ├─ v2.3.0  (staging)     ← tag: @staging               │   │
   │  │  ├─ v2.4.0-rc1            ← tag: @canary (5% traffic)   │   │
   │  │  └─ v1.9.4  (deprecated)                                 │   │
   │  │                                                         │   │
   │  │  각 버전은 immutable:                                   │   │
   │  │   - template (문자열)                                   │   │
   │  │   - variables schema (JSON Schema)                      │   │
   │  │   - model binding (claude-opus-4-7)                     │   │
   │  │   - sampling params (temp, top_p, max_tokens)           │   │
   │  │   - tool definitions (JSON Schema)                      │   │
   │  │   - eval_result_id (어느 Eval 통과했는지 포인터)        │   │
   │  │   - author, created_at, commit_message                  │   │
   │  └─────────────────────────────────────────────────────────┘   │
   └─────────────────────────────────────────────────────────────────┘
         ▲                             │                           ▲
         │ ⑤ 감사 로그                 │ ④ 응답 생성                │
         │                             ▼                           │
         │                      [Production LLM 호출]              │
         │                             │                           │
         └─────────────────────────────┴─ Observability (어느 버전이 응답했는지 trace에 박힘)
```

핵심은 네 가지다.

1. **Immutable 버전**: 한 번 publish된 `v2.3.1`은 절대 수정 불가. 수정하려면 `v2.3.2`를 만들어야 한다.
2. **Tag로 라우팅**: 코드는 `prompt.get("refund_policy_bot", tag="prod")`로 조회 → 운영자는 코드 배포 없이 tag만 옮긴다.
3. **Model + Params + Tools가 한 세트**: `v2.3.1`은 "이 프롬프트 + claude-opus-4-7 + temp=0.3 + 이 tool schema"의 묶음이다. 모델만 바꿔도 새 버전.
4. **Eval 통과 증명서 첨부**: `v2.3.1`은 어떤 Eval set에서 몇 점을 받았는지가 메타데이터에 박혀 있어야 한다. "Eval 통과 안 한 버전은 `@prod` tag를 못 받는다"가 CI 게이트.

#### 3. Semantic Versioning for Prompts

프롬프트에도 SemVer를 적용해야 하는데, 코드와는 **의미가 다르다**.

| 변경 레벨 | 코드 SemVer | 프롬프트 SemVer |
|---|---|---|
| **Major (X.y.z)** | Breaking API 변경 | **출력 구조/스키마 변경, 모델 교체, Tool 추가·제거** |
| **Minor (x.Y.z)** | 기능 추가 | **새 지시문·새 예시 추가**, 응답 길이/톤 눈에 띄게 변화 |
| **Patch (x.y.Z)** | 버그 수정 | **오탈자, 어색한 조사 교정, 동의어 치환** — 의미 불변 |

**왜 중요한가**: downstream 소비자(파싱 코드, 평가자, 다른 Agent)는 Major 버전이 바뀌면 반드시 재검증해야 한다. "오탈자 하나 고쳤는데 왜 다시 Eval 돌려요?"의 답이 Patch다. Patch는 자동 승격, Minor는 Eval 통과 시 승격, Major는 **승격 외에 downstream contract 재확인**이 필수.

#### 4. 네 가지 구현 패턴

##### 패턴 A. Git-based (코드 리포에 YAML/MD로 저장)

```
prompts/
├── refund_policy_bot/
│   ├── v2.3.1.yaml   ← template, model, params 포함
│   └── CHANGELOG.md
```

**언제 쓰나**: 프롬프트 수정 주체가 100% 개발자고, 변경 빈도가 주 1회 이하.
**깨지는 지점**: PM이 "제가 직접 수정하고 싶어요"를 꺼낸 그 순간. PM에게 Git을 가르치는 비용 vs 중앙 Registry를 구축하는 비용을 비교해보라.

##### 패턴 B. Managed Registry (LangSmith Hub, PromptLayer, Humanloop)

**언제 쓰나**: 초기 ~ 중기, 팀 규모 50명 이하, 보안 검토를 통과한 SaaS 벤더 사용 가능.
**깨지는 지점**: ① 프롬프트에 **고객 개인정보가 섞인 few-shot example**이 들어가는 금융·헬스케어. ② 월 호출 수가 수억을 넘어가면 SaaS 비용이 자체 구축을 역전. ③ 벤더가 서비스를 종료하면 (Humanloop는 2024년 Anthropic에 인수된 후 구조 개편) migration이 2개월 프로젝트가 된다.

##### 패턴 C. Database-backed Self-hosted (자체 구축)

PostgreSQL + S3 조합이 가장 흔하다. 메타데이터는 Postgres, 긴 템플릿 본문은 S3.

```sql
CREATE TABLE prompt_versions (
    id UUID PRIMARY KEY,
    prompt_name TEXT NOT NULL,
    version TEXT NOT NULL,              -- '2.3.1'
    template_s3_key TEXT NOT NULL,       -- immutable
    model_id TEXT NOT NULL,              -- 'claude-opus-4-7'
    sampling_params JSONB NOT NULL,
    variable_schema JSONB NOT NULL,      -- JSON Schema
    tool_definitions JSONB,
    eval_run_id UUID REFERENCES eval_runs(id),  -- NULL이면 production 승격 불가
    created_by TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    commit_message TEXT NOT NULL,
    UNIQUE(prompt_name, version)
);

CREATE TABLE prompt_tags (
    prompt_name TEXT NOT NULL,
    tag TEXT NOT NULL,                   -- 'prod', 'staging', 'canary'
    version_id UUID REFERENCES prompt_versions(id),
    updated_by TEXT NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (prompt_name, tag)
);

CREATE TABLE prompt_tag_history (  -- 감사 로그
    prompt_name TEXT, tag TEXT, from_version_id UUID, to_version_id UUID,
    actor TEXT, changed_at TIMESTAMPTZ, reason TEXT
);
```

**언제 쓰나**: 금융·공공·헬스케어, 월 1억 호출 이상, 또는 **"프롬프트가 영업 비밀"** 인 경우.
**깨지는 지점**: Web UI를 자체 개발해야 하는데, PM이 쓸만한 UI를 만드는 비용이 최소 2주. 이걸 빼먹으면 결국 "개발자에게 Slack으로 수정 요청"이 되돌아온다.

##### 패턴 D. Hybrid (Git + Overlay Registry)

프롬프트의 뼈대(system prompt, few-shot 구조)는 Git, 지속적으로 바뀌는 **설정값(톤, 금칙어 리스트, 응답 길이 제약)** 만 Registry에 overlay.

```
# Git (코드 리뷰 필수)
system: "너는 {company}의 {role}이다. 다음 원칙을 지켜라: ..."

# Registry (PM이 수정)
overlay:
  company: "큐베어"
  role: "상담 전문가"
  tone_guidelines:
    - "'불가능합니다' 대신 '다른 방법을 찾아보겠습니다'"
  forbidden_terms: ["환불 불가", "책임 없음"]
```

**언제 쓰나**: 가장 현실적. 구조는 안정적이지만 **운영 중 조정이 잦은** 챗봇·고객지원·마케팅 카피 생성.

#### 5. 실제 사례

##### 사례 1: OpenAI Prompt Caching + System Message Versioning (2024)

OpenAI가 prompt caching을 발표하면서 공식 문서에 명시한 가이드: **"system prompt 앞 1024 토큰은 자주 바꾸지 마라. 캐시 miss로 비용이 폭증한다."** → 이게 바로 Registry가 필요한 이유다. "앞 1024토큰은 안정 버전, 뒤의 variable 영역만 교체" 라는 규칙을 Registry에서 schema로 강제할 수 있어야 한다. Prompt를 **"수정 가능 영역 / 수정 금지 영역"** 으로 쪼개서 저장하는 것.

##### 사례 2: Anthropic Workbench (2024~)

Anthropic이 Workbench를 공개한 핵심 이유 중 하나가 **"Draft → Save → Evaluate → Deploy"** 라이프사이클을 콘솔 안에서 완결시키는 것. 프롬프트와 모델 설정(temperature, max_tokens, extended thinking budget)을 묶어서 immutable snapshot으로 저장한다. 패턴 B의 교과서.

##### 사례 3: LangSmith Hub + LangFuse (2024)

LangSmith는 Registry에 Eval 결과를 직접 attach한다. `v2.3.1`의 metadata를 열면 "이 버전은 100개 Eval 샘플 중 94개 통과"가 바로 보인다. 승격 CI가 "eval_score >= 0.9"를 체크하도록 설계된 덕에, PM이 수정한 프롬프트가 Eval 통과 전엔 `@prod`로 넘어가지 않는다.

##### 사례 4: Shopify Semantic Search 운영팀 (2024 Dev Blog)

Shopify는 검색 품질을 담당하는 "Query Understanding Prompt"를 patch는 주 2회, minor는 월 2회 승격한다. **Major 변경(출력 JSON 스키마 변경)은 분기 1회로 제한**한다 — downstream 랭킹 모델이 재학습을 요구하기 때문. 이게 Prompt SemVer의 Major가 왜 중요한지에 대한 가장 명확한 사례다.

##### 사례 5 (실패): 국내 K 커머스 (2025) — "Settings 테이블 사고"

B2C 챗봇의 system prompt를 운영 DB `settings` 테이블의 `TEXT` 컬럼에 저장. PM이 Admin 페이지에서 자유롭게 수정 가능. 변경 로그가 없고, Eval 연동도 없음.
- 2025-08: PM이 "조금 더 공손하게"를 세 번 수정하면서 문장 끝마다 "~일지도 모르겠네요"를 추가.
- 2025-09: CS 민원 1,247건 — "챗봇이 말을 흐리고 책임을 안 집니다"
- 2025-10: 롤백하려 했지만 **원본 프롬프트를 아무도 못 찾음**. git에도 없고, 수정 로그도 없음. PM도 "제가 뭘 바꿨는지 기억이…".

**교훈**: Registry 없는 운영은 "조용히 썩는다". 500 에러처럼 터지지 않기 때문에 발견이 늦고, 발견했을 때는 돌아갈 지점이 없다.

##### 사례 6 (실패): 국내 S 핀테크 (2025) — "Prompt + Model 분리 저장의 비극"

Registry는 있었다. 하지만 **프롬프트와 모델 버전을 따로 관리**했다.
- Prompt v3.1은 `claude-sonnet-4-6`에서 Eval 94% 통과.
- 운영팀이 "비용 절감"으로 `claude-haiku-4-5-20251001`로 모델만 교체.
- 같은 프롬프트, 다른 모델 → Haiku가 긴 체인 추론을 약하게 수행 → 금융 상품 설명에서 금리 계산을 생략하기 시작.
- Eval은 재실행하지 않음. "프롬프트는 안 바뀌었으니까."

**교훈**: `(prompt, model, params, tools)` 는 **원자적 단위**다. 어느 하나만 바꿔도 새 버전. Registry가 이걸 schema로 강제하지 않으면 사용자가 반드시 분리해서 저장한다.

#### 6. 트레이드오프 매트릭스

| 패턴 | 변경 속도 | 거버넌스 | 운영 비용 | 적합 규모 |
|---|---|---|---|---|
| A. Git-based | 느림 | 최상 (PR review) | 낮음 | 소규모, 개발자 중심 |
| B. Managed SaaS | 빠름 | 중 (벤더 UI 의존) | 중 ($) | 중소규모, 비민감 데이터 |
| C. Self-hosted DB | 빠름 | 상 (내가 설계) | 높음 (UI 개발비) | 대규모, 민감 데이터 |
| D. Hybrid | 중간 | 상 | 중 | 대부분의 실무 — 가장 추천 |

#### 7. ✅ 반드시 Prompt Registry를 써야 하는 경우

1. **프롬프트 수정 주체가 비개발자**를 포함할 때 (PM, 법무, 운영팀).
2. **A/B 테스트, 카나리 배포**를 하는 경우 — 트래픽의 5%에만 새 프롬프트를 노출하려면 tag 기반 라우팅이 필수.
3. **감사/규제 요구**가 있는 산업 (금융권 설명의무, 의료 환자 커뮤니케이션) — "그 응답이 생성될 때 어떤 프롬프트가 쓰였는지" 재현 가능해야 함.
4. **Multi-Agent 시스템** — Agent별로 프롬프트가 10개 이상 되면 git 안에서 추적이 불가능.
5. **Eval 자동화와 연결**해야 할 때.

#### 8. ❌ 쓰면 안 되는 / 신중해야 하는 경우

1. **프롬프트 1~2개짜리 사이드 프로젝트** — Git const로 충분. Registry는 과잉.
2. **프롬프트가 코드 로직과 강하게 결합**된 경우 (예: LangChain Agent의 reasoning prompt) — 프롬프트만 교체해서 뭔가 좋아지길 기대하는 건 환상. 코드 PR과 함께 가야 함.
3. **PM이 수정할 UI를 만들 리소스가 없는데** 패턴 C를 선택 — 결국 "Slack으로 요청"으로 돌아간다. 그럴 바엔 패턴 B.
4. **매 호출마다 프롬프트가 동적으로 조립**되는 경우 (예: 사용자별 personalization) — 조립 로직 자체가 코드고, Registry는 조립 "뼈대"만 저장해야 함.

#### 9. 함정 모음

**함정 1. "최신이 항상 좋다"는 환상**
→ `@prod` tag는 **승격 결정의 결과**지, 최신 버전이 자동으로 받는 상이 아니다. CI가 Eval 통과를 체크해야 함.

**함정 2. 프롬프트와 모델을 분리 저장**
→ 사례 6의 참사. `(prompt, model, params, tools)` 는 원자 단위.

**함정 3. 변수 schema를 안 넣음**
→ `"안녕 {user_name}"`에서 `{user_name}` 이 null로 들어가면 `"안녕 None"`이 고객에게 전송된다. Registry는 JSON Schema로 변수 타입·필수 여부를 강제해야 함.

**함정 4. 응답 trace에 version을 안 박음**
→ "이 응답이 이상한데, 어느 버전?"에 답을 못 한다. 모든 LLM 호출 로그에 `prompt_version_id`가 attach되어야 Observability와 결합됨.

**함정 5. 롤백 훈련을 안 함**
→ "`@prod` tag를 v2.3.0으로 되돌리기"가 긴급 상황에서 3분 내 가능해야 함. 분기 1회 롤백 drill을 하지 않으면 실전에서 15분이 걸린다.

**함정 6. Few-shot example에 PII를 그대로 저장**
→ Registry가 S3라면 암호화는 당연, 그리고 example은 **합성 데이터로 교체**. 실제 고객 데이터를 example로 쓰면 Registry가 GDPR scope 안으로 끌려 들어온다.

**함정 7. Eval set과 Prompt를 같은 리포에 안 묶음**
→ 프롬프트는 올라갔는데 Eval은 뒤처진 상태 → `@prod`로 승격 가능해져버림. Eval set도 Registry에서 함께 버전 관리.

---

> 💡 **왜 중요한가**: 프롬프트는 코드처럼 터지지 않고 "조용히 썩기" 때문에, Registry 없는 운영은 사고가 났을 때 **"무엇이 바뀌었는지"와 "어디로 돌아갈지"** 둘 다 잃어버린 상태로 시작한다.
