### LLM Eval Pipeline — "프롬프트 좋아 보이는데?"라는 감(感), 그리고 배포 3일 뒤 결제 실패율이 12%로 튄 이유

#### 1. 새벽 2시 47분, PM이 슬랙으로 보낸 스크린샷

배포는 화요일 오후 4시였다. 프롬프트 v2.3 → v2.4. 변경 사항은 딱 두 줄, "친절한 톤을 강화" + "JSON 응답에 `refund_eligible` 필드 추가". 스테이징에서 손으로 15개 시나리오 돌려봤고, 팀장은 "느낌 좋다"고 승인했다. 그리고 목요일 새벽 2시 47분, PM이 스크린샷 하나를 던진다.

> "환불 요청하신 주문은 환불 대상이 맞으십니다. `refund_eligible: true`. 다만 저희 정책상 30일 이내 환불만 가능하며, 현재 32일이 경과하여 실제 환불은 불가능합니다."

`refund_eligible: true`인데 실제로는 환불 불가. JSON은 파싱되고, 백엔드는 그대로 결제 취소 API를 태우고, PG사에서 정책 위반으로 롤백. 결제 실패율이 평소 0.3%에서 12%로 튀었다. 프롬프트를 v2.3으로 롤백하니까 그날 낮에 잡았어야 할 다른 종류의 CS 티켓이 다시 올라오기 시작한다.

이 팀에는 Unit Test도 있고, Integration Test도 있고, Postman Collection도 있고, DataDog도 붙어 있다. **그런데 프롬프트 하나가 바뀌었을 때 그 변화가 얼마나 위험한지 측정할 방법이 없다.** 이게 LLM Eval이 해결하려는 문제다.

---

#### 2. 왜 기존 테스트로는 안 되는가

백엔드 시니어라면 이 질문을 먼저 던져야 한다. "그냥 assertion 늘리면 되는 거 아니야?"

| 기존 테스트가 붙잡는 것 | LLM 시스템에서 실제로 깨지는 것 |
|---|---|
| 함수가 예외를 던지지 않는가 | JSON은 정상인데 **의미가 틀림** |
| HTTP 200을 반환하는가 | 응답은 왔는데 **hallucinate한 정책** |
| 스키마가 맞는가 | 스키마는 맞는데 **필드 간 논리 모순** |
| 응답 시간이 SLA 안인가 | 시간은 맞는데 **톤이 갑자기 반말** |
| 결정적(deterministic) 동작 | Temperature 0.3에서 **같은 입력에 다른 답** |

핵심은 마지막 줄이다. LLM은 결정적이지 않다. `assertEquals(expected, actual)`가 **원리적으로 성립하지 않는다.** 그래서 "정답과 같은가"가 아니라 "**정답에 얼마나 가까운가**"를 측정해야 하고, 그것도 여러 축(정확도, 관련성, 안전성, 톤, 형식)으로 나눠 측정해야 한다.

#### 3. Eval Pipeline이 CI에 어떻게 끼어드는가

```
┌──────────────────────────────────────────────────────────────────────┐
│                     프롬프트/모델 변경 PR                             │
└──────────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────────────┐
│  1. Golden Dataset 로드 (200~2000건, prod 로그에서 샘플링 + 라벨링)   │
└──────────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────────────┐
│  2. Candidate 실행: 새 프롬프트 × 골든 데이터셋 → 응답 N개 생성       │
└──────────────────────────────────────────────────────────────────────┘
                              │
              ┌───────────────┼─────────────────┐
              ▼               ▼                 ▼
        ┌──────────┐    ┌──────────┐     ┌──────────────┐
        │  Rule-   │    │  Metric  │     │ LLM-as-Judge │
        │  based   │    │  based   │     │  (GPT-4/     │
        │ (regex,  │    │ (BLEU,   │     │  Claude Opus)│
        │  JSON    │    │  ROUGE,  │     │              │
        │  parse)  │    │  Embed   │     │  · 사실성    │
        │          │    │  cos-sim)│     │  · 관련성    │
        │  빠름    │    │  중간    │     │  · 톤        │
        │  값싸다  │    │  중간    │     │  느림 비쌈   │
        └────┬─────┘    └────┬─────┘     └──────┬───────┘
             │               │                  │
             └───────────────┼──────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────────────┐
│  3. Aggregate: 카테고리별 pass rate, regression 여부 계산            │
│     - 전체 pass rate ≥ baseline - 2%p ?                              │
│     - "결제/환불" 카테고리 pass rate ≥ 95% ?  (business-critical)    │
│     - Safety violation = 0 ?                                         │
└──────────────────────────────────────────────────────────────────────┘
                             │
                             ▼
┌──────────────────────────────────────────────────────────────────────┐
│  4. 결과를 PR 코멘트로 (v2.3 vs v2.4 diff, 회귀한 케이스 링크)        │
│     - 통과 시 shadow 배포 → A/B → prod                               │
│     - 실패 시 merge block                                            │
└──────────────────────────────────────────────────────────────────────┘
```

여기서 백엔드 관점의 포인트는 **3단계의 threshold**다. Unit test는 "pass/fail"이지만 Eval은 "**baseline 대비 얼마나 나빠졌는가**"다. 어제의 v2.3이 오늘의 baseline이고, 그 baseline을 코드 어딘가에 커밋된 숫자로 관리해야 한다 — 안 그러면 매 배포마다 조금씩 나빠져도 아무도 모른다.

#### 4. 세 가지 Eval 계층, 그리고 각각의 진짜 비용

##### (a) Rule-based / Schema Eval — 값싸고 촘촘한 1차 방어선

```python
def eval_refund_response(response: dict) -> dict:
    checks = {
        "valid_json": True,
        "has_required_fields": all(k in response for k in ["refund_eligible", "reason"]),
        "no_contradiction": not (
            response.get("refund_eligible") is True
            and any(kw in response.get("reason", "") for kw in ["불가능", "제외", "만료"])
        ),
        "reason_length_ok": 20 <= len(response.get("reason", "")) <= 500,
    }
    return checks
```

**앞의 사고를 잡을 수 있었던 건 딱 이 레이어**다. `refund_eligible: true`인데 `reason`에 "불가능"이 들어있다? → 논리 모순 flag. 이런 프로퍼티 기반 assertion은 골든 데이터셋이 없어도 구조적으로 실행 가능하다. 백엔드 시니어라면 여기부터 시작해야 한다. **가장 값싸고, 가장 자주 놓치는 계층이다.**

##### (b) Reference-based Metric — Embedding Cosine

정답이 있는 경우(FAQ, 정책 응답)에 쓴다. `sentence-transformers`로 정답과 응답을 임베딩해서 cosine similarity 0.85 이상이면 pass. BLEU/ROUGE는 자연어 응답에서는 낡았다 — 지금 스택이라면 embedding 유사도 + LLM Judge 조합이 표준.

##### (c) LLM-as-Judge — 비싸지만 유일한 선택지

톤, 관련성, 사실성은 rule로 못 잡는다. 그래서 **더 강한 모델에게 채점을 시킨다.**

```
[System]
당신은 CS 응답 품질 평가자입니다. 아래 5개 축으로 1~5점 채점하세요.
- 사실성: 정책 문서와 모순되지 않는가
- 관련성: 사용자 질문에 답하는가
- 톤: 정중하고 일관된가
- 완결성: 다음 액션이 명확한가
- 안전성: 개인정보/금액을 함부로 노출하지 않는가

[User Question] {question}
[Policy Context] {retrieved_docs}
[Model Answer] {answer}

JSON으로만 응답: {"facticity": N, "relevance": N, ...}
```

**함정 3개**:
1. **Position bias** — Judge에게 A/B 두 답을 비교시키면 앞에 놓인 것을 편애한다. → 순서 섞고 두 번 채점.
2. **Self-preference bias** — GPT-4가 심사하면 GPT-4가 만든 답에 후한 점수를 준다. → Judge와 Candidate은 다른 벤더로.
3. **비용 폭발** — 골든셋 500건 × 5축 × 3회 반복 = 요청 7,500건. Judge를 Opus로 돌리면 CI 한 번에 $30~50이 우습게 나간다. → PR CI에는 200건, 야간 nightly는 2000건으로 계층 분리.

#### 5. Golden Dataset — 가장 지루하고 가장 중요한 자산

Eval 파이프라인 구축에서 90%의 시간이 여기 든다. 그리고 팀들이 90% 실패하는 지점도 여기다.

| 안티패턴 | 왜 문제인가 | 실무 처방 |
|---|---|---|
| "PM이 예쁘게 손으로 만든 100건" | Prod에서 실제로 오는 질문과 분포가 다름 | 지난 30일 prod 로그에서 **stratified sampling**(카테고리별 비율 유지) |
| "정답을 개발자가 씀" | 도메인 지식 부족으로 정답이 틀림 | 정답은 **CS팀/도메인 전문가**가 라벨링, 개발자는 인프라만 |
| "한 번 만들고 6개월 방치" | 신규 상품·정책이 반영 안 됨 | 매주 신규 CS 티켓 중 **모델이 틀린 케이스** 20건씩 편입 |
| "성공 케이스만 넣음" | Adversarial 입력에 약함 | 오탈자, 반말, 다국어 섞임, 프롬프트 인젝션 시도 별도 카테고리로 |

여기서 백엔드 관점의 인사이트: **골든 데이터셋은 DB 스키마처럼 버전 관리되어야 한다.** `golden_v2026_08.jsonl`처럼 이름을 박고, PR 승인에는 어떤 버전 대비 얼마나 좋아졌는지가 명시돼야 한다. 안 그러면 "우리 프롬프트 v2.4가 v2.3보다 좋아졌다"는 문장이 재현 불가능해진다.

#### 6. 실제 사례

##### Anthropic — "Model Card" 뒤에 있는 실제 자동화
Anthropic이 Claude 4 계열을 릴리스할 때 공개하는 벤치마크(MMLU, HumanEval, MATH, TAU-bench)는 결과일 뿐, 실제 릴리스 게이트는 **수백 개의 내부 Eval 스위트**다. 안전성 관련 축(bio/chem/cyber 리스크, sycophancy, jailbreak resistance)은 각각 별도 데이터셋 + 별도 Judge로 돌리고, **어느 한 축도 baseline보다 나빠지면 릴리스 블록**. RSP(Responsible Scaling Policy) 문서가 이 게이트의 제도적 근거다.

##### Notion AI — 프롬프트 A/B의 Eval-first 워크플로우
Notion은 "AI 요약" 같은 기능에 프롬프트 변경이 있을 때 (1) 내부 골든셋 대비 Judge 채점 → (2) 통과하면 1% shadow → (3) 유저 대상 A/B에서 accept/reject rate 관찰. **1단계에서 걸리면 A/B 자체를 안 튼다.** A/B는 비싼 자원이니까 Eval이 예산을 지킨다는 관점.

##### GitHub Copilot — "Acceptance Rate"를 온라인 Eval로
오프라인 Eval의 한계는 "**실제 유저는 다르게 행동한다**". Copilot이 유명해진 이유는 **온라인 신호를 KPI로 승격**시켰기 때문이다: 코드 제안 후 15초/30초/2분 시점에 그 코드가 살아있는가(retention). 오프라인 Eval은 배포 전 회귀 방지, 온라인 Eval(retention, thumbs up/down)은 진짜 품질. **두 개를 동시에 안 굴리는 팀은 결국 반년 뒤에 모른 채로 나빠져 있다.**

##### Booking.com — LLM 답변 → 도메인 KPI
Booking처럼 답변이 곧 예약 전환에 영향 주는 곳은 Eval의 마지막 축이 embedding cosine이 아니라 **"이 답을 본 유저의 예약 완료율"**이다. LLM Judge 스코어와 비즈니스 KPI의 correlation을 지속적으로 계산해서, correlation이 낮으면 Judge 프롬프트를 다시 뜯는다. 백엔드 시니어에게 익숙한 관점: **관측 지표는 결국 돈으로 환산되어야 신뢰받는다.**

#### 7. 트레이드오프

| 축 | 저비용 쪽 | 고비용 쪽 |
|---|---|---|
| **커버리지 vs 속도** | Rule-based만, CI 30초 | Judge 포함, CI 15분 |
| **정확성 vs 편향** | 단일 Judge(GPT-4o) | Ensemble Judge, 여러 벤더 |
| **재현성 vs 현실성** | 고정 골든셋 | Prod traffic replay |
| **자동화 vs 신뢰** | LLM Judge 100% | Human-in-the-loop 5~10% 샘플링 |
| **오프라인 vs 온라인** | 배포 전 게이트만 | 배포 후 retention/thumbs 지속 |

**시니어의 결정 지점**: 스타트업 초기에는 (1)+(3)+(5의 오프라인)만으로 시작. Growth 단계에서 (2)+(4)를 붙이고, 매출에 직결되면 (5의 온라인)까지 편입. **처음부터 다 하려다 아무것도 못 굴리는 팀을 여러 번 봤다.**

#### 8. 언제 쓰고, 언제 쓰면 안 되는가

**쓸 때 (반드시):**
- 프롬프트/모델이 **매주 이상** 바뀌는 프로덕션 LLM 시스템
- 답변의 정확성이 **돈, 안전, 컴플라이언스**에 직결되는 도메인 (금융/의료/법률/CS)
- 여러 팀이 같은 프롬프트 저장소를 만지는 상황 — Eval이 없으면 서로의 변경이 뭘 깨는지 모른다
- 모델 벤더 마이그레이션 (OpenAI → Claude, Claude 3.5 → 4.7) — 개발자 감(感)으로 "비슷하다"는 절대 금물

**쓰지 말아야 할 때 (오버엔지니어링):**
- 사내 데모, PoC, 해커톤 — 골든셋 만들 시간에 유저 인터뷰가 낫다
- **프롬프트가 3개월에 한 번 바뀌는** 정적인 시스템 — CI 파이프라인 유지 비용이 얻는 이득보다 크다
- 트래픽 하루 100건 미만 — 통계적 유의성이 안 나온다. 로그 눈으로 훑는 게 더 낫다
- LLM 응답이 **최종 사용자에게 노출되지 않고** 후단 시스템이 후처리로 fallback을 잡아주는 구조 — rule-based schema check만으로 충분

#### 9. 시니어 관점의 3가지 실전 조언

1. **Eval을 만들기 전에 로그부터.** 프롬프트, 응답, 유저 피드백, 다음 유저 액션을 함께 저장해라. 이게 없으면 골든셋을 못 만든다. `request_id`로 join 가능한 스키마를 먼저 설계.
2. **Judge 프롬프트도 버전 관리된 코드다.** `judge/v3.md`가 있고, judge 자체의 정확도(사람 라벨과의 agreement)를 주기적으로 재는 **meta-eval**이 있어야 한다. Judge가 조용히 나빠지는 걸 아무도 모르는 상황이 가장 위험하다.
3. **PR에 "Eval 결과" 코멘트를 봇으로 자동화.** 사람이 CI 로그 뒤져서 확인하게 만드는 순간 아무도 안 본다. GitHub Actions → PR comment에 v2.3 vs v2.4 diff, 회귀한 케이스 top-5 링크. 코드 리뷰 문화의 일부로 편입시켜야 살아남는다.

> 💡 **왜 중요한가**: LLM 시스템에서 "배포 가능한가"의 판정은 unit test pass가 아니라 **baseline 대비 회귀 없음**이며, 이 판정을 자동화하지 못한 팀은 모델 품질이 조용히 나빠져도 사고가 터지기 전까지 절대 알아채지 못한다.
