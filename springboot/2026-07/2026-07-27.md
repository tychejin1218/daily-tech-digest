### `@ConfigurationProperties`는 `@Value`와 달리 바인딩 실패 시 애플리케이션 시작을 막는다

`@Value("${...}")`는 존재하지 않는 프로퍼티나 타입 불일치를 런타임 첫 사용 시점에 터뜨리지만, `@ConfigurationProperties(prefix = "app")`는 시작 시점에 바인딩을 수행하며 `@Validated`와 조합하면 JSR-303 제약 위반 시 `BindValidationException`으로 부팅 자체를 실패시킨다. Fail-fast가 필요한 설정(예: 외부 API URL, 필수 시크릿)은 반드시 `@ConfigurationProperties + @Validated` 조합으로 선언해야 프로덕션에서 첫 요청이 아니라 배포 순간에 문제를 잡을 수 있다.

```java
@ConfigurationProperties(prefix = "payment")
@Validated
public record PaymentProperties(
    @NotBlank String apiKey,
    @NotNull @Min(100) Integer timeoutMs,
    @URL String callbackUrl
) {}
```

> 💡 **왜 중요한가**: 잘못된 설정은 배포 순간에 실패시켜야지, 자정에 첫 결제 트랜잭션이 발생한 뒤에 발견되어서는 안 된다.

### `@ControllerAdvice`의 `basePackages`/`assignableTypes`로 예외 처리 스코프를 좁혀야 API/Admin이 뒤섞이지 않는다

기본 `@ControllerAdvice`는 애플리케이션의 모든 컨트롤러에 전역으로 적용되므로, REST API와 서버사이드 렌더링 Admin이 공존하는 프로젝트에서 하나의 어드바이스가 HTML 화면에도 JSON 응답을 반환하는 사고가 흔하다. `@RestControllerAdvice(basePackages = "com.example.api")` 또는 `assignableTypes = {ApiController.class}`로 스코프를 명시적으로 제한하면 예외 응답 포맷이 컨트롤러 종류에 따라 정확히 분리된다.

```java
@RestControllerAdvice(basePackages = "com.example.api")
public class ApiExceptionHandler {
    @ExceptionHandler(EntityNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(EntityNotFoundException e) {
        return ResponseEntity.status(404).body(new ErrorResponse("NOT_FOUND", e.getMessage()));
    }
}
```

> 💡 **왜 중요한가**: 전역 어드바이스는 편해 보이지만, Admin 페이지가 JSON 에러 페이로드를 렌더링하는 순간 사용자에게 스택 형태의 원문이 노출될 수 있다.
