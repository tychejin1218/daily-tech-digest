### Service Mesh — "네트워크를 애플리케이션 밖으로 꺼내라"는 사이드카의 철학

MSA가 서비스 10개를 넘어가는 순간, 개발자는 이상한 현상을 마주한다. **비즈니스 로직보다 "다른 서비스를 안전하게 부르는 코드"가 더 길어진다.** Retry, Timeout, Circuit Breaker, mTLS, Tracing 헤더 전파, Rate Limiting, Canary 라우팅... 이 모든 것이 각 서비스의 코드베이스에 흩어져 있고, Java 서비스는 Resilience4j로, Python 서비스는 tenacity로, Go 서비스는 hystrix-go로 — **같은 정책을 언어마다 다르게 구현**한다. 정책 하나 바꾸려면 N개 팀이 N개 릴리스를 해야 한다.

Service Mesh는 이 문제에 급진적인 답을 낸다. **"네트워킹 관심사는 애플리케이션 코드가 아니라 인프라 레이어에 있어야 한다."** 각 서비스 Pod 옆에 사이드카 프록시(Envoy 등)를 붙이고, 서비스 간 모든 트래픽을 이 프록시가 가로챈다. 애플리케이션은 `http://order-service`로 그냥 호출하고, mTLS·재시도·회로 차단·트레이싱은 프록시가 처리한다. 정책은 YAML 한 장으로 중앙에서 선언한다.

#### 아키텍처: Data Plane과 Control Plane의 분리

```
┌─────────────────────────────────────────────────────────────┐
│                    Control Plane (istiod)                    │
│  - 설정 배포 (VirtualService, DestinationRule)               │
│  - 인증서 발급/회전 (SPIFFE)                                 │
│  - 서비스 디스커버리 통합                                     │
└──────────────────┬──────────────────────────┬───────────────┘
                   │ xDS API                  │ xDS API
                   ▼                          ▼
┌──────────────────────────┐    ┌──────────────────────────┐
│         Pod A            │    │         Pod B            │
│  ┌────────────────────┐  │    │  ┌────────────────────┐  │
│  │  App (order-svc)   │  │    │  │  App (payment-svc) │  │
│  │  :8080             │  │    │  │  :8080             │  │
│  └─────────┬──────────┘  │    │  └────────▲───────────┘  │
│            │ localhost   │    │           │ localhost    │
│  ┌─────────▼──────────┐  │    │  ┌────────┴───────────┐  │
│  │  Envoy Sidecar     │──┼────┼─▶│  Envoy Sidecar     │  │
│  │  (iptables 가로챔) │  mTLS│  │  (iptables 가로챔) │  │
│  └────────────────────┘  │    │  └────────────────────┘  │
└──────────────────────────┘    └──────────────────────────┘
        Data Plane                       Data Plane
```

핵심은 **iptables가 애플리케이션의 in/out 트래픽을 모두 사이드카로 리다이렉트**한다는 것이다. 앱은 이 존재를 모른다. 이 투명성이 Service Mesh의 최대 장점이자 최대 함정이다.

#### Sidecar가 실제로 해주는 일

Istio의 `VirtualService` 하나로 다음을 선언한다:

```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: payment-service
spec:
  hosts: [payment-service]
  http:
    - match: [{ headers: { x-canary: { exact: "true" } } }]
      route: [{ destination: { host: payment-service, subset: v2 } }]
    - route: [{ destination: { host: payment-service, subset: v1 }, weight: 95 }
             ,{ destination: { host: payment-service, subset: v2 }, weight: 5 }]
      retries: { attempts: 3, perTryTimeout: 2s, retryOn: 5xx,reset }
      timeout: 10s
      fault: { delay: { percentage: { value: 0.1 }, fixedDelay: 5s } }  # 카오스 주입
```

이 파일 한 장이 **Canary 배포 + 재시도 + 타임아웃 + 결함 주입**을 모두 처리한다. 애플리케이션 코드는 한 줄도 안 바뀐다. Circuit Breaker는 `DestinationRule`의 `outlierDetection`으로 선언하고, mTLS는 `PeerAuthentication` 하나로 클러스터 전체에 강제할 수 있다.

#### Istio vs Linkerd: 두 철학의 대립

|                | **Istio**                          | **Linkerd**                     |
| -------------- | ---------------------------------- | ------------------------------- |
| Proxy          | Envoy (C++, 범용)                  | linkerd2-proxy (Rust, 전용)     |
| 리소스 오버헤드| Pod당 100~150MB, 지연 +2~5ms       | Pod당 10~20MB, 지연 +0.5~1ms    |
| 기능 범위      | 광범위 (WASM 확장, JWT, 정책 언어) | 최소한 (mTLS, retry, tracing)   |
| 학습 곡선      | 가파름 (CRD 20+)                   | 완만 (CRD 5~6개)                |
| 대표 사용처    | Google, IBM, T-Mobile              | HP, Microsoft(일부), Xbox Cloud |

**Istio는 "네트워크의 Kubernetes"를 노리는 플랫폼**이고, **Linkerd는 "잘 만든 하나의 도구"를 지향**한다. HP는 Istio를 도입했다가 운영 복잡도로 Linkerd로 재이주한 사례가 유명하고(2019), 반대로 Airbnb는 초기 Linkerd에서 Envoy 생태계 필요성 때문에 Istio로 넘어갔다.

#### 실제 사례: Lyft가 Envoy를 만든 이유

Lyft는 2016년 모놀리스에서 MSA로 전환하며 **"각 언어(PHP/Python/Go) 팀이 저마다 다른 재시도 로직을 구현하는 지옥"**을 겪었다. 배포마다 특정 언어 서비스만 장애가 났고, 원인은 언어별 HTTP 클라이언트 라이브러리의 미묘한 차이였다. 그래서 Envoy를 만들어 **모든 언어의 out-going 요청을 하나의 프록시로 통일**했다. 지금 Envoy는 CNCF Graduated 프로젝트이고 Istio·AWS App Mesh·Consul Connect의 데이터 플레인이 됐다.

#### 어두운 면: Sidecar 세금

- **디버깅이 두 배로 어렵다.** 요청이 실패하면 앱 로그·Envoy 액세스 로그·Istio Control Plane 이벤트를 모두 봐야 한다. `503 upstream connect error`가 앱 문제인지 프록시 문제인지 mTLS 문제인지 즉시 분간이 안 된다.
- **리소스 세금이 크다.** Pod가 500개인 클러스터라면 Envoy만 50~75GB 메모리를 잡아먹는다. 이 문제 때문에 Istio 1.22부터 **Ambient Mesh(사이드카 없는 모드)**가 정식 출시됐고, Cilium은 eBPF로 사이드카를 대체하는 방향으로 가고 있다.
- **정책 오작동의 폭발 반경이 크다.** 잘못된 `AuthorizationPolicy` 하나가 클러스터 전체 서비스 간 통신을 즉시 끊는다. Reddit이 2023년 컨트롤 플레인 설정 롤아웃 오류로 314분 다운된 사례가 있다.
- **레이어의 중복.** Resilience4j로 Circuit Breaker를 이미 구현했는데 Mesh가 또 회로를 차단하면? **정책이 두 곳에 존재하는 순간 어느 쪽이 이겼는지 아무도 모른다.**

#### 시니어의 판단: 언제 쓰고 언제 쓰면 안 되는가

**써야 할 때:**
- 서비스가 **20개 이상**이고 언어가 **3종 이상** 섞여 있다. 언어별 라이브러리를 통일하는 비용이 Mesh 도입 비용을 넘어선다.
- **Zero-trust 네트워크(mTLS 전면 강제)**가 컴플라이언스 요구사항이다. 앱 코드 수정 없이 클러스터 전체에 강제할 유일한 방법.
- **Canary/Blue-Green 배포**를 트래픽 비율 단위로 세밀하게 하고 싶다.
- 조직에 **전담 플랫폼 팀(최소 2~3명)**이 있다. Mesh는 "설치하면 끝"이 아니다.

**쓰지 말아야 할 때:**
- 서비스가 10개 미만이고 언어가 하나다 → **Spring Cloud Gateway + Resilience4j**로 충분하다. Mesh 도입은 오버엔지니어링.
- 팀에 Envoy·xDS·iptables를 이해하는 사람이 없다 → **Sidecar 문제로 새벽에 깨는 것은 반드시 벌어진다.**
- 지연 시간이 극도로 민감하다(HFT, 실시간 게임) → 프록시 홉이 추가하는 밀리초가 SLA를 깬다.
- 서비스가 클러스터 밖(레거시 VM, 3rd party)까지 걸쳐 있고 아직 Kubernetes 이관이 덜 됐다 → Mesh는 K8s 안에서 가장 잘 동작한다.

**중간 지대의 선택지도 기억할 것.** Kubernetes의 기본 Service + CoreDNS만으로도 서비스 디스커버리와 L4 로드밸런싱은 해결된다. 그 위에 Ingress Gateway로 외부 트래픽만 다루고, 내부는 앱 라이브러리로 회복성을 챙기는 **"Half-Mesh" 전략**이 실무에서 가장 흔한 착지점이다. Mesh는 **"우리 조직이 진짜로 이 복잡도를 감당할 수 있는가"**를 먼저 물은 뒤 도입해야 한다.

> 💡 **왜 중요한가**: Service Mesh는 "네트워킹을 앱 밖으로 꺼낸다"는 강력한 추상화지만, 사이드카가 만드는 새 층의 복잡도가 조직의 운영 역량을 넘으면 오히려 장애의 원흉이 된다.
