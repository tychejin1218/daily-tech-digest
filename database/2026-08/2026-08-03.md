### MySQL `EXPLAIN ANALYZE` — 예측이 아닌 실측으로 실행 계획의 거짓말 잡아내기

`EXPLAIN`은 옵티마이저의 예측(rows, cost)을 보여주지만, `EXPLAIN ANALYZE`는 쿼리를 실제로 실행해서 각 노드별 실측 시간(actual time)과 실측 rows를 함께 뽑아준다. 예측 rows와 실측 rows가 10배 이상 벌어지면 통계가 왜곡되었다는 확실한 신호이고, `loops` 값이 폭발하면 그 지점이 진짜 병목이다. 실행 시간이 부담되면 `EXPLAIN ANALYZE FORMAT=TREE`로 트리 구조까지 뽑아 조인 순서 문제를 시각적으로 잡아낼 수 있다.

```
-> Nested loop inner join  (actual time=0.5..2340 rows=8500 loops=1)
    -> Index scan on orders  (actual time=0.1..12 rows=100 loops=1)   ← 예측 100, 실측 100 ✅
    -> Filter: (users.status = 'ACTIVE')  (actual time=1.2..23 rows=85 loops=100)  ← loops=100! ⚠️
        -> Table scan on users  (actual time=0.8..22 rows=50000 loops=100)  ← 500만 행 스캔
```

> 💡 **왜 중요한가**: 옵티마이저의 예측(`rows=100`)이 맞아도 `loops=100`이 곱해지면 실제 부하는 100배로 튀는데, `EXPLAIN`만 봐서는 절대 보이지 않는다.

### PostgreSQL `LATERAL JOIN` — 각 행마다 서브쿼리를 다시 실행하는 상관 조인을 명시적으로 표현하기

`LATERAL`은 오른쪽 서브쿼리가 왼쪽 테이블의 컬럼을 참조할 수 있게 해줘서, 각 사용자별 "최근 주문 3건", "카테고리별 TOP-N" 같은 상관 서브쿼리를 조인 문법으로 자연스럽게 풀어낸다. 윈도우 함수(`ROW_NUMBER() OVER PARTITION BY`)로 풀면 전체 데이터를 정렬해야 하지만, `LATERAL + LIMIT`은 각 파티션마다 인덱스로 top-k만 뽑아 훨씬 빠르다. 특히 사용자별 최신 N건 조회 같은 패턴에서 실행 시간이 10배 이상 차이 난다.

```sql
-- ❌ 윈도우 함수: 전체 주문 100만 건을 정렬한 뒤 필터
SELECT * FROM (
  SELECT o.*, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) rn
  FROM orders o
) WHERE rn <= 3;

-- ✅ LATERAL: user_id + created_at 인덱스로 각 유저당 3건씩만 스캔
SELECT u.id, o.*
FROM users u
CROSS JOIN LATERAL (
  SELECT * FROM orders
  WHERE user_id = u.id
  ORDER BY created_at DESC
  LIMIT 3
) o;
```

> 💡 **왜 중요한가**: "사용자별 최근 N건"은 모든 서비스에 존재하는 쿼리지만, 윈도우 함수로 풀면 데이터가 늘수록 선형 이상으로 느려지고 `LATERAL`은 인덱스 유효 범위 안에서 상수 시간에 가깝게 유지된다.
