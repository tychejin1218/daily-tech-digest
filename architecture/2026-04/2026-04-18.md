### API Gateway — "N개의 클라이언트 × M개의 서비스"를 O(1)로 만드는 경계

마이크로서비스로 쪼개는 순간 클라이언트는 지옥을 만난다. 모바일 앱이 주문 화면 하나를 그리려고 `/users`, `/orders`, `/products`, `/reviews`, `/inventory` 5개 서비스에 직접 호출하면, 네트워크 왕복은 5배가 되고 각 서비스의 URL·인증·버전을 앱이 전부 알아야 한다. 서비스가 하나 늘거나 URL이 바뀌면 앱을 재배포해야 한다. **API Gateway는 이 N×M 결합을 끊어내는 단일 진입점(Single Entry Point)이다.**

DDD·Clean Architecture 관점에서 보면, API Gateway는 시스템 전체의 "1차 어댑터 계층"이다. 각 마이크로서비스는 자기 Bounded Context 안에서 순수한 도메인 모델과 유즈케이스만 노출하고, Gateway가 그 앞단에서 인증·라우팅·집계·프로토콜 변환 같은 **횡단 관심사(cross-cutting concerns)** 를 모두 흡수한다. 헥사고날의 "도메인은 프레임워크(HTTP·인증·Rate Limiter)를 몰라야 한다"는 원칙을 시스템 스케일로 확장한 것이다.

```
[모바일 앱]  [웹 SPA]  [파트너 API]  [B2B 클라이언트]
     \         |          /             /
      \        |         /             /
       \       ↓        /             /
        ┌──────────────────────────────┐
        │        API Gateway           │
        │  ─────────────────────────   │
        │  • 인증/인가 (JWT 검증)      │
        │  • Rate Limiting             │
        │  • 라우팅 (/orders/* → ...)  │
        │  • 응답 집계 (Fan-out/in)    │
        │  • 프로토콜 변환 (HTTP↔gRPC) │
        │  • 로깅/트레이싱/캐싱        │
        │  • 서킷 브레이커             │
        └──────┬────────┬────────┬─────┘
               │        │        │
       ┌───────↓──┐ ┌───↓───┐ ┌──↓─────┐
       │ User svc │ │Order  │ │Product │
       │ (gRPC)   │ │(HTTP) │ │ (gRPC) │
       └──────────┘ └───────┘ └────────┘
```

**Gateway가 흡수하는 6가지 관심사**

| 관심사 | Gateway가 없을 때 | Gateway가 있을 때 |
|---|---|---|
| 인증 | 서비스마다 JWT 파서 중복 구현 | Gateway 한 곳에서 검증 후 서비스에 클레임 전달 |
| Rate Limit | 서비스별로 각자 카운터 (일관성 없음) | 전역 카운터, 클라이언트 단위 제어 |
| 응답 집계 | 클라이언트가 5개 호출 후 조합 | Gateway가 병렬 호출 후 하나로 합쳐서 반환 |
| 프로토콜 | 외부는 HTTP, 내부도 HTTP 강제 | 외부 REST, 내부 gRPC/Kafka 자유 선택 |
| 버저닝 | 클라이언트가 서비스별 버전 관리 | `/v1/orders`, `/v2/orders` Gateway가 라우팅 |
| 관측성 | 서비스별 로그 포맷 제각각 | Gateway 진입 시점에 상관 ID 부여, 전체 추적 |

**트레이드오프**

- **단일 실패 지점(SPOF)** — Gateway가 죽으면 모든 요청이 죽는다. 반드시 HA(다중 인스턴스 + LB) 구성 필수. Netflix Zuul 초창기 사고가 대표 사례.
- **레이턴시 추가** — 홉이 하나 늘어난다 (통상 1–5ms). 저지연이 생명인 트레이딩·게임 실시간 서버는 부담.
- **Gateway 비대화(Fat Gateway 안티패턴)** — 비즈니스 로직을 Gateway에 넣기 시작하면 "숨겨진 모놀리스"가 된다. Gateway는 **도메인 무지(domain-ignorant)** 여야 한다. 주문 할인 계산은 절대 Gateway에서 하면 안 된다.
- **팀 병목** — 모든 팀이 Gateway 설정을 바꿔야 하면 인프라팀이 병목이 된다. → 팀별 config 분리 or BFF 패턴(다음 단계 예정)으로 해결.

**언제 써야 하는가**

- ✅ 마이크로서비스 3개 이상, 외부 클라이언트(모바일·서드파티) 다수
- ✅ 인증·Rate Limit·감사 로그를 통일해야 하는 규제 환경(금융·헬스케어)
- ✅ 내부에서 gRPC·Kafka를 쓰면서 외부에는 REST/GraphQL로 노출해야 할 때
- ❌ 서비스 1–2개짜리 초기 스타트업 (오버엔지니어링, nginx로 충분)
- ❌ 초저지연(<1ms) SLA를 요구하는 실시간 시스템
- ❌ 팀이 Gateway 운영 역량이 없을 때 (SPOF 리스크 > 얻는 이득)

**실제 사례**

- **Netflix Zuul** — 마이크로서비스 800개+ 앞단에서 하루 수백억 요청을 라우팅. 동적 필터로 A/B 테스트 트래픽 분기까지 처리. 이후 Spring Cloud Gateway로 진화하며 Reactive(Netty) 기반으로 재작성.
- **Amazon API Gateway** — Lambda와 결합해 서버리스 백엔드의 사실상 표준. 인증(Cognito)·요청 매핑·응답 캐싱을 매니지드로 제공. 스타트업이 인프라팀 없이도 Gateway를 도입하게 만든 결정적 계기.
- **카카오·배민** — 자체 Gateway(카카오는 Spring Cloud Gateway 기반, 배민은 Kong/Envoy 조합)로 수백 개 마이크로서비스 앞단을 통제. 특히 트래픽 폭주(선착순 이벤트, 프로모션) 시 Gateway 레벨에서 백프레셔·서킷 브레이커를 걸어 후단 보호.
- **Kubernetes Ingress + Envoy(Istio)** — 서비스 메시 시대에는 Gateway 역할이 사이드카·인그레스로 분산되기도 한다. 하지만 "외부 트래픽의 경계"라는 개념은 사라지지 않고 오히려 강화된다.

**시니어 관점의 원칙 3가지**

1. **Gateway는 얇게, 서비스는 두껍게** — Gateway에 도메인 로직이 스며들면 그 순간 모놀리스로 회귀한다.
2. **Gateway는 계약(Contract)의 안정성을 책임진다** — 내부 서비스가 리팩터링·분해되어도 외부 API 계약은 Gateway가 흡수해 유지시켜야 한다.
3. **Gateway는 관측성의 시작점** — 모든 요청의 최초 진입점이므로, 여기서 상관 ID·사용자 컨텍스트·타이밍을 심어야 downstream 전체가 관측 가능해진다.

> 💡 **왜 중요한가**: API Gateway는 "클라이언트를 서비스 지형도로부터 격리하는 경계"이며, 이 경계를 얇게 유지할 수 있느냐가 마이크로서비스 아키텍처의 성패를 가른다.
