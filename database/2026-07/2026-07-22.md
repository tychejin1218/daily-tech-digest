### 1. PostgreSQL `BRIN` 인덱스 — 시계열·append-only 대용량 테이블을 B-tree의 1/1000 크기로 인덱싱하기
`CREATE INDEX ... USING brin (created_at)`은 값 자체가 아니라 페이지 블록 범위의 min/max 요약만 저장하기 때문에, 물리적 순서와 논리적 순서가 정렬된 컬럼(주로 타임스탬프, 시퀀스 ID)에서 B-tree 대비 인덱스 크기를 수백~수천 분의 1로 줄일 수 있습니다. 단, 무작위로 INSERT/UPDATE가 섞이면 블록 범위가 뒤섞여 선택도가 급락하므로 로그·이벤트·측정치 테이블처럼 시간순 적재가 보장되는 경우에만 효과적입니다.

> 💡 **왜 중요한가**: 수십억 행짜리 로그 테이블에서 "지난 1시간 데이터"를 뽑을 때, GB 단위 B-tree 유지 비용 없이 MB 수준의 인덱스로 동일한 범위 스캔 성능을 확보할 수 있습니다.

### 2. Spring `@Transactional(propagation = REQUIRES_NEW)` — 감사 로그·알림을 별도 트랜잭션으로 분리해 롤백에도 살아남게 하기
바깥 트랜잭션이 예외로 롤백되더라도 감사 로그, 실패 이력, 외부 API 호출 기록 등은 반드시 남아야 하는 경우가 있습니다. `REQUIRES_NEW`는 현재 트랜잭션을 잠시 보류(suspend)하고 별도의 물리 트랜잭션을 새로 열어 커밋하기 때문에, 바깥이 롤백돼도 안쪽은 독립적으로 살아남습니다. 다만 같은 DB 커넥션을 재사용할 수 없어 커넥션이 두 개 필요해지므로, 커넥션 풀 크기와 데드락 가능성을 함께 검토해야 합니다.

> 💡 **왜 중요한가**: "결제는 실패했지만 실패 로그는 반드시 남아야 한다" 같은 요구사항을, 애플리케이션 레벨 try-catch가 아닌 트랜잭션 경계로 명확히 표현할 수 있습니다.
