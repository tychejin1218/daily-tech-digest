### MySQL `Covering Index` — 인덱스만으로 SELECT를 끝내서 테이블 접근(Random IO)을 아예 제거하는 "은밀한 2배속 부스터"

`SELECT`가 필요로 하는 모든 컬럼이 인덱스에 포함되어 있으면, MySQL은 실제 테이블(clustered index)을 조회하지 않고 인덱스만 읽어서 응답한다. `EXPLAIN`에서 `Extra: Using index`로 확인할 수 있으며, 특히 InnoDB에서는 세컨더리 인덱스 → PK 조회의 이중 랜덤 IO가 사라져 체감 성능이 2~10배 뛴다. `(user_id, status)` 인덱스에 `created_at`을 하나 더 얹기만 해도 페이지네이션 쿼리가 완전히 다른 세계로 넘어간다.

```sql
-- Before: 세컨더리 인덱스 → PK 조회로 랜덤 IO 발생
CREATE INDEX idx_user_status ON orders (user_id, status);
SELECT id, created_at FROM orders WHERE user_id = 1 AND status = 'PAID';
-- EXPLAIN Extra: NULL (테이블 접근 필요)

-- After: 커버링 인덱스로 인덱스만 읽고 끝
CREATE INDEX idx_user_status_covering ON orders (user_id, status, created_at);
SELECT id, created_at FROM orders WHERE user_id = 1 AND status = 'PAID';
-- EXPLAIN Extra: Using index (테이블 접근 0회)
```

MySQL 8.0에서는 `INCLUDE` 문법이 없어서 인덱스 컬럼으로 직접 끼워 넣어야 하지만, InnoDB는 어차피 세컨더리 인덱스에 PK가 자동 포함되므로 `id`는 명시할 필요조차 없다.

> 💡 **왜 중요한가**: 인덱스 하나에 컬럼 하나 더 얹는 "5초짜리 수정"이 랜덤 IO를 절반으로 줄여 QPS를 두 배로 만드는, 가장 저렴한 성능 개선 카드다.

### JPA `@EntityGraph` — Fetch Join의 "쿼리 메서드용 형제", 페이지네이션까지 살리는 N+1의 정답

`@EntityGraph`는 특정 조회에서만 연관 엔티티를 즉시 로딩하도록 지시하는 어노테이션으로, JPQL을 직접 쓰지 않고도 Repository 메서드나 `find*` 호출에 붙일 수 있다. Fetch Join과 유사하지만 결정적 차이는 "LEFT OUTER JOIN을 기본으로 사용"하고, `@OneToMany` 컬렉션이라도 Hibernate가 페이지네이션을 인메모리로 처리하지 않고 별도 쿼리로 나눠 실행할 수 있다는 점이다(6.x부터). 매번 EAGER로 바꾸지 않고 "이 조회에서만 함께 가져오기"를 선언적으로 표현할 수 있어 유지보수성이 극적으로 올라간다.

```java
public interface OrderRepository extends JpaRepository<Order, Long> {

    // 이 조회에서만 user, items를 함께 fetch
    @EntityGraph(attributePaths = {"user", "items"})
    Optional<Order> findWithUserAndItemsById(Long id);

    // 명명된 그래프 사용 (Order 엔티티에 @NamedEntityGraph 정의 필요)
    @EntityGraph("Order.withDetails")
    List<Order> findByStatus(OrderStatus status);
}
```

단, `@OneToMany` 여러 개를 동시에 attributePaths에 넣으면 `MultipleBagFetchException`이 터지니 `Set`을 쓰거나 컬렉션 중 하나만 EntityGraph에 포함시켜야 한다.

> 💡 **왜 중요한가**: JPQL `fetch join`은 강력하지만 "쿼리 메서드"에는 붙일 수 없다 — `@EntityGraph`는 Spring Data JPA의 파생 쿼리에도 N+1 해결책을 붙일 수 있는 유일한 선언적 도구다.
