### 1. `Dispatchers.IO` vs `Dispatchers.Default`: "스레드 풀 크기"가 아니라 "블로킹을 허용하느냐"의 차이

`Dispatchers.Default`는 CPU 코어 수(최소 2개)만큼의 스레드로 **CPU-bound 연산**을 처리하도록 설계됐고, `Dispatchers.IO`는 기본 64개(혹은 코어 수 중 큰 값) 한도로 **블로킹 I/O**를 격리하도록 설계됐다. 둘은 실제로 같은 백엔드 스레드 풀을 공유하지만 `limitedParallelism`으로 동시 실행 한도만 다르게 걸어둔 구조라, `withContext(Dispatchers.IO)` 전환의 본질은 "새 스레드를 만드는 비용"이 아니라 **"블로킹이 허용된 격리 영역으로의 이동"**이다. JDBC 호출이나 `File.readText()`를 `Default`에서 돌리는 순간 CPU 스레드가 전부 묶이면서 다른 코루틴이 기아 상태에 빠진다.

```
Dispatchers.Default  ──► 코어 수(최소 2)    ──► CPU 연산 (논블로킹 전제)
Dispatchers.IO       ──► 최대 64+           ──► 블로킹 I/O 격리
       └───────── 같은 백엔드 풀, limitedParallelism만 다름 ─────────┘

❌ withContext(Default) { jdbc.query(...) }     ← CPU 스레드 전체가 블로킹됨
✅ withContext(Dispatchers.IO) { jdbc.query(...) }
```

> 💡 **왜 중요한가**: 코루틴 기반 서버에서 블로킹 코드를 `Default`에 올리는 한 줄이 "전체 이벤트 루프 정지"로 번지고, 장애 리포트에는 "Dispatcher 하나 바꿨더니 해결됨"으로 남는다.

### 2. Kotlin 클래스의 기본은 `final`: Spring이 왜 `kotlin-spring` 플러그인을 요구하는가

Kotlin은 Java와 달리 `class` 선언만으로 자동으로 `final`이 붙어 상속·오버라이드가 금지된다 — Effective Java의 **"상속을 설계하지 않았다면 금지하라"**를 언어 차원에서 강제한 것이다. 그런데 Spring의 `@Transactional`, `@Cacheable`, `@Async`는 CGLIB으로 **서브클래스 프록시**를 만들어 메서드를 오버라이드해야 동작하기 때문에, `final` 클래스에서는 기동 시점에 `Cannot subclass final class` 예외가 터지거나 조용히 프록시가 비활성화된다. `kotlin-spring` 컴파일러 플러그인은 `@Component`, `@Transactional`, `@Configuration` 등이 붙은 클래스/멤버에만 **컴파일 타임에 `open`을 자동 주입**해 이 충돌을 해결한다.

```
class UserService { ... }
    │
    ├─ 그냥 둠         →  final (상속 불가)  →  @Transactional 프록시 실패
    │
    ├─ open 수동 선언  →  모든 상속 허용      →  테스트에서 전 메서드 mocking 가능
    │                                           (의도치 않은 확장점 노출)
    │
    └─ kotlin-spring   →  애너테이션 붙은 곳만 선택적 open  ← ✅ 권장
       플러그인           (컴파일러가 바이트코드 수준에서 변환)
```

> 💡 **왜 중요한가**: `build.gradle.kts`에서 `kotlin("plugin.spring")` 한 줄이 빠진 프로젝트에서는 `@Transactional`이 **문자 그대로 "주석"**이 되어, 예외가 발생해도 커밋이 롤백되지 않고 조용히 성공한다.
