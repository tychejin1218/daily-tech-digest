### 1. Class-File API로 바이트코드를 표준 API로 직접 다루기 (Java 24 정식)

`java.lang.classfile` 패키지의 Class-File API를 사용하면 ASM, Javassist 같은 외부 라이브러리 없이 JDK 표준 API만으로 클래스 파일을 파싱·생성·변환할 수 있습니다. `ClassFile.of().build()`로 메서드와 필드를 람다 기반 빌더로 선언하고, `transformClass()`로 기존 바이트코드를 스트림처럼 변환하는 패턴이 가능합니다. JDK 내부에서도 lambda metafactory 등이 점진적으로 이 API로 마이그레이션되고 있어, JVM 버전 변경에 따른 ASM 호환성 문제에서 자유로워집니다.

> 💡 **왜 중요한가**: 프레임워크나 APM 에이전트가 외부 의존성 없이 안정적으로 바이트코드 조작을 수행할 수 있어, JDK 업그레이드 시 발생하던 ASM 버전 충돌 문제를 근본적으로 해결합니다.

### 2. `StructuredTaskScope`로 동시 작업의 생명주기를 부모-자식 관계로 묶어 관리하기 (Java 25 정식)

Structured Concurrency는 여러 Virtual Thread를 하나의 단위로 묶어, 부모 스코프가 종료되면 자식 작업도 함께 정리되도록 보장하는 동시성 모델입니다. `StructuredTaskScope.open()`으로 스코프를 열고 `fork()`로 작업을 제출한 뒤 `join()`을 호출하면, 한 작업이 실패할 때 형제 작업을 자동 취소하거나(`Joiner.anySuccessfulResultOrThrow`) 모든 결과를 수집하는(`Joiner.allSuccessfulOrThrow`) 정책을 선언적으로 적용할 수 있습니다. try-with-resources와 결합되어 스레드 누수와 좀비 작업이 구조적으로 차단됩니다.

```java
try (var scope = StructuredTaskScope.open(Joiner.<String>anySuccessfulResultOrThrow())) {
    scope.fork(() -> fetchFromPrimary());
    scope.fork(() -> fetchFromReplica());
    return scope.join();  // 먼저 성공한 결과 반환, 나머지는 자동 취소
}
```

> 💡 **왜 중요한가**: `ExecutorService` 기반 코드에서 흔히 발생하던 "한 작업이 실패해도 다른 작업은 계속 실행되는" 자원 낭비와 디버깅 난이도를 제거하고, 동시 작업의 에러 전파를 호출 스택처럼 명확하게 만듭니다.
