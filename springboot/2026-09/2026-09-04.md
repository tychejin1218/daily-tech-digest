### `@Transactional`의 기본 `rollbackFor`는 `RuntimeException`뿐 — `IOException` 던지면 커밋된다

`@Transactional`은 기본적으로 `RuntimeException`과 `Error`만 롤백한다. 즉 `throws IOException`, `throws SQLException` 같은 **체크 예외(Checked Exception)**는 아무리 예외를 던져도 트랜잭션이 **커밋**된다. 파일 업로드 실패, 외부 API 호출 실패 후 "DB엔 저장됐네?" 하는 지옥의 근원이 여기다.

```java
@Transactional
public void saveWithUpload(Order order) throws IOException {
    orderRepository.save(order);      // DB 저장
    fileUploader.upload(order);       // IOException 발생
    // → order는 커밋된다. 파일은 없다. 데이터 정합성 붕괴
}

// 해결: rollbackFor를 명시하거나 RuntimeException으로 감싸라
@Transactional(rollbackFor = Exception.class)
public void saveWithUpload(Order order) throws IOException { ... }
```

동작 흐름:
```
[Service 호출]
    ↓
[TransactionInterceptor] → 트랜잭션 시작
    ↓
[비즈니스 로직 실행]
    ↓
    ├─ RuntimeException → rollback ✅
    ├─ Error           → rollback ✅
    └─ Checked Exception → COMMIT ❌ (기본 동작)
```

**실제 사례**: 결제 서비스에서 "카드 승인 → DB 저장 → 영수증 PDF 생성(IOException 던짐)" 순서로 짜여 있었는데, PDF 실패 시 결제는 DB에 저장되고 사용자는 영수증을 못 받는 상황이 반복됐다. 원인은 이 조용한 기본값.

**트레이드오프**: `rollbackFor = Exception.class`로 전역 통일하면 안전하지만, 팀에 따라 "체크 예외는 복구 가능해야 한다"는 원칙과 충돌할 수 있다. 대안은 **아키텍처 규칙**으로 서비스 계층에선 체크 예외를 던지지 않도록 강제하는 것(unchecked로 래핑).

> 💡 **왜 중요한가**: Spring의 기본 롤백 정책은 "예외 = 롤백"이라는 개발자의 직관과 정반대이며, 데이터 정합성이 조용히 무너지는 지점이다.

### `@Transactional`은 `private` 메서드에 붙여도 동작하지 않는다 — 프록시가 볼 수 없다

Spring AOP는 기본적으로 **JDK 동적 프록시** 또는 **CGLIB 서브클래스 프록시**로 동작한다. 두 방식 모두 **외부에서 호출되는 `public` 메서드**만 인터셉트할 수 있다. `private`, `protected`, `package-private` 메서드에 `@Transactional`을 붙이면 어노테이션은 무시되고 **트랜잭션 없이** 그냥 실행된다. 컴파일 에러도, 런타임 경고도 없다. 조용히 실패한다.

```java
@Service
public class OrderService {
    @Transactional
    public void placeOrder(Order o) {
        saveInternal(o);  // ← 프록시 우회 (같은 클래스 내부 호출)
    }

    @Transactional  // ← 이 어노테이션은 절대 동작하지 않는다
    private void saveInternal(Order o) {
        repository.save(o);
    }
}
```

프록시 구조:
```
[클라이언트]
    ↓
[Spring 프록시 객체] ← @Transactional 인터셉트 지점 (public만!)
    ↓ (this 참조로 우회 가능)
[실제 OrderService 인스턴스]
    ├─ public placeOrder()   → 프록시 통과 ✅
    └─ private saveInternal() → 프록시 도달 불가 ❌
```

**해결책 3가지**:
1. `public`으로 바꾼다 (가장 단순).
2. 별도 빈으로 분리해 주입받는다 (`this.saveInternal()` → `internalService.save()`).
3. **AspectJ 컴파일 타임 위빙**을 쓴다 — 프록시가 아닌 바이트코드 조작이라 `private`도 가능. 단, 빌드 복잡도가 급증.

**실제 사례**: "리팩터링하면서 내부 헬퍼 메서드를 `private`으로 바꿨더니, 그날 밤부터 특정 API의 데이터가 반쯤만 저장되기 시작했다"는 장애 리포트가 이 패턴의 전형이다. 테스트에선 안 잡힌다 — 단위 테스트는 프록시를 거치지 않으니까.

**트레이드오프**: `public`을 남발하면 캡슐화가 깨진다. 그렇다고 별도 빈으로 뽑으면 클래스가 폭발적으로 늘어난다. 실무에선 **"트랜잭션 경계는 서비스의 public API에서만 시작한다"**는 팀 규칙으로 못박는 게 가장 깔끔하다.

> 💡 **왜 중요한가**: `@Transactional`이 조용히 무시되는 대표적인 지점이며, 정적 분석 도구 없이는 발견하기 어렵다.
