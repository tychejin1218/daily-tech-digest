### 1. `ScopedValue.where(KEY, value).run(task)` (Java 25 정식, JEP 506)로 요청 컨텍스트 전파할 때 `ThreadLocal.set()` + `try { ... } finally { threadLocal.remove(); }` 관성 벗어나기

가상 스레드 수백만 개 환경에서 `ThreadLocal`은 메모리 누수 위험 + 스레드당 복사 비용이 치명적이다. `ScopedValue`는 불변(immutable) + 스코프 종료 시 자동 해제 + 자식 스레드(`StructuredTaskScope`)로 상속까지 되는데, `remove()` 깜빡해서 재사용된 스레드에 이전 요청 데이터가 남는 고전적 버그가 구조적으로 불가능해진다. 특히 `StructuredTaskScope`와 세트로 쓰면 자식 가상 스레드에서도 추가 비용 없이 읽을 수 있어서, 요청 ID·사용자 정보·트랜잭션 컨텍스트 전파의 정석이 된다.

```java
// Before: ThreadLocal 관성
private static final ThreadLocal<String> REQUEST_ID = new ThreadLocal<>();

void handle(Request req) {
    REQUEST_ID.set(req.id());
    try {
        processOrder();  // 내부에서 REQUEST_ID.get() 호출
    } finally {
        REQUEST_ID.remove();  // 빠뜨리면 스레드 풀 재사용 시 누수
    }
}

// After: ScopedValue - 불변 + 자동 해제
private static final ScopedValue<String> REQUEST_ID = ScopedValue.newInstance();

void handle(Request req) {
    ScopedValue.where(REQUEST_ID, req.id())
        .run(() -> processOrder());  // 블록 끝나면 자동 해제, 재바인딩 불가
}

void processOrder() {
    log.info("Processing {}", REQUEST_ID.get());  // 스코프 안에서만 읽힘
}
```

> 💡 **왜 중요한가**: 가상 스레드 시대에 `ThreadLocal`은 "스레드 1:1 자원"이라는 전제 자체가 깨져서 비용·누수 리스크가 커졌고, `ScopedValue`는 그 전제를 "스코프 1:1 자원"으로 바꿔 구조적으로 안전하게 만든다.

### 2. `Objects.requireNonNullElseGet(obj, supplier)` (Java 9 정식)로 기본값 계산이 비싼 경우 `obj != null ? obj : expensiveDefault()` 삼항 연산 관성 벗어나기

`Objects.requireNonNullElse(obj, default)`는 기본값을 **즉시 평가**하기 때문에, 기본값 생성이 비싼 경우(DB 조회, 객체 생성, 리스트 복사 등) 불필요한 비용을 매번 치른다. `requireNonNullElseGet`은 `Supplier`를 받아서 `obj`가 `null`일 때만 lazy 평가한다. `Optional.ofNullable(obj).orElseGet(...)` 쓰려고 `Optional` 래핑하는 것보다 간결하고, 삼항 연산자처럼 조건식 안에 메서드 호출을 중복으로 쓸 필요도 없다.

```java
// Before: 삼항 연산 — 가독성 떨어지고 obj 두 번 평가하면 사이드이펙트 위험
Config config = loadConfig();
List<Rule> rules = config.getRules() != null 
    ? config.getRules() 
    : fetchDefaultRulesFromDb();  // 조건 분기 확실하지만 verbose

// Before: Optional 우회
List<Rule> rules = Optional.ofNullable(config.getRules())
    .orElseGet(this::fetchDefaultRulesFromDb);  // Optional 래핑 오버헤드

// After: Objects.requireNonNullElseGet — 의도가 명확
List<Rule> rules = Objects.requireNonNullElseGet(
    config.getRules(),
    this::fetchDefaultRulesFromDb  // null일 때만 호출
);

// 주의: 아래는 비싼 호출을 항상 실행한다 — 안티패턴
List<Rule> rules = Objects.requireNonNullElse(
    config.getRules(),
    fetchDefaultRulesFromDb()  // 매번 실행됨!
);
```

> 💡 **왜 중요한가**: "null이면 기본값"이라는 흔한 패턴에서 기본값 계산 비용을 눈치 못 채고 매번 치르는 버그가 생각보다 많고, `requireNonNullElseGet`은 lazy 평가 의도를 코드에 명시적으로 박아 넣어 리뷰어가 바로 알아보게 한다.
