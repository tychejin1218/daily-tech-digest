### 1. Spring Boot의 `@Transactional`은 **자기 자신을 호출(self-invocation)할 때 프록시를 거치지 않아 트랜잭션이 적용되지 않는다** — 그래서 같은 클래스의 `public` 메서드 A가 `public` 메서드 B를 `this.B()`로 호출하면, B에 붙은 `@Transactional`은 "분명히 선언했는데도" 작동하지 않는다

Spring AOP는 **런타임 프록시 객체**가 메서드 호출을 가로채서 트랜잭션, 캐시, 비동기 등의 부가 기능을 끼워 넣는 구조다. 그런데 `this.method()` 호출은 프록시가 아닌 **실제 객체의 메서드를 직접 호출**하기 때문에, 그 사이에 끼어들 틈이 없다. 해결하려면 자기 자신을 `@Autowired`로 주입받아 `self.method()`로 호출하거나, `AopContext.currentProxy()`를 쓰거나, 아예 다른 빈으로 분리해야 한다.

```java
@Service
public class OrderService {
    @Transactional
    public void outer() {
        this.inner(); // ❌ inner()의 @Transactional은 무시됨
    }

    @Transactional(propagation = REQUIRES_NEW)
    public void inner() { ... }
}
```

> 💡 **왜 중요한가**: "분명히 `@Transactional`을 붙였는데 왜 롤백이 안 되지?"의 90%는 self-invocation 문제이고, 이걸 모르면 AOP 기반 어노테이션 전체를 신뢰할 수 없게 된다.

### 2. Spring Boot의 `BeanPostProcessor`는 **일반 빈보다 먼저 생성되기 때문에, 여기에 다른 빈을 `@Autowired`로 주입받으면 그 빈은 AOP/프록시가 적용되지 않은 "날것" 상태로 들어온다**

`BeanPostProcessor`는 모든 빈의 초기화 과정에 개입하는 "메타 빈"이므로, Spring은 이것을 **컨테이너가 다른 빈들을 만들기 전에 먼저 등록**한다. 문제는 이 시점에 주입된 의존성은 아직 다른 `BeanPostProcessor`(예: `AnnotationAwareAspectJAutoProxyCreator`)를 거치지 않은 원본 객체라는 것이다. 그래서 여기 주입된 `UserService`에 `@Transactional`이 있어도 트랜잭션이 열리지 않고, "왜 내 Aspect가 안 걸리지?"라는 미궁에 빠진다.

```java
@Component
public class MyPostProcessor implements BeanPostProcessor {
    @Autowired
    private UserService userService; // ❌ 프록시 없는 날것

    @PostConstruct
    public void init() {
        userService.doWork(); // @Transactional 안 걸림
    }
}
```

> 💡 **왜 중요한가**: `BeanPostProcessor`나 `BeanFactoryPostProcessor` 안에서 다른 빈을 주입받아 쓰는 건 "컨테이너 부트스트랩 순서"를 거스르는 짓이고, 이걸 모르면 Aspect가 조용히 증발하는 디버깅 지옥이 열린다.
