### 1. PostgreSQL 19 GA + pgai 2.0 공개 — '벡터 DB 춘추전국'이 Postgres 한 줄 안으로 접혔다, 'RAG = 전용 인프라 3개 쌓기'라는 2024년 상식이 드디어 무너졌다
PostgreSQL 19가 정식 릴리즈되면서 Timescale 주도 확장 `pgai 2.0`이 네이티브 벡터 인덱스(DiskANN 기반), SQL 안에서의 LLM 호출(`ai.generate()`, `ai.embed()`), 그리고 에이전트용 비동기 작업 큐를 한 번에 묶어 GA로 넘어왔다. 핵심은 "임베딩 → 검색 → 생성 → 상태 저장"의 전 구간을 **`psql` 세션 하나**로 끝낼 수 있게 된 것 — Pinecone·Weaviate·Redis·Postgres를 각각 운영하던 전형적인 RAG 스택이 'Postgres 하나 + S3 백업'으로 축소된다. 트레이드오프는 명확하다: 추론 QPS가 높아지면 OLTP 워크로드와 GPU/CPU를 공유하면서 **커넥션 풀이 가장 먼저 비명을 지른다**. 멀티테넌시 SaaS에서는 여전히 추론 전용 복제본(replica)이 필요하고, 'Postgres로 다 한다'는 '인덱싱 테이블 vs 소스 테이블 분리' 설계 숙제를 그대로 남긴다.

```
[2024년 RAG 스택]              [2026년 pgai 2.0 스택]
App → Embedding API            App
    → Pinecone(검색)              ↓
    → Redis(세션)             PostgreSQL 19
    → PG(원본)                  ├─ pgvector + DiskANN
    → OpenAI(생성)              ├─ ai.generate() / ai.embed()
                                └─ pgmq (에이전트 작업 큐)
```

> 💡 **왜 중요한가**: RAG 아키텍처의 '디폴트 다이어그램'이 4박스에서 1박스로 접히는 순간, 신규 스타트업의 인프라 비용 바닥과 시니어 백엔드의 '벡터 DB 운영 경력'이라는 간판이 동시에 깎인다.

### 2. Nvidia 'Dynamo Inference Framework' + 'NIM 2.0' 동시 GA — LLM 서빙이 '한 덩어리 거대 프로세스'에서 '마이크로서비스 그래프'로 쪼개졌다, 추론 레이턴시 튜닝이 드디어 '네트워크 스택 문제'가 됐다
Nvidia가 오늘 Dynamo 1.0을 GA로 올리면서 디스어그리게이션(disaggregation) 설계를 디폴트로 못박았다 — **프리필(prefill)**, **디코드(decode)**, **KV 캐시 스토어**, **라우터**를 서로 다른 GPU 풀·심지어 다른 노드에 배치하고, 요청을 투입 토큰 길이·KV 재사용 가능성에 따라 자동 라우팅한다. NIM 2.0은 이 조각들을 `Deployment` 단위 컨테이너로 패키징해서 Kubernetes 위에서 **vLLM/TensorRT-LLM/SGLang을 한 매니페스트로 섞어 쓸 수 있게** 만들었다. 실제 벤치에선 동일 H200 8장 기준 Llama-5-405B의 TTFT가 단일 서빙 대비 ~2.3배 빨라졌지만, 핵심 비용은 **노드 간 NVLink/InfiniBand KV 전송량**이 늘어나면서 네트워크 토폴로지가 서빙 설계 1급 변수로 올라왔다는 점이다. 'LLM 서빙 = 모델 파일 + GPU 1대' 시대의 멘탈 모델은 끝났고, 이제 SRE가 **TCP 윈도우·RDMA 큐 깊이**를 튜닝해야 한다.

> 💡 **왜 중요한가**: '백엔드 엔지니어의 네트워크 지식'이 다시 1등석에 앉았다 — 10년간 관리형 PaaS가 숨겨놨던 L3/L4 튜닝 능력이, 하필이면 가장 비싼 워크로드인 LLM 서빙에서 다시 승패를 가르기 시작했다.

### 3. Datadog 'Bits AI SRE Agent' GA + Grafana 'LLM Investigation' 동시 공개 — 옵저버빌리티가 '사람 대시보드'에서 '에이전트의 눈'으로 자리를 옮겼다, MTTR 단축이 '알람 튜닝'이 아니라 '에이전트 프롬프트 튜닝' 문제가 됐다
Datadog이 Bits AI SRE Agent를 GA로 올리면서, PagerDuty 알람 → 로그·메트릭·트레이스 자동 조사 → Runbook 실행 → 1차 완화(스케일아웃·롤백) → 포스트모템 초안까지의 **온콜 플레이북 전 과정**을 에이전트가 수행한다고 발표했다. 같은 날 Grafana도 LLM Investigation을 공개하며 PromQL/LogQL을 사람이 짜는 게 아니라 '증상 자연어' → 쿼리 자동 생성 → 상관관계 그래프로 대체했다. 실전 현장에서 보고된 패턴은 둘로 갈린다 — **1차 심야 호출이 85% 감소**했지만, 에이전트가 '의심 가설'을 좁히지 못하는 긴 꼬리(long-tail) 장애에선 오히려 **사람 온콜이 에이전트의 추론 로그 수십 페이지를 역으로 읽어야** 하는 새 작업이 생겼다. SRE의 가치가 '빠른 추론'에서 '에이전트 프롬프트 설계 + 실패 가설 라이브러리 관리'로 이동한다.

```
[기존 온콜]                   [Bits AI SRE 2026]
PagerDuty 알람                알람 → Agent 자동 조사
  → 사람이 대시보드 10개 뒤짐    → 쿼리/로그/트레이스 자동 상관
  → PromQL 수기 작성            → 1차 완화(스케일/롤백) 실행
  → 가설 세우고 롤백            → Slack에 '증상/원인/조치' 리포트
  → 포스트모템 수기              → 사람은 '승인'만
MTTR: 42분                    MTTR: 8분 (단, 꼬리 장애 90분↑)
```

> 💡 **왜 중요한가**: '시니어 SRE'의 정의가 조용히 바뀌는 중 — 이제는 '얼마나 빨리 PromQL을 치느냐'가 아니라 '에이전트가 잘못된 가설에 꽂혔을 때 얼마나 빨리 궤도 수정 프롬프트를 던지느냐'가 연봉을 가른다.
