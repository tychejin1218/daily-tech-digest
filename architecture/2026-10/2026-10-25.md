### 프롬프트 버저닝 & 롤백 (Prompt Versioning) — "Git에 커밋해두면 되지"라는 순진함, 그리고 새벽 2시 "그때 그 프롬프트" 못 찾아 되돌리지 못한 토요일

---

#### 리드 사건

금요일 18:47. 상담 챗봇 담당 ML 엔지니어 A가 `prompts/refund_v3.md`의 두 번째 문장 "환불 가능 여부를 먼저 안내해주세요"를 "환불 조건을 상세히 설명한 뒤 가능 여부를 안내해주세요"로 수정한다. PR을 올리고, 오프라인 평가셋 100건에서 Golden Match 94% → 95%가 나오자 머지한다. 20:12 배포. 주말 사이 챗봇은 조용히 돈다.

토요일 02:14. 결제팀 온콜이 PagerDuty를 받는다. 환불 세션당 평균 토큰이 1,840 → 3,620으로 뛰면서 Azure OpenAI 분당 TPM(Tokens Per Minute) 할당량이 터져 챗봇 응답 지연이 p99 32초. CS 야간팀 수신 민원이 평시 대비 7배.

롤백해야 한다. A에게 전화. "방금 전 프롬프트로 되돌릴 수 있나?"

A가 Git을 연다. 금요일 PR은 머지되어 있다. `git revert`를 돌리고 재배포한다 — 그런데 챗봇 Pod 20개는 **런타임에 Confluence의 "최신 승인본" 페이지를 폴링**해서 프롬프트를 로드하도록 되어있다. 2주 전 "운영팀이 코드 배포 없이 프롬프트 고치고 싶다"는 요구로 B가 급히 추가했던 경로다. Confluence 페이지에는 금요일 수정본만 있고, 수정 이력은 "최근 50건"만 남은 채 그 전 버전은 이미 잘려나갔다.

A는 Slack `#chatbot-ops` 채널의 2주 전 스크린샷을 뒤진다. 이미지에 담긴 프롬프트 중간이 말풍선 꼬리에 가려 보이지 않는다. 03:40, 결국 직전 모델 체크포인트 GPT-4o-2024-11-20을 2024-08-06으로 함께 되돌리면서 "그때쯤 돌던 비슷한 프롬프트"를 수기로 재구성해 올린다. 민원은 05:20에 평시로 돌아온다.

월요일 오전 포스트모템.

- **1차 원인**: 프롬프트 수정이 토큰 사용량에 미치는 영향을 오프라인 평가셋이 측정하지 않았다 (LLM Eval 이슈)
- **2차 원인**: 프롬프트의 **"배포된 바로 그 바이트열"**을 복원할 수 없었다 — Git과 런타임 소스가 분리되어 있었다
- **3차 원인**: 프롬프트와 모델 버전이 **독립적으로 배포**되고 있어서 "어떤 조합이 돌고 있었는지" 재구성이 불가능

이 글은 2·3차 원인에 대한 이야기다. "프롬프트는 Git에 커밋하면 끝"이 아닌 이유.

---

#### 왜 Git 커밋만으로는 부족한가

"프롬프트도 코드다, Git에 넣고 PR로 리뷰해라"는 2024년 베스트 프랙티스였다. 이는 **필요조건이지만 충분조건이 아니다**. 백엔드 시니어 관점에서 프롬프트는 "코드"보다 **"스키마 마이그레이션"**에 더 가깝다 — 바뀌는 순간 돌아가고 있는 모든 트래픽의 거동이 바뀌고, 이전 상태로의 역호환이 자동으로 보장되지 않는다.

Git 커밋만 믿었을 때 깨지는 4가지 가정:

| 가정 | 현실 |
|------|------|
| ① "코드 리포지의 `main` HEAD가 운영에 배포된 버전이다" | 런타임이 외부 소스(Confluence, DB, S3, Prompt Hub)에서 로드하면 Git은 **스냅샷 히스토리의 일부**일 뿐 |
| ② "`git revert` 하면 운영이 돌아간다" | 모델 버전·툴 스키마·시스템 메시지·few-shot 예시가 **독립 축**으로 변했으면 "그때의 조합"은 복원 불가 |
| ③ "변경 임팩트는 PR diff로 보인다" | 토큰 비용·레이턴시·거절률·Jailbreak 성공률 — 전부 **런타임에서만** 드러남 |
| ④ "리뷰어 2명이 LGTM 하면 안전하다" | 프롬프트는 자연어 — LGTM이 **의미**를 승인한 것이지 **분포**를 승인한 게 아님 |

바꿔야 할 멘털 모델: 프롬프트는 "텍스트 파일"이 아니라 **(prompt_text, model_id, tool_schema, params, few_shots)의 불변 튜플**이며, 각 튜플은 전역 고유 ID(`prompt_v142_gpt4o-2024-11-20_tools@3`)로 식별되어야 하고, **런타임이 요청마다 어떤 ID를 썼는지 로그에 남겨야** 한다.

**핵심 분리**:
- **"프롬프트 코드"(Git)** = 리뷰·협업·블레임을 위한 소스
- **"프롬프트 아티팩트"(Registry)** = 런타임이 로드하는 **불변 바이트열 + 해시**
- **"프롬프트 포인터"(Tag)** = `@prod`, `@staging`, `@canary-10` — 런타임이 참조하는 **움직이는 라벨**

이 세 축을 분리하면: Git은 코드 리뷰 소스, Registry는 서빙 소스, Tag는 "지금 이 환경에서 돌 버전"을 가리키는 포인터. 롤백은 Git revert가 아니라 **"@prod 태그를 이전 아티팩트 ID로 재지정"**하는 1-click 작업이 된다.

---

#### 핵심 설계 요소 5가지

**1. 불변 아티팩트 ID**
`sha256(prompt_text + system_message + tool_schema_json + model_id + temperature + top_p + stop_sequences + few_shot_examples)`를 아티팩트 ID로 쓴다. 한 바이트라도 바뀌면 새 ID. 운영 로그엔 매 요청마다 이 ID가 찍혀야 한다 — 사후 재현의 유일한 보증.

**2. 모델/프롬프트 공동 버저닝**
`prompt@142` + `model=claude-sonnet-4-6` + `tool_schema@7` 조합을 **릴리스 번들**로 묶는다. GPT-4o Nov → GPT-4o Aug로 모델을 롤백할 때 프롬프트까지 자동으로 당시 매칭 버전으로 되돌아간다. 넷플릭스가 Metaflow에서 모델 아티팩트에 하는 것과 같은 발상.

**3. 런타임이 Registry에서 Pull (코드 재배포 없이)**
`PromptClient.get("refund_handler", env="prod")` → Registry가 현재 `@prod` 태그가 가리키는 불변 아티팩트 리턴. 애플리케이션은 아티팩트 ID만 캐시하고, 캐시 TTL 60초 이내로 Rolling. 코드 배포 없이 1-click rollback이 가능해지는 조건.

**4. Shadow / Canary 라우팅은 Gateway 레이어에서**
"프롬프트 v141 vs v142를 10%로 쪼개 비교"는 애플리케이션 코드가 아니라 [[llm-gateway]] 레이어에서 수행한다. 애플리케이션은 `generate(intent="refund", session=...)`만 호출. Gateway가 세션 해시로 버킷팅하고, 두 버전 응답을 쉐도우 비교(동일 입력에 대한 응답 유사도, 토큰 비용, 거절률)해서 메트릭을 Prom으로 쏜다.

**5. 블랙박스 Guardrail**
배포 전 반드시: ① **거절률 변화**(이전 대비 ±3%p 이상 이동 시 자동 홀드), ② **토큰 사용량 분포**(p95 +30% 이상 시 홀드 — 금요일 사건의 핵심), ③ **Jailbreak Red Team 셋 200개 재통과**. 셋 중 하나라도 깨지면 머지 자체를 블록.

#### 트레이드오프

| 항목 | Git-only (순진한 접근) | Prompt Registry (분리) |
|------|------|------|
| 셋업 비용 | 0 (리포지만 있으면) | Registry + Gateway + 로깅 파이프라인 설치 |
| 롤백 시간 | 10~20분 (재빌드) | 2~5초 (태그 재지정) |
| 재현성 | 애매함 (런타임 로드 소스 분리 시 불가) | 완벽 (아티팩트 해시로 바이트 일치 보장) |
| 비개발자 수정 | 불가 (PR 권한 필요) | 가능 (Registry UI 권한만 부여) ↔ **거버넌스 리스크** |
| 조직 의존도 | 낮음 | 높음 (Registry가 SPOF, 가용성 설계 필수) |
| 비용 | 저장소 비용만 | Registry/Gateway 운영비 + 벤더 종속(LangSmith/Vellum/Humanloop) |
| 리뷰 흐름 | Git PR = 자연스러움 | PR + Registry 승격 2단계 → 리뷰 피로도 ↑ |

**가장 자주 걸리는 함정**: Registry를 도입했는데 애플리케이션이 여전히 Fallback으로 "코드 번들된 프롬프트"를 쓰는 코드 경로가 남아있는 경우. Registry 장애 시 두 소스가 섞여 돌아가고 사후 재현 불가 상태가 된다. **Registry가 다운되면 서비스를 중단시키거나(fail-close), Registry 응답을 로컬 디스크에 **버전 해시와 함께** 캐시(fail-open)해야 한다. 어느 쪽을 선택할지는 비즈니스 결정이지만 결정 자체는 반드시 명시해야 한다.

#### 실제 사례

- **Notion AI (2024~)**: 자체 "Prompt Hub" 운영. 매 요청마다 `prompt_sha`를 트레이스에 기록. 2024년 중반 요약 품질 저하 리포트 때 **12분 만에 2주 전 버전으로 롤백** — 이 사건을 기점으로 "프롬프트 변경도 Change Management 승인 대상"으로 격상.
- **Shopify Sidekick**: Vellum을 Prompt Registry로 사용. 모든 모델 호출을 자체 LLM Gateway 뒤에 두고, Shopify Data Platform에 `prompt_version × model_version × merchant_segment` 셀 단위로 CSAT·거절률·토큰비용 측정. 2025년 Mercury 결제 통합 시 **프롬프트 A/B를 120개 머천트 서브셋에 쉐도우로만** 돌린 뒤 승격.
- **GitHub Copilot (내부 자료 기준)**: `copilot-metrics` 파이프라인이 모든 요청에 `prompt_variant_id`를 태깅. 2024년 Claude 모델 라우팅 추가 시 **프롬프트 버전과 모델 라우트를 동일 릴리스 번들로 관리**해 "어떤 사용자가 어떤 조합을 받았는지" 재현 보장.
- **LinkedIn (Generative AI Assistant)**: 자체 "AI Workbench"에서 프롬프트를 버전 관리하되, 운영 배포는 반드시 **Experimentation Platform**을 거치도록 강제. 데이터 사이언스팀이 블랙박스 메트릭(engagement, downstream conversion)으로 승인하기 전엔 Gateway가 10% 이상 트래픽을 신버전에 보내지 않음.

**공통 패턴**: 단일 벤더 솔루션이 없다 — 모두 **Registry(SaaS 또는 자체) + Gateway + Observability**의 삼각 구조로 가고 있다. 벤더 선택보다 **"프롬프트가 애플리케이션 바이너리 바깥에서 서빙된다"**는 아키텍처적 결정이 본질.

#### 언제 쓰고 언제 쓰면 안 되는가

**써야 할 때**
- 운영 트래픽이 하루 10만 콜 이상인 LLM 서비스 (롤백 1분 지연 = CS 민원 수십 건)
- 비개발자(운영/QA/도메인 전문가)가 프롬프트를 자주 수정하는 조직
- 멀티 모델 라우팅(Claude/GPT/Gemini)을 운영하거나 할 예정
- 규제 산업(금융/의료) — "그 날 그 시점에 서빙된 바로 그 프롬프트"의 감사 추적이 요구됨
- A/B 테스트, Shadow 비교, Canary를 상시 돌리는 조직

**쓰지 말아야 할 때**
- 프롬프트가 1~2개뿐이고 월 변경이 1건 미만인 사내 도구 — 오버엔지니어링
- 트래픽 전체가 배치(Batch)로 돌고 사용자 실시간 노출이 없는 경우 — Git + CI로 충분
- 팀이 3명 미만, 모델 1개, 프롬프트 변경 == 앱 배포가 자연스러운 PoC 단계 — Registry가 또다른 SPOF가 됨
- Registry 벤더(LangSmith/Vellum/Humanloop) 중 하나에 종속되는 것을 조직이 받아들일 수 없는데 자체 구축할 리소스도 없는 경우 — 어설픈 자체 구현이 장애의 원점이 됨

**경계선**: "오프라인 평가셋만 통과하면 Git PR 머지 즉시 운영 반영"이 지금의 흐름이라면, 다음 사고가 터지는 것은 시간문제다. 금요일 밤 수정한 한 줄이 토큰 비용을 2배로 올렸을 때 **"지난 금요일 저녁 7시 48분에 서빙되던 바로 그 프롬프트 바이트열"**을 2초 안에 되돌릴 수 있는지가 성숙도 지표다.

---

> 💡 **왜 중요한가**: 프롬프트는 자연어라서 "리뷰로 안전해진다"는 착각을 주지만, 실제로는 모든 요청의 거동을 바꾸는 스키마 마이그레이션에 가깝다 — Git 커밋이 아니라 **불변 아티팩트 + 움직이는 태그 + 1-click 롤백**이 필요하다.
