### Semantic Cache — "똑같은 질문엔 캐시에서 꺼내면 되지"라는 순진함, 그리고 "환불 기간 얼마인가요?"와 "교환 기간은요?"의 코사인 유사도가 0.94가 나와 교환 고객 1,847명에게 "7영업일 내 환불됩니다"가 그대로 뿌려진 블랙프라이데이 새벽

> 전제: 여러분은 이미 **LLM Gateway**를 뚫어서 모든 호출을 한 레이어로 모았고, **LLM Routing**으로 비용/품질을 라우팅하며, **AI Observability**로 trace를 수집하고 있습니다. 그래서 월말 청구서에서 "같은 질문이 반복해서 들어오는데 매번 GPT-4o를 때리고 있다"는 걸 발견한 상태입니다. 이제 그 반복 호출을 캐시로 막아야 합니다.

---

#### 0. 그 새벽의 사고 — 왜 이 글이 필요한가

2026년 블랙프라이데이 새벽 3시, 국내 D 커머스의 CS 챗봇은 평소의 7배인 분당 2,400 QPS를 받고 있었다. GPT-4o 비용이 시간당 $380 찍히는 걸 본 백엔드 리드는 급하게 **Semantic Cache**를 켰다. Redis + 임베딩 유사도 0.9 이상이면 캐시 히트.

처음 2시간은 완벽했다. 캐시 히트율 68%, 비용은 1/3로 떨어졌다. 그런데 5시 47분부터 CS 센터에 "환불된다고 해놓고 왜 물건이 왔냐"는 전화가 쌓이기 시작했다.

원인: 사용자 A가 "환불 처리 기간은 얼마나 걸리나요?"로 물었고, 봇은 RAG로 "환불 정책 7영업일"을 답했다. 캐시에 저장. 사용자 B가 "교환 처리 기간은 얼마나 걸리나요?"로 물었을 때, 두 임베딩의 코사인 유사도는 **0.942**. 임계값 0.9를 가뿐히 넘겼다. 봇은 환불 답변을 그대로 뿌렸다.

4시간 동안 **1,847명이 교환 요청을 환불로 오해**했고, 그중 312명이 "환불 안 들어왔다"며 신고센터에 접수했다. 사고 리뷰에서 CTO가 던진 한마디:

> "우리가 캐시한 건 질문이 아니라, 답을 바꿔도 되는 조건이었어야 했는데."

#### 1. Semantic Cache란 무엇인가 — 그리고 왜 "LLM 캐시"가 아닌가

전통적 캐시는 **Key가 정확히 일치**해야 한다 (Redis `GET user:123`). 하지만 LLM 요청은 자연어라서 "환불 언제 와요?"와 "환불 며칠 걸려요?"는 같은 답을 원하지만 Key가 다르다.

Semantic Cache는 **질의를 임베딩으로 변환해 Vector DB에서 유사도 검색**하고, 임계값을 넘으면 저장된 답변을 반환한다.

```
┌─────────────┐   query   ┌──────────────────┐   embed   ┌─────────────┐
│   Client    │──────────▶│  Cache Lookup    │──────────▶│  Embedding  │
└─────────────┘           │   (semantic)     │           │   Model     │
      ▲                   └────────┬─────────┘           └──────┬──────┘
      │                            │                            │
      │                            ▼                            ▼
      │                   ┌──────────────────┐          ┌─────────────┐
      │        HIT        │  Vector Search   │◀─────────│  Vector DB  │
      │      (답변 반환)   │  (top-1, sim≥τ)  │          │ (query+ans) │
      ├────────────────── └────────┬─────────┘          └─────────────┘
      │                            │ MISS
      │                            ▼
      │                   ┌──────────────────┐
      │                   │   LLM Gateway    │
      │                   │   (GPT-4o 호출)  │
      │                   └────────┬─────────┘
      │                            │
      └────────────────────────────┼───▶ 캐시 저장
                                   │     (embed, query, answer, TTL, metadata)
                                   ▼
                              Client에게 응답
```

**핵심 오해**: Semantic Cache는 LLM 응답의 캐시가 아니라, **"이 질의에 대해 저장된 답을 재사용해도 안전한가"를 판단하는 결정 시스템**이다. 코사인 유사도는 그 결정의 입력 중 하나일 뿐이다.

#### 2. 세 가지 유형 — 그리고 각각의 사고 양상

| 유형 | 작동 방식 | 적합한 경우 | 전형적 사고 |
|---|---|---|---|
| **Exact Cache** | 문자열 hash 일치 | FAQ 봇, 결정론적 쿼리 | 거의 안 터짐 (히트율이 낮을 뿐) |
| **Semantic Cache** | 임베딩 유사도 ≥ τ | 자연어 Q&A, 반복 질문 많음 | 유사하지만 **다른 의도**를 같은 답으로 처리 |
| **Hierarchical Cache** | Exact → Semantic → LLM | 트래픽 큰 상용 서비스 | 복잡도 ↑, 디버깅 지옥 |

```
┌──────────────────────────────────────────────────┐
│                 Hierarchical Cache                │
├──────────────────────────────────────────────────┤
│                                                   │
│  L1: Exact (Redis string, TTL 5m)                │
│      │ miss                                       │
│      ▼                                            │
│  L2: Semantic (pgvector, sim≥0.95, TTL 1h)       │
│      │ miss                                       │
│      ▼                                            │
│  L3: Context-aware Semantic                       │
│      (sim≥0.90 AND same user_tier AND same       │
│       product_category, TTL 10m)                 │
│      │ miss                                       │
│      ▼                                            │
│  LLM Gateway → GPT-4o                             │
│                                                   │
└──────────────────────────────────────────────────┘
```

L2까지는 흔하지만, **L3 "context-aware"**가 D 커머스 사고의 진짜 해답이다. "환불/교환"은 context key(의도 분류)로 격리시켰어야 했다.

#### 3. 다섯 가지 함정

**함정 ①: 유사도 임계값을 "그냥 0.9"로 둔다**

0.9는 임베딩 모델마다 완전히 다른 의미다. `text-embedding-3-small`은 0.85부터 "유사", `bge-m3`는 0.75부터 "유사"다. 모델 바꿀 때마다 **임계값을 재튜닝**해야 하는데, 그걸 모르고 모델만 바꿔서 캐시 히트율이 2%로 떨어진 K 핀테크 사례가 있다.

> **How to apply**: 임계값은 **분위수 기반**으로 정해라. "최근 10,000건의 같은 의도 쌍의 유사도 중앙값 - 1σ"가 실용적 공식이다.

**함정 ②: 답변을 캐시하면서 "답변의 유효기간"을 캐시 TTL과 동일시한다**

"오늘의 환율은?" 답변을 TTL 1시간으로 캐시하면, 59분 전 환율이 59분 동안 서빙된다. 캐시 TTL은 **답변의 사실적 수명**과 다르다.

```
❌ 잘못된 TTL 설계
cache.set(key, answer, ttl=3600)  # 전부 1시간

✅ 답변 수명 기반 TTL
if intent == "pricing" or intent == "stock":
    ttl = 60             # 1분
elif intent == "policy":
    ttl = 86400 * 7      # 7일
elif intent == "faq_static":
    ttl = 86400 * 30     # 30일
```

**함정 ③: 사용자별 컨텍스트를 무시한다**

VIP 고객이 "내 쿠폰 뭐 있어?"로 물어 답을 받고, 캐시 저장. 10분 뒤 신규 고객이 같은 질문을 하면 VIP 쿠폰이 뿌려진다. **Cache Key에 user_tier, locale, A/B bucket을 반드시 포함**해라.

**함정 ④: RAG의 Context가 바뀌어도 캐시가 살아있다**

RAG에서 검색된 문서가 업데이트되면 답도 바뀌어야 하는데, Semantic Cache는 "질문이 비슷하니 옛 답"을 뿌린다. **문서 업데이트 이벤트가 캐시 invalidation 트리거**가 되어야 한다.

```
Document Update ──▶ Vector DB upsert ──▶ Cache invalidate
                        │
                        └─▶ (문서 ID가 포함된 캐시 엔트리 삭제)
```

**함정 ⑤: 캐시 히트율만 보고 품질 저하를 못 본다**

캐시 히트율은 올라가는데 CSAT은 떨어진다. **Shadow eval**: 캐시 히트의 N%는 실제 LLM도 돌려서 답을 비교하라. 두 답이 다르면 그 쌍을 리그레션 샘플로 축적.

#### 4. 트레이드오프 매트릭스

| 축 | Exact | Semantic (τ=0.95) | Semantic (τ=0.85) | Hierarchical |
|---|---|---|---|---|
| 히트율 | 5~15% | 30~45% | 55~70% | 60~75% |
| 오답 리스크 | 거의 0 | 낮음 | **높음** | 낮음 |
| 비용 (per req) | $0.00001 | $0.0001 (embed) | $0.0001 | $0.00011 |
| 응답 지연 | 1ms | 15~40ms | 15~40ms | 20~50ms |
| 디버깅 난이도 | 쉬움 | 중간 | 어려움 | **매우 어려움** |
| 모델 교체 영향 | 없음 | **크다 (재튜닝)** | **크다** | 크다 |

Semantic Cache는 공짜가 아니다. **GPT-4o 한 번 안 부르는 대신, 임베딩 호출 1회 + Vector Search 1회**가 추가된다. 유사 질의가 전체 트래픽의 **최소 25% 이상 반복**되지 않으면 ROI가 나오지 않는다.

#### 5. 실제 사례

**사례 1: GPTCache (Zilliz, 2023 오픈소스)**
- Milvus 팀이 공개한 LLM 캐시 라이브러리. 임베딩 유사도 기반.
- 교훈: 초기에 "임계값 하나로 전역 적용"을 제공했는데, 사용자들이 사고를 내서 **v0.1.30부터 "domain-specific threshold"와 "context awareness"를 핵심 기능으로 격상**시켰다. 설계자가 틀렸음을 인정한 드문 케이스.

**사례 2: Anthropic Prompt Caching (2024.08)**
- Claude 3.5가 공식 지원한 캐시는 **Semantic이 아니다**. 프롬프트의 "prefix hash 일치" 기반. 왜? 안전성 때문. 의미상 비슷해도 다른 답을 뱉어야 할 수 있다는 걸 알고 있어서, 모델 벤더는 Semantic Cache를 네이티브로 제공하지 않는다.
- 교훈: **Semantic Cache는 애플리케이션 레이어의 책임**이다. 벤더가 안 해주는 건 못 믿어서가 아니라, 못 책임지기 때문이다.

**사례 3: Perplexity (2024)**
- 뉴스/실시간 검색이 많아 Semantic Cache를 공격적으로 썼다가, "오늘 애플 주가는?"에 어제 답을 서빙한 사건 발생.
- 대응: **쿼리 분류기(news/factual/evergreen)를 먼저 돌려서, news는 캐시 금지, factual은 TTL 10분, evergreen은 24시간**으로 분리. 캐시 히트율은 42% → 31%로 떨어졌지만 신뢰도는 회복.

**사례 4: 국내 D 커머스 (2026 블랙프라이데이, 도입부 사고)**
- 사고 후 리팩토링:
  1. **의도 분류기**를 캐시 lookup 앞에 배치 (환불/교환/배송/계정)
  2. 캐시 Key = `hash(intent + user_tier + semantic_bucket)`
  3. **유사도 임계값을 0.9 → 0.96으로 상향**, 그리고 `intent==` 동일 조건을 추가
  4. Shadow eval 10% 샘플링 상설
- 결과: 히트율 68% → 51%, 오답률 1.3% → 0.04%, 월 비용 절감은 2억 → 1.4억으로 줄었지만 **CSAT가 61점 → 83점**으로 회복.

**사례 5 (실패): 국내 E 에듀테크 (2025)**
- "같은 문제 질문이 많으니 Semantic Cache 쓰자"며 도입. 하지만 **학생 수준(초6, 중2, 고1)별 설명이 달라야 하는데** Cache Key에 학년 정보를 안 넣음.
- 중2 학생이 "미분이 뭐야?"로 물었을 때 고2용 답변이 뿌려져, 학부모 민원 → 환불 요청 급증.
- 교훈: **Semantic이 같아도 Pedagogical context가 다르면 다른 답이다**. 캐시의 등가성(equivalence)은 도메인 지식이 정의한다.

**사례 6: Shopify Shop Assistant (2024 발표)**
- 하루 수억 쿼리를 받는 상용 서비스. Hierarchical cache 운영.
- L1(exact) 12%, L2(semantic within product category) 34%, L3(semantic cross-category) 비활성 (오답 리스크).
- **L3를 "활성화하지 않는 결정"**이 설계의 핵심 포인트로 공유됨. "할 수 있다 ≠ 해야 한다"의 교과서 사례.

#### 6. 언제 쓰고, 언제 쓰면 안 되는가 — 시니어의 판단

**✅ 반드시 도입해야 하는 경우**
- FAQ/고객지원처럼 **상위 20% 쿼리가 전체 트래픽의 60% 이상**을 차지하는 Long-tail 분포
- 답변의 사실적 수명이 **최소 10분 이상**인 도메인 (정책, 사용법, 개념 설명)
- 쿼리당 LLM 비용이 **임베딩 호출 비용의 100배 이상** (즉 GPT-4o/Claude Opus 급 모델 사용 시)

**⚠️ 신중히 도입할 경우**
- 사용자별 개인화 응답이 필요한 서비스 → Cache Key에 사용자 컨텍스트 필수 포함
- RAG 백엔드 문서가 자주 갱신되는 경우 → Invalidation 이벤트 파이프라인 선행 구축
- 다국어 서비스 → 언어별 임베딩 공간이 섞이지 않도록 locale 분리

**❌ 쓰면 안 되는 경우**
- **실시간성이 핵심**인 도메인 (주가, 환율, 재고, 뉴스)
- 사용자가 **"이전 답과 다른 각도"**를 기대하는 창작/브레인스토밍 (매번 같은 답 뿌리면 서비스가 "고장난" 걸로 인식됨)
- **법적 책임**이 캐시 답변에 묻을 수 있는 도메인 (법무, 의료, 세무) — 답변 단위로 timestamp와 source를 추적 못 하면 금지
- Agent의 **중간 단계 Tool call 응답** — 상태가 매번 다를 수 있고, 캐시 히트가 Agent의 Plan 자체를 왜곡

#### 7. 운영 체크리스트

```
[ ] 유사도 임계값은 임베딩 모델 교체 시 재튜닝 프로세스가 있는가?
[ ] Cache Key에 user_tier, locale, intent, A/B bucket이 포함되는가?
[ ] 답변 수명 기반 TTL 정책이 intent별로 분리되어 있는가?
[ ] RAG 문서 업데이트 이벤트가 캐시 invalidation을 트리거하는가?
[ ] Shadow eval이 캐시 히트의 N%에 대해 상설 운영되는가?
[ ] 캐시 히트율과 함께 CSAT/오답률이 같은 대시보드에 있는가?
[ ] 캐시 miss 시 LLM 응답을 저장할 때 PII가 마스킹되는가?
[ ] "캐시 즉시 무효화" 운영 커맨드가 있는가? (사고 대응용)
```

마지막 체크 하나는 특히 중요하다. D 커머스 사고 당일, **"지금 당장 캐시 전체 비우는 커맨드가 없다"**는 걸 CTO가 알게 된 순간이 사실 가장 비싼 교훈이었다. Redis `FLUSHDB`로 다 날렸고, 그 뒤 30분간 GPT-4o 비용이 폭발했지만, 그게 유일한 선택지였다.

---

> 💡 **왜 중요한가**: Semantic Cache는 "질문이 비슷하면 답도 같다"는 가정 위에 서있는데, 이 가정이 참인 순간과 거짓인 순간을 분리하는 것이 캐시 레이어가 아니라 **도메인 지식**이라는 걸 받아들여야만 안전하게 쓸 수 있다.
