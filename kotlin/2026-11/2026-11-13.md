### 1. `Sequence` vs `List`: 100만 개 데이터에서 `map().filter()`가 느린 진짜 이유

Kotlin의 컬렉션 함수(`map`, `filter`)는 매 단계마다 **중간 List를 새로 생성**하기 때문에, 체이닝이 길어지거나 데이터가 크면 메모리와 CPU를 낭비한다. `asSequence()`로 바꾸면 각 원소가 **파이프라인 전체를 통과한 뒤 다음 원소로 넘어가는 지연 평가(lazy evaluation)** 방식이 되어, 중간 컬렉션이 사라지고 `first()` 같은 종결 연산을 만나면 조기 종료까지 가능해진다.

```kotlin
// ❌ 100만 개 → map으로 100만 개 List 생성 → filter로 또 List 생성
val result = (1..1_000_000)
    .map { it * 2 }        // 중간 List 생성 (메모리 폭발)
    .filter { it % 3 == 0 } // 또 중간 List 생성
    .first()               // 결국 1개만 필요한데...

// ✅ Sequence: 원소 하나씩 파이프라인 통과, first() 만나면 즉시 종료
val result = (1..1_000_000)
    .asSequence()
    .map { it * 2 }
    .filter { it % 3 == 0 }
    .first()  // 조건 만족하는 첫 원소만 계산하고 종료
```

> 💡 **왜 중요한가**: 작은 컬렉션(~1000개)엔 List가 빠르지만, 큰 데이터나 긴 체이닝에선 Sequence가 수십 배 빠르다 — "컬렉션 함수는 무조건 빠르다"는 오해가 운영 장애의 시작이다.

### 2. `=` 함수 (Expression Body): "한 줄 함수"가 아니라 "표현식 지향" 설계의 신호

Kotlin에서 `fun foo(): Int = 42`는 단순히 중괄호를 생략한 문법 설탕이 아니라, **모든 것을 값(expression)으로 다루는 함수형 사고**를 강제하는 장치다. `if`, `when`, `try`도 값을 반환하는 표현식이므로, 함수 본문을 `=`로 쓰면 자연스럽게 **early return 없는 단일 반환 경로**가 만들어져 테스트와 디버깅이 쉬워진다.

```kotlin
// ❌ Java 스타일: 명령형, 반환 경로 여러 개
fun grade(score: Int): String {
    if (score >= 90) return "A"
    if (score >= 80) return "B"
    return "F"
}

// ✅ Kotlin 스타일: when을 값으로, 함수는 하나의 표현식
fun grade(score: Int): String = when {
    score >= 90 -> "A"
    score >= 80 -> "B"
    else -> "F"
}

// 응용: try도 표현식 — 예외를 값으로 변환
fun parseOrDefault(s: String): Int = try {
    s.toInt()
} catch (e: NumberFormatException) {
    -1
}
```

> 💡 **왜 중요한가**: `= expression` 스타일을 습관화하면 자연스럽게 불변성·단일 책임·부수효과 분리가 따라오고, 이게 Kotlin이 Java보다 "함수형 친화적"이라고 불리는 이유다.
