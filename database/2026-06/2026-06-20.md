### 1. PostgreSQL `GENERATED ALWAYS AS ... STORED` 계산 컬럼과 그 위의 인덱스
이메일 정규화·검색 키·세금 포함 가격처럼 "다른 컬럼으로부터 항상 도출되는 값"을 매번 애플리케이션 코드에서 계산하면 DB가 그 값을 인덱싱하지 못해 `WHERE LOWER(email) = ...` 형태에서 풀스캔이 나기 쉽다. PostgreSQL 12부터 도입된 `GENERATED ALWAYS AS (expr) STORED`를 쓰면 컬럼 자체로 물질화되어 `INSERT`/`UPDATE` 시 자동 계산되고, 일반 컬럼처럼 인덱스를 걸 수 있어 표현식 인덱스보다 의도가 명확해진다. 단 `STORED`만 지원되며 디스크 공간은 늘어나니, 핫 컬럼이 아닌 경우 표현식 인덱스가 더 나은 선택이 될 수 있다.

```sql
ALTER TABLE users
  ADD COLUMN email_norm TEXT
  GENERATED ALWAYS AS (lower(email)) STORED;

CREATE INDEX users_email_norm_idx ON users(email_norm);

-- 애플리케이션은 그냥 평범한 컬럼처럼 사용
SELECT * FROM users WHERE email_norm = lower($1);
```

> 💡 **왜 중요한가**: 계산식이 코드와 DB에 이중으로 흩어지면 한쪽만 바뀌어 캐시 키·인덱스 미스가 생기는 사고가 잦은데, 스키마 한 줄로 "계산 책임의 단일 소스"를 만들 수 있다.

### 2. JPA `@SqlResultSetMapping`으로 Native Query 결과를 DTO에 안전하게 매핑하기
복잡한 윈도우 함수나 CTE를 써야 해서 Native Query로 떨어졌는데, 결과를 `Object[]`로 받고 인덱스로 캐스팅하는 건 컬럼 추가만 생겨도 NPE·ClassCastException을 부른다. `@SqlResultSetMapping`에 `@ConstructorResult`를 선언해두면 DTO 생성자에 컬럼이 타입별로 안전하게 묶이고, 컬럼명이 바뀌면 컴파일·기동 단계에서 매핑 에러가 난다.

```java
@SqlResultSetMapping(
  name = "OrderSummaryMapping",
  classes = @ConstructorResult(
    targetClass = OrderSummary.class,
    columns = {
      @ColumnResult(name = "customer_id", type = Long.class),
      @ColumnResult(name = "order_count", type = Long.class),
      @ColumnResult(name = "total_amount", type = BigDecimal.class)
    }))
@Entity public class Order { /* ... */ }

List<OrderSummary> rows = em.createNativeQuery(
    "SELECT customer_id, COUNT(*) AS order_count, SUM(amount) AS total_amount " +
    "FROM orders WHERE created_at >= ? GROUP BY customer_id",
    "OrderSummaryMapping")
  .setParameter(1, since)
  .getResultList();
```

> 💡 **왜 중요한가**: Native Query의 마지막 약점이던 "결과 매핑이 깨지기 쉬움"을 해결해, 성능과 타입 안전성을 동시에 가져갈 수 있다.
