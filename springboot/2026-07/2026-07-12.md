### `@RequestBody`에 `@Valid`를 붙였을 때 검증 실패는 `MethodArgumentNotValidException`, `@RequestParam`은 `ConstraintViolationException`으로 예외 타입이 다르다

같은 검증이지만 바인딩 위치에 따라 튀어나오는 예외가 다르기 때문에 `@ControllerAdvice`에서 두 예외를 각각 처리해야 일관된 400 응답을 만들 수 있다. `MethodArgumentNotValidException`은 `BindingResult`에서 필드 에러를 꺼내고, `ConstraintViolationException`은 `getConstraintViolations()`에서 프로퍼티 경로를 파싱하는 방식이 완전히 다르다.

```java
@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ErrorResponse> handleBody(MethodArgumentNotValidException e) {
    List<FieldError> errors = e.getBindingResult().getFieldErrors();
    return ResponseEntity.badRequest().body(ErrorResponse.of(errors));
}

@ExceptionHandler(ConstraintViolationException.class)
public ResponseEntity<ErrorResponse> handleParam(ConstraintViolationException e) {
    return ResponseEntity.badRequest().body(ErrorResponse.of(e.getConstraintViolations()));
}
```

> 💡 **왜 중요한가**: 두 예외를 통합 처리하지 않으면 클라이언트는 검증 실패 응답 포맷이 API마다 달라진다는 혼란을 겪는다.

### `@SpringBootTest`에 `webEnvironment = RANDOM_PORT`를 쓰면 `@LocalServerPort`로 실제 포트를 주입받아 TestRestTemplate으로 통합 테스트가 가능하다

`MOCK`은 서블릿 컨테이너를 띄우지 않아 필터 체인이 실제와 다르게 동작할 수 있는 반면, `RANDOM_PORT`는 임베디드 톰캣을 실제 기동해서 필터·인터셉터·에러 페이지까지 프로덕션과 동일하게 검증할 수 있다. 병렬 테스트 실행 시 포트 충돌도 자동으로 회피된다.

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class OrderApiTest {
    @LocalServerPort int port;
    @Autowired TestRestTemplate rest;

    @Test void 주문_생성() {
        var res = rest.postForEntity("http://localhost:" + port + "/orders", req, OrderResponse.class);
        assertThat(res.getStatusCode()).isEqualTo(HttpStatus.CREATED);
    }
}
```

> 💡 **왜 중요한가**: 필터·시큐리티·예외 핸들러가 실제로 엮여 동작하는지는 MockMvc만으로는 잡히지 않는 회귀가 존재한다.
