### 1. `reified` 타입 파라미터: "제네릭의 타입 소거"를 inline으로 뚫어버리는 Kotlin의 트릭

JVM의 제네릭은 런타임에 타입 정보가 사라지는 "타입 소거(Type Erasure)" 때문에 `T::class.java`를 직접 쓸 수 없다. 하지만 Kotlin은 `inline fun <reified T>`로 함수 본문을 호출부에 복사하면서 `T`를 실제 타입으로 치환해, 마치 런타임에 타입을 "아는 것처럼" 동작하게 만든다. 이게 `objectMapper.readValue<User>(json)`이나 `getSystemService<AlarmManager>()`가 `.class`를 넘기지 않고도 작동하는 비밀이다.

```kotlin
// Java 스타일: 타입 소거 때문에 Class<T>를 직접 받아야 함
fun <T> fromJson(json: String, clazz: Class<T>): T =
    objectMapper.readValue(json, clazz)

// Kotlin: reified로 타입을 "실체화"
inline fun <reified T> fromJson(json: String): T =
    objectMapper.readValue(json, T::class.java)

// 호출부에서 타입만 명시하면 끝
val user: User = fromJson(jsonString)  // Class 넘길 필요 없음
val users: List<User> = fromJson(jsonString)  // 중첩 제네릭도 OK
```

**트레이드오프**: `reified`는 반드시 `inline`과 함께여야 한다. 즉, 호출부마다 함수 본문이 복사되므로 바이트코드가 커지고, 재귀 호출이나 다른 함수에 `T`를 넘기는 건 불가능하다. Spring의 `ApplicationContext.getBean<MyService>()`, Jackson의 `readValue<T>()`, Retrofit의 `create<ApiService>()` 같은 API 디자인이 전부 이 패턴이다.

> 💡 **왜 중요한가**: `Class<T>` 파라미터를 받는 "Java스러운" API를 설계하는 대신, `reified`로 호출부가 깔끔해지는 라이브러리 수준의 설계 도구를 가질 수 있다 — 단, inline의 바이트코드 비용을 지불할 가치가 있을 때만.

### 2. `backing field` (`field` 키워드): "프로퍼티는 변수가 아니다"라는 Kotlin의 설계 철학

Kotlin에서 `var name: String`은 Java의 필드가 아니라 **getter/setter 쌍**이다. 커스텀 setter 안에서 `name = value`라고 쓰면 setter가 자기 자신을 무한 호출해 StackOverflow가 난다. 이때 "진짜 저장 공간"에 접근하려면 `field`라는 암묵적 키워드를 써야 하며, 이게 바로 Kotlin의 **backing field**다.

```kotlin
class User {
    // ❌ 무한 재귀 - setter가 자기 자신을 호출
    var email: String = ""
        set(value) {
            email = value.lowercase()  // StackOverflowError!
        }

    // ✅ field로 진짜 저장소에 접근
    var username: String = ""
        set(value) {
            require(value.isNotBlank()) { "username cannot be blank" }
            field = value.trim().lowercase()  // 실제 메모리에 저장
        }
        get() = field.ifEmpty { "guest" }

    // backing field가 아예 생성되지 않는 경우: 계산된 프로퍼티
    val displayName: String
        get() = "@$username"  // field 사용 안 함 → 저장소 없음
}
```

**트레이드오프**: `field`는 오직 프로퍼티의 접근자(getter/setter) 내부에서만 쓸 수 있다. 그리고 커스텀 접근자가 `field`를 참조하지 않으면 컴파일러가 backing field를 아예 생성하지 않는다 — 즉 JPA Entity에서 `@Transient` 없이도 "DB에 저장되지 않는 계산 프로퍼티"를 만들 수 있다. 반대로 Hibernate는 backing field에 리플렉션으로 접근하므로, `field`의 존재 여부가 ORM 동작까지 바꾼다.

> 💡 **왜 중요한가**: "프로퍼티 = 필드"라는 Java적 사고를 버려야 Kotlin의 캡슐화, 유효성 검증, 계산 프로퍼티, JPA 매핑이 모두 자연스럽게 설계된다 — `field` 키워드는 그 세계관의 입구다.
