### JPA `@Version`을 이용한 낙관적 락 (Optimistic Locking) — "먼저 커밋한 놈이 임자"인 동시성 제어의 정석

엔티티에 `@Version private Long version;` 필드 하나만 추가하면, JPA가 UPDATE 시 `WHERE id=? AND version=?` 조건을 자동으로 붙이고 성공하면 version을 +1 한다. 두 트랜잭션이 같은 행을 동시에 수정하면 나중에 커밋한 쪽은 `OptimisticLockException`을 맞고 롤백된다. 락을 걸지 않으므로 읽기 성능은 그대로, 충돌이 드문 도메인(주문 상태 변경, 게시글 수정)에서 `SELECT ... FOR UPDATE`보다 압도적으로 빠르다.

```java
@Entity
public class Order {
    @Id private Long id;
    private String status;

    @Version  // Long, Integer, Timestamp 가능
    private Long version;
}

// 트랜잭션 A: version=5 읽음 → status="PAID"로 UPDATE
// UPDATE orders SET status='PAID', version=6 WHERE id=1 AND version=5  ✅ 성공

// 트랜잭션 B: 같은 시점에 version=5 읽음 → status="CANCELED"로 UPDATE
// UPDATE orders SET status='CANCELED', version=6 WHERE id=1 AND version=5  ❌ 0 rows updated
// → OptimisticLockException → 애플리케이션에서 재시도 or 사용자에게 충돌 안내
```

**함정**: 재시도 로직(Spring Retry의 `@Retryable(OptimisticLockException.class)`)이 없으면 사용자에게 "다시 시도해주세요"가 그대로 노출된다. 충돌 빈도가 10%를 넘으면 오히려 비관적 락(`@Lock(PESSIMISTIC_WRITE)`)이 총 처리량은 더 높다 — 재시도 폭풍이 DB보다 더 비싸질 수 있기 때문.

> 💡 **왜 중요한가**: 재고 차감처럼 "동시 수정 충돌이 드물지만 데이터 정합성은 절대 깨지면 안 되는" 시나리오에서, DB 락 없이 원자성을 보장하는 가장 저렴한 방법이다.

### MySQL `Index Merge` — 두 개의 단일 인덱스를 "합쳐서" 쓰는, 복합 인덱스 없이도 살아남는 옵티마이저의 잔재주

`WHERE user_id = 1 OR email = 'a@b.com'` 같은 쿼리에서 `(user_id, email)` 복합 인덱스가 없어도, MySQL은 `idx_user_id`와 `idx_email`을 각각 태워서 결과를 병합(Union/Intersect/Sort-Union)한다. `EXPLAIN`에서 `type: index_merge`, `Extra: Using union(idx_user_id, idx_email)`로 확인 가능. 복합 인덱스를 새로 만드는 부담 없이도 "일단은 인덱스를 타게" 만드는 임시 방편.

```sql
-- 인덱스: idx_user_id(user_id), idx_status(status) 두 개만 존재
EXPLAIN SELECT * FROM orders WHERE user_id = 100 OR status = 'PENDING';

-- type: index_merge
-- key: idx_user_id,idx_status
-- Extra: Using union(idx_user_id,idx_status); Using where
--        → 두 인덱스로 각각 PK 목록을 뽑고 UNION → 테이블 조회
```

**진짜 함정**: Index Merge가 "동작한다"고 안심하면 안 된다. 대부분의 경우 옵티마이저는 Index Merge보다 **단일 인덱스 풀 스캔이 낫다고 오판**하거나, 반대로 **Index Merge를 억지로 골라서 복합 인덱스보다 느려지는** 경우가 자주 발생한다 (특히 5.7 → 8.0 업그레이드 후 플랜이 뒤집히는 대표 케이스). `EXPLAIN`에서 `index_merge`가 보이면 "정말로 이게 최선인가"를 의심하고, `optimizer_switch='index_merge=off'`로 껐을 때의 플랜과 반드시 비교해봐야 한다. 궁극적으로는 자주 함께 조건에 걸리는 컬럼은 **복합 인덱스로 명시적으로 만드는 것이 정답**이다.

> 💡 **왜 중요한가**: `EXPLAIN`에서 `index_merge`를 보고 "인덱스 잘 타네"라고 넘기면 안 된다 — 절반은 최적화의 신호지만, 절반은 옵티마이저가 복합 인덱스를 만들라고 보내는 SOS 신호다.
