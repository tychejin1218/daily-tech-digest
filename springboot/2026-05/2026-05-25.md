### `@ControllerAdvice` + `@RestControllerAdvice`로 전역 예외 처리 일원화하기

컨트롤러마다 try-catch를 반복하는 대신 `@RestControllerAdvice` 클래스에 `@ExceptionHandler`를 모아두면 모든 컨트롤러의 예외를 한 곳에서 처리할 수 있다. `basePackages`나 `assignableTypes` 속성으로 적용 범위를 좁힐 수 있어 관리자용/공개용 API의 응답 포맷을 분리하기도 좋다.

```java
@RestControllerAdvice(basePackages = "com.example.api")
public class ApiExceptionHandler {

    @ExceptionHandler(IllegalArgumentException.class)
    public ResponseEntity<ErrorResponse> handleBadRequest(IllegalArgumentException e) {
        return ResponseEntity.badRequest()
            .body(new ErrorResponse("BAD_REQUEST", e.getMessage()));
    }

    @ExceptionHandler(EntityNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(EntityNotFoundException e) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
            .body(new ErrorResponse("NOT_FOUND", e.getMessage()));
    }
}
```

> 💡 **왜 중요한가**: 예외 응답 포맷이 컨트롤러마다 제각각이면 클라이언트 파싱 로직이 지옥이 되고, 로깅·모니터링 훅을 심을 자리도 사라진다.

### `@Sql`로 슬라이스 테스트에 필요한 데이터만 선언적으로 세팅하기

`@DataJpaTest`나 `@SpringBootTest`에서 매번 `@BeforeEach`로 데이터를 insert하는 대신 `@Sql(scripts = "/sql/user-fixture.sql")`을 붙이면 테스트 메서드 실행 전에 지정한 SQL 스크립트가 자동 실행된다. `executionPhase = AFTER_TEST_METHOD`로 정리 스크립트를 붙일 수도 있고, 클래스 레벨과 메서드 레벨을 조합해 공통 fixture + 개별 데이터를 층층이 쌓을 수 있다.

```java
@DataJpaTest
@Sql("/sql/common-fixture.sql")
class UserRepositoryTest {

    @Test
    @Sql(scripts = "/sql/vip-users.sql",
         executionPhase = Sql.ExecutionPhase.BEFORE_TEST_METHOD)
    void findVipUsers_returnsOnlyVip() {
        // given: SQL 스크립트로 데이터 세팅 완료
        List<User> vips = userRepository.findByGrade(Grade.VIP);
        assertThat(vips).hasSize(3);
    }
}
```

> 💡 **왜 중요한가**: Java 코드로 fixture를 만들면 도메인 로직 변경마다 테스트 데이터 코드가 함께 깨지지만, SQL 스크립트로 분리하면 스키마만 안정적이면 테스트가 흔들리지 않는다.
