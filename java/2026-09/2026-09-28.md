### 1. `HashMap.newHashMap(numMappings)` (Java 19 정식)로 `new HashMap<>((int)(size/0.75f)+1)` 수동 캐퍼시티 계산 관성 벗어나기

원하는 매핑 개수를 실제로 리사이즈 없이 담을 수 있는 초기 용량을 자동 계산해 `HashMap`을 만든다. 지금까지는 부하율(load factor 0.75)을 고려해 `(int)(expectedSize / 0.75f) + 1` 같은 마법 수식을 외우거나, 그냥 `new HashMap<>(size)`로 넘겨 실제로는 size의 75%만 채워도 리사이즈가 일어나는 미묘한 성능 함정을 만들어 왔다. Java 19부터 `HashMap`, `LinkedHashMap`, `HashSet`, `LinkedHashSet`, `WeakHashMap`에 각각 `newHashMap(int numMappings)` 계열 정적 팩토리가 추가되어 이 계산을 표준 API로 흡수했다.

```java
// 관성 (부하율 마법 수식을 외워야 함)
Map<String, User> map = new HashMap<>((int) (users.size() / 0.75f) + 1);

// Java 19+
Map<String, User> map = HashMap.newHashMap(users.size());
```

> 💡 **왜 중요한가**: `new HashMap<>(size)`는 "size개 담을 수 있는 맵"이 아니라 "초기 버킷이 size개인 맵"이라 부하율 때문에 반드시 한 번은 리사이즈가 일어나는데, 표준 API가 이 함정을 처음으로 명시적으로 제거해준다.

### 2. `ScopedValue.where(KEY, value).call(callable)` (Java 25 정식, JEP 506)로 `ThreadLocal.remove()` finally 관성 벗어나기

특정 코드 블록이 실행되는 동안에만 값이 바인딩되고, 블록이 끝나면 자동으로 해제되는 불변 스레드 로컬 대체재다. `ThreadLocal`은 값이 스레드가 죽을 때까지 남아 스레드 풀에서 메모리 누수를 일으키고, 가상 스레드 시대에는 수백만 개의 스레드마다 로컬 저장소가 폭증할 수 있어 반드시 finally에서 `remove()`를 호출해야 안전했다. `ScopedValue`는 스택 프레임이 존재하는 동안에만 유효한 불변 값이고, `StructuredTaskScope`와 결합하면 자식 가상 스레드로만 안전하게 전파된다.

```java
// 관성 (remove() 잊으면 스레드 풀에서 누수)
private static final ThreadLocal<String> TRACE_ID = new ThreadLocal<>();
try {
    TRACE_ID.set(traceId);
    return handler.handle(request);
} finally {
    TRACE_ID.remove();
}

// Java 25+ (블록 종료 시 자동 해제, 불변 보장)
private static final ScopedValue<String> TRACE_ID = ScopedValue.newInstance();
return ScopedValue.where(TRACE_ID, traceId)
                  .call(() -> handler.handle(request));
```

> 💡 **왜 중요한가**: 가상 스레드가 등장하면서 `ThreadLocal`은 "누수를 막기 위해 finally를 항상 붙여야 하는 위험한 API"가 되었고, `ScopedValue`가 요청 컨텍스트(traceId, userId, tenantId) 전파의 새 표준이 된다.
