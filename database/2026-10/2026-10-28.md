### Database Tip 1: MySQL `Covering Index` — 테이블을 "아예 열지 않고" 인덱스만으로 쿼리를 끝내는 B+Tree의 숨은 지름길

InnoDB의 세컨더리 인덱스는 리프 노드에 "인덱스 컬럼 + 클러스터링 키(PK)"만 담고 있어서, 실제 데이터 행을 보려면 PK로 클러스터드 인덱스를 한 번 더 뒤지는 **Random I/O (Index Lookup)** 가 추가로 발생한다. 그런데 SELECT 하는 모든 컬럼이 인덱스 자체에 이미 들어있다면 — 즉 `(status, created_at)` 인덱스에 `SELECT id, status, created_at` 처럼 — InnoDB는 테이블 접근을 **완전히 건너뛰고** 인덱스 리프 노드만 스캔해서 결과를 돌려주는데, 이게 바로 `EXPLAIN`의 `Extra` 컬럼에 뜨는 그 유명한 **"Using index"** 다. 수백만 건 조회에서 Lookup 한 번당 수 ms씩 사라지던 쿼리가 10배 빨라지는 마법의 정체는, 결국 "읽을 필요가 없는 페이지를 안 읽는 것"뿐이다.

```
일반 세컨더리 인덱스 조회:
  [세컨더리 인덱스 리프] ──(PK)──▶ [클러스터드 인덱스 리프] ──▶ Row 데이터
                                   ↑ 여기서 Random I/O 폭발 (N번)

Covering Index (Using index):
  [세컨더리 인덱스 리프] ──▶ 끝. 테이블은 열지도 않음.
   ↑ 모든 SELECT 컬럼이 여기 안에 다 있음
```

실무 트릭은 **INCLUDE 흉내내기**: 자주 조회되지만 WHERE에는 쓰지 않는 컬럼(`user_name`, `thumbnail_url` 등)을 복합 인덱스 **뒤쪽**에 끼워넣어 Covering으로 만든다. 단, 인덱스는 공짜가 아니라 INSERT/UPDATE 비용과 디스크 용량을 함께 먹기 때문에, "Top N 조회", "페이지네이션 카운트", "집계 쿼리"처럼 **읽기 >>> 쓰기**인 테이블에서만 쓰는 게 트레이드오프의 정답이다. PostgreSQL은 `CREATE INDEX ... INCLUDE (col)` 로 WHERE에 쓰지 않을 컬럼을 명시적으로 리프에만 넣을 수 있어서 더 깔끔하다.

> 💡 **왜 중요한가**: 쿼리 튜닝의 끝판왕은 "더 빠른 I/O"가 아니라 "I/O를 아예 없애는 것"이고, Covering Index는 그걸 코드 한 줄 안 바꾸고 인덱스 정의만으로 해내는 가장 가성비 좋은 무기다.

### Database Tip 2: JPA `@EntityGraph` — N+1을 잡는다고 Repository마다 `JOIN FETCH` 쿼리를 복붙하지 않는 선언적 Fetch Plan

Hibernate에서 N+1을 해결하는 전통적인 방법은 JPQL에 `JOIN FETCH`를 박아넣는 것이지만, 이건 **"쿼리 하나당 Fetch 전략 하나"** 라서 같은 엔티티를 다른 조합으로 당겨오려면 Repository 메서드를 N개 만들어야 한다 (`findByIdWithOrders`, `findByIdWithOrdersAndItems`, `findByIdWithReviews` ...). `@EntityGraph`는 이 문제를 뒤집어서, **"엔티티 매핑은 전부 LAZY로 두고, 호출하는 쪽이 그때그때 어떤 연관을 즉시 로딩할지 선언"** 하게 해준다. 즉, Fetch 전략의 결정권을 엔티티(`@ManyToOne(fetch = EAGER)`) 가 아니라 **유스케이스**로 옮기는 것이다.

```java
// 전통 방식: 조합마다 쿼리 복제
@Query("SELECT o FROM Order o JOIN FETCH o.items WHERE o.id = :id")
Order findWithItems(Long id);
@Query("SELECT o FROM Order o JOIN FETCH o.items JOIN FETCH o.coupon WHERE o.id = :id")
Order findWithItemsAndCoupon(Long id);

// @EntityGraph: 쿼리는 그대로, Fetch Plan만 주입
@EntityGraph(attributePaths = {"items", "items.product", "coupon"})
Optional<Order> findById(Long id);  // 상속 메서드에 그냥 얹기
```

함정은 두 가지다. 첫째, **`@EntityGraph`는 결국 LEFT OUTER JOIN으로 번역**되므로 `*ToMany` 두 개 이상을 한꺼번에 걸면 그 악명 높은 **MultipleBagFetchException** 혹은 데카르트 곱으로 결과가 뻥튀기된다 — 이땐 `Set`을 쓰거나, 하나는 `@BatchSize`로 분리해야 한다. 둘째, Pagination(`Pageable`)과 `*ToMany` Fetch를 섞으면 Hibernate가 **"HHH000104: firstResult/maxResults specified with collection fetch; applying in memory!"** 를 띄우면서 수십만 건을 다 끌어와 메모리에서 자르는 참사가 벌어진다. 그래서 실전에서는 `*ToOne`은 `@EntityGraph`, `*ToMany`는 `@BatchSize` 또는 별도 쿼리로 분리하는 **하이브리드 전략**이 정답이 된다.

> 💡 **왜 중요한가**: N+1을 잡는 진짜 설계 포인트는 "어디서 Fetch를 결정하느냐"이고, `@EntityGraph`는 엔티티의 글로벌 정책을 포기하지 않으면서도 유스케이스별로 쿼리를 특화할 수 있는 **JPA 표준 레벨의 선언적 튜닝 레버**다.
