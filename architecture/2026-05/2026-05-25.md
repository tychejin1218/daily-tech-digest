### 이벤트 드리븐 아키텍처(EDA) — "요청/응답"에서 "사실의 흐름"으로, 서비스가 서로를 모르는 세계

MSA를 처음 쪼갤 때 대부분의 팀은 REST로 시작한다. `OrderService`가 `PaymentService`를 부르고, `PaymentService`가 `InventoryService`를 부르고, `InventoryService`가 `NotificationService`를 부른다. 코드는 익숙하고, 디버깅은 쉽고, 흐름은 명확하다. 그런데 6개월 후 어느 순간, 팀은 이상한 현상을 목격한다. **`NotificationService`가 죽으면 주문이 실패한다.** 알림 하나 못 보낸다고 주문을 거절하는 게 맞나? 아무도 그렇게 설계하지 않았는데, 호출 체인이 그렇게 만들어버렸다. 이것이 **동기 호출이 만들어내는 시간적 결합(temporal coupling)** 이며, 이벤트 드리븐 아키텍처(EDA)는 이 결합을 "사실의 브로드캐스트"로 대체하는 패러다임이다.

핵심 전환은 문장 하나로 요약된다. **"A가 B를 호출한다"에서 "A는 사실을 발행한다. 관심 있는 자가 반응한다"로.** `OrderService`는 더 이상 `PaymentService`를 알지 않는다. 대신 `OrderPlaced`라는 사실(event)을 발행할 뿐이다. 그 사실에 관심 있는 서비스들 — 결제, 재고, 알림, 분석, 추천 — 이 각자 알아서 구독하고 반응한다. `OrderService`는 구독자가 3개인지 30개인지 모른다. 알 필요도 없다.

```
[동기 호출 세계]                          [이벤트 드리븐 세계]
                                          
Order ──REST──> Payment                   Order ──publish──> [OrderPlaced]
       ──REST──> Inventory                                        │
       ──REST──> Notification                    ┌────────────────┼────────────────┐
       ──REST──> Analytics                       ▼                ▼                ▼
                                              Payment        Inventory       Notification
"Order는 4개 서비스를 안다"                  "Order는 아무도 모른다.
"하나 죽으면 Order도 죽는다"                  구독자는 각자 알아서 반응한다"
"새 소비자 추가 = Order 코드 수정"           "새 소비자 추가 = Order 코드 무변경"
```

### 두 개의 큰 축: Event Notification vs Event-Carried State Transfer

EDA를 실무에 도입할 때 가장 먼저 부딪히는 결정은 **"이벤트에 무엇을 담을 것인가"** 다. 이건 단순한 페이로드 설계 문제가 아니라 아키텍처 전체의 결합도를 결정한다.

**Event Notification(알림형 이벤트)** 은 "뭔가 일어났다"만 알린다. 페이로드는 최소한(id, timestamp)이고, 소비자가 필요하면 되돌아와 API를 호출해 상세를 가져간다.

```json
{ "eventType": "OrderPlaced", "orderId": "ord-8821", "occurredAt": "2026-05-25T10:14:22Z" }
```

**Event-Carried State Transfer(상태 운반형 이벤트)** 는 소비자가 필요한 상태 전체를 이벤트에 실어 보낸다. 소비자는 되돌아 호출하지 않는다.

```json
{
  "eventType": "OrderPlaced",
  "orderId": "ord-8821",
  "customerId": "cus-127",
  "items": [{ "sku": "BK-001", "qty": 2, "price": 15000 }],
  "totalAmount": 30000,
  "shippingAddress": { ... },
  "occurredAt": "2026-05-25T10:14:22Z"
}
```

둘의 트레이드오프는 극명하다.

| 관점 | Event Notification | Event-Carried State Transfer |
|------|-------------------|------------------------------|
| 결합도 | 소비자가 발행자 API에 다시 의존 (여전히 결합) | 발행자가 죽어도 소비자는 처리 가능 (진짜 분리) |
| 페이로드 크기 | 작음 | 큼 (때로 수 KB) |
| 데이터 신선도 | 조회 시점 최신 | 이벤트 발행 시점의 스냅샷 (stale 가능) |
| 스키마 관리 | 얇음 | 두꺼움 — 스키마 진화가 큰 문제로 부상 |
| 언제 쓰나 | 소비자가 극소수, 발행자가 항상 사는 시스템 | 소비자가 많고 발행자 부하를 낮춰야 할 때 |

넷플릭스는 초기 EDA에서 Event Notification을 많이 썼는데, 결과적으로 이벤트를 받은 서비스들이 다시 원본 서비스로 폭발적인 fan-in 호출을 만들어냈다. "이벤트로 분리했다"고 믿었지만 실제로는 **호출 방향만 뒤집힌 동기 결합**이었다. 이후 State Transfer 방식으로 이동하며 진짜 분리를 얻었다. 반면 우버는 위치 데이터처럼 초당 수십만 건이 발생하는 이벤트에는 Notification만 담고, 필요한 서비스가 별도 API로 상세를 가져가는 방식을 유지한다 — 페이로드 크기가 시스템 전체를 죽이기 때문이다.

### EDA가 진짜로 해결하는 것: 시간적 결합의 해체

동기 호출의 근본 문제는 "동시에 살아 있어야 한다"는 제약이다. `OrderService`가 `PaymentService`를 호출하는 순간, 두 서비스는 **같은 밀리초에 둘 다 건강해야** 한다. 하나가 GC 스톱만 걸려도 다른 하나가 타임아웃을 겪는다. 서비스가 10개면 이 조합은 기하급수적으로 늘어난다.

EDA는 브로커(Kafka, RabbitMQ, SNS/SQS)에 이벤트를 밀어넣고, 브로커가 살아 있는 한 발행자와 소비자는 **서로 다른 시간대에 살아 있어도 된다.** `NotificationService`가 30분간 죽어 있어도, 부활하면 밀렸던 이벤트를 순서대로 처리한다. 발행자는 애초에 그런 일이 있었는지도 모른다. 이것이 **비동기의 진짜 가치** — 성능이 아니라 **가용성의 독립** 이다.

넷플릭스 Keystone은 하루 수천억 개 이벤트를 Kafka로 흘리며, "재생 시작", "일시정지", "품질 조정" 같은 사실들이 추천/분석/과금/A/B 테스트/장애 감지 서비스로 각자 흘러간다. 어떤 소비자가 죽어도 재생 자체는 계속된다 — 이게 넷플릭스가 배포를 하루 수천 번 하면서도 서비스가 안 멈추는 이유다. Uber의 Cadence(현재 Temporal)도, LinkedIn의 Kafka 자체도 이 철학에서 태어났다.

### 어두운 면: EDA가 만드는 새로운 종류의 지옥

EDA를 도입하면 사라진 문제 대신 **완전히 다른 종류의 문제들**이 생긴다. 이걸 모르고 도입하는 팀은 6개월 후 "REST로 돌아가고 싶다"는 말을 하게 된다.

**1. 흐름을 추적할 수 없다.** `OrderPlaced` 이벤트 하나가 15개 서비스에 어떻게 퍼지고 어떤 후속 이벤트를 낳는지, 그 인과 그래프를 코드만 봐서는 알 수 없다. 이걸 해결하려면 반드시 **분산 트레이싱(OpenTelemetry, Jaeger)** 과 **이벤트 카탈로그**(EventCatalog, AsyncAPI 같은 문서화)를 강제해야 한다. 안 하면 신입이 "이 이벤트를 처리하는 서비스가 어디 있는지" 알아내는 데만 이틀이 걸린다.

**2. 순서 보장이 어렵다.** Kafka는 파티션 내에서만 순서를 보장한다. `OrderPlaced` 다음에 `OrderCancelled`가 와야 하는데 파티셔닝 키를 잘못 잡으면 취소가 먼저 도착한다. 파티션 키는 보통 **어그리게이트 ID**(orderId, userId)로 잡아야 하는데, 이걸 도메인마다 정확히 설계하는 건 생각보다 어렵다.

**3. 최소 한 번 전달(at-least-once)이 표준이다.** Kafka도, SQS도, 대부분의 브로커는 "정확히 한 번"을 보장하지 않는다. 같은 이벤트가 두 번 도착할 수 있다는 뜻이다. 그래서 모든 소비자는 반드시 **멱등성(idempotency)** 을 구현해야 한다. 이걸 안 지키면 어느 날 "주문이 두 번 결제됐다"는 CS가 들어온다.

**4. 스키마 진화가 조직 문제가 된다.** 발행자가 `OrderPlaced`에 새 필드를 추가할 때, 15개 소비자 중 몇 개가 깨질지 발행자는 모른다. Schema Registry(Confluent, AWS Glue), 하위 호환 규칙(BACKWARD compatibility), 스키마 리뷰 프로세스가 없으면 이벤트가 "고쳐질 수 없는 공용 API"가 되어 발전이 멈춘다.

**5. 결과적 일관성이 사용자에게 노출된다.** 사용자가 주문 직후 "주문 내역" 페이지를 열었는데 아직 프로젝션에 반영되지 않아 안 보인다. 이건 버그가 아니라 아키텍처의 자연스러운 결과다. UX 팀과 미리 합의해야 하고, 필요하면 "방금 만든 항목은 화면에 stub으로 보여주기" 같은 대응이 필요하다.

### 언제 쓰고, 언제 쓰면 안 되는가

**써야 할 때:**
- **하나의 사실이 여러 소비자를 낳는 도메인.** 주문/결제/재고/알림/분석이 모두 반응해야 하는 이커머스, 사용자 행동 로그가 추천/광고/과금으로 흐르는 미디어 플랫폼.
- **발행자와 소비자의 릴리스 주기가 다를 때.** 발행자 팀은 하루에 5번 배포하고 소비자 팀은 주 1회 배포하는 조직 구조 — 동기 호출로는 답이 없다.
- **fan-out이 필요하고 부하가 큰 시스템.** 넷플릭스, 카카오, 우버처럼 이벤트당 소비자가 5개 이상.
- **감사 로그가 자연 부산물로 필요할 때.** 금융, 헬스케어 — 어차피 이벤트 로그를 남겨야 한다면 그 로그가 아키텍처 자체가 되도록.

**쓰면 안 될 때:**
- **소비자가 1~2개인 소규모 시스템.** 그냥 REST 호출하는 게 10배 단순하다. Kafka 클러스터 운영 비용이 얻는 것보다 크다.
- **강한 일관성이 필수인 트랜잭션.** 계좌 이체처럼 "즉시 반영, 즉시 확인"이 필요하면 EDA는 오히려 방해다. 이런 건 단일 서비스 내 DB 트랜잭션이 답.
- **동기 응답이 UX상 필수인 흐름.** 로그인, 결제 승인 화면 — 사용자가 결과를 기다리는 흐름은 이벤트로 풀면 안 된다.
- **팀에 분산 시스템 경험이 없을 때.** EDA는 "쉬워 보이지만 실제로 어려운" 대표적 사례다. 트레이싱/멱등성/스키마 관리를 자신 있게 못 하는 조직이 도입하면 REST 세계보다 훨씬 큰 부채를 만든다.

### 시니어의 관점

EDA는 **"우리는 서로를 모르는 편이 낫다"** 는 조직적 판단이다. 이건 기술 선택이 아니라 **팀 자율성과 시스템 진화 속도**에 대한 베팅이다. 서비스가 5개일 때는 REST가 이긴다. 서비스가 30개가 되고 팀이 10개가 되면, EDA를 쓰는 조직만이 배포 독립성과 장애 격리를 유지한다. 반대로 도메인 이해가 얕은 상태에서 EDA를 도입하면 "이벤트 스파게티" — 누가 무엇을 발행하고 누가 무엇을 소비하는지 아무도 모르는 상태 — 가 된다. **EDA의 성공 조건은 Kafka가 아니라 Bounded Context와 이벤트 카탈로그다.** 도구는 그 다음이다.

> 💡 **왜 중요한가**: EDA는 성능 최적화가 아니라 "서비스들이 서로 몰라도 되게 만드는" 조직·아키텍처적 결합 해체이며, 이 결합을 못 끊으면 MSA는 이름만 MSA인 분산 모놀리스로 귀결된다.
