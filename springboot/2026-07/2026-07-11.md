### `@Transactional(propagation = Propagation.REQUIRES_NEW)`는 같은 클래스 내부 호출 시 새 트랜잭션이 열리지 않는다

`REQUIRES_NEW`는 별도 트랜잭션을 시작해 부모 트랜잭션과 독립적으로 커밋/롤백되지만, 이는 스프링 AOP 프록시를 거쳐야만 동작한다. 같은 빈 내부 메서드에서 `this.saveLog()`처럼 직접 호출하면 프록시가 개입하지 않아 부모 트랜잭션이 그대로 이어지고, 롤백이 나면 로그까지 함께 사라진다.

```java
@Service
public class OrderService {
    @Autowired private OrderService self; // 자기 자신을 프록시로 주입

    @Transactional
    public void placeOrder(Order order) {
        orderRepository.save(order);
        self.saveAuditLog(order); // this가 아닌 self로 호출해야 REQUIRES_NEW 적용
        throw new RuntimeException("결제 실패"); // audit log는 남아있음
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveAuditLog(Order order) { ... }
}
```

> 💡 **왜 중요한가**: 감사 로그, 실패 알림처럼 "무조건 남아야 하는" 사이드 이펙트가 부모 롤백에 휩쓸려 사라지는 사고를 막을 수 있다.

---

### `@ConditionalOnMissingBean`은 같은 `@Configuration` 안에서 정의 순서에 의존한다

`@ConditionalOnMissingBean`은 특정 타입의 빈이 없을 때만 자동 등록되도록 하는 조건 어노테이션이다. 하지만 같은 설정 클래스 안에서 두 개의 `@Bean`을 정의할 때는 메서드 정의 순서가 조건 평가에 영향을 준다 — 조건이 걸린 빈이 다른 빈보다 먼저 선언되어 있으면 아직 대상 빈이 존재하지 않는 시점에 평가되어 항상 조건이 참이 된다.

```java
@Configuration
class AppConfig {
    @Bean
    @ConditionalOnMissingBean // 위쪽에 있으면 아래 objectMapper()가 아직 없다고 판단
    public ObjectMapper objectMapper() { return new ObjectMapper(); }

    @Bean
    public ObjectMapper customObjectMapper() { return new CustomMapper(); }
}
```

라이브러리 사용자가 자기 `ObjectMapper`를 오버라이드하려는 상황에서는 반드시 별도 `@Configuration` 클래스로 분리하거나, 사용자 설정 클래스가 라이브러리 설정보다 먼저 로드되도록 `@AutoConfigureBefore`를 활용해야 한다.

> 💡 **왜 중요한가**: 자동 설정 라이브러리를 만들 때 사용자의 커스텀 빈이 조용히 무시되는 원인 대부분이 이 순서 문제다.
