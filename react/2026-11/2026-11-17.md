### 1. `useRef`는 "값을 저장하는 상자"가 아니다 — 리렌더링을 유발하지 않는 "변경 가능한 서랍"의 진짜 용도

많은 개발자가 `useRef`를 단순히 DOM 노드 접근용으로만 쓰지만, 실제로는 "렌더링과 무관하게 값을 유지해야 할 때" 쓰는 이스케이프 해치다. `useState`는 값이 바뀌면 리렌더링을 트리거하지만, `useRef.current`는 아무리 바꿔도 컴포넌트가 다시 그려지지 않는다. 그래서 setInterval ID, 이전 값(previous value), throttle/debounce 타이머, 외부 라이브러리 인스턴스처럼 "저장은 해야 하지만 UI와 무관한 값"을 담는 용도로 쓴다.

```jsx
function Timer() {
  const [count, setCount] = useState(0);
  const intervalRef = useRef(null); // 리렌더링과 무관한 저장소

  useEffect(() => {
    intervalRef.current = setInterval(() => {
      setCount(c => c + 1);
    }, 1000);
    return () => clearInterval(intervalRef.current);
  }, []);

  // ❌ 만약 useState(null)로 저장했다면?
  // setInterval ID가 바뀔 때마다 리렌더링 → 또 다른 setInterval 생성 → 무한 루프
  return <button onClick={() => clearInterval(intervalRef.current)}>정지</button>;
}

// 흔한 패턴: 이전 값 추적
function usePrevious(value) {
  const ref = useRef();
  useEffect(() => { ref.current = value; }); // 렌더 후 저장
  return ref.current; // 렌더 중에는 "이전" 값
}
```

핵심은 **"ref.current를 렌더링 중에 읽거나 쓰지 말라"**는 React의 규칙이다. 렌더 함수는 순수해야 하는데, ref를 렌더 중 수정하면 "같은 입력에 다른 출력"이 나올 수 있다. 오직 이벤트 핸들러, useEffect 안, 또는 콜백에서만 ref.current를 건드려야 한다.

> 💡 **왜 중요한가**: `useState`를 "저장소"로 오남용하면 불필요한 리렌더링과 stale closure 지옥에 빠지고, `useRef`를 모르면 "렌더링과 상태의 분리"라는 React의 가장 중요한 멘탈 모델을 놓친다.

### 2. `useCallback`은 "함수 재생성을 막는 최적화"가 아니다 — `React.memo`나 의존성 배열과 짝지어야 의미가 생기는 "참조 안정화" 도구

초보자가 가장 많이 하는 실수는 모든 함수를 `useCallback`으로 감싸는 것이다. 사실 `useCallback` 자체는 **오히려 메모리와 CPU를 더 쓴다** — 함수를 저장하고, 의존성을 비교하고, 캐시를 유지하기 때문이다. 그런데도 쓰는 이유는 딱 두 가지뿐이다: (1) 자식 컴포넌트가 `React.memo`로 감싸져 있어서 props로 전달되는 함수의 참조 동일성이 필요할 때, (2) 다른 Hook의 의존성 배열에 그 함수가 들어갈 때.

```jsx
// ❌ 무쓸모: Child가 memo도 아니고, 의존성 배열에도 안 들어감
function Parent() {
  const handleClick = useCallback(() => console.log('click'), []);
  return <Child onClick={handleClick} />; // 어차피 매번 리렌더링됨
}

// ✅ 의미 있음: memo된 자식에게 안정적인 참조 전달
const Child = React.memo(({ onClick }) => {
  console.log('Child 렌더링');
  return <button onClick={onClick}>클릭</button>;
});

function Parent() {
  const [count, setCount] = useState(0);
  const handleClick = useCallback(() => {
    console.log('click');
  }, []); // 의존성 [] → 참조 고정

  return (
    <>
      <button onClick={() => setCount(c => c + 1)}>{count}</button>
      <Child onClick={handleClick} /> {/* count가 바뀌어도 Child는 리렌더링 X */}
    </>
  );
}

// ✅ useEffect 의존성 안정화
function Search({ query }) {
  const fetchData = useCallback(async () => {
    const res = await fetch(`/api?q=${query}`);
    return res.json();
  }, [query]);

  useEffect(() => {
    fetchData(); // fetchData가 매 렌더마다 새로 생기면 useEffect가 무한 호출됨
  }, [fetchData]);
}
```

React 19의 **React Compiler**가 정식 안정화되면 이 모든 수동 최적화가 자동화된다. 하지만 그전까지는 "`useCallback`을 쓰는 순간, 그 함수가 왜 참조 안정성이 필요한지 설명할 수 있어야 한다"는 원칙을 지켜야 한다. 설명할 수 없다면 그건 그냥 성능을 깎아먹는 보일러플레이트다.

> 💡 **왜 중요한가**: `useCallback`/`useMemo`를 반사적으로 남발하는 코드베이스는 "최적화한다는 착각 속에서 오히려 느려지는" 전형적인 안티패턴이며, 메모이제이션의 비용-편익을 이해해야 React 성능 튜닝의 다음 단계로 넘어갈 수 있다.
