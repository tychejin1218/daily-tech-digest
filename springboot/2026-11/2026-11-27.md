### 1. Spring Boot의 `@ConfigurationProperties`는 **`setter`가 없으면 바인딩이 조용히 실패한다** — 그래서 `application.yml`에 값을 분명히 적어놓고도 필드가 `null`로 들어오는 상황이 벌어진다

`@ConfigurationProperties`는 기본적으로 JavaBeans 규약을 따라 `setter`를 통해 값을 주입한다. 그래서 Lombok의 `@Getter`만 붙이고 `@Setter`를 빠뜨리거나, 불변 객체로 만들겠다고 `final` 필드로 선언하면 바인딩 자체가 실패한 채로 애플리케이션이 "정상 기동"해 버린다. 불변으로 가고 싶다면 생성자 바인딩을 명시적으로 켜야 한다 — 클래스에 `@ConstructorBinding`을 붙이고 `@EnableConfigurationProperties(MyProps.class)`로 등록하거나, Spring Boot 3.x에서는 `record` 타입으로 선언하면 자동으로 생성자 바인딩이 적용된다.

```java
// ❌ 조용히 실패 — setter가 없어 값이 안 들어온다
@ConfigurationProperties(prefix = "app.redis")
@Getter
public class RedisProps {
    private String host;      // null
    private int port;         // 0
}

// ✅ 불변으로 가고 싶다면 생성자 바인딩
@ConfigurationProperties(prefix = "app.redis")
public record RedisProps(String host, int port) {}
```

> 💡 **왜 중요한가**: "설정값이 분명히 있는데 왜 `null`이지?"라며 YAML을 몇 번이고 들여다보게 만드는 함정이고, 바인딩 실패가 기동 에러가 아니라 런타임 `NullPointerException`으로 지연되기 때문에 production에서 터지면 원인 추적이 오래 걸린다.

### 2. Spring Boot의 `@Scheduled` 메서드는 **기본적으로 단일 스레드 풀에서 순차적으로 실행된다** — 그래서 스케줄러를 여러 개 등록해 두면, 하나가 늦어지는 순간 다른 스케줄러들이 줄줄이 밀려서 "분명히 1분마다 돌라고 했는데" 10분 뒤에 실행되는 일이 벌어진다

`@EnableScheduling`만 켜면 Spring은 내부적으로 `ThreadPoolTaskScheduler`가 아닌 **단일 스레드** `ScheduledExecutorService`를 쓴다. 즉 `@Scheduled`가 붙은 메서드가 10개여도 한 번에 하나씩만 돌아간다. 한 작업이 DB락이나 외부 API 호출로 3분을 잡아먹으면, 그 시간 동안 다른 모든 스케줄러는 큐에서 대기한다. 해결하려면 `TaskScheduler` 빈을 직접 등록해 풀 크기를 명시적으로 늘려야 한다.

```java
// ✅ 스케줄러 풀을 명시적으로 늘려준다
@Configuration
@EnableScheduling
public class SchedulingConfig implements SchedulingConfigurer {
    @Override
    public void configureTasks(ScheduledTaskRegistrar registrar) {
        ThreadPoolTaskScheduler scheduler = new ThreadPoolTaskScheduler();
        scheduler.setPoolSize(10);
        scheduler.setThreadNamePrefix("scheduled-");
        scheduler.initialize();
        registrar.setTaskScheduler(scheduler);
    }
}
```

> 💡 **왜 중요한가**: 배치성 작업이 늘어날수록 "왜 특정 시간대만 스케줄이 밀리지?"라는 유령 같은 지연 현상을 만들고, 풀 크기를 바꾸지 않으면 `@Scheduled` 메서드 하나가 사실상 전체 스케줄러 라인을 인질로 잡는 구조가 된다.
