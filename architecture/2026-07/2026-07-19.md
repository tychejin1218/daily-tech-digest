### 모듈러 모놀리스 — "쪼개기 전에 정리하라"는 아키텍처의 재발견

#### 왜 이 주제가 다시 뜨는가

2015년경 마이크로서비스가 정답처럼 유행하면서 수많은 팀이 "모놀리스는 레거시, MSA는 미래"라는 이분법에 빠졌다. 그러나 2020년 이후 Shopify, GitHub, Basecamp 등이 공개적으로 "우리는 마이크로서비스가 아니라 모듈러 모놀리스를 쓴다"고 선언하면서 방향이 재조정됐다. Shopify의 Rails 모놀리스는 여전히 세계 최대급 커머스 트래픽을 처리하고, GitHub도 여전히 하나의 Rails 앱이다. **문제는 모놀리스가 아니라 "정리되지 않은 모놀리스"였다는 것**이 요지다.

Lv1에서 이미 "모놀리스 = 배포 단위, 설계 단위는 별개"라는 명제를 다뤘다. 모듈러 모놀리스는 이 명제를 실행 가능한 아키텍처로 구현한 형태다.

---

#### 정의: 무엇이 "모듈러"인가

모듈러 모놀리스는 다음 세 가지 조건을 모두 만족해야 한다.

1. **단일 배포 단위** — 하나의 프로세스, 하나의 아티팩트로 배포된다.
2. **명시적 모듈 경계** — 모듈 간 호출은 반드시 공개 API(퍼블릭 인터페이스)를 거친다. 옆 모듈의 내부 클래스에 직접 접근하는 것은 컴파일/린트 단계에서 차단된다.
3. **모듈별 데이터 소유권** — 하나의 물리 DB를 쓰더라도, 각 모듈의 테이블은 그 모듈만 직접 접근한다. 다른 모듈은 API를 통해서만 데이터를 읽는다.

이 세 조건 중 하나라도 빠지면 그냥 "잘 나눠진 모놀리스"이지 모듈러 모놀리스가 아니다. 특히 3번(데이터 소유권)이 가장 자주 무너진다.

```
┌───────────────────────────────────────────────────────────────────┐
│                     Modular Monolith (단일 프로세스)                │
│                                                                    │
│  ┌─────────────────┐   public API   ┌─────────────────┐            │
│  │  Order Module   │◄──────────────►│ Payment Module  │            │
│  │                 │                │                 │            │
│  │  ┌───────────┐  │                │  ┌───────────┐  │            │
│  │  │  domain   │  │                │  │  domain   │  │            │
│  │  │application│  │                │  │application│  │            │
│  │  │  infra    │  │                │  │  infra    │  │            │
│  │  └─────┬─────┘  │                │  └─────┬─────┘  │            │
│  │  ── private ──  │                │  ── private ──  │            │
│  └────────┼────────┘                └────────┼────────┘            │
│           │                                  │                     │
│           ▼                                  ▼                     │
│    ┌──────────────┐                    ┌──────────────┐            │
│    │ orders.*     │  ← 옆 모듈이       │ payments.*   │            │
│    │ (schema)     │    직접 접근 금지 │ (schema)     │            │
│    └──────────────┘                    └──────────────┘            │
│                                                                    │
│                     (하나의 물리 DB, 논리적으로 분리)               │
└───────────────────────────────────────────────────────────────────┘

  ⚡ 모듈 간 통신: in-process 함수 호출 (직렬화 없음)
  ⚡ 트랜잭션:    필요 시 하나의 DB 트랜잭션으로 묶을 수 있음
  🚫 금지 규칙:   Payment 모듈이 orders.* 테이블을 SELECT 하는 것
```

#### 모듈 경계를 어떻게 강제할 것인가

이론은 쉽고 실전은 어렵다. 시니어 관점에서 중요한 건 **"규약을 문서로 두지 말고 도구로 강제하라"**는 원칙이다.

| 방법 | 예시 | 강제력 |
|---|---|---|
| 코드 리뷰만 | "이 import 옆 모듈 건드리네요" | 약함 (사람이 지침) |
| 정적 분석 | Java의 ArchUnit, JS의 dependency-cruiser | 중간 (CI에서 실패) |
| 언어 수준 캡슐화 | Java Modules(JPMS), Rust crate, Kotlin `internal` | 강함 (컴파일 실패) |
| 물리적 분리 | 모듈별 Gradle subproject, `packages/*` monorepo | 강함 + 빌드 캐시 이점 |

Shopify는 Rails에서 이걸 강제하려고 **Packwerk**라는 자체 gem을 만들었다. 각 패키지가 자신의 `public/` 하위만 외부에 노출하고, 그 외 경로에 대한 참조는 CI에서 실패한다. 언어가 이걸 지원하지 않을 때는 이렇게 도구를 만들어서라도 강제해야 한다는 뜻이다.

#### 실제 사례와 채택 이유

**1. Shopify (Rails, 수백만 LOC)**
- 마이크로서비스로 쪼개보려 했으나, 대부분의 도메인 경계가 명확하지 않아 분산 트랜잭션 지옥에 빠짐
- 대신 Packwerk로 모듈 경계를 코드 레벨에서 강제 → "componentization"
- 결과: 팀별 소유권 명확화, 배포는 여전히 단일

**2. GitHub (Rails)**
- 여전히 monolithic Rails 앱. 성능 크리티컬한 일부만 별도 서비스(Git 저장소 접근 등)로 분리
- 대부분의 신규 기능은 여전히 모놀리스 내부에서 개발

**3. Amazon Prime Video (2023년 화제의 사례)**
- 서버리스 마이크로서비스로 만든 오디오/비디오 모니터링 시스템을 **모놀리스로 재통합**하여 비용 90% 절감
- 마이크로서비스 간 S3 왕복, Step Functions 상태 전이 비용이 원흉

**4. DHH / Basecamp**
- "The Majestic Monolith" 선언. 20명 규모 팀에는 마이크로서비스가 불필요한 오버헤드

공통점: **조직 규모가 인프라 오버헤드를 감당할 만큼 크지 않거나, 도메인 경계가 아직 유동적일 때** 모듈러 모놀리스가 승리한다.

#### 트레이드오프

| 항목 | 모듈러 모놀리스 | 마이크로서비스 |
|---|---|---|
| **모듈 간 호출 비용** | in-process (수 ns) | 네트워크 (수 ms) + 직렬화 |
| **트랜잭션** | 단일 DB 트랜잭션 가능 | Saga, 최종 일관성 필요 |
| **배포 독립성** | 없음 (전체 재배포) | 있음 (팀별 독립) |
| **장애 격리** | 없음 (한 모듈 OOM = 전체 다운) | 있음 (부분 장애) |
| **기술 스택 다양성** | 단일 스택 | 모듈별 자유 |
| **디버깅** | 단일 프로세스 → 스택 트레이스 하나로 추적 | 분산 트레이싱 필수 |
| **인프라 복잡도** | 낮음 (하나의 앱 + DB) | 높음 (서비스 메시, 게이트웨이 등) |
| **팀 확장성** | 20~50명 이후 병목 | 100명+ 확장 가능 |
| **초기 개발 속도** | 빠름 | 느림 (경계 설계에 시간) |

핵심 트레이드오프는 **"운영 복잡도 vs 조직 확장성"**이다. 모듈러 모놀리스는 운영 복잡도를 최소화하면서 미래에 마이크로서비스로 쪼갤 수 있는 옵션을 남겨둔다.

#### 언제 쓰고, 언제 쓰면 안 되는가

**써야 하는 경우**
- 도메인 경계가 아직 유동적인 초·중기 스타트업 (경계를 잘못 그으면 마이크로서비스는 재앙)
- 팀 규모 50명 이하, 서비스 수 5개 이하
- 트랜잭션 일관성이 비즈니스적으로 중요한 도메인 (커머스 주문/결제, 금융)
- DevOps/SRE 리소스가 부족한 조직

**쓰면 안 되는 경우**
- 모듈별로 확연히 다른 스케일링 특성이 있을 때 (예: 실시간 스트리밍 + 배치 분석 + 트랜잭션)
- 팀 수가 이미 10개 이상이고 배포 병목이 실제로 발생 중일 때
- 규제 요구사항으로 특정 모듈이 물리적/네트워크적으로 분리돼야 할 때 (예: 카드 정보 처리 PCI-DSS 격리)
- 기술 스택이 완전히 달라야 하는 도메인이 섞여 있을 때 (Python ML + Java 트랜잭션)

**흔한 실패 패턴**
1. **DB 스키마는 하나로 두고 아무나 접근** — 이건 모듈러가 아니라 그냥 모놀리스. 6개월 지나면 조인 지옥
2. **모듈 간 순환 참조** — Order가 Payment를 부르고 Payment가 Order 상태를 수정. 결국 하나의 큰 진흙 덩어리
3. **"나중에 쪼갤 거니까 지금은 대충"** — 나중은 오지 않는다. 처음부터 경계를 강제하지 않으면 영원히 강제할 수 없음

#### 마이크로서비스로의 진화 경로

모듈러 모놀리스의 가장 큰 실용적 가치는 **점진적 분리(strangler fig)의 안전한 출발점**이라는 점이다.

```
Phase 1: Monolith        Phase 2: Modular Monolith    Phase 3: Selective Extraction
┌────────────┐           ┌──────┬──────┬──────┐        ┌──────┬──────┐   ┌──────┐
│  뒤엉킨    │   →       │Order │ Pay  │ Ship │   →   │Order │ Ship │   │ Pay  │
│  코드      │           │ mod  │ mod  │ mod  │        │ mod  │ mod  │   │ svc  │
└────────────┘           └──────┴──────┴──────┘        └──────┴──────┘   └──────┘
                          단일 프로세스                  모놀리스           별도 서비스
                                                     (경계 유지)      (병목 도메인만 분리)
```

경계가 코드 레벨에서 이미 강제돼 있으므로, 특정 모듈을 별도 서비스로 뽑아낼 때 리팩터링 범위가 예측 가능하다. 반대로 뒤엉킨 모놀리스에서 마이크로서비스로 가려면 "이 함수를 부르는 곳이 얼마나 되지?"부터 알 수 없다.

> 💡 **왜 중요한가**: 모듈러 모놀리스는 "마이크로서비스의 이점(경계 명확성)을 갖되, 대가(분산 시스템 복잡도)는 미루는" 전략이다 — 언제 쪼갤지는 조직 규모가 결정하지, 트렌드가 결정하지 않는다.
