### Reranking — "Vector Search top-10을 LLM에 그대로 넘긴다"는 게으름, 그리고 Cross-Encoder가 새벽 2시 CS 티켓의 hallucination을 절반으로 줄이는 방식

RAG 구축 첫 스프린트를 마친 팀의 아키텍처 다이어그램은 대개 이렇게 생겼다.

```
[사용자 질문] → [임베딩] → [Vector DB top-10] → [LLM] → [답변]
```

Notion에 이런 그림 하나 붙여놓고 "우리도 이제 AI 회사예요"라고 선언한다. 그리고 3주 뒤, CS 팀에서 "이 챗봇이 자꾸 없는 정책을 만들어냅니다"라는 티켓이 쌓이기 시작한다. 로그를 뒤져보면 놀랍게도 **retrieval은 잘 되어 있다**. 관련 문서가 top-10 안에 들어와 있다. 그런데 왜 hallucination이 나오는가?

답은 하나다. **관련 문서가 top-10에 있긴 한데, 3위나 7위쯤에 처박혀 있다.** LLM은 컨텍스트 앞쪽을 더 신뢰하는 경향이 있고("Lost in the Middle" 논문이 실증한 바 그대로), 1~2위에 앉아 있는 살짝 관련 있어 보이는 오답 문서가 LLM의 판단을 오염시킨다. Reranking은 이 순서를 뒤집는 층이다.

#### Bi-encoder vs Cross-encoder: 왜 벡터 검색만으로는 부족한가

Vector DB 안에서 도는 임베딩 모델은 **Bi-encoder**다.

```
Bi-encoder:
  embed(query) → 벡터 A
  embed(doc)   → 벡터 B     ← 미리 계산해서 DB에 저장
  score = cosine(A, B)

Cross-encoder:
  score = model(query, doc)  ← query와 doc을 한꺼번에 입력
                              ← Transformer가 둘 사이의 상호작용을 봄
```

Bi-encoder는 query와 doc을 **독립적으로** 인코딩한 뒤 벡터 공간에서 거리를 잰다. 이 방식은 doc 임베딩을 미리 저장할 수 있어서 검색이 밀리초 단위로 끝난다. 500만 문서 검색이 20ms에 끝나는 이유다.

문제는 정확도다. "query와 doc이 같은 벡터 공간에서 가깝다"는 것이, "이 doc이 이 query의 답을 담고 있다"와 같은 명제가 아니다. 벡터 공간은 **의미의 유사성**을 잡지, **답변으로서의 적합성**을 잡지 않는다. "MySQL 8.0 파티셔닝 제약사항"이라는 질문에 "MySQL 8.0 설치 가이드"가 top-1으로 뜨는 이유가 이것이다. 둘 다 MySQL 8.0 이야기니까.

Cross-encoder는 다르다. (query, doc) 쌍을 하나의 시퀀스로 묶어 Transformer에 통째로 넣는다. Attention 헤드가 query 토큰과 doc 토큰 사이의 상호작용을 직접 본다. "이 doc에 이 query의 답이 있는가"를 판단하는 task로 학습되어 있어서 정확도가 압도적으로 높다.

대신 비용이 비대칭이다. 100개 문서를 리랭킹하려면 100번의 Transformer forward pass가 필요하다. Bi-encoder처럼 doc 임베딩을 캐시할 방법이 없다. query가 바뀌면 처음부터 다시 계산해야 한다.

#### 프로덕션 RAG 아키텍처: 2-stage retrieval

```
                   ┌─────────────────────────────────┐
                   │  Stage 1: Retrieval (Recall)    │
                   │  목표: 관련 문서를 놓치지 마라   │
                   └─────────────────────────────────┘
[User Query]
     │
     ├─────────────┐
     ▼             ▼
┌──────────┐  ┌──────────┐
│  BM25    │  │ Vector   │    Bi-encoder
│ (Elastic)│  │ Search   │    5~20ms, cheap
└────┬─────┘  └────┬─────┘
     │             │
     └──────┬──────┘
            ▼
    ┌───────────────┐
    │ Fusion (RRF)  │  top-100 후보 확보
    └───────┬───────┘
            │
            ▼
                   ┌─────────────────────────────────┐
                   │  Stage 2: Reranking (Precision) │
                   │  목표: 최고를 위로 올려라        │
                   └─────────────────────────────────┘
    ┌──────────────────┐
    │ Cross-encoder    │   Cohere Rerank v3 / BGE
    │ Reranker         │   150~400ms, expensive
    │ (query, doc)×100 │
    └───────┬──────────┘
            │ top-5
            ▼
    ┌──────────────────┐
    │      LLM         │
    └──────────────────┘
```

핵심은 **두 단계의 목표가 다르다는 것**이다.

- **Stage 1 (Retrieval)**: Recall이 목표다. "정답이 후보 100개 안에 반드시 들어와야 한다." 여기서 놓치면 뒷단계에서 아무리 잘해도 복구 불가능. 그래서 싸고 넓게 잡는다 (BM25 + Vector Hybrid).
- **Stage 2 (Reranking)**: Precision이 목표다. "100개 중 진짜 답을 top-3에 올려라." 여기서는 비싸도 정확해야 한다.

이 분리는 그냥 아름다운 이론이 아니다. **비용 함수가 근본적으로 다르기 때문에** 두 층을 나눈다. Stage 1은 문서 수 N에 대해 sub-linear (HNSW는 대략 O(log N))로 확장되지만, Stage 2는 후보 수 K에 대해 O(K) 선형이다. K를 100으로 두면 감당 가능하지만, 500만 문서 전체를 Cross-encoder로 돌리는 건 지구가 뜨거워지는 일이다.

#### 실제 사례: Anthropic Contextual Retrieval의 숫자

Anthropic이 2024년 9월 공개한 "Contextual Retrieval" 실험은 이 아키텍처의 각 층이 얼마나 기여하는지 정직하게 보여줬다.

| 파이프라인 | Retrieval Failure Rate |
|---|---|
| Vector only (Naive RAG) | 5.7% |
| + BM25 (Hybrid) | 4.9% |
| + Contextual embeddings | 3.7% |
| + Reranker (Cohere Rerank) | **1.9%** |

Vector-only 대비 **retrieval 실패율이 67% 감소**했다. 이 중 상당 부분이 reranker의 몫이다. 200ms의 지연을 추가로 감수하고 얻은 대가치고는 남는 장사다.

Perplexity의 검색 파이프라인도 유사한 구조다. 그들은 자체 학습한 reranker를 쓴다고 알려져 있는데, 이유는 도메인 특화 재순위가 오답률에 직접 꽂히기 때문이다. Notion Q&A, Glean, Elastic ESRE 같은 엔터프라이즈 검색 스택도 대부분 Cohere Rerank 아니면 자체 BGE 파생 모델을 붙인다.

한편 GitHub Code Search는 reranker를 안 쓴다. 왜? 코드 검색은 정확한 심볼 매칭이 곧 답이라, BM25 top-K가 이미 충분히 정확하다. 자연어 QA와는 성격이 다르다.

#### 트레이드오프: 무엇을 지불하는가

**지연 시간의 재조명**

Reranker는 대략 100~400ms의 지연을 추가한다. Cohere Rerank v3는 100 문서 기준 ~300ms, BGE-Reranker-Large는 GPU 위에서 ~150ms, ColBERT (late interaction) 는 ~80ms 수준이다.

LLM이 답변 생성에 이미 2~5초를 쓰는 시스템에서 이 300ms는 노이즈다. 하지만 검색 API를 그대로 노출하는 시스템(예: Elasticsearch 대체)에서는 300ms가 재앙이다. **누가 이 시스템을 소비하는가**가 reranker 도입 여부를 결정한다.

**비용의 재조명**

Cohere Rerank는 대략 1,000 검색당 $2 수준이다. 하루 100만 검색이면 $2,000/일, 월 $60,000. 감당 가능한가? SaaS 스타트업 초기에는 세게 아프다. 반면 오픈소스 BGE-Reranker를 자체 GPU에 올리면 인프라 비용은 A10 한 대(대략 $0.6/시간, 월 $500)면 충분하지만, 모델 서빙/배치/장애 대응 인력이 필요하다. **관리형이냐 셀프냐**는 팀 크기에 따라 다르다.

**리랭커의 실패 모드**

Reranker도 hallucination의 원인이 될 수 있다. Cross-encoder는 학습 데이터의 분포를 강하게 반영하는데, 도메인이 학습셋과 멀면(의료, 법률, 금융 내부 문서) 오히려 BM25보다 못한 순위를 뽑기도 한다. **"Reranker 붙였는데 왜 더 나빠졌지?"** 라는 상황이 실제로 있다. 도메인 파인튜닝 없이 general-purpose reranker를 그대로 얹었을 때 흔히 벌어진다.

#### 시니어 백엔드 관점: 언제 쓰고 언제 쓰지 말 것

**써야 하는 경우**

- 자연어 QA 시스템 (문서 기반 챗봇, 내부 지식 검색, CS 자동응답)
- Retrieval 후보가 20개 이상이고 그 중 top-3만 LLM에 넣는 구조
- LLM API 비용이 컨텍스트 토큰에 민감한 경우 (top-3만 넣으면 토큰이 절반으로 준다)
- 답변 품질에 대한 SLA가 존재하고, retrieval failure rate를 측정 중인 팀

**쓰지 말아야 하는 경우**

- 코드 검색, 심볼 검색, 정확 매칭 위주의 도메인 (BM25 top-K로 충분)
- 사용자 대면 지연 예산이 500ms 이하인 실시간 검색 API
- 후보가 애초에 10개 이하로 나오는 좁은 도메인 (재순위할 이유 없음)
- Retrieval failure rate를 아직 측정 안 하고 있는 팀 (측정 없이 도입하면 무엇이 좋아졌는지 증명 불가 → [[mlops-for-llm]] 참조)
- 학습 데이터와 도메인 격차가 큰 특수 분야에서 **파인튜닝 없이** 그냥 얹으려는 경우

**아키텍처 판단 기준**

Reranker는 [[hybrid-search]]와 함께 있을 때 진가가 나온다. Hybrid로 recall을 확보하고, reranker로 precision을 확보하는 구조. Hybrid 없이 벡터 단일 검색에 reranker만 붙이면 recall 병목이 그대로 남아서 효과가 반감된다. 반대로 hybrid만 있고 reranker가 없으면 LLM 컨텍스트에 노이즈 문서가 섞여 들어가 hallucination이 조용히 증가한다. 이 두 층은 세트로 설계해야 한다.

그리고 잊지 마라. Reranker의 효과는 [[ai-observability]] 없이는 증명되지 않는다. "top-3에 정답이 있는가"를 측정하는 지표(recall@3, MRR, NDCG)를 [[mlops-for-llm]]의 eval 파이프라인에 집어넣지 않으면, reranker가 실제로 일하는지 알 수 없다. **측정하지 않는 층은 존재하지 않는 층이다.**

> 💡 **왜 중요한가**: 벡터 검색의 "가까움"은 "답임"과 다르며, 이 간극을 메우는 유일한 실전 레버가 Cross-encoder reranker다.
