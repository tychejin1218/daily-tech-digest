### MySQL `Index Condition Pushdown (ICP)` — 스토리지 엔진까지 WHERE 절을 밀어넣어 불필요한 행 읽기 자체를 없애기

전통적으로 옵티마이저는 인덱스로 위치를 찾고 테이블에서 행을 가져온 뒤 서버 계층에서 WHERE 조건을 평가했지만, ICP는 인덱스에 이미 존재하는 컬럼 조건을 스토리지 엔진(InnoDB) 레벨에서 먼저 필터링한다. 예를 들어 `INDEX(last_name, first_name)`에서 `WHERE last_name LIKE 'K%' AND first_name = 'Jane'` 같은 쿼리를 실행할 때, 선행 컬럼만 범위 조건이라 후행 컬럼은 인덱스로 좁힐 수 없지만 ICP가 켜져 있으면 인덱스 튜플에서 `first_name`을 미리 체크해 매칭되지 않는 행은 테이블 접근을 아예 건너뛴다. `EXPLAIN` 결과의 `Extra` 컬럼에 `Using index condition`이 뜨면 ICP가 적용된 상태이며, 반대로 함수·형변환이 걸린 조건은 인덱스 레벨에서 평가할 수 없어 ICP가 무력화된다.

> 💡 **왜 중요한가**: "인덱스를 탔는데 왜 여전히 느린가"의 답이 대부분 여기다. 인덱스는 위치만 찾아주지 필터링은 서버가 하는데, ICP가 없으면 조건에 안 맞는 행까지 랜덤 I/O로 읽어와서 버린다.

### PostgreSQL `TOAST(The Oversized-Attribute Storage Technique)` — 큰 필드가 조용히 행을 부풀리고 쿼리를 느리게 만드는 진짜 원인

PostgreSQL은 한 행이 페이지(기본 8KB)를 초과할 수 없기 때문에, 2KB(TOAST_TUPLE_THRESHOLD)를 넘는 가변 길이 컬럼(TEXT, JSONB, BYTEA 등)을 자동으로 별도의 TOAST 테이블에 압축·분할 저장한다. 문제는 이런 TOAST된 컬럼을 `SELECT *`로 매번 가져오면 메인 테이블뿐 아니라 TOAST 테이블에서도 랜덤 I/O가 발생해 시퀀셜 스캔 성능이 급격히 나빠진다는 점이다. `SELECT pg_column_size(col), pg_total_relation_size('table')`로 실제 크기와 TOAST 오버헤드를 진단할 수 있고, `ALTER TABLE ... SET STORAGE MAIN|EXTERNAL|EXTENDED|PLAIN`으로 컬럼별 저장 전략(압축 여부, TOAST 사용 여부)을 조정할 수 있다. JSONB 같은 큰 필드는 자주 조회하지 않는다면 `EXTERNAL`(압축만 안 함) 대신 기본 `EXTENDED`가 낫고, 반대로 압축·해제 CPU가 부담이면 `EXTERNAL`로 압축을 끄는 게 유리하다.

> 💡 **왜 중요한가**: "왜 이 테이블은 인덱스도 안 타는데 갑자기 느려졌나"의 범인이 대개 TOAST다. JSONB에 큰 페이로드를 던지는 순간 `SELECT *` 한 방이 수배의 I/O를 유발하는데, 이걸 모르면 인덱스만 계속 추가하다 원인을 놓친다.
