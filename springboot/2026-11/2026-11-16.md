### 1. Spring Boot의 `@ConfigurationProperties`는 **`@Value`와 달리 setter(또는 생성자) 바인딩이 실패해도 조용히 기본값으로 넘어간다** — 그래서 YAML 오타 하나가 "분명히 설정했는데 왜 반영이 안 되지?"라는 미궁을 만든다

`@Value("${app.timeout}")`는 프로퍼티가 없으면 애플리케이션 기동 자체가 실패하지만, `@ConfigurationProperties`는 바인딩 실패 시 해당 필드만 기본값(또는 null)으로 남긴다. 심지어 `app.time-out`과 `app.timeOut`, `app.TIME_OUT`은 모두 같은 필드에 매핑되는 **Relaxed Binding** 규칙 때문에, 오타난 프로퍼티는 "맞는 것처럼 보이지만" 바인딩되지 않은 채 조용히 무시된다. 안전하게 가려면 `spring.config.import` + `@Validated` + `@NotNull`을 걸어 기동 시점에 실패하도록 강제해야 한다.

```
app:
  time-out: 3000   # ✅ 바인딩됨
  timeOut: 3000    # ✅ 바인딩됨 (같은 필드)
  tim-out: 3000    # ❌ 오타지만 에러 없음, timeout은 null
```

> 💡 **왜 중요한가**: "설정이 안 먹힌다"의 80%는 코드 버그가 아니라 조용히 실패한 바인딩이며, `@Validated` 없는 `@ConfigurationProperties`는 프로덕션에서 가장 긴 디버깅 시간을 만드는 원흉이다.

### 2. Spring Boot의 `@Primary`는 **`@Qualifier`가 있으면 완전히 무시된다** — 그래서 "기본 빈"이라고 선언해놓고도, 호출자가 명시적으로 이름을 지정하는 순간 네가 설계한 폴백은 작동하지 않는다

`@Primary`는 "타입이 애매할 때 나를 골라라"는 신호일 뿐이지, "내가 왕이다"가 아니다. 주입 지점에 `@Qualifier("otherBean")`이 붙어 있으면 Spring은 `@Primary`를 쳐다보지도 않고 지정된 이름의 빈을 주입한다. 더 위험한 건, 테스트에서 `@MockBean`으로 `@Primary` 빈을 덮어쓰려 할 때 다른 곳에서 `@Qualifier`로 특정 구현을 콕 집어 주입받고 있으면 **그 테스트에서만 Mock이 안 먹히는** 상황이 벌어진다는 점이다.

```java
@Primary @Service("fast") class FastImpl implements Service {}
@Service("slow") class SlowImpl implements Service {}

// 아래 주입은 FastImpl이 아니라 SlowImpl이 들어간다
@Autowired @Qualifier("slow") Service service;
```

> 💡 **왜 중요한가**: `@Primary`는 "기본값"이고 `@Qualifier`는 "명시적 지정"인데, 명시가 항상 기본을 이긴다 — 이 우선순위를 모르면 "분명히 Mock으로 바꿨는데 왜 실제 구현이 호출되지?"라는 유령 버그에 시달린다.
