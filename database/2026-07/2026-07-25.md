### PostgreSQL `BRIN 인덱스` — 시계열·로그 테이블에서 B-Tree의 1/100 크기로 범위 스캔 처리하기

`BRIN(Block Range Index)`은 페이지 블록 범위마다 최소/최대값만 저장하는 초경량 인덱스로, 물리적 순서와 논리적 순서가 일치하는 컬럼(생성일시, 자동증가 ID 등)에 적합하다. 10억 행 로그 테이블에 `CREATE INDEX ON logs USING BRIN (created_at) WITH (pages_per_range = 128)`을 걸면 B-Tree 대비 인덱스 크기가 수백 배 작아지고, 삽입 오버헤드도 거의 없다.

```sql
-- 3억 행 이벤트 테이블, created_at 순으로 물리 저장
CREATE INDEX idx_events_brin ON events
  USING BRIN (created_at) WITH (pages_per_range = 64);

-- B-Tree: 6GB, BRIN: 40MB (150배 차이)
SELECT pg_size_pretty(pg_relation_size('idx_events_brin'));

-- 범위 스캔에서 실제로 읽는 페이지만 필터링
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM events
WHERE created_at BETWEEN '2026-07-01' AND '2026-07-07';
```

단, 데이터가 물리적으로 정렬되어 있지 않으면 효과가 급락하므로 `CLUSTER`나 파티셔닝과 함께 쓴다. 카디널리티가 낮거나 랜덤 삽입되는 컬럼에는 부적합.

> 💡 **왜 중요한가**: 시계열 워크로드에서 B-Tree를 무작정 만들면 인덱스 크기가 테이블만큼 커지지만, BRIN은 물리적 순서를 활용해 극소 크기로 같은 범위 필터링을 해낸다.

### MySQL `Covering Index`와 `Index Condition Pushdown` — 테이블 접근 없이 쿼리를 인덱스만으로 끝내기

`Covering Index`는 `SELECT`·`WHERE`·`ORDER BY`에 필요한 모든 컬럼이 인덱스에 포함된 경우로, InnoDB가 클러스터드 인덱스(테이블 본체)까지 방문하지 않고 세컨더리 인덱스만 읽고 끝낸다. `EXPLAIN`의 `Extra` 컬럼에 `Using index`가 뜨면 커버링이 성립한 것이다. 여기에 8.0의 `Index Condition Pushdown(ICP)`이 결합되면, 인덱스에 포함되지 않은 조건도 스토리지 엔진 단에서 미리 필터링해 상위 계층으로 넘어가는 행 수를 줄인다.

```sql
-- BAD: name만 인덱싱 → 매 행마다 PK로 테이블 접근
CREATE INDEX idx_users_name ON users(name);
SELECT id, name, email FROM users WHERE name LIKE 'kim%';
-- Extra: NULL (테이블 lookup 발생)

-- GOOD: 필요한 컬럼 모두 인덱스에 포함 (커버링)
CREATE INDEX idx_users_name_email ON users(name, email);
SELECT id, name, email FROM users WHERE name LIKE 'kim%';
-- Extra: Using index (인덱스만으로 처리)

-- ICP 예: 인덱스 (last_name, first_name)에서
-- first_name LIKE '%son'을 스토리지 엔진 단에서 필터
SELECT * FROM employees
WHERE last_name = 'Park' AND first_name LIKE '%son';
-- Extra: Using index condition
```

인덱스에 컬럼을 무한정 추가하면 쓰기 비용이 커지므로, 실측(`SHOW STATUS LIKE 'Handler_read%'`)으로 hot 쿼리에만 적용한다.

> 💡 **왜 중요한가**: 세컨더리 인덱스 lookup 후 테이블 재접근은 랜덤 I/O 폭탄의 주범이며, 커버링과 ICP는 이 왕복을 제거해 지연시간을 한 자릿수 ms로 낮춘다.
