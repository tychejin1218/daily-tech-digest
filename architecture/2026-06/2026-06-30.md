### 트랜잭션 경계 설계: 왜 Service 레이어에 두는가, 그리고 어디서 새는가

#### 1. 트랜잭션 경계(Transaction Boundary)란

트랜잭션 경계는 "어디서 `BEGIN`이 시작되고, 어디서 `COMMIT/ROLLBACK`이 결정되는가"의 코드상 위치를 말한다. 곧 **하나의 원자적 비즈니스 작업이 시작되고 끝나는 지점**이다. 단순히 `@Transactional`을 어디에 붙이느냐의 문제가 아니라, **"무엇이 하나의 원자 단위인가"를 도메인 관점에서 정의하는 행위**다.

```
주문 생성이라는 "하나의 일"은 무엇으로 구성되는가?
 → 주문 INSERT + 재고 차감 UPDATE + 결제 요청 + 포인트 적립
   이 4개 중 어디까지가 ACID로 묶여야 하는가?  ← 이게 트랜잭션 경계 설계
```

#### 2. 왜 Service 레이어인가

```mermaid
flowchart LR
    A[Controller<br/>HTTP 관심사] -->|@Transactional ❌| B[Service<br/>비즈니스 단위]
    B -->|@Transactional ✅<br/>여기가 경계| C[Repository<br/>퍼시스턴스 관심사]
    C -->|@Transactional ❌<br/>너무 좁음| D[(DB)]

    style B fill:#d4f1d4,stroke:#2a7
```

| 위치 | 문제 |
|---|---|
| **Controller** | HTTP 응답 직렬화·예외 변환까지 트랜잭션 안에 들어가 커밋 후 LazyInitializationException, 응답 늦어질수록 락 보유 시간이 길어짐 |
| **Repository** | 한 메서드 = 한 트랜잭션. `findOrder()` + `updateStock()` 같은 **여러 호출의 원자성**을 보장 못 함. 그래서 비즈니스 단위가 사라짐 |
| **Service** | "주문하기"라는 **유스케이스 단위**와 트랜잭션 경계가 일치 → 유지보수 단위 = 트랜잭션 단위 |

즉 트랜잭션 경계 = **유스케이스 단위**여야 한다. Repository에 붙이면 "조각"의 트랜잭션이 되고, Controller에 붙이면 "HTTP 처리"의 트랜잭션이 된다. 둘 다 비즈니스 의미가 없다.

#### 3. 시니어 관점: 자주 새는 5가지 지점

##### (1) 자기 호출(self-invocation) — Spring AOP의 가장 큰 함정
```java
@Service
class OrderService {
    public void placeOrder(...) {
        this.createOrder(...);     // ❌ 같은 빈 내부 호출 → 프록시 우회 → 트랜잭션 안 걸림
    }
    @Transactional
    public void createOrder(...) { ... }
}
```
Spring의 `@Transactional`은 **프록시 기반**이라 외부에서 들어올 때만 동작한다. `this.xxx()`는 프록시를 거치지 않아 어노테이션이 무력화된다. 코드는 멀쩡해 보이는데 운영에서 `ROLLBACK`이 안 도는 가장 흔한 사고.

##### (2) `private` 메서드에 붙이기
프록시 기반이라 `private`/`final` 메서드에는 적용되지 않는다. IDE 경고도 약해서 그대로 배포되기 쉽다.

##### (3) 트랜잭션 안에서 외부 API 호출 — 진짜 위험한 함정
```java
@Transactional
public void placeOrder(...) {
    Order order = orderRepository.save(...);     // DB 락 시작
    pgClient.requestPayment(order);              // ❌ 외부 호출 (3초 ~ 30초)
    order.markPaid();
}
```
이 코드는 **DB 트랜잭션을 외부 PG사 응답시간만큼 끌고 간다**. 결과:
- 커넥션 풀이 외부 응답 대기로 마름 → 전체 서비스 장애
- PG 응답은 오지만 우리쪽이 타임아웃 → **결제는 됐는데 주문은 롤백** (정합성 깨짐)

원칙: **트랜잭션 안에서는 절대 외부 I/O를 하지 않는다.** 외부 호출은 트랜잭션 밖으로 빼거나, "결제 요청 보냄" 상태로 먼저 커밋 후 비동기로 결과를 갱신한다 (이게 나중 단계의 SAGA로 가는 씨앗).

##### (4) `readOnly = true`를 안 쓴다
조회 전용 메서드에 `@Transactional(readOnly = true)`를 붙이면:
- Hibernate의 `dirty checking` 비활성화 → 성능 ↑
- DB에 따라 read replica로 라우팅 가능
- 의도가 코드에 드러남 (이 메서드가 쓰기인지 읽기인지)

##### (5) Checked Exception은 기본 롤백 대상이 아니다
Spring은 기본적으로 `RuntimeException`과 `Error`만 롤백한다. `IOException` 같은 checked는 **커밋된다**. `@Transactional(rollbackFor = Exception.class)`로 명시하거나, 도메인 예외를 `RuntimeException` 계열로 통일해야 한다.

#### 4. 전파(Propagation) — 자주 헷갈리는 두 가지

| 옵션 | 동작 | 언제 |
|---|---|---|
| `REQUIRED` (기본) | 진행 중 트랜잭션 있으면 합류, 없으면 새로 시작 | 99%의 경우 |
| `REQUIRES_NEW` | **항상 새 트랜잭션**. 기존 트랜잭션은 일시정지 | "주 트랜잭션이 롤백돼도 이건 살아남아야 함" — 감사 로그, 실패 이력 기록 |

흔한 실수: 주문 실패 시 "실패 로그"를 같은 트랜잭션에 남기면 주문이 롤백될 때 로그도 같이 사라진다. 감사·이력성은 `REQUIRES_NEW`로 분리해야 한다.

#### 5. 트레이드오프

| 큰 트랜잭션 (넓은 경계) | 작은 트랜잭션 (좁은 경계) |
|---|---|
| ✅ 정합성 보장 쉬움 | ✅ 락 보유 짧음, 동시성 ↑ |
| ✅ 비즈니스 단위 명확 | ✅ 외부 I/O와 분리 가능 |
| ❌ 락 보유 시간 ↑, 데드락 ↑ | ❌ 정합성을 애플리케이션이 책임 (보상 로직 필요) |
| ❌ 커넥션 풀 압박 | ❌ 부분 실패 처리 복잡 |

**원칙: 트랜잭션은 가능한 짧게, 단 비즈니스 원자성이 깨지지 않는 범위에서.**

#### 6. 실제 사례

- **토스(Toss)**: 송금은 "출금 → 입금"이 원자적이어야 하지만, 출금은 우리 DB, 입금은 상대 은행이라 ACID로 묶을 수 없음. 그래서 **"이체 요청"이라는 상태를 먼저 커밋 → 외부 통신 → 결과로 상태 전이**하는 패턴을 쓴다. 이게 모놀리스에서도 "트랜잭션 경계 ≠ 비즈니스 완료 시점"으로 분리하는 출발점.
- **배달의민족 초기 모놀리스**: 주문/결제/배차를 한 트랜잭션에 묶었다가 PG 응답 지연으로 커넥션 풀이 마르는 장애를 겪고, **결제 요청과 주문 생성을 분리**(`REQUIRES_NEW` + 상태 머신)하는 구조로 전환한 사례가 공개돼 있다.
- **공공/금융권 SI**: 반대로 "정합성 > 성능"이라 큰 트랜잭션을 유지하고 동시성은 batch window로 푸는 선택을 한다. 도메인이 트랜잭션 경계를 결정한다는 좋은 예.

#### 7. 언제 쓰고, 언제 쓰면 안 되는가

**Service 레이어 단일 트랜잭션 경계가 적합한 경우**
- 단일 DB만 사용하는 모놀리스
- 비즈니스 작업이 모두 우리 DB 안에서 끝남 (주문·재고·포인트가 모두 our DB)
- 동시 요청이 수백 TPS 이하 수준

**경계 재설계가 필요한 경우 (이 패턴을 그대로 쓰면 안 됨)**
- 트랜잭션 안에 외부 API 호출이 들어와야 함 → **상태 머신 + 보상**으로 분리
- 트랜잭션이 수 초 이상 걸림 → 배치/이벤트로 분리
- 여러 DB/서비스에 걸친 작업 → 분산 트랜잭션 또는 SAGA (이건 다음 단계)
- 읽기 트래픽이 압도적인데 트랜잭션이 길어 read replica를 못 쓰는 상황

> 💡 **왜 중요한가**: 트랜잭션 경계는 코드 스타일이 아니라 "무엇이 하나의 비즈니스 원자 단위인가"를 결정하는 설계이며, 잘못 그으면 정합성·성능·장애 전파가 동시에 무너진다.
