### 1. `Stream.toList()`가 아닌 `Collectors.toUnmodifiableList()` (Java 10 정식)로 "불변 리스트가 필요한데 toList()면 되지?" 관성 벗어나기

`Stream.toList()` (Java 16)가 반환하는 리스트는 "구조적으로 불변"이지만 `null`을 허용하고, 반환 타입이 구현 세부사항에 의존합니다. 반면 `.collect(Collectors.toUnmodifiableList())`는 `null` 요소가 하나라도 있으면 `NullPointerException`을 즉시 던져 "불변 + null-free" 계약을 명시적으로 강제합니다. API 응답/DTO처럼 외부에 노출하는 리스트라면 후자가 방어적 프로그래밍 관점에서 더 안전합니다.

> 💡 **왜 중요한가**: `toList()`의 "null 허용"은 장점이 아니라 함정이다 — 공개 API 경계에서는 `Collectors.toUnmodifiableList()`로 "null은 버그다"를 타입이 아닌 런타임이 선언하게 하라.

### 2. `java.lang.ScopedValue` (Java 25 정식, JEP 506)로 `ThreadLocal`의 "set 하면 clear 잊어버려서 누수" 관성 벗어나기

`ThreadLocal`은 요청 컨텍스트(사용자 ID, trace ID)를 스레드에 심을 때 쓰지만, `remove()`를 깜빡하면 스레드 풀 환경에서 다음 요청으로 값이 샙니다. 가상 스레드가 수백만 개 뜨는 환경에선 메모리 압박까지 겹칩니다. `ScopedValue.where(USER_ID, "u-123").run(() -> handle())`는 람다 종료 시점에 자동으로 바인딩이 해제되고 **불변**이라 하위 호출에서 덮어쓸 수 없습니다.

```java
private static final ScopedValue<String> USER_ID = ScopedValue.newInstance();

// 바인딩 → 람다 실행 → 자동 해제. clear() 없음.
ScopedValue.where(USER_ID, "u-123").run(() -> {
    service.handleRequest();  // 내부에서 USER_ID.get() 가능
});
```

> 💡 **왜 중요한가**: 가상 스레드 시대엔 `ThreadLocal`의 "수동 clear" 모델이 메모리 지뢰 — `ScopedValue`는 스코프 종료 = 바인딩 해제라는 구조적 보장으로 누수 자체를 설계에서 제거한다.
