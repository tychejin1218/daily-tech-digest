### 1. `data class`: equals/hashCode/toString을 "무료로" 얻는 대신 치러야 하는 숨은 비용

Kotlin의 `data class`는 주 생성자 프로퍼티만으로 `equals()`, `hashCode()`, `toString()`, `copy()`, `componentN()`을 자동 생성해준다. Java에서 Lombok의 `@Data`로 대신하던 보일러플레이트가 언어 차원에서 해결되는 것이다. 하지만 "자동 생성"이라는 편리함 뒤에는 세 가지 함정이 숨어 있다 — ① `copy()`는 얕은 복사라서 내부 가변 컬렉션을 공유하고, ② JPA 엔티티로 쓰면 `hashCode()`가 ID 기반이 아니라 모든 필드 기반이라 영속성 라이프사이클과 충돌하며, ③ 상속이 불가능해 `open`을 붙일 수 없다. 그래서 "DTO/VO는 `data class`, Entity는 일반 `class`"가 실무 표준이 된다.

```kotlin
// ✅ 좋은 예: 불변 DTO
data class UserDto(val id: Long, val name: String, val email: String)

// ❌ 나쁜 예: JPA 엔티티를 data class로
@Entity
data class User(@Id val id: Long, var name: String)
// → Hibernate 프록시의 hashCode가 깨짐, equals가 lazy loading 트리거

// ✅ JPA 엔티티는 일반 class + ID 기반 equals
@Entity
class User(@Id val id: Long, var name: String) {
    override fun equals(other: Any?) = other is User && other.id == id
    override fun hashCode() = id.hashCode()
}
```

> 💡 **왜 중요한가**: `data class`는 "값(Value)"을 표현하는 도구이지 "엔티티(Entity)"를 표현하는 도구가 아니다 — 정체성(identity)이 있는 객체에 값 의미론을 강제하면 ORM 라이프사이클이 조용히 망가진다.

### 2. Kotlin의 `null` 안전성은 "`?` 하나" 가 아니다: 플랫폼 타입(`String!`)이라는 조용한 지뢰

Kotlin에서 `String`과 `String?`은 컴파일러가 보장해주는 타입이다. 하지만 Java 코드를 호출하는 순간, 세 번째 타입이 등장한다 — **플랫폼 타입(`String!`)**. 이는 "Kotlin은 null인지 모르겠으니 네가 책임져"라는 뜻으로, non-null처럼 쓸 수 있지만 런타임에 NPE가 터질 수 있다. Spring Boot + Kotlin 환경에서 `@Autowired` 필드, `ResponseEntity.getBody()`, Jackson 역직렬화 결과가 모두 플랫폼 타입을 반환하는 대표 사례다. 그래서 외부 경계에서는 명시적으로 `?`를 붙이거나 `requireNotNull()`로 의도를 선언해야 "컴파일은 되는데 프로덕션에서 NPE" 패턴을 막을 수 있다.

```kotlin
// Java 라이브러리
public class LegacyService {
    public String getName() { return null; } // nullable인지 명세 없음
}

// Kotlin에서 호출
val name: String = legacyService.name  // ✅ 컴파일 통과
println(name.length)                    // 💥 런타임 NPE!

// ✅ 안전한 처리: 플랫폼 타입을 명시적으로 nullable로 받기
val name: String? = legacyService.name
println(name?.length ?: 0)

// ✅ 또는 계약을 명시적으로 강제
val name: String = requireNotNull(legacyService.name) { "name은 null일 수 없다" }
```

실무 체크리스트:
- Spring `@Value("\${app.key}")` → `String?`로 받거나 기본값 지정
- Jackson 역직렬화 → `kotlin-module` 등록 필수 (`jackson-module-kotlin`)
- JPA `findById()` → `Optional<T>` 반환이므로 `.orElseThrow()` 또는 `.getOrNull()`

> 💡 **왜 중요한가**: Kotlin의 null 안전성은 "Kotlin 세상 안에서만" 완전하다 — Java와의 경계(JPA, Spring, Jackson, 외부 라이브러리)에서 플랫폼 타입을 방치하면 "컴파일러가 보장해준다"는 환상이 프로덕션 NPE로 돌아온다.
