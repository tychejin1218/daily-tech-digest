### `@Transactional(readOnly = true)`는 성능 최적화가 아니라 **함정 방지 장치**다

많은 개발자가 `readOnly = true`를 "읽기 전용 트랜잭션이니 성능이 좋아진다"고 생각하지만, 실제로는 Hibernate의 dirty checking을 끄고 flush 모드를 `MANUAL`로 바꾸는 것이 핵심 효과다. 즉, 조회 메서드에서 실수로 엔티티를 수정해도 DB에 반영되지 않아 예기치 않은 UPDATE를 막아준다. DB 커넥션 자체의 read-only 최적화는 드라이버와 DB 벤더에 따라 다르며, MySQL에서는 거의 효과가 없다.

```java
@Transactional(readOnly = true)
public UserDto getUser(Long id) {
    User user = userRepository.findById(id).orElseThrow();
    user.setLastAccessedAt(LocalDateTime.now()); // 조용히 무시됨 (flush 안 됨)
    return UserDto.from(user);
}

// readOnly = false (기본값) 였다면?
// → 커밋 시점에 dirty checking으로 UPDATE 쿼리가 나감
// → "왜 조회만 했는데 UPDATE가 찍히지?" 라는 미스터리 발생
```

트레이드오프:
- **장점**: 실수로 인한 사이드 이펙트 차단, dirty checking 스냅샷 생략으로 메모리 절약
- **단점**: 같은 트랜잭션 내에서 진짜 수정이 필요할 때는 별도 트랜잭션을 열어야 함

> 💡 **왜 중요한가**: `readOnly = true`의 진짜 가치는 "빠르다"가 아니라 "조회 메서드에서 발생하는 유령 UPDATE를 원천 차단한다"는 데 있다.

### `Optional`을 JPA 엔티티 필드나 메서드 파라미터로 쓰면 안 되는 이유

`Optional`은 **메서드 반환 타입**을 위해 설계된 도구다. Joshua Bloch(Optional 설계자)도 "필드나 파라미터로 쓰지 말라"고 명시했는데, Spring/JPA 세계에서는 이 규칙을 어겼을 때의 대가가 특히 크다. `Optional` 필드는 직렬화 불가(`Serializable` 미구현), JPA가 매핑을 인식하지 못함, Jackson이 기본 설정에서 `{"value":..., "present":true}` 같은 이상한 JSON을 뱉는 문제가 연쇄적으로 발생한다.

```java
// 안티패턴
@Entity
public class User {
    @Id private Long id;
    private Optional<String> nickname; // JPA가 매핑 못 함, 직렬화 실패
}

// 안티패턴
public User createUser(Optional<String> nickname) { // API 호출 시 어떻게 넘길지 모호
    ...
}

// 올바른 사용: 반환 타입에만
public Optional<User> findByEmail(String email) {
    return userRepository.findByEmail(email);
}
```

대안:
- **필드**: 그냥 nullable로 두고 getter에서 `Optional.ofNullable(field)` 반환
- **파라미터**: 오버로딩 또는 `@Nullable` 어노테이션 사용
- **DTO**: Jackson `Jdk8Module` 등록해야 정상 직렬화됨 (Spring Boot는 자동 등록)

> 💡 **왜 중요한가**: `Optional`은 "값이 없을 수 있다"는 API 계약을 표현하는 도구지, null을 대체하는 만능 래퍼가 아니다 — 필드/파라미터에 쓰는 순간 직렬화·매핑·성능이 동시에 무너진다.
