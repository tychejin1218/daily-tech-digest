### 1. `Collectors.groupingBy(classifier, LinkedHashMap::new, downstream)`로 그룹 결과의 삽입 순서 보존하기 (Java 8 정식)

`groupingBy(classifier)`의 기본 반환은 `HashMap`이라 그룹 키 순서가 원본 스트림 등장 순서와 무관하게 뒤섞인다. 오버로드 `groupingBy(classifier, mapFactory, downstream)`에 `LinkedHashMap::new`를 넘기면 **처음 등장한 키 순서 그대로** 유지되고, 리포트·CSV·페이지네이션 결과에서 "왜 순서가 매번 다르지?" 하는 디버깅 지옥을 피할 수 있다. `TreeMap::new`를 넣으면 키 정렬, `ConcurrentHashMap::new`는 병렬 안전까지 한 방에 처리된다.

```java
// ❌ 관성: HashMap, 키 순서 미보장
Map<String, List<Order>> byRegion = orders.stream()
    .collect(Collectors.groupingBy(Order::region));

// ✅ 삽입 순서 보존
Map<String, List<Order>> byRegion = orders.stream()
    .collect(Collectors.groupingBy(
        Order::region,
        LinkedHashMap::new,
        Collectors.toList()));

// ✅ 키 정렬 + 합계까지 한 번에
Map<String, Long> totalByRegion = orders.stream()
    .collect(Collectors.groupingBy(
        Order::region,
        TreeMap::new,
        Collectors.summingLong(Order::amount)));
```

> 💡 **왜 중요한가**: "그룹핑 후 다시 정렬"이라는 두 번째 순회를 없애면서, 순서에 의존하는 UI/리포트 버그를 스트림 파이프라인 안에서 원천 차단한다.

### 2. `List.copyOf(collection)`로 방어적 복사 + 불변화를 한 줄에 (Java 10 정식)

외부에서 받은 `List`를 필드에 저장할 때 `new ArrayList<>(input)`으로 방어적 복사만 하는 관성은 두 가지 구멍이 있다 — **여전히 가변이라 내부에서 실수로 수정 가능**, 그리고 **입력이 이미 불변이어도 무조건 새 배열을 만든다**. `List.copyOf(collection)`은 방어적 복사 + 불변 래핑을 한 번에 처리하고, 입력이 이미 `List.copyOf`/`List.of` 결과라면 **복사조차 생략**하는 최적화까지 자동으로 해준다. `Set.copyOf`, `Map.copyOf`도 동일한 규칙.

```java
// ❌ 가변 상태로 저장 → 내부 수정 사고 가능
public Order(List<Item> items) {
    this.items = new ArrayList<>(items);
}

// ❌ Collections.unmodifiableList: 원본이 바뀌면 뷰도 바뀜 (진짜 불변 아님)
this.items = Collections.unmodifiableList(new ArrayList<>(items));

// ✅ 진짜 불변, 이미 불변이면 재복사 생략
public Order(List<Item> items) {
    this.items = List.copyOf(items);  // NPE는 null 원소일 때만
}
```

주의: `List.copyOf`는 **null 원소를 허용하지 않는다**(NPE 발생). 이는 버그가 아니라 의도 — 불변 컬렉션에는 null이 들어가면 안 된다는 API 설계 원칙이다.

> 💡 **왜 중요한가**: `record` 컴팩트 생성자와 조합하면 "불변 값 객체" 계약을 한 줄로 완성할 수 있어, DTO·이벤트·도메인 모델의 방어 코드 부피가 절반으로 준다.
