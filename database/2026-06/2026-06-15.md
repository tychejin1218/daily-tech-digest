### 1. PostgreSQL PreparedStatement Generic Plan 함정 — 6번째 실행부터 갑자기 느려지는 쿼리

PostgreSQL JDBC는 같은 `PreparedStatement`를 5번까지는 매번 실행 계획을 새로 짜는(custom plan) 반면, 6번째 실행부터는 파라미터를 무시한 generic plan으로 캐싱한다. 데이터 분포가 편향된 컬럼(예: `status = 'DONE'`이 99%인 테이블에서 `status = 'PENDING'` 조회)에서는 인덱스 스캔이어야 할 쿼리가 갑자기 Seq Scan으로 바뀌면서 한참 잘 돌던 API가 어느 순간 폭주한다. JDBC URL의 `prepareThreshold=0`으로 끄거나, 문제 쿼리는 `plan_cache_mode = force_custom_plan`을 SET 해서 매번 다시 계획하도록 강제할 수 있다.

> 💡 **왜 중요한가**: "어제까지 멀쩡했는데 오늘 갑자기 느려졌다"는 장애의 단골 원인이며, EXPLAIN을 psql에서 따로 돌리면 빠르게 나와서 재현 자체가 안 되는 가장 짜증나는 류의 함정이다.

### 2. Spring Boot `spring.jpa.open-in-view=true` 기본값 — 컨트롤러·뷰까지 DB 커넥션을 붙잡는 침묵의 누수

Spring Boot의 OSIV(Open Session In View)는 기본값이 `true`라서, 서비스 계층이 끝난 뒤에도 트랜잭션 없이 영속성 컨텍스트와 DB 커넥션을 **응답이 클라이언트에게 다 나갈 때까지** 붙들고 있다. 컨트롤러에서 외부 API를 호출하거나 직렬화가 느리면 그 시간 동안 커넥션 풀 한 자리가 계속 점유되어, 평시엔 멀쩡하다가 트래픽이 몰리는 순간 풀 고갈로 모든 요청이 타임아웃 나는 장애가 터진다. `application.yml`에 `spring.jpa.open-in-view: false`로 끄고, 컨트롤러에서 지연 로딩이 필요한 곳은 `@EntityGraph`나 fetch join으로 서비스 계층에서 명시적으로 로딩하도록 바꿔야 한다.

> 💡 **왜 중요한가**: 부트는 시작할 때 WARN 한 줄만 띄우고 기본값을 켜둬서 대부분의 팀이 모른 채 운영하고 있고, 커넥션 풀 고갈 장애의 진짜 원인이 OSIV였다는 사실은 보통 사후 부검 단계에서야 발견된다.
