### 1. `Files.mismatch(path1, path2)` (Java 12 정식)로 두 파일이 같은지 비교할 때 `Files.readAllBytes()` 두 번 읽어서 `Arrays.equals` 하는 관성 벗어나기

두 파일의 내용을 비교할 때 `Arrays.equals(Files.readAllBytes(p1), Files.readAllBytes(p2))` 패턴은 두 파일을 모두 메모리에 올리기 때문에 큰 파일에서는 OOM 위험이 있고, 전체를 다 읽은 뒤에야 비교가 끝난다. `Files.mismatch(p1, p2)`는 스트리밍으로 바이트를 비교하며 **첫 번째 다른 바이트 위치**를 반환하고(같으면 -1), 크기가 다르면 즉시 종료하므로 메모리와 I/O 모두 유리하다.

```java
// 😵 관성적인 방식 — 두 파일을 통째로 메모리에 적재
boolean same = Arrays.equals(
    Files.readAllBytes(original),
    Files.readAllBytes(backup)
);

// ✅ Java 12+ — 스트리밍 비교, 첫 불일치 위치까지만 읽음
long mismatchAt = Files.mismatch(original, backup);
boolean same = (mismatchAt == -1L);
// 디버깅할 때 "몇 번째 바이트에서 깨졌는지"까지 바로 얻을 수 있음
```

**트레이드오프**: 해시 비교(SHA-256 등)와 달리 두 파일 모두 로컬에 있어야 의미가 있다. 네트워크 양쪽에 분산된 파일을 비교해야 한다면 여전히 해시가 답이다. 또한 심볼릭 링크/하드 링크로 같은 파일을 가리키는 경우 `isSameFile`을 먼저 체크하면 I/O를 아예 생략할 수 있다.

> 💡 **왜 중요한가**: 백업 검증, 배포 산출물 비교, 캐시 무결성 체크 같은 "파일 두 개 같냐" 질문에서 전체 로드 → 통짜 비교 패턴은 파일 크기가 커질수록 선형으로 비용이 폭증하지만, `Files.mismatch`는 다른 첫 바이트에서 끊어 대부분의 "다른 파일" 케이스를 조기 종료할 수 있다.

### 2. `AutoCloseable` + try-with-resources로 **잠금(lock) 해제**까지 관리하기 — `lock.lock()` / `try { ... } finally { lock.unlock(); }` 관성 벗어나기

`ReentrantLock`을 쓸 때 거의 모든 코드가 `lock.lock(); try { ... } finally { lock.unlock(); }` 보일러플레이트에 묶이는데, `AutoCloseable`을 구현한 얇은 래퍼 하나만 만들면 `try-with-resources`로 해제 보장이 **문법적으로 강제**된다. Java 21 가상 스레드 환경에서 `synchronized`가 캐리어 스레드를 핀(pin)시키는 문제 때문에 `ReentrantLock`으로 갈아타는 경우가 늘고 있어 더 유용하다.

```java
// 😵 관성적인 방식 — finally 깜빡하면 영구 데드락
lock.lock();
try {
    if (!cache.containsKey(key)) {
        cache.put(key, load(key));
    }
    return cache.get(key);
} finally {
    lock.unlock();  // 이거 빠뜨리면 끝장
}

// ✅ try-with-resources 패턴 — 컴파일러가 해제를 강제
public final class Locked implements AutoCloseable {
    private final Lock lock;
    private Locked(Lock lock) { this.lock = lock; lock.lock(); }
    public static Locked of(Lock lock) { return new Locked(lock); }
    @Override public void close() { lock.unlock(); }
}

try (var ignored = Locked.of(lock)) {
    return cache.computeIfAbsent(key, this::load);
}
// 예외가 던져지든, early return이든, break든 — 반드시 unlock
```

**주의할 점**: `lock.lockInterruptibly()`나 `tryLock(timeout)` 변형이 필요하면 래퍼를 분리해서 만들거나 팩터리 메서드를 늘려야 한다. 또한 `ignored` 변수를 쓰지 않는다고 IDE가 경고하는 걸 `@SuppressWarnings`로 눌러야 하는 경우도 있다 — 명시적으로 `var _ = ...` (Java 22+ unnamed variables)를 쓰면 깔끔하다.

> 💡 **왜 중요한가**: 가상 스레드 전환 과정에서 `synchronized` → `ReentrantLock` 마이그레이션이 활발하지만, 명시적 Lock은 "해제 책임"이 코드 작성자에게 넘어오면서 finally 누락이 바로 데드락으로 이어진다. `AutoCloseable` 래퍼는 이 책임을 **문법 레벨로 끌어올려** 리뷰어가 눈으로 추적할 필요를 없앤다.
