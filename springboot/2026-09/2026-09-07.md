### `@RequestParam`의 `required=true`는 **빈 문자열을 통과시킨다** — `?name=`은 검증을 우회한다

`@RequestParam(required=true) String name`에 `?name=`으로 요청하면 **빈 문자열 `""`이 그대로 주입된다**. `required`는 "파라미터 키의 존재 여부"만 체크할 뿐, 값이 비어있는지는 관심이 없다. `@NotBlank` 같은 Bean Validation 없이는 프론트가 빈 값을 보내도 컨트롤러가 그대로 실행되고, 서비스 계층에서 뒤늦게 터진다.

```java
// 위험: ?name= 요청 시 name=""으로 들어와 통과
@GetMapping("/search")
public List<User> search(@RequestParam(required = true) String name) {
    return userService.findByName(name); // "" 로 조회
}

// 안전: 명시적 검증
@GetMapping("/search")
public List<User> search(@RequestParam @NotBlank String name) { ... }
// + 컨트롤러 클래스에 @Validated 필수
```

실제 사고 패턴:
- 프론트 폼에서 빈 input을 제출 → `?name=`으로 전송
- 백엔드는 `""`을 정상 값으로 간주 → `LIKE '%%'`로 **전체 테이블 스캔**
- 서비스는 죽지 않고 조용히 느려짐 → 원인 추적에 반나절

> 💡 **왜 중요한가**: `required=true`는 "값이 있어야 한다"가 아니라 "키가 있어야 한다"이므로, 빈 문자열 방어는 반드시 Bean Validation으로 별도로 해야 한다.

### `@SpringBootTest`는 **모든 빈**을 로드한다 — 단위 테스트 하나에 컨텍스트가 통째로 뜨는 이유

`@SpringBootTest`를 붙이면 프로덕션과 동일한 전체 애플리케이션 컨텍스트가 뜬다. 컨트롤러 하나만 테스트하려는데도 JPA, Redis, Kafka, 모든 `@Service`가 다 초기화된다. 테스트 100개면 컨텍스트 100번 뜨는 게 아니라 캐싱되지만, `@MockBean`을 쓰는 순간 컨텍스트 캐시가 무효화되어 **재생성 폭탄**이 터진다.

```java
// 느림: 전체 컨텍스트 로드 (10초+)
@SpringBootTest
class UserControllerTest {
    @MockBean UserService userService; // 캐시 무효화 트리거
}

// 빠름: 웹 레이어만 로드 (1초 이내)
@WebMvcTest(UserController.class)
class UserControllerTest {
    @MockBean UserService userService;
}

// JPA만: @DataJpaTest
// JSON 직렬화만: @JsonTest
// RestClient만: @RestClientTest
```

Slice 테스트 선택 기준:
| 목적 | 어노테이션 | 로드되는 것 |
|------|------------|-------------|
| 컨트롤러 검증 | `@WebMvcTest` | MVC + `@ControllerAdvice`만 |
| Repository 쿼리 | `@DataJpaTest` | JPA + 임베디드 DB만 |
| 통합 시나리오 | `@SpringBootTest` | 전부 |

`@MockBean`을 여러 테스트에서 **다르게** 선언하면 컨텍스트 캐시가 조각나 CI 시간이 5배로 늘어난다. `@MockBean` 대신 `@TestConfiguration`으로 공통 mock을 묶으면 캐시가 재사용된다.

> 💡 **왜 중요한가**: 테스트는 좁을수록 빠르고 명확하다 — `@SpringBootTest`는 통합 테스트 전용이며, 컨트롤러 하나 검증에 쓰는 순간 CI 파이프라인이 무너진다.
