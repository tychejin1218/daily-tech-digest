### MySQL `Covering Index` — 테이블을 아예 열지 않고 인덱스만 읽고 끝내는 "그림자 스캔"

인덱스는 보통 WHERE 조건을 걸러낸 뒤 실제 데이터 행(테이블)을 찾아가서 SELECT 컬럼을 읽는다. 하지만 SELECT하는 모든 컬럼이 인덱스 안에 이미 포함되어 있다면, InnoDB는 테이블(클러스터드 인덱스 리프)을 아예 방문하지 않고 세컨더리 인덱스만 읽고 결과를 반환한다. 이걸 `Using index` (EXPLAIN에서 확인)라 부르고, 목적을 위해 일부러 만드는 인덱스가 `Covering Index`다.

```sql
-- 느린 쿼리
SELECT user_id, status FROM orders WHERE shop_id = 42;
-- 기존 인덱스: (shop_id) → shop_id로 찾고, 매 행마다 테이블 접근해서 user_id, status 읽음

-- Covering Index로 재설계
CREATE INDEX idx_shop_covering ON orders (shop_id, user_id, status);
-- 이제 인덱스만 스캔하면 끝. 테이블 페이지는 건드리지도 않음
-- EXPLAIN: Extra 컬럼에 "Using index" 등장
```

핵심은 "인덱스 = 정렬된 데이터 조각의 복사본"이라는 관점 전환이다. 인덱스에 컬럼을 추가하면 저장 공간과 쓰기 비용이 늘지만, 읽기가 많은 워크로드에서는 랜덤 I/O 한 번(테이블 접근)을 완전히 제거하므로 10~100배까지 빨라진다. MySQL 8.0부터는 `INCLUDE` 문법은 없지만, 인덱스 컬럼 순서 뒤쪽에 SELECT 컬럼을 붙이는 방식으로 동일한 효과를 낼 수 있다. 반대로 `SELECT *`를 남발하면 커버링이 원천 불가능해진다는 뜻이기도 하다.

> 💡 **왜 중요한가**: WHERE 조건만 인덱스로 태우고 만족하는 게 아니라, SELECT 컬럼까지 인덱스에 태워야 진짜 "인덱스만으로 끝나는 쿼리"가 된다.

### JPA `OSIV (Open Session In View)` — 트랜잭션이 끝났는데도 커넥션이 컨트롤러까지 따라오는 조용한 병목

Spring Boot의 `spring.jpa.open-in-view` 기본값은 `true`다. 이 설정이 켜져 있으면, 요청이 들어오는 순간 영속성 컨텍스트(Persistence Context)와 DB 커넥션이 열리고, 컨트롤러 → 뷰 렌더링까지 요청이 완전히 끝날 때까지 유지된다. 트랜잭션은 서비스 계층에서 이미 커밋됐지만, 커넥션은 여전히 스레드에 붙어 있다.

```
[요청 시작]
  ↓
  Filter → 영속성 컨텍스트 OPEN, 커넥션 획득 시작 대기
  ↓
  Controller
  ↓
  @Transactional Service (여기서 트랜잭션 시작/커밋)
  ↓
  Controller (트랜잭션 끝났지만 커넥션은 유지 → Lazy 로딩 여기서도 가능)
  ↓
  View 렌더링 (Lazy 프록시 초기화 → 여기서도 쿼리 나감)
  ↓
[요청 끝 → 커넥션 반납]
```

장점은 명확하다. Controller나 View에서 Lazy 프록시를 만져도 `LazyInitializationException`이 나지 않는다. 단점은 더 명확하다. HikariCP 커넥션 풀이 10개인데 요청 하나가 500ms 걸리면, 서비스 로직이 50ms에 끝나도 나머지 450ms 동안 커넥션을 붙잡고 있다. 트래픽이 몰리면 커넥션 풀이 순식간에 고갈되고, 외부 API 호출이 컨트롤러에서 일어나는 순간 커넥션은 그동안에도 잠긴다.

프로덕션에서는 `spring.jpa.open-in-view=false`로 끄고, 대신 서비스 계층에서 DTO로 변환하거나 `@EntityGraph` / fetch join으로 필요한 연관관계를 미리 로딩하는 게 정석이다. 끄는 순간 곳곳에서 `LazyInitializationException`이 터질 텐데, 그게 바로 "커넥션 낭비 지점"이 드러나는 신호다.

> 💡 **왜 중요한가**: 트랜잭션 경계와 커넥션 반납 시점이 다르다는 사실을 모르면, 커넥션 풀 튜닝을 아무리 해도 특정 시점에 서버가 멈추는 이유를 영원히 찾지 못한다.
