### Spring Boot `@Transactional`의 `propagation = REQUIRES_NEW`는 **같은 클래스 내부 호출에서 작동하지 않는다** — 그리고 외부 트랜잭션의 `rollback-only` 플래그를 공유한다

`@Transactional(propagation = REQUIRES_NEW)`는 "기존 트랜잭션을 잠시 중단하고 새 트랜잭션을 시작"하는 걸로 유명하지만, 함정이 두 개 있다. 첫째, self-invocation(같은 클래스 내부 메서드 호출)에서는 프록시를 거치지 않기 때문에 그냥 기존 트랜잭션에 참여해버린다. 둘째, 로그를 남기려고 `REQUIRES_NEW`로 분리한 메서드에서 외부 트랜잭션이 롤백되면 — 분리된 트랜잭션은 커밋됐더라도 — `UnexpectedRollbackException`이 터지는 경우가 있다. 외부 호출자가 `rollback-only` 플래그를 봤기 때문이다.

```
┌─────────────────────────────────────────────┐
│ outerService.doWork()  [TX A]               │
│  ├─ this.saveLog()  ← 같은 클래스 호출       │
│  │   @Transactional(REQUIRES_NEW) 무시됨!   │
│  │   → TX A에 그대로 참여                   │
│  │                                          │
│  └─ logService.saveLog()  ← 다른 Bean       │
│      → TX B 새로 시작 ✓                     │
│      → 커밋돼도 TX A 롤백 시 영향 가능       │
└─────────────────────────────────────────────┘
```

**실무 사례**: 결제 실패 로그를 "실패해도 반드시 남겨야 한다"고 `REQUIRES_NEW`로 분리했는데, 같은 서비스 안에서 호출했더니 결제 롤백과 함께 로그도 날아간다. 별도 Bean(`AuditLogService`)으로 빼야 작동한다.

> 💡 **왜 중요한가**: "로그는 반드시 남는다"는 비즈니스 요구사항이 조용히 깨지고, 운영 사고 조사에서 증거가 사라진다.

### Spring Boot Actuator의 `/actuator/health`는 **기본적으로 디스크 공간과 DB 커넥션을 체크한다** — 그리고 쿠버네티스 환경에서는 `liveness`와 `readiness`를 반드시 분리해야 한다

Actuator의 health endpoint는 편해 보이지만, 쿠버네티스 환경에서 그대로 쓰면 재앙이 된다. DB가 잠깐 느려지면 `/health`가 DOWN을 반환하고, 쿠버네티스는 Pod가 죽은 줄 알고 재시작한다 — 결국 **DB 장애 → 애플리케이션 전체 재시작 폭풍**으로 번진다. Spring Boot 2.3+는 `livenessState`(죽었나?)와 `readinessState`(트래픽 받을 준비 됐나?)를 분리해서 제공한다.

```
┌──────────────────────────────────────────────┐
│  /actuator/health/liveness                   │
│  → 프로세스가 살아있는가? (JVM 데드락 등)   │
│  → DB 상태 체크 ❌ (죽은 게 아님)            │
│  → k8s livenessProbe에 연결                  │
├──────────────────────────────────────────────┤
│  /actuator/health/readiness                  │
│  → 지금 트래픽을 처리할 수 있는가?           │
│  → DB, 외부 API 체크 ⭕                       │
│  → k8s readinessProbe에 연결                 │
│  → 실패 시 트래픽만 차단, 재시작 ❌          │
└──────────────────────────────────────────────┘
```

```yaml
management:
  endpoint:
    health:
      probes:
        enabled: true
      group:
        liveness:
          include: livenessState
        readiness:
          include: readinessState, db, redis
```

**트레이드오프**: liveness에 DB를 넣으면 "장애 자동 복구" 환상에 빠지지만, 실제로는 단일 DB 장애가 전체 클러스터 재시작 루프로 증폭된다. readiness로만 두면 트래픽만 끊고 Pod는 살아있어서 복구가 빠르다.

> 💡 **왜 중요한가**: health check 하나 잘못 설정하면, DB 1초 지연이 전체 서비스 10분 다운으로 확대된다.
