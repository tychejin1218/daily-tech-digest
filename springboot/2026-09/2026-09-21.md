### `@Qualifier`보다 `@Primary`가 우선한다 — 예상과 정반대다

같은 타입의 빈이 여러 개일 때 `@Primary`가 붙은 빈이 기본으로 주입되는 건 알려져 있지만, `@Qualifier("beanName")`으로 명시적 지정을 해도 `@Primary`가 우선 매칭되는 상황이 있다. 정확히는 **`@Qualifier`의 이름이 어떤 빈과도 매치되지 않을 때** Spring은 조용히 `@Primary` 빈으로 폴백한다. 오타 하나가 컴파일 오류 없이 완전히 다른 빈을 주입한다.

```java
@Bean @Primary
public PaymentService kakaoPay() { ... }

@Bean
public PaymentService naverPay() { ... }

// "naverpay" 오타 → 예외 없이 kakaoPay 주입됨
@Autowired @Qualifier("naverpay")
private PaymentService paymentService;
```

> 💡 **왜 중요한가**: 결제 라우팅, 알림 채널 선택 같은 크리티컬 로직에서 조용히 잘못된 빈이 주입되면 로그에도 안 남고 프로덕션에서만 터진다.

---

### `WebClient`는 `RestTemplate`의 대체가 아니다 — 블로킹으로 쓰면 성능이 더 나쁘다

`RestTemplate`이 deprecated 되면서 `WebClient`로 갈아타는 팀이 많지만, `.block()`으로 감싸서 동기적으로 쓰면 **Netty 이벤트 루프 스레드를 점유**하기 때문에 오히려 처리량이 더 떨어진다. `WebClient`의 진짜 이점은 리액티브 스트림 전체에서 논블로킹으로 흐를 때 나온다. Spring MVC(서블릿) 환경에서 단순 HTTP 호출용으로 쓴다면 `RestClient`(Spring 6.1+)가 정답이다.

```java
// 안티패턴 - MVC에서 WebClient.block()
String response = webClient.get().uri("/api").retrieve()
    .bodyToMono(String.class).block();  // 이벤트 루프 점유

// 정답 - Spring 6.1+ RestClient
String response = restClient.get().uri("/api").retrieve().body(String.class);
```

> 💡 **왜 중요한가**: "최신 = 좋음"이라는 이유로 도구를 바꾸면 프로그래밍 모델 불일치로 인해 트래픽 급증 시 스레드 고갈이 발생한다.
