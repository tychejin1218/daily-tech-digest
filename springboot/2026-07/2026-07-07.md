### `@Scheduled` 메서드에 `@Transactional`을 붙일 때 propagation 기본값이 위험한 이유

스케줄러 진입점에서 `@Transactional`을 기본 propagation(`REQUIRED`)로 걸면 하나의 실행 사이클 전체가 단일 트랜잭션에 묶여, 중간에 처리한 배치 항목의 성공/실패가 마지막 커밋 시점까지 반영되지 않는다. 배치성 작업은 스케줄러 메서드는 트랜잭션 없이 두고, 내부에서 항목 단위로 `@Transactional(propagation = REQUIRES_NEW)`을 건 서비스 메서드를 반복 호출해 항목별로 커밋을 끊어야 부분 실패에도 나머지가 저장된다.

```java
@Scheduled(fixedDelay = 60000)
public void syncOrders() {
    orderIds.forEach(id -> orderProcessor.processOne(id)); // 트랜잭션 없음
}

@Transactional(propagation = Propagation.REQUIRES_NEW)
public void processOne(Long id) { /* 항목별 커밋 */ }
```

> 💡 **왜 중요한가**: 스케줄러 트랜잭션 범위를 잘못 잡으면 1건 실패로 수천 건이 롤백되어 배치 전체가 무너진다.

### `application.yml`의 `spring.config.import`로 외부 설정 파일을 명시적으로 로드하기 (Spring Boot 2.4+)

Spring Boot 2.4부터 `spring.config.location`/`spring.config.additional-location`의 위치 우선순위 규칙이 복잡해지면서, 대신 `spring.config.import`로 파일·Vault·Consul 등 어떤 소스를 어떤 순서로 병합할지 프로퍼티 안에서 선언적으로 지정할 수 있게 됐다. `optional:` 접두사를 붙이면 파일이 없어도 부팅이 실패하지 않고, `configtree:`로 Kubernetes ConfigMap 마운트 디렉토리를 그대로 프로퍼티로 흡수할 수도 있다.

```yaml
spring:
  config:
    import:
      - optional:file:./config/secrets.yml
      - configtree:/etc/config/
      - vault://secret/myapp
```

> 💡 **왜 중요한가**: 외부 설정을 코드나 실행 인자가 아닌 프로퍼티 파일 안에서 명시적으로 조립할 수 있어, 컨테이너 환경마다 다른 부트 스크립트를 관리할 필요가 없다.
