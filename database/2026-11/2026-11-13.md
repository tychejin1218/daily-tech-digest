### Database Tip 1: MySQL `Doublewrite Buffer` — 16KB 페이지를 쓰다가 크래시 나면 "반쪽짜리 페이지"가 남는 Torn Page 지옥을 막는 이중 쓰기 방패

InnoDB는 16KB 페이지 단위로 디스크에 쓰지만, OS·파일시스템·디스크는 4KB 블록 단위로 쓴다. 16KB 중 앞의 4KB만 디스크에 반영된 상태에서 서버가 죽으면 페이지가 "찢어진(torn)" 상태로 남고, Redo Log는 "변경 사항"만 담고 있으므로 이걸로는 복구할 수 없다. Doublewrite Buffer는 데이터 파일에 쓰기 전에 공유 테이블스페이스의 전용 영역(기본 128페이지)에 먼저 순차적으로 한 번 더 써서, 크래시 복구 시 "온전한 복사본"을 찾아 원본을 덮어쓸 수 있게 하는 안전장치다.

```
[변경된 페이지]
      │
      ├─► ① Doublewrite Buffer (순차 쓰기, fsync)
      │        │
      │        └─ 크래시 발생 시 ‟온전한 16KB”를 여기서 발견
      │
      └─► ② 실제 데이터 파일 (랜덤 쓰기)
```

> 💡 **왜 중요한가**: SSD가 하드웨어 레벨 Atomic Write(예: Fusion-io, 일부 NVMe)를 지원하면 `innodb_doublewrite=OFF`로 쓰기 증폭(Write Amplification)을 절반으로 줄일 수 있지만, 지원 여부를 모르고 끄면 전원 장애 한 번에 테이블스페이스가 손상되어 복구 불가능한 데이터 손실로 이어진다.

### Database Tip 2: Hibernate `Statement Batching`과 `GenerationType.IDENTITY`의 치명적 충돌 — `batch_size=50`을 설정해도 AUTO_INCREMENT를 쓰는 순간 배치 INSERT가 "조용히 비활성화"되는 함정

`hibernate.jdbc.batch_size=50`을 켜도 `@GeneratedValue(strategy = IDENTITY)`를 쓰는 엔티티는 INSERT 배치가 적용되지 않는다. IDENTITY 전략은 DB가 ID를 할당해야 영속성 컨텍스트에 엔티티를 등록할 수 있고, Hibernate는 생성된 ID를 받아내려고 매 `persist()` 호출마다 즉시 INSERT를 날려 `getGeneratedKeys()`를 호출해야 하기 때문이다. 대량 INSERT가 필요하면 `SEQUENCE`(PostgreSQL/Oracle) 전략으로 바꾸고 `allocationSize`를 50 이상으로 설정해 미리 ID 풀을 가져오게 해야 진짜 JDBC 배치가 작동한다.

```java
// ❌ MySQL + IDENTITY: 10,000건 = INSERT 10,000번 라운드트립
@GeneratedValue(strategy = GenerationType.IDENTITY)

// ✅ PostgreSQL + SEQUENCE: 10,000건 = INSERT 200번 배치
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "user_seq")
@SequenceGenerator(name = "user_seq", sequenceName = "user_seq", allocationSize = 50)
```

> 💡 **왜 중요한가**: "`batch_size`를 설정했는데 왜 여전히 INSERT가 N번 나가지?"의 90%는 IDENTITY 전략 때문이며, `show_sql` 로그에서 쿼리가 한 줄처럼 보여도 실제 네트워크 라운드트립은 N번 발생한다 — MySQL을 쓸 수밖에 없다면 대량 INSERT 구간만 JdbcTemplate의 `batchUpdate`로 우회하는 것이 현실적이다.
