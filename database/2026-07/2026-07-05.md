### PostgreSQL `pg_stat_statements` — 실제 워크로드의 무거운 쿼리를 통계로 잡아내기

`pg_stat_statements` 확장을 활성화하면 정규화된 쿼리 텍스트별로 `total_exec_time`, `calls`, `mean_exec_time`, `rows`가 누적되어, "느낌상 느린 쿼리"가 아니라 실제 부하 상위 쿼리를 정량적으로 골라낼 수 있다. `total_exec_time DESC` 정렬로 누적 시간이 큰 순서, `mean_exec_time DESC`로 개별 응답이 느린 순서를 각각 봐야 하며 — 자주 불리는 짧은 쿼리와 가끔 불리는 무거운 쿼리는 튜닝 우선순위가 다르다.

```sql
CREATE EXTENSION pg_stat_statements;
-- postgresql.conf: shared_preload_libraries = 'pg_stat_statements'

SELECT queryid, calls, total_exec_time, mean_exec_time, rows,
       substring(query, 1, 80) AS query_preview
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

-- 튜닝 후 재측정을 위해 통계 리셋
SELECT pg_stat_statements_reset();
```

> 💡 **왜 중요한가**: 감이 아닌 누적 통계로 튜닝 대상을 정하면 가장 큰 병목부터 순서대로 해결할 수 있어 성능 개선의 ROI가 극대화된다.

### MySQL `ANALYZE TABLE` — 옵티마이저가 참조하는 통계를 최신화해 잘못된 실행 계획 막기

InnoDB는 인덱스 카디널리티·데이터 분포 통계를 기반으로 실행 계획을 세우는데, 대량 INSERT/DELETE 후 통계가 오래되면 옵티마이저가 잘못된 인덱스를 고르거나 조인 순서를 뒤집어 쿼리가 급격히 느려진다. `ANALYZE TABLE`로 통계를 수동 갱신하면 `EXPLAIN`의 `rows` 예측값이 실제와 가까워지고 옵티마이저가 다시 올바른 계획을 세운다.

```sql
-- 통계 갱신 (짧은 메타데이터 락만 걸림, 데이터 재작성 없음)
ANALYZE TABLE orders, order_items;

-- 인덱스별 카디널리티 확인
SHOW INDEX FROM orders;

-- 자동 갱신 설정 확인 — 기본 ON이지만 큰 테이블에서는 샘플이 부족할 수 있음
SHOW VARIABLES LIKE 'innodb_stats_auto_recalc';
SHOW VARIABLES LIKE 'innodb_stats_persistent_sample_pages';  -- 기본 20, 큰 테이블은 상향
```

> 💡 **왜 중요한가**: "어제까지 잘 돌던 쿼리가 오늘 갑자기 느려졌다"의 상당수는 통계 노후화가 원인이라, `ANALYZE TABLE` 한 줄로 실행 계획이 원복되는 경우가 많다.
