### 1. Spring Boot의 `@Async`는 **같은 클래스 내부 호출(self-invocation)에서 비동기로 동작하지 않는다** — 프록시를 거치지 않는 `this.asyncMethod()` 호출은 그냥 호출한 스레드에서 동기적으로 실행되어, "분명히 백그라운드로 보냈는데" 왜 API 응답이 느려지는지 알 수 없는 미궁에 빠진다

`@Async`는 `@Transactional`과 동일하게 Spring AOP 프록시 기반으로 동작하기 때문에, 외부에서 빈을 주입받아 호출할 때만 비동기 스레드 풀로 작업이 디스패치된다. 더 치명적인 건, `@EnableAsync`를 선언하지 않으면 `@Async`가 **아무 오류도 없이 조용히 무시된다**는 점이다. 그리고 반환 타입이 `void`인 `@Async` 메서드에서 터진 예외는 호출자에게 전파되지 않고 그냥 로그에만 찍힌 뒤 삼켜지므로, 비동기 작업이 실패해도 아무도 모르는 상태가 된다.

> 💡 **왜 중요한가**: "비동기로 처리해서 빠를 거야"라고 믿고 짠 코드가 실제로는 동기 실행되거나 에러가 조용히 사라져버리면, 성능 문제와 데이터 유실을 동시에 겪게 된다.

### 2. Spring Boot의 `Jackson ObjectMapper`는 **기본적으로 알 수 없는 JSON 필드를 만나면 역직렬화에 실패한다** — `FAIL_ON_UNKNOWN_PROPERTIES`가 기본 `true`이기 때문에, 외부 API가 응답에 새 필드 하나만 추가해도 네 서비스가 500을 뱉으며 쓰러진다

Spring Boot는 `application.properties`의 `spring.jackson.deserialization.fail-on-unknown-properties=false`로 이 동작을 바꿀 수 있지만, 많은 팀은 이 기본값을 모른 채 운영에 배포한다. 반대로 내부 API 간 통신에서는 이 옵션을 켜두는 게 오히려 안전장치가 되기도 한다 — 오타난 필드가 조용히 무시되는 것보다 즉시 터지는 게 나을 때가 있다. 중요한 건 **"외부에서 들어오는 JSON"과 "내부에서 주고받는 JSON"에 서로 다른 정책을 적용해야 한다는 것**이다. 외부 API 클라이언트용 `ObjectMapper`는 관대하게, 내부 계약용은 엄격하게.

> 💡 **왜 중요한가**: 네가 제어할 수 없는 외부 API의 "작은 스펙 변경"이 네 서비스의 장애로 번지는 걸 막으려면, 역직렬화 정책을 의식적으로 설계해야 한다.
