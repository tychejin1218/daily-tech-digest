### 1. `Collectors.groupingBy` 없이 `Map.Entry.comparingByValue()`로 빈도 순 Top-N 뽑기

`Map<K, Long>` 형태의 빈도 집계 결과에서 상위 N개를 뽑을 때 커스텀 `Comparator<Map.Entry<K, Long>>`를 매번 새로 쓰는 관성을 벗어나자. `Map.Entry.comparingByValue()`는 값 기준 자연 순서 비교자를, `.reversed()`와 조합하면 내림차순 정렬을 한 줄에 얻는다. `stream().sorted(Map.Entry.comparingByValue(Comparator.reverseOrder())).limit(N)` 파이프라인으로 익명 람다 없이 Top-N 추출이 완결된다.

```java
// Before: 매번 comparator 재작성
list.entrySet().stream()
    .sorted((a, b) -> Long.compare(b.getValue(), a.getValue()))
    .limit(10)
    .toList();

// After: 표준 팩토리 활용
list.entrySet().stream()
    .sorted(Map.Entry.<String, Long>comparingByValue(Comparator.reverseOrder()))
    .limit(10)
    .toList();
```

> 💡 **왜 중요한가**: `Map.Entry`의 정적 팩토리 비교자는 JDK 표준이라 팀원 누구나 의도를 즉시 읽고, 제네릭 타입 힌트만 붙이면 `null` 안전성과 자연 순서 계약까지 무료로 얻는다.

### 2. `Files.mismatch(Path, Path)`로 두 파일의 첫 차이 위치를 O(1) 코드로 찾기 (Java 12 정식)

두 파일이 같은지 비교할 때 전체를 `Files.readAllBytes()`로 읽어 `Arrays.equals()`로 돌리던 관성은 대용량에서 힙 부담이 크다. `Files.mismatch(path1, path2)`는 스트리밍 방식으로 바이트를 순차 비교하며, 완전히 같으면 `-1L`을, 다르면 **첫 번째 다른 바이트의 오프셋**을 반환한다. 파일 크기가 달라도 즉시 감지하며, 디스크 I/O 버퍼링까지 JDK가 최적화해준다.

```java
// Before: 전체 로드 후 비교 (수백 MB면 OOM 위험)
byte[] a = Files.readAllBytes(p1);
byte[] b = Files.readAllBytes(p2);
boolean same = Arrays.equals(a, b);

// After: 스트리밍 비교 + 차이 위치까지
long offset = Files.mismatch(p1, p2);
if (offset == -1L) {
    // 완전히 동일
} else {
    log.warn("파일 불일치, 첫 차이 오프셋: {}", offset);
}
```

> 💡 **왜 중요한가**: 로그 파일·바이너리 아티팩트·백업 검증 같은 실무 시나리오에서 "다른가?"뿐 아니라 "어디서부터 다른가?"를 힙 폭발 없이 표준 API 한 줄로 얻는다.
