### 1. `Collectors.mapping(mapper, downstream)`으로 `groupingBy` 이후 `map().collect()` 이중 스트림 관성 벗어나기 (Java 8 정식)

`groupingBy`로 묶은 뒤 각 그룹의 값을 특정 필드로 변환하고 싶을 때, 흔히 `entrySet().stream().collect(toMap(..., v -> v.stream().map(...).toList()))` 같은 이중 스트림으로 후처리한다. `Collectors.mapping(User::getName, toList())`를 다운스트림에 넣으면 그룹핑과 매핑이 한 번의 순회로 끝나며, 중간 컬렉션도 만들지 않는다.

```java
// Before: 그룹핑 후 다시 스트림 열어서 매핑
Map<Dept, List<String>> byDept = users.stream()
    .collect(groupingBy(User::getDept))
    .entrySet().stream()
    .collect(toMap(Map.Entry::getKey,
        e -> e.getValue().stream().map(User::getName).toList()));

// After: 다운스트림 컬렉터로 한 번에
Map<Dept, List<String>> byDept = users.stream()
    .collect(groupingBy(User::getDept,
        mapping(User::getName, toList())));

// 조합도 자유롭다: 부서별 이름 Set
Map<Dept, Set<String>> uniqueNames = users.stream()
    .collect(groupingBy(User::getDept,
        mapping(User::getName, toSet())));
```

> 💡 **왜 중요한가**: 다운스트림 컬렉터를 조립하는 감각이 있어야 `filtering`·`flatMapping`·`teeing` 같은 Java 9+ 컬렉터를 자연스럽게 쓸 수 있다. `mapping`은 그 조립의 가장 기본 블록이다.

### 2. `CompletableFuture.orTimeout(duration)`으로 `.get(timeout)` 블로킹·`whenComplete` 수동 취소 관성 벗어나기 (Java 9 정식)

비동기 작업에 타임아웃을 걸 때 `future.get(3, SECONDS)`는 호출 스레드를 블로킹하고, `ScheduledExecutorService`로 별도 타이머를 걸어 수동 취소하는 코드는 누수 위험이 크다. `orTimeout(3, SECONDS)`는 지정 시간 내 완료되지 않으면 해당 Future를 `TimeoutException`으로 완료시키며, 논블로킹 체이닝을 유지한다. `completeOnTimeout(default, 3, SECONDS)`는 예외 대신 기본값으로 완료한다.

```java
// Before: 블로킹 + 별도 스케줄러 관리
try {
    return future.get(3, TimeUnit.SECONDS);
} catch (TimeoutException e) {
    future.cancel(true);
    return fallback;
}

// After: 논블로킹 + 자동 완료
CompletableFuture<Order> result = orderClient.fetchAsync(id)
    .orTimeout(3, TimeUnit.SECONDS)
    .exceptionally(ex -> ex instanceof TimeoutException ? Order.EMPTY : rethrow(ex));

// 기본값 fallback이 더 자연스러운 경우
CompletableFuture<List<Item>> items = catalogClient.searchAsync(q)
    .completeOnTimeout(List.of(), 500, TimeUnit.MILLISECONDS);
```

**주의**: `orTimeout`은 원본 작업을 실제로 중단하지 않는다. HTTP 호출·DB 커넥션 등 리소스를 쥔 작업은 별도의 취소 신호(예: `HttpRequest.timeout()`)를 함께 걸어야 유휴 스레드가 남지 않는다.

> 💡 **왜 중요한가**: 타임아웃 하나 걸겠다고 `ScheduledExecutorService`를 손수 만드는 순간 스레드 누수·취소 경합 버그가 시작된다. 표준 API로 끝날 일을 프레임워크급으로 키우지 않는 것이 실무 안정성의 첫걸음이다.
