### PostgreSQL `LATERAL JOIN` — 행마다 서브쿼리를 실행해 "그룹별 상위 N개"를 우아하게 뽑기

일반 `JOIN`은 두 테이블을 데카르트 곱한 뒤 필터링하지만, `LATERAL`은 왼쪽 테이블의 각 행을 참조해 오른쪽 서브쿼리를 반복 실행한다. 특히 "사용자별 최근 주문 3개", "카테고리별 최상위 상품" 같은 top-N-per-group 쿼리를 윈도우 함수보다 직관적이고 빠르게 처리할 수 있다.

```sql
-- 각 사용자의 최근 주문 3건씩 조회
SELECT u.id, u.name, o.order_id, o.created_at
FROM users u
CROSS JOIN LATERAL (
    SELECT order_id, created_at
    FROM orders
    WHERE user_id = u.id
    ORDER BY created_at DESC
    LIMIT 3
) o;
```

`orders(user_id, created_at DESC)` 인덱스가 있다면, 각 사용자당 인덱스 스캔 3건만 발생해 `ROW_NUMBER() OVER (PARTITION BY ...)` 방식보다 훨씬 적은 I/O로 끝난다.

> 💡 **왜 중요한가**: "그룹별 상위 N개"를 인덱스 스캔만으로 처리해 윈도우 함수의 전체 정렬 비용을 피할 수 있다.

### JPA `EntityGraph` — 쿼리별로 페치 전략을 동적으로 바꿔 N+1과 과다 조회를 동시에 잡기

엔티티에 `FetchType.EAGER`를 박아버리면 모든 쿼리에서 강제로 조인이 일어나고, `LAZY`만 쓰면 N+1이 터진다. `@EntityGraph`는 특정 쿼리에서만 필요한 연관관계를 선언적으로 페치하도록 지시해, 리포지토리 메서드마다 최적의 조회 전략을 지정할 수 있다.

```java
public interface OrderRepository extends JpaRepository<Order, Long> {

    @EntityGraph(attributePaths = {"customer", "items", "items.product"})
    @Query("SELECT o FROM Order o WHERE o.status = :status")
    List<Order> findWithDetailsByStatus(@Param("status") OrderStatus status);

    // 목록 화면은 연관관계 없이 가볍게
    List<Order> findByCustomerId(Long customerId);
}
```

`attributePaths`에 지정된 연관관계는 `LEFT JOIN FETCH`로 변환되며, 컬렉션이 여러 개면 `MultipleBagFetchException`이 발생하니 `Set`을 사용하거나 별도 쿼리로 나눠야 한다.

> 💡 **왜 중요한가**: 엔티티 매핑을 바꾸지 않고도 쿼리 단위로 페치 전략을 조정해 N+1과 과다 조인을 상황에 맞게 최적화할 수 있다.
