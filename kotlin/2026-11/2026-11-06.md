### 1. Inline Function: 람다의 "숨은 비용"을 제로로 만드는 컴파일러 치트키

Kotlin의 람다는 편리하지만, 매 호출마다 `Function` 객체가 힙에 생성되는 숨은 비용이 있다. `inline` 키워드를 붙이면 컴파일러가 함수 본문과 람다를 호출 지점에 그대로 복사해 넣어 객체 생성 없이 바이트코드가 전개된다. 표준 라이브러리의 `let`, `run`, `apply`, `forEach`, `map`이 모두 inline인 이유가 바로 이것 — "편한 추상화는 공짜여야 한다"는 Kotlin의 철학이다.

```kotlin
// ❌ 일반 고차 함수: 호출 시마다 Function0 객체 할당
fun measure(block: () -> Unit) {
    val start = System.nanoTime()
    block()
    println("${System.nanoTime() - start}ns")
}

// ✅ inline: 바이트코드에 본문이 "복사"되어 객체 할당 제로
inline fun measureFast(block: () -> Unit) {
    val start = System.nanoTime()
    block()
    println("${System.nanoTime() - start}ns")
}

// 추가 혜택 1: 람다 안에서 non-local return 가능
inline fun List<Int>.findFirstEven(): Int? {
    forEach { if (it % 2 == 0) return it }  // 바깥 함수에서 return!
    return null
}

// 추가 혜택 2: reified로 제네릭 타입 정보를 런타임에 보존
inline fun <reified T> Any.castOrNull(): T? = this as? T

val user = json.castOrNull<User>()  // Java였다면 Class<T> 파라미터 필요
```

**주의할 트레이드오프**:

| 상황 | inline 적절성 |
|------|--------------|
| 함수 본문이 1~3줄 + 람다 파라미터 | ✅ 최적 |
| 함수 본문이 20줄 이상 | ❌ 호출처마다 복사되어 바이트코드 비대화 |
| 람다를 변수에 저장하거나 다른 함수로 전달 | ❌ `noinline` 필요 |
| 람다 파라미터가 없음 | ❌ inline 효과 없음, 경고 발생 |

> 💡 **왜 중요한가**: Kotlin의 "함수형 스타일이 Java 수동 루프만큼 빠르다"는 성능 공약을 떠받치는 핵심 메커니즘이 inline이다 — 알고 쓰면 추상화 비용을 걱정하지 않아도 된다.

### 2. by lazy vs lateinit: "언제 초기화할 것인가"의 두 가지 답

Kotlin은 Java의 `null 체크 지옥`을 제거하기 위해 non-null 타입을 기본으로 삼지만, 실제로는 "생성자 시점엔 값이 없고, 나중에 채워지는" 프로퍼티가 흔하다. `by lazy`는 "최초 접근 시 한 번 계산"하는 지연 초기화이고, `lateinit`은 "곧 외부에서 주입될 테니 지금은 비워두기"의 명시적 약속이다. 둘을 혼동하면 쓸데없는 synchronized 비용을 치르거나 `UninitializedPropertyAccessException`을 만난다.

```kotlin
class UserService(private val repo: UserRepository) {

    // ✅ by lazy: 비싼 계산을 처음 쓸 때까지 미룸, 결과는 캐싱
    val adminList: List<User> by lazy {
        println("adminList 계산 중...")  // 최초 접근 시 딱 한 번
        repo.findAll().filter { it.role == "ADMIN" }
    }

    // ✅ lateinit: DI나 @BeforeEach에서 주입될 값
    @Autowired
    lateinit var mailer: MailService
}

val service = UserService(repo)
service.adminList  // "adminList 계산 중..." 출력
service.adminList  // 아무 출력 없음 — 캐시 반환
```

**핵심 비교표**:

| 특성 | `by lazy` | `lateinit var` |
|------|-----------|----------------|
| 변경 가능성 | `val` 전용 (불변) | `var` 전용 (가변) |
| 초기화 시점 | 최초 접근 시 자동 | 외부에서 수동 할당 |
| 사용 가능 타입 | 모든 타입 (primitive 포함) | non-null 참조 타입만 (Int, Boolean 불가) |
| 스레드 안전성 | 기본 `SYNCHRONIZED` (안전) | 없음 (수동 보장 필요) |
| 적합한 상황 | 비싼 연산 결과, 설정 객체 | DI, 테스트 fixture, Android `findViewById` |

**실무에서 자주 놓치는 함정**:

```kotlin
// ❌ Spring 생성자 주입이 가능한데 lateinit field injection
class OrderService {
    @Autowired lateinit var repo: OrderRepository  // 테스트 어려움
}

// ✅ 생성자 주입 — final 보장 + 테스트 용이
class OrderService(private val repo: OrderRepository)

// ❌ lazy인데 멀티스레드가 전혀 아닌 상황
val config: AppConfig by lazy { loadConfig() }  // synchronized 오버헤드

// ✅ 단일 스레드 확정이면 NONE 모드로
val config: AppConfig by lazy(LazyThreadSafetyMode.NONE) { loadConfig() }
```

> 💡 **왜 중요한가**: non-null 타입 시스템의 혜택을 포기하지 않으면서도 "생성자 시점엔 값이 없다"는 현실을 다루는 두 가지 관용구 — 상황에 맞게 골라야 성능과 안전성을 모두 지킨다.
