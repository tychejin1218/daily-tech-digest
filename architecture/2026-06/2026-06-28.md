### Service Discovery — "IP는 죽는다"는 전제에서 다시 짓는 서비스 간 통신

Lv3까지의 세계에서 우리는 서비스 A가 서비스 B를 부를 때 "B의 주소는 알고 있다"고 암묵적으로 가정했다. 모놀리스 시절엔 in-process call이라 주소가 필요 없었고, 초기 MSA에서도 `application.yml`에 `payment-service.url=http://10.0.1.15:8080`처럼 박아두면 그럭저럭 돌아갔다. 그러나 Kubernetes 위에서 Pod가 초당 여러 번 죽고 살아나는 세계, Auto Scaling으로 인스턴스 수가 3에서 300으로 요동치는 세계에 오면 그 가정은 **첫 배포 이후 30초** 만에 무너진다. Service Discovery는 이 붕괴에 대한 답이다 — "누가 살아있고, 어디에 있는가"를 **런타임에** 알아내는 메커니즘.

#### 문제의 본질: 정적 설정 vs 동적 현실

전통적인 아키텍처의 서비스 간 통신은 이랬다.

```
[Order Service] --(config.url=http://payment:8080)--> [Payment Service]
                                                        인스턴스 1개, IP 고정
```

이 모델에는 세 가지 숨은 가정이 있다.

1. Payment의 IP/포트는 잘 바뀌지 않는다
2. Payment 인스턴스는 하나이거나, 앞에 하드웨어 L4 로드밸런서가 있다
3. Payment가 죽으면 사람이 알아채고 대응한다

클라우드 네이티브 환경에서 이 세 가정은 전부 거짓이다. Pod는 노드 장애·롤링 업데이트·HPA 스케일 이벤트로 IP가 바뀌고, 인스턴스는 3~300개 사이를 오가며, 죽는 건 사람이 아니라 kubelet이 감지해야 한다. 그래서 필요한 것이 "서비스 이름 → 현재 살아있는 인스턴스 목록"을 지속적으로 유지·조회할 수 있는 **레지스트리**와, 그것을 참조해 실제 호출을 라우팅하는 **클라이언트/프록시**다.

#### 두 가지 축: Client-side vs Server-side Discovery

Service Discovery는 크게 두 패턴으로 갈린다. 이 구분은 시니어가 반드시 머릿속에 넣고 있어야 한다 — 아키텍처 선택의 갈림길이기 때문이다.

```
[Client-side Discovery]                  [Server-side Discovery]

  ┌─────────┐                              ┌─────────┐
  │  Client │                              │  Client │
  └────┬────┘                              └────┬────┘
       │ 1. Query registry                      │ 1. Call
       ▼                                        ▼
  ┌─────────┐                              ┌──────────────┐
  │Registry │                              │Load Balancer │◀──┐
  │(Eureka) │                              │  / Router    │   │ query
  └────┬────┘                              └──────┬───────┘   │
       │ 2. Instance list                        │ 2. Forward  │
       │    [10.0.1.5, 10.0.1.7]                │             │
       ▼                                        ▼             │
  ┌─────────┐  ┌─────────┐            ┌─────────┐ ┌─────────┐ │
  │ Svc B#1 │  │ Svc B#2 │            │ Svc B#1 │ │ Svc B#2 │ │
  └─────────┘  └─────────┘            └─────────┘ └─────────┘ │
   ▲ 3. Direct call                                           │
   └──────                                                    │
                                        ┌──────────┐          │
                                        │ Registry │──────────┘
                                        │  (etcd)  │
                                        └──────────┘
```

**Client-side (Netflix Eureka + Ribbon 조합의 시대)**: 클라이언트가 레지스트리에서 인스턴스 목록을 통째로 받아와, 자기 프로세스 안에서 로드밸런싱 알고리즘을 돌린다. 홉이 하나 줄어드니 latency가 낮고, 클라이언트가 각 인스턴스의 상태(recent failures, latency)를 관찰해 지능적인 라우팅이 가능하다. 대신 **모든 언어에 SDK가 필요**하고, 레지스트리 프로토콜이 언어별로 결합된다. Polyglot MSA에선 지옥이다.

**Server-side (Kubernetes Service, AWS ALB, Consul + Envoy)**: 클라이언트는 안정적인 가상 엔드포인트 하나(`payment-service`)만 안다. 실제 라우팅은 그 뒤의 프록시/로드밸런서가 담당한다. 언어 중립적이고 클라이언트 코드가 단순해지지만, 홉이 하나 늘고 프록시가 SPOF가 될 수 있다.

Kubernetes를 쓰고 있다면 사실상 **Server-side가 기본값**이다. `Service` 리소스가 kube-proxy를 통해 iptables/IPVS 룰을 관리하고, `payment-service.default.svc.cluster.local`이라는 이름을 ClusterIP로, 다시 살아있는 Pod들의 IP로 풀어낸다. 우리가 별도로 Eureka를 안 세워도 이미 서비스 디스커버리는 돌아가고 있다.

#### 레지스트리에 무엇이 저장되는가

이름 하나에 여러 인스턴스가 매달리는 구조라, 레지스트리는 단순한 DNS가 아니다. 최소한 이런 정보가 필요하다.

- **Instance ID / IP:Port**
- **Health status** (healthy / unhealthy / draining)
- **Metadata** (version=v2, region=ap-northeast-2, weight=10)
- **Last heartbeat timestamp**

특히 **Health check**의 방식이 서비스 디스커버리의 신뢰성을 좌우한다. 두 가지 방식이 있다.

- **Self-registration + Heartbeat**: 인스턴스가 시작 시 자기를 등록하고, 주기적으로 "나 살아있어" 신호를 보낸다 (Eureka 방식). 프로세스가 좀비가 되어도 heartbeat만 나가면 살아있는 것으로 판정되는 문제가 있다.
- **Third-party health check**: 외부 컴포넌트가 `/health` 엔드포인트를 실제로 호출해 확인한다 (Kubernetes readinessProbe 방식). 더 정확하지만 부하가 더 든다.

시니어라면 여기서 한 층 더 파고들어야 한다 — `readinessProbe`와 `livenessProbe`의 차이. Readiness가 "지금 트래픽 받을 준비 됐어?"라면 Liveness는 "너 재시작해야 해?"이다. 이 둘을 헷갈리게 설정한 클러스터는 배포 중 대량 502를 뿌려대거나, DB 커넥션이 잠깐 튄 것 때문에 애먼 Pod들이 우수수 재시작되는 참사를 겪는다.

#### 실제 사례로 보는 선택

- **Netflix (2010년대 초반)**: Eureka를 자체 개발했다. 당시 AWS엔 쓸 만한 서비스 디스커버리가 없었고, 수천 개의 마이크로서비스가 EC2 인스턴스 위에서 돌아가야 했다. Client-side를 선택한 이유는 **AZ-aware routing** — 같은 AZ 인스턴스를 우선 부르는 로직을 클라이언트에 심을 수 있었기 때문이다. AZ 간 데이터 전송비와 latency가 컸던 시절의 판단.
- **HashiCorp Consul**: 멀티 데이터센터·멀티 클라우드 환경을 정면 겨냥. Gossip 프로토콜로 노드 상태를 전파하고, DNS와 HTTP API를 동시에 제공한다. Kubernetes 밖 워크로드(VM, 베어메탈)와 클러스터를 섞어 쓰는 조직들이 애용한다.
- **Kubernetes 내장 서비스**: 대부분의 신규 프로젝트가 별도 레지스트리를 안 세우고 이걸 그대로 쓴다. `Service` + CoreDNS 조합으로 90%의 요구사항이 충족되고, 부족한 부분(가중치 기반 라우팅, 세밀한 헬스체크, mTLS)은 Istio/Linkerd로 얹는다.
- **AWS Cloud Map / ECS Service Discovery**: EKS를 안 쓰고 ECS/Lambda 조합을 쓰는 조직들의 선택지. Route53과 통합돼 DNS 기반으로 동작한다.

#### 트레이드오프의 진짜 지점들

**1. CAP에서 어디를 포기할 것인가.** 레지스트리 자체가 분산 시스템이다. Eureka는 **AP**를 택했다 — 파티션이 생겨도 각 노드가 자기가 아는 인스턴스 목록을 계속 제공한다. 대신 노드 간 정보가 잠깐씩 불일치할 수 있다. etcd/Consul은 **CP**를 택했다 — Raft로 강한 일관성을 보장하지만, 쿼럼이 깨지면 쓰기가 불가능해진다. Netflix의 선택은 "잘못된 인스턴스 목록을 잠깐 받는 게, 아예 목록을 못 받는 것보다 낫다"였다. 결제 시스템이라면 반대의 판단을 내릴 수도 있다.

**2. 캐싱과 stale data.** 클라이언트가 매번 레지스트리를 조회하면 레지스트리가 병목이 된다. 그래서 대부분 클라이언트 측에 캐시를 둔다. 문제는 인스턴스가 죽었는데 캐시가 30초 동안 살아있다고 착각하는 경우 — 이래서 Circuit Breaker와 retry가 반드시 함께 와야 한다. Service Discovery만으로는 실패를 완전히 숨길 수 없다.

**3. Discovery vs Load Balancing의 경계.** Client-side Discovery는 로드밸런싱까지 클라이언트 몫이다. Round-robin, weighted, least-connection, latency-based… 어떤 걸 쓸 것인가? 그리고 이걸 각 언어별 SDK에 다 구현할 것인가? 이 질문에 지친 조직들이 결국 **Service Mesh**로 넘어간다 — 사이드카(Envoy)가 discovery와 LB를 모두 흡수해서 애플리케이션 코드에서 그 관심사를 아예 뽑아내 버린다.

#### 언제 쓰고, 언제 쓰지 말아야 하는가

**써야 할 때**
- 인스턴스가 동적으로 뜨고 지는 환경 (K8s, ECS, Nomad, AutoScaling Group)
- 서비스 수가 10개를 넘어가는 시점 — 그 이하는 하드코딩된 URL로도 살 만하다
- 롤링 배포·카나리·블루그린 등 배포 전략이 필요한 조직

**안 써야 할 때 (혹은 오버엔지니어링인 때)**
- 서비스가 2~3개인 초기 스타트업 — DNS와 정적 설정으로 충분하다. Consul 클러스터 운영 비용이 얻는 것보다 크다.
- 완전히 정적인 인프라(온프레미스 고정 IP) — DNS + L4 스위치가 더 단순하고 안정적이다.
- 이미 Kubernetes를 쓰는데 별도로 Eureka를 세우려는 경우 — 이건 대부분 안티패턴이다. 두 개의 discovery source를 두면 어떤 게 진실인지 아무도 모르게 된다.

시니어 관점에서 가장 중요한 통찰은 이것이다. **Service Discovery는 그 자체로 목적이 아니라, "인스턴스가 언제든 죽고 살아난다"는 클라우드 네이티브의 전제를 소프트웨어로 표현한 결과물이다.** 이걸 도입한다는 건 코드에 한 줄 추가한다는 뜻이 아니라, 애플리케이션이 "특정 인스턴스에 애착을 갖지 않는다"는 상태 비저장(stateless) 설계를 관철하겠다는 조직적 선언이다. 그래서 세션 스티키니스, 로컬 캐시, 인스턴스별 파일 저장 같은 것들이 이 선언과 충돌하는 순간, 아무리 정교한 레지스트리를 세워도 시스템은 결국 무너진다.

> 💡 **왜 중요한가**: Service Discovery는 "주소를 아는" 정적 세계에서 "이름만 알고 나머지는 런타임에 알아내는" 동적 세계로의 이주 티켓이며, 이 이주 없이는 Kubernetes·Auto Scaling·무중단 배포 어느 것도 실체 있게 작동하지 않는다.
